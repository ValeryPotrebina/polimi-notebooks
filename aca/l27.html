Virtual memory in one lesson, and VIPT: start the cache before the TLB answers

After this lesson you will translate a virtual address into a physical one by hand, tell a TLB miss from a page fault, and decide with one inequality, cache size / associativity ≤ page size, whether an L1 cache can start its lookup before the TLB answers without synonym problems.

Print the address of a variable in a running program and you get something like 0x7FFE_1234, the notes' Example 19 (p. 358). That is not where the byte sits in RAM: it is a virtual address, a name the operating system made up for your process. Yet its last three hex digits, 234, are true: they are also the last three digits of the RAM location that holds the byte.

Second fact. For about a decade Intel's L1 data cache was 32 KB with 8 ways. When it finally grew, in 2019, it became 48 KB with 12 ways. Divide: 32 / 8 = 48 / 12 = 4 KB, exactly the size of a page.

Why should a cache, a block of hardware, take its shape from a page, a notion of the operating system? Make a guess and keep it. By the end of the lesson you will derive the answer in one line, from the first fact.

Pages, frames and the page table

Virtual memory is an "OPTIONAL TOPIC" on the week-10 course page, but it is on the professor's exam-topic list. The notes treat it only as a refresher before VIPT (pp. 357–359).

Every program believes it owns one large, continuous address space of \(2^{32}\) or \(2^{64}\) bytes; real RAM is finite and fragmented (p. 357). Paging reconciles the two: the operating system and the hardware cut both spaces into blocks of one fixed size and keep, for every program, a map from its blocks to real ones.

The notes picture a city of identical hotel buildings, each with rooms 0 to 4095 (p. 358). Your booking names a building and a room; reception may move you to another building, but it never changes the room number. Room 0x234 stays room 0x234.

Virtual page — a block of the virtual address space, the program's view. All pages have one size, commonly 4 KB (2 MB and 1 GB exist too); each process has its own set, which isolates it from the others (p. 357).

Physical page, or frame — a block of RAM of the same size. Several virtual pages, of different processes or of one, may map to the same frame: shared memory.

Page table — the map of one process, kept in memory. It is indexed by the virtual page number (VPN); each entry holds the physical frame number (PFN) and some flags.

An address therefore has two fields: the low bits are the page offset, the byte inside the page (12 bits for pages of 4 KB = \(2^{12}\) bytes), and the bits above it are the page number. Translation replaces the page number and copies the offset:

\[ \text{VA} = \text{VPN} \mid \text{page offset} \] \[ \text{PA} = \text{PFN} \mid \text{page offset} \] \[ \text{PA} = \text{PFN} \times P + \text{page offset} \]
VPN
virtual page number, the high bits of the virtual address: 20 bits for 32-bit addresses and 4 KB pages
PFN
physical frame number, read from the page table; the notes also write PPN, physical page number (pp. 360–362)
\(P\)
page size; the page offset has \(\log_2 P\) bits and is the same in both addresses
A hex digit is four bits, so a 12-bit offset is exactly the last three hex digits.

Example 19 (p. 358), step by step. In the 32-bit virtual address 0x7FFE_1234 (the underscore only groups the hex digits by four), the last three digits are the offset, 0x234, and the five before them the VPN, 0x7FFE1. The page table maps VPN 0x7FFE1 to PFN 0x01AB0. Put the frame number in front of the unchanged offset: PA = 0x01AB0 | 0x234 = 0x01AB_0234 = 0x01AB0 × 4096 + 0x234 (Fig. 1).

"Virtual Page Number (VPN) = Physical Frame Number (PFN) + flags"

A page-table entry is indexed by the VPN and contains the PFN and the flags: PT[VPN] = (PFN, flags).

In Example 19 the VPN is 0x7FFE1 and the PFN 0x01AB0: no flags make them equal. Like a cache index (lesson 23), the VPN selects the entry; it is not a value stored in it.

Why bother? Hennessy & Patterson (Appendix B.4; not in the notes) list four gains: capacity, since RAM becomes a cache for the disk and a program may exceed it; protection, since a process reaches only the frames its table maps, with permissions checked on every access; relocation, since a program runs wherever its frames are; and sharing: two page tables may point to one frame — keep that one for section 4.

Virtual memory is one more level of the hierarchy, so the four questions of lesson 23 apply, with pages for blocks and frames for lines. Every answer follows from one number: a miss at this level, a page fault, goes to the disk and costs millions of cycles.

Why not one flat page table?

A flat table for 32-bit addresses and 4 KB pages has \(2^{20}\) entries, 4 MB per process at 4 bytes each, mostly for pages never touched. Real systems build a tree of small tables indexed by fields of the VPN (x86-64: four levels of 9 bits, \(4 \times 9 + 12 = 48\) bits), and a TLB miss walks several dependent reads (Hennessy & Patterson; not in the notes).

Translation replaces the page number and copies the page offset: with 4 KB pages the last 12 bits, three hex digits, are the same in the virtual and in the physical address.

The TLB: a cache for translations

The page table lives in memory, so reading it first would add a memory access to every load, store and instruction fetch (p. 359). The cure is the idea of this whole chapter: keep the recent entries in a small, fast memory.

Translation lookaside buffer (TLB) — "a small, fast cache that stores the most recent virtual-to-physical address translations" (p. 359). Its tag is the VPN; its data are the PFN and the flags of the page-table entry.

On every access the CPU generates a virtual address and checks the TLB (p. 359). A TLB hit gives the physical address at once; a TLB miss walks the page table in memory, slowly, and inserts the result into the TLB. In the notes' hotel, the TLB is a post-it note with your current room key, so you need not queue at reception every time.

The textbook picture, not in the notes: a TLB has tens of entries, fully or highly associative, often split into instruction and data TLBs behind a larger second-level TLB, and answers in about a cycle; its entries carry the protection bits, checked on every access. The memory it covers, its reach, is entries × page size: 64 entries × 4 KB = 256 KB. A miss is refilled by a hardware page walker (x86, ARM) or a software handler (MIPS), in tens of cycles.

Keep two events apart. A TLB miss means only that the translation is not in the small cache: usually the page is in RAM, and the walk finds a valid entry. A page fault means the entry is invalid: the page is not in RAM at all. The hardware raises an exception; the operating system reads the page from the disk into a free frame, sets the valid bit and restarts the instruction — millions of cycles, and a restart that needs precise exceptions (lesson 17).

One process, seven accesses: TLB, page table, page fault

A process with 32-bit virtual addresses and 4 KB pages. On top, the virtual address of the current access, split into VPN and offset; at the bottom, the physical address it reaches. In the middle, a TLB of four entries (fully associative, empty at the start) and the part of the page table that matters, in memory: V is the valid bit, "disk" a page that is not in RAM. The entries used by the current access sit on the highlighter. Press "Next" one access at a time. The insight: translation replaces only the page number; the offset is always true.

  1. Access 1 is Example 19, 0x7FFE_1234, with the TLB empty. Before pressing "Next", predict whether the TLB hits and write the physical address.
    What you should see

    A TLB miss, since the TLB is empty. The walk reads the entry of VPN 0x7FFE1: valid, PFN 0x01AB0, which goes into the TLB. The physical address is 0x01AB_0234: the last three hex digits come straight down from the virtual address.

  2. Accesses 2 and 3 are 0x7FFE_1238 and 0x7FFE_0FFC, both within 0x240 bytes of access 1. Predict which of them hits in the TLB.
    What you should see

    Access 2 hits: same VPN, 0x7FFE1, so PFN 0x01AB0 comes out at once and the PA is 0x01AB_0238. Access 3 misses: 0x7FFE_0FFC lies 4 bytes below the start of the page, so its VPN is 0x7FFE0, another page. Its frame, 0x00C17, is nowhere near 0x01AB0: pages that are neighbours in the virtual space need not be neighbours in RAM.

  3. Accesses 4 and 5 both miss in the TLB. Predict which of them needs the disk, and what each costs.
    What you should see

    Access 4 is an ordinary TLB miss: the entry of VPN 0x00403 is valid, the walk refills the TLB with PFN 0x001F2 in tens of cycles, PA 0x001F_2A2C. Access 5 finds V = 0 for VPN 0x00404: a page fault. The operating system loads the page from the disk into frame 0x0A3F7, sets V = 1 and restarts the access: millions of cycles. Access 6, in the same page, then hits.

  4. Access 7 returns to the page of Example 19, at 0x7FFE_1FF8. Write the physical address before you look.
    What you should see

    0x01AB_0FF8, a TLB hit: four entries are enough for the four pages used so far. Translation swapped 0x7FFE1 for 0x01AB0; the offset 0xFF8 went through untouched.

Virtual memory was invented in Manchester for the Atlas, inaugurated in December 1962: a core of 16K words and a drum of 96K words were made to look like one "one-level store" of 512-word pages. A page missing from the core raised a page-fault interrupt for the supervisor, and 32 associative page address registers translated in hardware.

A TLB miss costs a page walk of tens of cycles and never touches the disk; a page fault costs a trip to the disk through the operating system, millions of cycles.

Start the cache before the TLB answers

Now put the TLB in front of the L1. A physically addressed cache (lesson 23) needs the physical index to select a set, so it waits for the TLB: cache hit alone 1 cycle, TLB lookup 1 cycle, in sequence 2 cycles — "this doubles the critical latency" (p. 360). More than 90 % of accesses are hits, and the hit time is the term of AMAT that every access pays.

Look at what the cache needs, and when: the index first, to select a set and read its tags; the tag only at the end, for the comparison. And the index of a small cache sits in the low bits, inside the page offset, which translation does not change. In the hotel city, a porter who knows only your room number can already walk to the right floor — every building has the same layout — and check the building name on the door when reception phones it through.

Virtually indexed, physically tagged (VIPT) cache — a cache where "the index (which set to look at) is taken from the virtual address" and "the tag (to confirm if it's the right block) comes from the physical address after TLB translation" (p. 360).

The notes' five steps (p. 360), drawn in Fig. 2: the CPU issues a virtual address; its index bits select a set at once; meanwhile the TLB translates the VPN into the PFN; the PFN, which is the physical tag, is compared with the tags of the selected set; a match is a hit.

The set read and the translation now overlap. With \(T_{\text{TLB}}\) for the TLB lookup, \(T_{\text{read}}\) for indexing the cache and reading the set, and \(T_{\text{cmp}}\) for comparing the tags and selecting the way:

\[ T_{\text{serial}} = T_{\text{TLB}} + T_{\text{read}} + T_{\text{cmp}} \] \[ T_{\text{VIPT}} = \max(T_{\text{TLB}},\, T_{\text{read}}) + T_{\text{cmp}} \]

If the TLB answers before the set has been read, a VIPT hit costs what the cache alone costs. The widget puts both designs on one clock.

One hit, two designs, one clock

On top, a physically indexed L1: the cache waits for the physical address from the TLB. Below, a VIPT L1: it reads its set while the TLB translates, and only the comparison waits for the PFN. The sliders set how long each step takes, in fractions of a clock cycle; a hit takes as many whole cycles as its critical path needs, and the dashed lines are the clock edges. A miss costs 20 cycles more in both designs. The insight: VIPT removes the TLB from the hit path without removing the TLB.

  1. At the start (TLB 0.75, set read 0.75, compare 0.25 cycles, miss rate 5 %), predict the hit time of each design in whole clock cycles, then the AMAT of each.
    What you should see

    Serial: path 1.75, so 2 cycles. VIPT: max(0.75, 0.75) + 0.25 = 1.00, so 1 cycle: the notes' 2 against 1 (p. 360). AMAT = 2 + 0.05 × 20 = 3.00 against 1 + 0.05 × 20 = 2.00 cycles.

  2. Raise the TLB lookup to 1.5 cycles. Does VIPT still hide it?
    What you should see

    Not completely. The set is read at 0.75, the PFN arrives at 1.5, and the comparison waits: path 1.75, 2 cycles. The serial design gets worse too: 2.5, so 3 cycles. VIPT hides the TLB only up to the time of the set read, which is one reason a TLB is kept tiny.

  3. Back to the start. Move the miss rate from 0 to 20 %. Predict what happens to the AMAT gap between the two designs.
    What you should see

    It stays 1 cycle: 2 against 1 at 0 %, 6 against 5 at 20 %. Only the hit time differs; the miss term, miss rate × miss penalty, is the same in both. VIPT is a hit-time technique, not a miss-penalty one.

"A VIPT cache skips the TLB on a hit." No: the TLB is read on every access. Its PFN is the tag that decides the hit, and its permission bits are checked. VIPT takes the TLB off the critical path; it does not take it away.

The textbook name of VIPT is "avoiding address translation during indexing of the cache", a hit-time technique. The January 2026 quiz transcribed in the notes (pp. 503–504) offers it as a miss-penalty one, and the notes' solution accepts it (lesson 24 and lesson 26 settle that quiz). A miss still pays its full penalty; VIPT shortens every hit.

VIPT reads the set with page-offset bits while the TLB translates, then compares the physical tag: the TLB leaves the critical path of a hit, not the machine.

Two names for one byte: synonyms

Why not tag the cache with virtual addresses too? A virtually indexed, virtually tagged (VIVT) cache would need the TLB only on a miss. The obstacle is the synonym, or alias: two virtual addresses that map to the same physical address — normal with memory shared between processes, memory-mapped files, a page mapped twice (p. 361).

The notes' Example 20 (p. 362) takes two aliases, VA1 = 0x4000_1234 and VA2 = 0x8000_1234, both mapped to PA = 0x1000_1234. With 4 KB pages, 64 B blocks and a 4 KB direct-mapped cache of 64 sets, the 12-bit page offset splits into a 6-bit index and a 6-bit block offset. Do the arithmetic before reading the notes' story:

All three share the page offset 0x234 = 0010 0011 0100, so they share the index: set 8. The notes put VA1 in "Set 10" and VA2 in "Set 42" of a VIVT cache and tag the VIPT line "0x1000"; neither survives the arithmetic.

"VA1 index = bits [11 : 6] of 0x4000_1234 → suppose = Set 10." … "VA2 index = bits [11 : 6] of 0x8000_1234 → suppose = Set 42."

Bits [11:6] of both addresses are 001000: both aliases select set 8, in VIVT as in VIPT. This 4 KB direct-mapped VIVT cache cannot hold two copies: the aliases conflict in set 8 (virtual tags 0x40001 and 0x80001) and evict each other; the values stay correct, at the cost of a miss at every switch.

The index lies inside the page offset, 0x234 = 564 = 8 × 64 + 52, and all aliases share the page offset. Two copies need two places: a second way (the tables below) or an index that reaches into the VPN (section 5). The exam exercise on synonyms runs the notes' own cache to the end.

"Tag check uses Physical Page Number (0x1000) from TLB."

The physical page number of 0x1000_1234 is its upper 20 bits, 0x10001, and that is the tag of the line.

The underscore groups the hex digits four by four; with 4 KB pages the page boundary falls after the fifth digit: 0x10001 | 0x234. Example 19 splits correctly on p. 358: 0x7FFE_1234 gives 0x7FFE1 | 0x234.

Duplication needs room for both names. Give the cache a second way: 8 KB, 2-way, still 4 KB per way, so still 64 sets and index [11:6]. Run four accesses, write-back with write-allocate and 0 in memory at the start: write 7 through VA1, read through VA2, write 9 through VA2, read through VA1.

VIPT avoids this with two facts at once (p. 361). The index comes from page-offset bits, identical in every alias, so all aliases select the same set; the tag is the physical page number, identical too, so all of them match the same line. One copy, no stale data. The notes call it the page offset trick: bits that translation never changes can index the cache before translation ends.

Virtual tags have a second problem, not in the notes: homonyms, one virtual address naming different frames in different processes. A VIVT cache must be flushed at every context switch or extend its tags with an address-space identifier; physical tags never meet it.

Aliases share their page offset and their physical page: VIPT sends them to one set and matches them against one tag, so the block has a single copy.

The size law: cache size / associativity ≤ page size

"Ok, now we can sleep peacefully knowing that the Synonym Problem has been solved." "Not at all!" (p. 363): the trick needs every index bit inside the page offset, and a larger cache needs more index bits. Example 21 (p. 364): 4 KB pages give 12 offset bits, 64-byte blocks take 6, so 6 index bits are left, 64 sets at most. A 32 KB 4-way cache has 8 KB per way, 128 sets, 7 index bits; the seventh, bit 12, belongs to the VPN.

Why that hurts: bit 12 is a page-number bit, and aliases need not agree on it. If VA1 = 0x4000_1234 and a third name, VA3 = 0x8000_0234, map to the same frame, the index [12:6] puts VA1 in set 72 and VA3 in set 8 (bit 12 is 1 in VA1, 0 in VA3). Two sets, two copies: the synonym problem is back, physical tags or not (p. 363).

  1. Count the sets: the cache holds \(C / B\) blocks, \(A\) per set.

    \[ S = \frac{C}{A \times B} \]

  2. Count the bits: index \(i = \log_2 S\), block offset \(o = \log_2 B\), page offset \(p = \log_2 P\). VIPT needs index and block offset inside the page offset:

    \[ i + o \le p \]

  3. A sum of logarithms is the logarithm of a product:

    \[ \log_2 S + \log_2 B \le \log_2 P \] \[ S \times B \le P \]

  4. Sets times block size is the size of one way, the cache divided by its ways:

    \[ S \times B = \frac{C}{A} \quad\Rightarrow\quad \frac{C}{A} \le P \]

  5. Example 21 fails by one bit; one more factor of two in \(A\) fixes it:

    \[ \frac{32\ \text{KB}}{4} = 8\ \text{KB} \gt 4\ \text{KB} \] \[ k = i + o - p = 7 + 6 - 12 = 1 \]

    With 8 ways, 32 KB / 8 = 4 KB: equality. With 4 ways the maximum is 4 × 4 KB = 16 KB (p. 364).

  6. Rearranged: the largest VIPT cache with \(A\) ways and the fewest ways for a cache of size \(C\). A law that fails by \(k\) bits lets an alias sit in any of \(2^k\) sets.

    \[ C_{\max} = A \times P \qquad A_{\min} = \frac{C}{P} \]
On p. 363 the notes justify eq. (80) with one garbled sentence; the steps above are the argument.

Address bit-slicer: does the index fit in the page offset?

The same 32-bit virtual address drawn twice, bit by bit, bit 31 on the left. On top as the page table splits it, VPN | page offset; below as the cache splits it, tag | index | block offset, with the bit ranges above each field. The dashed line is the page boundary: bits to its right are equal in the virtual and the physical address. Index bits to its left are VPN bits and turn red. The insight: the law cache size / associativity ≤ page size says where one bit field must end.

  1. The widget opens on Example 21: 32 KB, 4-way, 64 B blocks, 4 KB pages. Before reading the readouts, say how many index bits there are and which one leaks. Then predict the smallest associativity that fixes it, and set it.
    What you should see

    128 sets, 7 index bits [12:6]; bit 12 is red, so k = 1 and an alias may sit in 2 sets. At 8 ways: 64 sets, index [11:6], 32 KB / 8 = 4 KB = the page. This is the 32 KB 8-way L1 of the hook.

  2. Back to 4 ways. Would larger blocks help? Predict, then move the block size to 128 B.
    What you should see

    No. The block offset gains a bit and the index loses one: index [12:7], and bit 12 is still red. Index plus block offset stays 13 bits, because the law C / A ≤ P has no block size in it.

  3. Pick the AMD Opteron preset, 64 KB 2-way. How many sets could hold an alias? Find two fixes, each with a single slider.
    What you should see

    32 KB per way: 9 index bits [14:6], three of them from the VPN, so an alias may sit in any of 2³ = 8 sets (the Opteron checked them in hardware, according to Hennessy & Patterson). Fixes: 16 ways (64 KB / 16 = 4 KB per way), or pages of 32 KB (15 offset bits).

  4. With 16 KB pages, what is the largest VIPT cache with 8 ways? Predict, then check with the last preset.
    What you should see

    8 × 16 KB = 128 KB: 256 sets, index [13:6], and the page offset now ends at bit 13. A larger page is the other way to grow a VIPT L1.

"VIPT caps the L1 at the size of a page." No: it caps one way at a page. Twelve ways of 4 KB make 48 KB, all VIPT-safe.

Back to the hook

32 KB / 8 ways = 4 KB, one page: that L1 used every index bit the page offset allows (p. 364 gives the same example), and to grow it added ways: 48 KB / 12 = 4 KB again. The first fact of the hook is the reason: only the page offset, the last three hex digits, is known before the TLB answers, so one way can cover at most one page. With 16 KB pages, as on Apple silicon, 8 ways would allow 8 × 16 KB = 128 KB.

The lower levels escape the law: "Higher-level caches (L2, L3) are usually physically indexed, physically tagged (PIPT), so they don't suffer this limitation" (p. 364). They are accessed only after an L1 miss, when the TLB has long answered, so there is nothing left to hide.

Adding ways is not free: each adds a tag comparison, widens the multiplexer and costs energy on every access. So VIPT pushes L1 associativity up while a short hit time, the theme of lesson 28, pushes it down. Way prediction (lesson 25) eases the conflict by reading the predicted way first; many processors also accept a pipelined L1 hit of two or more cycles. Other escapes (Hennessy & Patterson; not in the notes): OS page colouring, so that all aliases of a frame agree on the leaking index bits; hardware that checks the \(2^k\) candidate sets on a miss, as in the 64 KB 2-way L1 of the AMD Opteron; larger pages.

A VIPT L1 keeps every alias in one set only while cache size / associativity ≤ page size: to grow, it adds ways or uses larger pages.

Exam-style questions

The three official papers have no question on virtual memory, so these questions follow the forms the papers use for the cache (the July 2024 address quiz and cache table, the formula-sheet AMAT) and the June 2026 open question. The model answers are computed here; there are no official solutions.

Explain the main concepts and benefits of each one of the following techniques used in the memory hierarchy of modern processors: 1. Paged virtual memory; 2. Per-process page tables; 3. Translation lookaside buffer (TLB); 4. Handling of TLB misses and page faults; 5. Virtually indexed, physically tagged (VIPT) L1 caches; 6. Indexing the cache with page-offset bits only; 7. Higher associativity in a VIPT L1 cache; 8. Physically indexed, physically tagged (PIPT) L2 and L3 caches.

Show model answer

1. The virtual and the physical address spaces are divided into pages of one fixed size (for example 4 KB). Each process sees a large, private, contiguous virtual space; the OS maps its pages onto physical frames anywhere in RAM. A virtual address is VPN | page offset; translation replaces the VPN with the PFN and leaves the offset unchanged. Benefits: programs larger than RAM (main memory acts as a cache for the disk), protection and isolation between processes, relocation, sharing of frames; fixed-size pages avoid external fragmentation. Cost: a translation on every access.

2. Each process has a page table in memory, indexed by the VPN; each entry holds the PFN, a valid bit, a dirty bit, a use bit and protection bits. The same virtual address in two processes maps to different frames (isolation), two VPNs may point to one frame (sharing), and the hardware enforces the permissions. Because a page fault costs millions of cycles, placement is fully associative (any frame), replacement approximates LRU with the use bit, and the write policy is always write-back with the dirty bit. Cost: memory for the tables, hence multi-level tables.

3. A small, fast, fully or highly associative cache of recent translations: tag = VPN, data = PFN and the flags. It is looked up on every access; on a hit the physical address is available in about one cycle, with the protection check. Benefit: without it every access would need an extra memory access to read the page table. Cost: it must stay tiny (tens of entries) to answer within the cycle.

4. On a TLB miss the page table is walked in memory, by a hardware walker or a software handler, in tens of cycles; if the entry is valid it is inserted into the TLB and the access completes, with no OS involvement for a hardware walker. If the entry is invalid, the page is not in RAM: a page-fault exception transfers control to the OS, which chooses a frame (writing back a dirty victim), reads the page from the disk, updates the entry and restarts the faulting instruction; this costs millions of cycles and requires precise exceptions. A TLB miss is not a page fault.

5. The cache index is taken from the virtual address and the tag from the physical address. The set is read while the TLB translates the VPN; the PFN is then compared with the tags of the set. Benefit: the TLB latency leaves the hit time, max(TLB, set read) + compare instead of TLB + cache, for example 1 cycle instead of 2 (notes, p. 360); since most accesses are hits, the AMAT drops. The TLB is still read on every access, for the tag and the permissions. Cost: the size restriction of point 7.

6. Translation never changes the page offset, so index and block-offset bits taken from it are the same in the virtual and the physical address and can be used before the TLB answers (the page offset trick). It also solves synonyms, two virtual addresses mapped to one physical address (shared memory, mapped files): all aliases select the same set and, with physical tags, match the same line, so only one copy exists and no stale value can be read. A VIVT cache could keep two copies with different virtual tags.

7. All index bits must lie in the page offset: index bits + block-offset bits ≤ page-offset bits, that is cache size / associativity ≤ page size. With 4 KB pages and 64-byte blocks a 32 KB 4-way cache (8 KB per way, 7 index bits) takes one index bit from the VPN; 8 ways make it safe (4 KB per way), and 48 KB needs 12 ways. A larger VIPT L1 therefore needs more ways. Cost: more comparators, a wider way multiplexer, more energy and a longer hit time, which way prediction mitigates. Alternatives: page colouring, hardware alias detection, larger pages.

8. L2 and L3 use the physical address for both index and tag. They are accessed only after an L1 miss, when the TLB has already translated the address, so translation adds nothing to their access and they have no synonym problem and no page-size limit: they can be large (MBs) and highly associative. Their longer hit time is acceptable because it is paid only on L1 misses.

The form is the June 2026 question: eight sub-points, about five lines each. For each technique the examiner looks for the mechanism, what it buys and what it costs. Sub-points 4 and 7 carry the usual traps: a TLB miss is not a page fault, and the law limits one way, not the whole cache.

A processor has 32-bit virtual addresses, 4 KB pages and an L1 data cache with 32-byte blocks. 1. The L1 is 8 KB, 2-way set-associative: give the structure of the address as seen by the cache (tag | index | offset, with bit positions) and say whether the cache can be virtually indexed and physically tagged without synonym problems. 2. The designers want 64 KB, keeping 2 ways: how many index bits come from the virtual page number, and in how many sets could an alias of a block be found? 3. What is the minimum associativity of a 64 KB VIPT L1? 4. Give two other ways to make the 64 KB 2-way cache safe.

Show model answer

Page offset = log₂ 4096 = 12 bits, [11:0]. Block offset = log₂ 32 = 5 bits, [4:0].

1. Sets = 8 KB / (32 B × 2) = 128, so the index has 7 bits, [11:5], and the tag 32 − 7 − 5 = 20 bits, [31:12]: |20-bit tag | 7-bit index | 5-bit offset|. Index + offset = 7 + 5 = 12 bits = the page offset; equivalently 8 KB / 2 = 4 KB ≤ 4 KB. The cache can be VIPT, and its tag is exactly the PFN.

2. Sets = 64 KB / (32 B × 2) = 1024, so the index has 10 bits, [14:5]. Bits 14, 13 and 12 lie above the page offset: k = 10 + 5 − 12 = 3 bits come from the VPN, and an alias may be in any of 2³ = 8 sets.

3. Minimum associativity = 64 KB / 4 KB = 16 ways: 128 sets, index [11:5] again.

4. Pages of 32 KB (15 offset bits contain index [14:5]); page colouring by the OS, so that all aliases of a frame agree on virtual-address bits 14 to 12; hardware that checks the 8 candidate sets on a miss and removes a duplicate (as the AMD Opteron did).

A physically indexed L1 cache waits for the TLB: TLB lookup 1 clock cycle, then the cache hit 1 clock cycle. A VIPT version overlaps the TLB lookup completely with the indexing, so its hit takes 1 clock cycle. In both designs the miss rate is 5 % and the miss penalty 20 clock cycles. How much is the speed-up of the average memory access time of the VIPT design over the serial one?

Show model answer
\[ \text{AMAT}_{\text{serial}} = 2 + 0.05 \times 20 = 3 \] \[ \text{AMAT}_{\text{VIPT}} = 1 + 0.05 \times 20 = 2 \]

Speed-up = 3 / 2 = 1.5.

The miss term is the same 1 cycle in both designs: only the hit time changes. The widget of section 3 shows that the gap stays one cycle at any miss rate.

(SINGLE ANSWER) An L1 data cache of 64 KB with 64-byte blocks must be virtually indexed and physically tagged on a machine with 4 KB pages. What is the minimum associativity such that no index bit comes from the virtual page number?

  • Answer 1: 4-way 16 KB per way: 8 index bits [13:6], two of them from the VPN.
  • Answer 2: 8-way 8 KB per way: 7 index bits [12:6], bit 12 still from the VPN.
  • Answer 3: 16-way 64 KB / 16 = 4 KB per way = one page: 64 sets, index [11:6].
  • Answer 4: 32-way Safe, with 2 KB per way, but not the minimum: 16 ways already fit.
Show model answer

Answer 3. Minimum associativity = cache size / page size = 64 KB / 4 KB = 16. The block size does not enter: it moves bits between index and block offset, not out of the page offset.

The quick route is the law, C / A ≤ P; the slow route counts sets and bits. Both give 16. Answer 2 is the near miss: 8 ways halve the overflow, but bit 12 is still a VPN bit.

(SINGLE ANSWER) In a virtually indexed, physically tagged cache, the tag stored with each block is:

  • Answer 1: the virtual page number of the address that brought the block into the cache That is a virtually tagged (VIVT) cache, the design with synonyms.
  • Answer 2: bits of the physical address, from the physical page number supplied by the TLB The tag is physical: every alias of the block matches it.
  • Answer 3: the page offset of the address The page offset supplies the index and the block offset; it is never compared.
  • Answer 4: no tag, because the index identifies the block Many blocks share an index; without a tag a hit could not be recognised.
Show model answer

Answer 2. The index comes from the page-offset bits of the virtual address, the tag from the physical address: the PFN delivered by the TLB is compared with the tags of the selected set.

Read the name backwards: physically tagged. The distractors are the other two designs and the index.

(True/False) A TLB miss means that the page is not in main memory, so the operating system must load it from the disk.

  • True That describes a page fault. After a TLB miss the page is usually in memory, and the walk only refills the TLB.
  • False A TLB miss is a miss in the cache of translations: the page table is walked in tens of cycles. Only an invalid entry, a page fault, involves the disk.
Show model answer

False. On a TLB miss the page table in memory is walked and the translation inserted into the TLB, in tens of cycles. Only if the page-table entry is invalid does a page fault occur, and the OS loads the page from the disk, in millions of cycles.

The distinction between the two misses is the whole point. If asked to motivate, give the cost of each.

Check yourself

Pages are 4 KB. A process accesses the virtual address 0x0040_3A2C, and its page table maps VPN 0x00403 to PFN 0x001F2. Which physical address does the access reach?

  • 0x001F_2A2C PFN 0x001F2 in front of the unchanged offset 0xA2C, the last three hex digits.
  • 0x0040_3A2C That is the virtual address: no translation happened.
  • 0x001F_2000 The frame is right, but the offset 0xA2C was dropped. Translation never touches the offset.
  • 0x01F2_0A2C The PFN was shifted by 16 bits instead of 12. A 12-bit offset is three hex digits, so the PFN starts at the fourth digit from the right.

The TLB holds the translation of VPN 0x7FFE1, with 4 KB pages. Which of these accesses hit in the TLB? Select all that apply.

  • 0x7FFE_1000 The first byte of the same page: VPN 0x7FFE1.
  • 0x7FFE_1FFF The last byte of the same page: VPN 0x7FFE1.
  • 0x7FFE_2000 One byte past the end of the page: VPN 0x7FFE2, another page.
  • 0x7FFE_0234 Same offset as Example 19, but VPN 0x7FFE0. The offset plays no part in the TLB lookup.

An access misses in the TLB, and the page walk finds a valid entry for its VPN. What happens next?

  • The translation is inserted into the TLB and the access completes, in tens of cycles, without a page fault A TLB miss with a valid entry is a refill, not a fault: the disk is never touched.
  • A page fault: the OS reads the page from the disk Only an invalid entry, a page that is not in RAM, raises a page fault.
  • The data cache is flushed, since its contents may be stale A TLB miss says nothing about the contents of the data cache.
  • The program is stopped with a protection error Only a violation of the permission bits does that; nothing here says the access is forbidden.

Why can a VIPT cache select its set before the TLB has answered?

  • Its index bits lie inside the page offset, which translation does not change The bits it needs first are already the physical ones.
  • Because the TLB is faster than the cache Speed is not the argument: a cache that needed translated index bits would wait for any TLB. The index needs no translation at all.
  • Because it compares virtual tags Its tags are physical: the comparison does wait for the PFN of the TLB.
  • Because the OS keeps virtual and physical addresses equal Only the page offset is equal; the page numbers differ.

Intel's L1 data cache of 2019 is 48 KB, 12-way, with 64-byte blocks, and pages are 4 KB. Can it be VIPT without synonym problems?

  • Yes: one way is exactly one page 48 KB / 12 = 4 KB per way: 64 sets, so index + block offset = 6 + 6 = 12 bits, the whole page offset.
  • No: 48 KB is not a power of two, so the index cannot be a bit field The number of sets must be a power of two, and it is: 48 KB / (12 × 64 B) = 64.
  • No: it would need 16 ways 16 ways are needed for 64 KB; for 48 KB, 12 ways give 4 KB per way.
  • Only with 16 KB pages 4 KB per way already fits a 4 KB page.

A 64 KB 4-way L1 on a machine with 4 KB pages is not VIPT-safe. Which changes, each on its own, would make it safe? Select all that apply.

  • 16 ways 64 KB / 16 = 4 KB per way.
  • 16 KB pages 64 KB / 4 = 16 KB per way = one page: the 14 offset bits hold index and block offset.
  • Page colouring by the operating system All aliases of a frame get virtual addresses that agree on the two leaking index bits, so they select the same set.
  • Blocks of 128 B instead of 64 B One bit moves from the index to the block offset; their sum, the log of the size of a way, stays 14 bits.
  • Making it direct-mapped 64 KB in one way: four leaking bits instead of two.

The notes' Example 20 cache, 4 KB, direct-mapped, 64-byte blocks, 4 KB pages, with virtual tags. A program alternates reads through VA1 = 0x4000_1234 and VA2 = 0x8000_1234, aliases of one physical address. What happens?

  • Both select set 8 with different virtual tags: they evict each other at every switch, and every value read is correct The ping-pong of the exam exercise above: misses, not stale data.
  • VA1 goes to set 10 and VA2 to set 42: two copies and stale data That is the notes' story; bits [11:6] of both addresses are 001000, set 8.
  • Both hit the same line, as in a VIPT cache Their virtual tags differ, 0x40001 and 0x80001. Only physical tags would match.
  • The second access raises a page fault Both pages are mapped; an alias is legal and common.

Key take-aways

  • Paging cuts virtual and physical memory into pages of one size; a virtual address is VPN | page offset, and translation replaces the VPN with the PFN read from the per-process page table, leaving the offset untouched.
  • The TLB is a small cache of translations: a hit gives the PFN in about a cycle, a miss walks the page table in tens of cycles, and only an invalid entry is a page fault, handled by the OS in millions of cycles.
  • A physically indexed L1 waits for the TLB on every hit. A VIPT L1 selects its set with page-offset bits while the TLB translates, then compares the physical tag: the TLB leaves the hit path but is still used on every access.
  • Synonyms are two virtual addresses for one physical address. Virtual tags allow two copies and stale data; page-offset index plus physical tag give every alias the same set and the same line.
  • VIPT keeps synonyms in one set only if cache size / associativity ≤ page size, which follows from S × B = C / A. A larger VIPT L1 needs more ways (32 KB 8-way, 48 KB 12-way with 4 KB pages) or larger pages, unless the OS or extra hardware handles the aliases; L2 and L3 are PIPT.
  • At the exam, "avoiding address translation during indexing of the cache" is a hit-time technique, not a miss-penalty one.
