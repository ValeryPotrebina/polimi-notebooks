Issue, execute, write result: the three stages and the exam table

After this lesson you will fill the ISSUE / START EXEC / WRITE RESULT / Hazards Type / RSi / UNIT table of an exam loop with the paper's own conventions, and point, for every cell, at the rule that fixed it.

The paper of 22 June 2026 hands you seven instructions — a loop body with two loads, two FP adds, a store, an increment of the index and a branch — and a machine built to run them out of order: two load/store units, one FP unit, one integer unit, one Common Data Bus, every cache access a hit. You will compute the answer in this lesson: the body takes 19 cycles, and the last instruction to finish is the fifth one, the store. The branch issued after it is resolved four cycles earlier.

Here is the puzzle. Issuing seven instructions takes seven cycles. Where do the other twelve go — and how many of them are the machine's fault? The store cannot even enter the machine before cycle 7; the branch loses a fight for the bus at cycle 14. Count those against the machine if you like. The answer at the end of the lesson is a single number, and it is smaller than you expect.

First the three stages, each walked on this loop; then the rules the papers use; then the table, cell by cell.

Three stages, and where the order is kept

Lesson 11 built the machine: reservation stations in front of every functional unit, a register file with a tag next to each value, and one Common Data Bus carrying every result to everybody. The table below is all you need to recall; this lesson is about what happens in time.

Everything here is walked on the loop of the June 2026 paper, written as the paper writes it (older papers write $F2 and $R1; the 2026 paper drops the dollar sign, and so does this notebook):

I0  FOR: LD    F2, AA(R1)
I1       FADD  F2, F2, F2
I2       LD    F4, BB(R1)
I3       FADD  F2, F2, F4
I4       SD    F2, A(R1)
I5       ADDUI R1, R1, 8
I6       BNE   R1, R2, FOR

The machine of the paper: 2 reservation stations (RS1, RS2) with 2 load/store units (LDU1, LDU2) of latency 4; 2 reservation stations (RS3, RS4) with 1 FP unit (FPU1) of latency 3; 2 reservation stations (RS5, RS6) with 1 integer/branch unit (ALU1) of latency 2; all cache hits; a single Common Data Bus.

An instruction goes through three stages (notes, page 151). Issue, in program order: decode it and park it in a reservation station. Execute, out of order: wait in the station for the operands, then compute in the unit. Write Result, out of order: broadcast the result on the CDB to the stations and the register file. Unlike the scoreboard of lesson 9 there is no Read Operands stage: operands are read at issue when they exist, or delivered by the bus when they do not — which is exactly what removes the WAR stall, because nobody reads a register later.

Robert Tomasulo's January 1967 paper on the IBM System/360 Model 91 sums up its floating-point unit in one line of the abstract: "a simple common data busing and register tagging scheme which permits simultaneous execution of independent instructions while preserving the essential precedences". Tagging is Issue, busing is Write Result, and the precedences are the true dependences that Execute still waits for.

Issue: in order, one per cycle — or stall

Issue does four things to the instruction at the head of the queue (notes, page 151): decode it; find a free reservation station of its type (an FADD needs a station of the FP unit); for each source register, copy the value into Vj or Vk if the register is valid, otherwise its tag Qi into Qj or Qk; and rename the destination by writing this station's name into its Qi. Watch it on the first four cycles of the loop.

Cycle 1. I0 LD F2, AA(R1) goes into RS1. R1 is valid, so Vj = v(R1) and the offset AA waits in the address field. Then F2.Qi ← RS1: from now on, whoever needs F2 will wait for RS1, not for "F2".

Cycle 2. I1 FADD F2, F2, F2 goes into RS3. Both sources are F2 and F2.Qi says RS1, so Qj = RS1 and Qk = RS1. Then the destination is renamed again: F2.Qi ← RS3. The register file has forgotten RS1; only RS3 remembers it.

Cycle 3. I2 LD F4, BB(R1) goes into RS2, with Vj = v(R1) and F4.Qi ← RS2.

Cycle 4. I3 FADD F2, F2, F4 goes into RS4 with Qj = RS3 and Qk = RS2, and F2.Qi ← RS4 — the third name F2 has had in four cycles.

The notes' Example 7 (page 152) does the same with ADD.D F6, F2, F4 and MUL.D F8, F6, F10 — the notes' spelling of FADD and FMUL, as in Hennessy and Patterson; this lesson writes its own code the papers' way. RS2, holding the multiply, "knows that it must listen for RS1's result on the Common Data Bus". The example stops one step short: the multiply also renames its destination, F8.Qi ← RS2.

What stalls the issue stage

Cycle 5 of the loop: RS1 holds I0 until its write at 6, RS2 holds I2 until 8. The store waits, and so do the two instructions behind it.

Three things, and a RAW dependence is not one of them (page 152). First, no free reservation station of the needed type — a structural hazard, the stall the June 2025 and June 2026 papers both contain: in cycle 5 the store I4 needs a load/store station, RS1 holds I0 and RS2 holds I2 (a station stays busy from ISSUE through WRITE RESULT), so I4 issues only at 7, and the independent I5 and I6 wait behind it. (A type is a unit class: the notes' page 162 sends SUB.D to an ADD-type station and DIV.D to a MUL-type one; the papers have one FP class.)

Second, a full load/store queue — the same kind of stall for memory operations. Third, in the basic, non-speculative machine, an unresolved branch: the instructions after it must wait until it is resolved, and without a prediction the machine does not even know which instruction comes next. The speculative machine of lesson 17 removes that wait. A RAW dependence never stops an issue — the instruction takes a tag and waits in its own station, blocking nobody.

Why issue is kept in order

Renaming works only because every issue sees the register status table as the previous instruction left it: the destination's Qi must name the youngest writer, and a consumer must capture the tag of the last writer before it. Let I3 issue before I1 and all three go wrong: I3 captures RS1, the wrong producer of its F2; I1 then captures RS4, a younger instruction; and F2 ends up owned by I1 instead of I3. The second reason is memory order (the load/store queue takes the order of the stores from the issue sequence), the third simplicity. Precise exceptions are not on the list: results are still written out of order.

"Ensures precise exceptions, it helps the machine know which instruction caused a fault."

In-order issue does not make exceptions precise: basic Tomasulo completes and writes results out of order, so its exceptions are imprecise, and only in-order commit through a reorder buffer (lesson 17) fixes that. The real reasons are correct renaming, memory order and simplicity.

In the loop the younger I5 has written R1 at 11 when the older store I4 finishes at 19: if the store faulted, R1 would already hold the incremented value, a state no sequential execution ever passes through. Hennessy and Patterson give the 360/91 as the textbook case of imprecise exceptions, and item 7 of the June 2026 open question, the reorder buffer, is the fix.

"(in more advanced versions) Pending branch: speculative instructions must wait."

The other way round. It is the basic, non-speculative machine whose instructions wait behind an unresolved branch: they may not start executing until it is resolved (the notes' own page 154 lists "no pending branches" among the conditions for executing). The more advanced, speculative version with a reorder buffer issues and executes them on the prediction; only their commit waits.

Waiting behind a branch is exactly what speculation removes — Hennessy and Patterson's basic Tomasulo lets no instruction begin execution before the branches ahead of it have completed, and the speculative version drops that rule. The 2026 open question pairs "dynamic branch prediction and speculative execution" for that reason.

Issue copies a value or a tag, never a promise to read later — that is why a later writer can never hurt an earlier reader.

Execute: when Qj = Qk = 0 and the unit is free

A station fires its instruction into the unit when both tags are zero — the operands are in Vj and Vk — and the unit is free (page 154). Nothing else: not the program order, not a fixed cycle count. On the loop, I0 starts on LDU1 in cycle 2, the cycle after its issue, because R1 was ready, and I2 starts on LDU2 in cycle 4 — two loads overlap because there are two units. I1 sits in RS3 from cycle 2 to cycle 6 with Qj = Qk = RS1: a RAW wait, but one that blocks nobody. The notes call this dataflow execution: instructions run when their data are ready, not when the program says so.

When two stations of one unit are ready in the same cycle, the oldest goes first (page 155). Then the unit executes for its latency, with the convention every cell of the exam table depends on: a unit of latency L that starts in cycle s executes in cycles s … s + L − 1 and writes in cycle s + L — the paper's own pre-filled row, LD with latency 4 as ISSUE 1, START EXEC 2, WRITE RESULT 6. The papers do not say whether a unit is pipelined; the tables solved in the notes treat every unit as not pipelined, busy from its start through its write: FPU1 is busy with I1 from 7 through 10, and RS3 stays busy until that same write. In the three official papers the question never decides a cell — each second FADD depends on the first anyway.

"This time is internal to the FU, the RS has already “let go” of the instruction. The RS is now free and can be reused after the instruction completes Stage 3 (write-back)."

The station is not free during execution: it stays Busy from ISSUE through WRITE RESULT and is reusable from the next cycle. The sentence contradicts itself and the notes' own page 157, where "Free the RS and FU" is step 4 of Write Result.

Hennessy and Patterson clear RS[r].Busy at Write Result. Count RS1 free as soon as I0 starts executing (cycle 2) and the store finds a station at cycle 5 instead of 7, so I4, I5 and I6 all get different ISSUE cells; in the February 2025 paper solved in the notes (lesson 14) the SD takes the load's station the cycle after that load writes.

Loads and stores

Memory is global, must stay precise and can raise exceptions, so loads and stores get special treatment (pages 155–156). A load waits for its base register (a tag in the load buffer if it is pending), computes the address and reads memory — both inside the exam's 4-cycle latency — then broadcasts the value like any result. A store needs two things, the address and the data, and either may arrive by tag: in the loop I4 waits in RS1 with Qk = RS4 until I3 broadcasts at 14, starts at 15 and writes memory at 19. Loads may pass other loads but never an earlier store to the same address; stores keep program order among themselves. And a store broadcasts nothing: it produces no register value, so nobody waits for its tag. The table still has a WRITE RESULT cell for the store; the solved tables fill it with the end of the memory write, START EXEC + 4, and that cycle takes no bus slot.

Fixed issue → execute. Data flow through registers. A RAW hazard stalls issue, and everything behind it. WAR and WAW are possible.

Execute waits dynamically for operands. Data flow through tags in the stations. A RAW wait happens inside one station only. WAR and WAW are eliminated by renaming.

Start = the cycle after issue, or the cycle after the last missing operand's broadcast, or the cycle after the unit's last write — whichever is latest; write = start + latency.

Write Result: one broadcast, every listener

When the unit finishes, the result goes on the CDB with the tag of the station that produced it (page 157): ⟨tag, value⟩, "anyone waiting for this, come get it". Three things follow in that same cycle. Every station compares the tag with its Qj and Qk; each match copies the value into Vj or Vk and clears the tag, which "allows many instructions to simultaneously wake up". The register file writes the register whose Qi matches, if there is one, and clears its Qi; a register whose Qi names another station is not written. The station is freed, and so is the unit.

The register write is for the instructions that have not issued yet: they will read the register file, and Qi = 0 tells them the value is there. Everybody already waiting got the value from the bus, before any register was written — the CDB is Tomasulo's forwarding path.

Cycle 6 of the loop is a complete example. I0 broadcasts ⟨RS1, v(F2)⟩ — v(F2) is the notes' way of writing "the value this instruction produces for F2"; the bus itself carries only the value and the producer's tag, never a register name. RS3 holds Qj = Qk = RS1: both of its operands come from this one broadcast. RS4 holds RS3 and RS2: no match. The register file finds F2.Qi = RS4, not RS1: the write is skipped. The load's F2 never reaches the register file — and nothing is lost, because the only instruction that needed it, I1, has it in RS3.

Example 8 done right

The notes justify the skipped write with A ADD.D F6, F2, F4 in RS1 and B MUL.D F6, F6, F8 in RS2 (page 158): after B issues, F6.Qi = RS2, so RS1's broadcast must not land in F6. True — but B reads F6, so RS2 holds Qj = RS1 and needs that broadcast: the value is anything but obsolete. And B cannot finish before A, so an early write by A would have changed nothing (as long as the tag RS2 stayed in place); the example cannot show the danger. The case the rule protects is the independent one. Below, F2 comes late from a load that missed, so I0 waits in RS1; I1 waits in RS2 with Qj = RS1; I2 has both operands and goes ahead (stations named as in the notes' example):

I0  FADD  F6, F2, F4    ; RS1
I1  FMUL  F8, F6, F10   ; RS2
I2  FSUB  F6, F10, F12  ; RS3

I2 finishes first and writes F6 — its tag matches — and clears Qi. Then the slow F2 arrives, I0 executes and broadcasts ⟨RS1, v(F6)⟩: RS2 fills its Vj, so I1 multiplies the old F6, as program order demands; and the register file finds F6.Qi = 0, not RS1, so F6 keeps I2's newer value, as program order demands. One broadcast, two correct outcomes: the WAR for I1 and the WAW for I2 both dissolved by a tag comparison.

"RS1's result is now obsolete, because it was overwritten by a newer instruction." … "Because if we allowed RS1 to write to F6 now, it would overwrite the result of RS2, which hasn't been computed yet, and then we'd break correctness."

In the notes' own example RS1's result is needed: MUL.D F6, F6, F8 reads F6, so RS2 waits for the tag RS1 and consumes the broadcast; only the register write is skipped. And the danger is not this RAW chain, where RS2 would overwrite F6 later anyway, but the independent case where the younger writer finishes first and the older broadcast must not clobber it.

Trace the fragment above: I2 writes F6 before I0 broadcasts; without the Qi test F6 would end up holding I0's older value. Cycle 6 of the exam loop shows the skipped write with the exam's own numbers.

One bus, one result per cycle

A single CDB carries one broadcast per cycle. When two units finish together, the older instruction writes first and the younger slips by one cycle — and again if the next cycle is taken too. In the loop, I3 and I6 are both ready at 14: I3 writes, I6 is resolved at 15 — if the branch, too, needs the bus, which no solved paper settles (convention C4 below). The other timing rule of the bus: a value broadcast in cycle w is usable from cycle w + 1, so I1 starts at 7, not at 6.

The tag on the bus is the producer's name: every station with that tag fills in, the register file writes only if its Qi still says that name.

Reading the dependences before the hardware does

Part 1 of the exercise asks, before any cycle is counted, for a table of "all types of true-data-dependences, anti-dependences and output dependences for each instruction". The rules are mechanical; what makes the table right is that nothing is missing. For each instruction look at every earlier instruction of the iteration: a true data dependence (RAW) on the nearest earlier writer of a register it reads; an anti-dependence (WAR) on every earlier reader of a register it writes; an output dependence (WAW) on every earlier writer of the same register. Every pair once per register, R registers included — R1 under the loads and the store counts.

Twelve dependences in seven instructions: five true, four anti, three output. The three anti-dependences on R1 are the easiest to forget.

A dependence belongs to the program; a hazard belongs to a machine. The same twelve arcs exist on the 5-stage pipeline of lesson 2, on the scoreboard and on Tomasulo's machine; what changes is which of them cost cycles. Tomasulo keeps every true dependence as a wait in a station and turns the anti- and output dependences into non-hazards. In the Hazards Type column of Part 2 they cost nothing: write "WAR / WAW with I# solved by renaming" or leave them out — naming them shows that you saw them and knew they were harmless.

Why renaming makes them harmless, in two cases. Case A: the producer has already written when the consumer issues — the consumer copies the value into Vj, and no later writer of that register can touch its private copy. Case B: the producer is still pending — the consumer copies the producer's tag, and waits for that broadcast, not for "whatever the register ends up holding". The notes (pages 160–161) tell case B: DIV.D "still listening" for the first load while ADD.D renames F6 — which needs a slow load; in the run of lesson 13 that load has written before DIV.D issues, and DIV.D takes the value (case A). Both are safe; and because the register status table only ever names the youngest writer, an older writer's late broadcast is dropped at the register file (cycle 6 again).

Now the puzzle of the hook: how many of the twelve extra cycles are the machine's fault? None. Every one of the nineteen lies on the chain LD → FADD → FADD → SD through F2: one cycle to issue the load, then each link's latency plus its broadcast cycle — 1 + (4 + 1) + (3 + 1) + (3 + 1) + (4 + 1) = 19. Ten CDBs and a hundred stations could not shorten it, because each link needs the previous link's value. The hardware ran I2, I5 and I6 underneath the chain, and the two waits you could have blamed on it — the store's two cycles without a station, the branch's lost bus cycle — fall inside the chain and change nothing. That is the honest reading of CPI = 2.71: the program is serial, and dynamic scheduling hid what could be hidden.

Start = max(issue + 1, producers' writes + 1, unit free); write = start + latency; one CDB, oldest first; CPI = last write / instructions.

Exam-style questions

Explain the main concepts and benefits of each one of the following techniques used by modern superscalar processors (Tomasulo-style): 4. Reservation stations; 5. Dynamic register renaming; 6. Out-of-order execution. (Five lines each.)

Show model answer

Reservation stations. Buffers in front of each functional unit, each holding one issued instruction: its operation, its operand values (Vj, Vk) if they were available at issue, otherwise the tags (Qj, Qk) of the stations that will produce them, and a busy bit; the station's name is the tag under which its result will be broadcast. Benefits: the instruction leaves the in-order front end at once (a RAW dependence never stalls issue), waits locally and fires as soon as both operands arrive (data-driven execution); hazard detection is distributed, there is no central scoreboard; the stations give pending results more names than the ISA has registers. Cost: when all stations of a class are busy, issue stalls (structural hazard).

Dynamic register renaming. At issue the destination register's status field Qi is set to the station's tag, so the register always names its youngest writer; a consumer copies the value or the producer's tag at issue and never reads the register later. A result is broadcast with its tag, captured by every waiting station, and written into the register only if Qi still holds that tag. Benefits: WAR and WAW hazards (name dependences created by register reuse in loops and by the compiler's allocation) can neither stall nor corrupt — only true RAW dependences remain; the ISA's register count no longer limits scheduling; it is invisible to the program.

Out-of-order execution. An instruction starts in its unit as soon as Qj = Qk = 0 and the unit is free, independently of program order; results return out of order on the common data bus, one per cycle. Benefits: independent instructions proceed while a long-latency one (a load miss, a divide) waits, so stalls are hidden and throughput rises (lower CPI); latencies unknown at compile time are tolerated. Cost: completion out of order makes exceptions imprecise — a reorder buffer with in-order commit restores them.

The paper gives five blank lines per item: write short labelled statements, mechanism first, then "benefit:", then "cost:" where there is one. A complete answer names the fields of a station, the Qi tag and the "write only if the tag still matches" rule, and the exact firing condition of execution.

In Tomasulo's algorithm a reservation station is released: (single answer)

  • when the instruction is issued into it Issue is when it is allocated; it then holds the instruction's operands and tags.
  • when the instruction starts execution in the functional unit The station stays busy during execution; the exam counts it busy through the write cycle.
  • when the instruction writes its result on the CDB Step 4 of Write Result frees the station; it can take a new instruction from the next cycle.
  • when the next instruction of the same type is issued If no station is free, the next instruction of that type waits; it never evicts.
Show model answer

Answer 3: a station is busy from ISSUE through WRITE RESULT and reusable from the cycle after the write.

Which of the following can stall the ISSUE stage of Tomasulo's algorithm? (multiple answers)

  • a RAW hazard on a source register No: the instruction is issued with a tag in Qj or Qk and waits inside its station.
  • no free reservation station of the required type The structural hazard of every exam table: the instruction and everything behind it wait.
  • a WAW hazard on the destination register No: the destination is simply renamed to the new station; the older writer's broadcast will be dropped at the register file.
  • a full load/store queue Memory operations need a buffer entry, exactly like a station.
  • an unresolved branch, in a machine without speculation Without speculation the instructions after the branch must wait for it (the notes list it among the issue stalls); without a prediction the next instruction is not even known.

Answers 2, 4 and 5. Data hazards never stall issue: RAW waits in the station, WAW and WAR are dissolved by renaming.

F6.Qi = RS2. RS1, an older writer of F6, now broadcasts ⟨RS1, value⟩, and RS3 holds Qj = RS1. What happens?

  • F6 is written and RS3 fills its Vj The register file compares RS2 with RS1: no match, no write.
  • RS3 fills its Vj; F6 is not written The station that waited gets the value; the register keeps its youngest name.
  • Nothing: the broadcast is discarded because F6 was renamed Renaming protects the register, not the consumers: RS3 captured the tag RS1 at its issue and needs this very value.

Which statements about the Issue stage are true?

  • It happens in program order, one instruction per cycle The one place the order is kept; renaming depends on it.
  • A source register whose Qi is not zero gives the station a tag, not a value Qj or Qk = Qi of the register: "wait for that producer".
  • A RAW dependence on a pending result delays the issue No: the instruction issues with a tag and waits in its station.
  • The destination's Qi is overwritten even if an older writer of the same register is still executing Yes — that is how the youngest writer comes to own the register, and how WAW is handled.

Issue is where names are given out; waiting is what the stations do afterwards.

A producer writes its result on the CDB in cycle 10. The earliest cycle in which a consumer in a reservation station can start executing is …

  • 10 The value is travelling on the bus during cycle 10; the consumer's station latches it at the end of the cycle.
  • 11 The papers' convention: START EXEC = producer's WRITE RESULT + 1 (the pre-filled row 1 / 2 / 6 and every solved table).
  • 12 That would add a read-operands cycle the machine does not have: there is no Read Operands stage.

Two instructions finish executing in the same cycle and both need the single CDB. Who writes in that cycle?

  • The one with the longer latency Latency is not a priority.
  • The older one in program order; the younger writes the next free cycle Oldest first; the younger slips, and so do its consumers.
  • Both: the bus carries two results when they come from different units One CDB, one ⟨tag, value⟩ per cycle — that is why the exam says "a single Common Data Bus".

Why must issue stay in program order even though execution does not?

  • Because the functional units would otherwise be used out of order They are used out of order anyway; that is the point of the stations.
  • Because the register status table must always name the youngest writer, and each consumer must capture the tag of the last writer before it Issue out of order and a consumer could record a stale tag or a writer could lose its ownership of the register.
  • Because in-order issue makes exceptions precise It does not: results are still written out of order. Precise exceptions need the reorder buffer.

Which waits can appear in a Tomasulo exam table?

  • A RAW wait in the station for a producer's broadcast The one data hazard that remains; it sets START EXEC.
  • A WAR wait before writing the result That is the scoreboard's wait; Tomasulo's readers hold their own copy or tag.
  • A structural wait at issue for a free reservation station The favourite of the papers: two stations per class, three loads.
  • A structural wait for the CDB One write per cycle, oldest first; the younger slips.
  • A WAW wait at issue for an earlier writer of the destination The scoreboard stalls there; Tomasulo renames the destination and goes on.

RAW and structural: everything the Hazards column can hold besides "solved by renaming".

Key take-aways

  • Three stages: Issue in program order (decode, allocate a station or stall, copy values or tags, rename the destination through Qi); Execute out of order when Qj = Qk = 0 and the unit is free; Write Result out of order as one ⟨tag, value⟩ broadcast on the CDB.
  • Issue stalls when a resource is missing (no free station, a full load/store queue) and, in the basic machine, behind an unresolved branch — never on a data hazard; it is kept in order so that the youngest writer owns each register, not for precise exceptions.
  • A station is busy from ISSUE through WRITE RESULT; a unit is busy from START EXEC through WRITE RESULT; a result broadcast at w is usable at w + 1; one CDB carries one result per cycle, oldest first.
  • At the broadcast every matching Qj / Qk fills in; the register is written only if its Qi still names the broadcaster — an older writer's value reaches the stations that wait for it and is dropped at the register file (Example 8 done right).
  • Stores wait for address and data (the data may arrive on the CDB), keep program order, write memory and never broadcast on the CDB; their WRITE RESULT cell is the end of the memory write.
  • Part 1 of the exercise: true = nearest earlier writer of a source, anti = every earlier reader of the destination, output = every earlier writer of it; every pair once per register, R1 included. A dependence belongs to the program, a hazard to the machine.
  • June 2026: 19 cycles, CPI = 19 / 7 ≈ 2.71, and every cycle lies on the F2 chain; the hardware overlapped the rest.
