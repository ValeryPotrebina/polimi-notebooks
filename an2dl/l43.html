Лаба 1. Первая сеть на PyTorch

После этого урока ты напишешь по памяти весь путь от таблицы цветков до обученной сети на PyTorch — данные, DataLoader, nn.Module, цикл обучения — и по форме кривой узнаешь баг, который не выдаёт ни одной ошибки.

Сеть из 259 чисел 500 эпох учится различать три вида ирисов. На 75-й эпохе она впервые угадывает все 20 цветков validation set — проверочной выборки, на которой сеть не учится. С 138-й эпохи и до конца угадывает 19 из 20: accuracy, доля верных ответов, стоит на 95 %.

Похоже на overfitting (переобучение), и остановиться стоило бы на 75-й. Но validation loss, ошибка сети на тех же 20 цветках, всё это время падает: с 0.336 до 0.091. А на test-цветках, отложенных до самого конца, каждая «идеальная» эпоха даёт 90 %, финальная модель — 95 %.

И ещё: 10 из 32 скрытых нейронов заканчивают обучение с теми же весами, с какими начали, бит в бит. В консоли ни одной ошибки. К концу урока обе странности получат объяснение.

От цветков к батчам

Данные — классический Iris: 150 цветков, у каждого четыре размера в сантиметрах (длина и ширина чашелистика, sepal, и лепестка, petal) и вид: Setosa, Versicolor или Virginica, по 50 штук. Setosa отрезается одной прямой по лепесткам, а два других вида заходят друг на друга ("One class is linearly separable from the other 2; the latter are NOT linearly separable from each other", из описания датасета). Граница одного нейрона — плоскость, и такую пару она без ошибок не разделит. Поэтому лаба берёт сеть со скрытым слоем: её граница может изгибаться (урок 8).

X = iris_dataset.values.astype(np.float32)
y = target.astype(np.int64)

X_train, X_val, y_train, y_val = train_test_split(
    X_train_val, y_train_val, test_size=20, random_state=SEED, stratify=y_train_val

  • float32 — тип весов во всех слоях PyTorch. NumPy по умолчанию даёт float64, и такой вход nn.Linear не примет: "mat1 and mat2 must have the same dtype".
  • int64 — метки как номера классов 0, 1, 2. CrossEntropyLoss ждёт их в этом типе (или в uint8): с int32 или float он падает с "expected target dtype to be Long or Byte".
  • test_size=20 целым числом — это 20 строк, а не доля. Два разреза дают 110 / 20 / 20: training для обучения, validation для наблюдения за ним, test для одной финальной оценки (урок 18). stratify сохраняет доли видов: в validation 7, 7 и 6 цветков.

Обе ошибки типов громкие: код падает сразу и с понятным сообщением. Это хорошие ошибки. Плохие будут в разделе 3.

min_df = X_train.min(axis=0)
max_df = X_train.max(axis=0)

X_train = (X_train - min_df) / (max_df - min_df)
X_val = (X_val - min_df) / (max_df - min_df)
X_test = (X_test - min_df) / (max_df - min_df)

Min-max scaling (масштабирование) переводит каждый признак обучающей выборки в отрезок [0, 1]. Минимум и максимум берут только по X_train и теми же числами сдвигают validation и test: иначе сведения о проверочных цветках протекли бы в обучение (урок 18). Поэтому проверочные значения могут выйти за [0, 1]: самый длинный чашелистик validation, 7.9 см, длиннее обучающего максимума 7.7 и превращается в 1.06. Так и должно быть. И запомни: после scaling все обучающие входы неотрицательны. В разделе 5 это аукнется.

  • torch.from_numpy делает из массива tensor — многомерный массив PyTorch — того же типа. TensorDataset склеивает i-ю строку признаков с i-й меткой.
  • DataLoader нарезает выборку на mini-batches, порции по 16 цветков (урок 27). 110 = 6 · 16 + 14: за эпоху 7 батчей, последний из 14 цветков. Каждый батч — пара: x формы [16, 4] (float32) и y формы [16] (int64).
  • shuffle=True стоит только у обучающего: каждую эпоху цветки перемешиваются заново, и батчи всякий раз другие. Validation и test только оцениваются, порядок там ничего не меняет.

Сеть, которая возвращает logits

class FeedForwardNet(nn.Module):
    def __init__(self, in_features, hidden_size, num_classes):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(in_features, hidden_size),
            nn.ReLU(),
            nn.Linear(hidden_size, num_classes)
        )

    def forward(self, x):
        return self.net(x)
  • Модель — наследник nn.Module. Строка super().__init__() обязательна и идёт первой: без неё self.net = … падает с "cannot assign module before Module.__init__() call". Именно nn.Module потом собирает все веса для model.parameters() и state_dict().
  • nn.Linear(4, 32) — слой из урока 9: каждый из 32 нейронов берёт взвешенную сумму четырёх входов и прибавляет свой bias (смещение). Веса хранятся матрицей [32, 4], строка на нейрон. Дальше nn.ReLU() и второй nn.Linear(32, 3): три числа на цветок.
  • forward отдаёт выход последнего слоя как есть. Эти три числа — logits: сырые оценки классов, без softmax. Вызов model(x) запускает forward.
device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
model = FeedForwardNet(input_features, HIDDEN_SIZE, num_classes).to(device)

.to(device) переносит параметры на GPU, если он есть (наш запуск шёл на CPU). Батчи в цикле переносятся той же строкой, x.to(device): модель и данные на разных устройствах — снова громкая ошибка.

LEARNING_RATE = 1e-3
EPOCHS = 500

criterion = nn.CrossEntropyLoss()
optimizer = torch.optim.Adam(model.parameters(), lr=LEARNING_RATE)

nn.CrossEntropyLoss принимает logits формы [B, 3] и метки [B] типа int64. Softmax он делает сам, вместе с логарифмом (log-softmax), и считает cross-entropy из урока 11, усреднённую по батчу:

\[ y_{n,k} = \frac{e^{z_{n,k}}}{\sum_j e^{z_{n,j}}} \] \[ E = -\frac{1}{B}\sum_{n=1}^{B} \ln y_{n,c_n} \]
\(z_{n,k}\)
logit класса k у n-го цветка батча (в уроке 11 — \(a_k\))
\(y_{n,k}\)
его вероятность после softmax
\(c_n\)
верный класс, число из y
\(B\)
размер батча: 16, в последнем 14

Поэтому в модели нет softmax. Вероятности нужны только человеку: torch.softmax(logits, dim=1). Для ответа хватает logits.argmax(dim=1): softmax не меняет порядок чисел, и у самого большого logit самая большая вероятность.

Лишний nn.Softmax в конце модели — тихий баг. Loss применит softmax ещё раз, к числам из [0, 1], и даже идеальный ответ (1, 0, 0) обойдётся дорого:

\[ \begin{aligned} -\ln\frac{e^{1}}{e^{1}+e^{0}+e^{0}} &= \ln\Bigl(1+\frac{2}{e}\Bigr) \\ &\approx 0.551 \end{aligned} \]

Ниже loss не опустится никогда, а accuracy при этом может быть в полном порядке.

torch.optim.Adam — Adam из урока 27. lr — learning rate, шаг обучения, в обозначениях теории \(\eta\) (lr = η); 1e-3 — значение Adam по умолчанию. Оптимизатор получает model.parameters() и запоминает ссылки именно на эти тензоры. Создай model заново после этой строки — и он останется со старыми тензорами: градиенты пойдут в новую модель, а у старой их нет, так что шаги не сдвинут ни одного веса.

Пять строк, которые учат

def train_one_epoch(model, loader, criterion, optimizer, device):
    model.train()
    total_loss, targets, preds = 0.0, [], []
    for x, y in loader:
        x, y = x.to(device), y.to(device)
        logits = model(x)               # (1)
        loss = criterion(logits, y)     # (2)
        optimizer.zero_grad()           # (3)
        loss.backward()                 # (4)
        optimizer.step()                # (5)
        total_loss += loss.item() * x.size(0)
        targets.append(y.cpu())
        preds.append(logits.argmax(dim=1).cpu())
    return total_loss / len(loader.dataset), accuracy_score(torch.cat(targets), torch.cat(preds))

Номера (1)–(5) — наши пометки. Что трогает каждая строка:

  1. Forward pass, прямой проход: батч [16, 4] превращается в logits [16, 3]. Попутно PyTorch записывает граф операций — журнал, по которому потом пойдёт обратный проход.
  2. Loss батча: одно число, тензор без размерностей с графом за спиной.
  3. Обнуляет .grad всех 259 параметров (точнее, ставит None). Он нужен из-за следующей строки.
  4. Backpropagation из урока 14: проход по графу от loss назад, который прибавляет \(\pd{E}{w}\) к .grad каждого параметра. Потом граф освобождается.
  5. Шаг Adam: читает .grad и меняет сами веса. Веса трогает только эта строка.

backward() прибавляет к .grad, а не записывает заново, поэтому zero_grad() стоит до него.

Ставь optimizer.zero_grad() первой строкой тела цикла: тогда он не окажется случайно между backward() и step(). Там он стирает только что посчитанный градиент, и step() пропускает параметры без градиента.

Остальные строки — бухгалтерия. loss.item() достаёт из тензора обычное число Python, уже без графа. Его умножают на x.size(0), размер батча, а в конце делят на 110: последний батч из 14 цветков весит меньше полных. На первой эпохе такое среднее равно 1.1141, простое среднее семи батчей — 1.1144. logits.argmax(dim=1) — предсказанный класс каждого цветка.

def evaluate(model, loader, criterion, device):
    model.eval()
    total_loss, targets, preds = 0.0, [], []
    with torch.no_grad():
        for x, y in loader:
            x, y = x.to(device), y.to(device)
            logits = model(x)
            total_loss += criterion(logits, y).item() * x.size(0)
            targets.append(y.cpu())
            preds.append(logits.argmax(dim=1).cpu())
    return total_loss / len(loader.dataset), accuracy_score(torch.cat(targets), torch.cat(preds))

Проверку от обучения отличают две строки. model.eval() переключает слои, которые при обучении и при проверке ведут себя по-разному: dropout (урок 23) и batch normalization (урок 26); model.train() в начале эпохи включает режим обучения обратно. В нашей сети таких слоёв нет, и числа не изменились бы, но со второй лабы это важно. torch.no_grad() не записывает граф: backward при проверке не нужен, а память и время экономятся. Ни одна из двух строк не трогает веса.

for epoch in range(1, epochs + 1):
    train_loss, train_acc = train_one_epoch(model, train_loader, criterion, optimizer, device)
    val_loss, val_acc = evaluate(model, val_loader, criterion, device)

Это ядро fit; остальное в ней — история, печать и живые графики. В fit нет ни early stopping (ранней остановки), ни сохранения лучшей эпохи: после 500 эпох в model лежат веса последней. Живые графики съедают почти всё время: три минуты с ними против 7.5–20 секунд без них.

Шесть изменений без единой ошибки

Громкие ошибки ловит сам PyTorch. Опаснее те, после которых код честно отрабатывает 500 эпох. Мы прогнали лабу ещё шесть раз, каждый раз меняя одну вещь при том же seed. Ни один прогон не выдал ошибки, но каждый оставил на кривой training loss свой след.

Одна строка — одна кривая

Training loss по эпохам: правильный код и тот же код с одним изменением, реальные прогоны. Пунктиры — два уровня, которые стоит узнавать в лицо: \(\ln 3\) и \(\ln(1 + 2/e)\). В режиме загадки название изменения скрыто: выбери в списке свой диагноз.

  1. Предскажи, как выглядит кривая, если optimizer.zero_grad() стоит между backward() и step(). Выбери этот вариант, потом «model создана заново после optimizer».
    Что должно получиться

    Обе кривые — ровные линии, 1.1225 и 1.1108: это loss начальных весов, которые так и не сдвинулись. В первом случае zero_grad() ставит .grad = None перед самым шагом, и Adam пропускает параметры без градиента. Во втором оптимизатор держит тензоры старой модели: градиентов у них нет, и Adam их тоже пропускает, а новая модель получает градиенты, но ни одного шага. Validation accuracy — 0.35, как у необученной сети. Плоская линия около ln 3 значит «веса не меняются».

  2. Лишний nn.Softmax: опустится ли loss ниже 0.5 за 500 эпох? Что будет с accuracy?
    Что должно получиться

    Не опустится. Кривая застывает чуть выше пола \(\ln(1 + 2/e) \approx 0.551\): на 500-й эпохе 0.584, а validation accuracy — те же 0.95, что без бага. По accuracy этот баг не виден совсем, только по loss.

  3. Удали zero_grad(): обучение пойдёт быстрее или медленнее? А если строки отсортированы по видам и не перемешиваются? А без scaling?
    Что должно получиться

    Без zero_grad() сначала быстрее: к 100-й эпохе 0.066 против 0.258, ведь каждый шаг делается по сумме всех прошлых градиентов. Потом эта сумма разгоняет веса, и кривая срывается: 1.21 на 260-й эпохе, 0.28 в конце, validation 0.90. Отсортированные строки без shuffle учатся медленнее (0.108 против 0.062 в конце): в каждой эпохе сначала одни Setosa, потом Versicolor, потом Virginica, и шаги тянут сеть то к одному виду, то к другому. Без scaling старт выше ln 3, 1.348: сантиметры до 7.7 дают крупные logits. На ирисах это сходит с рук (validation 1.00), но старт не около ln K — первый тревожный сигнал.

  4. Включи режим загадки и поставь диагноз нескольким загадкам подряд («Следующая загадка»). Какие две нельзя различить по одной кривой?
    Что должно получиться

    Две плоские: zero_grad() между backward() и step() и модель, созданная после оптимизатора. Уровень линии задают только случайные начальные веса, так что различает их лишь код: порядок строк шага и то, какая model была передана в optimizer. Остальные узнаются по форме: пол на 0.551, быстрый спуск со срывом, медленный спуск, старт выше ln 3.

500 эпох на 20 цветках

Первая эпоха: training loss 1.1141, почти \(\ln 3 = 1.0986\). Столько стоит ответ «не знаю» — по трети на каждый класс, ведь \(-\ln\frac13 = \ln 3\). Свежая сеть так и отвечает, в среднем 0.40 / 0.30 / 0.30. Старт около \(\ln K\) — первая проверка любого обучения на K классов: если loss первой эпохи заметно другой, причину ищи ещё до цикла, в данных или в модели (без scaling, например, старт 1.348). К 500-й эпохе: 0.0618 на training и 0.0914 на validation.

Две кривые loss меряют по-разному. Training loss — среднее по батчам во время эпохи: первые батчи посчитаны ещё старыми весами. Validation loss считается после эпохи, новыми весами. Первые 60 эпох validation идёт ниже training, что для кривых обучения необычно. Отчасти это запаздывание: если мерить training тоже после эпохи, кривые пересекаются уже на 49-й. Остальное — 20 лёгких проверочных цветков.

Лестница и склон

Повтор нашего запуска по эпохам. Сверху loss, ниже — доля верных ответов на 110 обучающих и 20 проверочных цветках, внизу — вероятности трёх видов у validation-цветка 17. Жирным подписан его настоящий вид, жёлтым выделен ответ сети.

  1. Предскажи: сколько разных значений может принимать validation accuracy на 20 цветках? Потом проведи эпоху от 1 до 150 и сравни, как движутся кривые loss и лесенки accuracy.
    Что должно получиться

    21 значение: 0, 0.05, …, 1. Validation-лесенка шагает по 5 пунктов, по одному цветку, и подолгу стоит на месте; training-лесенка — по 0.9 пункта (1 из 110). Loss тем временем скользит плавно и почти всё время вниз: он чувствует уверенность сети на каждом цветке, а accuracy замечает цветок, только когда тот переходит границу.

  2. Поставь эпоху 74, затем 75. Сколько цветков прибавилось и что стало со столбиками цветка 17? Предскажи, сколько раз он ещё сменит ответ до 138-й эпохи, и проверь, двигая ползунок по одной эпохе (стрелками).
    Что должно получиться

    На 74-й эпохе верно 18 из 20, на 75-й — 20: исправились сразу два цветка, и один из них — цветок 17, у которого теперь 0.499 за Versicolor против 0.488 за Virginica. Дальше он качается на границе: до 138-й эпохи ответ меняется 19 раз, и каждое «100 %» — это его удачная эпоха.

  3. Включи test accuracy. Предскажи, какая модель лучше на test: из эпохи со 100 % на validation или финальная.
    Что должно получиться

    Финальная. Во всех 42 эпохах со 100 % на validation test accuracy равна 0.90, а с 240-й эпохи и до конца — 0.95. Граница, при которой цветок 17 оказывается Versicolor, даёт на test две ошибки вместо одной. Выбирать эпоху по такой accuracy — значит выбирать по одному цветку. Test после каждой эпохи — наш дополнительный замер: в лабе его открывают один раз, в конце, и так и надо делать.

Разгадка первой странности. Окно 100 % — это один цветок: validation-цветок 17 (X_val[17]), Versicolor с лепестком 4.5 × 1.5 см, на самой границе с Virginica. На 75-й эпохе за Versicolor у него 0.499 против 0.488, до 138-й ответ меняется 19 раз, а дальше сеть каждую эпоху зовёт его Virginica, к концу с вероятностью 0.653. Accuracy видит только, по какую сторону границы лёг цветок. Loss измеряет уверенность на всех 20, и остальные 19 всё это время становятся увереннее: validation loss 0.336 на 75-й эпохе, 0.209 на 138-й, 0.089 на 498-й. Overfitting выглядел бы иначе: validation loss развернулся бы вверх (урок 20).

«Validation accuracy выросла с 95 до 100 % — модель стала лучше». На 20 цветках шаг accuracy — 5 пунктов, один цветок, а стандартная ошибка \(\sqrt{0.95 \cdot 0.05 / 20} \approx 0.05\) (урок 18): разница в цветок-два — шум. Мы проверили по числам этого запуска, что сделал бы early stopping с терпением 20 эпох (в лабе его нет). По validation accuracy он остановился бы на 95-й эпохе и вернул веса 75-й: 90 % на test. По validation loss не остановился бы вовсе и взял бы 498-ю: 95 %. На такой выборке accuracy читай в цветках, а не в процентах, и всегда рядом с loss.

  • state_dict() — словарь «имя → тензор»: net.0.weight [32, 4], net.0.bias [32], net.2.weight [3, 32], net.2.bias [3]. Числа 0 и 2 — номера слоёв в nn.Sequential; слой 1 — ReLU, весов у него нет.

«best_model — лучшая эпоха обучения». Нет: fit ничего не выбирает, и в файле лежат веса 500-й эпохи. Имя обещает выбор, которого в этой лабе нет; лучшую эпоху начнут выбирать и восстанавливать во второй лабе, вместе с early stopping.

На test сеть права в 19 случаях из 20: accuracy 0.95; macro precision, recall и F1 (средние по трём классам) — 0.958, 0.952 и 0.952.

Единственная ошибка — test-цветок 18: Versicolor с чашелистиком 6.7 × 3.0 см и лепестком 5.0 × 1.7 см, то есть с лепестком размера Virginica (рис. 4). Сеть даёт ему 0.61 за Virginica, и это не случайность последней эпохи: если проверять test после каждой эпохи (наш дополнительный замер), он неверен на 498 эпохах из 500. По четырём размерам этот цветок похож на чужой вид, и обучением такое не исправить.

Числа сдвигает даже строка с summary(): она прогоняет через сеть случайный батч и тем самым меняет все следующие случайные числа.

Внутри сети: веса, градиенты, мёртвые нейроны

Лаба следит и за самими параметрами: раз в 20 эпох рисует распределение чисел каждого тензора, и гистограммы стоят друг за другом, как гребёнка. Что на них видно:

  • веса первого слоя, W1, расползаются из ±0.5 примерно до ±1.5;
  • у bias скрытого слоя, b1, есть пик, который не двигается совсем;
  • веса второго слоя, W2, расходятся от −1.8 до 1.2, но узкий пик в центре стоит на месте;
  • bias выхода, b2, — всего три числа: от 0.126, −0.136, 0.127 к 0.323, 0.108, −0.249 (Setosa, Versicolor, Virginica);
  • гистограммы градиентов показывают последний батч эпохи: шум с пиком у нуля. Три градиента b2 на любом батче в сумме дают ноль: \(\pd{E}{z_k} = y_k - t_k\) (урок 11), а и \(y_k\), и \(t_k\) в сумме дают 1.

«Широкие градиенты — большие шаги» ("wide gradients mean large steps", подпись к гистограммам градиентов в лабе). Так работает SGD: там шаг равен \(\eta \cdot g\). Adam делит на среднеквадратичный градиент самого веса (урок 27):

\[ w_{k+1} = w_k - \eta\,\frac{\hat m_k}{\sqrt{\hat v_k} + \varepsilon} \]

Дробь порядка единицы или меньше, поэтому шаг любого веса — около \(\eta = 10^{-3}\) или меньше, как бы ни были широки градиенты. На первой эпохе у b2 самые большие градиенты и самые маленькие шаги, а к 500-й шаги всех четырёх тензоров около \(10^{-4}\). Ширина гребёнки говорит о шуме градиента, но не о размере шага.

Десять нейронов, родившихся мёртвыми

Вторая странность из начала урока. Нейрон с ReLU мёртв (dead ReLU, урок 24), если его вход до ReLU, pre-activation \(a\), не больше нуля на всех обучающих примерах. Тогда выход всегда 0 и производная ReLU всегда 0: градиент не доходит ни до четырёх входящих весов, ни до bias. Исходящие веса умножаются на его нулевой выход, и их градиент тоже ноль. А если градиент нулевой с самого первого шага, то и шаг Adam нулевой: \(\hat m\) и \(\hat v\) так и остаются нулями.

В нашем запуске мертвы 10 из 32 нейронов, причём с самой инициализации, до первого шага. Ещё один, нейрон 21, умирает на 23-й эпохе. Через 500 эпох бит в бит совпадают с начальными 40 из 128 весов W1, 10 из 32 чисел b1 и 30 из 96 весов W2 — ровно строки и столбцы десяти мёртвых от рождения. Это и есть неподвижные пики на гребёнках.

Причина — два обстоятельства вместе. Все входы после min-max неотрицательны. А PyTorch берёт и веса, и bias слоя nn.Linear(4, 32) из \(U(-0.5,\ 0.5)\), где \(0.5 = 1/\sqrt{4}\). В уроке 25 bias стартует с нуля — PyTorch по умолчанию делает иначе. Нейрону с отрицательным bias и в основном отрицательными весами неоткуда взять плюс: у 9 из 10 мёртвых bias от −0.2 до −0.5.

Бывает и обратное: нейрон отвечает на всех 110 цветках. Он жив, но работает как линейный — его излом лежит вне данных. Таких на старте 8, к концу обучения семь из них загнуты внутрь данных.

Родились мёртвыми

Каждая строка — скрытый нейрон, точки на ней — его pre-activation \(a\) на 110 обучающих цветках нашего разбиения. В серой зоне слева ReLU выдаёт 0. Справа от строки крест — мёртвый нейрон (все точки слева от нуля), кружок — линейный (все справа).

  1. Найди мёртвый нейрон, чьи точки почти дотягиваются до нуля. Предскажи: оживёт ли он за 500 эпох, раз до жизни так близко?
    Что должно получиться

    Нейрон 31: его самая правая точка около −0.03, у остальных девяти мёртвых она левее −0.2. Bias у него даже положительный, +0.06, но все четыре веса отрицательные, и на неотрицательных входах сумма уходит в минус на каждом цветке. Не оживёт: градиент у него не маленький, а ровно нулевой, так что близость к нулю ничего не даёт — через 500 эпох его веса те же, бит в бит.

  2. Оставь наши веса и переключи входы на z-score. Предскажи число мёртвых. Затем — сырые сантиметры.
    Что должно получиться

    z-score: мёртвый один, линейных ни одного, гнутся 31. Центрированные входы бывают и положительными, и отрицательными, поэтому излом почти каждого нейрона проходит сквозь облако данных. Сырые сантиметры: 13 мёртвых и 12 линейных — входы до 7.7 см ещё дальше уводят излом от данных.

  3. Выбери новые веса из U(−0.5, 0.5) и понажимай «Новые веса» при входах min-max. Сколько мёртвых бывает? Сравни среднее по 200 наборам с z-score.
    Что должно получиться

    От набора к набору мёртвых обычно от 5 до 13; в среднем по 200 наборам 9.0 мёртвых и 8.8 линейных, примерно по четверти слоя. С z-score в среднем 0.2 мёртвых и 0.3 линейных. Главное здесь: неотрицательные входы вместе с bias из U(−0.5, 0.5) выключают около четверти нейронов ещё до первого шага, центрированные входы заставляют почти каждый нейрон гнуться внутри данных.

Как не терять нейроны: центрировать входы (с z-score вместо min-max при тех же весах мёртвым остаётся один), начинать bias с нуля или с маленького плюса, взять Leaky ReLU (урок 24). Ирисам потеря не вредит: 21 рабочего нейрона хватает с запасом. Обе странности начала урока объяснились: окно 100 % — один нерешительный цветок, а неподвижные веса — десять нейронов, которым за 500 эпох не пришло ни одного градиента.

Если PyTorch впервые

Карточка только с тем, что встречается в коде этой лабы. В примерах x = torch.tensor([[5.1, 3.5], [4.9, 3.0]]) — два цветка по два признака, a — массив NumPy.

Производные PyTorch считает сам, если попросить его следить за тензором (requires_grad=True):

w = torch.tensor(2.0, requires_grad=True)
loss = 3 * w ** 2
loss.backward()      # d(3w²)/dw = 6w
w.grad               # tensor(12.)

У параметров nn.Linear этот флаг уже стоит, и loss.backward() заполняет .grad всех 259 сразу. Посчитай loss ещё раз и снова вызови backward(), не обнулив .grad, — получится tensor(24.): градиенты складываются.

Из Python лаба берёт три вещи: класс-наследник с super().__init__(), распаковку пары в цикле for x, y in loader и блок with torch.no_grad(): — всё внутри блока выполняется без записи графа. Подробнее — в трёх вводных ноутбуках к лабам: по Python, NumPy и тензорам PyTorch.

A fully connected network for the Iris data set has 4 inputs, one hidden layer of 32 ReLU units and 3 output units; both layers have biases. How many trainable parameters does it have?

Hidden layer: 4 · 32 weights + 32 biases = 160. Output layer: 32 · 3 + 3 = 99. Total: 259.

Проверяют, не забыты ли bias: без них вышло бы 224. Следом могут спросить: "How many weight updates does Adam make in 500 epochs with 110 training samples and batch size 16?" — 7 за эпоху (последний батч из 14), всего 3500.

This training loop runs without any error message. What is wrong, what would you see in the training loss, and how do you fix it?

for x, y in train_loader:
    x, y = x.to(device), y.to(device)
    logits = model(x)
    loss = criterion(logits, y)
    loss.backward()
    optimizer.step()
Show model answer

optimizer.zero_grad() is missing. loss.backward() adds the new gradients to the .grad already stored in every parameter, so each step uses the sum of all gradients computed so far instead of the gradient of the current batch. The loss typically falls faster at first, then the accumulated gradient makes the steps unstable and the loss jumps up and oscillates. Fix: call optimizer.zero_grad() in every iteration before loss.backward(), for example as the first line of the loop body.

В нашем прогоне так и вышло: 0.066 на 100-й эпохе против 0.258, затем скачок до 1.21 на 260-й. Следом спрашивают: "Can zero_grad() go between backward() and step()?" — нет: он сотрёт только что посчитанный градиент, и веса не сдвинутся вовсе.

The model below is trained with criterion = nn.CrossEntropyLoss(). The accuracy is good, but the training loss never goes below about 0.55. Explain why and fix the code.

self.net = nn.Sequential(
    nn.Linear(in_features, hidden_size),
    nn.ReLU(),
    nn.Linear(hidden_size, num_classes),
    nn.Softmax(dim=1)
)
Show model answer

nn.CrossEntropyLoss expects raw logits and applies log-softmax itself. With nn.Softmax in the model it receives probabilities in [0, 1] and applies softmax a second time. Even the perfect output (1, 0, 0) then costs −ln(e / (e + 2)) = ln(1 + 2/e) ≈ 0.551 for three classes, so the loss has a floor, and the gradients are squashed. The argmax is unchanged, which is why the accuracy still looks fine. Fix: remove nn.Softmax and apply torch.softmax(logits, dim=1) only when probabilities are needed.

Следом спрашивают: "Why does PyTorch put softmax and the logarithm into one loss?" — так устойчивее численно (логарифм суммы экспонент не переполняется), а градиент по logits выходит простым: \(y_k - t_k\).

A network is trained for 500 epochs with a validation set of 20 samples. Validation accuracy first reaches 100% at epoch 75, alternates between 100% and 95% until epoch 137 and stays at 95% from epoch 138 to 500, while the validation loss keeps decreasing, from 0.34 at epoch 75 to 0.09. Is the network overfitting? Would early stopping on validation accuracy be a good choice here?

Show model answer

There is no sign of overfitting: overfitting shows up as a validation loss that starts to increase, and here it keeps decreasing. With 20 samples one sample is 5 percentage points (standard error about √(0.95 · 0.05 / 20) ≈ 0.05), so 100% → 95% is a single borderline sample crossing the decision boundary while the others become more confident. Early stopping on validation accuracy would pick epoch 75 because of that one sample, which is noise. A larger validation set or cross-validation is needed to compare epochs, and the validation loss should be read together with the accuracy.

Проверяют два факта: overfitting — это рост validation loss, а шаг accuracy на маленькой выборке — один пример. В нашем запуске выбор по accuracy дал бы 90 % на test против 95 % у финальной модели. Следом спрашивают: "So which epoch would you keep?" — ту, где validation loss минимален (здесь почти последнюю); сравнивать эпохи по одному цветку нельзя.

In a 4–32–3 ReLU network trained with Adam on min-max-scaled inputs (all features in [0, 1]), 10 of the 32 hidden units output 0 for every training sample already at initialisation, and after training their weights are exactly the initial ones. Explain why, and propose two remedies.

Show model answer

They are dead ReLU units: the pre-activation a = w·x + b is ≤ 0 for every training input, so the output is 0 and the derivative of ReLU is 0. No gradient reaches the incoming weights and the bias, and the outgoing weights get the gradient δ·h = 0. With zero gradients the Adam update is zero, so nothing changes. It happens here because all inputs are non-negative and PyTorch initialises the weights and the biases of nn.Linear uniformly in ±1/√n_in = ±0.5: a unit with a negative bias and mostly negative weights is negative on the whole data set. Remedies: zero-centred inputs (standardisation), biases initialised at zero or slightly positive, Leaky ReLU or ELU instead of ReLU.

Следом спрашивают: "Is a unit that outputs 0 on half of the samples dead?" — нет, это sparse activation: мёртвый нейрон молчит на всех обучающих примерах.

In the evaluation function below, what do model.eval() and torch.no_grad() each do? What changes if you forget one of them, in this Linear–ReLU network and in a network with dropout?

def evaluate(model, loader, criterion, device):
    model.eval()
    total_loss, targets, preds = 0.0, [], []
    with torch.no_grad():
        for x, y in loader:
            ...
Show model answer

model.eval() switches the layers that behave differently in training and inference to inference mode: dropout stops dropping units and batch normalization uses its running statistics. It does not disable gradients. torch.no_grad() stops autograd from recording the computation graph, which saves memory and time; it does not change any output. In the Linear–ReLU network forgetting either one changes no number. With dropout, forgetting model.eval() gives noisy, too pessimistic validation results; forgetting torch.no_grad() only wastes memory.

Частая путаница — думать, что eval() выключает градиенты. Следом спрашивают: "Why is model.train() called at the start of every epoch?" — потому что evaluate() в конце прошлой эпохи перевёл модель в режим eval.

Проверь себя

Сколько раз за одну эпоху этой лабы вызывается optimizer.step()?

  • 1 Один шаг за эпоху был бы при батче размером со всю выборку, 110. Здесь батч 16.
  • 7 110 цветков по 16: шесть полных батчей и один из 14. Шаг делается после каждого батча.
  • 16 16 — размер батча, а не число батчей.
  • 110 Так было бы при batch_size=1, по шагу на цветок.

Что возвращает model(x) для батча x формы [16, 4]?

  • Тензор [16, 3] вероятностей, каждая строка в сумме 1 Вероятности даёт только torch.softmax(logits, dim=1); в модели softmax нет, его делает loss.
  • Тензор [16] с номерами классов Это logits.argmax(dim=1), отдельный шаг после модели.
  • Тензор [16, 3] с logits Последний слой — Linear(32, 3), softmax в модели нет: три сырые оценки на цветок.
  • Одно число — loss батча Loss считает criterion(logits, y), а не модель.

Какие изменения в коде лабы пройдут без единой ошибки, но испортят обучение? Отметь все.

  • Метки y в int32 вместо int64 Это громкая ошибка: CrossEntropyLoss сразу падает с "expected target dtype to be Long or Byte".
  • Удалить optimizer.zero_grad() Градиенты копятся от шага к шагу: кривая сначала быстрая, потом срывается.
  • Добавить nn.Softmax(dim=1) в конец модели Softmax применяется дважды, и loss упирается в пол 0.551.
  • Признаки в float64 вместо float32 Тоже громкая: nn.Linear падает с "mat1 and mat2 must have the same dtype".
  • Переставить zero_grad() между backward() и step() Градиент стирается перед самым шагом: веса стоят, loss — ровная линия около 1.12.
  • Создать model заново после строки с optimizer Оптимизатор держит параметры старой модели; новая не получает ни одного шага.

Ошибки типов PyTorch ловит сам. Ошибки порядка и смысла выдаёт только кривая loss.

Почему минимум и максимум для min-max scaling берут только по X_train?

  • Чтобы validation и test точно попали в [0, 1] Наоборот: с чужими минимумом и максимумом они могут выйти за отрезок, как 1.06 у самого длинного чашелистика validation. Это нормально.
  • Чтобы сведения о validation и test не попали в обучение Иначе проверочные цветки влияют на входы обучения, и оценка выходит оптимистичной: это утечка.
  • У validation минимум и максимум не определены Определены, как у любой непустой выборки. Их не берут по другой причине.
  • Так быстрее считать Разница во времени ничтожна; дело в честности оценки.

Validation accuracy на 20 цветках упала со 100 % до 95 %, а validation loss продолжает падать. Что это, скорее всего?

  • Начался overfitting, пора останавливаться Overfitting виден по росту validation loss, а здесь он падает.
  • Слишком большой learning rate Тогда скакал бы и loss, а он падает плавно.
  • В validation попали обучающие цветки Утечка сделала бы validation слишком хорошим, а не хуже.
  • Один пограничный цветок перешёл границу, остальные стали увереннее 5 пунктов на 20 цветках — один цветок, а loss следит за уверенностью на всех.

Нейрон мёртв с самой инициализации. Что будет с его входящими весами после 500 эпох Adam?

  • Чуть сдвинутся: Adam растягивает даже маленький градиент до шага около lr Растягивать нечего: градиент не маленький, а нулевой.
  • Обнулятся Их ничто не обнуляет; без weight decay они просто стоят.
  • Останутся точно такими же, бит в бит Градиент ровно 0 на каждом шаге, моменты Adam остаются нулями, и шаг тоже 0.
  • Уйдут далеко из-за накопленного momentum Momentum копит прошлые градиенты, а у этого нейрона их не было ни одного.

Унести с собой

  • Конвейер лабы: признаки float32 и метки int64, разбиение 110 / 20 / 20 со stratify, min-max по training, TensorDataset и DataLoader с батчем 16 и shuffle только у training.
  • Модель возвращает logits; softmax живёт внутри CrossEntropyLoss, и лишний nn.Softmax молча ставит loss на пол 0.551.
  • Шаг обучения — пять строк в таком порядке: forward, loss, zero_grad(), backward(), step(); backward() прибавляет к .grad, поэтому обнуление идёт до него.
  • Ошибки типов громкие, ошибки порядка тихие: их выдаёт только форма кривой loss — плоская, с полом, со срывом или слишком медленная.
  • Loss первой эпохи около ln K — первая проверка обучения; на 20 validation-цветках accuracy шагает по 5 пунктов, и окно 100 % — один пограничный цветок, а не лучшая модель.
  • С неотрицательными входами и bias из \(U(\pm 1/\sqrt{n})\) часть ReLU-нейронов мертва с рождения и не учится вовсе.
