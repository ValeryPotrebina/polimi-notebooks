CQL: the key that decides everything

After this lesson you will read a PRIMARY KEY line the way Cassandra does — which columns choose the node, which ones sort the rows — predict which SELECT, UPDATE and DELETE it accepts, and write the CQL of every Cassandra exercise of the past papers.

The exercise session asks for a table of cars "sorted by max_speed in ascending order" and answers with the key PRIMARY KEY (car_id, max_speed) and the option WITH CLUSTERING ORDER BY (max_speed ASC) (p. 1607). Cassandra accepts the table without a word.

Load nine cars and ask for all of them with SELECT * FROM car;. One run printed the speeds 340, 190, 180, 160, 320, 160, 296, 180, 170. Ask for the promised order, SELECT * FROM car ORDER BY max_speed;, and Cassandra refuses: "ORDER BY is only supported when the partition key is restricted by an EQ or an IN."

Nothing is broken: the table does exactly what its PRIMARY KEY line says. Read that line as Cassandra reads it, and section 6 repairs the table by moving one column.

Cassandra in one slide, and a keyspace to work in

The slide adds "It's created by Meta". The lecture says "Originally designed at Facebook" (p. 410): the same company, called Meta since 2021.

The session opens with a definition (p. 1548): "Apache Cassandra is a highly scalable, high-performance non-relational, distributed database designed to handle large amounts of data, providing high availability with no single point of failure." The feature list (p. 1549) adds "Highly and Linearly Scalable", "Quick Response Time", "Flexible Data Storage", "Easy Data Distribution", "BASE Properties" and "Fast Writes".

Behind each claim is a mechanism. No master: every node can serve any request and every row is copied to several nodes, so one dead machine stops nothing. A new node takes over its share of the rows, so capacity grows with the nodes. A write is appended to memory and a log without reading first, so writes are fast. How the nodes share the rows is lesson 22; this lesson is the language you talk to them in. The session sums up the theory in two tables worth knowing word for word:

Is a Cassandra write really "partial"?

Not inside one partition. Background from the Cassandra documentation, not from the slides: an INSERT, UPDATE or DELETE that touches one partition is applied as a whole, and a logged BATCH ends up either fully applied or not at all. What Cassandra gives up is the bank transaction: several partitions changed in isolation. Answer with the table as printed, and add this when the question is open. The CAP side of the story is lesson 5.

The vocabulary nests like a filing cabinet. A keyspace is "the outermost container in Cassandra" (p. 1553), roughly a database. It holds tables, the lecture's column families: the keyword TABLE "can be interchanged with COLUMNFAMILY" (p. 1563). Tables hold rows, rows hold columns; lesson 20 draws the picture, and from here on everything is CQL typed at the cqlsh prompt.

-- p. 1553: a keyspace that keeps three copies of every row
CREATE KEYSPACE population
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};

Read it aloud: create a container called population; replicate every row with the simple strategy, three copies. The replication map, strategy plus factor, is the one property a keyspace must declare. On a one-node laptop the statement still runs, with a warning: "Your replication factor 3 for keyspace population is higher than the number of nodes 1".

-- p. 1555: the prompt becomes cqlsh:population>
USE population;
-- p. 1555: list the keyspaces (DESCRIBE tables; and
-- DESCRIBE person; do the same for tables, pp. 1558-1559)
DESCRIBE keyspaces;
-- p. 1556: change the properties of a keyspace
ALTER KEYSPACE population
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 2};
-- p. 1556: remove the keyspace and every table in it
DROP KEYSPACE population;

"Type the code as the slide shows it." The slides print typographic quotes, ‘SimpleStrategy’, and several boxes end without a semicolon. cqlsh rejects the curly quotes ("Invalid syntax at line 1, char 48") and waits for more input until it sees ;. Straight single quotes and a final semicolon, always.

PRIMARY KEY: where a row lives, and in which order

The session's first table (p. 1558) describes people:

-- p. 1558: one partition per person, its rows sorted by age
CREATE TABLE person (
  personal_id text,
  name text,
  age varint,
  birth_date text,
  gender text,
  PRIMARY KEY (personal_id, age)
);

Column by column it is SQL; the last line is not. The columns inside PRIMARY KEY "have different meaning depending on the order and the brackets" (p. 1560), and the slide gives both meanings:

Partition key — "The first value (or set of values) is referred to as the Partition Key(s). It defines how the data is partitioned within the Cassandra nodes." Here: personal_id.

Clustering key — "The second value (or set of values) is named Clustering Key(s). It is used to define the way data is stored within a partition (i.e., the sorting)." Here: age.

The mechanism: Cassandra hashes the partition-key value, and the number that comes out, the token, names the node that stores the row. Rows with the same partition-key value get the same token, so they sit together in one partition on one node, kept sorted by the clustering key. Think of an archive: the hash of the surname picks the building, and inside it the folders stand in date order.

A composite partition key is one value: (Fiat, 2024) and (Fiat, 2023) are two partitions, possibly on two nodes. And the full primary key, partition plus clustering columns, identifies one row: two rows with the same full key are the same row — the trap of section 4.

The list must start at the first clustering column: with clustering columns year, max_speed, the order (max_speed DESC) alone is refused, "Missing CLUSTERING ORDER for column year".

Inside a partition the order is ascending unless the table says otherwise (p. 1554):

-- p. 1554's option (printed ASC), here DESC:
-- in each partition, the oldest first
CREATE TABLE person_by_age_desc (
  personal_id text,
  age varint,
  name text,
  PRIMARY KEY (personal_id, age)
) WITH CLUSTERING ORDER BY (age DESC);

The papers state the key in words:

Inside the inner brackets: where the row lives. After them: the order the rows keep there. All of it together: which row it is.

Changing a table, and what cannot change

The other table statements work as in SQL (pp. 1561–1563), and each accepts COLUMNFAMILY in place of TABLE. The session adds the address that its INSERT fills in section 4:

-- p. 1562: a new column; the existing rows have no value in it
ALTER TABLE person ADD address text;
-- p. 1562: salary, added the same way, is dropped again
ALTER TABLE person DROP salary;
-- p. 1563: remove every row, keep the table
TRUNCATE TABLE person;
-- p. 1563: remove the table itself
DROP TABLE person;

The key is the one thing ALTER cannot touch: ALTER TABLE person DROP age; answers "Cannot drop PRIMARY KEY column age", so a wrong key means a new table and a copy of the data. And this is what "Schema is flexible" (p. 1551) means in CQL: every table declares its columns, a row may leave any non-key column empty at no cost, and ALTER TABLE adds a column at any time.

Reading: what a WHERE clause may say

The query Cassandra is built for names the partition (p. 1567):

-- one hash, one node, one partition: Francesco's rows
SELECT * FROM person WHERE personal_id = 'FRNTRZ95E12F675T';

Cassandra hashes the value, goes to the node that owns the token and reads one partition. A WHERE clause that does not name the partition is a question one hash cannot answer, and the session tries one at once (p. 1568), "Let's retrieve people by gender":

-- refused: gender is neither a key column nor indexed
SELECT * FROM person WHERE gender = 'Male';

cqlsh answers: "Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING". An exact description: to find the men, Cassandra would read every row on every node and throw most of them away.

"To solve the issue, it’s necessary to query with respect to the attributes included in the partition key AND to create a secondary index on gender."

Either one is enough. With an index on gender, SELECT * FROM person WHERE gender = 'Male'; runs with no partition key; with the full partition key and no index, the gender condition needs ALLOW FILTERING, cheap inside one partition.

The session does it itself on p. 1611: CREATE INDEX car_price ON car (price);, then SELECT * FROM car WHERE price = 35000;, no partition key. Both forms run on Cassandra 5.0.9. The printed query fails even earlier: in gender = "male" the double quotes make male a column name (a SyntaxException), and the stored value is 'Male'. The exam may be matched against the printed sentence: know it as printed, and write the either/or in your own answers.

The next slide (p. 1569) lists the rules. In order, each with its reason:

  1. Name every column of the partition key, with = or IN: "WHERE clauses must include ALL components of the partition key". Half a composite key gives no token.
  2. Restrict clustering columns as a prefix, in their order; only the last may be a range. "To filter on a later clustering key, all preceding clustering key(s) must be specified". The rows are sorted by the clustering columns, so such a prefix is one contiguous slice; anything else means hopping. Skip one and cqlsh says, for example, "PRIMARY KEY column "max_speed" cannot be restricted as preceding column "year" is not restricted".
  3. No OR. "Clustering Keys constraints producing non-contiguous results will fail": a range with a hole in it cannot be asked for. Conditions are joined by AND only; the red pen below explains why the slide's own example fails.
  4. Any other column needs a secondary index, and then only =. "To include additional fields in the query, it is necessary to create a secondary index." A range on an indexed column, gender > 'A', still needs ALLOW FILTERING.
  5. ALLOW FILTERING switches the rules off, "although it is not recommended due to bad execution-time performance": Cassandra reads and discards, so the cost grows with the table, not with the answer.

"Clustering Keys constraints producing non-contiguous results will fail (i.e., age < '30' OR age > '33')."

The example fails for another reason: CQL has no OR at all, so it is a syntax error before any key rule is checked, and '30' in quotes is text, not a varint. And "will fail" is too absolute: IN is non-contiguous and runs.

On Cassandra 5.0.9 the printed condition stops at "no viable alternative at input 'OR'". With the key (brand, max_speed, car_id), WHERE brand = 'Ferrari' AND max_speed IN (296, 340) runs and skips the 320 in between. The exam may be matched against the printed rule: know it with its example, and why the example fails.

A SELECT with no WHERE, SELECT * FROM car;, needs no ALLOW FILTERING: it reads everything but discards nothing. The index of rule 4 is created as on p. 1564, and the car exercise uses it so (p. 1611):

-- p. 1611: an index on a column that is not part of the key
CREATE INDEX car_price ON car (price);
-- p. 1611: now legal, without partition key or ALLOW FILTERING
SELECT * FROM car WHERE price = 35000;
-- p. 1610: a range on that column: only ALLOW FILTERING helps
SELECT * FROM car WHERE price > 100000 ALLOW FILTERING;
-- p. 1565: remove an index you no longer need
DROP INDEX person_address;
The slide calls indexes "one of the most important elements of a table". Why does the lecture prefer an "index factory"?

Background from the Cassandra documentation: a secondary index is local. Every node indexes only its own rows, so a query by the indexed column alone asks every node. Fine for a small table, and exactly the exam's "further operation". On a large cluster the lecture's answer scales better: "cassandra is an index factory" (p. 431, lesson 20) — a second table whose partition key is the searched column, so the query is one hash again (section 5).

The bracket grammar on three nodes

Nine cars in the table car (car_id, brand, year, max_speed, price). Choose a PRIMARY KEY and watch the rows move: the partition key places each partition on a node (a toy hash, not Cassandra's), the clustering columns sort the rows inside it. Then pick or type a WHERE clause: the verdict and the message are those of a real Cassandra 5.0.9 node, checked on this very table. Rows the query returns are tinted; rows it reads and then throws away are struck through.

  1. Key (car_id, max_speed), the session's, and "(no WHERE clause)". Before looking: how many partitions are there, and how many rows does each one hold? In what order will SELECT * FROM car; return them?
    What you should see

    Nine partitions of one row each, three per node: car_id is unique, so every car is a partition of its own and max_speed has nothing to sort. The rows come back partition by partition, in token order — the order of hashes, not of speeds. The toy hash gives one order, the real one another; that is why the hook's run printed 340, 190, 180, …

  2. WHERE brand = 'Ferrari'. Switch between ((brand, year), max_speed, car_id) and (brand, year, max_speed, car_id). Predict which one answers without ALLOW FILTERING, and how many nodes each one contacts once you tick it.
    What you should see

    (brand, year, …): brand is the whole partition key, so node 3 reads one partition and returns three rows, sorted by year and then speed. ((brand, year), …): brand is half a partition key, there is no token, and cqlsh asks for ALLOW FILTERING; with it, all three nodes read all nine rows to return three. Same columns, other brackets: the brackets decide where a row lives.

  3. Key (brand, year, max_speed, car_id), WHERE brand = 'Fiat' AND max_speed = 160. Predict cqlsh's answer, then repair the query in two different ways.
    What you should see

    "PRIMARY KEY column "max_speed" cannot be restricted as preceding column "year" is not restricted" — rule 2. Repair one: name the year too, brand = 'Fiat' AND year = 2023 AND max_speed = 160, and node 1 reads exactly one row. Repair two: tick ALLOW FILTERING; node 1 still answers alone, because the partition key is given, but it reads the whole Fiat partition and discards one of the three rows.

  4. Key (brand, max_speed, car_id): try price = 35000, then price > 100000. Predict, then create the index on price and predict again. Last, choose the key (brand, max_speed): how many cars are stored?
    What you should see

    Without the index both need ALLOW FILTERING. With it, price = 35000 runs: every node looks up its local index and two cars come back, but price > 100000 still needs ALLOW FILTERING — a secondary index answers equality only (pp. 1610–1611). With the key (brand, max_speed) only 7 of the 9 cars remain: two Fiats share (Fiat, 160) and two Lancias share (Lancia, 180), and the later INSERT overwrote the earlier one. A key that does not identify the car loses cars, silently.

"If any further operation is required, write its CQL code" asks exactly this: is the WHERE column part of the key? If not, the further operation is CREATE INDEX for an equality; for a range only ALLOW FILTERING works — write it, and say it is not recommended.

Writing: every write is an upsert

The session inserts a person (p. 1566):

-- p. 1566: Francesco, aged 26
INSERT INTO person (personal_id, address, age,
                    birth_date, gender, name)
VALUES ('FRNTRZ95E12F675T', 'Via Milano 12', 26,
        '12-05-1995', 'Male', 'Francesco Terzani');

Columns and values match in order; the primary-key columns must be there, the others may be left out. The template's USING <option> is not explained on the slide: it sets a time to live, USING TTL 86400 expires the values after a day, or a write timestamp (Cassandra documentation).

Now the question no slide asks: what if a row with that primary key already exists? In SQL, a duplicate-key error. In Cassandra, nothing: the INSERT overwrites the columns it lists and keeps the others. An INSERT is an upsert — update or insert, decided by the primary key alone. Cassandra never reads before writing, part of why writes are fast; to refuse duplicates you ask for it, INSERT … IF NOT EXISTS, a lightweight transaction (not in the slides).

UPDATE follows the same logic (p. 1570): "The WHERE clause must include all components of the primary key (partition key and clustering keys). You cannot update or change primary key values." Leave out age and cqlsh answers "Some clustering keys are missing: age"; try SET age = 27 and it answers "PRIMARY KEY part age found in SET part". When no row has the key, the UPDATE creates one.

-- p. 1570 as printed: "Let's update Francesco's address"
UPDATE person
SET address = 'Via Milani 13'
WHERE personal_id = 'FRNTRZ95E12F675T' AND age = 32;

"Let’s update Francesco’s address to ‘Via Milani 13’" — WHERE personal_id = ‘FRNTRZ95E12F675T’ AND age = 32;

Francesco was inserted with age 26 (p. 1566); the statement that updates him ends with AND age = 26;.

age is part of the primary key, so (FRNTRZ95E12F675T, 32) is another row, one that does not exist. The UPDATE creates it with only the address and leaves Francesco at Via Milano 12: on Cassandra 5.0.9 the partition then holds two rows, and cqlsh reports no error. The widget below replays it. The exam may be matched against the printed slide: know that its statement writes a second, ghost row, and write the key Francesco really has.

The upsert trap

The session's person table, empty. Choose its PRIMARY KEY, pick a statement and press Run; under the statement you see what SELECT * FROM person WHERE personal_id = 'FRNTRZ95E12F675T'; returns afterwards, and below it cqlsh's replies so far. Changing the key starts the table over.

  1. Key (personal_id, age). Run "INSERT Francesco, age 26", then predict: after "INSERT Francesco again, age 32", how many rows? Then switch the key to (personal_id) and run the same two statements.
    What you should see

    Two rows: age is part of the key, so (…, 32) is a new row. With the key (personal_id): one row — the second INSERT overwrote age and name, and the address of the first one stayed, because an upsert writes only the columns it lists. No error either time.

  2. Start over with (personal_id, age). Run the session's INSERT (p. 1566) and its UPDATE (p. 1570). Is Francesco's address updated?
    What you should see

    No. The UPDATE names age = 32, a key no row has, so it creates a second row holding only the address; Francesco keeps Via Milano 12. cqlsh answers OK both times. The insight: the primary key alone decides which row a write lands on, and Cassandra never checks whether that row exists.

  3. Run "DELETE … by partition key". How many rows go? Then try "UPDATE … without age" and "DELETE … AND age = 26" under each key.
    What you should see

    Every row of Francesco: the partition key alone deletes the whole partition (p. 1571). "UPDATE … without age" is refused under (personal_id, age) with "Some clustering keys are missing: age" — an UPDATE must name one row. Under (personal_id) age is not a key column at all, so the DELETE that names it is refused: "Non PRIMARY KEY columns found in where clause: age".

DELETE needs less (p. 1571): "You must specify the full partition key in the WHERE clause of a DELETE. Instead, Clustering Key(s) are not strictly required." The width of the WHERE decides how much goes:

-- p. 1571: the whole partition, every row of Francesco
DELETE FROM person WHERE personal_id = 'FRNTRZ95E12F675T';
-- one row of the partition
DELETE FROM person
WHERE personal_id = 'FRNTRZ95E12F675T' AND age = 26;
-- one column of one row: the address becomes null
DELETE address FROM person
WHERE personal_id = 'FRNTRZ95E12F675T' AND age = 26;

A delete is itself a write: a marker, a tombstone, hides the old values until a later cleanup (lesson 22). Several writes can also travel together (p. 1572):

-- the template of p. 1572, filled in:
-- one request, one timestamp for every statement
BEGIN BATCH
  INSERT INTO person (personal_id, age, name)
    VALUES ('RSSMRA80A01F205X', 45, 'Maria Rossi');
  UPDATE person SET address = 'Via Roma 1'
    WHERE personal_id = 'RSSMRA80A01F205X' AND age = 45;
  DELETE FROM person
    WHERE personal_id = 'FRNTRZ95E12F675T';
APPLY BATCH;

"A set of INSERT, UPDATE, and DELETE operations can be organized in a BATCH. In that way, they are executed one after another with a single command."

One command, yes; one after another, no. All statements of a batch carry the same timestamp, so their order decides nothing: when two of them write the same cell, a delete beats a write and the larger value beats the smaller, wherever they stand.

On Cassandra 5.0.9, a batch with DELETE of a row followed by INSERT of the same row leaves no row — the delete wins although it came first — and INSERT … name 'b' followed by UPDATE … SET name = 'a' leaves 'b'. The exam may be matched against the printed sentence, for example in a true/false question: know it as printed, and know that the statements are sent together and applied as one write.

The batch earns its place elsewhere: when one fact is stored in two tables, a logged batch (the default) writes both copies or neither — background from the Cassandra documentation, and the glue of section 5.

Types, scripts, and the JOIN that is not there

Types first (p. 1577): "text, varint, float, double, Boolean, etc.", plus int, date, timestamp and uuid, filled by the function uuid() (p. 1609). Two kinds are special. A collection keeps several values in one column: list<T> (ordered, duplicates allowed), set<T> (unique values), map<K, V>. The slide shows the list:

-- p. 1577: a column that holds a list of e-mails
CREATE TABLE test (id int PRIMARY KEY, email list<text>);
-- p. 1577: append to the list; a set takes {'x'}, a map {'k': 1.5}
UPDATE test SET email = email + ['a@polimi.it'] WHERE id = 1;

A user-defined type is a named record used as a column type; "it is necessary to define the data type before using it" (p. 1578). The car exercise defines a feature (p. 1608):

-- p. 1608: a feature has a name and a description
CREATE TYPE feature (
  name text,
  description text
);
The slide says frozen is necessary for every user-defined type. Cassandra 5.0 refuses only the collection case: Non-frozen UDTs are not allowed inside collections. At the exam, write frozen anyway.
-- p. 1608: a list of features, the type frozen
ALTER TABLE car ADD features list<frozen<feature>>;

"A frozen data type can only be overwritten; it can't be edited anymore" (p. 1608): the value is stored as one block. DESCRIBE TYPE feature; checks it; ALTER TYPE and DROP TYPE change or remove it (p. 1578). Three commands of the cqlsh console, not CQL statements, complete the toolkit (pp. 1573–1575):

-- p. 1575 (path quoted): run every statement of a file, as if typed
SOURCE 'D:/Program Files/Cassandra/Queries/query_1.txt';
-- p. 1573 (path quoted): query results go to the file until CAPTURE off;
CAPTURE 'D:/Program Files/Cassandra/Outputs/output.txt';
-- p. 1574: one line per column, for wide rows; EXPAND off; stops it
EXPAND on;

cqlsh> SOURCE D:/Program Files/Cassandra/Queries/query_1.txt;

The path is a string in single quotes: SOURCE 'D:/Program Files/Cassandra/Queries/query_1.txt';. The same holds for CAPTURE, printed unquoted on p. 1573.

cqlsh 5.0.9 answers the unquoted form with "Improper SOURCE command." — space in the path or not — and the CAPTURE twin with "Improper CAPTURE command."; quoted, both work, spaces and backslashes included. The session itself quotes the path on pp. 1610 and 1612. SOURCE earned a whole point on 11 Feb 2025 and part of one on 6 Jun 2024: quote the path. The exam may be matched against the printed form: recognise it, but write the quotes.

Last, the slide everybody expects, "FOREIGN KEY (?)" (p. 1576): "In Cassandra there is no concept of FOREIGN KEYS and/or relationships, if you want any cross-table check to be performed, you have to manage it by yourself." The reason is again the key: two tables place their rows by two different partition keys, on different nodes, so a join would be a conversation between machines for every row. Instead, p. 1551: "Data is denormalized and duplicated for query efficiency", and the lecture's method (lesson 20): "Start from queries, then design the data model" (p. 430); "cassandra is an index factory" (p. 431). The puzzles paper of 30 May 2025 searches purchases by puzzle and by the buyer's city or country — two tables, every purchase written into both:

One table per query: its equality conditions become the partition key, its order the clustering key, and every column it returns is copied in.

The car dealership, end to end

The exercise session (pp. 1606–1612) is a complete exam script on one table. Keyspace and table first:

-- p. 1606: the keyspace of the exercise

                      'replication_factor': 3};
-- p. 1607: "sorted by max_speed in ascending order"
CREATE TABLE car (
  car_id uuid,
  brand text,
  max_speed varint,

  consumption_lt_per_km float,

DESCRIBE car_dealer; checks the keyspace (p. 1606). After USE car_dealer; and the feature column of section 5 — added and dropped again, "As we do not want to deal with complex fields" (p. 1609) — the session inserts a car with a generated key:

VALUES (uuid(), 'Ferrari', 320, 200000.00, 30.00);

The rest of the data comes from a file, SOURCE '<path_to_your_folder>/car_data.txt'; (p. 1610). The deck does not show the file; the runs quoted here used nine cars, three Ferraris, three Fiats and three Lancias — the nine of the widget. The queries of pp. 1610–1612 then give:

-- p. 1610: "cost more than 100'000": a range, so ALLOW FILTERING (3 Ferraris)
SELECT * FROM car WHERE price > 100000 ALLOW FILTERING;
-- p. 1611: "exactly 35'000 (without using ALLOW FILTERING)": an index first
CREATE INDEX car_price ON car (price);
-- p. 1611: then the equality (a Fiat and a Lancia)
SELECT * FROM car WHERE price = 35000;
-- p. 1611: the sum of all prices: 805000, printed 8.05e+05 for a float
SELECT SUM(price) FROM car;
-- p. 1612: count the Ferraris and store the result in ferrari_count.txt
CAPTURE '<path_to_folder>/ferrari_count.txt';
CREATE INDEX car_brand ON car (brand);
SELECT COUNT(*) FROM car WHERE brand = 'Ferrari';

Neither aggregate names a partition, so both ask every node, and cqlsh adds the warning "Aggregation query used without partition key". The file receives the count, 3, and that warning; while the capture is on, the screen only says "Now capturing query output to …".

Back to the hook

Read the key of p. 1607 as Cassandra does. car_id is the partition key, so every car is a partition of its own, and max_speed sorts the rows of a partition that holds a single row. SELECT * FROM car; walks the partitions in token order — the order of the hashes, hence 340, 190, 180 — and ORDER BY is refused because it only sorts inside partitions that the WHERE clause names. The repair moves one column into the partition key:

-- the cars of each brand, sorted by speed: brand decides the node
CREATE TABLE car_by_brand (
  brand text,
  max_speed varint,
  car_id uuid,
  price float,
  PRIMARY KEY (brand, max_speed, car_id)
) WITH CLUSTERING ORDER BY (max_speed ASC);
-- 296, 320, 340: one partition, already in order
SELECT * FROM car_by_brand WHERE brand = 'Ferrari';

car_id stays at the end of the key so that it still identifies a car: without it, two Fiats with the same top speed would be one row. With the partition named, ORDER BY works as well: ORDER BY max_speed DESC gives 340, 320, 296. The exam keeps using the session's pattern — "Personal_ID as the partition key and Phone Number as the clustering key, ordering the table based on the Phone Number" (6 Sep 2024) — and there the order is real: a chef with two phone numbers is one partition of two sorted rows.

Exam of 6 Sep 2024, exercise 5 (restaurant). ER: Person (Personal_ID, Name, Surname, Birth Date, Phone Number) is the parent of Owner, Customer, Waiter and Chef (Hiring Date); Head Chef (Head Chef Since) is a Chef.

"Consider the Chef table. Write a Cassandra script to perform the operations listed below. Create the Chef table, with Personal_ID as the partition key and Phone Number as the clustering key, ordering the table based on the Phone Number. (1.5 PT) Write a CQL query to collect the chef whose name is "Riccardo". If any further operation is required, write its CQL code. (1 PT) Create a Custom data type named "contact" that contains the name, surname, and phone number of the chef (1.5 PT)"

Show model answer 
CREATE KEYSPACE restaurant
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};
USE restaurant;

CREATE TABLE chef (
  personal_id text,
  phone_number text,
  name text,
  surname text,
  birth_date date,
  hiring_date date,
  PRIMARY KEY (personal_id, phone_number)
) WITH CLUSTERING ORDER BY (phone_number ASC);

-- name is not part of the key: the further operation is an index
CREATE INDEX chef_name ON chef (name);
SELECT * FROM chef WHERE name = 'Riccardo';

CREATE TYPE contact (
  name text,
  surname text,
  phone_number text
);
-- optional, to use it: a list of contacts of the chef

Without the index, SELECT * FROM chef WHERE name = 'Riccardo' ALLOW FILTERING; also works, but it scans the table and is not recommended.

The three sub-questions test three things: the bracket form with the clustering order, the index as the "further operation" for a non-key column, and the type definition. Phone numbers are text (a leading + or 0 must survive). On test data, a Riccardo with two phone numbers came back as two rows of one partition, sorted by number: here the clustering order means something.

Explain the roles of the partition key and of the clustering key of a Cassandra table. Which conditions can the WHERE clause of a SELECT contain without ALLOW FILTERING, and why does Cassandra impose these rules?

Show model answer

The primary key has two parts. The partition key, the first element (or the columns in the inner brackets), is hashed into a token that decides on which nodes the row is stored: all rows with the same partition key form one partition on the same replicas. The clustering key, the remaining columns, decides how the rows are sorted inside the partition (WITH CLUSTERING ORDER BY sets ASC or DESC). Without ALLOW FILTERING, a SELECT that restricts the partition key must restrict every one of its columns with = or IN, so Cassandra can compute the token and go to the right node. Clustering columns may be restricted only as a prefix in their declared order, with a range only on the last one, because then the result is one contiguous slice of the sorted partition; OR does not exist. Any other column needs a secondary index and an equality condition, and such a query may omit the partition key, at the price of asking every node. ALLOW FILTERING lifts the rules, but makes Cassandra read and discard rows, so its cost grows with the size of the table.

A complete answer names both roles, the three legal kinds of condition and the reason behind each: the hash for the partition key, the sorted storage for the clustering prefix, the per-node lookup for the index. Quoting the slide's definitions (p. 1560) is safe.

Which statements about CQL are true? Select all that apply.

  • The clustering key decides on which node a row is stored. That is the partition key; the clustering key sorts the rows inside a partition (p. 1560).
  • With PRIMARY KEY ((a, b), c) and no index, the clause WHERE a = 1 is rejected unless ALLOW FILTERING is added. Rule 1 of p. 1569: "WHERE clauses must include ALL components of the partition key"; half a composite key gives no token.
  • A secondary index makes range conditions (<, >) on the indexed column legal without ALLOW FILTERING. An index answers equality only: "most comparison operators require the additional statement ALLOW FILTERING" (p. 1568), and price > 100000 still needs it after CREATE INDEX car_price.
  • An INSERT fails if a row with the same primary key already exists. INSERT is an upsert: it overwrites the listed columns without an error.
  • With PRIMARY KEY (a, b, c) and no index, the clause WHERE a = 1 AND c = 2 is rejected unless ALLOW FILTERING is added. c is restricted while the preceding clustering column b is not (rule 2).
  • A DELETE that names only the partition key removes every row of that partition. p. 1571: the clustering key is "not strictly required"; without it the whole partition goes.
Show model answer

True: the second, the fifth and the sixth.

Check yourself

A table has PRIMARY KEY ((city, year), month, day). Which WHERE clause runs without ALLOW FILTERING?

  • city = 'Milan' AND month = 5 The partition key is (city, year): without year there is no token.
  • city = 'Milan' AND year = 2025 AND day = 3 day is restricted but month, the clustering column before it, is not: "PRIMARY KEY column "day" cannot be restricted as preceding column "month" is not restricted".
  • city = 'Milan' AND year = 2025 AND month >= 5 The whole partition key, then a prefix of the clustering columns with the range on its last column: one contiguous slice.
  • year = 2025 AND month = 5 AND day = 3 city is missing, so the partition cannot be found.

The table person has PRIMARY KEY (personal_id, age) and one row ('X', 26) with an address. You run INSERT INTO person (personal_id, age, name) VALUES ('X', 26, 'Ann');. What happens?

  • cqlsh reports a duplicate primary key Cassandra has no such error: it never reads before writing.
  • A second row ('X', 26) appears Two rows with the same full key are the same row.
  • The row is replaced: the address becomes null An upsert writes only the columns it lists; the address is kept.
  • The existing row gets the name 'Ann' and keeps its address Same key, same row; the INSERT overwrote the name and touched nothing else.

The table car has PRIMARY KEY (brand, max_speed, car_id) and a secondary index on price. Which SELECTs run without ALLOW FILTERING? Select all that apply.

  • WHERE price = 35000 Equality on an indexed column: every node looks up its local index.
  • WHERE price > 100000 An index serves equality only; a range needs ALLOW FILTERING.
  • WHERE brand = 'Fiat' AND max_speed >= 160 The partition key, then a range on the first clustering column: a slice of one partition.
  • WHERE max_speed = 160 A clustering column without the partition key: every partition would be searched.
  • WHERE brand = 'Fiat' AND price > 20000 The partition is named, but the range on price cannot use the index: it must be filtered.

All five were run on Cassandra 5.0.9. Equality uses an index, a range never does.

Francesco has two rows in person, ages 26 and 32. What does DELETE FROM person WHERE personal_id = 'FRNTRZ95E12F675T'; remove?

  • Nothing: the clustering key is missing For a DELETE the clustering key is "not strictly required" (p. 1571).
  • Both rows The partition key alone names the whole partition.
  • Only the row with age 26 Nothing in the statement singles out age 26.
  • Only the most recently written row Write order plays no role; the WHERE names the partition.

A batch holds DELETE FROM person WHERE personal_id = 'B'; followed by INSERT INTO person (personal_id, age, name) VALUES ('B', 1, 'Bo');. What is left after APPLY BATCH;?

  • Bo's row, since the INSERT came last That is the "one after another" reading of p. 1572, and it is wrong.
  • An error: a batch cannot mix DELETE and INSERT The slide's own template mixes INSERT, UPDATE and DELETE.
  • No row for 'B' Both statements share one timestamp, and at equal timestamps the delete wins, wherever it stands.
  • Two versions of the row A primary key identifies one row.

The session's table has PRIMARY KEY (car_id, max_speed), car_id a uuid, and WITH CLUSTERING ORDER BY (max_speed ASC). What does the clustering order change in the output of SELECT * FROM car;?

  • The cars come out sorted by speed Only rows inside one partition are sorted, and here each partition holds one car.
  • The cars of each brand come out sorted by speed brand is not part of the key; it plays no role in placement or order.
  • The SELECT is refused without ORDER BY A SELECT with no WHERE is allowed; it is the ORDER BY that is refused.
  • Nothing visible: partitions come out in token order Every car is its own partition, so there is nothing to sort inside one.

Which command runs the statements stored in D:\Cassandra\Scripts\statement.txt from cqlsh?

  • SOURCE D:\Cassandra\Scripts\statement.txt; Without quotes cqlsh answers "Improper SOURCE command."
  • SOURCE 'D:\Cassandra\Scripts\statement.txt'; The path is a quoted string; the backslashes are kept as typed.

Key take-aways

  • Cassandra is a distributed, masterless, BASE database: no single point of failure, linear scaling, fast writes. Know the ACID/BASE table of p. 1550 and the comparison with relational systems of p. 1551.
  • In PRIMARY KEY ((partition key), clustering columns) the partition key is hashed to pick the node, the clustering columns sort the rows inside the partition (WITH CLUSTERING ORDER BY), and the whole key identifies one row.
  • Without ALLOW FILTERING a WHERE clause either names every partition-key column with = or IN and then a prefix of the clustering columns, with at most one range at its end, or uses = on a column with a secondary index; OR does not exist.
  • INSERT and UPDATE are upserts: the key decides the row and nothing is checked, so a wrong clustering value writes a ghost row. UPDATE needs the full primary key and cannot change it; DELETE needs the partition key and removes as much as its WHERE names; a BATCH gives all its statements one timestamp.
  • No joins, no foreign keys: denormalise, one table per query, its equalities as partition key and its order as clustering key. Collections and frozen user-defined types keep related values in one row.
  • cqlsh commands take quoted paths: SOURCE 'file';, CAPTURE 'file'; … CAPTURE off;, and EXPAND on; for wide rows.
