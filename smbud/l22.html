Inside Cassandra: ring, gossip, replicas, quorums; HBase

After this lesson you will trace a key from its hash to the nodes that hold its copies, follow a write and a read inside a Cassandra node, tell which consistency levels guarantee a fresh read, and say what HBase does differently.

On more than 50 GB of data, MySQL writes in 300 ms and reads in 350 ms on average — about the same. Cassandra writes in 0.12 ms and reads in 15 ms (p. 459). So Cassandra writes 125 times faster than it reads. What did it give up to make writing so cheap?

The second puzzle comes from the company that built Cassandra. In November 2010 Facebook chose HBase, not Cassandra, for its new Messages system: its engineers found Cassandra's eventual consistency hard to fit to what Messages needed (Facebook Engineering). Yet HBase writes with the same machinery — a log, a table in memory, sorted files on disk. Where does the different consistency come from?

Keep both questions. Section 3 answers the first, section 5 the second.

Where a key lives: the hash ring

Take the exam of 12 Sep 2025: farmers' sales at local markets, a large table that keeps growing, stored in Cassandra and queried by market location or product name. Partition the sales by market location: every Milano sale lands in the partition 'Milano'. Eight machines hold the data, and they are all equal: no master, no slaves, peer to peer (p. 440). So how does anyone know which machine holds 'Milano' (p. 439)?

Every node works it out alone, with the same arithmetic. The partitioner turns the key into a number, its token — on the slides, the MD5 hash of the key (p. 457). Picture the tokens on a circle. Each node owns one token, and a key belongs to the first node clockwise from the key's token. The replication factor N says how many copies of each key exist; the Simple Strategy puts the other N − 1 copies on the next nodes clockwise (p. 442). A client may send a request to any node: that node becomes the request's coordinator and forwards it to the right replicas (p. 443).

Why a circle, and not the hash modulo the number of nodes? With modulo 8, a ninth machine changes the remainder of almost every key: nearly all the data moves. On the ring a new node takes one arc from one neighbour, and nothing else moves. That is consistent hashing.

Two partitioners

There are two ways to turn a key into a token (p. 457; Table 1). The random partitioner hashes the key: keys spread evenly over the nodes, but their order is lost. The order-preserving partitioner keeps keys in order, so you can scan a range of them — at the price of hot spots. Real keys are as uneven as Scrabble letters: the node owning the M's gets far more rows than the one owning the X's, the slide's "'scrabble' distribution". The hash is the default. Cassandra gives up range scans over partition keys and keeps order inside a partition instead, with the clustering key of lesson 21.

Where the copies go

Replication takes two settings: the replication factor, and a placement strategy that decides where the copies go (p. 456). The Simple Strategy is for a single datacenter and ignores racks (p. 442). The Network Topology Strategy is for several datacenters. You give it a replication factor per datacenter, so each datacenter can answer its own local queries; and inside each datacenter the clockwise walk skips nodes of a rack that already holds a copy (Fig. 1). Why racks? The machines of one rack share power and a network switch, so they tend to fail together. Older versions called the two strategies rack unaware and data center shard (p. 456).

In CQL you set this when you create the keyspace — the first statement of every Cassandra script in the exercise session (p. 1553):

-- three copies of every row
CREATE KEYSPACE population
  WITH replication = {
    'class': 'SimpleStrategy',
    'replication_factor': 3};

For the two datacenters of Fig. 1 you give one replication factor each:

-- two copies in each datacenter
CREATE KEYSPACE population
  WITH replication = {
    'class':
      'NetworkTopologyStrategy',
    'DC1': 2, 'DC2': 2};

The hash picks the first node clockwise; the strategy picks the other N − 1: the next nodes, or the next racks of each datacenter.

Nobody in charge: gossip and failure detection

Node B3 reboots at night. With no master, nobody keeps the list of who is alive: each node keeps its own list and corrects it by talking to the others. The news that B3 is back spreads from node to node like a rumour — hence the name, gossip (p. 440).

Gossip runs in rounds (p. 441). In each round a node picks a few partners — up to three, however large the cluster — and has a three-message conversation with each (Fig. 2). Afterwards both know the newer of what each knew, so the views of all nodes converge. This is anti-entropy: entropy is the disorder of nodes that disagree, and gossip removes it. Because each node talks to only a few partners per round, the network traffic stays constant as the cluster grows — except in a "gossip storm", when many nodes change state at once.

Don't mix up the two threes: up to three partners per round, and three messages per conversation. And gossip carries node state — heartbeats, tokens, versions — never rows: writes go from the coordinator to the replicas (p. 445).

The membership list

What does a node gossip about? Its membership list: one row per node, with the node's address, its heartbeat counter and the local time when this node last saw that counter grow (p. 451). Each node raises only its own counter, as a sign of life. When a list arrives, the receiver merges it row by row: the larger counter wins, and it is stamped with the receiver's own clock, because the clocks of different machines are not synchronised. Fig. 3 shows one merge.

From silence to suspicion

A node that stops gossiping may be dead or only slow. A fixed timeout errs one way or the other: too short, and slow nodes are declared dead; too long, and requests keep going to a dead node. The accrual failure detector does not answer yes or no. It outputs a level of suspicion, φ (PHI), that grows with the silence, measured against the usual gaps between gossip messages; the application chooses the threshold at which it acts. On the slide, PHI = 5 means a detection time of 10–15 s (p. 452). Step by step:

In statistical terms: \(P_{\text{later}}\) is the p-value of the silence if the node is alive, and \(\varphi\) is that p-value on a minus-log scale.

  1. Let \(\Delta t = t_{now} - t_{last}\) be the silence and F the distribution of past gaps. A live node stays silent this long with the tail probability

    \[ P_{\text{later}}(\Delta t) = 1 - F(\Delta t) \]

  2. φ = 1 means a 10 % chance that a live node is this late; 2 means 1 %, 5 means 0.001 %:

    \[ \varphi = -\log_{10} P_{\text{later}}(\Delta t) \]

  3. Cassandra takes the gaps as exponential with mean μ, so \(P_{\text{later}} = e^{-\Delta t / \mu}\) and

    \[ \varphi = \frac{\Delta t}{\mu \ln 10} \]

  4. Gossip runs about once a second, so μ ≈ 1 s and φ reaches 5 after 5 ln 10 ≈ 11.5 s — inside the 10–15 s of the slide. On a slower network μ is larger and the alarm comes later: the detector adapts to the real gaps (p. 452).

The slide writes the formula with the CDF, F(Δt). Write the tail, 1 − F(Δt), as above: with the CDF itself φ would fall as the silence grows, the opposite of suspicion (p. 452).

A write is an append; a read is a merge

A sale arrives for 'Milano'. The client sends it to any node, which becomes the coordinator. The coordinator uses the partitioner to find the replicas of 'Milano' and sends the write to all of them (p. 445).

Today the hint window is a setting, three hours by default.

What if a replica is down? The write still succeeds. The coordinator writes to the other replicas and keeps the write for the missing one — a hint — until it comes back up. If all the replicas are down, the coordinator keeps the write itself, for up to an hour. This hinted handoff is why Cassandra is "always writable" (p. 445). Two more facts about writes: one write to one partition is atomic — applied whole or not at all — but there are no transactions across keys; and with several datacenters there is one ring per datacenter, and the coordinator also sends the write to one replica in each remote datacenter (p. 445).

At the replica: commit log, memtable, SSTable

A write must be fast and lock-free: no reads, no disk seeks (p. 445). So the replica does only two things (p. 446). First it appends the write to the commit log on disk — an append needs no seek, and the write now survives a crash. Then it adds the write to the memtable, an in-memory table of key-value pairs sorted by key. Now it can acknowledge (Fig. 4).

When the memtable is full or old, the replica flushes it to disk in one go, in key order, as an SSTable (Sorted String Table): a file of key-value pairs sorted by key. Next to it go an index of (key, position in the file) pairs and a Bloom filter (p. 446). SSTables are never modified. A newer value of 'Milano' lands in a newer file, so over time one key has versions in several files. Compaction merges SSTables and keeps only the newest version of each key.

The Bloom filter: a cheap "no"

A read should not open every SSTable. So each SSTable has a Bloom filter: a small bit array that answers "is this key in the file?" with "definitely not" or "maybe" (p. 447). It uses k hash functions. To insert a key, set the k bits its hashes point to. To check a key, look at its k bits. If any of them is 0, the key was never inserted. If all are 1, the key may be there — or other keys may have set those bits. So a Bloom filter can give false positives, but never false negatives.

Deletes write a tombstone

If files are never modified, how do you delete? You write. A delete adds a tombstone: a timestamped marker, written like any other write, that hides the older values of the key from reads. Compaction later removes both the tombstone and the values it hides (p. 448; Fig. 5). So right after a delete the disk holds more data, not less. The tombstone is kept for a grace period, ten days by default, so that replicas that were down also hear of the delete.

Reads merge

A read of 'Milano' looks in the memtable and in every SSTable whose Bloom filter says "maybe", and merges what it finds, keeping the value with the newest timestamp. That is why reads may be slower than writes (p. 446). A read never needs the commit log, even though the slide lists it: everything in the log is also in a memtable or an SSTable, and the log is replayed only when a node restarts, to rebuild the memtables it lost.

Inside a node, all this work — writes, reads, gossip, compaction — runs as a Staged Event-Driven Architecture (SEDA): stages connected by queues, built for many requests at once and for load peaks (p. 455). Under overload a queue grows instead of everything slowing down at once, and a slow compaction does not stop gossip.

Back to the first puzzle

Now the 0.12 ms against 15 ms makes sense. A write is one log append and one memory insert, with no read, seek or lock. A read merges several files, often on several replicas. Cassandra gave up cheap reads and in-place updates, and pays later instead: flushes, compactions, tombstones. The slide names no hardware or workload, so read the numbers as a ratio, not as a benchmark (p. 459).

How many copies must answer: quorums

'Milano' has three copies. How many of them must answer a write, and how many a read? The client chooses, for every operation (p. 449). Call N the number of replicas of the key, W the number that must acknowledge a write, and R the number that must answer a read.

A read waits for R replicas and checks the other N − R in the background (p. 449). The coordinator may ask the closest replica first, for example one in the same rack. If two replicas return different values, the coordinator starts a read repair: it writes the newest value back to the stale replicas (p. 448). The slide says read repair "uses gossip", but it is the coordinator's job: gossip carries node state, not rows. A write either blocks until enough replicas have acknowledged it, or is asynchronous: written to any node, with an immediate answer (p. 449). A quorum is a majority of the N copies:

\[ Q = \left\lfloor \frac{N}{2} \right\rfloor + 1 \]
\(N\)
replication factor: copies of the key
\(\lfloor \cdot \rfloor\)
round down

"For N = 3, the quorum N/2 + 1 is 2.5 replicas." No: the division rounds down — 2 of 3, 3 of 4, 3 of 5 (pp. 449, 453). Write the floor.

Why W + R > N is enough

The rule on the slide is "if W+R > N and W > N/2, you have consistency", and it allows three settings: (W = 1, R = N), (W = N, R = 1) and (W = Q, R = Q) (p. 449). The first condition does the work. Here is why:

  1. The write was acknowledged by a set A of W replicas; a later read hears from a set B of R replicas, out of the same N:

    \[ |A \cup B| \le N \]

  2. So the two sets share at least

    \[ |A \cap B| = W + R - |A \cup B| \] \[ |A \cap B| \ge W + R - N \]

  3. If W + R > N, at least one replica answering the read holds the write, and the coordinator returns the value with the most recent timestamp (p. 453).

  4. All three allowed settings pass: 1 + N, N + 1 and 2⌊N/2⌋ + 2 all exceed N.

The three settings pay differently: (1, N) has fast writes, but a read needs every replica up; (N, 1) has fast reads, but one replica down stops the writes; (Q, Q) balances both and survives N − Q failures — one of three, two of five.

"W > N/2 is required too." Not by the slide's own list: it allows W = 1 with R = N, and 1 is not more than N/2. W > N/2 stops two concurrent writes from being accepted by disjoint sets of replicas; Cassandra settles concurrent writes by timestamp instead, so the rule it uses is W + R > N alone.

Quorum explorer: a write, then a read

    What you should see

    Yes. 1 + 1 = 2 ≤ 3: r1 acknowledged the write, the read asks r3, which still holds v1, and the coordinator returns v1. Read repair fixes r3 only afterwards.

  2. Raise only the read to QUORUM. Enough? Then raise the write to QUORUM too.
    What you should see

    1 + 2 = 3 is still not greater than 3: the read set r2, r3 misses r1. With QUORUM on both sides, 2 + 2 = 4 > 3 and r2 is in both sets. That is the insight: when W + R > N, there is no room left for two disjoint sets.

  3. Keep QUORUM and QUORUM and set N = 5. How many replicas does each operation wait for, how many may be down, and what does it cost against N = 3?
    What you should see

    ⌊5/2⌋ + 1 = 3 for both; 3 + 3 = 6 > 5. Two replicas may be down instead of one, but each operation waits for the third-fastest answer (9 ms) instead of the second (6 ms) — illustrative times.

  4. Try write ALL with read ONE, then write ANY with read ALL. What does each buy, and what does it cost?
    What you should see

    ALL/ONE: reads are fast and always fresh (3 + 1 > 3), but a write waits for the slowest replica and fails if any replica is down. ANY/ALL: the write may exist only as a hint on the coordinator, so even reading every replica can miss it — no guarantee. ANY buys availability, not consistency.

Consistency levels

In practice the client does not give W and R as numbers: it picks a named consistency level for each read or write (p. 450; Table 2). Older versions had other names: a level ZERO, which waited for nobody, is gone, and the old "DCQ" is today's LOCAL_QUORUM (p. 453). In cqlsh you set the level for the statements that follow:

-- next statements: wait for a majority
CONSISTENCY QUORUM

"The level ANY works for reads too." No: a hint kept on a node that is not a replica cannot be read, so a read at ANY is refused with "Try ONE instead" (pp. 450, 453).

With three copies in each of two datacenters: QUORUM waits for 4 of the 6, wherever they are; LOCAL_QUORUM for 2 in the coordinator's datacenter, with no trip to the other one — this is what lets each datacenter serve its own queries; EACH_QUORUM for 2 in each, the strictest and slowest.

The trade, and when it pays

In the CAP terms of lesson 5, Cassandra prefers availability over consistency, and HBase prefers (strong) consistency over availability (p. 460). Cassandra's model is called BASE: Basically Available, Soft state, Eventual consistency. But in Cassandra the choice is made per operation: ONE and ANY keep accepting writes while replicas are down, QUORUM and ALL refuse rather than return stale data — "eventual consistency, tunable per query" (p. 1550). When is Cassandra worth it? See Table 3.

A read is sure to see the latest acknowledged write when W + R > N; a quorum is ⌊N/2⌋ + 1, chosen per operation.

HBase: the same engine, one owner per row

HBase is an open-source implementation of Google's Bigtable, built as part of Hadoop; today it is a major Apache project, and Facebook uses it internally (p. 463). Google published only a paper on Bigtable, never its code, so HBase rebuilt the design from the paper — nobody "open-sourced" Bigtable itself. Its API has four calls (p. 464): Get(row), Put(row), Scan(row range, filter) for range queries, and MultiPut(rows). The scan is the first difference from Cassandra: HBase keeps rows sorted by row key, as the order-preserving partitioner would, so a range of rows is one sequential read. (Data model: lesson 32.)

The architecture has two floors (p. 465; Fig. 6). Upstairs, HBase: a client asks ZooKeeper which HRegionServer serves its rows, then talks to it directly; the HMaster assigns regions and watches the servers. Downstairs, Hadoop: every byte lives in HDFS DataNodes, which keep the copies.

Now from the outside in (p. 466). A table is split into regions, each a range of row keys. A region has one Store per column family: a column family groups columns that are read together, so they are stored together. A Store has a MemStore, which collects the updates in memory and is flushed to disk when full, and StoreFiles, where the data lives, in blocks. A StoreFile is an HFile, HBase's version of Bigtable's SSTable: data blocks, an index and a trailer. Every key-value record in it carries its whole key — row, column family, column, timestamp (p. 467; Table 4).

The slide says regions are "replicated across servers", but that is misleading: each region is served by exactly one HRegionServer at a time, and what is copied is the files, by HDFS (p. 466; Fig. 6). This single owner per region is what lets HBase promise strong consistency.

Write-ahead log and replay

Like Cassandra, HBase writes the log first. Every put(), delete() or incr() is appended to the HLog before it reaches the MemStore, so the server can recover from a crash (p. 468). The HLog is HBase's commit log: a Log Flusher forces it to disk (sync()) and a Log Roller cuts it into files (rollWriter()). After a crash, or at startup, the server replays the logs that are not yet in HFiles: timestamps tell it how far the database got, and the missing edits go back into the MemStore (p. 469). There is one HLog per region server, not one per region, because many logs written at once would mean many disk seeks (p. 469).

Across datacenters

Replication to another datacenter reuses the log too (p. 470). Each region server of the master cluster ships its HLog edits, in batches, to the slave clusters. ZooKeeper — in effect a small file system for control information — keeps the bookkeeping: whether replication is on, which clusters are peers, and for each region server the HLogs still to ship and how far it got.

"The 'Synchronous Call' on the slide means a client's write waits for the other datacenter." No: each shipping call is synchronous, but replication runs behind the client — a write is acknowledged once it is in the local HLog and MemStore. The HBase Reference Guide calls this replication asynchronous.

Back to the second puzzle

Same engine, different owner. Cassandra lets any of N equal replicas take a write, so writes never wait for one machine, and replicas may disagree for a while. HBase gives each row one server, so a read sees every acknowledged write of the row, with no quorum arithmetic; but while a crashed server's regions are reassigned and its HLog replayed, those rows cannot be served. Facebook chose that simpler consistency for Messages.

The other columnar: storing each column apart

The word "columnar" has a second meaning (p. 471). Cassandra and HBase keep a row's columns together (HBase within each column family). MonetDB and LucidDB store each column apart — the column storage of lesson 20, made for queries that read a few columns of many rows.

MonetDB has one storage engine, the Monet back-end, and several front-ends on top of it: SQL for the relational model, ODMG for objects, an OLAP tool and a data-mining tool, all talking to the back-end in the MIL language (p. 472). The back-end uses full vertical fragmentation: every column becomes a table of its own. Order(id, day, discount) becomes order_id, order_day and order_discount, each pairing an object id, the oid, with one value (p. 473; Fig. 7).

LucidDB keeps all its column-store tables in one file, db.dat (p. 474). A table is a set of clusters, by default one cluster per column, and each page of a cluster holds the values of one stretch of row ids (rids). To find a rid, each cluster has a B-tree that maps the first rid of every page to that page (p. 475). For example, if page 49 starts at rid 984 and page 50 at rid 1248, then page 49 holds rids 984–1247 (p. 476). Inside a page each distinct value is stored once, with a bit vector that marks the rows holding it (p. 477; Table 6).

This layout pays three times (p. 478). A query reads only the columns it needs. It can work on the compressed form directly: discount = 0.000 is answered by the vector 0 0 0 1 1 0, with nothing to decompress. And storing each value once takes less disk space.

Exam-style questions

Five theory questions in the forms of the theory part — open answers of a few sentences, and closed ones where a wrong tick may cost points — then two exercises: a quorum computation and a deployment question on the ER scenario of a past paper.

Describe step by step what a Cassandra replica node does when it receives a write, and explain why reads can be slower than writes.

Show model answer

The replica first appends the write to the commit log on disk, a sequential append that makes it durable, and then applies it to the memtable, an in-memory structure of key-value pairs sorted by key; then it can acknowledge. No read, no disk seek and no lock are needed. When the memtable is full or old, it is flushed to disk as an SSTable (Sorted String Table): an immutable file of key-value pairs sorted by key, with an index file of (key, position) pairs and a Bloom filter. Because SSTables are never modified, new versions and deletes (tombstones) accumulate in newer SSTables, and compaction periodically merges them, keeping the newest version of each key and removing deleted items. A read, instead, must look in the memtable and possibly in several SSTables — skipping those whose Bloom filter says the key is absent — and merge the versions by timestamp; the coordinator may also contact several replicas and start a read repair. This is why reads may be slower than writes.

A complete answer gives the order (commit log, then memtable), the words SSTable, flush, compaction and Bloom filter, and the reason for the asymmetry. The slide of p. 446 says reads "touch log and multiple SSTables": write memtable, and mention the log only for restarts.

A keyspace has replication factor N = 3. Which write/read consistency-level pairs guarantee that a read returns the most recent acknowledged write? Select all that apply.

  • W = ONE, R = ONE 1 + 1 = 2 ≤ 3: the read may ask a replica the write has not reached.
  • W = QUORUM, R = QUORUM 2 + 2 = 4 > 3: the two majorities share at least one replica.
  • W = ANY, R = ALL ANY can be satisfied by a hint on a coordinator that is not a replica: until the hint is delivered, no replica has the value, so even reading all three can miss it.
  • W = ALL, R = ONE 3 + 1 = 4 > 3: every replica has the value.
  • W = ONE, R = ALL 1 + 3 = 4 > 3: the read asks every replica, including the one that acknowledged.
  • W = ONE, R = QUORUM 1 + 2 = 3, not greater than 3: the two replicas read may both be stale.
Show model answer

QUORUM/QUORUM, ALL/ONE and ONE/ALL. The condition is W + R > N (here 2 + 2, 3 + 1 and 1 + 3, all greater than 3): it forces the replicas that acknowledged the write and the replicas that answer the read to overlap in at least one node, and the coordinator returns the value with the most recent timestamp. ONE/ONE and ONE/QUORUM fail the inequality; ANY guarantees no replica at all, because a hint stored on the coordinator counts as a successful write.

Three correct options out of six. ANY/ALL is the trap: it looks like the "read everything" corner, but W counts only real replicas. Wrong ticks may be penalised, so tick only what the inequality proves.

True or false: a Bloom filter may report that a key is absent from an SSTable although the key is stored in it.

  • True That would be a false negative, which a Bloom filter never gives: the bits set when the key was inserted are never cleared.
  • False No false negatives; only false positives — an absent key whose bits were all set by other keys.
Show model answer

False. When a key is inserted, all its k hashed bits are set, and bits are never reset, so a stored key always finds its bits set and the filter answers "maybe present". The filter can only err the other way: an absent key may find all its bits set by other keys (a false positive). The rate is low; the lecture's example has k = 4 hash functions, 100 items and 3200 bits, with a false-positive rate of 0.02 %.

A true/false question that tests the direction of the error. Write the reason, not just the word: "bits are never cleared".

Explain how the nodes of a Cassandra cluster learn which nodes are alive without a master. Describe the membership list and how a node decides that another node is down.

Show model answer

Cassandra is peer to peer: no master knows the membership, so each node keeps its own membership list with, for every node, its address, the latest heartbeat counter heard and the local time at which that counter was received. Each node increments its own counter and periodically gossips its list to a few peers (up to three per round), with a three-message exchange (GossipDigestSyn, GossipDigestAck, GossipDigestAck2). On receipt, for every address the node keeps the larger counter and stamps it with its own local time, because the clocks are not synchronised: node 2 at local time 70 receives 10120 and 10098 for nodes 1 and 3, larger than its 10118 and 10090, and stores (10120, 70) and (10098, 70), while it keeps its own entry and the equal one. The traffic per node stays constant and the views converge (anti-entropy). A node whose counter stops increasing becomes suspect: the accrual failure detector computes a suspicion value PHI, minus the base-10 logarithm of the probability that a heartbeat arrives later than the silence observed so far, from the past inter-arrival times; the application sets the threshold (on the slide, PHI = 5 gives a detection time of 10–15 seconds).

A complete answer has three parts: no master and gossip with few peers; the merge rule with local times; suspicion as a value with a threshold rather than a fixed timeout. The numbers of p. 451 make the merge rule concrete.

Cassandra "prefers availability over consistency", while HBase "prefers (strong) consistency over availability". Explain where this difference comes from in the two architectures.

Show model answer

In Cassandra every row has N equal replicas on a masterless ring. Any node can coordinate a write and sends it to all replicas; with levels such as ONE or ANY, and with hinted handoff, a write is accepted even while replicas are down, so the replicas may hold different versions for a while; they are reconciled later by timestamps, read repair and compaction (eventual consistency, BASE). In HBase a table is split into regions, and each region is served by exactly one HRegionServer at a time, assigned by the HMaster through ZooKeeper. Every write of a row goes through that single server, which appends it to its write-ahead log (HLog) before applying it to the MemStore, so every read of the row sees the latest write. The copies of the data are kept by HDFS at the file level, not by several servers answering for the same row. When a region server fails, its regions are unavailable until the HMaster reassigns them and the HLog is replayed into the new MemStores: HBase gives up availability during recovery to keep strong consistency.

The core is "N equal replicas" against "one owner per region". The write-ahead log alone gives durability; consistency comes from the single owner. Mention BASE for Cassandra, and the unavailability during recovery for HBase.

A keyspace uses the Simple Strategy with replication factor 4. Writes are performed at consistency level QUORUM. What is the smallest number of replicas a read must wait for, so that it is guaranteed to return the latest acknowledged write?

Show model answer

QUORUM with N = 4 is ⌊4/2⌋ + 1 = 3 replicas, so W = 3. A fresh read needs W + R > N, that is R > 4 − 3 = 1, so R = 2 replicas. Of the lecture's levels, ONE is not enough and QUORUM (3) is more than needed.

The two steps are the quorum size and the inequality. With N = 4 the slide's N/2 + 1 gives 3 with or without rounding; with an odd N only the rounded-down form is a whole number, so always write the floor.

ER scenario of the exam of 12 Sep 2025 (the exercise itself is exam-style, not from the paper): a data structure for tracking farmers and their sales at local markets. Market (Name, Location, Opening Time, Closing Time, Size) and Product (Product ID, Name, Quantity, Expiration Date) are linked by the relationship Sell, with cardinality (1, N) on both sides.

The sales are stored in Cassandra, partitioned by market location, on one datacenter of six nodes n1–n6 with tokens 10, 25, 40, 55, 70 and 85; the token of the partition 'Milano' is 62. Write the CQL statement that creates the keyspace markets so that every row is stored three times. Say which nodes hold the copies of 'Milano', and choose consistency levels for writes and reads so that a read always returns the latest acknowledged sale while one replica may be down.

Show model answer 
CREATE KEYSPACE markets
  WITH replication = {
    'class': 'SimpleStrategy',
    'replication_factor': 3};

With the Simple Strategy the first copy goes to the first node clockwise from the token 62, that is n5 (token 70), and the other two to the next nodes clockwise, n6 (85) and n1 (10, after wrapping around the ring). Writes and reads at QUORUM wait for ⌊3/2⌋ + 1 = 2 replicas each: 2 + 2 > 3, so every read overlaps the last acknowledged write, and either operation still succeeds with one replica down. (ONE/ALL or ALL/ONE would also be consistent, but a single replica down would block the reads or the writes.)

The keyspace line opens every Cassandra script of the exercise session (p. 1553); here it is joined to the placement and quorum rules of this lesson. The wrap-around from n6 to n1 is where answers usually slip.

Which statements about gossip in Cassandra are true? Select all that apply.

  • In each round a node talks to a few peers, up to three "Each node picks its discussants (up to 3)" (p. 441).
  • Gossip carries the rows written by clients to the replicas Writes go from the coordinator to the replicas directly (p. 445); gossip carries heartbeats and node state.
  • The network traffic per node stays about the same as the cluster grows "Always a constant amount of network traffic": the partners per round do not grow with the cluster.
  • A received entry replaces the local one only if its heartbeat counter is larger The merge rule of p. 451; the time is then the receiver's own.
  • A master node decides which nodes are dead and tells the others There is no master: each node's own accrual detector turns silence into suspicion.

Gossip spreads state about nodes, cheaply and repeatedly; the decisions — dead or alive — are taken by each node for itself.

Node 3 is at local time 42. Its list holds the row 1: (counter 500, time 30). A gossip message from node 4 carries 1: (498, 41). What does node 3 store for node 1 afterwards?

  • (500, 42) The time is restamped only when a larger counter arrives; here nothing changed.

You delete the partition 'Lodi' and look at a replica's disk right away. What do you find?

N = 3. A client writes a new price at ONE and, a millisecond later, another client reads it at ONE. What can happen?

  • The read always returns the new price, because read repair runs first Read repair fixes stale replicas after a read has noticed them, and with R = 1 the read may compare nothing at all.
  • The read may return the old price; the stale replica is fixed later 1 + 1 is not greater than 3: the two sets may not overlap. Eventual consistency, as in the widget's first task.
  • The read fails, because ONE cannot be used for reads ONE is a read level ("1 replica", p. 453); ANY is the one that is not.

  • Every edit is appended to the HLog before it reaches the MemStore "Write to HLog before writing to MemStore" (p. 468): the log makes the edit survive a crash.

Key take-aways

  • A partitioner turns a key into a token — MD5 on the slide (p. 457) — and the first node clockwise on the ring owns it. The replication factor N sets the number of copies; the Simple Strategy puts them on the next nodes clockwise, the Network Topology Strategy per datacenter on different racks (pp. 442–444, 456). The order-preserving partitioner allows key ranges but gives the "'scrabble' distribution".
  • With no master, nodes gossip with up to three peers per round in a three-message handshake (p. 441). Membership lists merge by the larger heartbeat counter, stamped with the receiver's own time (p. 451); the accrual detector outputs a suspicion φ = −log₁₀ of the chance of a later heartbeat, against a threshold the application sets (p. 452).
  • The coordinator sends a write to all replicas and keeps hints for those that are down (p. 445). A replica appends to the commit log and updates the memtable; full memtables are flushed to immutable, sorted SSTables with an index and a Bloom filter; compaction merges them; a delete writes a tombstone (pp. 446–448, 454).
  • A read merges the memtable and the SSTables its Bloom filters do not rule out — never the commit log — so reads are slower than writes (pp. 446, 459). A Bloom filter has false positives but never false negatives (p. 447).
  • Q = ⌊N/2⌋ + 1, and a read is sure to see the latest acknowledged write when W + R > N (p. 449). The levels are ANY (writes only), ONE, QUORUM, LOCAL_QUORUM, EACH_QUORUM and ALL (pp. 450, 453); read repair is done by the coordinator.
  • HBase splits tables into regions, each served by one HRegionServer, with one Store per column family (MemStore plus HFiles) and one HLog per server written before the MemStore and replayed after a crash; HDFS replicates the files (pp. 463–470). One owner per region gives strong consistency; Cassandra's N equal replicas give availability (p. 460).
  • MonetDB and LucidDB are column stores in the other sense: MonetDB splits every column into its own (oid, value) table, LucidDB stores columns in clusters of pages with distinct values and bit vectors (pp. 471–478).
