One object, one document: the document model and how to design it

After this lesson you will read and write a MongoDB document with its types, decide for every relationship whether to embed or to reference, and answer the exam's "how many collections" question from an ER diagram.

Ann's order 1001 is a single card: her name, three line items and an Amex card (p. 291). The relational database behind the shop keeps the same order in four tables — orders, customers, order lines, credit cards — and every time the order is shown, it puts the card back together with joins.

A document database offers to store the card itself. Yet the same lecture soon asks a question and leaves it open: "To embed or not to imbed. That is the question!" (p. 307). If storing the card is so plainly better, why is it a question at all? And why did the exam of 30 January 2026 take away the one operator, $lookup, that would let you dodge it?

Keep both questions. The last section answers them.

One order, four tables: why a document store

Why store documents at all? There are three reasons, and the exam asks for them: a document store handles schema changes well, it solves the impedance mismatch problem, and it fits the rise of JSON (p. 291). The second reason is the biggest, so start there, with Ann's order.

The impedance mismatch is the gap between these two shapes. Your program thinks in objects that contain lists and other objects. A relational database thinks in flat rows linked by keys. So every read has to join the rows, and every write has to take the object apart (lesson 4 met this as the ORM problem). A document has the shape of the object, and you read and write it as one unit.

Now the first reason, change. A relational table fixes its columns. A document carries its own field names, so a new document can have one more field while the old ones keep working: the schema is dynamic (p. 293). And JSON, the third reason, is what web applications already exchange, so a document travels from the browser to the database almost unchanged.

One document is also fast, because of data locality: its parts lie next to each other on disk, so one read gets the whole object (Fig. 2; p. 295). MongoDB's other two speed claims, in-memory caching and the distributed architecture, wait for lesson 16.

MongoDB is a document store, one of the four NoSQL families next to graph, key-value and wide-column stores (p. 286; compared in lesson 5). This lesson is about the part of it you design yourself: its rich data model (p. 294).

A document stores an object the way the application uses it: one unit, one read, no join to rebuild it.

Database, collection, document, field — and the _id

Think of a filing cabinet (Fig. 3). The database is the cabinet, and it holds one or more collections, the folders. A folder holds documents, the sheets of paper. A document is the basic unit of data, and it is a set of key-value pairs: the fields written on the sheet (p. 1416).

The rest of the SQL dictionary is short. Two of its rows change how you design, not only what you call things:

Read the joins row twice: a join is not replaced by a faster join, but by a design decision — embed the related data or link to it (section 4).

A collection is a bag of documents: they may share their fields, but nothing forces them to (p. 302). A field can hold a native type such as a number or a string, an array, or another document (p. 303). That last option, documents inside documents, is what makes embedding possible. And one rule has no exceptions: "Every document must have an _id" (p. 303).

Check it by hand: 5ea64532 in hexadecimal is 1587954994, the seconds since 1 January 1970 at 27 April 2020, 02:36:34 UTC.

The _id identifies the document in its collection. If you supply none, MongoDB creates an ObjectId of 12 bytes, written as 24 hexadecimal digits (p. 1420). Take ObjectId("5ea64532a7678a3b27d34e00"). It has three parts:

  • 5ea64532, 4 bytes: a timestamp, the creation time in seconds since the Unix epoch. Because it comes first, ids stay roughly in creation order.
  • a7678a3b27, 5 bytes: a random value, generated once per process.
  • d34e00, 3 bytes: an incrementing counter that starts from a random value.

The random value and the counter let two programs create ids at the same moment without asking anybody. You can also give your own _id of another type, as long as it is unique: the string "First Post" (p. 309), integers (p. 312), the key "12345" (p. 1443).

A sub-collection is an array of sub-documents, and the papers use the word: "Perform the query starting from the Chef Collection or Sub-Collection" (exam of 6 Sep 2024). Dot notation reaches inside both (p. 1423). "address.city" names one value, while "mobile_phone_numbers.service_provider" names one value per element of the array, which is the main trap of lesson 14.

You add a document with insertOne, and MongoDB adds the _id for you (p. 1421):

// p. 1421: adds one document; MongoDB generates its _id
db.people_collection.insertOne({
   "name": {"first": "Mike", "last": "Ruby"},
   "age": 63
})

You get it back with find (every match), findOne (the first match) or, as a number, countDocuments (p. 1424). The filter is itself a document, here with two dotted fields:

// p. 1424: returns every document whose name is Mark Jonhson
db.people_collection.find(
   {"name.first": "Mark", "name.last": "Jonhson"}
)

An index speeds such reads up. You list the fields, with 1 for ascending or -1 for descending. The price: writes get slower and the index takes storage (p. 1422). Filters and indexes are lesson 14's.

// p. 1422: a compound index on three fields
db.people_collection.createIndex(
   {"name.last": -1, "name.first": 1, "age": 1}
)

JSON on the screen, BSON on the disk

Here is a real document, a record from a business directory (p. 292):

// p. 292 (and p. 308): one business, one document
{
"business_id": "rncjoVoEFUJGCUoC1JgnUA",
"full_address": "8466 W Peoria Ave\nSte 6\nPeoria, AZ 85345",
"open": true,
"categories": ["Accountants", "Professional Services",
               "Tax Services"],
"city": "Peoria",
"review_count": 3,
"name": "Peoria Income Tax Service",
"neighborhoods": [],
"longitude": -112.241596,
"state": "AZ",
"stars": 5.0,
"latitude": 33.581867000000003,
"type": "business"
}

Read it as a list of types: strings, a boolean, an integer, floating-point numbers, an array of strings, an empty array ("neighborhoods": [] exists and holds nothing), newlines escaped inside a string. So a document is typed, nested and self-describing: every value travels with its field name.

The JSON syntax is short: name/value pairs with a colon between them, commas between pairs, curly braces around an object, square brackets around an array (p. 300). In the slide's example, two Star Wars characters, only R2-D2 has a race. That is already the polymorphism of section 4: two documents, not quite the same fields.

"Quoting field names is optional." In the shell, yes — it is JavaScript, and the slide itself leaves race bare (p. 300). In JSON, no. Quote every name in an exam answer, as the exercise session does: the document is then valid both ways.

MongoDB does not keep this text. For speed it stores BSON (Binary JSON), and the language drivers translate between your program's objects and BSON (p. 299). Each entry holds a field name, a data type and a value, and large elements start with their length (p. 301). Fig. 4 shows what that means, byte by byte.

Why the extra bytes? Speed. A reader looking for age reads the type and name of the first field, finds the string's length, 4, and jumps over the value, without parsing it. BSON also aims to save space, but Fig. 4 shows that this is a goal, not a promise (p. 301): speed is the sure gain.

BSON also has more types than JSON, and closed questions quote this sentence (p. 301): "BSON types are a superset of JSON types (JSON does not have a date or a byte array type, for example), with one exception of not having a universal "number" type as JSON does." Where JSON has one number, BSON picks a 32-bit integer like the 26 above, a 64-bit integer or a double. So the integer 1 and the double 1.0 are two BSON types, although a query compares them by value.

A document also has a ceiling: 16 MB (p. 298). The server counts that as 16,777,216 bytes and refuses a bigger insert ("object to insert too large"). Larger files, such as videos, go to GridFS, which stores them in chunks over several documents. For design, the cap warns you against arrays that never stop growing.

The same slide's "No Schemas", "No transactions", "No joins" describe early MongoDB (p. 298): today schemas are optional, multi-document transactions exist since version 4.0 and the $lookup stage joins two collections, so in an open answer write that MongoDB avoids joins by embedding, not that it cannot join.

On security, MongoDB encrypts traffic with SSL, between client and server and inside the cluster, and gives read-only, read+write or administrator rights per database (p. 296). These rights protect you only when they are switched on: in January 2017 about 10,500 MongoDB databases open to the internet, with no administrator password, were wiped and held for ransom within days (BleepingComputer, 7 January 2017).

Embed or reference: the one design decision

Take a user with contact data and access rights. You can store them in two ways. Embedded: one document, with contact and access as sub-documents inside it (p. 304). Referenced: three documents, where contact and access point back to the user through user_id, the user's _id (p. 305).

An embedded document is read with its parent in one fetch and written with it in one operation. A reference is only a field holding another document's _id. It is weaker than a foreign key: MongoDB does not check that the target exists, and find does not follow it, so the application sends a second query. It can sit on either side. Each child can hold its parent's id (p. 305), or the parent can hold an array of its children's ids, "orders": [ "order1", "order2" ] (p. 1444). Use references everywhere and you have rebuilt a relational database (notes, 3.5.2).

One slide turns an unreadable relational schema into a single document (p. 306). Its contributors, Eliot Horowitz and Dwight Merriman, co-founded 10gen in 2007, the company that released MongoDB in 2009 and became MongoDB Inc. in 2013 (Wikipedia).

So which one do you choose? You start from the application, not from the data: what it reads and writes (its CRUD operations) shapes the documents. No modelling standard or CASE tool decides for you; there is only a slogan worth remembering: "Rule of thumb is to imbed whenever possible" (p. 307). The lecture shows three structures:

// p. 309: a post with its comments, one document
{
  "_id": "First Post",
  "comments": [
    {"author": "Bob", "text": "Nice Post!"},
    {"author": "Tom", "text": "Dislike!"}
  ],
  "comment_count": 2
}

A one-to-many folded into the parent and read in one go. The array can hold plain values, like the categories of the business above (p. 308), or sub-documents, like these comments (p. 309). comment_count repeats the array's length on purpose: this denormalized counter makes "posts with more than two comments" a plain comparison, at the price of updating it with each comment.

// p. 310: two collections, post and comments
// db.post
{
  "_id": "First Post",
  "author": "Rick",
  "text": "This is my first post."
}
// db.comments
{
  "_id": ObjectId("..."),
  "post_id": "First Post",
  "author": "Bob",
  "text": "Nice Post!"
}

Each comment is a document of its own and points to its post through post_id. A post with its comments now costs two queries. In exchange, you can find, edit or page through comments on their own, and the post never grows.

// p. 312: two kinds of document in one collection, nodes
// Page document
{
  _id: 1,
  title: "Welcome",
  url: "/",
  type: "page",
  text: "Welcome to my wonderful wiki."
}
// Photo document
{
  _id: 3,
  title: "Cool Photo",
  url: "/photo.jpg",
  type: "photo",
  content: Binary(...)
}

The documents of one collection are similar, but not identical (p. 311). All of them have _id, title, url and type, which tells the application which shape to expect. text and content (binary data, a type JSON lacks) belong to one kind each. You gain simpler schema changes, no spare columns like custom_field_1, and a direct match for inheritance in object-oriented code. Section 5 stores ISA hierarchies this way.

As a default the rule of thumb is right. Four situations — call them the four stop signs — make it a mistake:

  1. Size and growth. An array that grows forever — sensor readings, a customer's orders — drifts towards the 16 MB limit (p. 298), and each new element rewrites a bigger document.
  2. Duplication. Data embedded in many parents is copied into each; a change must find every copy.
  3. Many-to-many. The shared side of an M:N relationship is such data: one product in thousands of orders.
  4. Independent access. An entity read or updated on its own — a product page — needs its own collection.

The exercise session says it in two lines: embed related data that is often queried together; store references when it is large or accessed independently (p. 1444). The widget tests the four signs on the invoice of lesson 9.

    One find: everything is in the customer document. 16,777,216 / 465 is about 36,000; each array element also carries its own type byte and index key, about 7 bytes more, so the growth readout names the exact limit, 35,569 orders, and turns red past it.     What you should see

    Still few finds, and nothing grows — but customer 2 is copied into every one of its orders, and a customer who has not ordered yet (the 0 in Customer (0,N)) has no document to live in. This is the reverse link that the recipe tells you to skip (p. 1449).

  4. The one insight: every embedding buys finds with a stop sign. Reference everything — "Customer_ID in each order" and "Product_ID in each line" — and predict the finds and the colours.
    What you should see

    Three finds, three collections, four green stop signs: you have rebuilt the tables of lesson 9, with only the order lines still inside their order. No setting gives one find and four green signs — so the decision is taken per relationship, by what the pages read together.

Embed what is read together, stays bounded and belongs to one parent; reference what grows, is shared or is read on its own.

From ER diagram to documents: the session's recipe

The exercise session turns these principles into rules for the diagram every exam starts from (pp. 1443–1450). Entities are the easy part: an entity becomes a collection, each of its instances a document, and each attribute a field (p. 1443):

// p. 1443: one entity, one collection
db.createCollection('user');
{
   "_id": "12345",
   "name": "John Doe",
   "email": "john.doe@example.com",
   "age": 30
}

Relationships change that picture, because some entities stop having a collection of their own. For a one-to-many the rule is: "Nest the entity on the N side inside the entity on the 1 side." Do not also copy the 1 side into each N-side document; you do not need that reverse link (p. 1449).

// p. 1449: the books (N side) inside their author (1 side)
{
   "_id": ObjectId("..."),
   "name": "J.K. Rowling",
   "books": [
      { "title": "Harry Potter and the Sorcerer's Stone",
        "year": 1997 },
      { "title": "Harry Potter and the Chamber of Secrets",
        "year": 1998 }
   ]
}

Which side is N? Read the pairs as lesson 6 taught (read it from the right side): the pair next to an entity counts the partners of one of its instances. Author (1,N) — Writes — (1,1) Book: an author writes one to many books, a book has exactly one author, so Book is the N side and the books go inside the author. For the papers: nest the entity next to (1,1) inside the entity next to (1,N).

"Nesting the other way round is just as good." It copies the 1 side into every N-side document and loses the instances without a partner: with Customer (0,N) — places — (1,1) Order, a customer who has not ordered yet has no document (try it in the widget above). Likewise an N-side instance that may lack a parent, (0,1), cannot be nested.

A many-to-many has no single parent to nest into, so you use references (p. 1450). One way is arrays of ids, here on both sides:

// p. 1450: Student (M:N) Course with reference ids
db.createCollection('student');
{
   "_id": ObjectId("..."),
   "name": "Alice",
   "enrolledCourses": [ ObjectId("course1"), ObjectId("course2") ]
}
db.createCollection('course');
{
   "_id": ObjectId("course1"),
   "title": "Database Systems",
   "students": [ ObjectId("student1"), ObjectId("student2") ]
}

The other way is a separate linking collection, with one document per pair:

// p. 1450: the same relationship as a linking collection
db.createCollection('enrollment');
{
    "studentId": ObjectId("student1"),
    "courseId": ObjectId("course1"),
    "enrolledOn": "2025-09-01"
}
ObjectId("course1") is a placeholder: a real ObjectId has 24 hexadecimal digits. In an answer write ObjectId("...") or use the entity's key as _id.

The linking document is the natural home of a relationship's own attribute: enrolledOn belongs to the pair (student, course), not to either side. The exam diagrams are full of them — Role on Works For, Since on Play, Production Date on Produce — and wherever the pair ends up, the attribute goes with it.

An ISA hierarchy carries the two letters you met in lesson 6, and each letter tells you which documents may exist (pp. 1445–1448). Take Person with the children Student and Professor:

  • Total (every person must be a student or a professor): only the children become documents, each with its own attributes plus the ones inherited from the parent.
  • Partial (may be): the parent becomes a document too, so a person who is neither child has a document with only the parent's attributes.
  • Exclusive (not both): each document has the attributes of one child.
  • Overlapping (also both): one document may have the attributes of several children.

In all four cases the documents go into one collection, person: the polymorphic structure of section 4 (p. 311). If the hierarchy lives inside another document, you can use one sub-collection or several; the slides list this under partial (p. 1469).

// after p. 1445 (total): only children, distinct _ids
db.createCollection('person');
// Instance of a student
{ "_id": "p1", "name": "John Doe", "fee": 1000 }
// Instance of a professor
{ "_id": "p2", "name": "Jane Roe", "salary": 1400 }
In one collection every document needs its own _id. The slides reuse "_id": "12345" in all their examples because they show alternative shapes, not documents that live side by side.

Write the fee on the student and the salary on the professor, even though the exclusive slide swaps them by mistake (p. 1447; compare pp. 1445–1446).

The exam's design question, solved

Every past paper opens its MongoDB exercise with a design question on a few entities of the ER diagram. Most papers of 2025 ask: "How many collections would you define within a documental database (clearly state it)? How would you implement the relations between the concepts? Provide a simple documental representation. (1 PT)"

Some papers ask for more. The exam of 11 Feb 2025 wants all attributes with their types or an example, none beyond the ER model, and leaves a blank for the number of collections. The paper of 30 January 2026 gives the question 2 points, wants all attributes, their types and comments, and adds: "You must design the relationships without using the MongoDB $lookup operation."

$lookup is the aggregation stage that joins two collections. The practical lectures never teach it, and the ban spells out the consequence: every query runs on one collection, so each document must contain everything the queries read. Here is that paper, exercise 3, step by step.

The scenario is a hospital heating management system. The question names four entities: Hospital (Hospital_ID, Name), Building (Building_ID, Name, Year), Department (Department_ID, Specialty, N_Beds, Head_Physician_ID) and Person (P_ID, Email), related as in Fig. 6. Two queries are printed below the design: for each hospital with more than 10 buildings, the number of departments with more than 25 people; and the total number of departments each person with the role 'maintenance' works for.

  1. Keep only the entities asked. Hospital, Building, Department, Person. Floor and the heating systems are on the diagram but not in the question: they stay out.

  2. List their relationships with the pairs. Has Building and Has Dept. have 1:N next to Hospital and 1:1 next to Building and Department: one-to-many. Works For has 1:N on both sides: many-to-many, with Role.

  3. Nest the N sides (p. 1449). Building and Department become the sub-collections buildings and departments of the hospital document, with no reverse link.

  4. Place the many-to-many by the queries. The recipe offers reference ids or a linking collection (p. 1450), but without $lookup a query on departments cannot reach people stored elsewhere. So each department carries its people, and Role goes inside each person entry, because it belongs to the pair.

  5. Count and type. One collection, hospital. The ER key becomes _id; every attribute appears once, with its type.

  6. Check against the queries. Buildings per hospital, people per department, the Role of each person entry: all inside one document, no join needed. (The pipelines are lesson 15's.)

// NUMBER OF COLLECTIONS: 1 (hospital)
db.createCollection('hospital');
{
  "_id": "H01",                    // Hospital_ID: String
  "Name": "Ospedale Nord",         // String
  "buildings": [                   // Has Building (1:N)
    { "Building_ID": "B01",        // String
      "Name": "Pavilion A",        // String
      "Year": 1968 }               // Integer
  ],
  "departments": [                 // Has Dept. (1:N)
    { "Department_ID": "D07",      // String
      "Specialty": "cardiology",   // String
      "N_Beds": 40,                // Integer
      "Head_Physician_ID": "P042", // String
      "people": [                  // Works For (M:N)
        { "P_ID": "P042",          // String
          "Email": "p042@nord.it", // String
          "Role": "head physician" // String, of Works For
        }
      ] }
  ]
}

The comments the paper asks for: Building and Department are nested because each belongs to one hospital; a person working for three departments appears three times, Email included — accepted, so that both queries run on one collection. A second collection person (P_ID, Email), with only P_ID and Role in the departments, would also work and store each Email once: say which you chose, and why. Both queries of the paper were run on this design on a real MongoDB server, without $lookup.

Read the queries first. They are printed right under the design question, and they tell you the root of your documents ("for each hospital…") and every entity that must be reachable from it by nesting.

No solutions are published, so this is our reading of what a complete answer shows:

  • the number of collections, stated;
  • every ER attribute with its type, none invented;
  • each relationship placed and named in a comment;
  • the duplication acknowledged;
  • documents on which the paper's queries run without $lookup.

Back to the hook. Storing the card is right when the pieces are read together, stay bounded and belong to this one order. That is true of the line items and the payment details. It is not true of Ann, who orders for years, nor of the products, each in thousands of orders. That is why the rule of thumb stops at "whenever possible": whether to embed is decided per relationship, by the four stop signs. With $lookup banned it becomes the exam's question: no query may join, so you nest along the queries and copy, with a comment, what a many-to-many shares.

Exam-style questions

Four theory questions in the form of the theory part — open answers of a few sentences, and closed ones where a wrong tick may cost points — and two design questions from past papers. The MongoDB exercise always starts from the paper's ER diagram; its design sub-question was worth 1 point in the 2024–2025 papers and 2 in the paper of 30 January 2026.

Explain why document-based databases were introduced. Describe the impedance mismatch problem with an example and explain how a document store addresses it.

Show model answer

The lecture gives three reasons: document databases handle schema changes well (easy development), they solve the impedance mismatch problem, and they follow the rise of JSON. The impedance mismatch is the difference between the shape of the data in the application and in a relational database. In the program an order is one object with a customer, a list of line items and payment details; in a relational database it is split over the tables orders, customers, order lines and credit cards, so every read must join the tables and every write must take the object apart. A document store keeps the order as one JSON-like document, with the line items as an array of sub-documents and the payment details as an embedded sub-document. The object is read and written as a unit, with one fetch and no join, and its data is stored together (better data locality). Since a collection does not impose a schema, new documents can carry new fields without changing the old ones.

A complete answer has three parts: the three reasons in the slide's words, a concrete object split over several tables, and the mechanism of the cure (embedding, one read). The order of p. 291 is the example the slide itself draws.

Which statement about BSON is correct according to the lecture?

  • BSON is a text encoding of JSON that is always more compact than JSON. BSON is binary, and not always smaller: {name: "sue", age: 26} takes 28 bytes as BSON and 23 characters as JSON text. Its gain is speed of scanning.
  • BSON types are a superset of JSON types, with the exception that BSON has no universal "number" type. The words of p. 301: BSON adds types such as date and byte array, but must choose between 32-bit integer, 64-bit integer and double where JSON has one number.
  • BSON cannot store dates, so dates are stored as strings. The opposite: the slide names the date as a type JSON lacks and BSON has.
  • A BSON document can have any size; MongoDB splits large ones automatically. A document may not exceed 16 MB (p. 298). GridFS stores large files in chunks, but it is a separate mechanism you choose, not an automatic split of documents.
Show model answer

BSON types are a superset of JSON types, with the exception of not having a universal "number" type as JSON does. BSON is a binary serialization of JSON-like documents: each entry has a field name, a data type and a value, and large elements are prefixed with their length to speed up scanning.

A closed question that quotes p. 301 almost word for word. Wrong ticks may be penalised: the "always more compact" option is the tempting one, and Fig. 4 shows why it is false.

A document has "_id": ObjectId("5ea64532a7678a3b27d34e00"), generated by MongoDB. Which statements are correct? Select all that apply.

  • The value is 12 bytes long, written as 24 hexadecimal digits. "The 12-byte ObjectId value" (p. 1420); two hexadecimal digits per byte.
  • Its first 4 bytes, 5ea64532, are the creation time in seconds since the Unix epoch. "A 4-byte timestamp value … measured in seconds since the Unix epoch": here 27 April 2020, 02:36:34 UTC.
  • It is assigned by a central counter of the server, like an auto-increment key. No central counter: a random value per process and a counter initialised to a random value make ids unique without coordination.
  • It is the value of the field that acts as the primary key of the collection. "_id field is always the primary key" (p. 297); "Every document must have an _id" (p. 303).
  • Another document of the same collection may have the same _id. The _id identifies a document within its collection, like a primary key: it must be unique there.
Show model answer

The first, second and fourth statements. An ObjectId is the default value of the mandatory _id field, the primary key of the collection. It has 12 bytes: a 4-byte timestamp (seconds since the Unix epoch), a 5-byte random value generated once per process, and a 3-byte incrementing counter initialised to a random value.

Three correct options of five. Wrong ticks may be penalised, so tick only what you can justify from p. 1420 and p. 297.

Explain the difference between embedding and referencing documents in MongoDB, and give one situation in which each is preferable.

Show model answer

Embedding stores the related data inside the document, as a sub-document or an array of sub-documents — for example the contact and access data inside the user, or the comments inside a post. One read returns everything, without a join, and the whole document is written in one operation. Referencing stores in one document the _id of another document, which lives in its own collection — for example user_id in a contact document, or post_id in a comment. The database does not enforce the reference and does not follow it: the application needs a second query. The lecture's rule of thumb is to embed whenever possible; the exercise session says to embed data that is often queried together and to reference data that is large or accessed independently. The line items of an order are always shown with the order and belong only to it, so they are embedded. A product appears in many orders and has its own catalogue page, so it is referenced by its id: embedding it would copy it into every order, and every price change would have to update all the copies.

A complete answer gives the two definitions, the cost of each (second query against duplication and growth), the rule of thumb and a pair of situations that follow from the criteria. Naming the 16 MB limit as the reason not to embed unbounded arrays is a good addition.

A blog shows each post with all its comments. A comment is never shown or edited on its own, and posts rarely get more than fifty. Which design follows the lecture's rule of thumb?

  • Embed the comments in the post as an array of sub-documents Read together, bounded, owned by one post: no stop sign is lit. This is p. 309.
  • A comments collection with a post_id in each comment It works, but every page view pays a second query for nothing. That is p. 310's normalized structure, worth it when comments are read alone or grow without bound.
  • Embed the post inside each of its comments This copies the post into every comment — the reverse link p. 1449 says you do not need.

Which of these are reasons to reference rather than embed? Select all that apply.

  • The related data grows without bound, like all the readings of a sensor Stop sign 1: the array drifts towards the 16 MB limit and every write rewrites a bigger document.
  • The related entity is shared by many parents, like a product in many orders Stop signs 2 and 3: embedding copies it into every parent, and a change must find every copy.
  • The related entity is read or updated on its own, like a product page Stop sign 4: it needs a collection of its own. The session: "accessed independently, store references".
  • The related data is always shown together with the parent That is the reason to embed: "If related data is often queried together, embed it" (p. 1444).
  • The related data is small Small, bounded data is the ideal thing to embed; size matters only when it is large or unbounded.

The session's two lines (p. 1444) contain all four stop signs: "large" is growth, "accessed independently" is access alone, and duplication and M:N are what "embed everything" costs.

The diagram says Author (1,N) — Writes — (1,1) Book. Following the session's recipe, where do the books go?

  • Inside the author document, as a sub-collection books Book is the N side: an author writes one to many books, a book has exactly one author. "Nest the entity on the N side inside the entity on the 1 side" (p. 1449).
  • Each book document embeds its author That is the reverse link: the author would be copied into every book, and an author with no book yet would have no document.

Why does MongoDB store documents as BSON rather than as JSON text?

  • Every field carries its type, and large elements carry their length, so the server has richer types and can skip what it does not need without parsing it "Each entry consists of a field name, a data type, and a value" and the length prefix "to facilitate scanning" (p. 301): hence "used for speed" (p. 299).
  • Because BSON is always smaller than JSON Not always: the type bytes and length prefixes cost space — 28 bytes against 23 in Fig. 4.
  • Because applications cannot produce JSON They produce it all the time; the drivers translate between the application's objects and BSON (p. 299).

In the paper of 30 January 2026, Works For links Department and Person (1:N on both sides) and has the attribute Role, and $lookup is banned. Where does Role go?

  • Inside each person entry embedded in the department: people: [{P_ID, Email, Role}] Role belongs to the pair (department, person), and the department's queries can read it without a join.
  • In a single Role field of the person A person may work for several departments with different roles; one field cannot hold the role of each pair.
  • In a single Role field of the department A department has many people with different roles; again the attribute belongs to the pair.

On p. 309 the post has "_id": "First Post". What does that show?

  • The _id need not be an ObjectId: a string or an integer works, as long as it is unique in the collection ObjectId is only the default when you supply none (p. 1420); p. 312 uses the integers 1 and 3, p. 1443 the key "12345".
  • It is a mistake: an _id must be an ObjectId The slides themselves use strings and integers; the ObjectId is generated only when no _id is given.
  • The post has no primary key It has one: the _id is always the primary key (p. 297), whatever its type.

Key take-aways

  • Document stores keep an object as the application sees it. The slide's three reasons are schema changes handled well, the impedance mismatch solved, and the rise of JSON (p. 291); data locality makes one document one read (p. 295).
  • A database holds collections, a collection holds documents, a document holds fields (pp. 1416–1418; p. 297: table, row, column). A field's value is a native type, an array or another document (p. 303). Every document has an _id, the primary key; by default a 12-byte ObjectId — 4-byte timestamp, 5-byte random value, 3-byte counter (p. 1420).
  • Documents are stored as BSON: field name, type and value per entry, lengths in front, types a superset of JSON's except the single number (pp. 299–301). A document may not exceed 16 MB; files go to GridFS (p. 298). The slide's "No Schemas", "No transactions", "No joins" are dated: $lookup and multi-document transactions exist.
  • Embedding puts related data inside the document (one read); referencing stores another document's _id (a second query, no enforcement) (pp. 304–305). The deck's structures are embedded (array of values, array of sub-documents), normalized and polymorphic (pp. 308–312).
  • "Rule of thumb is to imbed whenever possible" (p. 307) — until a stop sign: growth towards 16 MB, duplication, many-to-many, independent access. The session: embed what is queried together, reference what is large or accessed independently (p. 1444).
  • The recipe: entity → collection, attribute → field; 1:N → nest the N side in the 1 side, no reverse link; M:N → reference ids or a linking collection; ISA total/partial and exclusive/overlapping decide which document shapes exist, in one collection (pp. 1443–1450, 1469). At the exam: state the number of collections, type every attribute, comment the duplication, and with $lookup banned, nest along the queries.
