The relational model and the ER-to-table recipe

After this lesson you will read a relation as a set of tuples with named attributes, test whether a set of attributes is a key, check a referential constraint, and turn any binary relationship of an ER diagram into tables — knowing from its two (min,max) pairs where the foreign key goes.

Three sales, three customers. Heather bought S1 and S3, Steven bought S2, Dave has bought nothing yet. Three designs store who bought what:

  • A — a column in the Sale table: S1 → C1, S2 → C2, S3 → C1.
  • B — a column in the Customer table: Heather → "S1, S3", Steven → "S2", Dave → nothing.
  • C — a third table, one row per purchase: (S1, C1), (S2, C2), (S3, C1).

Same facts, three fates: one is not even a relation, one is a legal relation the slides tell you not to build, one is the slides' answer. By the end of the lesson two small pairs on the ER diagram — (1,1) next to Sale, (0,N) next to Customer — will tell you which is which, before you write a single row.

A relation is a set of tuples — with names

Page 85 in four lines: the relational model was "Proposed by E. F. Codd in 1970", "Made available in commercial DBMSs in 1981"; "It is based on (a variant of) the mathematical notion of relation"; "Relations are naturally represented by means of tables". The variant adds names, nulls and constraints.

Start with four football games (p. 88): Juve–Lazio 3–1, Lazio–Milan 2–0, Juve–Roma 1–2, Roma–Milan 0–1. Each is an ordered list of four values: string, string, integer, integer.

Cartesian product of the sets \(D_1, \dots, D_n\) ("n sets, not necessarily distinct") — "the set of all (ordered) n-tuples \((d_1, d_2, \dots, d_n)\) such that \(d_1 \in D_1, \dots, d_n \in D_n\)". A mathematical relation on \(D_1, \dots, D_n\) is "a subset of the cartesian product" (p. 86).

\[ \begin{aligned} &D_1 \times \dots \times D_n \\ &\quad = \{ (d_1, \dots, d_n) \mid d_i \in D_i \} \end{aligned} \] \[ r \subseteq D_1 \times D_2 \times \dots \times D_n \]
\(D_i\)
the domains
\(n\)
the degree
\(|r|\)
the cardinality: the number of n-tuples, "in practice, it is always finite"

So games \(\subseteq\) string × string × integer × integer has degree 4 and cardinality 4. Being a set, it has "no ordering between n-tuples", and "the n-tuples are distinct from one another" (p. 87). Inside a tuple, order rules: "the i-th value come from the i-th domain".

"Cardinality is the (min,max) pair." Not here. The word has two meanings in this course: the number of tuples of a relation (p. 86), and the (min,max) pair of an ER relationship (lesson 6), which rules the second half of this lesson.

The domain string plays two roles here, home team and visitors: "Each of the domains has two roles, distinguished by means of position" — "The structure is positional" (p. 88). Swap the first two values and Juve's home win becomes Lazio's. The relational data model wants "a non-positional structure": it associates "a unique name (attribute) with each domain; it 'describes' the role of the domain" (p. 89).

With names, a tuple is a set of attribute–value pairs and the column order means nothing. In Python terms, ('Juve', 'Lazio', 3, 1) became {'HomeTeam': 'Juve', …}: a tuple became a dict.

References are values, not arrows

Page 90 draws every row of Exams as two arrows, one into Students and one into Courses, and stops there. The relational model stores no arrows: Exams holds the values that identify the student and the course, and a reference is the same value in two tables.

Values beat arrows: 3456 means something on its own, survives a copy to another system, and can be checked by a rule — the subject of section 3.

Schema and instance

Page 91 fixes the words. A relation schema is "a name (of the relation) R with a set of attributes", a database schema "a set of relation schemas with different names"; an instance is the "set r of tuples on X" a schema holds now, one relation per schema for a database:

\[ R(A_1, \dots, A_n) \] \[ \mathbf{R} = \{ R_1(X_1), \dots, R_n(X_n) \} \] \[ \mathbf{r} = \{ r_1, \dots, r_n \} \]
\(R(A_1, \dots, A_n)\)
relation schema; its instance \(r\) is a set of tuples
\(\mathbf{R}\)
database schema
\(\mathbf{r}\)
database instance: one relation \(r_i\) per \(R_i\)

The schema is stable; the instance changes with every insert.

Nulls, constraints and keys

The structure is rigid (p. 92): "information is represented by means of tuples" and "tuples have to conform to relation schemas". What goes into a cell when there is no value? A null, of "(at least) 3 types" (p. 93):

The line to remember: "DBMSs do not distinguish between the types: they implicitly adopt the no-information value". SQL has one NULL — which is why NULL = NULL is not true there and you write IS NULL.

Constraints are predicates

An integrity constraint is "a property that must be satisfied by all meaningful database instances"; seen "as a predicate", an instance "is legal if it satisfies all integrity constraints" (p. 94). Intrarelational constraints stay in one relation — domain constraints check one value (a grade between 18 and 30), tuple constraints one tuple (honours only with a 30); interrelational ones span several relations. Keys are intrarelational, referential constraints interrelational.

Superkeys and keys

A key is "a set of attributes that uniquely identifies tuples in a relation"; p. 95 makes it precise in two steps.

Superkey — "a set of attributes K is a superkey for a relation r if r does not contain two distinct tuples \(t_1\) and \(t_2\) with \(t_1[K] = t_2[K]\)". Key — "K is a key for r if K is a minimal superkey (that is, there exists no other superkey K' of r that is contained in K as proper subset)" (p. 95).

\[ \forall\, t_1, t_2 \in r: \] \[ t_1[K] = t_2[K] \;\Rightarrow\; t_1 = t_2 \]
\(t[K]\)
the values of \(t\) on the attributes of \(K\)
key
no superkey \(K' \subsetneq K\)

Page 96 tries it on five students:

"RegNum is a key": five different values, and one attribute is minimal by force. The second claim, "Surname, Firstname, BirthDate is another key", takes four checks:

  1. Superkey? The five (Surname, FirstName, BirthDate) triples are all different: no two distinct tuples agree on them.

  2. Drop BirthDate. (Black, Lucy) occurs in 934856 and 965536: {Surname, FirstName} is not a superkey.

  3. Drop FirstName. (Smith, 29/04/59) occurs in 284328 and 296328: not a superkey.

  4. Drop Surname. (Lucy, 01/05/61) occurs in 587614 and 934856: not a superkey.

  5. Minimal. Smaller subsets lie inside these pairs, and tuples that agree on a set agree on its subsets. "no proper subset is also a superkey" (p. 96): a key.

The same test on {FirstName, BirthDate, DegreeProg} finds five different triples and only repeated pairs: on this instance, a key nobody would declare. Hence p. 97: constraints "correspond to properties in the real world", so "they are relevant at the schema level", and "individual instances could satisfy ('by chance') other constraints". An instance can refute a key, never prove one.

"{RegNum, Surname} is a key: its values never repeat." It is a superkey, not a key: drop Surname and RegNum alone still identifies. Every superset of a superkey is a superkey; only the minimal ones are keys. And every relation has a key: having no duplicate tuples, the set of all its attributes is a superkey.

"The presence of nulls in keys has to be limited", so "for each relation we select a primary key on which nulls are not allowed"; it is underlined, and "References between relations are realized through primary keys" (p. 98). A key with a null could neither tell its tuple apart nor be pointed at.

A key is a minimal set of attributes that never takes the same value twice in a legal instance; the primary key is the one chosen, underlined, never null.

Referential constraints: every value must find its row

Values link the tables — "Pieces of data in different relations are correlated by means of values of (primary) keys" — so nothing physical stops a value from pointing nowhere. "Referential integrity constraints are imposed in order to guarantee that the values refer to actual values in the referenced relation" (p. 99).

The slides' example (p. 100) is a database of traffic offences from 1992: Offences(Code, Date, Officer, Dept, Registration), Officers(RegNum, Surname, FirstName) and Cars(Registration, Dept, Owner). Look at the key of Cars: plate 6544 XY appears twice, with Dept 75 (Cordon Edouard's car) and with Dept 47 (Mimault Bernard's). The plate alone does not identify a car; the pair (Registration, Dept) does.

Referential constraint — it "imposes to the values on a set X of attributes of a relation \(R_1\) to appear as values for the primary key of another relation \(R_2\)". In the example: "the attribute Officer of Offences and relation Officers" and "the attributes Registration and Department of Offences and relation Cars" (p. 101).

\[ \forall\, t_1 \in r_1 \;\; \exists\, t_2 \in r_2 :\; t_1[X] = t_2[K_2] \]
\(X\)
the referencing attributes of \(R_1\) (the foreign key)
\(K_2\)
the primary key of \(R_2\); same number of attributes as \(X\)
The formula is the slide's sentence in the notation of p. 95. Tuples with a null in X are left out of the check.

Two features of the definition are easy to miss. It is directional: every offence must find its officer, but Officers may hold an officer whom no offence names — 638, Larue Jacques, is perfectly legal. And with a composite key it is checked on the pair as a whole: offence 630876 points at (6544 XY, 47), Mimault's car, and (6544 XY, 75) is another car altogether. Note too that the referencing attribute needs neither the key's name (Officer refers to RegNum) nor unique values (456 appears in three offences).

In SQL, which you know, the two constraints of p. 101 are two clauses of one statement; the composite one needs the FOREIGN KEY (…) REFERENCES … form:

-- p. 101 in SQL: Offences must find its officer and its car
CREATE TABLE Offences (
  Code         CHAR(6) PRIMARY KEY,
  Date         DATE,
  Officer      CHAR(3) REFERENCES Officers (RegNum),
  Dept         CHAR(2),
  Registration CHAR(7),
  FOREIGN KEY (Registration, Dept)
    REFERENCES Cars (Registration, Dept)
);

Pick an offence and change its officer or its car, or delete one row of Officers or Cars. A red cell holds a value that refers to no row; the outlined rows are where the chosen offence points.

From diagram to tables: Step 1 and the two rules

Pages 102–118, "ER to Relational — Quick summary", are a recipe. Step 1 handles the entities (p. 103): "Create a separate table to represent each entity in the conceptual model" — "1A: Each attribute of the entity becomes a column in the relational table", "1B: Each instance of the entity set will become a row in the relational table". The identifier, the filled circle of the diagram, becomes the primary key: Sale(SaleID, Date, Amount).

Entities are the easy part. A relationship can live in two places: in a separate table whose rows are the links, or as a posted foreign key — a column added to one entity's table that holds the key of the other ("post" is the slides' verb; the asterisk marks such a column: Sale(SaleID, Date, Amount, Cust-ID*)). Page 103 names the two criteria that choose:

Page 103 says "Steps 2-4 (see next)". The steps that follow run to Step 5.
  • "Redundancy = one fact in multiple places or multiple facts in one place";
  • "Load = the percentage of non-null values in a column";

and where to read them: "Participation Cardinalities communicate some of the information regarding redundancy and load".

\[ \text{load} = \frac{\begin{array}{c}\text{non-null values}\\ \text{in the column}\end{array}}{\text{rows of the table}} \]

Page 104 turns the criteria into two rules, one per number of the (min,max) pair:

Maximum cardinalities — "The general rule is to post into a '1' entity table" (it "avoids 'repeating groups' redundancy"); "You can NEVER post into an 'N' entity".

Minimum cardinalities — "The general rule is to post into a '1' (mandatory) entity table" (it "avoids null values in the foreign key column"); "This rule can be violated in some circumstances".

Why two rules of different strength? Read them as questions about the foreign-key cell of each row. The maximum asks how many partners a row can have. If more than one, one cell cannot hold them: you would need a list in a cell, a repeating group — "multiple facts in one place", the second kind of redundancy of p. 103. A list is not an atomic value, so the table stops being a relation: that rule cannot bend. The minimum asks whether every row has a partner. If it is 0, some cells stay empty: nulls, a lower load. That costs space and care, but the table is still a relation, so this rule may bend.

The maximum decides where a foreign key may live; the minimum decides whether its cells can be empty.

Step 2: many-to-many always gets its own table

Step 2 (p. 105) covers the four patterns (0,N)-(0,N), (0,N)-(1,N), (1,N)-(0,N), (1,N)-(1,N): "You must create a separate table to represent the relationship"; "The primary keys of the related entity tables are posted into the relationship table to form its primary key. This kind of primary key is called a composite or concatenated primary key" — and "There are no exceptions to this rule!!!".

Both maxima are N, so the maximum rule closes both entity tables; what is left is a table whose rows are the links. Its key is the pair because the pair identifies the link: a student takes a given course once. Note the crossed-out column: an array of course ids inside the student is exactly how a document database stores this relationship (lesson 13). What the relational model forbids, MongoDB allows on purpose.

Step 3: (1,1)-(1,1), one direction only

For the pattern (1,1)-(1,1), Step 3 (p. 108) first asks a design question: "consider whether the two entities are conceptually separate or whether they should be combined". If they stay separate: "3A: Post the primary key from one entity's table into the other entity's table as a foreign key", "3B: It doesn't matter which entity's primary key is posted into the other entity's table, but DO NOT post both", "DO NOT make a separate table". Page 109 shows Sale (1,1) — yield — (1,1) Cash Receipt both ways, CR-ID* in Sale or S-ID* in Cash Receipt: "Choose ONE of these; DO NOT do both!!!".

Why is the direction free? Both maxima are 1 and both minima are 1, so in either table every cell gets exactly one value: load 100 %, no list. Why not both? Then every link is stored twice — one fact in two places, two copies that can disagree. And a separate table would only repeat the two keys row by row.

Steps 4 and 5: the (1,1) side takes the key, otherwise load decides

Step 4 (p. 110): "For remaining relationships that have (1,1) participation by one entity set, post the related entity's primary key into the (1,1) entity's table as a foreign key" — six patterns: (0,N)-(1,1), (1,N)-(1,1), (1,1)-(0,N), (1,1)-(1,N), (0,1)-(1,1), (1,1)-(0,1). "Do NOT make a separate table". "Post a foreign key INTO the (1,1) entity's table from the other entity's table". And the warning that explains the hook: "If you post the opposite direction, either redundancy [for N maximums] OR load [for 0 minimums] will be a problem".

Page 111 is the hook's case: Sale (1,1) — Is-to — (0,N) or (1,N) Customer. Cust-ID* in Sale holds C1, C2, C1, one value per row. The other way both failures arrive at once: Heather's cell needs "S1, S3", Dave's stays empty. Page 112 isolates the second failure: Sale (1,1) — yields — (0,1) Cash Receipt. CR-ID* in Sale is full; S-ID* in Cash Receipt leaves CR4 empty — a receipt of $1,000 that comes from no sale.

"Post the (1,1) entity's key into the other table." Backwards. The foreign-key column lives in the (1,1) entity's table and holds the other entity's key. Read the cardinalities, never the verb on the diamond.

Step 5: when only (0,1) sides are left

Step 5 (p. 113) takes the five remaining patterns: (0,N)-(0,1), (1,N)-(0,1), (0,1)-(0,N), (0,1)-(1,N), (0,1)-(0,1). Now no table satisfies both rules. The maximum rule leaves two options: "posting into a (0,1) or making a separate table; you CANNOT post into the (0,N) or (1,N)". The minimum rule objects to the first, because it "will create null values that waste valuable space in the database" — "However, if a separate table would waste more space, then it is better to follow the maximum rule and break the minimum rule". Load breaks the tie:

  • "5A: Post the related entity's primary key into the (0,1) entity's table as a foreign key for any relationships for which that results in a high load";
  • "5B: Create a separate table for any relationships for which posting a foreign key results in low load";
  • "Note: For (0,1)-(0,1), step 5A, post whichever direction results in highest load; if neither direction yields high load, then follow step 5B".

The worked example (pp. 114–115) has 18 purchases, 26 cash disbursements and a few purchase returns. "pays for" is Purchase (0,1) — (0,1) Cash Disbursement: "Most purchases (14/18) result in cash disbursements", so Check# posted into Purchase is non-null in 14 rows of 18 — "a high load", "Worth breaking the minimum rule" — and the slide concludes: post Check# into Purchase. "allowance for" is Purchase (0,1) — (1,N) Purchase Return: "Few purchases (3/18) result in purchase returns" — "low load"; the other direction is closed by the maximum rule, "because one purchase return slip # can be associated with multiple purchases". "Conclusion: Make a separate table to represent the 'allowance for' relationship". Its rows are the three links; since a purchase has at most one return, Receiving Report# alone is its key (not on the slides; the widget below underlines it).

"Some cash disbursements (13/26) pay for purchases"

Each payment links one purchase to one disbursement — (0,1) on both sides — so the disbursements that pay are exactly as many as the purchases that are paid: 14, not 13. The two loads are 14/18 ≈ 78 % (Check# into Purchase) and 14/26 ≈ 54 % (Receiving Report# into Cash Disbursement).

The same slide says "Most purchases (14/18) result in cash disbursements", and its own drawing has 14 lines between the two clouds (and 28 disbursement dots, not 26). The conclusion does not change: Purchase has the higher load, and it is high. But if a question quotes the slide, the exam may be matched against the printed 13/26, "a medium load": know both.

Why should 50 % be the borderline between the two options?

The slides give no number; a count of cells gives one (this argument is not on the slides). Say the (0,1) table has n rows, r of them linked, and each key takes one cell. Posting costs one cell per row: n cells, n − r of them null. A separate table costs two cells per link: 2r. Posting is cheaper when n < 2r, that is when the load r/n is above one half — which fits the slide calling 13/26 = 50 % "a medium load" (p. 114). Today a null costs almost no space: the real trade-off is a nullable column against an extra join.

Relationship attributes travel with the link

Page 116 adds the last piece: "If relationship becomes a separate table, then relationship attributes are placed in that table"; "If relationship can be represented by a posted foreign key, relationship attribute is posted alongside the foreign key". A relationship attribute describes one link, so it lives where the link lives: a grade on TAKES goes into TAKES(Student#, Course#, Grade). In the exam of 12 September 2025, Animal (1,1) — House — (1,N) Farm carries a Housing Date: it goes into Animal next to the posted key, Animal(Tag, Name, Age, AnimalType, Breed, FarmName*, HousingDate). It can never go to the N side: a farm houses many animals, so which animal's housing date would the farm's one cell hold?

One fact in many places: the diagram was wrong

Page 117 ends the section with a diagnosis: an Employee table (EmpID, EmpName, Payrate, Hours Worked, Dept#, DeptName) and five questions: "What facts are in multiple places in this table?", "Reverse engineer to get the ER model that this table must represent", "Is the ER model that results in this table correct?", "What SHOULD the ER model have been instead?", "What is the correct relational model?"

The answers, in order. The facts in multiple places are "D423 is called Audit" (Andy's and Jennifer's rows) and "D821 is called Tax" (Craig's and Steven's) — the first kind of redundancy of p. 103. Reverse engineering the table gives one entity, Employee, with Dept# and DeptName among its attributes. That model is wrong: a department is a thing of its own, with its own identifier, and its name is a fact about the department. The model should have been Employee — Assigned to — Department (p. 118), and Step 4 then posts Dept# into Employee.

Why it matters: rename Audit and you must edit two rows — miss one and the table contradicts itself; a department with no employee cannot be recorded at all; delete Arlie and the fact that D777 is ISAAS disappears with that row. A correct ER gives tables in which every non-key column describes the thing its row stands for, so one fact in many places is the fingerprint of a wrong ER. Lesson 9 gives the same diagnosis a name: DeptName depends on Dept#, which is not the key — a transitive dependency — and the split of p. 118 is the step to third normal form.

Now the hook. Design B is not a relation: Heather's cell holds a list of sales, a repeating group, forbidden because Customer's maximum is N — and Dave's cell is NULL because Customer's minimum is 0. Design C is a legal relation, but Step 4 says "Do NOT make a separate table" when one side is (1,1). Design A is the slides' answer: Sale is (1,1), so Cust-ID* holds exactly one value in every row, load 100 %. Two pairs on the diagram decided it.

Exam-style questions

Five theory questions in the forms of the written exam (open, multiple choice, true/false; wrong closed answers may carry a penalty, announced just before the exam), then a load computation and a design on a past paper's ER diagram. The model answers use the slides' wording.

True or false: in the relational model a relation may contain two identical tuples, provided that they are stored in different positions of the table.

  • True A relation is a set: "the n-tuples are distinct from one another", and "there is no ordering between n-tuples", so there are no positions to tell two copies apart (p. 87).
  • False A relation is a set of tuples: no duplicates and no order between the tuples (p. 87).
Show model answer

False. A relation is a subset of a cartesian product, i.e. a set of n-tuples: the tuples are distinct from one another and there is no ordering between them. Only inside a tuple are the values ordered (the i-th value comes from the i-th domain), and the relational data model removes even that order by naming the attributes.

The trap is "different positions": tuples have no positions. SQL tables may contain duplicate rows when no key is declared; the relational model, as the slides define it, may not.

Define superkey and key of a relation. Using the relation Students(RegNum, Surname, FirstName, BirthDate, DegreeProg) with the five tuples shown in the lecture, show that {Surname, FirstName, BirthDate} is a key. Why are keys nevertheless defined at the schema level?

Show model answer

A set of attributes K is a superkey for a relation r if r does not contain two distinct tuples t1 and t2 with t1[K] = t2[K]. K is a key if it is a minimal superkey: no proper subset of K is a superkey.

The five tuples have five different (Surname, FirstName, BirthDate) triples, so the triple is a superkey. Each proper subset repeats a value: {Surname, FirstName} has (Black, Lucy) twice, {Surname, BirthDate} has (Smith, 29/04/59) twice, {FirstName, BirthDate} has (Lucy, 01/05/61) twice, and the single attributes repeat as well. Hence the triple is minimal: a key — of this instance.

Constraints correspond to properties of the real world, so they are associated with the schema and must hold in every legal instance. An individual instance can satisfy other uniqueness properties by chance (here {FirstName, BirthDate, DegreeProg} is also unique), and it can refute a key but never prove one.

A complete answer has three things: "distinct tuples" in the superkey definition, the word "minimal" with one counter-pair for each two-attribute subset, and the schema-versus-instance point of p. 97.

Which types of null value does the lecture distinguish, and which one do DBMSs adopt? Why are nulls not allowed in the primary key?

Show model answer

At least three: the unknown value (a domain value exists, but it is not known); the non-existent value (the attribute is not applicable for the tuple); the no-information value (we do not know whether a value exists or not — the logical or of the other two). DBMSs do not distinguish between them and implicitly adopt the no-information value.

The primary key is the key chosen to identify the tuples and to realise the references between relations. A tuple with a null in its key could neither be told apart from the others nor be referenced, so for each relation one key is selected as primary key and nulls are not allowed on it; its attributes are underlined.

A complete answer gives the three names, the "logical or", and the phrase "no-information value" for what DBMSs do. The second half asks for the reason, not just "PK is NOT NULL".

Define a referential constraint. In the database of the lecture — Offences(Code, Date, Officer, Dept, Registration), Officers(RegNum, Surname, FirstName), Cars(Registration, Dept, Owner) with primary key (Registration, Dept) — say which of these operations violates a referential constraint and why: (a) delete officer 638; (b) delete officer 456; (c) change the Dept of offence 630876 from 47 to 75; (d) set the car of offence 143256 to (5694 FR, 47).

Show model answer

A referential constraint imposes that the values on a set X of attributes of a relation R1 appear as values of the primary key of another relation R2. Here Offences.Officer refers to Officers and Offences.(Registration, Dept) refers to Cars.

(a) No violation: no offence references officer 638, and the constraint does not require every officer to be referenced. (b) Violation: offences 987554, 987557 and 630876 reference 456 and would refer to nothing. (c) No violation: (6544 XY, 75) is a row of Cars — although the offence now refers to Cordon's car instead of Mimault's: the constraint checks existence, not correctness. (d) Violation: 5694 FR and 47 both occur in Cars, but not in the same row; the foreign key is the pair, and (5694 FR, 47) is not a primary-key value of Cars.

The four cases test the two properties: direction ((a) against (b)) and the composite key matched as a whole ((d)). Case (c) is the subtle one: a legal instance is not necessarily a true one.

Key take-aways

  • A relation is a subset of a cartesian product: a set of tuples, so no order and no duplicates; degree = number of attributes, cardinality = number of tuples. The relational model names the domains, so the structure is non-positional, and it references by values, not by arrows.
  • The schema (R(A1, …, An), a set of relation schemas) is stable; the instance is the current content. Nulls have three meanings — unknown, non-existent, no-information — and DBMSs keep only the last.
  • Integrity constraints are predicates that every legal instance satisfies: intrarelational (domain, tuple, keys) or interrelational (referential). A superkey never repeats; a key is a minimal superkey; keys are schema decisions that an instance can refute but not prove; the primary key is underlined and never null.
  • A referential constraint makes the values of X in R1 appear as primary-key values of R2. It is directional, and a composite key is matched as a whole pair.
  • Step 1: entity → table, attribute → column, instance → row, identifier → primary key. For relationships the maximum decides where a foreign key may live (never in an N side) and the minimum whether its cells can be empty (prefer a mandatory side).
  • Step 2: many-to-many → separate table with a composite key, no exceptions. Step 3: (1,1)-(1,1) → one direction, never both. Step 4: post into the (1,1) side. Step 5: with (0,1) sides, high load → post (5A), low load → separate table (5B). Relationship attributes travel with the link.
  • One fact in many places is the fingerprint of a wrong ER: promote the repeated thing to an entity, and the tables come out right.
