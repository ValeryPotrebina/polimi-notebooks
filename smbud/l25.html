Inside an Elasticsearch index — and the rest of ELK

After this lesson you will say what survives when a node of an Elasticsearch cluster fails, write the complete mapping of an index from an ER entity as the exam asks for it, predict which terms an analyzer makes of a text, and name what Beats, Logstash and Kibana do around the index.

Page 597 sends one request to an index of New York restaurant inspections: GET /nyc-restaurants/_search with a match on "BORO": "Queens". The first hit is NEW YORK SHAKE & BURGER, borough Queens, with "_score" : 1.4879451.

Page 598 sends the same request with one letter changed, "BORO": "queens", and gets "hits" : [ ]: not a single document, "max_score" : null. Same index, same field, same borough — and match is the query that is supposed to be lenient with text.

Nothing is wrong with the data, and the query is not to blame: the outcome was decided before anybody typed a query. Keep both responses in mind. By the end of the lesson you will know what decided them, and why the person who set it up may still have made the right choice.

Who does what: the ELK stack

Page 569 stacks four programs as coloured bars: Kibana, "Visualize and Manage"; Elasticsearch, "Store, Search and Analyze"; Logstash + Beats, "Ingest". The initials of the first three name the ELK stack; p. 571 calls it the Elastic Stack.

Page 570 shows who talks to whom (Fig. 1). Beats are small programs on the machines where data is produced, each collecting one kind of data and shipping it, through their shared library libbeat, straight into Elasticsearch or to Logstash, which parses and enriches it first. Kibana reads what Elasticsearch holds and draws it.

The arrows carry a design decision: in this picture no data is born in Elasticsearch. It arrives from elsewhere — a web server's log, a database's rows — and is indexed to be searched, while the system it came from keeps the original. That is why two of the four programs exist only to bring data in.

Elasticsearch itself is the "Core of the Elastic Stack", a "Search & Analytic engine" with four properties (p. 571, again on p. 575):

  • "Based on Apache Lucene which enables full-text search": every text and keyword field ends up as terms in an inverted index, term → documents (lesson 24); the mapping and the analyzers decide which terms. (Numbers and dates get their own structures for range queries — background.)
  • "Distributed": an index is cut into shards on several machines, with copies.
  • "RESTful": you talk to it with HTTP requests carrying JSON.
  • "Near real-time: the time for a document to be searchable after indexing is very short" — short, not zero: by default new documents become searchable about once a second (background).

Documents, indices, shards and replicas

Start from one record: six fields of the inspection that p. 590 fetches from the index nyc-restaurants.

{
  "DBA" : "BENTO HOUSE",
  "BORO" : "Queens",
  "CUISINE DESCRIPTION" : "Chinese",
  "INSPECTION DATE" : "02/17/2021",
  "ZIPCODE" : 11354,
  "VIOLATION CODE" : "22G"
}

That is a document: "Elasticsearch stores data structures in JSON documents" (p. 576), JSON objects like MongoDB's (lesson 13), nesting included. "When stored, new documents are indexed and made fully searchable", and they "can be accessed from any ES node when in a cluster".

The documents of one kind form an index: a "Data organization mechanism", "Partitioned in shards", whose structure is defined "via mappings"; and "Elasticsearch is based on the concept of Inverted Index" (p. 577). Page 586 lines the words up with the relational ones:

The analogy holds for words, not mechanisms: a document nests, an index is cut into pieces, and "index" means the whole collection, not SQL's helper structure on a column.

Shards and replicas

An index is split into primary shards — "Each document in an index belongs to one Primary Shard" (p. 1621) — spread over the nodes of a cluster: the partitioning of lesson 3. A replica is a copy of a primary shard, with one condition: "Replicas: copies of shards stored on a different node" (p. 578). The same slide gives the traffic rules:

  • "Write operation → Primary → Replica (to copy)": the primary writes the document, then copies it to every replica.
  • "Read operation → Routed to primary or replica": any copy may answer.

Why one writer? If every copy accepted writes, copies could disagree; one primary per shard orders the writes and the replicas follow. Reads change nothing, so any copy will do — more replicas, more reads at once. But every write is done once per copy, so replicas never speed up writing. Per index this is two numbers, number_of_shards and number_of_replicas (per primary), plus a name and a location per node (p. 579).

Page 579 draws the result, and is easy to misread: its five boxes labelled "Node" cannot be one cluster — a primary cannot exist twice. Read them as one index, three primaries with one replica each, laid out on two different clusters (Fig. 2), with \(3 \times (1 + 1) = 6\) copies in each. In general \(P\) primaries with \(R\) replicas make \(P\,(1 + R)\) shard copies.

"Shards: distribute operations to … Increase resistance to faults (e.g. crashes when an indices get too big)"

Splitting an index into primary shards spreads its size and its work, so no node has to hold the whole index: that prevents the slide's example, a node overwhelmed by an index too big for it, and gives the next bullet's "Improve performance". It does not let the index survive the failure of a node: with "number_of_replicas": 0 a failed node takes its shards, part of the index, with it. That resistance comes from replicas on other nodes.

Check it in the widget below: replicas at 0, fail a node, and its shard is lost. The session repeats the list (p. 1621) but counts replicas as one of "two types of shards" — read that way, it is the replica shards that resist the failure. The exam may be matched against the printed wording: know it as printed, and in an open answer credit the replicas.

Shards and replicas: what survives a failure

An index with some primary shards (P, solid) and replicas (R, dashed) on the nodes of a cluster. The widget places each replica on a different node from its primary, as Elasticsearch does; a copy with no possible node waits under "unassigned". Choose a node that fails, and step through a write and two reads of a document of shard 1. The widget shows the moment right after the failure; after a short delay Elasticsearch rebuilds missing replicas on the surviving nodes when there is room (background).

  1. Set the index of p. 579: 3 primaries, 1 replica, 2 nodes. Predict the number of shard copies, then predict what is still served when Node 1 fails.
    What you should see

    \(3 \times (1 + 1) = 6\) copies, all placed. The layout is not the slide's top row — the widget spreads the primaries — but it obeys the same rule. When Node 1 fails, R1 and R3 on Node 2 are promoted to primaries: every shard is still served. The health turns yellow, because the lost replicas have no third node to be rebuilt on.

  2. Now 3 nodes, 3 primaries and replicas at 0. Before failing Node 2, say what part of the index survives.
    What you should see

    Shard 2 lived only on Node 2: it is lost, and the health is red. A third of the index is gone even though the data was "distributed". This is the one insight of the widget: shards spread the index, only replicas let it survive a failure. Put the replicas back to 1 and fail Node 2 again: R2 on Node 3 becomes the primary and nothing is lost.

  3. One node, one replica. Where do the replicas go? Then add a second node.
    What you should see

    Nowhere: all three replicas are unassigned, because a replica may not sit on the node of its primary, and there is no other node. With two nodes every replica finds a place. In general an index with R replicas needs at least R + 1 nodes to place them all.

  4. Step through the write and the reads with the default index. Then fail the node that holds P1 and step again: which copy receives the write now, and how many copies of shard 1 remain?
    What you should see

    The write goes to the primary, which copies it to the replica; a read can be answered by either copy. After the failure the promoted replica takes the write, and shard 1 exists once — one more failure and it is gone, which is why the health is yellow, not green, until Elasticsearch rebuilds a replica of shard 1 on Node 3.

Shards are not free: "The more shards you have, the more the management overheads", and "The larger the shard size, the more it takes to move them (if needed)" (p. 1622). The number of primaries is fixed when the index is created; the number of replicas can change at any time (background).

Talking to Elasticsearch: one REST request at a time

"Interactions with Elasticsearch happen through requests to REST endpoints", and "Actions depend on HTTP verbs" (p. 582): GET to read, POST and PUT "often used to create new documents, indices, etc.", and DELETE. You send them from a command line, from Postman, or from the "Developer Tools built in Kibana", the console of the exercise sessions. A request is a verb, an endpoint and, often, a JSON body. The shortest creates an index (p. 587):

# create an empty index
PUT /my_index

The answer, "acknowledged" : true, says that the index exists. Now add a document (p. 584):

# add a document; Elasticsearch picks its _id
POST /my_index/_doc
{
  "author":"Andrea",
  "title":"Set up Elasticsearch and Kibana in 15 minutes!",
  "date":"Tue, 23 Feb 2021 11:40:00 +0000",
  "categories": ["elasticsearch","tutorial",
                 "data science","bigdata"],
  "lang":"en-US"
}

Read it aloud: verb POST; endpoint /my_index/_doc, the documents of my_index; body, the document. No identifier is given, so "Elasticsearch takes care of creating and assigning IDs to documents" (p. 583): the answer carries "_id": "jYpU_XQBkGeBYJKltRh8" and "result": "created" (p. 585). With PUT you choose the identifier:

# create or replace document my_id
PUT /my_index/_doc/my_id
{
  "author":"Andrea",
  "lang":"en-US"
}

Hence the slide's warning (p. 583): "POST doesn't require the ID of the resource → duplicates", "PUT requires the ID of the resource → create or update the same one". Send the POST twice and the post is stored twice, under two ids; send the PUT twice and one document has _version 2. A PUT to a known address is idempotent; a POST to a collection is not.

A GET on a document's address reads it back (p. 590):

# one document by its _id
GET /nyc-restaurants/_doc/pZpozncBDaS7kSRanan2

The answer wraps the document in metadata — _index, _id, _version, _seq_no, _primary_term, "found" : true — and returns under _source the JSON exactly as it was sent. Searches look in the inverted index; _source is what they hand back. The last verb removes:

# delete one document; DELETE /my_index drops the whole index
DELETE /my_index/_doc/my_id

The mapping: what each field becomes

Ask the restaurant index for its structure:

# the mapping this index is using
GET /nyc-restaurants/_mapping
The _meta line of p. 581 names the tool that wrote this mapping: Kibana's file uploader ("ml-file-data-visualizer"), which proposes a type for every column of the uploaded file. BORO came out a keyword (p. 598).

Nobody typed the answer of p. 581, yet every field has a type: "@timestamp" : { "type" : "date" }, "ACTION" : { "type" : "text" }, "BBL" : { "type" : "long" }… "Is Elasticsearch really schemaless?" the slide asks, with an arrow labelled "Proof" to this answer. No: "Elasticsearch tries to guess the structure of the documents" — dynamic mapping — when it first meets a field, and keeps the guess.

A mapping is the schema of an index: with it "you can tell Elasticsearch the types of your documents' fields", "Decide which fields are searchable" and "Enable full-text search, time and geo-based queries" (p. 580). The type decides how a value is indexed, so it decides which questions can be asked of it. Page 589 teaches four types; the session's table adds more (p. 1635):

The hard choice is text against keyword. A text field is cut into words by an analyzer and searched word by word; a keyword field is one exact value, matched whole, counted and sorted. Decide by the question: "violations that mention mice" wants words, so text; "only Queens" and "how many per cuisine" want whole values, so keyword. Mind the slide's own list: a postcode is keyword even when it arrives as a number, like "ZIPCODE" : 11354 — you match postcodes, you never add them.

The guess is "risky (e.g. dates could be parsed as strings)" (p. 581): "02/22/2021" is not a date format Elasticsearch recognises by default, so it becomes a string — a text field with a keyword sub-field (background) — and sorting by it compares characters, not days.

What may change once documents are in

"Be careful as you CANNOT change the mapping on an existing index that already has documents!"

You cannot change the type — or most settings — of a field that already exists: for that you create a new index with the right mapping and copy the documents into it, a reindex. New fields can be added at any time, with PUT /my_index/_mapping.

The deck adds a field this way on p. 588, the session on p. 1632, and the session gives the rule for the rest: to update the mapping of a field "it is necessary to create a new index and reindex the data" (p. 1633). A type cannot change because the field's terms were indexed for the old type. The exam may be matched against the printed sentence: know it, and write the precise version in an open answer.

Adding a field (p. 588):

# add a text field to the mapping
PUT /my_index/_mapping
{
  "properties": {
    "field_name": {
      "type": "text"
    }
  }
}

The exam's question: the complete mapping of the index

Safer than any guess is a mapping written before the first document. The session shows the full form, settings and mapping side by side (p. 1663, "Define the full mapping describing a Person with 10 shards and 3 replicas"):

# an index with settings and mapping
PUT /people
{
  "settings": {
    "number_of_shards": 10,
    "number_of_replicas": 3
  },
  "mappings": {
    "properties": {
      "personal_id": { "type": "keyword" },
      "name": { "type": "text" },
      "surname": { "type": "text" },
      "birth date": { "type": "date", "format": "yyyy-MM-dd" },
      "address": { "type": "text" },
      "eye_color": { "type": "keyword" },
      "height": { "type": "integer" }
    }
  }
}

Read it from the outside in: PUT /people creates the index; settings gives it 10 primaries with 3 replicas each; mappings → properties holds one entry per field with its type and, for a date, its format. Analyzers: how a text becomes terms

A text field is "pre-processed" by an analyzer (p. 589), the program that turns a string into the terms of the inverted index. You can run one on any text (p. 594):

# the terms of a text
POST /_analyze
{
  "analyzer": "standard",
  "text": "The 2 QUICK Brown-Foxes jumped over the lazy dog's bone."
}

The answer lists tokens with their offsets and positions; the slide shows the first, "token" : "the" at position 0. The table runs the same sentence through every analyzer of pp. 591–593:

Check the slide's definitions against the rows. The standard analyzer "divides text into terms on word boundaries, as defined by the Unicode Text Segmentation algorithm. It removes most punctuation, lowercases terms, and supports removing stop words" (p. 592). The simple analyzer cuts "whenever it encounters a character which is not a letter" and "lowercases all terms": the 2 vanishes, "dog's" falls apart. The whitespace analyzer "does not lowercase terms": QUICK and Brown-Foxes survive. The stop analyzer "is like the simple analyzer, but also supports removal of stop words"; the keyword analyzer, a "noop", "outputs the exact same text as a single term"; the pattern analyzer splits "according to a custom regexp pattern" (p. 593) — the pattern marks the separators, by default every run of non-word characters, \W+, and the terms are lower-cased (background). A language analyzer "removes stopwords of a given language" and performs "stemming" (p. 591): english makes foxes fox and lazy lazi — a stem need not be a word, only shared by related words.

"The standard analyzer removes stop words." It "supports removing stop words" (p. 592) if you configure it to; by default it removes none — the first token on p. 594 is "the".

The analyzer runs twice: on every document when it is indexed, and on the query text of a match. Both sides must end with the same terms, or "Brown-Foxes" never meets "brown" — AN2DL's training–serving skew, where preprocessing that differs at serving time feeds the model inputs it never learned.

And a keyword field? "Borough (BORO) was mapped as a keyword. A keyword does not have any analyser!" (p. 598). Its value enters the index whole, as written, and so does the query text. The widget replays the hook on three documents from the slides.

    Keyword: 0 hits, because the whole string is one term and "Queens County" is not "Queens". Standard: 2 hits, because the text becomes two terms, "queens" and "county", and a match needs any one of them; "county" simply finds nothing.

The rest of ELK: Beats, Logstash and Kibana

Ingestion takes two programs because it has two jobs: "Beats focus on data collection and shipping", "Logstash focuses on processing and data normalization" (p. 617). Beats, a "Platform for data shippers" — Filebeat, Metricbeat, Packetbeat, Heartbeat — "Collect and ship logs and metrics from hosts or containers" (p. 616), light enough for every machine. Logstash, the "Streaming ETL engine of the ELK stack", does the heavy work once, centrally: "centralized data collection, processing and enrichment on the fly", "Data agnostic", with a "Wide range of integrations and processors" and "Ready-to-use monitoring and administrative panes built in Kibana" (p. 615). ETL is the warehouse word of lesson 23; streaming means event by event.

The slides print "Pool-based": read pull-based. A JDBC input polls a database on a schedule; Beats, TCP, UDP and HTTP inputs wait for data pushed to them.

Logstash also takes data without Beats, "Via TCP, UDP, HTTP protocols" or "Pool-based inputs like JDBC" that fetch it (p. 617), and emits it "to Elasticsearch, to other data stores or via TCP, UDP and HTTP protocols" (p. 619); in between, filters "structure, normalize and enrich data" (p. 618) — the three columns of p. 620.

Events and the pipeline

The slide prints the timestamp 2021-16-02T01-01-01: there is no month 16. Below, the intended 16 February 2021, as Logstash writes it.

What flows is an event: the "Primary unit of data in Logstash", "Similar to JSON documents", which "Flow through pipelines" (p. 623). The slide prints one as Logstash's debug output shows it, with => where JSON has a colon:

{
  "@timestamp" => 2021-02-16T01:01:01.000Z,
  "message" => "hello",
  "other_field" => {
    "nested_field" => 5678
  }
}

The pipeline, the "Logical flow of data" (p. 624, Fig. 3), "Supports multiple inputs", has a "Single queue to buffer data", "Either in-memory or persistent", and "Workers ensure server-side scalability".

Why a queue? Inputs and filters run at different speeds: bursts wait in the queue, and a slow Elasticsearch fills it until the inputs wait, without dropping events. Why workers? Parsing and enriching are expensive, so several threads do it at once, each on its own batch — scaling inside one server (background).

Codecs and filters

A codec changes "the data representation of an event" — "Serialization and de-serialization" — "as part of an input or output" (p. 625):

# parse the JSON lines of file.log
input{
  file {
    path => "file.log"
    codec => json
  }
}
# pretty-print events on the console
output{
  stdout {
    codec => rubydebug
  }
}

They are the slide's "Parse JSON data in file.log" (a real file input wants an absolute path, like /var/log/file.log) and "Format console output with Ruby Amazing Print", the => form above. A codec works at the edges, on bytes; a filter in the middle, on fields (pp. 626–627):

One filter almost every pipeline uses is missing: grok, which cuts an unstructured line into named fields with patterns (background) — the "structure" of p. 620, which geoip needs before it can enrich (Fig. 4).

The slide's own pipeline is the smallest complete one (p. 628):

# Beats in, Elasticsearch out
input {
  beats { port => 5043 }
}
filter {
  mutate { lowercase => ["message"] }
}
output {
  elasticsearch {}
}

The slide reads it: "Receive data from a host that uses Beats" (port 5043; a Beat sends to 5044 unless told otherwise — background), "Process that input via a filter" (lower-case message), "Output directly to Elasticsearch". Type straight quotes, not the slide's curly ones.

Delivery: at least once, and the dead letter queue

Page 629 promises "“At Least Once” message delivery": "In most conditions messages are delivered exactly once", but "Unclean shutdowns could lead to duplicates". With the persistent queue, an event leaves the queue only after the outputs accept it; if Logstash dies in between, the event is processed again at restart — twice in Elasticsearch, never zero times.

"“At Least Once” message delivery"

At least once holds only with the persistent queue, on disk. With the default in-memory queue, the events in flight are lost in a crash.

The guarantee needs a queue that survives the restart, and RAM does not (Elastic's documentation, background); p. 624 itself offers both queues, "Either in-memory or persistent". The exam may be matched against the printed bullet: know it, with its condition.

Some events can never be delivered: Elasticsearch rejects them, typically when a field contradicts the mapping. Retrying forever blocks the pipeline; dropping them breaks the at-least-once promise. The slide squeezes this into "Due to “at least once” policy these are undeliverable": the refusal makes them undeliverable, the policy forbids dropping them. The dead letter queue (DLQ) sets them aside on disk for later inspection: it "Avoids losing those events and halting the pipeline, freeing processing resources for subsequent events" (p. 629). It is off by default, and only the Elasticsearch output writes to it (background).

Modules, finally — "Provided by Logstash and Beats", "Available only for specific data types" — package the whole chain: "Automated parsing and enrichment in Logstash", "Custom schema in Elasticsearch", "Default dashboards in Kibana" (p. 621).

Kibana: every panel is a question to Elasticsearch

Kibana "is an open source data visualization dashboard for Elasticsearch" that "provides visualization capabilities on top of the content indexed on an Elasticsearch cluster" (p. 631): it shows what an index holds, nothing else. With it "you can aggregate, organize, filter and represent data" (p. 632) in dashboards of "basic representations, location-based analyses, time series, machine learning and graphs/networks" (p. 633), some paid.

A first dashboard (p. 635) is an editor with four labelled zones: "Dashboard Management", "Time and Fields Filters", "Tools to create a new Graph" and the space where "The Graphs you will create will be displayed". Its "Create Panel" (p. 636) offers Lens, Maps, "Aggregation based" charts, TSVB, a "Custom visualization" in Vega, Text and Controls: "easy to learn … but really hard to master" (p. 637).

Back to Queens

The hook resolves. BORO is a keyword, so "Queens" entered the index as one term, capital Q included. The query "Queens" became the same term; "queens" became a term with no posting list, hence "hits" : [ ]. A text field with the standard analyzer would have lower-cased both sides and found both.

Was keyword a mistake? No. A borough is a category to filter and count by, and "term aggregations only work on keywords" (p. 1658): the Kibana pie of inspections per borough needs this very mapping. Exactness costs spelling the value as stored. To have both, map text with a keyword sub-field, as dynamic mapping does, and query BORO for words, BORO.keyword for exact values. The mapping did not fail: it answered the question it was built for.

An index of restaurant inspections answers the request below with "hits" : [ ], although many of its documents contain "BORO" : "Queens". Which explanation is correct?

GET /nyc-restaurants/_search
{ "query": { "match": { "BORO": "queens" } } }
  • A match query is always case-sensitive. On a text field with the standard analyzer both sides are lower-cased, and "queens" finds "Queens".
  • The index has a single shard, so only part of the documents is searched. A search reaches every shard of the index; with one shard, that shard holds every document.
  • A match query cannot be used on fields that hold strings. The same match with "Queens" returns hits (p. 597).
  • BORO is mapped as keyword, which has no analyzer, so the query term "queens" must equal the stored term "Queens" exactly. The words of p. 598: "Borough (BORO) was mapped as a keyword. A keyword does not have any analyser!"
Show model answer

BORO is mapped as keyword. A keyword field has no analyzer: the stored value "Queens" is indexed as one exact term, and the query text "queens" is also used as one exact term. The two terms differ in case, so no document matches. With a text field and the standard analyzer, both would be lower-cased and the query would match.

A closed question built on pp. 597–598. Wrong ticks may be penalised: the tempting wrong answer is the first, which holds only for keyword fields and for analyzers that do not lower-case.

Explain the difference between primary shards and replica shards in Elasticsearch. How are write and read operations routed, and which of the two makes an index resistant to the failure of a node?

Show model answer

An index is partitioned into primary shards: each document belongs to exactly one primary shard, and the shards are distributed over the nodes of the cluster, so the data and the work are spread over several machines. A replica shard is a copy of a primary shard, always stored on a different node from its primary. A write operation is performed on the primary shard and then copied to its replicas, so all copies stay identical; a read operation can be routed to the primary or to any replica, so replicas also increase the capacity to serve reads. Resistance to faults comes from the replicas: when a node fails, a replica of each primary that was on it is promoted to primary and no data is lost, while without replicas the shards of the failed node are lost. Both numbers are set per index with number_of_shards and number_of_replicas.

The slides (p. 578) list resistance to faults under shards; the session (p. 1621) repeats it and counts replicas as one of "two types of shards". An answer that names the mechanism — a copy on another node — is right under every reading and shows that you know why.

True or false: once an index contains documents, the type of one of its existing fields can be changed in place with PUT /index_name/_mapping.

  • True The terms of that field were indexed for the old type. PUT /index_name/_mapping can add new fields, but not retype an existing one.
  • False To change the type you create a new index with the new mapping and reindex the documents into it.
Show model answer

False. The mapping of an existing field cannot be changed once documents are indexed: to change its type, create a new index with the correct mapping and reindex the data. PUT /index_name/_mapping can add new fields, but it cannot retype an existing one.

The statement is false both by the slide's printed sentence (p. 580) and by the precise rule — safe either way. Had it read "No field can be added to an index that has documents", the slide's wording and the facts would part ways (p. 588 adds one).

Describe the logical flow of data inside a Logstash pipeline. What are the queue and the workers for, and which delivery guarantee does Logstash offer?

Show model answer

A Logstash pipeline receives events from one or more inputs, for example Beats, TCP, UDP or HTTP listeners, or a JDBC input that polls a database. All inputs write into a single queue that buffers the events, either in memory or persistently on disk; the queue decouples the inputs from the processing and absorbs bursts. Worker threads take batches of events from the queue and run them through the filters, which structure, transform, normalize and enrich the events (for example mutate or geoip), and then through the outputs, for example Elasticsearch. Several workers run in parallel, which gives server-side scalability. Codecs attached to inputs and outputs deserialize and serialize the data. Logstash offers at-least-once delivery: in most conditions an event is delivered exactly once, but after an unclean shutdown it may be delivered twice; this requires the persistent queue. Events that cannot be processed go to the dead letter queue, so that they are not lost and the pipeline does not halt.

The figure of p. 624 is the skeleton: Input → Queue → Worker (Filter → Output). Naming the two kinds of queue and the condition of at least once shows that you know why the guarantee holds, not only its name.

An index is created with "number_of_shards": 2 and "number_of_replicas": 2. How many shard copies does it have, and how many nodes does it need so that every copy is placed?

  • 4 copies, 2 nodes 2 replicas per primary: each shard has 3 copies, not 2.
  • 6 copies, at least 3 nodes \(2 \times (1 + 2) = 6\); the 3 copies of a shard must sit on 3 different nodes.
  • 6 copies, 2 nodes With 2 nodes one of the three copies of each shard would have to share a node with another copy — not allowed, so it stays unassigned.
  • 2 copies, 1 node That counts only the primaries; replicas are copies too, and they can never sit on their primary's node.

Dynamic mapping meets the field "RECORD DATE" : "02/22/2021" for the first time. What does it most likely make of it?

Which analyzer keeps "Brown-Foxes" as one term but still cuts "The 2 QUICK Brown-Foxes" into several terms?

  • standard It splits on the hyphen: brown, foxes.
  • simple The hyphen is not a letter, so it splits there too — and it drops the 2.
  • keyword It keeps the hyphen, but makes the whole input a single term.
  • whitespace It cuts only at spaces: The, 2, QUICK, Brown-Foxes — and does not lower-case.

In a Logstash pipeline, where do the filters run?

  • In the input threads, before the events enter the queue Inputs only produce events and write them into the queue.
  • Inside the worker threads, on batches taken from the queue, before the outputs Input → Queue → Worker (Filter → Output), p. 624.
  • Inside Elasticsearch, when the document is indexed Logstash finishes its filters before the output sends anything to Elasticsearch.

Key take-aways

  • ELK: Beats and Logstash ingest, Elasticsearch stores, searches and analyzes, Kibana visualizes and manages (p. 569). Beats ship through libbeat either straight into Elasticsearch or through Logstash, which parses and enhances first (p. 570).
  • A document is a JSON object; an index is the collection of documents of one kind, with a mapping, partitioned in shards — table, row, column and schema in relational words (pp. 576–577, 586).
  • Each document belongs to one primary shard; replicas are copies on other nodes. Writes go to the primary, then to the replicas; reads go to either (p. 578). An index has \(P\,(1 + R)\) shard copies, and only replicas let it survive a node failure.
  • REST: PUT /index creates an index, POST /index/_doc adds a document with a generated id, PUT /index/_doc/id creates or replaces that one, GET /index/_doc/id returns it with its _source (pp. 582–590).
  • The mapping types the fields: text is analyzed and searched by words, keyword is one exact value, date takes a format, long and the other numbers hold numbers (p. 589). Dynamic mapping guesses once and keeps the guess; fields can be added later, a type changes only through a new index and a reindex (pp. 580–581, 588). The exam asks for PUT /index with mappings → properties.
  • An analyzer turns text into terms at index time and at query time — standard, simple, whitespace, stop, keyword, pattern, language (pp. 591–594). A keyword field has none, so "queens" does not find "Queens" (p. 598).
  • Logstash runs input → queue (memory or persistent) → workers (filter → output), with codecs at the edges, filters such as mutate, split, drop, geoip and translate, at-least-once delivery with a persistent queue, and a dead letter queue (pp. 615–629). Kibana draws what Elasticsearch computes (pp. 631–637).
