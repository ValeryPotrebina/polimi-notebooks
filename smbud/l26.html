Asking Elasticsearch: match, filter, bool and aggregations

After this lesson you will turn every Elasticsearch sentence of the exam — "includes the words", "removing the ones", "must not affect the final score", "prioritising", "the count for each" — into the right clause of a bool query or a terms aggregation, and predict the hits and scores that come back.

The lecture searches New York's restaurant inspections — the nyc-restaurants index of lesson 25 — with one query built in three steps. Step one keeps the inspections between 23 February 2020 and 23 February 2021: 9510 hits, each with score 1.0. Step two throws out the violation code 02G: 8923 hits, still 1.0. Step three adds one more clause, which the slide labels OR: the borough is Queens (pp. 604–606).

If the new clause were a real OR, more inspections could come in. If it were one more condition, only the Queens ones would stay. Write down your guess for the number of hits.

The answer is 8923 — not one more, not one fewer. Yet the best score jumps from 1.0 to 2.487945, and a Queens restaurant moves to the top. 2.487945 is 1.0 plus 1.4879451, the score of a plain search for Queens (p. 597). By the last section you will predict both numbers yourself.

match: the words you meant

A search is one HTTP request: a GET on the _search endpoint of an index, with a JSON body that holds the query (p. 595).

# the shape of every search (p. 595)
GET /nyc-restaurants/_search
{
  "query": {
    "match": {
      "FIELD": "TEXT"
    }
  }
}

Read it aloud: from nyc-restaurants, get the documents whose FIELD matches TEXT. Query clauses come in two kinds (p. 1641):

  • a leaf query clause — match, term, range — looks for a value in one field;
  • a compound query clause — bool — combines other clauses.

In SQL a leaf is one condition of a WHERE; bool is the AND, OR and NOT around the conditions.

The lecture starts with two match queries. One on INSPECTION TYPE returns inspections, the best scored 0.53188044 (p. 596). One on the borough, "BORO": "Queens", returns restaurants, the best scored 1.4879451 (p. 597) — keep that number in mind, it comes back at the end. Now write "queens" in lower case. The answer is empty (p. 598):

# the response to a match on "BORO": "queens" (p. 598)
{
  "took" : 0,
  "timed_out" : false,
  "_shards" : { "total" : 1, "successful" : 1, "skipped" : 0, "failed" : 0 },
  "hits" : {
    "total" : { "value" : 0, "relation" : "eq" },
    "max_score" : null,
    "hits" : [ ]
  }
}

Learn to read hits:

  • total.value counts the matches, and relation says whether that count is exact ("eq") or only a lower bound ("gte");
  • max_score is the best score, null when nothing matched;
  • the array hits lists the documents, best first and 10 at most by default, each with its _score and its stored JSON under _source.

Why nothing? On this index BORO is mapped as a keyword, and a keyword has no analyzer (p. 598). A match query first sends its text through the field's analyzer (p. 1644). On a text field the analyzer lower-cases the text and splits it into words, and by default a document qualifies when it contains at least one of them. On a keyword field nothing is split or lower-cased: the whole value must equal the stored one byte for byte, capital Q included. Lesson 25 shows how the mapping makes that choice; here you see what it does to your queries.

match analyses its text with the field's own analyzer: separate words on a text field, the whole value on a keyword field.

So be careful with the session's note that a match on publisher finds the games with "Daybreak", "Game" or "Company": here publisher is a keyword field, so the match looks for the whole value "Daybreak Game Company ", trailing space included — the note holds only for text fields (pp. 1638, 1645).

How many of the words?

A match with several words needs a rule: how many of them must a document contain? The operator sets it (p. 1646). With or, the default, one of the analysed words is enough; with and, the document needs all of them. The session tries both on its Steam video games, index steam_overviews (p. 1647):

# the AND variant of p. 1647: overview contains free, to and play
GET /steam_overviews/_search
{
  "query": {
    "match": {
      "overview": {
        "query": "free-to-play",
        "operator": "and"
      }
    }
  }
}

The analyzer cuts "free-to-play" into free, to and play. With "or" 61 games match; with "and", 35. The best score is 1.4712923 both times (p. 1648): the top game contains all three words, so its score — a sum over the words — stays the same. The operator decides who qualifies, not how a qualifying document is scored.

Options such as operator sit inside the field's object, next to "query". With no options the short form is enough — here, the games whose tags contain Free-to-Play (p. 1665):

# games whose tags contain free, to or play (p. 1665)
GET /steam_overviews/_search
{
  "query": {
    "match": {
      "tags": "Free-to-Play"
    }
  }
}

One field per match, and a count without documents

A match looks at one field. Name two fields in one match and Elasticsearch refuses with status 400: "[match] query doesn't support multiple fields, found [SCORE] and [BORO]" (p. 600). Two conditions are two clauses inside a bool (section 3). When you need only the number of matches, send the same body to _count (p. 599):

# how many inspections scored 13 (p. 599)
GET /nyc-restaurants/_count
{
  "query": {
    "match": {
      "SCORE": 13
    }
  }
}

The answer is "count" : 32930: no hits, no scores. You will meet 32930 again in section 4.

Exact conditions and the filter context

For an exact value there is the term query: it returns the documents whose field holds exactly the term you give. It does not analyse its input, and that is why the slide warns, in capitals, "DO NOT use term queries for text fields" (p. 1649): a text field stores analysed words, not the value you typed.

# games published by exactly "Ubisoft " (p. 1649)
GET /steam_overviews/_search
{
  "query": {
    "term": {
      "publisher": {
        "value": "Ubisoft "
      }
    }
  }
}

The space inside "Ubisoft " is not a typo. In this dataset every publisher ends with a space — a stored game reads "publisher": "Daybreak Game Company " (p. 1640) — and a term compares bytes: without the space, nothing matches. The short form { "term": { "publisher": "Ubisoft " } } is the session's answer when it asks for all the games published by Ubisoft (p. 1664). Fig. 1 shows what goes wrong when you use term on a text field.

Two options go inside the field's object, next to value (p. 1651):

  • case_insensitive (false by default) lets a term ignore case;
  • boost multiplies the clause's score — useful when the scores of several clauses add up and one should weigh more.
# "Ubisoft " in any case (p. 1651)
GET /steam_overviews/_search
{
  "query": {
    "term": {
      "publisher": {
        "value": "ubisoft ",
        "case_insensitive": true
      }
    }
  }
}

The third leaf, range, keeps the values inside an interval. Its bounds are gt, gte, lt and lte — greater than, greater or equal, less than, less or equal — and you use it mostly on numbers and dates (p. 1650):

# published in the last ten days, score doubled (p. 1650)
GET /steam_overviews/_search
{
  "query": {
    "range": {
      "publish_date": {
        "gte": "now-10d/d",
        "lte": "now",
        "boost": 2.0
      }
    }
  }
}

This request only shows the syntax: the Steam index has no publish_date (p. 1638). "now-10d/d" is date math, read in three steps: start from now, go back ten days (-10d), round to the day (/d). The slide's other examples are typed with spaces and wrong symbols; the working forms are now+1d/M, now-1y/y and 2022-07-28||+2M/M — small y for years, capital M for months, small m for minutes, and two pipes after an anchor date (p. 1652).

Two questions: how well, or whether

By default the hits come sorted by a relevance score: a number that says how well each document matches the query (p. 1642). Today that score is BM25, a descendant of the TF-IDF of lesson 24. But many conditions have no "how well": an inspection has violation code 04M or it does not. For those the lecture uses a filter: an exact yes/no test with no relevance score, whose answer can be cached (p. 601). You write it inside the filter array of a bool (p. 602):

The slide calls this request "IN Query", but a term is SQL's equality. SQL's IN, with a list of values, is the terms query (with an s), which the slides do not use.
# inspections with violation code 04M, unscored (p. 602)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "filter": {
        "term": {
          "VIOLATION CODE": "04M"
        }
      }
    }
  }
}

8711 hits, and every score is 0.0, max_score included. A clause can run in two contexts, and they differ only in the question they answer (p. 1643):

  • Query context asks "How well does this document match this query clause?" It decides whether the document matches and also computes a score.
  • Filter context asks "Does this document match this query clause?" It decides the same membership, but computes no score. The filter and must_not clauses of a bool run here.

Fig. 2 sends one clause through both.

Why have two contexts? A yes/no answer depends neither on the other clauses nor on the statistics of the index. So Elasticsearch can store it as a bit set, reuse it in the next query, and skip the scoring work — which is why the lecture calls filters more efficient than queries alone (p. 608). A filter is also how you ask for no score at all — for example, the games whose publisher is exactly Lag Studios, with no relevance score computed (p. 1667):

A filter usually tests an exact value on a field that is not analysed, but that is a habit, not a rule: filter is a context, any clause can run in it, and the session even filters with a match on a text field (p. 1678).
# publisher exactly "Lag Studios ", no score (p. 1667)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "publisher": "Lag Studios " } }
      ]
    }
  }
}

The lecture's last filter is prefix: it keeps the documents with a word that starts with the given string (p. 607).

# descriptions with a word starting with "flies" (p. 607)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "filter": {
        "prefix": {
          "VIOLATION DESCRIPTION": "flies"
        }
      }
    }
  }
}

The first hit's description begins "Filth flies": the prefix was tested on each word of an analysed text field, not on the whole value. The prefix itself is not analysed, like a term, so "Flies" would find nothing. The response says "value" : 10000, "relation" : "gte": at least ten thousand hits. By default Elasticsearch counts exactly only up to 10000.

bool: four clauses, two questions

Real questions carry several conditions, and one match can hold only one field. The answer is the bool query: four arrays of clauses, each with its own rule (pp. 603, 1653):

  • must: the document must match the clause, and the clause adds to its score — an AND that scores;
  • filter: the document must match the clause, but the score is ignored — an AND without score;
  • should: the document may match the clause, and if it does, the clause adds to its score. If should is the only clause, at least one of its conditions must hold — then, and only then, it is an OR;
  • must_not: the document must not match the clause; no score — a NOT.

Two questions sort the four (Fig. 3): must a document match the clause, and does the clause add to its score?

Each array is a list, so it can hold several clauses, and a query may use any of the four arrays, from one to all of them (pp. 1654–1655):

# Multiplayer games by exactly "Ubisoft ", Action first (p. 1655)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Multiplayer" } }
      ],
      "filter": [
        { "term": { "publisher": "Ubisoft " } }
      ],
      "should": [
        { "match": { "tags": "Action" } }
      ]
    }
  }
}

Read it clause by clause. Tagged Multiplayer: required and scored. Published by exactly "Ubisoft ": required, no score. Tagged Action: not required, but its score is added, so the Action games rise. A hit's _score is the sum of the scores of its must clauses and of the should clauses it matches, each multiplied by its boost; filter and must_not add nothing.

Next to a must or a filter, should never removes a document: it only adds score.

This second role of should is what the exam calls "prioritising". The session's example: the Free-to-Play games, with those developed by Daybreak Game Company first (p. 1666):

# Free-to-Play games, Daybreak's first (p. 1666)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Free-to-Play" } }
      ],
      "should": [
        {
          "term": {
            "developer": {
              "value": "Daybreak Game Company "
            }
          }
        }
      ]
    }
  }
}

So the lecture's label for should, OR, is only half true: should is an OR only in a bool with no must and no filter — the hook's third step, where the count stayed at 8923, is the proof (pp. 603, 605–606).

Where a clause sits

Four clauses over the dishes of Table 1. Put each in must, filter, should or must_not, or leave it out. You see the request, then every dish: the hits first, best score first, with the share of the score each clause gave; then, dashed, the dishes not returned and why. Scores are BM25 (k1 = 1.2, b = 0.75), Elasticsearch's default, computed on these twelve documents and rounded to two decimals; a range scores a constant 1.0, as on p. 604.

  1. Start with the salmon clause in must (the button "Start again"). Before touching anything, predict: if you move it to filter, which dishes disappear, and what happens to their scores? Then move it.
    What you should see

    Nothing disappears: the same four salmon dishes come back. Their scores (1.31, 1.21, 1.04, 0.91) all become 0.00, and the list falls back to the order of the index. This is the one thing the widget is built to show: moving a clause from must to filter never changes which documents come back, only its share of the score, which drops to zero. The order before the move is BM25 at work: Salmon salad says "salmon" twice; Salmon tartare has the shortest description.

  2. Leave the salmon clause out and put "stir boil" alone in should. How many hits? Now put the salmon clause back in must: predict the number of hits and the dish on top.
    What you should see

    Alone, should is an OR: the seven dishes whose recipe says stir or boil, Trofie al pesto first (both words, short recipe). With the salmon clause in must, the hits drop to the four salmon dishes — should no longer decides anything — and Salmon pasta rises to the top with 0.91 + 1.75 = 2.66, because its recipe has both words. Grilled salmon and Salmon salad stay, with a should share of 0.

  3. With salmon in must, put "butter" in must_not, then in filter. Predict both results before you switch.
    What you should see

    must_not: Grilled salmon disappears ("excluded by must_not"), and the three others keep exactly their scores — a negation adds nothing. filter: the opposite set, Grilled salmon alone, still 1.04, with butter contributing 0. Same clause, same membership test, opposite meaning — and neither placement scores.

  4. With salmon in must, put "price > 10" in must, then move it to filter. Can the order of the hits change?
    What you should see

    In must, Salmon salad (9.50) leaves and the three others each gain exactly 1.00: 2.21, 2.04, 1.91. In filter, the same three come back with 1.21, 1.04, 0.91 — the same order. A clause that gives every hit the same score cannot reorder them; it only costs scoring work. That is why a yes/no condition belongs in filter.

Filters and queries in one request

Put filters and queries in one request and you get both jobs done: the filters cut the set cheaply, and the queries rank what is left — you can raise a document's relevance at query time (p. 608). The lecture's example, though, puts both of its clauses in must:

# the lecture's filter-and-query example (p. 609)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "SCORE": "20"
          }
        },
        {
          "term": {
            "BORO": {
              "value": "Manhattan"
            }
          }
        }
      ]
    }
  }
}

The slide labels the term on BORO "Filter", but it sits in must, so it is scored like any query. The match on the number SCORE gives a constant 1.0; the best score of the 3935 hits is 1.9322574, so about 0.93 of it comes from the borough (p. 609). A condition meant as a filter goes in its own filter array, next to must — the only correct answer when the exam says the borough "must not affect the final score".

One more trick sits in the address: a search can cover several indices at once (p. 610). /_search searches every index, index_1,index_2/_search a list of them, and prefix*/_search every index whose name starts with the prefix.

Counting without reading: aggregations

Now count instead of search. In SQL, the number of inspections for each score is SELECT score, count(*) FROM nyc-restaurants GROUP BY score. In Elasticsearch it is (p. 611):

# inspections per score, SQL's GROUP BY (p. 611)
GET /nyc-restaurants/_search
{
  "size": 0,
  "aggs": {
    "score_groups": {
      "terms": {
        "field": "SCORE"
      }
    }
  }
}

Read it line by line:

  • "size": 0 — send back no documents, only the results of the aggregation (p. 1656);
  • "aggs" — the aggregations; it sits next to "query", not inside it;
  • "score_groups" — a name you choose; the response repeats it;
  • terms — a bucket aggregation: one bucket per distinct value of SCORE, each with its doc_count.

The response (p. 612):

# the first four buckets of the response (p. 612)
"aggregations" : {
  "score_groups" : {
    "doc_count_error_upper_bound" : 0,
    "sum_other_doc_count" : 184789,
    "buckets" : [
      { "key" : 12, "doc_count" : 41375 },
      { "key" : 13, "doc_count" : 32930 },
      { "key" : 10, "doc_count" : 21892 },
      { "key" : 11, "doc_count" : 21330 },
      …

Bucket 13 holds 32930 inspections — the _count of section 1. The buckets come sorted by doc_count, largest first. Then comes the line that is easy to miss: "sum_other_doc_count" : 184789. That many inspections fell in buckets that were not returned at all, because a terms aggregation returns only the 10 biggest buckets unless you raise its own size. So the request is really GROUP BY with ORDER BY count DESC LIMIT 10. Finally, "doc_count_error_upper_bound" : 0 says the counts are exact; on an index with several shards they can be approximate.

"With "size": 0 no buckets come back." No: there are two sizes. The top-level size is the number of hits — 10 by default — and 0 drops them. The size inside terms is the number of buckets, also 10 by default. The session's sentence about "the size parameter" mixes the two up; its own example uses the top-level one (p. 1656).

Aggregations come in families. The session names three (p. 1656):

  • metric aggregations compute a number from field values: count, min, max, avg, sum;
  • bucket aggregations group documents into buckets — by value (terms), by ranges (range) or by other criteria (filters);
  • pipeline aggregations take their input from other aggregations, not from documents.

The lecture adds a fourth family, matrix aggregations, which compute statistics over several fields at once (p. 613); current Elasticsearch files those under metrics. Know both lists: the course prints both.

On the 64 Steam games the session's games_per_publisher gives "Daybreak Game Company " 3 games and "sum_other_doc_count": 44 (p. 1657): the ten biggest publishers own only 20 games. Three combinations complete the toolkit.

First, a query and an aggregation in one request: the query selects the documents, and the aggregation groups only those (p. 1658). The session's exercise counts, for each developer, the games tagged Free-to-Play (p. 1668):

# Free-to-Play games per developer (p. 1668)
GET /steam_overviews/_search
{
  "size": 0,
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Free-to-Play" } }
      ]
    }
  },
  "aggs": {
    "f2p_per_devs": {
      "terms": {
        "field": "developer"
      }
    }
  }
}

A terms aggregation groups by exact values, so it needs a keyword field; for a text field, group by its keyword version, field_name.keyword. The slide says it as "term aggregations only work on keywords" (p. 1658) — it means the terms aggregation of the code, not the term query.

Second, several aggregations can sit side by side in one aggs, each its own GROUP BY (p. 1659). With "size": 0 the response has "hits": [] and "max_score": null, while total.value still reports 64.

Third, a bucket aggregation can carry sub-aggregations: they are computed separately inside each bucket, on that bucket's documents only (p. 1660):

# average price inside each publisher bucket (p. 1660)
GET /steam_overviews/_search
{
  "size": 0,
  "aggs": {
    "games_per_publisher": {
      "terms": {
        "field": "publisher"
      },
      "aggs": {
        "average_games_per_publisher": {
          "avg": {
            "field": "price"
          }
        }
      }
    }
  }
}

Every bucket answers "value": null: the syntax is right, but the index has no price field, so there is nothing to average (p. 1660). Despite its name, the sub-aggregation averages a price, not games: in pandas it would be df.groupby("publisher")["price"].mean(), kept to the ten largest groups. The widget's dishes have prices, so try it there.

Buckets, the cut, and what falls outside it

The twelve dishes of Table 1 again. Choose a query (it runs first), an aggregation and a field; for terms, set the size inside it and, if you like, an average price per bucket. The bars show the buckets that come back and, dashed, the documents that are only counted in sum_other_doc_count. Below them: the request and the response as Elasticsearch would print them, error texts included.

  1. Keep terms on course, no query, size 10. Predict the number of buckets and their order. Then set the size to 2 and predict sum_other_doc_count.
    What you should see

    Four buckets: first course 4, dessert 3, starter 3, main course 2 — largest first, and the tie goes to the smaller key ("dessert" before "starter"). With size 2 only first course and dessert come back, and sum_other_doc_count is 5: the three starters and the two main courses, counted but not shown. This is the one thing the widget is built to show: a terms aggregation returns the top size buckets by count, and everything below the cut is reduced to one number.

  2. Choose the field name.keyword and leave the size at 10. Twelve dishes, twelve names: what comes back?
    What you should see

    Ten buckets with doc_count 1, in alphabetical order because all counts tie, and sum_other_doc_count: 2 — Tiramisu and Trofie al pesto fall off the end. The default cut bites even on twelve documents; on p. 612 it left 184789 inspections outside.

  3. Now choose the field name (or description). What does Elasticsearch answer?
    What you should see

    An error, HTTP 400: "Text fields are not optimised for operations that require per-document field data like aggregations and sorting…". A text field keeps analysed words, not one value per document, so it cannot be grouped. name.keyword works — the slide's "field_name.keyword" (p. 1658).

  4. Set the query to match description "salmon", terms on course with the average price per bucket. Predict the buckets and the averages; then switch the aggregation to avg on price.
    What you should see

    The query keeps the four salmon dishes, and only they are grouped: starter 2 (average 11.75, from 14.00 and 9.50), first course 1 (12.00), main course 1 (18.00); total.value is 4. As a metric, avg returns one number for the four, 13.375 — no buckets, no sum_other_doc_count.

From the exam sentence to the request

Seven of the nine past papers carry an Elasticsearch exercise of 3 or 4 points, always on one entity of the paper's ER diagram, always in two moves. First the complete mapping of the index, from a stub "PUT …" to complete — lesson 25 teaches it. Then one or two queries, the subject of this section.

The two moves are linked: write the mapping for the queries that follow (lesson 25 has the full list of types). A field searched by its words is text, and you query it with match. A value matched whole or counted by is keyword, and you query it with term or count it with terms — a terms count on a text field fails. Numbers are integer or double, dates are date with their format, and both take a range; a Yes/No attribute is boolean. The query sentences themselves follow a small phrase book (Table 2).

One sentence, read clause by clause

The exam of 11 Feb 2025 followed Formula 1 races. Its Pilot is a Team Member, ISA (P, E), which is a Person, ISA (T, E): Personal_ID, Name, Surname, Birth_Date and Gender come from Person; Championships_Won and Career (Textual) are the pilot's own. The first sub-question, the mapping (1 PT), is solved in lesson 25: gender is a keyword, championships_won an integer, career text.

Then (2 PT): "Write a query to return male pilots who won at least 10 championships and whose career must include the words "Champion" and "Car", assigning a higher score to the ones whose career includes the word "Young"." Cut it at the clauses:

  • "male" and "at least 10 championships" are yes/no conditions with no "how well": filter;
  • "must include the words" is about words in a text field: two match clauses in must;
  • "assigning a higher score": should.
# male pilots, 10+ championships, Champion and Car; Young first
GET /pilots/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "career": "Champion" } },
        { "match": { "career": "Car" } }
      ],
      "filter": [
        { "term": { "gender": "Male" } },
        { "range": { "championships_won": { "gte": 10 } } }
      ],
      "should": [
        { "match": { "career": "Young" } }
      ]
    }
  }
}

The paper does not say that gender or the championships must leave the score alone, so must would be correct for them too: a term on a keyword field and a range give every hit the same score, which cannot change the order — task 4 of the first widget shows it. filter says what you mean, and costs less.

The counting move is the shortest. The exam of 30 May 2025 followed the production and sales of puzzles; its Puzzle has Puzzle ID, Name, Collection Name (e.g., Museum Collection), Number of Pieces, Width, Height and Description. It asks: "Write a query to compute the total number of puzzles for each collection name. (2 PT)". With collection_name mapped as keyword:

# puzzles per collection name, exam of 30 May 2025
GET /puzzles/_search
{
  "size": 0,
  "aggs": {
    "puzzles_per_collection": {
      "terms": {
        "field": "collection_name"
      }
    }
  }
}

Thirteen session exercises, and the hook

The session ends with thirteen exercises on the index employees50k (p. 1669). Address, Designation, FirstName, Gender, Interests, LastName and MaritalStatus are text; Age and Salary are integers; DateOfJoining is a date. The text fields behave as dynamically mapped strings, with a keyword sub-field — the last solution counts on Gender.keyword (p. 1682). Write each request before you open its answer.

The printed solutions use typographic quotes (“query”) and Swiss thousands separators (80’000). In the safe exam browser type plain JSON: straight quotes, 80000, a comma between two members and none after the last. {

  7. "… whose interests contains one or more words among "Paragliding", "Kayaking", and "Playing". The more words are found, the higher the final score." (p. 1676)

    Check yourself 
    GET /employees50k/_search
{

    "match": {
      "Interests": {
        "query": "Paragliding Kayaking Playing",
        "operator": "or"
      }
    }
  }
}

    One match with OR does both jobs: one word is enough to qualify, and the score is a sum over the words found. OR is the default, so { "match": { "Interests": "Paragliding Kayaking Playing" } } is the same request. The printed solution writes "operator" next to the field name, not inside its object, and calls the field "Interest": Elasticsearch would read operator as a second field and refuse, as on p. 600 (pp. 1651, 1676).

Back to the hook

Now you can read the lecture's three steps yourself (Fig. 5):

  • Steps one and two hold a must, the date range, and a must_not, the code 02G. A range gives every match the same score, 1.0, and must_not scores nothing: 9510 hits, then 8923, all at 1.0 (pp. 604–605).
  • Step three adds a should next to that must, so the new clause is optional: no inspection joins, none leaves — still 8923.
  • But every Queens inspection now adds the score of the should to the range's 1.0. The clause is a term on the keyword field BORO, which gives every Queens document the same score: 1.4879451, the score of the match on "Queens" (p. 597). So the best score is 1.0 + 1.4879451 = 2.4879451, printed as 2.487945 (p. 606).

Exam of 6 Jun 2024, exercise 4 — Elasticsearch (4 PT). ER (tracking natural disasters), the part used: Location (Postal Code, City, Country, Description); Occurr: Location 0:N – Natural Disaster 1:N.

"Consider the Location entity. 4.1. Provide the complete mapping of the index (i.e., field name, field type, the structure of the mapping, etc.) (1 PT) PUT …"

"Write a query to return the list of all the locations whose description includes the words "Beautiful" and "Town", removing the ones whose name includes the word "Milano". The condition on the word "Town" should not affect the final score. (1.5 PT)"

"Write a query to return the count of the locations for each country. (1.5 PT)"

Show model answer 
PUT /locations
{
  "mappings": {
    "properties": {
      "postal_code": { "type": "keyword" },
      "city": { "type": "text" },
      "country": { "type": "keyword" },
      "description": { "type": "text" }
    }
  }
}
GET /locations/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "Beautiful" } }
      ],
      "filter": [
        { "match": { "description": "Town" } }
      ],
      "must_not": [
        { "match": { "city": "Milano" } }
      ]
    }
  }
}
GET /locations/_search
{
  "size": 0,
  "aggs": {
    "locations_per_country": {
      "terms": { "field": "country" }
    }
  }
}

Location has no Name attribute: I assume the paper means the city.

Three choices decide this exercise. Postal code and country are keyword — one matched whole, one counted by — and the description is text. "Town … should not affect the final score" sends that word to filter, where a match is still analysed but scores nothing; "Beautiful" stays in must. The readme of the papers warns that an exercise may name something its diagram lacks and tells you to "consider all the necessary assumptions to solve the exercise": write yours in one line, as above. Add "size": 250 inside terms if every country must appear, not only the ten largest.

Exam of 24 Jun 2024, exercise 4 — Elasticsearch (4 PT). ER (tracking Disney's digital products), the part used: Location (ID, Name, Description, Furniture (Text), Indoor (Yes/No)); Located: Script 1:N – Location 1:1.

"Consider the Location entity. 4.1. Provide the complete mapping of the index (i.e., field name, field type, the structure of the mapping, etc.) (1 PT) PUT …"

"Write a query to return the list of Locations whose description includes the words "Stadium" and "Basketball", assigning a higher score to those including the words "Planet" in their furniture and "Space" in their description. (1.5 PT)"

"Write a query to return the count of indoor and outdoor locations. (1.5 PT)"

PUT /locations
{

}

{

  }
}

  "size": 0,

Exam of 13 Jun 2025, exercise 5 — Elasticsearch (3 PT). (The paper's header misprints its date as "Jan. 21, 2025".) "Consider the Track entity. Provide the complete mapping of the index for the considered entity (i.e., field name, field type, the structure of the mapping, etc.) (1 PT) PUT /"

"Write a query to return the documents whose composer is "Bach", whose duration is greater than 8 minutes, and whose music type is classical, prioritizing those with duration greater than 11 minutes. The condition on the composer must not affect the final score (2 PT)"

Show model answer 
PUT /tracks
{
  "mappings": {
    "properties": {
      "title": { "type": "text" },
      "duration": { "type": "integer" },
      "composer": { "type": "keyword" },
      "music_type": { "type": "keyword" }
    }
  }
}

{

    "bool": {
      "must": [

      ],
      "filter": [
        { "term": { "composer": "Bach" } }

Explain the difference between query context and filter context in Elasticsearch. Which clauses of a bool query run in each context, and when would you place a condition in filter context?

Show model answer

In query context a clause answers the question "how well does this document match?": it decides whether the document matches and also computes a relevance score, and the hits are sorted by that score. A leaf query placed directly under query, and the must and should clauses of a bool query, run in query context. In filter context a clause answers only "does this document match?": it decides membership, but no score is computed. The filter and must_not clauses of a bool query run in filter context. A condition belongs in filter context when it must hold but should not influence the ranking — an exact category, a date range, or any condition that the task says "must not affect the final score". Filtering is also cheaper: no scoring is done, and the yes/no result can be cached and reused by later queries.

A complete answer names the two questions (how well / does), says that the score is computed in one and not in the other, places all four clauses — must_not is in filter context too, which is often forgotten — and gives a reason to filter: ranking versus a pure condition, and the cache.

A bool query with a must clause (a range on the inspection date) and a must_not clause returns 8923 hits, all with score 1.0. A should clause, a term on the borough "Queens", is added. Which statement describes the new response?

  • Fewer hits: only the inspections in Queens. That is what a second must or a filter would do. Next to a must, a should clause is optional.
  • More hits: those in the date range or in Queens. A should clause cannot bring in documents that fail the must: every hit must still match the range.
  • The same 8923 hits; the Queens inspections get a higher score and move to the top. With a must present, should only adds its score to the documents that match it: the lecture prints 8923 hits and a best score of 2.487945 (p. 606).
  • The same hits with the same scores. A matching should clause "will contribute to the score" (p. 1653): the Queens inspections gain 1.4879451 each.
Show model answer

The same 8923 hits. Because the query has a must clause, the should clause is optional: it removes and adds no document, but it adds its score to the inspections in Queens, which rise to the top (best score 1.0 + 1.4879451 = 2.487945).

This is the lecture's own example (pp. 604–606). The slide labels should "OR", and the trap is the answer "more hits". Wrong closed answers may be penalised at the exam, so if you hesitate, remember that should is an OR only when it is alone.

Check yourself

A bool query has a match on the description in must and a range on the price in must. You move the range to filter. What happens?

  • Some hits disappear: filter is stricter than must. Both arrays are required: a document must match the clause either way, so membership does not change.
  • The same hits in the same order, each score 1.0 lower. A range gives every hit the same 1.0 in query context; in filter it gives 0. Subtracting the same amount from every score keeps the order — the first widget's task 4.
  • The same hits, but in a completely different order. The order could change only if the range gave different hits different scores; it gives all of them 1.0.
  • Every score becomes 0. Only the clause in filter stops scoring; the match in must still scores.

A bool query contains only should clauses. Which statements are true? Select all that apply.

  • A document must match at least one of them to be returned. "If should is the only clause included, at least one of the conditions must be satisfied" (p. 1653).
  • Every document of the index is returned; the clauses only reorder them. Alone, should is an OR: a document that matches none of the clauses is not returned. Reordering without removing is what should does next to a must or a filter — among the documents those clauses let in.
  • A document that matches two clauses scores more than one that matches only one, other things equal. The scores of the matching should clauses add up.
  • Every hit has score 0. should runs in query context: it is scored. Score 0 comes from filter and must_not.

Alone, should is an OR that scores; beside must or filter, it is a bonus.

The text field description of a dish holds "Salmon fillet with butter and herbs". What does { "term": { "description": "Salmon" } } return?

  • The dish, with a high score. A term is not analysed: it looks for "Salmon" with a capital S, and the index holds only "salmon".
  • An error: term is not allowed on text fields. Elasticsearch runs it without complaint. "DO NOT use" is advice, and the reason is the silent empty answer.
  • The dish, with score 0. Score 0 is what a filter gives. Here the dish is not found at all.
  • No hit at all. The analyzer stored the lower-case word salmon; match would have lower-cased the query too and found the dish (Fig. 1).

The response of p. 607 reads "total" : { "value" : 10000, "relation" : "gte" }. What do you know about the number of matching documents?

  • Exactly 10000 matched. An exact count would say "relation" : "eq".
  • At most 10000 could be found. Elasticsearch finds every match; it only stops counting them exactly.
  • At least 10000 matched; the exact number was not counted. "gte" means "greater than or equal": the count is a lower bound.
  • The query failed after 10000 documents. Nothing failed: the hits are there, best first.

You send "size": 0 and a terms aggregation, with no size inside it, on a keyword field with 25 distinct values. What comes back?

  • No hits; 10 buckets, the most frequent values first; the documents of the other 15 values counted in sum_other_doc_count. The top-level size drops the hits; the bucket count is the size of terms, 10 by default.
  • No hits and no buckets, because the size is 0. The top-level size counts hits, not buckets.
  • 25 buckets, one per value. Only with "size": 25 or more inside terms.
  • 10 hits and 25 buckets. "size": 0 means no hits, and the buckets stop at 10.

Which requests does Elasticsearch refuse with an error? Select all that apply.

  • A match whose object names two fields, SCORE and BORO. "[match] query doesn't support multiple fields", status 400 (p. 600).
  • A term query for "Male" on the text field Gender. It runs and silently returns nothing: no error, no hit.
  • A terms aggregation on a text field such as description. Text fields keep no single value per document: "term aggregations only work on keywords" (p. 1658).
  • size and aggs written inside query. Inside query Elasticsearch expects a query type; size is not one (p. 1681).

The dangerous slip is the one without an error: a term on a text field returns an empty list that looks like a real answer.

A bool query has a filter clause and a should clause, and no must. Which dishes come back?

  • Those matching both the filter and the should clause. With a filter present, should is optional, exactly as with a must.
  • Those matching the filter or the should clause. The filter is required: a dish that fails it is out.
  • All the dishes that match the filter; those that also match the should clause come first. The filter decides membership with score 0, and the should clause provides the only score.
  • Only the dishes that match the should clause, scored by the filter. A filter never scores.

Key take-aways

  • A search is GET /index/_search with a JSON body whose query is one leaf clause — match, term, range, prefix — or a bool that combines them; _count returns only the number, and one match looks at one field.
  • match analyses its text with the field's analyzer: words joined by OR (or by AND with "operator": "and") on a text field, the whole value on a keyword field. term never analyses and does not belong on text fields; range takes gt, gte, lt, lte and date math such as now-10d/d.
  • Query context asks how well a document matches and computes a score; filter context asks only whether it matches, scores 0 and can be cached. filter and must_not run in filter context.
  • must is a required, scored AND; filter a required AND without score; must_not a NOT without score; should a bonus, and an OR only when it stands alone. Scores add up — 2.487945 = 1.0 + 1.4879451 on p. 606 — and boost multiplies a clause's share.
  • "size": 0 and a named terms aggregation are GROUP BY with counts: the 10 biggest buckets come back, the rest only in sum_other_doc_count; a query filters first, sub-aggregations run inside each bucket, and a text field must be counted through field.keyword.
  • The exam exercise is a mapping written for the queries that follow, then sentences translated clause by clause: "includes the words" → must, "removing" → must_not, "must not affect the final score" → filter, "prioritising" → should, "the count for each" → terms.
