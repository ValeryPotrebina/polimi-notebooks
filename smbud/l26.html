Asking Elasticsearch: match, filter, bool and aggregations

After this lesson you will turn every Elasticsearch sentence of the exam — "includes the words", "removing the ones", "must not affect the final score", "prioritising", "the count for each" — into the right clause of a bool query or a terms aggregation, and predict the hits and scores that come back.

The lecture searches New York's restaurant inspections — the nyc-restaurants index of lesson 25 — with one query built in three steps (pp. 604–606). Step one keeps the inspections between 23 February 2020 and 23 February 2021: 9510 hits, each with score 1.0. Step two throws out the violation code 02G: 8923 hits, still 1.0. Step three adds a clause that the slide labels OR: the borough is Queens.

An OR can only let more documents in; read as a condition, the clause would keep Queens alone. Write down your guess for the number of hits.

The slide prints 8923 — not one more, not one fewer. Yet the best score jumps from 1.0 to 2.487945, and a Queens restaurant moves to the top. 2.487945 is 1.0 plus 1.4879451, a score printed on another slide (p. 597). The last section puts the two numbers together; by then you will have predicted them yourself.

match: the words you meant

A search is one HTTP request to the _search endpoint of an index, with a JSON body; the slide frames the request line as "Query" and the JSON as "Body" (p. 595).

# the shape of every search (p. 595)
GET /nyc-restaurants/_search
{
  "query": {
    "match": {
      "FIELD": "TEXT"
    }
  }
}

Read it aloud: from nyc-restaurants, get the documents whose FIELD matches TEXT. The session calls match, term and range leaf query clauses — they "look for a particular value in a specific field" — and bool a compound query clause, which wraps others "to combine multiple queries logically" (p. 1641). In SQL a leaf is one condition of a WHERE; bool is the AND, OR and NOT around the conditions.

The lecture's first real searches are two match queries. One on INSPECTION TYPE brings back inspections, the first scored 0.53188044 (p. 596); one on the borough, "BORO": "Queens", brings back restaurants, the first scored 1.4879451 (p. 597). With "queens" in lower case the complete answer is (p. 598):

# the response to a match on "BORO": "queens" (p. 598)
{
  "took" : 0,
  "timed_out" : false,
  "_shards" : { "total" : 1, "successful" : 1, "skipped" : 0, "failed" : 0 },
  "hits" : {
    "total" : { "value" : 0, "relation" : "eq" },
    "max_score" : null,
    "hits" : [ ]
  }
}

Learn to read hits: total.value counts the matches, and relation says whether that count is exact ("eq") or a lower bound ("gte"); max_score is the best score, null when nothing matched; the array hits lists the documents, best first and 10 at most by default, each with its _score and its stored JSON under _source.

Why nothing? "Borough (BORO) was mapped as a keyword. A keyword does not have any analyser!" (p. 598). A match query sends its text through the field's analyzer: "Whenever a text field is provided, it is analyzed before matching" (p. 1644). On a text field that gives lower-case words, and by default a document qualifies when it contains at least one of them; on a keyword field nothing is cut, and the whole value must equal the stored one byte for byte, capital Q included. Lesson 25 shows how the mapping takes that decision; here you see what it does to your queries.

match analyses its text with the field's own analyzer: separate words on a text field, the whole value on a keyword field.

This will match documents that contain “Daybreak", “Game", or “Company" in the publisher field

On this index publisher is a keyword field: the match looks for the one term "Daybreak Game Company ", trailing space included, and finds only the games whose publisher is exactly that.

The dataset slide types Publisher as Keyword (p. 1638), and the terms aggregation on it works (p. 1657), which a text field would refuse; a keyword "does not have any analyser" (p. 598). The sentence holds for text fields only. The exam may be matched against the printed note: know what it says, and that on a keyword field it is false.

How many of the words?

The operator decides how many of the analysed words a document needs: OR, "at least 1 word among the ones returned by the analyzer", is "the DEFAULT"; AND wants "all the words" (p. 1646). The session tries both on its Steam video games, index steam_overviews (p. 1647):

# the AND variant of p. 1647: overview contains free, to and play
GET /steam_overviews/_search
{
  "query": {
    "match": {
      "overview": {
        "query": "free-to-play",
        "operator": "and"
      }
    }
  }
}

The analyzer cuts "free-to-play" into free, to and play: with "or", the slide's request, 61 games match; with "and", 35. The best score is 1.4712923 both times (p. 1648): the top game contains all three words, and its score, a sum over them, cannot change. The operator decides who qualifies, not how a qualifying document is scored.

Options live inside the field's object, next to "query"; when there are none, the compact form is enough, as in "Extract all games which tags field contains the "Free-to-Play" tag" (p. 1665):

# games whose tags contain free, to or play (p. 1665)
GET /steam_overviews/_search
{
  "query": {
    "match": {
      "tags": "Free-to-Play"
    }
  }
}

One field per match, and a count without documents

Name two fields in one match and Elasticsearch refuses: "[match] query doesn't support multiple fields, found [SCORE] and [BORO]", status 400 — "You can only match 1 field at time" (p. 600). Two conditions are two clauses inside a bool (section 3). When only the number matters, the same body goes to _count (p. 599):

# how many inspections scored 13 (p. 599)
GET /nyc-restaurants/_count
{
  "query": {
    "match": {
      "SCORE": 13
    }
  }
}

The answer is "count" : 32930: no hits, no scores. The number comes back in section 4.

Exact conditions and the filter context

For an exact value the session has the term query, which returns "documents that contain an exact term in a provided field". Underlined on the same slide, DO NOT in red: "DO NOT use term queries for text fields. Remember that text fields are analyzed" (p. 1649).

# games published by exactly "Ubisoft " (p. 1649)
GET /steam_overviews/_search
{
  "query": {
    "term": {
      "publisher": {
        "value": "Ubisoft "
      }
    }
  }
}

The space inside "Ubisoft " is not a typo. The publishers of this dataset end with a space — the stored game reads "publisher": "Daybreak Game Company " (p. 1640) — and a term compares bytes: without the space, nothing matches. The compact form { "term": { "publisher": "Ubisoft " } } is the session's answer to "Extract all the games which publisher is "Ubisoft"" (p. 1664). Fig. 1 shows what the warning about text fields protects you from.

Two parameters "must be added within the field, together with the value parameter" (p. 1651): case_insensitive (default false) lets a term ignore case, and boost "is a float number that multiplies the relevance score of a query", useful when the scores of several clauses add up.

# "Ubisoft " in any case, with the parameter of p. 1651
GET /steam_overviews/_search
{
  "query": {
    "term": {
      "publisher": {
        "value": "ubisoft ",
        "case_insensitive": true
      }
    }
  }
}

The third leaf, range, takes the bounds gt, gte, lt and lte and is "usually employed with numerical fields or dates" (p. 1650):

# published in the last ten days, score doubled (p. 1650)
GET /steam_overviews/_search
{
  "query": {
    "range": {
      "publish_date": {
        "gte": "now-10d/d",
        "lte": "now",
        "boost": 2.0
      }
    }
  }
}

The Steam index has no publish_date (p. 1638 lists five fields): the slide shows the syntax only. "now-10d/d" is date math: an anchor, now; a step back of ten days, -10d; a rounding to the day, /d (p. 1652).

e.g., now +1d /M, now -1Y /Y, 2022.07.28 II +2M /M

Written without spaces and with the real symbols: now+1d/M, now-1y/y, 2022-07-28||+2M/M. Years are a lowercase y, and the slide's "II" stands for two pipes, ||.

Elasticsearch's date math knows the units y, M, w, d, h (or H), m and s: capital M is months, small m is minutes, and there is no Y, so now-1Y is refused. The anchor date must follow the field's date format, and the default reads 2022-07-28, not 2022.07.28. The rounding /M goes to the start of the month for gte and lt and to its end for gt and lte — not "to the closest" unit, as the slide says. The exam may be matched against the slide's wording: know it, and write the working syntax.

Two questions: how well, or whether

"By default, Elasticsearch sorts matching search results by Relevance Score, which measures how well each document matches a query" (p. 1642) — today a BM25 score, the descendant of the TF-IDF of lesson 24. Not every condition has a "how well". The lecture's slide on filters lists five properties (p. 601): "Exact match", "For fields that are not analyzed", "No relevance", "The filter is either satisfied or not", "Cacheable". Its example wraps a term in the filter of a bool (p. 602):

The slide labels this request "IN Query". A term is SQL's equality; SQL's IN with a list of values is the terms query, which the slides do not use.
# inspections with violation code 04M, unscored (p. 602)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "filter": {
        "term": {
          "VIOLATION CODE": "04M"
        }
      }
    }
  }
}

8711 hits, "max_score" : 0.0, and "_score" : 0.0 on every hit. The session names the two worlds (p. 1643). Query context asks "How well does this document match this query clause?": it decides whether the document matches, and the relevance score IS computed. Filter context asks "Does this document match this query clause?": it decides the same thing, but the score IS NOT computed; it is "Applied with the filter or must_not parameter". Fig. 2 sends one clause through both.

Why keep two contexts? A yes/no answer depends neither on the other clauses nor on the statistics of the index, so Elasticsearch can store it as a bit set and reuse it in the next query, and it skips the scoring work. That is the lecture's "It's more efficient than doing only queries" (p. 608). A filter is also how you ask for no score at all, as in "Extract all games which publisher is exactly "Lag Studios" without computing the relevance score" (p. 1667):

"For fields that are not analyzed" describes the usual filter, not a rule: filter is a context, and the session itself filters with a match on a text field (p. 1678).
# publisher exactly "Lag Studios ", no score (p. 1667)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "publisher": "Lag Studios " } }
      ]
    }
  }
}

The lecture's last filter is prefix: the documents with a word that starts with the given string (p. 607).

# descriptions with a word starting with "flies" (p. 607)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "filter": {
        "prefix": {
          "VIOLATION DESCRIPTION": "flies"
        }
      }
    }
  }
}

The first hit's description begins "Filth flies": the prefix was tested word by word on an analysed text field, not on the whole value. The prefix itself is not analysed, like a term: "Flies" would find nothing. The response reads "value" : 10000, "relation" : "gte" — at least ten thousand hits. Elasticsearch counts exactly only up to 10000 unless asked to go on (background, from the Elasticsearch documentation).

bool: four clauses, two questions

Real questions carry several conditions, and the one-field rule forbids packing them into one match. The lecture answers with a skeleton of three arrays, framed and labelled (p. 603): must — AND, must_not — NOT, should — OR. The fourth array, filter, is where the lecture's own filters sat (pp. 602, 607); the session gives the rule of each in a table (p. 1653):

  • must: "The query must appear in matching documents and it will contribute to the score."
  • filter: "The query must appear in matching documents. However, unlike must the score of the query will be ignored."
  • should: "The query should appear in the matching document. If so, it will contribute to the score. If should is the only clause included, at least one of the conditions must be satisfied."
  • must_not: "The query must not appear in the matching documents. The scoring is ignored."

Two questions sort the four (Fig. 3): must a document match the clause, and does the clause add to its score?

Each array holds a list of clauses — "Each of the clauses described may contain multiple conditions" (p. 1654) — and a query may use "all or just a few of the clauses" (p. 1655):

# Multiplayer games by exactly "Ubisoft ", Action first (p. 1655)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Multiplayer" } }
      ],
      "filter": [
        { "term": { "publisher": "Ubisoft " } }
      ],
      "should": [
        { "match": { "tags": "Action" } }
      ]
    }
  }
}

Read it clause by clause. Tagged Multiplayer: required and scored. Published by exactly "Ubisoft ": required, no score. Tagged Action: not required, but its score is added, so the Action games rise. A hit's _score is the sum of the scores of its must clauses and of the should clauses it matches, each multiplied by its boost; filter and must_not add nothing.

Next to a must or a filter, should never removes a document: it only adds score.

That second life of should is the session's "prioritizing" — "Extract all games which tags field contains the "Free-to-Play" tag, prioritizing those whose developer is "Daybreak Game Company"" (p. 1666):

# Free-to-Play games, Daybreak's first (p. 1666)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Free-to-Play" } }
      ],
      "should": [
        {
          "term": {
            "developer": {
              "value": "Daybreak Game Company "
            }
          }
        }
      ]
    }
  }
}

"should": [ {} ] OR

should is an OR only in a bool query that has no must and no filter clause. Next to a must or a filter its clauses are optional: they add their score to the documents that match them and never remove a document.

The lecture's own build shows it — the hook of this lesson: adding the clause labelled OR left the count at 8923 (pp. 605–606) and only raised the best score. The session's table states the rule: "If should is the only clause included, at least one of the conditions must be satisfied" (p. 1653). The exam may be matched against the printed label: know that the lecture calls should OR, and when that is true.

Where a clause sits

Four clauses over the dishes of Table 1. Put each in must, filter, should or must_not, or leave it out. You see the request, then every dish: the hits first, best score first, with the share of the score each clause gave; then, dashed, the dishes not returned and why. Scores are computed here with BM25 (k1 = 1.2, b = 0.75), the default scoring function of current Elasticsearch, on these twelve documents, and rounded to two decimals; a range scores a constant 1.0, as on p. 604.

  1. Start with the salmon clause in must (the button "Start again"). Before touching anything, predict: if you move it to filter, which dishes disappear, and what happens to their scores? Then move it.
    What you should see

    Nothing disappears: the same four salmon dishes come back. Their scores (1.31, 1.21, 1.04, 0.91) all become 0.00, and the list falls back to the order of the index. This is the one thing the widget is built to show: moving a clause from must to filter never changes which documents come back, only its share of the score, which drops to zero. The order before the move is BM25 at work: Salmon salad says "salmon" twice; Salmon tartare has the shortest description.

  2. Leave the salmon clause out and put "stir boil" alone in should. How many hits? Now put the salmon clause back in must: predict the number of hits and the dish on top.
    What you should see

    Alone, should is an OR: the seven dishes whose recipe says stir or boil, Trofie al pesto first (both words, short recipe). With the salmon clause in must, the hits drop to the four salmon dishes — should no longer decides anything — and Salmon pasta rises to the top with 0.91 + 1.75 = 2.66, because its recipe has both words. Grilled salmon and Salmon salad stay, with a should share of 0.

  3. With salmon in must, put "butter" in must_not, then in filter. Predict both results before you switch.
    What you should see

    must_not: Grilled salmon disappears ("excluded by must_not"), and the three others keep exactly their scores — a negation adds nothing. filter: the opposite set, Grilled salmon alone, still 1.04, with butter contributing 0. Same clause, same membership test, opposite meaning — and neither placement scores.

  4. With salmon in must, put "price > 10" in must, then move it to filter. Can the order of the hits change?
    What you should see

    In must, Salmon salad (9.50) leaves and the three others each gain exactly 1.00: 2.21, 2.04, 1.91. In filter, the same three come back with 1.21, 1.04, 0.91 — the same order. A clause that gives every hit the same score cannot reorder them; it only costs scoring work. That is why a yes/no condition belongs in filter.

"Filter and Query combination"

The lecture sums up the gain in three lines (p. 608): "You can combine filter and queries", "It's more efficient than doing only queries", "You can increase the relevance of a document at query time". Its example, though, labels its clauses in a way that would mislead you at the exam.

# the lecture's "Filter and Query combination" (p. 609)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "SCORE": "20"
          }
        },
        {
          "term": {
            "BORO": {
              "value": "Manhattan"
            }
          }
        }
      ]
    }
  }
}

"match": { "SCORE": "20" } labelled Query, and "term": { "BORO": { "value": "Manhattan" } } labelled Filter — both inside "must": [ ]

Both clauses sit in must, so both run in query context and both are scored. A condition that is meant as a filter goes in its own array, "filter": [ … ], next to must.

The response shows the cost: "max_score" : 1.9322574 for 3935 hits (p. 609). An exact match on a number scores a constant 1.0, like the range of p. 604 (computed, not printed), so about 0.93 of the best score comes from the clause labelled Filter. Asked for "the condition on the borough must not affect the final score", this structure breaks the requirement. The exam may be matched against the printed labels: know them, and know where a real filter goes.

One more address trick (p. 610): "Elasticsearch allows to search in multiple index at the same time". /_search searches every index, index_1,index_2/_search a list of them, and prefix*/_search every index whose name starts with the prefix.

Counting without reading: aggregations

The lecture starts from SQL (p. 611): SELECT score, count(*) FROM nyc-restaurants GROUP BY score becomes

# inspections per score, SQL's GROUP BY (p. 611)
GET /nyc-restaurants/_search
{
  "size": 0,
  "aggs": {
    "score_groups": {
      "terms": {
        "field": "SCORE"
      }
    }
  }
}

Read it line by line. "size": 0: send back no documents — "size=0 means we don't want actual documents, just the aggregation results" (p. 1656). "aggs": the aggregations, a sibling of "query". "score_groups": a name you choose, which the response repeats. terms: a bucket aggregation — one bucket per distinct value of SCORE, each with its doc_count. The response (p. 612):

# the first four buckets of the response (p. 612)
"aggregations" : {
  "score_groups" : {
    "doc_count_error_upper_bound" : 0,
    "sum_other_doc_count" : 184789,
    "buckets" : [
      { "key" : 12, "doc_count" : 41375 },
      { "key" : 13, "doc_count" : 32930 },
      { "key" : 10, "doc_count" : 21892 },
      { "key" : 11, "doc_count" : 21330 },
      …

Bucket 13 holds 32930 inspections — the _count of section 1. The buckets arrive sorted by doc_count, largest first. And "sum_other_doc_count" : 184789 says that 184789 inspections fell in buckets that were not returned at all: a terms aggregation returns only the 10 biggest buckets unless its own size is raised (background, from the Elasticsearch documentation). So the slide's request is GROUP BY with ORDER BY count DESC LIMIT 10. "doc_count_error_upper_bound" : 0 says the counts are exact; on an index with several shards they can be approximate.

"With "size": 0 no buckets come back." No. The top-level size is the number of hits — 10 by default — and 0 drops them. The number of buckets is the size inside terms, also 10 by default. The session's sentence "The size parameter defines how many results are returned in the aggregation" (p. 1656) blurs the two; its parenthesis — "size=0 means we don't want actual documents, just the aggregation results" — is the exact meaning of the top-level one.

The lecture lists four families of aggregations: "Metrics aggregations", "Bucket aggregations", "Pipeline aggregations", "Matrix aggregations" (p. 613). The session gives three, with definitions (p. 1656). Metric aggregations "calculate metrics from field values (count, min, max, avg, sum)". Bucket aggregations "group documents into buckets, based on field values (terms), ranges (range), or other criteria (filters, etc..)". Pipeline aggregations "take input from other aggregations instead of documents or fields". The lecture's fourth, matrix, computes statistics over several fields at once; today's documentation counts the session's three families and files those statistics under metrics (background). Know both lists: the course material prints both.

On the 64 Steam games the session's games_per_publisher gives "Daybreak Game Company " 3 games and "sum_other_doc_count": 44 (p. 1657): the ten biggest publishers own only 20 games. Three combinations complete the toolkit. First, a query selects the documents and the aggregation groups those: "Aggregations can be combined with regular queries to filter the data and then perform the aggregation" (p. 1658). The session's exercise "For each developer, extract the count of the games whose tags field contains the "Free-to-Play" tag" (p. 1668):

# Free-to-Play games per developer (p. 1668)
GET /steam_overviews/_search
{
  "size": 0,
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Free-to-Play" } }
      ]
    }
  },
  "aggs": {
    "f2p_per_devs": {
      "terms": {
        "field": "developer"
      }
    }
  }
}

The same slide adds an N.B.: "term aggregations only work on keywords (for texts, one can use field_name.keyword to use the keyword version of the field)" (p. 1658) — its "term aggregations" are the terms aggregations of the code, not the term query. Second, several aggregations can sit side by side in one aggs, each its own GROUP BY (p. 1659); with "size": 0 the response has "hits": [] and "max_score": null, while total.value still reports 64. Third, a bucket aggregation can carry sub-aggregations, "computed for each aggregation by considering the documents within each one of them" (p. 1660):

# average price inside each publisher bucket (p. 1660)
GET /steam_overviews/_search
{
  "size": 0,
  "aggs": {
    "games_per_publisher": {
      "terms": {
        "field": "publisher"
      },
      "aggs": {
        "average_games_per_publisher": {
          "avg": {
            "field": "price"
          }
        }
      }
    }
  }
}

Every bucket answers "value": null — "Price does not exists in the mapping, so it is set to null" (p. 1660): the syntax is right, the index has no price. Despite its name, the sub-aggregation averages a price, not games: in pandas it would be df.groupby("publisher")["price"].mean(), kept to the ten largest groups. The widget's dishes have prices, so try it there.

    What you should see

    An error, HTTP 400: "Text fields are not optimised for operations that require per-document field data like aggregations and sorting…". A text field keeps analysed words, not one value per document, so it cannot be grouped. name.keyword works — the slide's "field_name.keyword" (p. 1658).

From the exam sentence to the request

Seven of the nine past papers carry an Elasticsearch exercise of 3 or 4 points, always on one entity of the paper's ER diagram, always in two moves. First: "Provide the complete mapping of the index for the considered entity (i.e., field name, field type, the structure of the mapping, etc.)", with a stub "PUT …" or "PUT /" to complete. Then one or two queries. The session's own mapping exercise shows the structure: "Define the full mapping describing a Person with 10 shards and 3 replicas" (p. 1663).

# a Person index with 10 shards and 3 replicas (p. 1663)
PUT /people
{
  "settings": {
    "number_of_shards": 10,
    "number_of_replicas": 3
  },
  "mappings": {
    "properties": {
      "personal_id": { "type": "keyword" },
      "name": { "type": "text" },
      "surname": { "type": "text" },
      "birth date": {
        "type": "date",
        "format": "yyyy-MM-dd"
      },
      "address": { "type": "text" },
      "eye_color": { "type": "keyword" },
      "height": { "type": "integer" }
    }
  }
}

settings belongs in an answer only when the paper asks for shards or replicas; mappings, properties and one entry with its type per attribute are what every paper wants. Choose each type for the queries that follow — lesson 25 has the full list: text for anything searched by its words, keyword for a value matched whole or counted by, integer or double for numbers, date with its format, boolean for a Yes/No attribute. A terms count on a text field fails, so the field you will count by must be keyword. The queries then follow a small phrase book (Table 2).

One sentence, read clause by clause

The exam of 11 Feb 2025 followed Formula 1 races. Its Pilot is a Team Member, ISA (P, E), which is a Person, ISA (T, E): Personal_ID, Name, Surname, Birth_Date and Gender come from Person; Championships_Won and Career (Textual) are the pilot's own (the paper prints Career twice). The first sub-question, the mapping (1 PT), is solved in lesson 25: gender is a keyword, championships_won an integer, career text.

Then (2 PT): "Write a query to return male pilots who won at least 10 championships and whose career must include the words "Champion" and "Car", assigning a higher score to the ones whose career includes the word "Young"." Cut it at the clauses. "Male" and "at least 10 championships" are yes/no conditions with no "how well": filter. "Must include the words" is about words: two match clauses in must. "Assigning a higher score": should.

# male pilots, 10+ championships, Champion and Car; Young first
GET /pilots/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "career": "Champion" } },
        { "match": { "career": "Car" } }
      ],
      "filter": [
        { "term": { "gender": "Male" } },
        { "range": { "championships_won": { "gte": 10 } } }
      ],
      "should": [
        { "match": { "career": "Young" } }
      ]
    }
  }
}

The paper does not say that gender or the championships must leave the score alone, so must would be correct for them too: a term on a keyword field and a range give every hit the same score, which cannot change the order — task 4 of the first widget shows it. filter says what you mean, and costs less.

The counting move is the shortest. Back to the hook

Now the three steps of pp. 604–606 read themselves (Fig. 5). Steps one and two hold a must, the date range, and a must_not, the code 02G. A range gives every match the same score, 1.0, and must_not scores nothing: 9510 hits, then 8923, all at 1.0. Step three adds a should next to a must, so the new clause is optional: no inspection joins, none leaves — 8923. But every Queens inspection collects the score of the should on top of the range's 1.0. That clause is a term on the keyword field BORO, which scores every Queens document alike: 1.4879451, the score of the match on "Queens" printed on p. 597. The best score is therefore 1.0 + 1.4879451 = 2.4879451, displayed as 2.487945 (p. 606).

Explain the difference between query context and filter context in Elasticsearch. Which clauses of a bool query run in each context, and when would you place a condition in filter context?

Show model answer

In query context a clause answers the question "how well does this document match?": it decides whether the document matches and also computes a relevance score, and the hits are sorted by that score. A leaf query placed directly under query, and the must and should clauses of a bool query, run in query context. In filter context a clause answers only "does this document match?": it decides membership, but no score is computed. The filter and must_not clauses of a bool query run in filter context. A condition belongs in filter context when it must hold but should not influence the ranking — an exact category, a date range, or any condition that the task says "must not affect the final score". Filtering is also cheaper: no scoring is done, and the yes/no result can be cached and reused by later queries.

A complete answer names the two questions (how well / does), says that the score is computed in one and not in the other, places all four clauses — must_not is in filter context too, which is often forgotten — and gives a reason to filter: ranking versus a pure condition, and the cache.

A bool query with a must clause (a range on the inspection date) and a must_not clause returns 8923 hits, all with score 1.0. A should clause, a term on the borough "Queens", is added. Which statement describes the new response?

  • Fewer hits: only the inspections in Queens. That is what a second must or a filter would do. Next to a must, a should clause is optional.
  • More hits: those in the date range or in Queens. A should clause cannot bring in documents that fail the must: every hit must still match the range.
  • The same 8923 hits; the Queens inspections get a higher score and move to the top. With a must present, should only adds its score to the documents that match it: the lecture prints 8923 hits and a best score of 2.487945 (p. 606).
  • The same hits with the same scores. A matching should clause "will contribute to the score" (p. 1653): the Queens inspections gain 1.4879451 each.
Show model answer

The same 8923 hits. Because the query has a must clause, the should clause is optional: it removes and adds no document, but it adds its score to the inspections in Queens, which rise to the top (best score 1.0 + 1.4879451 = 2.487945).

This is the lecture's own example (pp. 604–606). The slide labels should "OR", and the trap is the answer "more hits". Wrong closed answers may be penalised at the exam, so if you hesitate, remember that should is an OR only when it is alone.

Check yourself

A bool query has a match on the description in must and a range on the price in must. You move the range to filter. What happens?

  • Some hits disappear: filter is stricter than must. Both arrays are required: a document must match the clause either way, so membership does not change.
  • The same hits in the same order, each score 1.0 lower. A range gives every hit the same 1.0 in query context; in filter it gives 0. Subtracting the same amount from every score keeps the order — the first widget's task 4.
  • The same hits, but in a completely different order. The order could change only if the range gave different hits different scores; it gives all of them 1.0.
  • Every score becomes 0. Only the clause in filter stops scoring; the match in must still scores.

A bool query contains only should clauses. Which statements are true? Select all that apply.

  • A document must match at least one of them to be returned. "If should is the only clause included, at least one of the conditions must be satisfied" (p. 1653).
  • Every document of the index is returned; the clauses only reorder them. Alone, should is an OR: a document that matches none of the clauses is not returned. Reordering without removing is what should does next to a must or a filter — among the documents those clauses let in.
  • A document that matches two clauses scores more than one that matches only one, other things equal. The scores of the matching should clauses add up.
  • Every hit has score 0. should runs in query context: it is scored. Score 0 comes from filter and must_not.

Alone, should is an OR that scores; beside must or filter, it is a bonus.

The text field description of a dish holds "Salmon fillet with butter and herbs". What does { "term": { "description": "Salmon" } } return?

  • The dish, with a high score. A term is not analysed: it looks for "Salmon" with a capital S, and the index holds only "salmon".
  • An error: term is not allowed on text fields. Elasticsearch runs it without complaint. "DO NOT use" is advice, and the reason is the silent empty answer.
  • The dish, with score 0. Score 0 is what a filter gives. Here the dish is not found at all.
  • No hit at all. The analyzer stored the lower-case word salmon; match would have lower-cased the query too and found the dish (Fig. 1).

The response of p. 607 reads "total" : { "value" : 10000, "relation" : "gte" }. What do you know about the number of matching documents?

  • Exactly 10000 matched. An exact count would say "relation" : "eq".
  • At most 10000 could be found. Elasticsearch finds every match; it only stops counting them exactly.
  • At least 10000 matched; the exact number was not counted. "gte" means "greater than or equal": the count is a lower bound.
  • The query failed after 10000 documents. Nothing failed: the hits are there, best first.

You send "size": 0 and a terms aggregation, with no size inside it, on a keyword field with 25 distinct values. What comes back?

  • No hits; 10 buckets, the most frequent values first; the documents of the other 15 values counted in sum_other_doc_count. The top-level size drops the hits; the bucket count is the size of terms, 10 by default.
  • No hits and no buckets, because the size is 0. The top-level size counts hits, not buckets.
  • 25 buckets, one per value. Only with "size": 25 or more inside terms.
  • 10 hits and 25 buckets. "size": 0 means no hits, and the buckets stop at 10.

Which requests does Elasticsearch refuse with an error? Select all that apply.

  • A match whose object names two fields, SCORE and BORO. "[match] query doesn't support multiple fields", status 400 (p. 600).
  • A term query for "Male" on the text field Gender. It runs and silently returns nothing: no error, no hit.
  • A terms aggregation on a text field such as description. Text fields keep no single value per document: "term aggregations only work on keywords" (p. 1658).
  • size and aggs written inside query. Inside query Elasticsearch expects a query type; size is not one (p. 1681).

The dangerous slip is the one without an error: a term on a text field returns an empty list that looks like a real answer.

A bool query has a filter clause and a should clause, and no must. Which dishes come back?

  • Those matching both the filter and the should clause. With a filter present, should is optional, exactly as with a must.
  • Those matching the filter or the should clause. The filter is required: a dish that fails it is out.
  • All the dishes that match the filter; those that also match the should clause come first. The filter decides membership with score 0, and the should clause provides the only score.
  • Only the dishes that match the should clause, scored by the filter. A filter never scores.

Key take-aways

  • A search is GET /index/_search with a JSON body whose query is one leaf clause — match, term, range, prefix — or a bool that combines them; _count returns only the number, and one match looks at one field.
  • match analyses its text with the field's analyzer: words joined by OR (or by AND with "operator": "and") on a text field, the whole value on a keyword field. term never analyses and does not belong on text fields; range takes gt, gte, lt, lte and date math such as now-10d/d.
  • Query context asks how well a document matches and computes a score; filter context asks only whether it matches, scores 0 and can be cached. filter and must_not run in filter context.
  • must is a required, scored AND; filter a required AND without score; must_not a NOT without score; should a bonus, and an OR only when it stands alone. Scores add up — 2.487945 = 1.0 + 1.4879451 on p. 606 — and boost multiplies a clause's share.
  • "size": 0 and a named terms aggregation are GROUP BY with counts: the 10 biggest buckets come back, the rest only in sum_other_doc_count; a query filters first, sub-aggregations run inside each bucket, and a text field must be counted through field.keyword.
  • The exam exercise is a mapping written for the queries that follow, then sentences translated clause by clause: "includes the words" → must, "removing" → must_not, "must not affect the final score" → filter, "prioritising" → should, "the count for each" → terms.

  • Boolean query Elastic documentation

    The four clauses in the vendor's words, the rule for minimum_should_match (1 when should is alone, 0 beside must or filter) and the remark that filter clauses return a score of 0 — section 3 in reference form.

    The top-10 default and its size, sum_other_doc_count, the count error across shards, and the rule that a text field cannot be aggregated by default. Read it next to the second widget.
