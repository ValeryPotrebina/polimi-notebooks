Spark SQL, Catalyst and the columnar file formats

After this lesson you will follow a DataFrame query through Catalyst's four phases, say which bytes of a Parquet file it reads and why, and explain where Spark SQL's speed comes from.

In the paper behind the chart of p. 1287, two Spark programs compute the same thing: the average of one column for every value of another, over a billion pairs of numbers, on the same five worker machines. Both are written in Python. One hands its work to map and reduceByKey as lambdas; the other is a single line, df.groupBy("a").avg("b"). On the chart the lambdas need about 180 seconds and the one-liner about 15: twelve times less.

Same language, same data, same cluster. What does Spark know about the one-liner that it cannot know about the lambdas? By the end of the lesson you will have three answers, and one of them is not in Spark at all but in the file on disk.

Spark SQL is about more than SQL

The title slide says it in five words: Spark SQL "is about more than SQL" (p. 1262). Page 1263 gives the reasons. Big-data work must "perform ETL to and from various (semi- or unstructured) data sources" and "perform advanced analytics (e.g. machine learning, graph processing) that are hard to express in relational systems". The answer: "a DataFrame API that can perform relational operations on both external data sources and Spark's built-in RDDs", plus "a highly extensible optimizer, Catalyst".

Page 1264 turns this into three promises of declarative big-data processing: write less code, read less data, let the optimizer do the hard work. You state what you want; Spark decides how. This lesson follows the data: your code, the optimizer, the file.

Write less code: one average, four dialects

On p. 1265 the Hadoop mapper writes every value under the key 1: it averages the whole file, the Spark lines per key.

Page 1265 computes an average in about thirty lines of Hadoop Java and five of Spark; p. 1266 writes the average age per name in four dialects: RDDs, SQL, Pig and the DataFrame. Take people(name, age): Ann 30, Bob 20, Ann 40, Cid 10. (The slides' sqlCtx is today's session object spark.)

from pyspark.sql import functions as F
# one row per name: Ann 35.0, Bob 20.0, Cid 10.0
spark.table("people").groupBy("name").agg(F.avg("age")).show()

Using DataFrames: sqlCtx.table("people") \ .groupBy("name") \ .agg("name", avg("age")) \ .collect()

Pass only the aggregate: .groupBy("name").agg(F.avg("age")). The grouping column comes back by itself.

agg takes column expressions, not a column name in front of them: on PySpark 4.2 the slide's line stops with AssertionError: all exprs should be Column, while the corrected one returns name and avg(age). The exam may quote the printed line: recognise it, and write the corrected form in a SparkQL answer.

The RDD version of p. 1266 carries the average's ingredients by hand:

# the same averages with RDDs: carry (sum, count) pairs yourself
(sc.textFile("people.tsv")
   .map(lambda line: line.split("\t"))
   .map(lambda x: (x[0], [int(x[1]), 1]))
   .reduceByKey(lambda x, y: [x[0] + y[0], x[1] + y[1]])
   .map(lambda x: [x[0], x[1][0] / x[1][1]])
   .collect())
Averages do not merge: the average of 10 and 20 is 15, of 15 and 60 it is 37.5, but of 10, 20 and 60 it is 30.

Why [int(x[1]), 1]? reduceByKey combines partial results in any order, on any machine, like the combiner of lesson 30. Averages cannot be combined; (sum, count) pairs can, and the last map divides:

\[ \begin{aligned} &(s_1, c_1) \oplus (s_2, c_2) \\ &\quad = (s_1 + s_2,\ c_1 + c_2) \end{aligned} \]

The DataFrame just says avg, and Spark supplies this machinery. (The slide's sc.textFile(...).split("\t") would fail: an RDD has no split, so each line is split inside a map.)

One engine, two front ends

Spark SQL is "part of the core distribution since Spark 1.0" and "runs SQL / HiveQL queries, optionally alongside or replacing existing Hive deployments" (p. 1270). Page 1272 shows where it sits.

The slide presents Spark SQL as "Originally called Shark" with three limitations (p. 1271): it "can only be used to query external data in Hive catalog → limited data sources", "can only be invoked via SQL string from Spark → error prone", and its "Hive optimizer tailored for MapReduce → difficult to extend". Read backwards, they are Spark SQL's design: any source and native RDDs, a DataFrame API, a new optimizer.

"Spark SQL can only query Hive tables." That was Shark's limitation. Strictly, Shark was the predecessor project, Hive running on Spark, stopped in July 2014 in favour of Spark SQL (background).

What a program has that an SQL string has not

Page 1273 lists the "Advantages over Relational Query Languages": "Holistic optimization across functions composed in different languages", "Control structures (e.g. if, for)" and "Logical plan analyzed eagerly → identify code errors associated with data schema issues on the fly". Execution is lazy, analysis is eager: on a table sales(region, amount) the line sales.select("col") fails at once, before any data is read, with ... `col` cannot be resolved. Did you mean one of the following? [`amount`, `region`] (Spark 4.2, executed).

Spark SQL also queries your own objects (p. 1274): it can "infer column names and types directly from data objects (via reflection in Java and Scala and data sampling in Python, which is dynamically typed)", reads them "in-place", and lets you "combine RDDs with external structured data", with "hot columns cached in memory".

Inside a full programming language a user-defined function (UDF) needs no packaging: Spark SQL "allows inline registration of UDFs", whereas Pig "requires the UDF to be written in a Java package", and a registered UDF is "available to other interfaces" (p. 1275) — the slide registers a trained model as predict and calls SELECT predict(age, weight) FROM users. Page 1269 adds composition: add_demographics takes a DataFrame and returns one. Runnable, with the caller of p. 1281:

from pyspark.sql import functions as F
from pyspark.sql.types import StringType

zipToCity = F.udf(lambda z: "Melbourne" if z.startswith("3")
                            else "Other", StringType())

def add_demographics(events):
    u = spark.table("users")
    return (events.join(u, events.user_id == u.user_id)
                  .withColumn("city", zipToCity(u.zip)))

# the timestamps of the events of users living in Melbourne
events = add_demographics(spark.read.parquet("/data/events"))
training_data = (events.where(events.city == "Melbourne")
                       .select(events.timestamp)
                       .collect())

events \ .join(u, events.user_id == u.user_id) \ .withColumn("city", zipToCity(df.zip)) — "Takes and returns a DataFrame"

Take the zip code from the users table, zipToCity(u.zip), and return the chain.

df is defined nowhere, so Python stops with a NameError; and a function without return gives back None, not the DataFrame the brace promises. Page 1281 repeats the lines, and the exam may quote them as printed: know both versions.

Spark SQL is one structured API and one optimizer behind both SQL strings and DataFrame code, executed as RDD operations.

Let the optimizer do the hard work: Catalyst

A lambda is a black box: Spark can call it but cannot look inside. A DataFrame query is kept as a tree of node objects. The expression x + (1 + 2) is Add(Attribute(x), Add(Literal(1), Literal(2))), and a rule is a function that finds a pattern in the tree and replaces it (p. 1276):

tree.transform {
  case Add(Literal(c1), Literal(c2)) => Literal(c1+c2)
}

Rules (p. 1277) are "pattern matching functions that transform subtrees into specific structures", and partial functions: they "skip over subtrees that do not match → no need to modify existing rules when adding new types of operators" — which is why Catalyst is extensible. One transform may hold several patterns; rules come in batches and "may take multiple batches to reach a fixed point", where no rule changes the tree any more (one rewrite can enable the next); and "transform can contain arbitrary Scala code".

Four phases, from query to RDDs

Page 1278 is the map of the optimizer, and its caption is the fact to remember: "DataFrames and SQL share the same optimization/execution pipeline".

Unresolved attribute — an attribute whose "type is not known or it's not matched to an input table" (p. 1279).

Spark prints a quote ' in front of every name it has not resolved yet.

Analysis (p. 1279) turns the unresolved logical plan into a logical plan. For SELECT col FROM sales it must "look up relations by name from the catalog", "map named attributes to the input provided given operator's children", give a "UID for references to the same value" and "propagate and coerce types through expressions (e.g. 1 + col)". Spark lets you watch: for SELECT amount + 1 FROM sales the parsed plan holds 'amount and 'UnresolvedRelation [sales], the analysed plan amount#32 + cast(1 as double) — a column with a unique id, and a literal cast to its type.

Logical optimization (p. 1280) "applies standard rule-based optimization (constant folding, predicate-pushdown, projection pruning, null propagation, boolean expression simplification, etc)", all in "800LOC". Predicate pushdown moves a filter as close to the data as possible; projection pruning keeps only the columns used further up. Page 1282 spells out one such rule: "Find filters on top of projections", "Check that the filter can be evaluated without the result of the project", "If so, switch the operators".

Spark 4.2 goes further: its optimised plan drops the inner projection and turns the filter into isnotnull(id) AND (id = 1) (executed).

Page 1281 runs the slide's example through three plans (the widget replays them): the caller's where sits on top of the join written inside add_demographics, and Catalyst moves it down anyway — the "holistic optimization across functions" of p. 1273.

Catalyst at work: four plans of one query

The query of p. 1281 ("after the join, on users.city") with one change: users stores the city itself, so no UDF is needed (with the slide's Python UDF, Spark moves the filter below the join but cannot push it into the scan). Both tables are Parquet files: events(user_id, timestamp, kind) and users(user_id, zip, city). Choose how the filter is written, then step from the unresolved plan to the physical plan. The plans are simplified from what Spark 4.2 prints for this query. Illustrative sizes for the row readout: 1,000,000 events, 10,000 users; the 400 users in Melbourne have 40,000 events; 250,000 events are clicks.

  1. Keep "after the join" and step to the analysed plan. Before you press Next again: where will the Filter end up, and how many rows will the join produce?
    What you should see

    Below the join, directly above the users relation (with a new Project above it that keeps only user_id): city is a users column, so Catalyst tests it before joining. The join now builds 40,000 rows instead of 1,000,000. This is the insight of the widget: the optimizer moves the filter towards the data, whatever order you wrote it in.

  2. Switch to "before the join" and compare its optimised and physical plans with those of "after the join".
    What you should see

    They are identical, node for node. The two queries still differ in the unresolved and analysed plans; from the optimised plan on, Catalyst has made them the same. Write the filter wherever it reads best.

  3. Choose "after the join, on events.kind" and step to the physical plan. Which side receives the filter, and how many columns of users are read?
    What you should see

    The events side: kind is an events column. The users scan reads only user_id, 1 of 3 columns, because nothing above the join needs zip or city. Projection pruning works per table and per query.

  4. In the physical plan the filter has been pushed into the Parquet scan, yet a Filter node is still drawn above the scan. Why both?
    What you should see

    The scan uses the pushed filter to skip whole row groups whose statistics rule it out (next section); the rows of the row groups it does read are then checked one by one. Pushed filters are a help to the source, not a promise.

Physical planning turns the optimised plan into one or more physical plans of real operators, and a cost model selects one (p. 1278). In the Spark SQL paper it chose only the join algorithm — a broadcast join for a small table, as in the widget (background). The scans belong to data sources: "Spark's Data Source API allows optimizations like column pruning and filter pushdown into custom data sources" (p. 1268) — p. 1280's projection pruning and predicate pushdown. A source implements buildScan(requiredColumns: Array[String], filters: Array[Filter]): RDD[Row] (p. 1267): its two parameters are the two pushdowns. And since "DataFrame execution is done with Spark RDDs", custom code can drop to them: queryResult.rdd.mapPartitions { … }.

Code generation (p. 1283) "relies on Scala's quasiquotes": Catalyst "transforms a SQL tree into an abstract syntax tree (AST) for Scala code". The slide's generator is one pattern match:

def compile(node: Node): AST = node match {
  case Literal(value) => q"$value"
  case Attribute(name) => q"row.get($name)"
  case Add(left, right) =>
    q"${compile(left)} + ${compile(right)}"
}

Each q"…" is a code template. The tree of Fig. 2 becomes the line row.get("x") + 3, compiled once instead of walked for every row: for x+x+x a billion times, about 36 s interpreted against about 9 s generated, close to hand-written code (read off the chart), from a generator of "700LOC".

You say what; Catalyst decides how — it rewrites a tree with rules, chooses operators by cost and compiles the result.

Files that know their own shape: Avro and Parquet

Catalyst hands a scan requiredColumns and filters; what the scan does with them depends on the file. Page 1242 lists the "Available File Formats": text and CSV, JSON, SequenceFile ("binary key/value pair format"), Avro, Parquet, ORC ("optimized row columnar format") and "Data Frames". Three families hide in it: text (readable, slow to parse, no schema), binary rows (SequenceFile, Avro) and binary columns (Parquet, ORC).

Available File Formats: "-Avro -Parquet -Data Frames -ORC"

A DataFrame is not a file format but Spark's in-memory table, "a distributed collection of rows organized into named columns" (p. 1246), which files are read into and written from.

No file on disk is "a DataFrame": df.write.parquet(path) writes Parquet. A closed question may be matched against the printed list, so know both: the slide lists it, the concept says no.

Avro: rows, with the schema inside

Avro (p. 1243) is a "language neutral data serialization system": "write a file in python and read it in C". The schema is "language independent", "usually written in JSON", the data "encoded in binary format". It "supports schema evolution" — "producers and consumers at different versions of schema" — and "supports compression and are splittable". The tweets schema of p. 1244, repaired:

{
  "type": "record",
  "name": "tweets",
  "doc": "schema for storing tweets",
  "fields": [
    { "name": "username",  "type": "string" },
    { "name": "tweet",     "type": "string" },
    { "name": "timestamp", "type": "long" }
  ]
}

"name" : "username", "type" : "string", }, { … and "doc:" : “schema for storing tweets"

No comma before a closing brace, straight quotes only, and the attribute is "doc" — the schema above.

JSON forbids a trailing comma, so a parser rejects the printed schema at its first field (checked with Python's json); "doc:" would be another, unknown attribute. The exam may show the schema as printed: take its structure from the slide, its punctuation from here.

An Avro file (p. 1244) is a header — metadata holding the JSON schema, and a sync marker — then blocks: auxiliary data (record count and size), the serialized objects, and the same marker. That marker makes the file splittable: a task that starts mid-file, at an HDFS split, skips to the next marker and is aligned on a block. The schema is written once, so records carry no field names.

Parquet: columns inside row groups

"Apache Parquet is a columnar storage format available to any project in the Hadoop/Spark ecosystem, regardless of the choice of data processing framework, data model or programming language" (p. 1250). Page 1254 draws the difference on a table X, Y, Z: a row format stores x1 y1 z1 x2 y2 z2 …, a columnar format stores x1 … x5, then y1 … y5, then z1 … z5, each column as one "encoded chunk" — the column store of lesson 20, as a file.

The units nest (pp. 1245, 1251). A row group is "a group of rows in columnar format": the "max size buffered in memory while writing", "one (or more) per split while reading", "roughly: 50MB < row group < 1 GB". A column chunk is "the data for one column in a row group" and "can be read independently". A page is the "unit of access in a column chunk", "big enough for compression to be efficient", "roughly: 8KB < page < 1MB". The footer (p. 1252) "contains column chunks offset and schema": per column chunk its type, encodings, codec, number of values, offsets and sizes. It comes last, so the writer can stream row groups out and append the index at the end; a reader reads it first and jumps to the chunks it needs.

Mind the word block: p. 1245 calls a row group a block; p. 1260 means the HDFS block of lesson 31. No row group straddles two HDFS blocks — the slide packs two into one and pads the rest — so a task reads its row group from one machine.

"Columnar means the whole file is one column after another." Not in Parquet: the file is a sequence of row groups, and only inside a row group are the columns contiguous, so every record can be rebuilt from one row group.

Avro writes whole records one after another with the schema in its header; Parquet writes each column of a row group together and indexes the file in its footer.

Read less data: inside a Parquet file

Page 1257 lists three ways to "Read Less Data". Columnar organization: "Encoding: make the data smaller" and "Column projection: read only the columns you need". Row group filtering: "Use footer stats to eliminate row groups" and "Use dictionary pages to eliminate row groups". Page filtering: "Use page stats to eliminate pages". Page 1255 calls the first moves projection push down (read only the requested columns) and predicate push down (use statistics, such as each chunk's minimum and maximum, to skip what cannot match): together you "read only the data you need". The layout also "minimizes CPU cache misses": a column's values lie side by side, so the processor fetches only useful ones.

The dictionary of a column chunk (p. 1261) "is a compact list of all the values": "Search term missing? Skip the row group" — "like a bloom filter without false positives". Minimum and maximum rule a value out only when it lies outside their range; inside it they say "maybe". A dictionary answers exactly.

One file written twice: what a query reads

Twelve tweets with the schema of p. 1244, in time order. Above, an Avro file: four records per block, each closed by a sync marker (violet). Below, a Parquet file: three row groups of four rows, each made of three column chunks; the narrow violet cell is the dictionary page of the username chunk. Sizes in the picture: a username 8 bytes, a tweet 120, a timestamp 8 — 1,632 bytes in all. Headers, markers, dictionaries and the footer are left out of the counts.

  1. Keep the first query with row-group filtering off. Predict the share of the 1,632 bytes that Avro reads and the share that Parquet reads. Then switch on the footer statistics.
    What you should see

    Avro reads 100 %: to find the timestamps it must read every record whole. Parquet reads 192 bytes (11.8 %), the username and timestamp chunks of every row group; the big tweet column is never touched. With statistics, 64 bytes (3.9 %): row group 1 ends at 09:14 and row group 3 starts at 09:47, so neither is opened. The two savings multiply: 11.8 % of the bytes of each row group, times 1 of 3 row groups, is 3.9 %. That is the insight of the widget: Parquet skips whole column chunks and whole row groups, Avro can skip neither.

  2. Choose "text of the tweets by eva" with the footer statistics on. Predict which row groups min/max can skip. Then add the dictionary pages.
    What you should see

    None: in every row group the usernames run from ada to ugo or to eva, and eva lies inside each range, so min/max can only answer "maybe" — 1,536 bytes. The dictionaries are exact: row groups 1 and 3 contain only ada, bob and ugo, so both are skipped and 512 bytes remain. "Like a bloom filter without false positives" (p. 1261).

  3. Choose "every field of every tweet". Compare the two files.
    What you should see

    Both read all 1,632 bytes: with no filter and every column needed, the columnar layout saves nothing, and Parquet must even stitch each record back together from three chunks. A row format suits writing and reading whole records; a columnar format suits analytics over a few columns.

Encodings: make the data smaller

Before any compressor runs, Parquet encodes each column with a trick that fits its content (pp. 1256, 1258; the examples are ours).

Of the "heavyweight algorithms (gzip, lzo, snappy)" of p. 1258 only gzip is really heavy: Snappy and LZO trade compression for speed (background).

Dictionary encoding is "useful for columns with few ( < 50,000 ) distinct values" and "when applicable, compresses better and faster than heavyweight algorithms". Bit packing stores small integers "in the minimum bits required": a value whose maximum is \(m\) needs \(\lceil \log_2(m+1) \rceil\) bits, so 16 bits cover any key below 65,536. Parquet 2.0 (p. 1259) adds "more encodings: compact storage without heavyweight compression" (delta encodings "for integers, strings and sorted dictionaries"), "statistics: to be used by query planners and predicate pushdown" and a "new page format: to facilitate skipping ahead at a more granular level".

"Dictionary encoding always pays." Only for few distinct values: beyond 1 MB of dictionary (parquet.dictionary.page.size, p. 1245) the writer falls back to plain encoding, and the chunk has no complete dictionary left to skip with.

Nested records in flat columns

Parquet's "key strength is to store nested data in truly columnar format using definition and repetition levels" (p. 1254). The technique comes from Google's Dremel; p. 1253 applies it to a schema with an optional group and two repeated fields.

Next to each stored value Parquet writes two small integers. The definition level D says how many of the optional or repeated fields on the value's path are actually present; the repetition level R says at which repeated field the value continues a list, 0 meaning that a new record starts. The slide's record, shredded step by step:

  1. Read the columns off the schema, one per leaf: DocId, Links.Backward, Links.Forward. The groups Document and Links store nothing themselves.

  2. Count, on each path, the fields that may be missing:

    \[ D_{\max} = \#\ \text{optional or repeated fields} \]

    DocId is required: 0. Links is optional and Backward repeated: 2; Forward too. A value must say how deep its path is defined.

  3. Count only the repeated fields:

    \[ R_{\max} = \#\ \text{repeated fields} \]

    0 for DocId, 1 for each list: with one repeated field on the path, R is 0 or 1.

  4. Shred DocId: 20: a required value at the start of a record gives (20, R 0, D 0).

  5. Shred Backward: 10, 30. The first value starts the record's list (R 0) with Links and Backward present (D 2): (10, 0, 2). The second continues the list at Backward, the first repeated field: (30, 1, 2).

  6. Shred Forward: 80, the record's first Forward: (80, 0, 2). These are the four rows of p. 1253; with maxima 1 and 2, bit packing stores R in 1 bit and D in 2.

  7. Not on the slide, same rules: a record without Links stores NULL in both Links columns with R 0, D 0 — the path stops before Links. R = 0 tells the assembler a new record begins, so it rebuilds the record exactly.

Parquet skips at three levels — column chunks, row groups, pages — and turns nesting into two tiny integers per value.

Beyond queries: extensions, JSON, pipelines, speed

Two "Extensions" complete the design (p. 1284). A new data source "must implement a createRelation function that takes a set of key-value params and returns a BaseRelation object" — "E.g. CSV, Avro, Parquet, JDBC". A user-defined type (UDT) maps "user-defined types to structures composed of Catalyst's built-in types": PointUDT stores a Point as a struct of two doubles, x and y, with serialize and deserialize. Catalyst never needs to understand a Point, only the struct.

Schema inference for JSON

JSON carries no schema, yet Spark SQL "automatically infers schema from a set of records, in one pass or sample" (p. 1285). Each record yields "a tree of STRUCT types"; each field gets "the most appropriate type … based on all data observed in that column"; the per-record schemas are merged "in one reduce operation" — possible because merging schemas is associative, like the (sum, count) pairs. The slide's three tweets:

An integer in one record and a fraction in another make FLOAT, the most specific type holding both; loc is missing from record 3, so it gets no NOT NULL. Spark 4.2 reads the same records as struct<lat: double, long: double>, every field nullable (executed): the slide's reasoning, newer type names. "Same trick for Python typing" is the data sampling of p. 1274, and all of it is the schema-on-read of lesson 4.

ML pipelines speak DataFrame

Page 1286, repeated on p. 1288, chains three stages of Spark's machine-learning library, MLlib (quotes straightened):

from pyspark.ml import Pipeline
from pyspark.ml.feature import Tokenizer, HashingTF
from pyspark.ml.classification import LogisticRegression

tokenizer = Tokenizer(inputCol="text", outputCol="words")
hashingTF = HashingTF(inputCol="words", outputCol="features")
lr = LogisticRegression(maxIter=10, regParam=0.01)
pipeline = Pipeline(stages=[tokenizer, hashingTF, lr])
# df: a "text" and a "label" column; returns a PipelineModel
model = pipeline.fit(df)

tokenizer and hashingTF only transform; lr is an estimator, whose fit on ds2 produces the transformer lr.model. That is why lr sits outside the dotted "Pipeline Model" box and lr.model inside (executed). If you have used scikit-learn pipelines, fit and transform mean the same here.

The twelve times, explained

Page 1287 measures the promises (Fig. 8).

Back to the opening puzzle. Lambdas are black boxes that Spark can only call, row by row, in a Python process; the one-liner is a tree it can read, and that gives three answers. Catalyst can rewrite it. Only the plan is built in Python and the work runs as JVM bytecode: the paper credits this for the 12×, and code generation, which "avoids expensive allocation of key-value pairs", for the 2× over Scala. And the plan names its columns and filters, so the data source can be asked for less: with Parquet, only the needed column chunks and row groups leave the disk — the answer in the file. The right chart adds that one DataFrame job beats an SQL query plus a separate Spark job by about 2×: nothing is saved to HDFS in between (paper).

The DataFrame wins because Spark sees the whole plan: it can rewrite it, compile it and ask the file for less.

Exam-style questions

Catalyst, the design of Spark SQL and the file formats are theory: open, multiple-choice and true-or-false questions in 10–15 minutes, where wrong answers may carry a penalty. The practical part's SparkQL exercise wants PySpark DataFrame code ("you are not allowed to use SQL syntax", paper of 30 January 2026); the last question is one in the wording of the past papers, and lesson 39 solves the papers' own.

Describe the phases of query optimization in Spark SQL's Catalyst, from a query written as SQL or with the DataFrame API to the RDDs that execute it. Which phase uses a cost model, and for what?

Show model answer

An SQL string (parsed into an AST) and a DataFrame both produce an unresolved logical plan: the same pipeline serves both. Analysis resolves it with the catalog — it looks up relations by name, maps named attributes to the inputs of each operator, gives each attribute a unique id and propagates and coerces types — and yields a logical plan. Logical optimization applies rule-based rewrites such as constant folding, predicate pushdown, projection pruning, null propagation and boolean expression simplification, producing an optimized logical plan. Physical planning generates one or more physical plans made of Spark operators, and a cost model selects one (for example the join algorithm: a broadcast join for a small table). Code generation finally compiles the selected plan, using Scala quasiquotes, into code that runs as RDD operations. Only physical planning is cost-based; the other phases apply rules.

A complete answer gives the four phases in order, what goes in and comes out of each, the catalog in analysis and the cost model only in physical planning. Name a few rules of logical optimization too: they are the easiest part to leave out.

What is an unresolved attribute in Spark SQL? Using the query SELECT col FROM sales, explain what the analyzer does, and what happens when sales has no column col.

Show model answer

An attribute is unresolved if its type is not known or it is not matched to an input table. After parsing, col is only a name and sales an unresolved relation. The analyzer looks up sales by name in the catalog, matches col to one of its columns, gives it a unique id so that every reference to the same value is recognised, and propagates and coerces types through expressions (in 1 + col the literal is cast to the type of col). If sales has no column col, analysis fails at once with an error, before any data is read: the logical plan is analyzed eagerly, even though the query is executed lazily.

The core is the definition in the slide's words and the catalog lookup. "Eager analysis, lazy execution" shows that you understand why the error comes early.

  • Generating Java bytecode with quasiquotes That is the last phase, code generation (p. 1283), not logical optimization.
Show model answer

Constant folding, predicate pushdown, projection pruning and null propagation (with boolean expression simplification, the list of p. 1280). The join algorithm is chosen in physical planning by the cost model; bytecode is produced by code generation.

The distractors are real Catalyst work, done in another phase. Wrong answers may carry a penalty, so the phase of each optimization is what to know for sure.

True or false: because DataFrames are evaluated lazily, a reference to a column that does not exist is reported only when an action such as show() or collect() runs.

  • True Execution is lazy, but the logical plan is analyzed eagerly (p. 1273): a wrong column name fails when the line is written.
  • False "Logical plan analyzed eagerly → identify code errors associated with data schema issues on the fly" (p. 1273).
Show model answer

False. Spark SQL analyzes the logical plan eagerly: column names and types are checked against the catalog as soon as the DataFrame operation is defined, while the data is processed only when an action runs.

The trap is to stretch "lazy" from execution to analysis. Analysis needs only metadata, so it is cheap to do at once.

Describe the internal structure of a Parquet file and explain how it lets a query that needs two columns and a filter read less data than a row-oriented format such as Avro.

Show model answer

A Parquet file is a sequence of row groups followed by a footer, with the magic number PAR1 at both ends. A row group holds a set of rows in columnar format (parquet.block.size, 128 MB by default) and never straddles two HDFS blocks; inside it each column is stored contiguously as a column chunk, and each column chunk is divided into pages, the unit of access, encoding and compression (1 MB by default). The footer stores the schema and, for every row group and column chunk, its offset, size, encodings, codec and statistics such as min and max. A reader reads the footer first. With projection pushdown it reads only the column chunks of the two requested columns. With predicate pushdown it uses the footer statistics and the dictionary pages to skip row groups that cannot contain matching rows, and page statistics to skip pages. Avro stores whole records one after another, so the same query must read every byte of every record.

A complete answer has the hierarchy (row group, column chunk, page), the footer's content and both kinds of pushdown, each tied to the structure that makes it possible.

Consider the Parquet schema message Document { required int64 DocId; optional group Links { repeated int64 Backward; repeated int64 Forward; } }.

(a) Give the maximum repetition and definition levels of each column. (b) Shred the record DocId: 10, Links { Forward: 20, Forward: 40, Forward: 60 }, which has no Backward value, into (value, R, D) triples.

Show model answer

(a) DocId: max R 0, max D 0 (required, nothing optional or repeated on its path). Links.Backward and Links.Forward: max R 1 (one repeated field on the path), max D 2 (Links is optional, the field itself repeated).

(b) DocId: (10, 0, 0). Links.Backward: (NULL, 0, 1) — Links is present but Backward is not, so one of the two fields of the path is defined; R 0 because the value belongs to a new record. Links.Forward: (20, 0, 2), (40, 1, 2), (60, 1, 2) — the first value starts the record's list, the next two repeat at level 1, and both Links and Forward are defined.

The slide's record (p. 1253) has a Backward list; this one does not, and the NULL with D = 1 is the point of the exercise. Max D counts optional and repeated fields, max R only repeated ones.

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("SMBUD").getOrCreate()
# users and events: DataFrames with the columns of the two tables

# (a) average age per city
users.groupBy("City").agg(F.avg("Age").alias("Avg_Age")).show()

# (b) timestamps of the clicks of users living in Melbourne
(events.join(users, "User_ID")
       .filter((F.col("City") == "Melbourne")
               & (F.col("Kind") == "click"))
       .select("Timestamp")
       .show())

# (c) events per city, only cities above 2 (the HAVING)
(events.join(users, "User_ID")
       .groupBy("City")
       .agg(F.count("Event_ID").alias("N_Events"))
       .filter(F.col("N_Events") > 2)
       .show())

Check yourself

You move .where(users.city == "Melbourne") from after the join to before it. What happens to the optimised plan?

  • Nothing: it is the same plan Catalyst pushes the filter below the join either way; the widget showed identical optimised and physical plans.
  • It gets faster, because the filter now runs first It runs first in both cases: predicate pushdown already moved it there.
  • It gets slower, because the join loses rows it needs The filter removes only rows that the query would drop anyway; the result is the same.
  • It fails, because users has no timestamp The timestamp comes from events; filtering users first is perfectly valid.

A Parquet file has 10 equally large columns in 8 row groups. A query needs 2 columns, and the footer statistics prove that only 2 row groups can hold matching rows. Roughly what share of the file is read?

  • 5 % The two skips multiply: 2/10 of the columns times 2/8 of the row groups is 1/20.
  • 20 % That counts only the column projection and forgets the skipped row groups.
  • 25 % That counts only the row groups and forgets that 8 of the 10 columns are not read.
  • 45 % The two savings do not add up; they multiply.

Why can Spark not move the filter of rdd.map(f).filter(g) below the map, as Catalyst does with a DataFrame?

  • f and g are opaque functions: Spark cannot see which fields they read or write Pushdown needs to know that the filter does not depend on what the map computes; a lambda does not tell.
  • Because RDDs are immutable DataFrames are immutable too, and Catalyst rewrites their plans all the time.
  • Because RDD operations are evaluated eagerly RDD transformations are lazy as well; laziness is not the obstacle.
  • Because Catalyst works only on Scala code Catalyst optimizes Python DataFrame code too; only the plan is built in Python.

Which statements about the footer of a Parquet file are true?

  • It is written after all the row groups The writer streams the row groups out and appends the footer last, in one pass.
  • It holds the schema and, for each column chunk, its offset and statistics "A footer contains column chunks offset and schema" (p. 1252); the statistics are the "footer stats" of p. 1257.
  • A reader reads it before any column chunk It needs the offsets to jump to the chunks, and the statistics to skip row groups.
  • It keeps a copy of the first row group for quick previews The footer holds metadata only, no data.
  • It sits at the end because HDFS cannot read files from the start HDFS reads from any offset; the reason is single-pass writing.

Same schema as p. 1253. A record has DocId: 7 and no Links at all. What does the column Links.Backward store for it?

  • NULL with R = 0 and D = 0 Nothing on the path is defined, so D = 0; the value belongs to a new record, so R = 0.
  • Nothing at all Then a reader could not tell where one record ends in this column: every record leaves a trace in every column.
  • NULL with R = 0 and D = 1 D = 1 would mean that Links is present and only Backward is missing.
  • NULL with R = 1 and D = 2 D = 2 means a real Backward value, and R = 1 a continued list: neither is the case.

A column chunk of city has the dictionary {Como, Lecco, Milano}; its statistics are min Como, max Milano. Which filter lets the reader skip the row group thanks to the dictionary, although min/max alone would not?

  • city == "Lodi" Lodi lies between Como and Milano, so min/max says "maybe"; the dictionary says it is not there.
  • city == "Monza" Monza comes after Milano: min/max alone already skips the row group.
  • city == "Lecco" Lecco is in the dictionary: the row group must be read.
  • city > "Bari" Every value of the chunk is after Bari: nothing can be skipped.

In the MLlib pipeline of p. 1286, which objects end up inside the fitted PipelineModel?

  • tokenizer A transformer: it is used as it is.
  • hashingTF A transformer too.
  • lr.model The transformer that lr.fit produced on ds2.
  • lr The estimator is used once, by fit; that is why the slide draws it outside the dotted box.
  • ds0 The input data is not a stage of the model.

Key take-aways

  • Spark SQL "is about more than SQL": one DataFrame API and one optimizer, Catalyst, behind SQL strings and DataFrame code alike, executed on RDDs; it removed Shark's limits (Hive catalog only, SQL strings only, a MapReduce-era optimizer).
  • Declarative code is shorter and checkable: agg(F.avg("age")) instead of hand-carried (sum, count) pairs, and eager analysis reports a wrong column before any data moves.
  • Catalyst rewrites trees with pattern-matching rules to a fixed point, in four phases: analysis with the catalog, rule-based logical optimization, physical planning with a cost model, code generation with quasiquotes.
  • Predicate pushdown and projection pruning move filters towards the data and drop unused columns, down into a data source's buildScan(requiredColumns, filters).
  • Avro stores whole records with the JSON schema in the header and sync markers for splitting; Parquet stores column chunks inside row groups, indexes them in the footer, and reads only the columns, row groups and pages a query needs.
  • Encodings (delta, prefix, dictionary, RLE, bit packing) shrink columns, and definition and repetition levels store nested data as flat columns.
  • Extensions, JSON schema inference by one reduce and MLlib pipelines all build on the DataFrame; on p. 1287 a DataFrame aggregation runs about 12 times faster than Python RDD code.
