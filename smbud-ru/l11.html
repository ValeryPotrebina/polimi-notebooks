Cypher: узлы, связи, паттерны и пути

После этого урока ты будешь записывать шаблон Cypher как рисунок, создавать, находить и удалять с его помощью, считать пути и людей, не путая одно с другим, и сможешь сказать, какой алгоритм Neo4j запускает для кратчайшего пути — и когда он может его упустить.

Johan хочет научиться сёрфингу. На слайдах занятия ты спрашиваешь у Neo4j, кто из друзей его друзей занимается сёрфингом, и считаешь их двумя способами. COUNT(surfer) отвечает 3. COUNT(DISTINCT surfer) отвечает 1. В графе ровно один сёрфер, Allison, и оба числа верны.

Позже на том же занятии два запроса кратчайшего пути отличаются двумя словами, WITH p. Один подписан "Always returns a result, if exists", другой — "Not guaranteed to return a result, even if it exists" (p. 1373). Держи обе загадки в голове. Обе решаются, если читать шаблон буквально: Neo4j ищет каждое место, куда твой рисунок ложится на граф, а то, что ты прицепишь к рисунку, решает, как именно он ищет.

Cypher — это ASCII-арт

Занятие открывается определением, которое годится для ответа на экзамене: Neo4j "is a graph database management system implemented in Java. It is A.C.I.D. compliant. It has its own query language, named Cypher" (p. 1332). Cypher "focuses on the clarity of expressing what to retrieve from a graph, not on how to retrieve it" (p. 1383): он декларативный (declarative), как SQL. Самому графу свойств посвящён урок 10; здесь ты учишься его записывать.

Слайд, который знакомит с Cypher, — это рисунок: кружок "You", стрелка ARE_LEARNING, кружок "Cypher". Cypher набирает этот рисунок на клавиатуре: круглые скобки для узла, квадратные скобки внутри стрелки для связи (рис. 1).

Шаблон узла (node pattern) содержит переменную, ноль или больше меток после двоеточий и свойства в фигурных скобках (p. 1336); каждая часть необязательна. Переменная — это имя, которое живёт внутри одного запроса; метка — ярлык типа, и у узла их может быть несколько; карта свойств — это набор условий равенства в MATCH и значений для записи в CREATE.

Шаблон связи (relationship pattern) состоит из тех же трёх частей, но у связи ровно один тип. Двоеточие — вся разница между именем и фильтром: [relatedTo] — переменная, которая совпадает со связью любого типа, [:ACTED_IN] — фильтр по типу без имени, а [r:ACTED_IN] — и то и другое. Слайды сами однажды теряют это двоеточие (p. 1365); разбор этой ошибки — в уроке 12.

Нет двоеточия — нет фильтра: [ACTED_IN] — это переменная, которая совпадает с любой связью; [:ACTED_IN] совпадает только с ACTED_IN.

[k:KNOWS {since:2007}] Relationship “KNOWS” with a parameter “since”

since — это свойство (property) связи, а KNOWS — её тип (type) (слово "labeled" в первой строке слайда значит то же самое). Метки бывают у узлов; у связи ровно один тип.

В Cypher параметр — это заполнитель с $, который подставляется во время выполнения, как $autostring_0 в плане со слайда (p. 1349). Экзамен могут сверять с напечатанной формулировкой: узнавай "parameter", когда вопрос цитирует слайд, но сам пиши property и type — экзамен 11 Feb 2025 требует "the proper notation for labels, types, etc.".

Наконечник стрелки — тоже фильтр. -[:MANAGES]-> и <-[:MANAGES]- фиксируют направление, и одну и ту же связь можно записать с любого конца: (a:Employee)<-[:MANAGES]-(b:Manager) — это "a is managed by b" (p. 1344). Убери наконечник, -[:KNOWS]-, и связь может смотреть в любую сторону. Соедини их в цепочку — и получишь шаблон пути (path pattern): (p)-[:KNOWS]-(friend)-[:KNOWS]-(foaf) — это "Friend-of-a-friend relationship" со слайда; в SQL — таблица Knows, соединённая сама с собой.

(n:Person)-[:KNOWS]- (m:Person) Path defining that n and m know each other

У шаблона нет наконечника, поэтому он совпадает со связью KNOWS в любом направлении: n знает m или m знает n. Обоих направлений он не требует. Взаимное знакомство — это (n)-[:KNOWS]->(m)-[:KNOWS]->(n).

Проверь на одной стрелке: если в графе только Ann→Bob, MATCH (n)-[:KNOWS]-(m) вернёт две строки, (Ann, Bob) и (Bob, Ann), хотя Bob не знает Ann. Экзамен могут сверять с напечатанной формулировкой: узнавай её и знай, с чем шаблон совпадает на самом деле.

Пишем граф: CREATE, MERGE, SET, DELETE

CREATE "allows the creation of nodes and relationships" (p. 1334); слайд подписывает части "Variable : Node Label", "Node Properties", "Node - Identified by the parenthesis".

// creates 1 node with the label Person and 3 properties
CREATE (ee:Person { name: "Emil", from: "Sweden", klout: 99 })

Один CREATE может записать несколько узлов через запятую, а свойство может хранить список (p. 1335):

// creates 3 Person nodes; Francis's "from" is a list
CREATE (ee:Person { name: "Emil", from: "Sweden", klout: 99 }),
  (a:Person { name: "Richard", from: "UK", klout: 80 }),
  (j:Person { name: "Francis", from: ["Sweden","UK"], klout: 75 })

Тот же слайд создаёт узел с двумя метками и узел без меток и возвращает то, что только что создал. Строки ограничиваются и двойными, и одинарными кавычками; список хранит значения одного типа, а вложенную карту свойство хранить не может.

// 2 nodes: one :Person:Fisherman, one with no label
CREATE (ee:Person:Fisherman), (a)
// returns 1 row: "Andy"
CREATE (a {name: 'Andy'}) RETURN a.name

Связи сначала нужны оба её конечных узла. Слайд (p. 1339) создаёт Mark и Mike, находит их и рисует стрелку:

// creates 2 Person nodes, Mark and Mike
CREATE (e:Person {name: "Mark"}), (a:Person {name: "Mike"})
// returns 1 row: "KNOWS"
MATCH
  (a:Person),
  (b:Person)
WHERE a.name = 'Mike' AND b.name = 'Mark'
CREATE (a)-[r:KNOWS]->(b)
RETURN type(r)

Neo4j добавляет два правила, о которых слайд молчит: в CREATE связи нужно направление ("Only directed relationships are supported in CREATE") и ровно один тип ("Exactly one relationship type must be specified for CREATE"). В MATCH и то и другое можно опустить.

Теперь выполни тот же MATCH со вторым CREATE (p. 1340):

// returns "KNOWS"; Mike now has two KNOWS and one BEFRIEND to Mark
MATCH
  (a:Person),
  (b:Person)
WHERE a.name = 'Mike' AND b.name = 'Mark'
CREATE (a)-[r:KNOWS {since: 2015}]->(b), (a)-[h:BEFRIEND]->(b)
RETURN type(r)

Слайд настаивает: "N.B. The two KNOWS relationships we created are different even though they have the same name". CREATE никогда не смотрит, прежде чем писать. Предложение «создай, если нет» — это MERGE, которое лекция 06 показывает "ID-based" (p. 270): MERGE (player:Player {id: row.playerUri}) находит игрока с этим id или создаёт его, а часть ON CREATE SET выполняется только при создании.

// creates a KNOWS from Mike to Mark only if none exists;
// a second run finds it and writes nothing
MATCH (a:Person {name: 'Mike'}), (b:Person {name: 'Mark'})
MERGE (a)-[:KNOWS]->(b)

«MERGE проверяет ключ». Нет: он сопоставляет весь шаблон. Если у Mark нет возраста, MERGE (p:Person {name: 'Mark', age: 30}) создаст второго Mark. Делай MERGE по идентифицирующему свойству, а остальное — через SET.

SET меняет то, что уже есть: SET p.age = 30 записывает свойство, SET p:Manager добавляет метку (так на слайде (p. 1367) помечают актёров), REMOVE p:Manager её снимает.

// 1 row: Emil, now :Person:Fisherman with klout 100
MATCH (ee:Person {name: "Emil"})
SET ee:Fisherman, ee.klout = 100
RETURN labels(ee), ee.klout

Удаление начинается с MATCH: ты удаляешь то, на что указывает переменная. Слайд (p. 1342) удаляет связи KNOWS у Ben, оставляя дальний конец анонимным, (); слайд 7 занятия E02 (O–Z) удаляет самого Ben.

// deletes Ben's outgoing KNOWS relationships, not the nodes
MATCH (n {name: 'Ben'})-[r:KNOWS]->() DELETE r
// deletes the node Ben, but only if no relationship touches him
MATCH (n:Person {name: 'Ben'}) DELETE n

Если Ben всё ещё кого-то знает, второй запрос падает, и ничего не меняется: "Cannot delete node<…>, because it still has relationships." Граф никогда не хранит стрелку без конца. DETACH "removes all the relationships before removing the nodes" (p. 1343):

// deletes every node with all its relationships: an empty graph
MATCH (n) DETACH DELETE n

Читаем граф: база фильмов

Читающие предложения идут в фиксированном порядке (p. 1338):

// 1 row: the node Emil
MATCH (ee:Person) WHERE ee.name = "Emil" RETURN ee;

Слайд говорит: "the MATCH clause returns all the nodes that match the conditions". Уточним: MATCH находит все способы, которыми шаблон ложится на граф, и делает по строке на каждый способ, WHERE оставляет строки, где условие истинно, RETURN выбирает столбцы. «Одна строка на способ» — ключ к загадке.

Дальше упражнения переходят на граф фильмов Neo4j (p. 1353) — тот, что загружает в Neo4j Browser команда :play movies. Слайд перечисляет "Actors", "Directors" и "Films – title, release, tagline"; в данных же каждый человек — :Person, каждый фильм — :Movie, игра в фильме и режиссура — это связи, а не метки, а год называется released.

Запросы к узлам (pp. 1354–1355) показывают два способа фильтрации. Карта свойств — это проверка на равенство, метка сужает поиск, LIMIT ограничивает число строк:

// 1 row: Tom Hanks (no label: every node is checked)
MATCH (tom {name: "Tom Hanks"}) RETURN tom
// 1 row: the film Cloud Atlas
MATCH (cloudAtlas {title: "Cloud Atlas"}) RETURN cloudAtlas
// 10 rows: the names of 10 people
MATCH (people:Person) RETURN people.name LIMIT 10
На скриншотах Browser рисует стрелки и «больше или равно» слитными глифами; набираешь ты ->, <- и >=.

Всё, кроме равенства, требует WHERE:

// 20 rows: the films released from 1990 to 1999
MATCH (nineties:Movie)
WHERE nineties.released >= 1990 AND nineties.released < 2000
RETURN nineties.title
// 1 row: 106
MATCH (person:Person)
WHERE person.born < 1970
RETURN COUNT(person.name)

«Значит, 133 − 106 = 27 человек родились в 1970 году или позже». Нет, 22: у пяти человек нет born, поэтому person.born < 1970 для них null, а WHERE оставляет только строки, где условие true.

Запросы с шаблонами заставляют работать связи (pp. 1356–1359). Читай каждый вслух: «Tom Hanks, играл в, какой-то фильм».

// 12 rows: Tom Hanks and one of his films per row
MATCH (tom:Person {name: "Tom Hanks"})-[:ACTED_IN]->(tomHanksMovies)
RETURN tom,tomHanksMovies

На картинке слайда видна ещё стрелка DIRECTED к That Thing You Do: Browser рисует все связи между узлами на экране (Tom Hanks этот фильм ещё и снял), но двенадцать строк содержат только совпадения ACTED_IN.

// 3 rows: Tom Tykwer, Lilly Wachowski, Lana Wachowski
MATCH (cloudAtlas {title: "Cloud Atlas"})<-[:DIRECTED]-(directors)
RETURN directors.name

"Inverse Relationship" со слайда (p. 1357) — та же стрелка, прочитанная со стороны фильма: (directors)-[:DIRECTED]->(cloudAtlas …) даёт те же имена. Две стрелки, сходящиеся в одном узле, находят партнёров по съёмкам (p. 1358):

// 39 rows but 34 different people: Meg Ryan comes back 3 times
MATCH (tom:Person {name:"Tom Hanks"})-[:ACTED_IN]->(m)
      <-[:ACTED_IN]-(coActors)
RETURN coActors.name

Общий фильм (m) делает работу join'а. Tom Hanks никогда не оказывается собственным партнёром: внутри одного шаблона каждая связь используется не больше одного раза, а его ACTED_IN к m уже занята левой ветвью. Meg Ryan появляется трижды: три общих фильма — три строки. Напоследок — связь с переменной и без типа (p. 1359):

// 10 rows: 4 ACTED_IN, 3 DIRECTED, WROTE, PRODUCED, REVIEWED
MATCH (people:Person)-[relatedTo]-(:Movie {title: "Cloud Atlas"})
RETURN people.name, Type(relatedTo), relatedTo

type() возвращает имя типа (имена функций нечувствительны к регистру, поэтому Type тоже работает); у фильма "No variable name", потому что из него ничего не возвращают. Попробуй каждый значок этих четырёх рисунков:

Шаблон — это рисунок

Девять узлов настоящего графа фильмов и все десять связей между ними. Каждая стрелка из верхнего ряда — ACTED_IN. Выбери один из четырёх запросов со слайдов, а потом меняй по одному значку его рисунка; каждая строка, которую находит шаблон, рисуется оранжевым и перечисляется под картинкой.

  1. Выбери запрос со слайда (p. 1356). Пока ничего не трогаешь: сколько будет строк, если развернуть каждую стрелку? А если наконечников нет вовсе?
    Что ты должен увидеть

    Развёрнутые: 0 строк — ни одна ACTED_IN не идёт от фильма к Tom Hanks. Без наконечников: 3 строки, столько же, сколько со стрелкой слайда, потому что все его связи ACTED_IN и так направлены от него. Наконечник работает как фильтр только тогда, когда в данных есть стрелки в обе стороны.

  2. Выбери запрос со слайда (p. 1357) и поставь тип связи «нет». Предскажи, кто присоединится к Tom Tykwer. Потом верни тип «как на слайде» и сними галочку с карты свойств: переменная по-прежнему называется cloudAtlas — какими узлами она может быть теперь?
    Что ты должен увидеть

    Без типа — 4 строки: Tom Tykwer (DIRECTED), David Mitchell (WROTE), Tom Hanks и Halle Berry (ACTED_IN) — это "any relationship" со слайда (p. 1359). С возвращённым типом и без карты — 3 строки: дважды Nora Ephron и Tom Tykwer, по всем трём фильмам. Имя переменной ничего не фильтрует; cloudAtlas привязывается к любому фильму.

  3. Выбери запрос со слайда (p. 1358). Предскажи число строк и число разных партнёров по съёмкам на этом срезе. Потом поставь тип «нет».
    Что ты должен увидеть

    3 строки, 2 человека: Meg Ryan дважды (два общих фильма) и Halle Berry; Tom Hanks не появляется никогда. С любым типом — 7 строк и 5 человек: добавляются Nora Ephron (дважды), Tom Tykwer и David Mitchell, потому что ветви теперь принимают DIRECTED и WROTE. Каждый значок, который ты убираешь, позволяет лечь на граф большей его части.

Строки — это пути: DISTINCT, COUNT и план

Вернёмся к загадке. Первый набор данных занятия — граф из руководства Neo4j для начинающих (getting-started guide; слайды показывают только запросы): Emil, Johan, Ian, Rik и Allison, соединённые семью связями KNOWS. "Let's find all of Emil's friends" (p. 1345):

// 2 rows: Emil with Johan, Emil with Ian
MATCH (ee:Person)-[:KNOWS]-(friends)
WHERE ee.name = "Emil" RETURN ee, friends

Потом "a new friend that can teach surf to Johan" (p. 1346): друг друга, с анонимным средним узлом (), потому что его имя никому не нужно.

// 1 row: Allison
MATCH (js:Person)-[:KNOWS]-()-[:KNOWS]-(surfer)
WHERE js.name = "Johan" AND surfer.hobby = "surfing"
RETURN DISTINCT surfer

"What would happen if we remove the DISTINCT clause from the query?" (p. 1347). С RETURN COUNT(surfer) ответ 3, с RETURN COUNT(DISTINCT surfer) — 1. От Johan к Allison ведут три разных пути из двух связей KNOWS: через Ian по стрелке Johan→Ian, через Ian по стрелке Ian→Johan (это вторая связь, и шаблон без наконечника её принимает) и через Rik. MATCH делает по строке на путь; COUNT(x) считает строки, где x не null, COUNT(DISTINCT x) — разные значения. Два числа — два вопроса: сколько способов и сколько людей.

Строка — это один способ, которым рисунок ложится на граф: COUNT(x) считает пути, COUNT(DISTINCT x) считает вещи.

Одно правило делает подсчёт конечным: внутри одного шаблона каждая связь используется не больше одного раза на строку, а узлы могут повторяться — это уникальность связей (relationship uniqueness). Johan может оказаться другом собственного друга — к Ian по одной стрелке и обратно по другой, — но никогда по одной и той же стрелке дважды.

Пути или люди?

Граф из руководства для начинающих; все семь стрелок — KNOWS. Запрос — со слайда (p. 1346), с тем RETURN, который ты выберешь. «Следующий путь» показывает пути по одному — так, как MATCH выдаёт строки; маленькое число у узла считает строки, которые на нём заканчиваются.

  1. С RETURN COUNT(surfer) предскажи значение счётчика после последнего пути. Потом пройди по шагам и смотри, какую стрелку между Johan и Ian использует каждый путь.
    Что ты должен увидеть

    3. Первый и третий пути оба идут через Ian к Allison, один по Johan→Ian, другой по Ian→Johan; второй идёт через Rik. Три строки, и все заканчиваются на Allison.

  2. Переключись на RETURN DISTINCT surfer, потом на COUNT(DISTINCT surfer). Сколько строк остаётся?
    Что ты должен увидеть

    Одна строка, Allison, и счёт 1. Пути разные; их последний узел один и тот же, а DISTINCT оставляет каждое значение один раз.

  3. Сними галочку с условия на хобби. Предскажи: окажется ли Johan другом собственного друга и сколько теперь путей?
    Что ты должен увидеть

    8 путей и 4 человека: Allison 3 раза, Emil и Johan дважды, Ian один раз. Johan возвращается по другой стрелке к Ian, никогда — по той, по которой ушёл: в счётчиках по этапам 12 прогулок из двух шагов сокращаются до 8, потому что 4 из них повторно используют свою первую связь.

На экзамене "the number of different X" значит count(DISTINCT x): два официанта по имени Federico за одним столом дают два пути к каждому блюду, заказанному за этим столом.

Как Neo4j превращает шаблон в строки? PROFILE "executes the query and provides a detailed execution plan" (p. 1348). Рис. 4 перерисовывает план со слайда (p. 1349): каждый блок — это оператор (operator), а числа между блоками — строки, которые текут от одного к следующему.

С ограничением уникальности на :Person(name) первые два блока превращаются в один index seek: индекс служит "only for access to initial node of the query" (p. 272).

Фильтр not anon_0 = anon_2 — это уникальность связей, записанная явно, а литерал "Johan" превратился в параметр $autostring_0 ("Use parameters instead of literals", p. 282). "Estimated rows" — догадка по статистике; "rows" и "db hits" измерены. EXPLAIN показывает то же дерево, не выполняя запрос, — только оценки: "Use PROFILE / EXPLAIN to analyze the performance of your queries" (p. 282).

Пути переменной длины и кратчайшие пути

Звёздочка внутри скобок повторяет связь. "Movies and actors up to 4 "hops" away from "Kevin Bacon"" (p. 1360):

// 135 rows: the nodes 1 to 4 relationships away
// (297 paths before DISTINCT)
MATCH (bacon:Person {name:"Kevin Bacon"})-[*1..4]-(hollywood)
RETURN DISTINCT hollywood

Слайд даёт правила: "Distance computed w.r.t. relationships", "Any node" и "Distinct clause, as many paths may lead to the same node". "Movies and actors" — это ещё скромно сказано: у (hollywood) нет метки, а у скобок нет типа, поэтому приходят и режиссёры, сценаристы, продюсеры и рецензенты — и сам Kevin Bacon, по циклу из четырёх разных связей через Apollo 13, Ron Howard и Frost/Nixon.

Значения по умолчанию важны: [*] значит одну или больше связей, никогда не ноль; [*0..] совпадает ещё и с путём нулевой длины, у которого оба конца — один узел; тип пишется перед звёздочкой, [:FRIEND*1..3]. И правило, которое надо запомнить: "Always set an upper limit for your variable length patterns. It's easy to have a query touch all nodes in a graph by mistake" (p. 282).

()-[]+->() One or more relationships (same as [*1..]) · ()-[]*->() Zero or more relationships (same as [*0..]) · ()-[]?-() Optional relationship (zero or one)

В Neo4j 5.9 и новее квантификатор ставится после всего шаблона связи, включая наконечник: ()-[]->+(), ()-[]->*() или {0,1} для «ноль или один»; ? не существует. Ещё надёжнее — первые строки того же слайда: [*1..], [*0..], [*0..1].

Neo4j 5.26 отвергает три напечатанные формы ("Invalid input '+': expected '-'"), а исправленные совпадают ровно с тем же, с чем [*1..], [*0..] и [*0..1]; лекция 06 использует только форму со звёздочкой в скобках (p. 278). Экзамен могут сверять с напечатанной таблицей: узнавай её строки в вопросе, но никогда не пиши эту форму.

Browser подчёркивает рискованные запросы жёлтым: "WARNINGS may arise … some operators may be deprecated or the query is performing a lot of operations e.g., cartesian products among the nodes or unbound number of relationships" (p. 1390). Предупреждение — не ошибка; запрос выполняется. MATCH (a:Person), (b:Person) со слайда (p. 1339) — это два шаблона без связи между ними: его строки — все пары людей, декартово произведение, и только WHERE сужает их до Mike и Mark (Neo4j сначала фильтрует каждую сторону, так что там произведение 1 × 1 и безвредно). Неограниченный [*] может обойти весь граф.

Кратчайший путь между двумя людьми — встроенная функция (p. 1361):

// 1 row: one path of length 4
// (six paths tie; Neo4j returns one of them)
MATCH p = shortestPath(
(bacon:Person {name:"Kevin Bacon"})-[*]-
(meg:Person {name:"Meg Ryan"})
)
RETURN p

p = … привязывает весь путь к переменной; RETURN p даёт "start node, end node and path". shortestPath возвращает один кратчайший путь, и если несколько путей равны по длине, выбрать, какой именно, нельзя; allShortestPaths возвращает их все, и лекция 06 пишет обе функции с границей, [*..6] (p. 280):

// 6 rows: every shortest path, all of length 4
MATCH p = allShortestPaths(
(bacon:Person {name:"Kevin Bacon"})-[*..6]-
(meg:Person {name:"Meg Ryan"})
)
RETURN p

Слайд (p. 1362) сначала привязывает обоих людей и разрешает один тип связи:

// as printed on p. 1362: no rows on the movie graph
MATCH (KevinB:Person {name: 'Kevin Bacon'} ),
      (Al:Person {name: 'Al Pacino'}),
      p = shortestPath((KevinB)-[:ACTED_IN*]-(Al))
WHERE all(r IN relationships(p) WHERE r.role IS NOT NULL)
RETURN p
Подпись на слайде (p. 1363) говорит "relationship() function"; функция называется relationships(p), во множественном числе, как и написано в коде на том же слайде.

Слайд (p. 1363) разбирает WHERE по частям: relationships(p) "returns a list containing all the relationships in a path", IN проводит по нему r, а all() "returns TRUE if the predicate holds for all elements in the given list". Родственники: nodes(p), length(p) (число связей), any(), none().

WHERE all(r IN relationships(p) WHERE r.role IS NOT NULL)

В графе фильмов свойство ACTED_IN называется roles, и это список — сам слайд (p. 1353) печатает "ACTED_IN – roles". С r.roles IS NOT NULL запрос возвращает путь длины 6, от Kevin Bacon через три фильма и двух актёров к Al Pacino (таких путей два, они равны по длине; Neo4j возвращает один).

Отсутствующее свойство читается как null, поэтому r.role IS NOT NULL ложно для каждой связи, и напечатанный запрос не возвращает ни одной строки; Neo4j даже предупреждает: "The provided property key is not in the database". Та же строка напечатана на слайдах (pp. 1363, 1371, 1373, 1389 и 1390). Мысль слайда остаётся верной, а экзамен могут сверять с напечатанной строкой: знай оба варианта.

Как Neo4j планирует кратчайший путь

Слайды (pp. 1368–1373) спрашивают, как ищется кратчайший путь, и следуют руководству Neo4j: "Depending on the predicates to be evaluated, Neo4j plans the shortest path in different ways."

  • "By default, Neo4j uses a Fast Bidirectional Breadth-first Search Algorithm if the conditions can be evaluated whilst searching for the path" — "e.g., all nodes must have the Person label", "e.g., no nodes should have a name property".
  • "If the predicates need to inspect the whole path before deciding on whether it is valid or not, Neo4j may have to resort to using a Slower Exhaustive Depth-first Search Algorithm" — "e.g., at least one node contains the property name = "Kevin Bacon"".
  • "When the Exhaustive Search is planned, it is still only executed when the Fast Algorithm fails to find any matching paths."

Зачем два алгоритма? Поиск в ширину (breadth-first search) наращивает по одному кольцу соседей за раз — здесь с обоих концов, пока два поиска не встретятся, — поэтому первый путь, который он достраивает, и есть кратчайший. Условие на каждый узел или связь проверяется в тот момент, когда элемент достигнут: узел Movie не проходит "all nodes must have the Person label", и всё, что за ним, — "Excluded a priori" (p. 1369). Условие на хотя бы один узел так проверить нельзя: ветвь через Movie ещё может дойти до Kevin Bacon, поэтому она "Cannot be excluded a priori" (p. 1370). Судить можно только целые пути, перебирая их в глубину (depth-first): одну ветвь до конца, потом следующую.

Слайды (pp. 1371–1373) сравнивают три запроса (вкладки ниже). WHERE length(p) > 1 нужен весь путь, поэтому план включает исчерпывающий запасной вариант (fallback): если путь, найденный быстрым поиском, не проходит предикат, исчерпывающий поиск возвращает кратчайший из тех, что проходят, — "Predicates used in the WHERE clause that apply to the shortest path pattern are evaluated before choosing the shortest matching path" (p. 1371). Вставь между ними WITH p — и предикат покидает шаблон: "the query plan will not include the fallback to the Slower Exhaustive Search Algorithm" (p. 1372). Быстрый поиск возвращает свой единственный путь; если это прямая связь длины 1, WHERE её выбрасывает, и не остаётся ничего.

Предикат внутри MATCH с кратчайшим путём управляет поиском; после WITH p он лишь фильтрует один уже найденный путь.

// fast search; "Always returns a result, if exists"
MATCH (KevinB:Person {name: 'Kevin Bacon'} ),
      (Al:Person {name: 'Al Pacino'}),
      p = shortestPath((KevinB)-[:ACTED_IN*]-(Al))
WHERE all(r IN relationships(p) WHERE r.role IS NOT NULL)
RETURN p

Условие на каждую связь: проверяется во время поиска, fallback не нужен (p. 1373; в графе фильмов пиши roles).

// exhaustive fallback planned; "Always returns a result, if exists"
MATCH (KevinB:Person {name: 'Kevin Bacon'}),
      (Al:Person {name: 'Al Pacino'}),
      p = shortestPath((KevinB)-[*]-(Al))
WHERE length(p) > 1
RETURN p

"Must check that the whole path follows the predicate before validity is evaluated" (p. 1372). Neo4j об этом сообщает: "Exhaustive shortest path has been planned for your query".

// fast search only;
// "Not guaranteed to return a result, even if it exists"
MATCH (KevinB:Person {name: 'Kevin Bacon'}),
      (Al:Person {name: 'Al Pacino'}),
      p = shortestPath((KevinB)-[*]-(Al))
WITH p
WHERE length(p) > 1
RETURN p

Сначала без всякого условия выбирается кратчайший путь; WHERE потом фильтрует этот один путь.

На графе фильмов эти три запроса не различить (первый — если читать role как roles): Kevin Bacon и Al Pacino не связаны напрямую, поэтому любой путь между ними длиннее 1, и каждый запрос возвращает путь длины 6. Вся суть — в гарантии, и показывает её игрушечный граф с прямой связью. Вторая загадка решена: два слова вынесли предикат из шаблона.

Быстро, исчерпывающе или ничего

Игрушечный граф, не данные фильмов: Kevin напрямую подписан на Al (FOLLOWS), оба играли в Movie A, а более длинная цепочка идёт через Ann и Bob. Свойство roles есть только у связей ACTED_IN. Запрос — MATCH (k:Person {name: 'Kevin'}), (al:Person {name: 'Al'}), p = shortestPath((k)-[*]-(al)), а за ним WHERE, который ты выберешь. Пройди поиск по шагам; числа показывают порядок, в котором узлы достигаются впервые.

  1. Выбери «без WHERE», потом WHERE length(p) > 1. Предскажи, какой путь вернёт каждый, потом пройди оба по шагам.
    Что ты должен увидеть

    Без WHERE: Kevin–Al, длина 1, найден на первом шаге. С length(p) > 1 быстрый поиск находит тот же Kevin–Al, предикат его отвергает, и запланированный исчерпывающий поиск идёт в глубину: Kevin–Al не проходит, Kevin–Ann–Bob–Al (длина 3) проходит, Kevin–Movie A–Al (длина 2) проходит и короче. Возвращается путь длины 2.

  2. Теперь выбери WITH p WHERE length(p) > 1. Предскажи результат, прежде чем идти по шагам.
    Что ты должен увидеть

    Ни одной строки. Ничему в шаблоне не нужен был весь путь, поэтому fallback не планировался; быстрый поиск передаёт свой единственный путь, Kevin–Al, в WITH, и WHERE его выбрасывает. Последнее показание говорит, что подходящий путь длины 2 всё равно существует: WITH вынес условие из поиска.

  3. Сравни r.roles IS NOT NULL с r.role IS NOT NULL со слайда. Какие связи становятся красными и когда?
    Что ты должен увидеть

    С roles каждая связь FOLLOWS отсекается в тот момент, когда поиск до неё доходит (три из четырёх; до Ann–Bob поиск так и не доходит), и один только быстрый поиск возвращает Kevin–Movie A–Al. С role отсекается каждая связь, до которой доходит поиск, оба поиска застревают, и запрос не возвращает ничего — ровно то, что запрос со слайда (p. 1362) делает на графе фильмов.

  4. Последняя пара: «все узлы — Person» против «хотя бы один узел — Movie». Какой из них планирует fallback?
    Что ты должен увидеть

    «Все узлы — Person» отсекает Movie A на первом шаге и возвращает Kevin–Al одним быстрым поиском: это универсальное условие. «Хотя бы один узел — Movie» не может судить о Kevin–Al, пока путь не достроен; путь не проходит, и исчерпывающий поиск возвращает Kevin–Movie A–Al: это экзистенциальное условие, как "at least one node … Kevin Bacon" на слайде.

Вопросы в стиле экзамена

Четыре упражнения в формулировках прошлых экзаменов, каждое — на ER-сценарии настоящей работы с уже данной графовой моделью (проектирование модели — урок 12), и два теоретических вопроса. Решения экзаменов не публикуются: эти образцы ответов — наши, и каждый запрос был выполнен на маленьком тестовом графе в Neo4j 5.26.

Scenario (the restaurant ER of the exam of 6 Sep 2024): Person (Personal_ID, Name, Surname, …) with the child entity Waiter (Hiring Date); Table (Table_ID, Table Number, Max Seats); Dish (Dish_ID, Name, Price, Recipe, Description). A waiter serves tables (Serve); dishes are ordered at tables (Order). Assume this graph model:

(:Person:Waiter {personal_id: String, name: String, …})
  -[:SERVE]->(:Table {table_id: String, max_seats: Integer, …})
(:Table)-[:ORDER]->(:Dish {dish_id: String, name: String, …})

Write a Cypher query to count the total number of different dishes ordered at tables whose max seats is greater than 10, considering only tables served by at least one waiter whose name is "Federico".

Показать образец ответа 
MATCH (w:Waiter {name: "Federico"})-[:SERVE]->(t:Table)
      -[:ORDER]->(d:Dish)
WHERE t.max_seats > 10
RETURN count(DISTINCT d) AS differentDishes

Адаптировано из упражнения 2 той работы, которое спрашивает "for each table" и поэтому требует группировки (урок 12). Что в ответе должно быть верно: один шаблон для цепочки официант → стол → блюдо, равенство внутри узла, диапазон в WHERE и DISTINCT. Тестовый граф: два Federico обслуживают стол 1 (12 мест; паста и рыба), один из них ещё и стол 2 (16 мест; рыба и салат). Шаблон даёт 6 строк для 3 разных блюд; count(d) ответил бы 6.

Scenario (the natural-disasters ER of the exam of 6 Jun 2024): Natural Disaster (ID, Start Time, Start Date, End Time, End Date, Disaster Description) with the total, exclusive children Earthquake (Magnitude, Mercalli Scale), Flooding (Water Height), Landslide (Landslide Class) and Tornado (EF Scale); the recursive relationship Cause ("A Natural Disaster may cause another Natural Disaster") with the attribute Causal Description. Assume each disaster is one node carrying both labels, and Cause is a relationship from the causing disaster to the caused one:

(:NaturalDisaster:Earthquake {id: String, magnitude: Float, …})
(:NaturalDisaster)-[:CAUSE {causal_description: String}]
  ->(:NaturalDisaster)

Write a Cypher query to return the earthquakes with a magnitude greater than 8 that caused at least one flooding with the causal description equal to "very strong earthquake", which in turn caused at least one landslide.

Показать образец ответа 
MATCH (e:Earthquake)-[c:CAUSE]->(f:Flooding)
      -[:CAUSE]->(:Landslide)
WHERE e.magnitude > 8
  AND c.causal_description = "very strong earthquake"
RETURN DISTINCT e

Адаптировано из упражнения 3 той работы, где это запрос MongoDB ("which in turn caused two landslides" требует подсчёта: урок 12). Первой связи нужна переменная, потому что условие стоит на её свойстве; оползень остаётся анонимным, потому что из него ничего не возвращают. DISTINCT — потому что наводнение, вызвавшее два оползня, возвращает своё землетрясение дважды; ровно это и сделал тестовый граф без него.

Scenario: the same natural-disasters ER and graph model as the previous question.

Write a Cypher query to return the ID and the description of every natural disaster caused, directly or through a chain of at most three Cause relationships, by the natural disaster with ID "ND-01".

Показать образец ответа 
MATCH (d:NaturalDisaster {id: "ND-01"})
      -[:CAUSE*1..3]->(x:NaturalDisaster)
RETURN DISTINCT x.id, x.disaster_description

Здесь важны три вещи: ограниченный шаблон переменной длины с типом перед звёздочкой, стрелка и DISTINCT. На тестовой цепочке ND-01 → ND-02 → ND-03 → ND-04 → ND-05, плюс ND-01 → ND-06 и ND-07 → ND-01, ответ — ND-02, ND-03, ND-04 и ND-06. Убери наконечник — и проскочит ND-07, бедствие, которое вызвало ND-01; убери границу — и проскочит ND-05, до которого четыре шага. DISTINCT ничего не стоит и защищает тебя, как только две цепочки могут дойти до одного и того же бедствия.

Scenario (the hospital-heating ER of the exam of 30 Jan 2026): Building (Building_ID, Name, Year), Floor (Floor_ID, Number, Has_Elevator), Heating System (Heater_Sys_ID, Heating_Power) with the (T, E) children HVAC System and Gas Heating System; Has Floor (Building – Floor) and Heats (Heating System – Floor, with Start_Time and End_Time). Assume this graph model:

(:Building {building_id: String, name: String, year: Integer})
  -[:HAS_FLOOR]->(:Floor {floor_id: String, number: Integer,
                          has_elevator: Boolean})
(:HeatingSystem:GasHeatingSystem {heater_sys_id: String, …})
  -[:HEATS {start_time: DateTime, end_time: DateTime}]->(:Floor)

Write a Cypher query that returns the buildings built after 1967 with at least one floor with an elevator that is heated by a Gas Heating System. Return the ID and the name of each building once.

Показать образец ответа 
MATCH (b:Building)-[:HAS_FLOOR]->(f:Floor)
      <-[:HEATS]-(:GasHeatingSystem)

Адаптировано из упражнения 1 той работы (её запрос суммирует кровати, а это требует группировки). Шаблон — та же «галочка» (V) партнёров по съёмкам со слайда (p. 1358), только посередине этаж, а дочерняя метка :GasHeatingSystem сама по себе выбирает газовые системы. Без DISTINCT тестовое здание вернулось трижды: две газовые системы отапливают один его этаж и одна — другой.

On the dataset of the exercise session, this query returns 3:

MATCH (js:Person)-[:KNOWS]-()-[:KNOWS]-(surfer)
WHERE js.name = "Johan" AND surfer.hobby = "surfing"
RETURN COUNT(surfer)

The same query with RETURN COUNT(DISTINCT surfer) returns 1. Explain why, and say which number answers "how many people can teach Johan to surf".

Показать образец ответа

MATCH produces one row for every way the pattern fits the graph, that is one row per path. The only surfer, Allison, is reached from Johan by three different paths of two KNOWS relationships: through Ian over the relationship Johan→Ian, through Ian over the relationship Ian→Johan (the pattern has no direction, and these are two different relationships), and through Rik. Within one path a relationship is never used twice, but different paths may end at the same node. COUNT(surfer) counts the rows, so 3; COUNT(DISTINCT surfer) counts the different nodes, so 1. The number of people is 1. The PROFILE plan shows it: 3 rows enter the Distinct operator and 1 leaves it.

Полный ответ опирается на две идеи: строки — это пути, а не узлы, и две связи KNOWS между Johan и Ian считаются разными путями. Если назвать три пути, расплывчатый ответ становится точным; числа PROFILE его подкрепляют.

True or false: in Neo4j, inserting WITH p between MATCH …, p = shortestPath((a)-[*]-(b)) and WHERE length(p) > 1 never changes the result of the query.

  • True Без WITH предикат принадлежит шаблону кратчайшего пути, и исчерпывающий fallback планируется; с WITH это обычный фильтр, применённый к одному уже выбранному пути.
  • False Если кратчайший путь имеет длину 1, а более длинный существует, запрос без WITH вернёт более длинный путь, а запрос с WITH не вернёт ничего.
Показать образец ответа

False. Without WITH, the predicate is evaluated as part of the shortest-path pattern; because it needs the whole path, Neo4j plans the slower exhaustive depth-first search as a fallback, so the query returns the shortest path of length greater than 1 whenever one exists. With WITH p, the fast bidirectional breadth-first search returns one shortest path with no predicate; if its length is 1, the WHERE removes it and the query returns no rows, even though a valid path exists.

Неверный ответ может стоить баллов, так что отмечай только то, что можешь обосновать. Запомнить стоит слова слайда: "Always returns a result, if exists" против "Not guaranteed to return a result, even if it exists" (p. 1373).

Проверь себя

Ann знает Bob, а Bob знает Ann: две связи KNOWS. Сколько строк вернёт MATCH (x:Person)-[:KNOWS]-(y:Person) RETURN x.name, y.name?

  • 1 Никакого объекта «пара» нет: строки — это способы, которыми ложится шаблон, а обе связи ложатся в обоих направлениях.
  • 2 Столько было бы с наконечником, -[:KNOWS]->: каждая связь читается в своём собственном направлении.
  • 4 Без наконечника каждая связь совпадает дважды: один раз с Ann в роли x и один раз с Bob в роли x — 2 связи × 2 направления.
  • 8 Шаблон из одной связи не может объединить две связи в одной строке; 4 — это максимум.

С чем совпадает MATCH (p:Person)-[ACTED_IN]->(m:Movie) RETURN p.name на графе фильмов?

  • Только со связями ACTED_IN Для этого нужно двоеточие, [:ACTED_IN].
  • С каждой связью от человека к фильму: ACTED_IN, DIRECTED, PRODUCED, WROTE, REVIEWED Без двоеточия ACTED_IN — просто имя переменной: "Only variable name (any relationship)", p. 1359.
  • Ни с чем: запрос — синтаксическая ошибка Это корректный Cypher; переменную вполне можно назвать ACTED_IN.
  • Ни с чем: ACTED_IN не определена Переменной не нужно определение; её вводит сам шаблон.

Ben знает Zoe. Ты выполняешь MATCH (n:Person {name: 'Ben'}) DELETE n. Что произойдёт?

  • Ben и его связь KNOWS удаляются Это DETACH DELETE.
  • Ben удаляется; KNOWS остаётся без одного конца Граф никогда не хранит связь без её конечного узла.
  • Запрос падает, и ничего не меняется "Cannot delete node…, because it still has relationships": сначала удали связи или используй DETACH.
  • Удаляются и Ben, и Zoe Удаляется только найденная переменная, и только когда у неё не осталось связей.

О запросе MATCH (bacon:Person {name:"Kevin Bacon"})-[*1..4]-(hollywood) RETURN DISTINCT hollywood (p. 1360). Отметь всё, что верно.

  • Он возвращает ещё и режиссёров, сценаристов и рецензентов, а не только фильмы и актёров У (hollywood) нет метки, а у скобок нет типа.
  • Он может вернуть самого Kevin Bacon К нему обратно ведёт цикл из четырёх разных связей; уникальность связей запрещает повторно использовать связь, а не снова зайти в узел.
  • Без DISTINCT он возвращает больше строк 297 путей против 135 разных узлов: многие пути приходят в один и тот же узел.
  • [*1..4] считает узлы, а не связи "Distance computed w.r.t. relationships": от 1 до 4 связей.
  • Если заменить [*1..4] на [*], запрос станет безопаснее Наоборот: неограниченный шаблон может затронуть весь граф, и Browser об этом предупреждает.

Ты выполняешь запрос со слайда (p. 1339) (MATCH для Mike и Mark, CREATE (a)-[r:KNOWS]->(b)) дважды, а потом тот же MATCH с MERGE (a)-[:KNOWS]->(b) один раз. Сколько связей KNOWS идёт от Mike к Mark?

  • 1 MERGE не удаляет дубликаты; он только не создаёт новых.
  • 2 Каждый CREATE записал по одной; MERGE нашёл шаблон уже на месте и ничего не записал.
  • 3 MERGE создаёт, только когда весь шаблон отсутствует, а здесь он есть.

Какой WHERE заставит Neo4j запланировать исчерпывающий fallback для p = shortestPath((a)-[*]-(b))?

  • all(n IN nodes(p) WHERE n:Person) Условие на каждый узел: проверяется, как только узел достигнут, так что быстрого поиска достаточно.
  • none(n IN nodes(p) WHERE n.name = "Ann") Тоже универсальное: каждый узел должен не пройти проверку, а это можно проверять узел за узлом.
  • any(n IN nodes(p) WHERE n.name = "Kevin Bacon") «Хотя бы один узел» можно решить только по целому пути: это собственный пример слайда для исчерпывающего случая.
  • Вообще без WHERE Тогда проверять нечего: быстрый поиск возвращает кратчайший путь.

Ты хочешь посмотреть, как Neo4j выполнил бы запрос DETACH DELETE, ничего не удаляя. Какое ключевое слово ты поставишь перед ним?

  • EXPLAIN Он показывает план с оценками числа строк и не выполняет запрос.
  • PROFILE PROFILE "executes the query" (p. 1348): узлы бы исчезли.
  • WITH WITH соединяет части запроса; выполнение он не останавливает.

Главное

  • Шаблон Cypher — это рисунок: (variable:Label {property: value}) для узла, -[variable:TYPE {property: value}]-> для связи. Каждый значок — фильтр; без двоеточия имя — всего лишь переменная, а без наконечника связь может смотреть в любую сторону.
  • CREATE всегда пишет (связи нужны направление и ровно один тип, а повторный запуск создаёт вторую); MERGE пишет, только когда весь шаблон отсутствует; SET обновляет; DELETE отказывается удалять узел, у которого ещё есть связи, DETACH DELETE сначала удаляет их.
  • MATCH делает по строке на путь. DISTINCT и count(DISTINCT x) превращают пути в вещи: 3 строки, 1 сёрфер. Внутри пути каждая связь используется один раз; узлы могут повторяться.
  • PROFILE выполняет запрос и показывает его операторы со строками между ними (5 → 1 → 4 → 12 → 3 → 1); EXPLAIN показывает план, не выполняя запрос.
  • Звёздочка повторяет связи: [*] — одна или больше, [*0..] — ещё и путь нулевой длины, [*1..4] — от одной до четырёх; всегда ставь верхнюю границу. ()-[]+->() со слайда — некорректный Cypher.
  • shortestPath возвращает один кратчайший путь, allShortestPaths — все. Neo4j ищет быстрым двунаправленным BFS, когда условие можно проверить во время поиска, и планирует исчерпывающий DFS как fallback, когда нужен весь путь; WITH p перед WHERE убирает fallback и может не вернуть ничего.
