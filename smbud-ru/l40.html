Spark SQL, Catalyst и колоночные форматы файлов

После этого урока ты сможешь провести DataFrame-запрос через четыре фазы Catalyst, сказать, какие байты Parquet-файла он прочитает и почему, и объяснить, откуда берётся скорость Spark SQL.

В статье, по которой построен график (p. 1287), две программы на Spark считают одно и то же: среднее одного столбца для каждого значения другого, по миллиарду пар чисел, на тех же пяти рабочих машинах. Обе написаны на Python. Одна отдаёт работу map и reduceByKey в виде лямбд; другая — одна строка, df.groupBy("a").avg("b"). На графике лямбдам нужно около 180 секунд, а однострочнику — около 15: в двенадцать раз меньше.

Тот же язык, те же данные, тот же кластер. Что Spark знает об однострочнике такого, чего он не может знать о лямбдах? К концу урока у тебя будет три ответа, и один из них вообще не в Spark, а в файле на диске.

Spark SQL — это больше, чем SQL

Титульный слайд говорит это пятью словами: Spark SQL "is about more than SQL" (p. 1262). Причины — на следующем слайде (p. 1263). Работа с большими данными должна "perform ETL to and from various (semi- or unstructured) data sources" (делать ETL из самых разных полу- и неструктурированных источников и обратно) и "perform advanced analytics (e.g. machine learning, graph processing) that are hard to express in relational systems" (то есть аналитику, которую трудно выразить в реляционных системах). Ответ: "a DataFrame API that can perform relational operations on both external data sources and Spark's built-in RDDs" плюс "a highly extensible optimizer, Catalyst".

Дальше (p. 1264) это превращается в три обещания декларативной (declarative) обработки больших данных: write less code — меньше кода, read less data — меньше читаемых данных, let the optimizer do the hard work — тяжёлую работу пусть делает оптимизатор. Ты говоришь, что хочешь получить; Spark решает, как. Урок идёт вслед за данными: твой код, оптимизатор, файл.

Write less code: одно среднее, четыре диалекта

На слайде (p. 1265) Hadoop-маппер пишет каждое значение под ключом 1: он усредняет весь файл, а строки Spark — по каждому ключу.

На слайде (p. 1265) среднее считается примерно в тридцати строках Java для Hadoop и в пяти — на Spark; следующий слайд (p. 1266) пишет средний возраст по имени на четырёх диалектах: RDD, SQL, Pig и DataFrame. Возьмём people(name, age): Ann 30, Bob 20, Ann 40, Cid 10. (sqlCtx со слайдов — это сегодняшний объект сессии spark.)

from pyspark.sql import functions as F
# one row per name: Ann 35.0, Bob 20.0, Cid 10.0
spark.table("people").groupBy("name").agg(F.avg("age")).show()

Using DataFrames: sqlCtx.table("people") \ .groupBy("name") \ .agg("name", avg("age")) \ .collect()

Передавай только агрегат: .groupBy("name").agg(F.avg("age")). Столбец группировки вернётся сам.

agg принимает выражения над столбцами, а не имя столбца перед ними: на PySpark 4.2 строка со слайда падает с AssertionError: all exprs should be Column, а исправленная возвращает name и avg(age). На экзамене строку могут процитировать как напечатано: узнай её, а в ответе на SparkQL пиши исправленный вариант.

RDD-версия со слайда (p. 1266) носит ингредиенты среднего вручную:

# the same averages with RDDs: carry (sum, count) pairs yourself
(sc.textFile("people.tsv")
   .map(lambda line: line.split("\t"))
   .map(lambda x: (x[0], [int(x[1]), 1]))
   .reduceByKey(lambda x, y: [x[0] + y[0], x[1] + y[1]])
   .map(lambda x: [x[0], x[1][0] / x[1][1]])
   .collect())
Средние не сливаются: среднее 10 и 20 — это 15, среднее 15 и 60 — 37.5, а среднее 10, 20 и 60 — 30.

Зачем [int(x[1]), 1]? reduceByKey объединяет частичные результаты в любом порядке и на любой машине, как combiner из урока 30. Средние так объединять нельзя, а пары (сумма, количество) — можно, и последний map делит одно на другое:

\[ \begin{aligned} &(s_1, c_1) \oplus (s_2, c_2) \\ &\quad = (s_1 + s_2,\ c_1 + c_2) \end{aligned} \]

DataFrame просто говорит avg, а всю эту механику Spark подставляет сам. (sc.textFile(...).split("\t") со слайда упал бы: у RDD нет split, поэтому каждую строку разбивают внутри map.)

Один движок, два входа

Spark SQL — "part of the core distribution since Spark 1.0", и он "runs SQL / HiveQL queries, optionally alongside or replacing existing Hive deployments" (выполняет SQL/HiveQL-запросы рядом с существующими установками Hive или вместо них) (p. 1270). Где он находится, показывает слайд (p. 1272).

Слайд представляет Spark SQL как "Originally called Shark" с тремя ограничениями (p. 1271): он "can only be used to query external data in Hive catalog → limited data sources", "can only be invoked via SQL string from Spark → error prone", а его "Hive optimizer tailored for MapReduce → difficult to extend". Прочитай их наоборот — и получишь устройство Spark SQL: любой источник и родные RDD, DataFrame API, новый оптимизатор.

«Spark SQL умеет запрашивать только таблицы Hive». Это было ограничение Shark. Строго говоря, Shark был проектом-предшественником — Hive поверх Spark, — и в июле 2014 года его остановили в пользу Spark SQL (контекст, не со слайдов).

Что есть у программы и нет у SQL-строки

Слайд (p. 1273) перечисляет "Advantages over Relational Query Languages": "Holistic optimization across functions composed in different languages", "Control structures (e.g. if, for)" и "Logical plan analyzed eagerly → identify code errors associated with data schema issues on the fly". Выполнение ленивое (lazy), а анализ — немедленный (eager): на таблице sales(region, amount) строка sales.select("col") падает сразу, ещё до чтения каких-либо данных, с ... `col` cannot be resolved. Did you mean one of the following? [`amount`, `region`] (Spark 4.2, проверено запуском).

Spark SQL запрашивает и твои собственные объекты (p. 1274): он умеет "infer column names and types directly from data objects (via reflection in Java and Scala and data sampling in Python, which is dynamically typed)" — выводить имена и типы столбцов прямо из объектов, — читает их "in-place" и позволяет "combine RDDs with external structured data", причём "hot columns cached in memory".

Внутри полноценного языка программирования пользовательской функции (user-defined function), UDF, не нужна никакая упаковка: Spark SQL "allows inline registration of UDFs", тогда как Pig "requires the UDF to be written in a Java package", а зарегистрированная UDF "available to other interfaces" (p. 1275) — слайд регистрирует обученную модель как predict и вызывает SELECT predict(age, weight) FROM users. Ещё один слайд (p. 1269) добавляет композицию: add_demographics принимает DataFrame и возвращает DataFrame. В рабочем виде, вместе с вызывающим кодом со слайда (p. 1281):

from pyspark.sql import functions as F
from pyspark.sql.types import StringType

zipToCity = F.udf(lambda z: "Melbourne" if z.startswith("3")
                            else "Other", StringType())

def add_demographics(events):
    u = spark.table("users")
    return (events.join(u, events.user_id == u.user_id)
                  .withColumn("city", zipToCity(u.zip)))

# the timestamps of the events of users living in Melbourne
events = add_demographics(spark.read.parquet("/data/events"))
training_data = (events.where(events.city == "Melbourne")
                       .select(events.timestamp)
                       .collect())

events \ .join(u, events.user_id == u.user_id) \ .withColumn("city", zipToCity(df.zip)) — "Takes and returns a DataFrame"

Бери почтовый индекс из таблицы пользователей, zipToCity(u.zip), и возвращай цепочку через return.

df нигде не определён, поэтому Python падает с NameError; а функция без return возвращает None, а не DataFrame, который обещает слайд. На другом слайде (p. 1281) эти строки повторяются, и экзамен может процитировать их как напечатано: знай обе версии.

Spark SQL — это один структурированный API и один оптимизатор за SQL-строками и DataFrame-кодом одновременно, а выполняется всё как операции над RDD.

Let the optimizer do the hard work: Catalyst

Лямбда — чёрный ящик: Spark может её вызвать, но не может заглянуть внутрь. DataFrame-запрос хранится как дерево (tree) объектов-узлов. Выражение x + (1 + 2) — это Add(Attribute(x), Add(Literal(1), Literal(2))), а правило (rule) — функция, которая находит в дереве шаблон и заменяет его (p. 1276):

tree.transform {
  case Add(Literal(c1), Literal(c2)) => Literal(c1+c2)
}

Правила (p. 1277) — это "pattern matching functions that transform subtrees into specific structures", то есть функции сопоставления с образцом, и при этом частичные функции: они "skip over subtrees that do not match → no need to modify existing rules when adding new types of operators" — именно поэтому Catalyst расширяем. Один transform может содержать несколько шаблонов; правила идут батчами (batches) и "may take multiple batches to reach a fixed point" — неподвижной точки, где ни одно правило уже не меняет дерево (одна перезапись может открыть дорогу следующей); и "transform can contain arbitrary Scala code".

Четыре фазы: от запроса до RDD

Слайд (p. 1278) — карта оптимизатора, и его подпись — тот самый факт, который надо запомнить: "DataFrames and SQL share the same optimization/execution pipeline".

Неразрешённый атрибут (unresolved attribute) — атрибут, чей "type is not known or it's not matched to an input table" (тип неизвестен или который не сопоставлен ни с одной входной таблицей) (p. 1279).

Перед каждым именем, которое ещё не разрешено, Spark печатает кавычку '.

Анализ (analysis) (p. 1279) превращает неразрешённый логический план в логический план. Для SELECT col FROM sales он должен "look up relations by name from the catalog" — найти отношения по имени в каталоге, "map named attributes to the input provided given operator's children", выдать "UID for references to the same value" и "propagate and coerce types through expressions (e.g. 1 + col)". Spark даёт за этим понаблюдать: для SELECT amount + 1 FROM sales разобранный план содержит 'amount и 'UnresolvedRelation [sales], а проанализированный — amount#32 + cast(1 as double): столбец с уникальным id и литерал, приведённый к нужному типу.

Логическая оптимизация (logical optimization) (p. 1280) "applies standard rule-based optimization (constant folding, predicate-pushdown, projection pruning, null propagation, boolean expression simplification, etc)", и всё это в "800LOC". Проталкивание предикатов (predicate pushdown) переносит фильтр как можно ближе к данным; отсечение проекций (projection pruning) оставляет только столбцы, которые используются выше. Ещё один слайд (p. 1282) расписывает одно такое правило: "Find filters on top of projections", "Check that the filter can be evaluated without the result of the project", "If so, switch the operators".

Spark 4.2 идёт дальше: в его оптимизированном плане внутренней проекции нет вовсе, а фильтр превращается в isnotnull(id) AND (id = 1) (проверено запуском).

Слайд (p. 1281) прогоняет пример через три плана (виджет их воспроизводит): where вызывающего кода стоит поверх join, написанного внутри add_demographics, и Catalyst всё равно опускает его вниз — та самая "holistic optimization across functions" (p. 1273).

Catalyst за работой: четыре плана одного запроса

Запрос со слайда (p. 1281) ("after the join, on users.city") с одним изменением: users хранит сам город, так что UDF не нужна (с питоновской UDF со слайда Spark опускает фильтр ниже join, но не может протолкнуть его в сканирование). Обе таблицы — Parquet-файлы: events(user_id, timestamp, kind) и users(user_id, zip, city). Выбери, как записан фильтр, и пройди по шагам от неразрешённого плана до физического. Планы упрощены по сравнению с тем, что Spark 4.2 печатает для этого запроса. Условные размеры для счётчика строк: 1,000,000 событий, 10,000 пользователей; у 400 пользователей из Мельбурна 40,000 событий; 250,000 событий — клики.

  1. Оставь «после join» и дойди до проанализированного плана. Прежде чем снова нажать «Дальше»: где окажется Filter и сколько строк выдаст join?
    Что должно получиться

    Ниже join, прямо над отношением users (и над ним появится новый Project, который оставляет только user_id): city — столбец users, поэтому Catalyst проверяет его до соединения. Теперь join строит 40,000 строк вместо 1,000,000. Ради этого вывода виджет и существует: оптимизатор двигает фильтр к данным, в каком бы порядке ты его ни написал.

  2. Переключись на «до join» и сравни его оптимизированный и физический планы с планами варианта «после join».
    Что должно получиться

    Они совпадают, узел в узел. Неразрешённый и проанализированный планы двух запросов ещё различаются; начиная с оптимизированного плана Catalyst сделал их одинаковыми. Пиши фильтр там, где он лучше читается.

  3. Выбери «после join, по events.kind» и дойди до физического плана. Какая сторона получает фильтр и сколько столбцов users читается?
    Что должно получиться

    Сторона events: kind — столбец events. Сканирование users читает только user_id, 1 столбец из 3, потому что выше join никому не нужны ни zip, ни city. Отсечение проекций работает для каждой таблицы и для каждого запроса отдельно.

  4. В физическом плане фильтр протолкнут в сканирование Parquet, но над сканированием всё ещё нарисован узел Filter. Зачем оба?
    Что должно получиться

    Сканирование использует протолкнутый фильтр, чтобы пропускать целые row group, чья статистика его исключает (следующий раздел); строки тех row group, которые оно всё же читает, затем проверяются по одной. Протолкнутые фильтры — это помощь источнику, а не обещание.

Физическое планирование (physical planning) превращает оптимизированный план в один или несколько физических планов из настоящих операторов, и модель стоимости (cost model) выбирает один из них (p. 1278). В статье о Spark SQL она выбирала только алгоритм соединения — broadcast join для маленькой таблицы, как в виджете (контекст, не со слайдов). Сканирования принадлежат источникам данных (data sources): "Spark's Data Source API allows optimizations like column pruning and filter pushdown into custom data sources" (p. 1268) — это и есть отсечение проекций и проталкивание предикатов (p. 1280). Источник реализует buildScan(requiredColumns: Array[String], filters: Array[Filter]): RDD[Row] (p. 1267): два его параметра и есть два вида проталкивания. А раз "DataFrame execution is done with Spark RDDs", собственный код может спуститься до них: queryResult.rdd.mapPartitions { … }.

Генерация кода (code generation) (p. 1283) "relies on Scala's quasiquotes" (опирается на квазицитаты Scala): Catalyst "transforms a SQL tree into an abstract syntax tree (AST) for Scala code". Генератор на слайде — одно сопоставление с образцом:

def compile(node: Node): AST = node match {
  case Literal(value) => q"$value"
  case Attribute(name) => q"row.get($name)"
  case Add(left, right) =>
    q"${compile(left)} + ${compile(right)}"
}

Каждый q"…" — шаблон кода. Дерево с рис. 2 превращается в строку row.get("x") + 3, которая компилируется один раз, а не обходится заново для каждой строки данных: для x+x+x, вычисленного миллиард раз, это около 36 секунд в режиме интерпретации против примерно 9 со сгенерированным кодом, почти как написанный вручную (снято с графика), — и всё это из генератора в "700LOC".

Ты говоришь «что»; Catalyst решает «как» — переписывает дерево правилами, выбирает операторы по стоимости и компилирует результат.

Файлы, которые знают свою форму: Avro и Parquet

Catalyst передаёт сканированию requiredColumns и filters; что сканирование с ними сделает, зависит от файла. Слайд (p. 1242) перечисляет "Available File Formats": text и CSV, JSON, SequenceFile ("binary key/value pair format"), Avro, Parquet, ORC ("optimized row columnar format") и "Data Frames". В этом списке прячутся три семейства: текст (читается глазами, медленно парсится, без схемы), двоичные строки (SequenceFile, Avro) и двоичные столбцы (Parquet, ORC).

Available File Formats: "-Avro -Parquet -Data Frames -ORC"

DataFrame — не формат файла, а таблица Spark в памяти, "a distributed collection of rows organized into named columns" (p. 1246), в которую файлы читаются и из которой записываются.

Ни один файл на диске не является «DataFrame»: df.write.parquet(path) пишет Parquet. Закрытый вопрос могут сверять с напечатанным списком, так что знай оба ответа: слайд его перечисляет, а по сути — нет.

Avro: строки со схемой внутри

Avro (p. 1243) — это "language neutral data serialization system", не зависящая от языка система сериализации: "write a file in python and read it in C". Схема "language independent", "usually written in JSON", а данные "encoded in binary format". Avro "supports schema evolution" — "producers and consumers at different versions of schema" (производители и потребители могут работать с разными версиями схемы) — и "supports compression and are splittable". Схема твитов со слайда (p. 1244), исправленная:

{
  "type": "record",
  "name": "tweets",
  "doc": "schema for storing tweets",
  "fields": [
    { "name": "username",  "type": "string" },
    { "name": "tweet",     "type": "string" },
    { "name": "timestamp", "type": "long" }
  ]
}

"name" : "username", "type" : "string", }, { … and "doc:" : “schema for storing tweets"

Никакой запятой перед закрывающей скобкой, только прямые кавычки, а атрибут называется "doc" — как в схеме выше.

JSON запрещает висячую запятую, так что парсер отвергнет напечатанную схему уже на первом поле (проверено питоновским json); "doc:" оказался бы другим, неизвестным атрибутом. На экзамене схему могут показать как напечатано: структуру бери со слайда, пунктуацию — отсюда.

Avro-файл (p. 1244) — это заголовок (метаданные с JSON-схемой и маркер синхронизации (sync marker)), а за ним блоки: служебные данные (число записей и размер), сериализованные объекты и тот же маркер. Благодаря маркеру файл делится на части (splittable): задача, которая начинает с середины файла, на границе HDFS-сплита, перескакивает к следующему маркеру и оказывается выровненной по блоку. Схема записана один раз, поэтому записи не несут имён полей.

Parquet: столбцы внутри row group

"Apache Parquet is a columnar storage format available to any project in the Hadoop/Spark ecosystem, regardless of the choice of data processing framework, data model or programming language" (колоночный формат хранения для любого проекта экосистемы Hadoop/Spark, независимо от фреймворка, модели данных и языка) (p. 1250). Разницу показывает слайд (p. 1254) на таблице X, Y, Z: строковый формат хранит x1 y1 z1 x2 y2 z2 …, колоночный — x1 … x5, затем y1 … y5, затем z1 … z5, каждый столбец одним "encoded chunk" — это колоночное хранилище из урока 20, только в виде файла.

Единицы вложены друг в друга (pp. 1245, 1251). Группа строк (row group) — "a group of rows in columnar format": "max size buffered in memory while writing" (максимум, который буферизуется в памяти при записи), "one (or more) per split while reading", "roughly: 50MB < row group < 1 GB". Фрагмент столбца (column chunk) — "the data for one column in a row group", и его "can be read independently". Страница (page) — "unit of access in a column chunk", "big enough for compression to be efficient", "roughly: 8KB < page < 1MB". footer (служебный хвост файла) (p. 1252) "contains column chunks offset and schema": для каждого column chunk — его тип, кодировки, кодек, число значений, смещения и размеры. Footer идёт последним, поэтому писатель может потоком выдавать row group и дописать индекс в конце; читатель же читает его первым и прыгает к нужным chunk.

Осторожно со словом block: один слайд (p. 1245) называет блоком row group, а другой (p. 1260) имеет в виду HDFS-блок из урока 31. Ни одна row group не лежит сразу на двух HDFS-блоках — в блок упаковываются целые row group, а остаток заполняется пустотой, — так что задача читает свою row group с одной машины.

«Колоночный — значит, весь файл — это один столбец за другим». В Parquet не так: файл — последовательность row group, и только внутри row group столбцы лежат подряд, поэтому каждую запись можно собрать из одной row group.

Avro пишет целые записи одну за другой, со схемой в заголовке; Parquet пишет каждый столбец row group вместе и индексирует файл в footer.

Read less data: внутри Parquet-файла

Слайд (p. 1257) перечисляет три способа "Read Less Data". Columnar organization: "Encoding: make the data smaller" и "Column projection: read only the columns you need". Row group filtering: "Use footer stats to eliminate row groups" и "Use dictionary pages to eliminate row groups". Page filtering: "Use page stats to eliminate pages". Другой слайд (p. 1255) называет первые приёмы projection push down (читать только запрошенные столбцы) и predicate push down (по статистике, например минимуму и максимуму каждого chunk, пропускать то, что совпасть не может): вместе ты "read only the data you need". Раскладка к тому же "minimizes CPU cache misses": значения столбца лежат рядом, и процессор подтягивает в кэш только полезные.

Словарь column chunk (p. 1261) "is a compact list of all the values": "Search term missing? Skip the row group" — "like a bloom filter without false positives" (как фильтр Блума, только без ложных срабатываний). Минимум и максимум исключают значение, только если оно лежит вне их диапазона; внутри диапазона они говорят «возможно». Словарь отвечает точно.

Один файл, записанный дважды: что читает запрос

Двенадцать твитов со схемой со слайда (p. 1244), по порядку времени. Сверху — Avro-файл: по четыре записи в блоке, каждый блок закрыт маркером синхронизации (фиолетовый). Снизу — Parquet-файл: три row group по четыре строки, каждая из трёх column chunk; узкая фиолетовая ячейка — словарная страница (dictionary page) chunk с username. Размеры на картинке: username — 8 байт, tweet — 120, timestamp — 8, всего 1,632 байта. Заголовки, маркеры, словари и footer в подсчёт не входят.

  1. Оставь первый запрос, а фильтрацию row group — выключенной. Предскажи, какую долю из 1,632 байт прочитает Avro и какую — Parquet. Потом включи статистику из footer.
    Что должно получиться

    Avro читает 100 %: чтобы найти timestamps, ему приходится читать каждую запись целиком. Parquet читает 192 байта (11.8 %) — chunk с username и timestamp из каждой row group; большой столбец tweet не трогается вовсе. Со статистикой — 64 байта (3.9 %): row group 1 заканчивается в 09:14, а row group 3 начинается в 09:47, так что ни одна из них не открывается. Две экономии перемножаются: 11.8 % байтов каждой row group, умноженные на 1 из 3 row group, дают 3.9 %. Ради этого вывода виджет и существует: Parquet пропускает целые column chunk и целые row group, а Avro не может пропустить ни то, ни другое.

  2. Выбери «текст твитов eva» с включённой статистикой из footer. Предскажи, какие row group сможет пропустить min/max. Потом добавь словарные страницы.
    Что должно получиться

    Никакие: в каждой row group имена идут от ada до ugo или до eva, и eva попадает в каждый диапазон, так что min/max может ответить только «возможно» — 1,536 байт. Словари точны: в row group 1 и 3 есть только ada, bob и ugo, поэтому обе пропускаются и остаётся 512 байт. "Like a bloom filter without false positives" (p. 1261).

  3. Выбери «все поля всех твитов». Сравни два файла.
    Что должно получиться

    Оба читают все 1,632 байта: когда фильтра нет и нужны все столбцы, колоночная раскладка ничего не экономит, а Parquet ещё и должен сшивать каждую запись обратно из трёх chunk. Строковый формат хорош для записи и чтения целых записей; колоночный — для аналитики по нескольким столбцам.

Кодировки: делаем данные меньше

Ещё до того как сработает какой-либо компрессор, Parquet кодирует каждый столбец приёмом, который подходит к его содержимому (pp. 1256, 1258; примеры наши).

Из "heavyweight algorithms (gzip, lzo, snappy)" со слайда (p. 1258) по-настоящему тяжёлый только gzip: Snappy и LZO жертвуют степенью сжатия ради скорости (контекст, не со слайдов).

Словарное кодирование (dictionary encoding) "useful for columns with few ( < 50,000 ) distinct values" и "when applicable, compresses better and faster than heavyweight algorithms". Bit packing хранит маленькие целые "in the minimum bits required": значению с максимумом \(m\) нужно \(\lceil \log_2(m+1) \rceil\) бит, так что 16 бит покрывают любой ключ меньше 65,536. Parquet 2.0 (p. 1259) добавляет "more encodings: compact storage without heavyweight compression" (delta-кодировки "for integers, strings and sorted dictionaries"), "statistics: to be used by query planners and predicate pushdown" и "new page format: to facilitate skipping ahead at a more granular level" — новый формат страниц, чтобы пропускать данные ещё мельче.

«Словарное кодирование всегда окупается». Только при малом числе различных значений: когда словарь перерастает 1 MB (parquet.dictionary.page.size, p. 1245), писатель откатывается к plain encoding, и у chunk уже нет полного словаря, по которому можно было бы пропускать.

Вложенные записи в плоских столбцах

Главная сила Parquet, его "key strength", — умение "store nested data in truly columnar format using definition and repetition levels", то есть хранить вложенные данные по-настоящему поколоночно с помощью уровней определения и повторения (p. 1254). Приём пришёл из Google Dremel; слайд (p. 1253) применяет его к схеме с одной необязательной группой и двумя повторяющимися полями.

Рядом с каждым сохранённым значением Parquet пишет два маленьких целых числа. Уровень определения (definition level) D говорит, сколько необязательных или повторяющихся полей на пути к значению реально присутствует; уровень повторения (repetition level) R говорит, на каком повторяющемся поле значение продолжает список, а 0 значит, что начинается новая запись. Запись со слайда, разобранная (shredded) шаг за шагом:

  1. Выпиши столбцы по схеме, по одному на каждый лист: DocId, Links.Backward, Links.Forward. Группы Document и Links сами ничего не хранят.

  2. Посчитай на каждом пути поля, которых может не быть:

    \[ D_{\max} = \#\ \text{optional or repeated fields} \]

    DocId обязательное (required): 0. Links необязательное, а Backward повторяющееся: 2; у Forward тоже. Значение должно сообщать, до какой глубины определён его путь.

  3. Посчитай только повторяющиеся поля:

    \[ R_{\max} = \#\ \text{repeated fields} \]

    0 для DocId, 1 для каждого списка: на пути одно повторяющееся поле, значит, R равно 0 или 1.

  4. Разбери DocId: 20: обязательное значение в начале записи даёт (20, R 0, D 0).

  5. Разбери Backward: 10, 30. Первое значение начинает список записи (R 0), при этом Links и Backward присутствуют (D 2): (10, 0, 2). Второе продолжает список на Backward, первом повторяющемся поле: (30, 1, 2).

  6. Разбери Forward: 80, первый Forward этой записи: (80, 0, 2). Это и есть четыре строки со слайда (p. 1253); при максимумах 1 и 2 bit packing хранит R в 1 бите, а D — в 2.

  7. Не со слайда, но по тем же правилам: запись без Links хранит NULL в обоих столбцах Links с R 0, D 0 — путь обрывается до Links. R = 0 говорит сборщику, что начинается новая запись, поэтому он восстанавливает запись в точности.

Parquet пропускает на трёх уровнях — column chunks, row groups, pages — и превращает вложенность в два крошечных целых числа на значение.

Вывод схемы для JSON

У JSON нет схемы, и всё же Spark SQL "automatically infers schema from a set of records, in one pass or sample" (сам выводит схему по набору записей за один проход или по выборке) (p. 1285). Каждая запись даёт "a tree of STRUCT types"; каждое поле получает "the most appropriate type … based on all data observed in that column"; схемы отдельных записей сливаются "in one reduce operation" — это возможно, потому что слияние схем ассоциативно, как пары (сумма, количество). Целое число в одной записи и дробное в другой дают FLOAT — самый узкий тип, вмещающий оба; loc нет в записи 3, поэтому он не получает NOT NULL. ML-конвейеры говорят на DataFrame

Слайд (p. 1286), повторённый ещё раз (p. 1288), соединяет в цепочку три стадии библиотеки машинного обучения Spark, MLlib (кавычки выпрямлены):

Откуда двенадцать раз

Слайд (p. 1287) измеряет, как выполняются обещания (рис. 8).

Вернёмся к загадке из начала. Лямбды — чёрные ящики, которые Spark может только вызывать, строка за строкой, в процессе Python; однострочник — дерево, которое он может прочитать, и отсюда три ответа. Catalyst может его переписать. В Python строится только план, а работа идёт как байткод JVM: статья приписывает этому 12×, а генерации кода, которая "avoids expensive allocation of key-value pairs", — выигрыш 2× над Scala. И план называет свои столбцы и фильтры, так что у источника данных можно попросить меньше: с Parquet с диска уходят только нужные column chunks и row groups — это и есть ответ, который лежит в файле. Правый график добавляет, что одно DataFrame-задание обгоняет SQL-запрос плюс отдельное задание Spark примерно в 2 раза: между ними ничего не сохраняется в HDFS (из статьи).

DataFrame выигрывает, потому что Spark видит весь план: он может его переписать, скомпилировать и попросить у файла меньше.

Describe the phases of query optimization in Spark SQL's Catalyst, from a query written as SQL or with the DataFrame API to the RDDs that execute it. Which phase uses a cost model, and for what?

Показать образец ответа

An SQL string (parsed into an AST) and a DataFrame both produce an unresolved logical plan: the same pipeline serves both. Analysis resolves it with the catalog — it looks up relations by name, maps named attributes to the inputs of each operator, gives each attribute a unique id and propagates and coerces types — and yields a logical plan. Logical optimization applies rule-based rewrites such as constant folding, predicate pushdown, projection pruning, null propagation and boolean expression simplification, producing an optimized logical plan. Physical planning generates one or more physical plans made of Spark operators, and a cost model selects one (for example the join algorithm: a broadcast join for a small table). Code generation finally compiles the selected plan, using Scala quasiquotes, into code that runs as RDD operations. Only physical planning is cost-based; the other phases apply rules.

Полный ответ называет четыре фазы по порядку, что входит в каждую и что из неё выходит, каталог в анализе и модель стоимости только в физическом планировании. Назови и несколько правил логической оптимизации: их пропускают легче всего.

What is an unresolved attribute in Spark SQL? Using the query SELECT col FROM sales, explain what the analyzer does, and what happens when sales has no column col.

Показать образец ответа

An attribute is unresolved if its type is not known or it is not matched to an input table. After parsing, col is only a name and sales an unresolved relation. The analyzer looks up sales by name in the catalog, matches col to one of its columns, gives it a unique id so that every reference to the same value is recognised, and propagates and coerces types through expressions (in 1 + col the literal is cast to the type of col). If sales has no column col, analysis fails at once with an error, before any data is read: the logical plan is analyzed eagerly, even though the query is executed lazily.

Суть — определение словами слайда и поиск в каталоге. Формула «немедленный анализ, ленивое выполнение» (eager analysis, lazy execution) покажет, что ты понимаешь, почему ошибка появляется так рано.

Which of the following are rule-based optimizations of Catalyst's logical optimization phase, as listed in the lecture? Select all that apply.

  • Constant folding Есть в списке (p. 1280); правило со слайда (p. 1276) превращает x + (1 + 2) в x + 3.
  • Predicate pushdown Есть в списке (p. 1280): фильтр движется к данным, ниже проекций и join.
  • Projection pruning Есть в списке (p. 1280): остаются только столбцы, которые используются выше.
  • Choosing a broadcast join because a table is small Этот выбор относится к физическому планированию, где модель стоимости выбирает среди физических планов.
  • Null propagation Есть в списке стандартных правил (p. 1280).

Неверные варианты — настоящая работа Catalyst, только в другой фазе. За неправильный ответ могут снять баллы, так что фазу каждой оптимизации надо знать наверняка.

True or false: because DataFrames are evaluated lazily, a reference to a column that does not exist is reported only when an action such as show() or collect() runs.

  • True Выполнение ленивое, но логический план анализируется немедленно (p. 1273): неверное имя столбца падает сразу, как только строка написана.

Показать образец ответа

Ловушка — растянуть «ленивость» с выполнения на анализ. Анализу нужны только метаданные, поэтому делать его сразу дёшево.

Describe the internal structure of a Parquet file and explain how it lets a query that needs two columns and a filter read less data than a row-oriented format such as Avro.

Показать образец ответа

A Parquet file is a sequence of row groups followed by a footer, with the magic number PAR1 at both ends. A row group holds a set of rows in columnar format (parquet.block.size, 128 MB by default) and never straddles two HDFS blocks; inside it each column is stored contiguously as a column chunk, and each column chunk is divided into pages, the unit of access, encoding and compression (1 MB by default). The footer stores the schema and, for every row group and column chunk, its offset, size, encodings, codec and statistics such as min and max. A reader reads the footer first. With projection pushdown it reads only the column chunks of the two requested columns. With predicate pushdown it uses the footer statistics and the dictionary pages to skip row groups that cannot contain matching rows, and page statistics to skip pages. Avro stores whole records one after another, so the same query must read every byte of every record.

В полном ответе есть иерархия (row group, column chunk, page), содержимое footer и оба вида проталкивания (pushdown), каждый — в связке со структурой, которая его делает возможным.

Consider the Parquet schema message Document { required int64 DocId; optional group Links { repeated int64 Backward; repeated int64 Forward; } }.

(a) Give the maximum repetition and definition levels of each column. (b) Shred the record DocId: 10, Links { Forward: 20, Forward: 40, Forward: 60 }, which has no Backward value, into (value, R, D) triples.

Показать образец ответа

(a) DocId: max R 0, max D 0 (required, nothing optional or repeated on its path). Links.Backward and Links.Forward: max R 1 (one repeated field on the path), max D 2 (Links is optional, the field itself repeated).

(b) DocId: (10, 0, 0). Links.Backward: (NULL, 0, 1) — Links is present but Backward is not, so one of the two fields of the path is defined; R 0 because the value belongs to a new record. Links.Forward: (20, 0, 2), (40, 1, 2), (60, 1, 2) — the first value starts the record's list, the next two repeat at level 1, and both Links and Forward are defined.

У записи со слайда (p. 1253) есть список Backward; у этой — нет, и NULL с D = 1 — вся суть упражнения. Max D считает необязательные и повторяющиеся поля, max R — только повторяющиеся.

Проверь себя

Ты переносишь .where(users.city == "Melbourne") из позиции после join в позицию до него. Что происходит с оптимизированным планом?

  • Ничего: это тот же самый план Catalyst в любом случае опускает фильтр ниже join; виджет показал одинаковые оптимизированные и физические планы.
  • Он становится быстрее, потому что фильтр теперь выполняется первым Он выполняется первым в обоих случаях: predicate pushdown уже перенёс его туда.
  • Он становится медленнее, потому что join теряет нужные ему строки Фильтр удаляет только строки, которые запрос и так бы отбросил; результат тот же.
  • Он падает, потому что в users нет timestamp timestamp берётся из events; отфильтровать users заранее совершенно законно.

В Parquet-файле 10 одинаково больших столбцов в 8 row group. Запросу нужны 2 столбца, а статистика в footer доказывает, что подходящие строки могут быть только в 2 row group. Какую примерно долю файла прочитают?

  • 5 % Два пропуска перемножаются: 2/10 столбцов умножить на 2/8 row group — это 1/20.
  • 20 % Так учтена только проекция столбцов, а пропущенные row group забыты.
  • 25 % Так учтены только row group, а забыто, что 8 из 10 столбцов не читаются.
  • 45 % Две экономии не складываются, а перемножаются.

Почему Spark не может перенести фильтр в rdd.map(f).filter(g) ниже map, как Catalyst делает это с DataFrame?

  • f и g — непрозрачные функции: Spark не видит, какие поля они читают или пишут Для проталкивания нужно знать, что фильтр не зависит от того, что вычисляет map; лямбда этого не сообщает.
  • Потому что RDD неизменяемы DataFrame тоже неизменяемы, а Catalyst постоянно переписывает их планы.
  • Потому что операции над RDD вычисляются немедленно Преобразования RDD тоже ленивые; ленивость тут не помеха.
  • Потому что Catalyst работает только с кодом на Scala Catalyst оптимизирует и DataFrame-код на Python; в Python строится только план.

Какие утверждения о footer Parquet-файла верны?

  • Он записывается после всех row group Писатель потоком выдаёт row group и дописывает footer последним, за один проход.
  • Он хранит схему и для каждого column chunk — его смещение и статистику "A footer contains column chunks offset and schema" (p. 1252); статистика — это "footer stats" (p. 1257).
  • Читатель читает его раньше любого column chunk Ему нужны смещения, чтобы прыгать к chunk, и статистика, чтобы пропускать row group.
  • Он хранит копию первой row group для быстрого предпросмотра В footer только метаданные, никаких данных.
  • Он стоит в конце, потому что HDFS не умеет читать файлы с начала HDFS читает с любого смещения; причина — запись за один проход.

Схема та же, что на слайде (p. 1253). У записи есть DocId: 7 и нет Links вообще. Что хранит для неё столбец Links.Backward?

  • NULL с R = 0 и D = 0 На пути ничего не определено, поэтому D = 0; значение принадлежит новой записи, поэтому R = 0.
  • Ничего Тогда читатель не смог бы понять, где в этом столбце кончается одна запись: каждая запись оставляет след в каждом столбце.
  • NULL с R = 0 и D = 1 D = 1 значило бы, что Links есть, а не хватает только Backward.
  • NULL с R = 1 и D = 2 D = 2 означает настоящее значение Backward, а R = 1 — продолжение списка: ни то, ни другое не наш случай.

У column chunk столбца city словарь {Como, Lecco, Milano}, а статистика — min Como, max Milano. Какой фильтр позволяет читателю пропустить row group благодаря словарю, хотя одних min/max для этого не хватило бы?

  • city == "Lodi" Lodi лежит между Como и Milano, так что min/max говорит «возможно»; словарь говорит, что его там нет.
  • city == "Monza" Monza идёт после Milano: одних min/max уже хватает, чтобы пропустить row group.
  • city == "Lecco" Lecco есть в словаре: row group придётся прочитать.
  • city > "Bari" Все значения chunk идут после Bari: пропустить ничего нельзя.

Какие объекты из MLlib-pipeline со слайда (p. 1286) оказываются внутри обученной PipelineModel?

  • tokenizer Transformer: используется как есть.
  • hashingTF Тоже transformer.
  • lr.model Transformer, который выдал lr.fit на ds2.
  • lr Estimator используется один раз, в fit; поэтому рис. 7 рисует его снаружи пунктирной рамки.
  • ds0 Входные данные — не стадия модели.

Главное

  • Spark SQL "is about more than SQL": один DataFrame API и один оптимизатор, Catalyst, стоят и за SQL-строками, и за DataFrame-кодом, а выполняется всё на RDD; он снял ограничения Shark (только каталог Hive, только SQL-строки, оптимизатор эпохи MapReduce).
  • Декларативный код короче и проверяем: agg(F.avg("age")) вместо пар (сумма, количество), которые носишь вручную, а немедленный анализ сообщает о неверном столбце ещё до того, как сдвинулись какие-либо данные.
  • Catalyst переписывает деревья правилами сопоставления с образцом до неподвижной точки, в четыре фазы: анализ с каталогом, логическая оптимизация на правилах, физическое планирование с моделью стоимости, генерация кода с квазицитатами.
  • Predicate pushdown и projection pruning двигают фильтры к данным и выбрасывают неиспользуемые столбцы — вплоть до buildScan(requiredColumns, filters) источника данных.
  • Avro хранит целые записи, с JSON-схемой в заголовке и маркерами синхронизации для деления на части; Parquet хранит column chunks внутри row groups, индексирует их в footer и читает только те столбцы, row groups и pages, которые нужны запросу.
  • Кодировки (delta, prefix, dictionary, RLE, bit packing) сжимают столбцы, а уровни определения и повторения (definition and repetition levels) хранят вложенные данные как плоские столбцы.
  • Расширения, вывод схемы JSON одним reduce и конвейеры MLlib — всё строится на DataFrame; на слайде (p. 1287) агрегация на DataFrame работает примерно в 12 раз быстрее, чем RDD-код на Python.
