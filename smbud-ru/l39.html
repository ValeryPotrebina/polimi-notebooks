RDD вручную: создать, преобразовать, выполнить

Практическое занятие открывается одной фразой: Apache Spark "is a multi-language, unified analytics engine for big data processing, with built-in modules for executing data engineering, data science, and machine learning tasks on single-node machines or clusters" (p. 1712). Это движок, а не хранилище: "Importers for most data formats and from most database technology" из лекции (p. 1227) дотягиваются до Cassandra, Elasticsearch, MongoDB, Neo4j, Redis и до файлов CSV, JSON, Avro или Parquet, а занятие рисует Spark в центре инструментов для стриминга, ETL, машинного обучения, анализа, графов и data lake (p. 1716; на следующем слайде (p. 1717) инструменты разложены по видам). Spark читает данные там, где они живут, вычисляет и записывает результат обратно.

Любая программа начинается с точки входа. Лекция называет её SparkContext: "Main entry point to Spark functionality", "Available in shell as variable sc" и "In standalone programs, you'd make your own" (p. 1228). Начиная со Spark 2.0 ты создаёшь SparkSession — это первая строка каждого ноутбука занятия и надёжная первая строка экзаменационного ответа — и получаешь контекст через неё:

# the entry point (E08, p. 1726); sc is the SparkContext of p. 1228
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("SMBUD").getOrCreate()
sc = spark.sparkContext

Занятие расшифровывает название RDD (p. 1720): Resilient — "Fault-tolerant"; Distributed — "Computed across multiple nodes"; Dataset — "Collection of partitioned data". Следующий слайд перечисляет четыре характеристики (p. 1721): RDD "Are immutable", "Work with lazy evaluation", "Are divided into partitions" и "Are fault-tolerant, which is achieved through lineage graphs" — как работает каждая, показывает урок 38.

RDD получается из одного из трёх источников (p. 1229): из коллекции Python, которую parallelize режет на партиции; из текстового файла, который читает textFile, по элементу на строку; или из любого существующего Hadoop InputFormat. Путь выбирает файловую систему — "file.txt" локальный, "hdfs://namenode:9000/path/file" — это HDFS, шаблон вроде "directory/*.txt" читает много файлов, — так что одна и та же программа работает и на ноутбуке, и на кластере.

# two RDDs: a Python list, and the lines of a file
nums = sc.parallelize([1, 2, 3])
lines = sc.textFile("hamlet.txt")

Трансформации строят, действия запускают

Большую часть работы делают три трансформации (p. 1230). map пропускает каждый элемент через функцию: один вошёл — один вышел. filter оставляет элементы, для которых предикат истинен. flatMap отображает каждый элемент в ноль или больше элементов и расплющивает результат: range(x) — это последовательность 0, 1, …, x − 1, так что 1, 2 и 3 превращаются в [0], [0, 1] и [0, 1, 2] — всего шесть элементов.

Слайды записывают содержимое RDD в фигурных скобках, например {1, 4, 9}. Это не множества Python: множество не могло бы содержать {0, 0, 1, 0, 1, 2}. collect() возвращает список.
# the three basic transformations of p. 1230, with what they hold
squares = nums.map(lambda x: x*x)               # [1, 4, 9]
even = squares.filter(lambda x: x % 2 == 0)     # [4]
nums.flatMap(lambda x: range(x))                # [0, 0, 1, 0, 1, 2]

"nums.flatMap(lambda x: => range(x))"

У лямбды Python нет стрелки: nums.flatMap(lambda x: range(x)), что даёт [0, 0, 1, 0, 1, 2].

=> — стрелка анонимных функций Scala (x => …); если набрать строку со слайда в PySpark, она остановится с SyntaxError. Комментарии // над ней — тоже из Scala и Java: в Python пишут #. Экзамен требует PySpark, так что пиши Python-вариант; но ответ могут сверять с напечатанной строкой, так что узнавай в ней этот flatMap, когда вопрос её процитирует.

Ни одна из этих строк ничего не вычисляет. Трансформация возвращает новое RDD и записывает, как его построить; действие (action) заставляет Spark выполнить записанные шаги и либо вернуть значение программе-драйверу, либо записать результат наружу (p. 1231):

# the basic actions of p. 1231: only these make Spark work
nums.collect()                          # [1, 2, 3], to the driver
nums.take(2)                            # [1, 2]
nums.count()                            # 3
nums.reduce(lambda x, y: x + y)         # 6
nums.saveAsTextFile("hdfs://file.txt")  # part files, not one file

collect хорош для трёх чисел и смертелен для терабайта: он копирует весь набор данных в память драйвера, тогда как take(n) забирает только n элементов. saveAsTextFile пишет каталог part-файлов, по одному на партицию. Практическое занятие раскладывает операции по двум спискам (p. 1722):

«reduce и reduceByKey звучат похоже, значит, и ведут себя похоже». Нет. reduce() — действие: возвращает драйверу одно значение. reduceByKey() — трансформация: возвращает новое RDD пар, и до действия ничего не выполняется. Слайд кладёт их в противоположные списки. На слайде (p. 1231) ещё сказано "Merge elements with an associative function"; документация Spark требует ещё и коммутативности, потому что Spark сворачивает каждую партицию отдельно, а потом сливает частичные результаты, так что ни группировку, ни порядок слияний ты не выбираешь. Вычитание не обладает ни тем, ни другим: в PySpark 4.2 sc.parallelize([1, 2, 3, 4], 1).reduce(lambda x, y: x - y) даёт −8, ((1 − 2) − 3) − 4, а с 2 партициями даёт 0, (1 − 2) − (3 − 4).

"It just builds a lineage graph, which is an optimized execution plan."

Граф lineage записывает, как каждое RDD получается из своих родителей. План выполнения — стадии, разрезанные в местах shuffle, по задаче на партицию, — строит из него DAG scheduler, когда запускается действие. Оптимизировать план в смысле переписывания запроса — это то, что делает Catalyst для DataFrame.

Та же лекция говорит, зачем нужна lineage: "Spark remembers how an RDD was built and can recompute lost partitions" (p. 1721). В lineage RDD ничего не переставляется — твои лямбды выполняются так, как написаны; только идущие подряд узкие шаги сливаются в одну задачу (рис. 2). В теоретическом ответе отведи lineage её роль — рецепт для отказоустойчивости, — а «оптимизированный план» оставь для DataFrame (урок 40). Ответ могут сверять с напечатанной формулировкой, так что предложение со слайда тоже знай.

Пары: reduceByKey, word count и shuffle

"Spark's "distributed reduce" transformations operate on RDDs of key-value pairs" (p. 1232). Ничего объявлять не нужно: в Python пара — это кортеж из двух элементов, pair[0] — ключ, pair[1] — значение (в Scala пишут pair._1 и pair._2, в Java строят Tuple2), и RDD, элементы которого — пары, получает операции …ByKey. В примере слайда три питомца (p. 1233):

# one value per key: merge the values with the function
pets = sc.parallelize([("cat", 1), ("dog", 1), ("cat", 2)])
pets.reduceByKey(lambda x, y: x + y)    # [('cat', 3), ('dog', 1)]
# all the values of a key; the pairs sorted by key
pets.groupByKey()     # [('cat', [1, 2]), ('dog', [1])]
pets.sortByKey()      # [('cat', 1), ('cat', 2), ('dog', 1)]
PySpark отдаёт каждую группу groupByKey как итерируемый объект; добавь .mapValues(list), чтобы напечатать её списком, как на слайде.

reduceByKey сливает все значения одного ключа функцией; groupByKey только собирает их, по списку на ключ; sortByKey упорядочивает пары по ключу. Слайд добавляет фразу, в которой и сидит «почему»: "reduceByKey also automatically implements combiners on the map side". Combiner (комбайнер) — это трюк из word count на MapReduce из урока 30: каждая машина сначала сливает значения одного ключа, которые лежат у неё, и по сети едут только частичные результаты. groupByKey так не умеет, потому что должен доставить каждое отдельное значение. Ответ тот же, трафик разный — рис. 1.

Word count из урока 30 занимал страницу на Java. Здесь это три вызова цепочкой над строками hamlet.txt (p. 1234):

# the word count of p. 1234: three transformations, then an action
lines = sc.textFile("hamlet.txt")
counts = lines.flatMap(lambda line: line.split(" ")) \
              .map(lambda word: (word, 1)) \
              .reduceByKey(lambda x, y: x + y)
counts.collect()
# [('be', 2), ('not', 1), ('or', 1), ('to', 2)] on the slide's lines

Читай это как поток данных. flatMap превращает каждую строку в её слова ("to be or" даёт to, be, or); map превращает каждое слово в пару (слово, 1); reduceByKey — это shuffle плюс reduce: частичный счёт слова из каждой партиции едет на машину, отвечающую за это слово, — какую именно, решает хеш ключа, — и там складывается. В примере слайда (be, 2) и (not, 1) оказываются на одной машине, (or, 1) и (to, 2) — на другой. Задание запускает только collect().

Слайд разбивает цепочку на три строки и ничего не ставит в их концах; если набрать так, Python примет первую строку за всю инструкцию и отвергнет следующую. Заканчивай каждую строку обратным слешем, как выше, или оберни всю цепочку в скобки — так оформлены экзаменационные ответы ниже.

Два RDD пар можно соединить по ключам (p. 1235). join возвращает по паре на каждую совпавшую комбинацию, два значения рядом; cogroup возвращает по паре на ключ, со списком значений с каждой стороны:

# join: one output pair per matching (left value, right value)
visits = sc.parallelize([("index.html", "1.2.3.4"),
                         ("about.html", "3.4.5.6"),
                         ("index.html", "1.3.3.1")])
pageNames = sc.parallelize([("index.html", "Home"),
                            ("about.html", "About")])
visits.join(pageNames)
# ('index.html', ('1.2.3.4', 'Home'))
# ('index.html', ('1.3.3.1', 'Home'))
# ('about.html', ('3.4.5.6', 'About'))
# cogroup: one output pair per key, with both lists of values
visits.cogroup(pageNames)
# ('index.html', (['1.2.3.4', '1.3.3.1'], ['Home']))
# ('about.html', (['3.4.5.6'], ['About']))
На слайде (p. 1236) третья строка соединяет visits с pageViews: RDD с предыдущего слайда называется pageNames.

Два посещения index.html и одно имя дают две строки join, но одну строку cogroup. Наконец, "All the pair RDD operations take an optional second parameter for number of tasks" (p. 1236): результат режется на столько партиций, и каждую обрабатывает одна reduce-задача. Слишком мало — кластер простаивает; слишком много — планирование и крошечные выходные файлы стоят больше, чем экономят.

# 5 reduce tasks: the result has 5 partitions
words.reduceByKey(lambda x, y: x + y, 5)

Под капотом: стадии и почему итерации летают

Когда запускается действие, DAG scheduler превращает записанные трансформации в работу для кластера. Слайд перечисляет, что он делает: "General task graphs", "Automatically pipelines functions", "Data locality aware", "Partitioning aware to avoid shuffles" (p. 1237). Его рисунок, перерисованный как рис. 2, показывает все четыре пункта.

Граф режется на стадии (stages) в каждом месте shuffle, потому что shuffle — это барьер: ни одна партиция после него не может начаться, пока не готовы все партиции до него. Внутри стадии узкие операции — каждая входная партиция питает ровно одну выходную (урок 38) — сцепляются в конвейер (pipelining): map и filter над C выполняются одной задачей на партицию, за один проход, и D никогда не сохраняется. Задачи идут туда, где уже лежит их партиция (локальность данных, data locality, как с блоками HDFS). B уже вышло из groupBy, партиционированное по ключу, так что join берёт его как есть, а ещё B закэшировано, поэтому Stage 1 пропускается.

Практическое занятие говорит то же самое в двух видах (pp. 1723–1724). В логическом виде "An RDD is seen as a single dataset", трансформации "form a lineage graph", и "everything is just a plan". В физическом виде "An RDD is split into partitions", "Each partition lives on a worker node", она "processed independently and in parallel", и "Fault tolerance is achieved by recomputing only the lost partitions". В API есть и другие операторы, кроме map и reduce (p. 1238): внешние джойны (outer joins), cogroup, cross (декартово произведение, в PySpark оно называется cartesian), zip, sample, fold и partitionBy — инструмент, на котором держится "partitioning aware".

Почему столбики такие короткие

Hadoop родился, когда "RAM was extremely expensive, so Hadoop was designed to rely heavily on hard disk drives (HDDs) for storage and processing" (p. 1713): каждое MapReduce-задание читает вход из HDFS и пишет выход обратно. Spark появился, когда RAM стала доступной, и "was designed to leverage RAM for in-memory computation, drastically reducing the time required for iterative tasks such as machine learning and interactive queries" (p. 1715). Между ними слайд занятия про HDFS (p. 1714) содержит одно предложение, которое надо исправить, прежде чем его цитировать.

Тот же слайд про HDFS говорит, что NameNode "manages and assigns work to all the DataNodes". На самом деле его работа — метаданные: из каких блоков состоит файл и где они лежат (урок 31).

"It means treating continuous, unbounded streams of incoming data as if they were tables, and applying the same queries and transformations you would use for batch data."

Для HDFS потоковый доступ к данным (streaming data access pattern) означает, что программа читает файл последовательно, от начала до конца, с высокой пропускной способностью: файлы пишутся один раз и много раз читаются батчевыми заданиями, а низкая задержка — не цель.

Второе предложение слайда описывает Structured Streaming, "modern API" со слайда (p. 1719), который рассматривает поток как таблицу, которая всё растёт. HDFS вообще не выполняет запросов: он хранит блоки, а задания MapReduce или Spark их сканируют (урок 31). Ответ могут сверять с напечатанным предложением: знай его, но давай значение для HDFS всякий раз, когда вопрос спрашивает про HDFS.

Рис. 3 ставит числа бенчмарков из лекции на одну шкалу.

K-means и логистическая регрессия — оба классические методы статистики — проходят по одним и тем же данным раз за итерацию и обновляют крошечную модель, центроиды или вектор весов. С данными, закэшированными в памяти, итерация стоит один проход в RAM; цепочкой заданий Hadoop она стоит чтение из HDFS, запуск задания и запись обратно. PageRank выигрывает меньше, потому что каждая итерация всё равно перемешивает ранги по сети. Удвоение числа машин сократило время итерации Hadoop больше чем вдвое (со 171 до 80 s), а у Spark — только с 23 до 14 s: чем короче итерация, тем больше в ней доля постоянных затрат, которые дополнительные машины не делят.

Проверь: 100 TB за 72 мин на 2100 машинах — это около 0.66 GB на машину в минуту; за 23 мин на 207 машинах — около 21.

Последний слайд с бенчмарками — самый сильный: "On-Disk Sort Record: Time to sort 100TB" — Hadoop, 2100 машин, 72 минуты; Spark, 207 машин, 23 минуты; "Also sorted 1PB in 4 hours" (p. 1241, из бенчмарка Daytona GraySort на sortbenchmark.org). 100 TB в память не помещаются, так что дело не только в RAM: треть времени на десятой части машин — это примерно в 30 раз больше данных, отсортированных одной машиной за минуту. Это заслуга самого движка — стадий, конвейеризации, лучшего shuffle.

DataFrame: RDD, которое знает свои столбцы

Лекция вводит DataFrame словарной статьёй (p. 1246):

DataFrame — "1. A distributed collection of rows organized into named columns. 2. An abstraction for selecting, filtering, aggregating and plotting structured data (cf. R, Pandas). 3. Archaic: Previously SchemaRDD (cf. Spark < 1.3)."

Представь DataFrame из pandas, чьи строки разложены по многим машинам, который нельзя изменить на месте и чьи операции ждут действия. Следующий слайд даёт причины (p. 1247): это "A distributed collection of rows with the same schema (RDDs suffer from type erasure)"; он "Can be constructed from external data sources or RDDs into essentially an RDD of Row objects"; он "Supports relational operators (e.g. where, groupby) as well as Spark operations"; и он "Evaluated lazily → unmaterialized logical plan". Стирание типов (type erasure) — довод из Java: во время выполнения RDD из объектов Person не может сказать Spark, какие поля у Person; в Python у RDD из кортежей тоже нет ни имён столбцов, ни типов. DataFrame несёт и то, и другое, поэтому Spark может проверить запрос, компактно хранить строки и оптимизировать план до запуска.

Слайд занятия говорит это одной строкой: "DataFrames, on the other hand, are RDDs with an added schema that defines column names and data types". RDD остаются "Best for unstructured data or custom transformations", а "DataFrames are preferred today because they run much faster, use less memory, are easier to write and maintain, and integrate with SQL and other paradigms/systems" (p. 1725). Скорость берётся из того, что позволяет схема: Spark видит весь запрос и оптимизирует его с помощью Catalyst (урок 40), а лямбда Python в коде на RDD для него — чёрный ящик, который он может только вызвать.

Слайд печатает "data" среди примитивных типов: читай "date". Unions пришли из статьи про Spark SQL; в API, которым ты будешь пользоваться, есть structs, arrays и maps.

Модель данных вложенная (p. 1248): примитивные типы SQL — boolean, integer, double, decimal, string, date, timestamp — и сложные типы, "structs, arrays, maps, and unions", с "First class support for complex data types". Поэтому в экзаменационной таблице в ячейке может лежать список: строка Hospital в экзамене от 30 января 2026 года содержит Heating_Systems = [HS_1, HS2, ...] — столбец типа array.

Запрос можно написать двумя способами (p. 1249): "Relational operations (select, where, join, groupBy) via a DSL", где "Operators take expression objects" и "build up an abstract syntax tree (AST), which is then optimized by Catalyst", — или "Alternatively, register as temp SQL table and perform traditional SQL query strings". Пример на слайде — на Scala, где === — это равенство столбцов; на PySpark он выглядит так:

# female employees per department (p. 1249)
from pyspark.sql import functions as F

(employees
    .join(dept, employees["deptId"] == dept["id"])
    .where(employees["gender"] == "female")
    .groupBy(dept["id"], dept["name"])
    .agg(F.count(employees["name"])))

В подсчёте указана таблица, employees["name"]: если в обеих таблицах есть столбец name, голый count("name") неоднозначен, и Spark его отвергнет.

То, что экзамены называют "SparkQL", — это вот этот API, а экзамен от 30 января 2026 года добавляет к каждому запросу: "Note that you are not allowed to use SQL syntax. Use PySpark instead." Значит, никакого spark.sql("SELECT …") — и, если читать осторожно, никаких строк с SQL-выражениями внутри filter тоже. Занятие показывает один запрос на Python, SQL и Java (p. 1726); его блок на PySpark — скелет любого ответа:

# the PySpark box of p. 1726: session, data, query, action
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("PythonExample").getOrCreate()

Filter: условия — это столбцы

Условие для filter или для его синонима where — это выражение над столбцами: df.Price, df["Pizza Name"] или col("Pizza Name") — для имени с пробелом нужен один из двух последних вариантов. Условия комбинируются через & (и), | (или) и ~ (не), каждое сравнение в своих скобках (ноутбук 2):

# Price above 7.9 and the name Calzone: one row, Calzone
df.filter((df.Price > 7.9) & (col("Pizza Name") == "Calzone")).show()

У фразы ноутбука "N.B. Parenthesis are essential!" есть причина. В Python & связывает сильнее, чем > и ==, так что без скобок он сначала вычисляет 7.9 & col("Pizza Name"), а потом спрашивает, истинен ли столбец, — и запрос до Spark так и не доходит:

# the same filter without parentheses: Python stops before Spark runs
df.filter(df.Price > 7.9 & col("Pizza Name") == "Calzone").show()
# PySparkValueError: [CANNOT_CONVERT_COLUMN_INTO_BOOL] Cannot convert
# column into bool: please use '&' for 'and', '|' for 'or',
# '~' for 'not' when building DataFrame boolean expressions.

Питоновский and даёт ту же ошибку. У текста свои методы: contains("&"), startswith("To"), endswith("one"), like("%on%") с подстановочными знаками SQL, rlike с регулярным выражением; isin([...]) проверяет список значений, а array_contains(df.Ingredients, "Basil") заглядывает внутрь столбца-списка.

«df.filter(df.Price == 7.95) возвращает четыре пиццы по 7.95». Не возвращает ни одной. Столбец FloatType хранит 32 бита, так что 7.95 хранится как 7.949999809265137, а литерал 7.95 — 64-битный double: они никогда не равны. Ноутбук пишет "PAY ATTENTION TO FLOATS!" и сравнивает вместо этого со строкой "7.95" — трюк, который работал в Spark 3 и не работает в Spark 4: в PySpark 4.2 df.Price != "7.95" возвращает все семь пицц. Сравнивай float через > или < или объявляй деньги как DoubleType.

Explode, группировка, агрегация

explode превращает столбец-список в строки: по строке на элемент, все остальные столбцы копируются (ноутбук 1). У семи пицц 3 + 3 + 3 + 3 + 4 + 4 + 1 = 21 ингредиент, так что выходит 21 строка; без alias новый столбец называется col. Это $unwind из MongoDB, из урока 15.

# one row per (pizza, ingredient): 21 rows
exploded_df = df.select(col("Pizza Name"), df.Price,
                        explode(df.Ingredients).alias("Ingredient"))

select оставляет только названные столбцы. withColumn добавляет или заменяет один столбец и оставляет все остальные: df.withColumn("Ingredient", explode(df.Ingredients)) даёт те же 21 строку, но список Ingredients остаётся при них.

groupBy, за которым идёт count() или agg(...), сворачивает строки до одной на ключ (ноутбук 3). agg принимает сколько угодно агрегатных функций, каждая переименовывается через alias: count, sum, avg, max, countDistinct для различных значений и collect_list или collect_set, которые собирают значения группы обратно в список, с дубликатами или без, — обратная операция к explode. HAVING из SQL — это filter после agg, по alias:

# at least four ingredients: Speck & Brie 4, Tonno & Cipolle 4
exploded_df.groupBy("Pizza Name") \
    .agg(count("Ingredient").alias("Number of Ingredients")) \
    .filter(col("Number of Ingredients") >= 4) \
    .show()

Теперь загадка из начала. Тот же ноутбук считает ещё и sum("Price").alias("Sum Price") по каждой пицце на exploded_df. Цена Calzone скопировалась в каждую из трёх строк её ингредиентов, так что сумма — это утроенная цена: код просит «цену, по разу на каждый ингредиент, сложить». Цифры берутся из схемы: 7.95, сохранённое как float, — это 7.949999809265137, а три таких числа, сложенные как double, дают 23.84999942779541. После explode суммируй и считай то, что обозначает каждая новая строка — здесь ингредиенты, на экзамене системы отопления, — и никогда не значение родительской строки, которое explode повторил; его бери через max или агрегируй до explode.

Join

Ноутбук 4 заменяет список внешним ключом — таблицей пицц (Pizza Name, Price, Ingredients_ID), которую ноутбук называет df, а этот урок — pizza_df, — и соединяет её с ingredient_df (Ingredients_ID, Ingredients). Две пиццы ссылаются на IG_7 и IG_8, которых нет в другой таблице, а IG_5 и IG_6 никогда не используются, поэтому каждый тип join даёт своё число строк (табл. 3).

# the inner join of notebook 4: 4 rows, both key columns kept
pizza_df.join(ingredient_df,
    pizza_df.Ingredients_ID == ingredient_df.Ingredients_ID,
    "inner").show()

Join по выражению сохраняет оба ключевых столбца, так что последующий select("Ingredients_ID") останавливается с [AMBIGUOUS_REFERENCE] Reference `Ingredients_ID` is ambiguous. Вместо этого делай join по имени — on="Ingredients_ID", — и Spark оставит один ключевой столбец, поставив его первым; или переименуй столбец до join. Ноутбук называет leftsemi "left inner join": это не так — он возвращает каждую совпавшую пиццу один раз, без столбцов другой таблицы, как WHERE … IN (…) в SQL.

The slides state that "reduceByKey also automatically implements combiners on the map side". Explain what this means and why it matters, and why groupByKey followed by a sum is slower even though it gives the same result. Use the word count as an example.

Показать образец ответа

In the word count, each partition produces pairs (word, 1), and the final count of a word needs all its pairs on one machine, so they must be shuffled across the network by key. reduceByKey(f) applies f inside each partition before the shuffle: a partition that holds "to" a thousand times sends one pair (to, 1000) instead of a thousand pairs — this local pre-aggregation is the combiner of MapReduce. The reducers then merge the partial results with the same f, which is why f must be associative and commutative. groupByKey cannot pre-aggregate, because it must deliver every value of a key to the reducer as a list; the sum happens only after the shuffle. Both give the same counts, but groupByKey moves far more data over the network and can build very large lists on one reducer, so for a reduction reduceByKey is preferred.

У полного ответа четыре части: shuffle как дорогой шаг, частичная агрегация в каждой партиции перед ним, условие на функцию и противопоставление groupByKey. Число делает ответ конкретным, как на рис. 1: когда обе строки слайда в одной партиции, едут 4 значения вместо 6.

Главное

  • RDD получается из sc.parallelize или sc.textFile; трансформации (map, filter, flatMap, reduceByKey, …) возвращают новые RDD и ленивы, действия (collect, count, take, reduce, saveAsTextFile, first) запускают задание.
  • На парных RDD reduceByKey сливает значения по ключу и комбинирует на стороне map, так что по сети едут только частичные результаты; groupByKey везёт каждое значение; join ставит в пары совпавшие значения, cogroup перечисляет их списками; дополнительное целое число задаёт число reduce-задач.
  • DAG scheduler режет задание на стадии в местах shuffle, сцепляет узкие операции в конвейер, запускает задачи рядом с их данными, переиспользует закэшированные партиции и пропускает shuffle для входа, уже партиционированного по ключу; итеративные алгоритмы выигрывают больше всего от данных в памяти, а рекорд сортировки на диске показывает, что быстрее и сам движок.
  • DataFrame — это "a distributed collection of rows organized into named columns", то есть RDD со схемой: ленивый, неизменяемый, вложенный (столбцы-массивы), запрашиваемый через DSL, который экзамены называют SparkQL; экзамен 2026 года запрещает SQL-строки.
  • Экзаменационный рецепт: explode списка, join по имени id, filter, groupBy(id, name).agg(F.f(...).alias(...)), filter по alias вместо HAVING, select; countDistinct для "unique"; чтобы добавить строку, сделай union с DataFrame из одной строки и присвой результат заново.
  • Ловушки: скобки вокруг каждого сравнения, равенство на столбцах float, два столбца с одним именем после join и значение родителя, просуммированное после explode, — 23.85 у Calzone.

    Почему DataFrame появились в Spark 1.3 как переименованный SchemaRDD со слайда (p. 1246), и график, где код на DataFrame в Python работает так же быстро, как в Scala, а код на RDD в Python отстаёт, — причина, стоящая за "DataFrames are preferred today".

  • RDD Programming Guide Документация Apache Spark

    Официальные таблицы трансформаций и действий, "Working with Key-Value Pairs" и "Shuffle operations" — это разделы 1 и 2 этого урока, с тем же word count на Python.

  • Quickstart: DataFrame Документация PySpark

    Создание DataFrame из строк, select, filter, groupBy — и правило, стоящее за каждым вопросом «лениво или энергично»: ничего не выполняется до действия вроде show() или collect().

  • PySpark Live Notebook: DataFrame Apache Spark, на Binder

    Настоящий PySpark в браузере, ничего не надо устанавливать (запуск занимает минуту-другую). Пересобери таблицы больниц, запусти образцы ответов, потом попробуй свои варианты прошлых экзаменов.

  • Functions (pyspark.sql.functions) Документация PySpark

    Все функции, которые используются в agg или filter, — sum, avg, count, count_distinct, collect_set, explode, to_date. Держи её открытой, пока перерешиваешь прошлые экзамены.

Каждая цепочка DataFrame в этом уроке становилась логическим планом ещё до того, как что-то выполнялось. Что Catalyst делает с этим планом — и почему файлы Parquet устроены так, чтобы Spark читал только те столбцы и группы строк, которые нужны запросу?
