CQL: ключ, который решает всё

После этого урока ты будешь читать строку PRIMARY KEY так, как её читает Cassandra, — какие столбцы выбирают узел, какие сортируют строки, — предсказывать, какие SELECT, UPDATE и DELETE она примет, и писать CQL для любого упражнения по Cassandra из прошлых экзаменов.

Практическое занятие просит таблицу машин, "sorted by max_speed in ascending order" (отсортированную по max_speed по возрастанию), и отвечает ключом PRIMARY KEY (car_id, max_speed) и опцией WITH CLUSTERING ORDER BY (max_speed ASC) (p. 1607). Cassandra принимает таблицу без единого слова.

Загрузи девять машин и попроси их все через SELECT * FROM car;. Один запуск напечатал скорости 340, 190, 180, 160, 320, 160, 296, 180, 170. Попроси обещанный порядок, SELECT * FROM car ORDER BY max_speed;, — и Cassandra отказывает: "ORDER BY is only supported when the partition key is restricted by an EQ or an IN."

Ничего не сломано: таблица делает ровно то, что написано в её строке PRIMARY KEY. Прочитай эту строку так, как её читает Cassandra, — и в разделе 6 мы починим таблицу, передвинув один столбец.

Cassandra на одном слайде и keyspace для работы

Слайд добавляет "It's created by Meta". Лекция говорит "Originally designed at Facebook" (p. 410): это одна и та же компания, с 2021 года она называется Meta.

Занятие открывается определением (p. 1548): "Apache Cassandra is a highly scalable, high-performance non-relational, distributed database designed to handle large amounts of data, providing high availability with no single point of failure." Список возможностей (p. 1549) добавляет "Highly and Linearly Scalable", "Quick Response Time", "Flexible Data Storage", "Easy Data Distribution", "BASE Properties" и "Fast Writes".

За каждым утверждением стоит механизм. Мастера нет: любой узел может обслужить любой запрос, и каждая строка скопирована на несколько узлов, так что одна упавшая машина ничего не останавливает. Новый узел забирает свою долю строк, поэтому ёмкость растёт вместе с числом узлов. Запись дописывается в память и в журнал без предварительного чтения, поэтому запись быстрая. Как узлы делят строки — это урок 22; этот урок — про язык, на котором ты с ними разговариваешь. Теорию занятие подытоживает двумя таблицами, которые стоит знать слово в слово:

Действительно ли запись в Cassandra бывает "partial"?

Не внутри одной партиции. Дополнительно, из документации Cassandra, а не со слайдов: INSERT, UPDATE или DELETE, затрагивающий одну партицию, применяется целиком, а logged BATCH в итоге либо применяется полностью, либо не применяется вовсе. От чего Cassandra отказывается — так это от банковской транзакции: изменения нескольких партиций в изоляции. Отвечай таблицей, как она напечатана, а это добавляй, если вопрос открытый. CAP-сторона истории — в уроке 5.

Словарь вложен, как картотечный шкаф. Keyspace — "the outermost container in Cassandra" (p. 1553), внешний контейнер, грубо говоря база данных. Он содержит таблицы (tables) — это column families из лекции: ключевое слово TABLE "can be interchanged with COLUMNFAMILY" (p. 1563). Таблицы содержат строки, строки — столбцы; урок 20 рисует эту картинку, а дальше всё — это CQL, набранный в приглашении cqlsh.

-- p. 1553: a keyspace that keeps three copies of every row
CREATE KEYSPACE population
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};

Прочитай вслух: создать контейнер population; реплицировать каждую строку по простой стратегии, три копии. Карта репликации, стратегия плюс коэффициент (replication factor), — единственное свойство, которое keyspace обязан объявить. На ноутбуке с одним узлом команда всё равно выполняется, с предупреждением: "Your replication factor 3 for keyspace population is higher than the number of nodes 1".

-- p. 1555: the prompt becomes cqlsh:population>
USE population;
-- p. 1555: list the keyspaces (DESCRIBE tables; and
-- DESCRIBE person; do the same for tables, pp. 1558-1559)
DESCRIBE keyspaces;
-- p. 1556: change the properties of a keyspace
ALTER KEYSPACE population
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 2};
-- p. 1556: remove the keyspace and every table in it
DROP KEYSPACE population;

«Набирай код так, как он на слайде». Слайды печатают типографские кавычки, ‘SimpleStrategy’, а некоторые блоки заканчиваются без точки с запятой. cqlsh отвергает фигурные кавычки ("Invalid syntax at line 1, char 48") и ждёт продолжения ввода, пока не увидит ;. Прямые одинарные кавычки и точка с запятой в конце — всегда.

PRIMARY KEY: где живёт строка и в каком порядке

Первая таблица занятия (p. 1558) описывает людей:

-- p. 1558: one partition per person, its rows sorted by age
CREATE TABLE person (
  personal_id text,
  name text,
  age varint,
  birth_date text,
  gender text,
  PRIMARY KEY (personal_id, age)
);

Столбец за столбцом это SQL; последняя строка — нет. Столбцы внутри PRIMARY KEY "have different meaning depending on the order and the brackets" (p. 1560) — смысл зависит от порядка и скобок, — и слайд даёт оба смысла:

Partition key (ключ партиционирования) — "The first value (or set of values) is referred to as the Partition Key(s). It defines how the data is partitioned within the Cassandra nodes." Здесь: personal_id.

Clustering key (ключ кластеризации) — "The second value (or set of values) is named Clustering Key(s). It is used to define the way data is stored within a partition (i.e., the sorting)." Здесь: age.

Механизм: Cassandra хеширует значение partition key, и получившееся число, токен (token), называет узел, который хранит строку. У строк с одинаковым значением partition key одинаковый токен, поэтому они лежат вместе в одной партиции (partition) на одном узле, отсортированные по clustering key. Представь архив: хеш фамилии выбирает здание, а внутри папки стоят по датам.

Составной partition key — это одно значение: (Fiat, 2024) и (Fiat, 2023) — две партиции, возможно на двух узлах. А полный первичный ключ, partition плюс clustering columns, определяет одну строку: две строки с одинаковым полным ключом — это одна и та же строка. Это ловушка из раздела 4.

Список должен начинаться с первого clustering column: при clustering columns year, max_speed порядок (max_speed DESC) сам по себе отвергается: "Missing CLUSTERING ORDER for column year".

Внутри партиции порядок по возрастанию, если таблица не говорит иного (p. 1554):

-- p. 1554's option (printed ASC), here DESC:
-- in each partition, the oldest first
CREATE TABLE person_by_age_desc (
  personal_id text,
  age varint,
  name text,
  PRIMARY KEY (personal_id, age)
) WITH CLUSTERING ORDER BY (age DESC);

Экзамены формулируют ключ словами:

Внутри внутренних скобок — где живёт строка. После них — порядок, в котором строки там стоят. Всё вместе — какая это строка.

Изменение таблицы и то, что изменить нельзя

Остальные команды для таблиц работают как в SQL (pp. 1561–1563), и каждая принимает COLUMNFAMILY вместо TABLE. Занятие добавляет адрес, который его INSERT заполняет в разделе 4:

-- p. 1562: a new column; the existing rows have no value in it
ALTER TABLE person ADD address text;
-- p. 1562: salary, added the same way, is dropped again
ALTER TABLE person DROP salary;
-- p. 1563: remove every row, keep the table
TRUNCATE TABLE person;
-- p. 1563: remove the table itself
DROP TABLE person;

Ключ — единственное, чего ALTER не может коснуться: ALTER TABLE person DROP age; отвечает "Cannot drop PRIMARY KEY column age", так что неправильный ключ означает новую таблицу и копирование данных. И вот что значит "Schema is flexible" (p. 1551) в CQL: каждая таблица объявляет свои столбцы, строка может бесплатно оставить пустым любой неключевой столбец, а ALTER TABLE добавляет столбец в любой момент.

Чтение: что может сказать WHERE

Запрос, для которого построена Cassandra, называет партицию (p. 1567):

-- one hash, one node, one partition: Francesco's rows
SELECT * FROM person WHERE personal_id = 'FRNTRZ95E12F675T';

Cassandra хеширует значение, идёт к узлу, которому принадлежит токен, и читает одну партицию. WHERE, который не называет партицию, — это вопрос, на который один хеш не ответит, и занятие сразу пробует такой (p. 1568), "Let's retrieve people by gender":

-- refused: gender is neither a key column nor indexed
SELECT * FROM person WHERE gender = 'Male';

cqlsh отвечает: "Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING". Точное описание: чтобы найти мужчин, Cassandra пришлось бы прочитать каждую строку на каждом узле и выбросить большую часть.

"To solve the issue, it’s necessary to query with respect to the attributes included in the partition key AND to create a secondary index on gender."

Достаточно чего-то одного. С индексом на gender SELECT * FROM person WHERE gender = 'Male'; выполняется без partition key; с полным partition key и без индекса условию на gender нужен ALLOW FILTERING, дешёвый внутри одной партиции.

Занятие само так делает (p. 1611): CREATE INDEX car_price ON car (price);, затем SELECT * FROM car WHERE price = 35000; — без partition key. Обе формы работают на Cassandra 5.0.9. Напечатанный запрос падает ещё раньше: в gender = "male" двойные кавычки делают male именем столбца (SyntaxException), а хранится значение 'Male'. Экзамен могут проверять по напечатанной фразе: знай её как напечатано, а в своих ответах пиши «либо — либо».

Следующий слайд (p. 1569) перечисляет правила. По порядку, каждое со своей причиной:

  1. Назови каждый столбец partition key, через = или IN: "WHERE clauses must include ALL components of the partition key". Половина составного ключа токена не даёт.
  2. Ограничивай clustering columns префиксом, в их порядке; только последний может быть диапазоном. "To filter on a later clustering key, all preceding clustering key(s) must be specified". Строки отсортированы по clustering columns, так что такой префикс — один непрерывный срез; всё остальное означает прыжки. Пропусти один — и cqlsh скажет, например, "PRIMARY KEY column "max_speed" cannot be restricted as preceding column "year" is not restricted".
  3. Никакого OR. "Clustering Keys constraints producing non-contiguous results will fail": диапазон с дыркой посередине запросить нельзя. Условия соединяются только через AND; красная ручка ниже объясняет, почему собственный пример слайда падает.
  4. Любому другому столбцу нужен вторичный индекс (secondary index), и тогда только =. "To include additional fields in the query, it is necessary to create a secondary index." Диапазону по индексированному столбцу, gender > 'A', всё равно нужен ALLOW FILTERING.
  5. ALLOW FILTERING отключает правила, "although it is not recommended due to bad execution-time performance": Cassandra читает и отбрасывает, поэтому стоимость растёт с таблицей, а не с ответом.

"Clustering Keys constraints producing non-contiguous results will fail (i.e., age < '30' OR age > '33')."

Пример падает по другой причине: в CQL вообще нет OR, так что это синтаксическая ошибка ещё до проверки любых правил ключа, а '30' в кавычках — текст, а не varint. И "will fail" слишком категорично: IN не непрерывен — и выполняется.

На Cassandra 5.0.9 напечатанное условие останавливается на "no viable alternative at input 'OR'". С ключом (brand, max_speed, car_id) условие WHERE brand = 'Ferrari' AND max_speed IN (296, 340) выполняется и пропускает 320 посередине. Экзамен могут проверять по напечатанному правилу: знай его вместе с примером — и почему пример падает.

SELECT без WHERE, SELECT * FROM car;, не требует ALLOW FILTERING: он читает всё, но ничего не отбрасывает. Индекс из правила 4 создаётся как на слайде (p. 1564), и упражнение с машинами использует его так (p. 1611):

-- p. 1611: an index on a column that is not part of the key
CREATE INDEX car_price ON car (price);
-- p. 1611: now legal, without partition key or ALLOW FILTERING
SELECT * FROM car WHERE price = 35000;
-- p. 1610: a range on that column: only ALLOW FILTERING helps
SELECT * FROM car WHERE price > 100000 ALLOW FILTERING;
-- p. 1565: remove an index you no longer need
DROP INDEX person_address;
Слайд называет индексы "one of the most important elements of a table". Почему же лекция предпочитает «фабрику индексов» (index factory)?

Дополнительно, из документации Cassandra: вторичный индекс локален. Каждый узел индексирует только свои строки, поэтому запрос только по индексированному столбцу опрашивает все узлы. Для маленькой таблицы это нормально — и это ровно та «further operation», которую ждёт экзамен. На большом кластере лучше масштабируется ответ лекции: "cassandra is an index factory" (p. 431, урок 20) — вторая таблица, partition key которой — искомый столбец, так что запрос снова сводится к одному хешу (раздел 5).

Грамматика скобок на трёх узлах

Девять машин в таблице car (car_id, brand, year, max_speed, price). Выбери PRIMARY KEY и смотри, как перемещаются строки: partition key размещает каждую партицию на узле (игрушечный хеш, не тот, что у Cassandra), clustering columns сортируют строки внутри неё. Затем выбери или впиши условие WHERE: вердикт и сообщение — те, что выдаёт настоящий узел Cassandra 5.0.9, проверенные на этой самой таблице. Строки, которые запрос возвращает, подкрашены; строки, которые он читает и потом выбрасывает, зачёркнуты.

  1. Ключ (car_id, max_speed), как на занятии, и «(без WHERE)». Прежде чем смотреть: сколько получится партиций и сколько строк в каждой? В каком порядке их вернёт SELECT * FROM car;?
    Что должно получиться

    Девять партиций по одной строке, по три на узел: car_id уникален, так что каждая машина — отдельная партиция, и max_speed нечего сортировать. Строки возвращаются партиция за партицией, в порядке токенов — в порядке хешей, а не скоростей. Игрушечный хеш даёт один порядок, настоящий — другой; поэтому запуск из загадки и напечатал 340, 190, 180, …

  2. WHERE brand = 'Ferrari'. Переключайся между ((brand, year), max_speed, car_id) и (brand, year, max_speed, car_id). Предскажи, какой ключ отвечает без ALLOW FILTERING и сколько узлов опрашивает каждый, когда ты включишь ALLOW FILTERING.
    Что должно получиться

    (brand, year, …): brand — весь partition key, так что узел 3 читает одну партицию и возвращает три строки, отсортированные по году, а затем по скорости. ((brand, year), …): brand — половина partition key, токена нет, и cqlsh требует ALLOW FILTERING; с ним все три узла читают все девять строк, чтобы вернуть три. Те же столбцы, другие скобки: скобки решают, где живёт строка.

  3. Ключ (brand, year, max_speed, car_id), WHERE brand = 'Fiat' AND max_speed = 160. Предскажи ответ cqlsh, затем почини запрос двумя разными способами.
    Что должно получиться

    "PRIMARY KEY column "max_speed" cannot be restricted as preceding column "year" is not restricted" — правило 2. Способ первый: назови ещё и год, brand = 'Fiat' AND year = 2023 AND max_speed = 160, и узел 1 прочитает ровно одну строку. Способ второй: включи ALLOW FILTERING; узел 1 по-прежнему отвечает один, потому что partition key задан, но читает всю партицию Fiat и отбрасывает одну из трёх строк.

  4. Ключ (brand, max_speed, car_id): попробуй price = 35000, затем price > 100000. Предскажи, потом создай индекс на price и предскажи снова. Напоследок выбери ключ (brand, max_speed): сколько машин хранится?
    Что должно получиться

    Без индекса обоим нужен ALLOW FILTERING. С индексом price = 35000 выполняется: каждый узел смотрит в свой локальный индекс, и возвращаются две машины, а price > 100000 всё равно требует ALLOW FILTERING — вторичный индекс отвечает только на равенство (pp. 1610–1611). С ключом (brand, max_speed) остаются только 7 из 9 машин: два Fiat делят (Fiat, 160), две Lancia делят (Lancia, 180), и более поздний INSERT перезаписал более ранний. Ключ, который не идентифицирует машину, теряет машины — молча.

"If any further operation is required, write its CQL code" спрашивает ровно об этом: входит ли столбец из WHERE в ключ? Если нет, дополнительная операция — CREATE INDEX для равенства; для диапазона работает только ALLOW FILTERING — напиши его и скажи, что он не рекомендуется.

Запись: каждая запись — upsert

Занятие вставляет человека (p. 1566):

-- p. 1566: Francesco, aged 26
INSERT INTO person (personal_id, address, age,
                    birth_date, gender, name)
VALUES ('FRNTRZ95E12F675T', 'Via Milano 12', 26,
        '12-05-1995', 'Male', 'Francesco Terzani');

Столбцы и значения соответствуют по порядку; столбцы первичного ключа обязательны, остальные можно опустить. USING <option> из шаблона на слайде не объясняется: он задаёт время жизни, USING TTL 86400 — значения истекут через сутки, или временную метку записи (документация Cassandra).

Теперь вопрос, которого не задаёт ни один слайд: а если строка с таким первичным ключом уже есть? В SQL — ошибка дублирующегося ключа. В Cassandra — ничего: INSERT перезаписывает перечисленные столбцы и сохраняет остальные. INSERT — это upsert: update или insert, и решает только первичный ключ. Cassandra никогда не читает перед записью — отчасти поэтому запись быстрая; чтобы отвергать дубликаты, об этом надо попросить: INSERT … IF NOT EXISTS, лёгкая транзакция (lightweight transaction, не со слайдов).

UPDATE следует той же логике (p. 1570): "The WHERE clause must include all components of the primary key (partition key and clustering keys). You cannot update or change primary key values." Опусти age — и cqlsh ответит "Some clustering keys are missing: age"; попробуй SET age = 27 — и он ответит "PRIMARY KEY part age found in SET part". Если строки с таким ключом нет, UPDATE её создаёт.

-- p. 1570 as printed: "Let's update Francesco's address"
UPDATE person
SET address = 'Via Milani 13'
WHERE personal_id = 'FRNTRZ95E12F675T' AND age = 32;

"Let’s update Francesco’s address to ‘Via Milani 13’" — WHERE personal_id = ‘FRNTRZ95E12F675T’ AND age = 32;

Франческо был вставлен с age 26 (p. 1566); команда, которая его обновляет, заканчивается на AND age = 26;.

age входит в первичный ключ, так что (FRNTRZ95E12F675T, 32) — другая строка, которой не существует. UPDATE создаёт её только с адресом и оставляет Франческо на Via Milano 12: на Cassandra 5.0.9 в партиции после этого две строки, и cqlsh не сообщает ни о какой ошибке. Виджет ниже это воспроизводит. Экзамен могут проверять по напечатанному слайду: знай, что его команда пишет вторую, строку-призрак, и пиши тот ключ, который у Франческо на самом деле.

Ловушка upsert

Таблица person с занятия, пустая. Выбери её PRIMARY KEY, выбери команду и нажми «Выполнить»; под командой видно, что после неё возвращает SELECT * FROM person WHERE personal_id = 'FRNTRZ95E12F675T';, а ниже — ответы cqlsh до этого момента. Смена ключа начинает таблицу заново.

  1. Ключ (personal_id, age). Выполни «INSERT Francesco, age 26», затем предскажи: сколько строк будет после «INSERT Francesco ещё раз, age 32»? Потом переключи ключ на (personal_id) и выполни те же две команды.
    Что должно получиться

    Две строки: age входит в ключ, так что (…, 32) — новая строка. С ключом (personal_id) — одна строка: второй INSERT перезаписал age и name, а адрес от первого остался, потому что upsert пишет только перечисленные столбцы. Ни разу никакой ошибки.

  2. Начни заново с (personal_id, age). Выполни INSERT с занятия (p. 1566) и его UPDATE (p. 1570). Обновился ли адрес Франческо?
    Что должно получиться

    Нет. UPDATE называет age = 32 — ключ, которого нет ни у одной строки, — поэтому создаёт вторую строку только с адресом; у Франческо остаётся Via Milano 12. cqlsh оба раза отвечает OK. Главная мысль: только первичный ключ решает, в какую строку попадёт запись, и Cassandra никогда не проверяет, существует ли эта строка.

  3. Выполни «DELETE … по partition key». Сколько строк уходит? Затем попробуй «UPDATE … без age» и «DELETE … AND age = 26» при каждом ключе.
    Что должно получиться

    Все строки Франческо: один partition key удаляет всю партицию (p. 1571). «UPDATE … без age» при (personal_id, age) отвергается с "Some clustering keys are missing: age" — UPDATE должен называть одну строку. При (personal_id) age вообще не ключевой столбец, поэтому DELETE, который его называет, отвергается: "Non PRIMARY KEY columns found in where clause: age".

DELETE нужно меньше (p. 1571): "You must specify the full partition key in the WHERE clause of a DELETE. Instead, Clustering Key(s) are not strictly required." Ширина WHERE решает, сколько уходит:

-- p. 1571: the whole partition, every row of Francesco
DELETE FROM person WHERE personal_id = 'FRNTRZ95E12F675T';
-- one row of the partition
DELETE FROM person
WHERE personal_id = 'FRNTRZ95E12F675T' AND age = 26;
-- one column of one row: the address becomes null
DELETE address FROM person
WHERE personal_id = 'FRNTRZ95E12F675T' AND age = 26;

Удаление само по себе — тоже запись: маркер, надгробие (tombstone), скрывает старые значения до более поздней очистки (урок 22). Несколько записей могут ехать и вместе (p. 1572):

-- the template of p. 1572, filled in:
-- one request, one timestamp for every statement
BEGIN BATCH
  INSERT INTO person (personal_id, age, name)
    VALUES ('RSSMRA80A01F205X', 45, 'Maria Rossi');
  UPDATE person SET address = 'Via Roma 1'
    WHERE personal_id = 'RSSMRA80A01F205X' AND age = 45;
  DELETE FROM person
    WHERE personal_id = 'FRNTRZ95E12F675T';
APPLY BATCH;

"A set of INSERT, UPDATE, and DELETE operations can be organized in a BATCH. In that way, they are executed one after another with a single command."

Одной командой — да; одна за другой — нет. Все команды батча несут одну и ту же временную метку, так что их порядок ничего не решает: когда две из них пишут одну ячейку, удаление побеждает запись, а большее значение побеждает меньшее, где бы они ни стояли.

На Cassandra 5.0.9 батч, в котором DELETE строки идёт перед INSERT той же строки, не оставляет строки — удаление побеждает, хотя шло первым, — а INSERT … name 'b' и за ним UPDATE … SET name = 'a' оставляют 'b'. Экзамен могут проверять по напечатанной фразе, например в вопросе «верно/неверно»: знай её как напечатано и знай, что команды отправляются вместе и применяются как одна запись.

Батч оправдывает себя в другом: когда один факт хранится в двух таблицах, logged batch (по умолчанию) записывает обе копии или ни одной — это дополнительно, из документации Cassandra, и это клей для раздела 5.

Типы, скрипты и JOIN, которого нет

Сначала типы (p. 1577): "text, varint, float, double, Boolean, etc.", плюс int, date, timestamp и uuid, который заполняет функция uuid() (p. 1609). Два вида особенные. Коллекция (collection) хранит несколько значений в одном столбце: list<T> (упорядоченный, дубликаты разрешены), set<T> (уникальные значения), map<K, V>. Слайд показывает список:

-- p. 1577: a column that holds a list of e-mails
CREATE TABLE test (id int PRIMARY KEY, email list<text>);
-- p. 1577: append to the list; a set takes {'x'}, a map {'k': 1.5}
UPDATE test SET email = email + ['a@polimi.it'] WHERE id = 1;

Пользовательский тип (user-defined type) — именованная запись, используемая как тип столбца; "it is necessary to define the data type before using it" (p. 1578). Упражнение с машинами определяет feature (p. 1608):

-- p. 1608: a feature has a name and a description
CREATE TYPE feature (
  name text,
  description text
);
Слайд говорит, что frozen необходим для любого пользовательского типа. Cassandra 5.0 отвергает только случай с коллекцией: Non-frozen UDTs are not allowed inside collections. На экзамене всё равно пиши frozen.
-- p. 1608: a list of features, the type frozen
ALTER TABLE car ADD features list<frozen<feature>>;

"A frozen data type can only be overwritten; it can't be edited anymore" (p. 1608): значение хранится одним блоком. DESCRIBE TYPE feature; его проверяет; ALTER TYPE и DROP TYPE меняют или удаляют (p. 1578). Набор инструментов дополняют три команды консоли cqlsh — не команды CQL (pp. 1573–1575):

-- p. 1575 (path quoted): run every statement of a file, as if typed
SOURCE 'D:/Program Files/Cassandra/Queries/query_1.txt';
-- p. 1573 (path quoted): query results go to the file until CAPTURE off;
CAPTURE 'D:/Program Files/Cassandra/Outputs/output.txt';
-- p. 1574: one line per column, for wide rows; EXPAND off; stops it
EXPAND on;

cqlsh> SOURCE D:/Program Files/Cassandra/Queries/query_1.txt;

Путь — это строка в одинарных кавычках: SOURCE 'D:/Program Files/Cassandra/Queries/query_1.txt';. То же касается CAPTURE, напечатанного без кавычек (p. 1573).

cqlsh 5.0.9 отвечает на форму без кавычек "Improper SOURCE command." — с пробелом в пути или без, — а на её близнеца с CAPTURE — "Improper CAPTURE command."; в кавычках обе работают, включая пробелы и обратные слеши. Само занятие берёт путь в кавычки (pp. 1610 и 1612). SOURCE принёс целый балл 11 февраля 2025 года и часть балла 6 июня 2024 года: бери путь в кавычки. Экзамен могут проверять по напечатанной форме: узнавай её, но пиши кавычки.

Наконец, слайд, которого все ждут, "FOREIGN KEY (?)" (p. 1576): "In Cassandra there is no concept of FOREIGN KEYS and/or relationships, if you want any cross-table check to be performed, you have to manage it by yourself." Причина — снова ключ: две таблицы размещают свои строки по двум разным partition keys, на разных узлах, так что джойн был бы разговором между машинами на каждую строку. Вместо этого (p. 1551): "Data is denormalized and duplicated for query efficiency", и метод лекции (урок 20): "Start from queries, then design the data model" (p. 430); "cassandra is an index factory" (p. 431). Экзамен про пазлы от 30 мая 2025 года ищет покупки по пазлу и по городу или стране покупателя — две таблицы, каждая покупка записывается в обе:

Одна таблица на запрос: его условия равенства становятся partition key, его порядок — clustering key, а каждый возвращаемый им столбец копируется внутрь.

Автосалон от начала до конца

Практическое занятие (pp. 1606–1612) — это полный экзаменационный скрипт на одной таблице. Сначала keyspace и таблица:

-- p. 1606: the keyspace of the exercise
CREATE KEYSPACE car_dealer
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};
-- p. 1607: "sorted by max_speed in ascending order"
CREATE TABLE car (
  car_id uuid,
  brand text,
  max_speed varint,
  price float,
  consumption_lt_per_km float,
  PRIMARY KEY (car_id, max_speed)
) WITH CLUSTERING ORDER BY (max_speed ASC);

DESCRIBE car_dealer; проверяет keyspace (p. 1606). После USE car_dealer; и столбца feature из раздела 5 — добавленного и снова удалённого, "As we do not want to deal with complex fields" (p. 1609), — занятие вставляет машину со сгенерированным ключом:

-- p. 1609: uuid() generates the unique car_id
INSERT INTO car (car_id, brand, max_speed, price, consumption_lt_per_km)
VALUES (uuid(), 'Ferrari', 320, 200000.00, 30.00);

Остальные данные приходят из файла, SOURCE '<path_to_your_folder>/car_data.txt'; (p. 1610). Лекция файл не показывает; в запусках, которые здесь цитируются, было девять машин: три Ferrari, три Fiat и три Lancia — те же девять, что в виджете. Запросы со слайдов (pp. 1610–1612) дают:

-- p. 1610: "cost more than 100'000": a range, so ALLOW FILTERING (3 Ferraris)
SELECT * FROM car WHERE price > 100000 ALLOW FILTERING;
-- p. 1611: "exactly 35'000 (without using ALLOW FILTERING)": an index first
CREATE INDEX car_price ON car (price);
-- p. 1611: then the equality (a Fiat and a Lancia)
SELECT * FROM car WHERE price = 35000;
-- p. 1611: the sum of all prices: 805000, printed 8.05e+05 for a float
SELECT SUM(price) FROM car;
-- p. 1612: count the Ferraris and store the result in ferrari_count.txt
CAPTURE '<path_to_folder>/ferrari_count.txt';
CREATE INDEX car_brand ON car (brand);
SELECT COUNT(*) FROM car WHERE brand = 'Ferrari';
CAPTURE off;

Ни один из агрегатов не называет партицию, поэтому оба опрашивают все узлы, и cqlsh добавляет предупреждение "Aggregation query used without partition key". В файл попадают count, 3, и это предупреждение; пока захват включён, на экране написано только "Now capturing query output to …".

Возвращаемся к загадке

Прочитай ключ со слайда (p. 1607) так, как его читает Cassandra. car_id — partition key, так что каждая машина — отдельная партиция, а max_speed сортирует строки партиции, в которой одна-единственная строка. SELECT * FROM car; обходит партиции в порядке токенов — в порядке хешей, отсюда 340, 190, 180, — а ORDER BY отвергается, потому что сортирует только внутри партиций, которые называет WHERE. Починка переносит один столбец в partition key:

-- the cars of each brand, sorted by speed: brand decides the node
CREATE TABLE car_by_brand (
  brand text,
  max_speed varint,
  car_id uuid,
  price float,
  PRIMARY KEY (brand, max_speed, car_id)
) WITH CLUSTERING ORDER BY (max_speed ASC);
-- 296, 320, 340: one partition, already in order
SELECT * FROM car_by_brand WHERE brand = 'Ferrari';

car_id остаётся в конце ключа, чтобы он по-прежнему идентифицировал машину: без него два Fiat с одинаковой максимальной скоростью были бы одной строкой. Когда партиция названа, работает и ORDER BY: ORDER BY max_speed DESC даёт 340, 320, 296. Экзамен продолжает использовать шаблон занятия — "Personal_ID as the partition key and Phone Number as the clustering key, ordering the table based on the Phone Number" (6 сентября 2024), — и там порядок настоящий: шеф-повар с двумя телефонами — это одна партиция из двух отсортированных строк.

Прошлые экзамены: шесть упражнений, пять шаблонов

Первое — разобранное полностью. ER от 6 июня 2024 года отслеживает стихийные бедствия: Person (Personal ID, Name, Surname, Postal Code) — родитель Paramedic, Firefighter и Policeman (Policeman ID, Rank), ISA (P, O). Вопросы в стиле экзамена

Пять упражнений из прошлых экзаменов в напечатанной формулировке, каждое после той части ER, которую оно использует, с баллами, как в задании; затем два теоретических вопроса. Официальных решений нет: каждый ответ на CQL ниже был выполнен на узле Cassandra 5.0.9 с тестовыми строками, в которых есть ловушки. Сначала напиши свой ответ.

Exam of 6 Sep 2024, exercise 5 (restaurant). ER: Person (Personal_ID, Name, Surname, Birth Date, Phone Number) is the parent of Owner, Customer, Waiter and Chef (Hiring Date); Head Chef (Head Chef Since) is a Chef.

"Consider the Chef table. Write a Cassandra script to perform the operations listed below. Create the Chef table, with Personal_ID as the partition key and Phone Number as the clustering key, ordering the table based on the Phone Number. (1.5 PT) Write a CQL query to collect the chef whose name is "Riccardo". If any further operation is required, write its CQL code. (1 PT) Create a Custom data type named "contact" that contains the name, surname, and phone number of the chef (1.5 PT)"

Показать образец ответа 
CREATE KEYSPACE restaurant
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};
USE restaurant;

CREATE TABLE chef (
  personal_id text,
  phone_number text,
  name text,
  surname text,
  birth_date date,
  hiring_date date,
  PRIMARY KEY (personal_id, phone_number)
) WITH CLUSTERING ORDER BY (phone_number ASC);

-- name is not part of the key: the further operation is an index
CREATE INDEX chef_name ON chef (name);
SELECT * FROM chef WHERE name = 'Riccardo';

CREATE TYPE contact (
  name text,
  surname text,
  phone_number text
);
-- optional, to use it: a list of contacts of the chef
ALTER TABLE chef ADD contacts list<frozen<contact>>;

Without the index, SELECT * FROM chef WHERE name = 'Riccardo' ALLOW FILTERING; also works, but it scans the table and is not recommended.

Три подвопроса проверяют три вещи: форму со скобками вместе с порядком кластеризации, индекс как "further operation" для неключевого столбца и определение типа. Телефонные номера — текст (ведущие + или 0 должны сохраниться). На тестовых данных Риккардо с двумя номерами вернулся двумя строками одной партиции, отсортированными по номеру: здесь порядок кластеризации что-то значит.

Exam of 11 Feb 2025, Cassandra exercise (Formula 1). ER: Person (Personal_ID, Name, Surname, Birth_Date, Gender) is the parent of Spectator (Favourite_Team), Team Owner and Team Member, ISA (T, E).

"Consider the spectator entity. Write a CQL statement to create its corresponding Cassandra Table using Favourite_Team as a clustering key and Name as an additional partition key (1 PT)." "Write a CQL statement to return a list of all the spectators whose name is Bill, whose age is over 65, and whose favourite team is "Ferrari". Besides the query, write any additional CQL statements only if it's strictly necessary. (2 PT)" "Write the CQL command to perform a set of statements by loading them from a file located in "D:\Cassandra\Scripts\statement.txt". (1 PT)"

Показать образец ответа 
CREATE TABLE spectator (
  personal_id text,
  name text,
  favourite_team text,
  surname text,
  birth_date date,
  gender text,
  PRIMARY KEY ((personal_id, name), favourite_team)
);

-- over 65 on the day of the exam (11/02/2025): born before 11/02/1960
SELECT * FROM spectator
WHERE name = 'Bill' AND favourite_team = 'Ferrari'
  AND birth_date < '1960-02-11'
ALLOW FILTERING;

SOURCE 'D:\Cassandra\Scripts\statement.txt';

No additional statement is strictly necessary. personal_id is unknown, so the partition key is incomplete, and age is a range on a column outside the key: ALLOW FILTERING is unavoidable. An index on name (allowed on one part of a composite partition key) would narrow the scan, but the query would still need ALLOW FILTERING because of the range.

Ключевое здесь — "additional partition key": name идёт во внутренние скобки рядом с personal_id. В ER нет возраста, поэтому он вычисляется из Birth_Date; оговори это допущение. Оба утверждения проверены на Cassandra 5.0.9: без ALLOW FILTERING запрос отвергается даже с индексом на name; с ним из пяти тестовых зрителей возвращается только Билл 1955 года рождения, болеющий за Ferrari. Путь можно писать и с прямыми слешами; важны кавычки.

Полный ответ показывает одну таблицу на запрос, искомый атрибут как partition key, clustering key, который сохраняет уникальность строк (иначе две покупки перезапишут друг друга), и денормализованные столбцы. Отдельные таблицы для города и для страны — тоже правильный ответ. Если партиция одной страны становится слишком большой, в partition key можно добавить временную корзину (time bucket), например ((country, buy_year), …).

Explain the roles of the partition key and of the clustering key of a Cassandra table. Which conditions can the WHERE clause of a SELECT contain without ALLOW FILTERING, and why does Cassandra impose these rules?

Показать образец ответа

The primary key has two parts. The partition key, the first element (or the columns in the inner brackets), is hashed into a token that decides on which nodes the row is stored: all rows with the same partition key form one partition on the same replicas. The clustering key, the remaining columns, decides how the rows are sorted inside the partition (WITH CLUSTERING ORDER BY sets ASC or DESC). Without ALLOW FILTERING, a SELECT that restricts the partition key must restrict every one of its columns with = or IN, so Cassandra can compute the token and go to the right node. Clustering columns may be restricted only as a prefix in their declared order, with a range only on the last one, because then the result is one contiguous slice of the sorted partition; OR does not exist. Any other column needs a secondary index and an equality condition, and such a query may omit the partition key, at the price of asking every node. ALLOW FILTERING lifts the rules, but makes Cassandra read and discard rows, so its cost grows with the size of the table.

Полный ответ называет обе роли, три допустимых вида условий и причину каждого: хеш — для partition key, отсортированное хранение — для префикса clustering columns, поиск на каждом узле — для индекса. Цитировать определения со слайда (p. 1560) — безопасно.

Which statements about CQL are true? Select all that apply.

  • The clustering key decides on which node a row is stored. Это partition key; clustering key сортирует строки внутри партиции (p. 1560).
  • With PRIMARY KEY ((a, b), c) and no index, the clause WHERE a = 1 is rejected unless ALLOW FILTERING is added. Правило 1 со слайда (p. 1569): "WHERE clauses must include ALL components of the partition key"; половина составного ключа токена не даёт.
  • A secondary index makes range conditions (<, >) on the indexed column legal without ALLOW FILTERING. Индекс отвечает только на равенство: "most comparison operators require the additional statement ALLOW FILTERING" (p. 1568), и price > 100000 требует его и после CREATE INDEX car_price.
  • An INSERT fails if a row with the same primary key already exists. INSERT — это upsert: он перезаписывает перечисленные столбцы без ошибки.
  • With PRIMARY KEY (a, b, c) and no index, the clause WHERE a = 1 AND c = 2 is rejected unless ALLOW FILTERING is added. c ограничен, а предшествующий clustering column b — нет (правило 2).
  • A DELETE that names only the partition key removes every row of that partition. Слайд (p. 1571): clustering key "not strictly required"; без него уходит вся партиция.

Проверь себя

У таблицы PRIMARY KEY ((city, year), month, day). Какое условие WHERE выполняется без ALLOW FILTERING?

  • city = 'Milan' AND month = 5 Partition key — это (city, year): без year нет токена.
  • city = 'Milan' AND year = 2025 AND day = 3 day ограничен, а month, clustering column перед ним, — нет: "PRIMARY KEY column "day" cannot be restricted as preceding column "month" is not restricted".
  • city = 'Milan' AND year = 2025 AND month >= 5 Весь partition key, затем префикс clustering columns с диапазоном на последнем столбце: один непрерывный срез.
  • year = 2025 AND month = 5 AND day = 3 Нет city, так что партицию не найти.

У таблицы person PRIMARY KEY (personal_id, age) и одна строка ('X', 26) с адресом. Ты выполняешь INSERT INTO person (personal_id, age, name) VALUES ('X', 26, 'Ann');. Что произойдёт?

  • cqlsh сообщит о дублирующемся первичном ключе В Cassandra такой ошибки нет: она никогда не читает перед записью.
  • Появится вторая строка ('X', 26) Две строки с одинаковым полным ключом — это одна и та же строка.
  • Строка заменится: адрес станет null Upsert пишет только перечисленные столбцы; адрес сохраняется.
  • Существующая строка получит имя 'Ann' и сохранит свой адрес Тот же ключ — та же строка; INSERT перезаписал имя и больше ничего не тронул.

У таблицы car PRIMARY KEY (brand, max_speed, car_id) и вторичный индекс на price. Какие SELECT выполняются без ALLOW FILTERING? Выбери все подходящие.

  • WHERE price = 35000 Равенство по индексированному столбцу: каждый узел смотрит в свой локальный индекс.
  • WHERE price > 100000 Индекс обслуживает только равенство; диапазону нужен ALLOW FILTERING.
  • WHERE brand = 'Fiat' AND max_speed >= 160 Partition key, затем диапазон по первому clustering column: срез одной партиции.
  • WHERE max_speed = 160 Clustering column без partition key: пришлось бы искать в каждой партиции.
  • WHERE brand = 'Fiat' AND price > 20000 Партиция названа, но диапазон по price не может использовать индекс: его надо фильтровать.

Все пять выполнены на Cassandra 5.0.9. Равенство использует индекс, диапазон — никогда.

У Франческо две строки в person, с age 26 и 32. Что удалит DELETE FROM person WHERE personal_id = 'FRNTRZ95E12F675T';?

  • Ничего: не хватает clustering key Для DELETE clustering key "not strictly required" (p. 1571).
  • Обе строки Один partition key называет всю партицию.
  • Только строку с age 26 Ничто в команде не выделяет age 26.
  • Только последнюю записанную строку Порядок записи роли не играет; WHERE называет партицию.

В батче DELETE FROM person WHERE personal_id = 'B';, а за ним INSERT INTO person (personal_id, age, name) VALUES ('B', 1, 'Bo');. Что останется после APPLY BATCH;?

  • Строка Bo, потому что INSERT шёл последним Это прочтение "one after another" со слайда (p. 1572), и оно неверно.
  • Ошибка: батч не может смешивать DELETE и INSERT Собственный шаблон слайда смешивает INSERT, UPDATE и DELETE.
  • Строки для 'B' нет У обеих команд одна временная метка, а при равных метках побеждает удаление, где бы оно ни стояло.
  • Две версии строки Первичный ключ определяет одну строку.

У таблицы с занятия PRIMARY KEY (car_id, max_speed), car_id — uuid, и WITH CLUSTERING ORDER BY (max_speed ASC). Что порядок кластеризации меняет в выводе SELECT * FROM car;?

  • Машины выходят отсортированными по скорости Сортируются только строки внутри одной партиции, а здесь в каждой партиции одна машина.
  • Машины каждой марки выходят отсортированными по скорости brand не входит в ключ; он не играет роли ни в размещении, ни в порядке.
  • SELECT без ORDER BY отвергается SELECT без WHERE разрешён; отвергается как раз ORDER BY.
  • Ничего заметного: партиции выходят в порядке токенов Каждая машина — своя партиция, так что внутри партиции сортировать нечего.

Какая команда выполняет из cqlsh команды, сохранённые в D:\Cassandra\Scripts\statement.txt?

  • SOURCE D:\Cassandra\Scripts\statement.txt; Без кавычек cqlsh отвечает "Improper SOURCE command."
  • SOURCE 'D:\Cassandra\Scripts\statement.txt'; Путь — строка в кавычках; обратные слеши сохраняются как набраны.
  • CAPTURE 'D:\Cassandra\Scripts\statement.txt'; CAPTURE записывает результаты запросов в файл; файл он не выполняет.
  • EXPAND 'D:\Cassandra\Scripts\statement.txt'; EXPAND только включает или выключает вертикальный вывод.

Главное

  • Cassandra — распределённая BASE-база без мастера: без единой точки отказа, с линейным масштабированием и быстрой записью. Знай таблицу ACID/BASE со слайда (p. 1550) и сравнение с реляционными системами (p. 1551).
  • В PRIMARY KEY ((partition key), clustering columns) partition key хешируется, чтобы выбрать узел, clustering columns сортируют строки внутри партиции (WITH CLUSTERING ORDER BY), а весь ключ определяет одну строку.
  • Без ALLOW FILTERING условие WHERE либо называет каждый столбец partition key через = или IN и затем префикс clustering columns, с не более чем одним диапазоном в конце, либо использует = по столбцу со вторичным индексом; OR не существует.
  • INSERT и UPDATE — это upserts: ключ решает, какая строка, и ничего не проверяется, так что неверное значение clustering column пишет строку-призрак. UPDATE нужен полный первичный ключ, и изменить ключ он не может; DELETE нужен partition key, и он удаляет столько, сколько называет его WHERE; BATCH даёт всем своим командам одну временную метку.
  • Ни джойнов, ни внешних ключей: денормализуй, одна таблица на запрос, его равенства — partition key, его порядок — clustering key. Коллекции и frozen пользовательские типы держат связанные значения в одной строке.
  • Команды cqlsh принимают пути в кавычках: SOURCE 'file';, CAPTURE 'file'; … CAPTURE off; и EXPAND on; для широких строк.
