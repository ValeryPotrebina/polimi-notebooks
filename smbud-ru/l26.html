Запросы к Elasticsearch: match, filter, bool и агрегации

После этого урока ты сможешь превратить любую фразу экзамена про Elasticsearch — "includes the words", "removing the ones", "must not affect the final score", "prioritising", "the count for each" — в нужную клаузу запроса bool или в агрегацию terms и заранее предсказать, какие документы и с какими оценками вернутся.

Лекция ищет по санитарным инспекциям нью-йоркских ресторанов — это индекс nyc-restaurants из урока 25 — одним запросом, который собирается в три шага (pp. 604–606). Шаг первый оставляет инспекции между 23 февраля 2020 и 23 февраля 2021: 9510 хитов, у каждого оценка 1.0. Шаг второй выкидывает код нарушения 02G: 8923 хита, всё ещё 1.0. Шаг третий добавляет клаузу, которую слайд подписывает как OR: район (borough) — Queens.

OR может только впустить больше документов; а если прочитать клаузу как условие, она оставила бы один Queens. Запиши свою догадку: сколько будет хитов?

Ответ — 8923, ни больше, ни меньше. Зато лучшая оценка прыгает с 1.0 до 2.487945, и наверх выходит ресторан из Queens. 2.487945 — это 1.0 плюс 1.4879451, оценка совсем другого поиска (p. 597). В последнем разделе мы сложим эти два числа; к тому моменту ты предскажешь их сам.

match: те слова, которые ты имел в виду

Поиск — это один HTTP-запрос к эндпоинту _search индекса с телом в JSON; слайд подписывает строку запроса как "Query", а JSON — как "Body" (p. 595).

# the shape of every search (p. 595)
GET /nyc-restaurants/_search
{
  "query": {
    "match": {
      "FIELD": "TEXT"
    }
  }
}

Прочитай вслух: из nyc-restaurants достань документы, у которых FIELD совпадает с TEXT. Занятие называет match, term и range листовыми клаузами запроса (leaf query clauses) — они "look for a particular value in a specific field", — а bool — составной клаузой (compound query clause): она оборачивает другие, "to combine multiple queries logically" (p. 1641). В SQL лист — это одно условие в WHERE; bool — это AND, OR и NOT вокруг условий.

Первые настоящие поиски лекции — два запроса match. Один, по INSPECTION TYPE, возвращает инспекции, у первой оценка 0.53188044 (p. 596); другой, по району, "BORO": "Queens", возвращает рестораны, у первого оценка 1.4879451 (p. 597). А с "queens" в нижнем регистре полный ответ выглядит так (p. 598):

# the response to a match on "BORO": "queens" (p. 598)
{
  "took" : 0,
  "timed_out" : false,
  "_shards" : { "total" : 1, "successful" : 1, "skipped" : 0, "failed" : 0 },
  "hits" : {
    "total" : { "value" : 0, "relation" : "eq" },
    "max_score" : null,
    "hits" : [ ]
  }
}

Научись читать hits: total.value — сколько документов совпало, а relation говорит, точное это число ("eq") или нижняя граница ("gte"); max_score — лучшая оценка, null, если ничего не нашлось; массив hits перечисляет сами документы, лучшие первыми и по умолчанию не больше 10, у каждого свой _score и сохранённый JSON в _source.

Почему пусто? "Borough (BORO) was mapped as a keyword. A keyword does not have any analyser!" (p. 598). Запрос match пропускает свой текст через анализатор (analyzer) поля: "Whenever a text field is provided, it is analyzed before matching" (p. 1644). На текстовом (text) поле получаются слова в нижнем регистре, и по умолчанию документ подходит, если содержит хотя бы одно из них; на keyword-поле ничего не режется, и всё значение целиком должно побайтно совпасть с сохранённым, вместе с заглавной Q. Как маппинг принимает это решение, показывает урок 25; здесь ты видишь, что оно делает с твоими запросами.

match анализирует свой текст собственным анализатором поля: на text-поле — отдельные слова, на keyword-поле — всё значение целиком.

This will match documents that contain “Daybreak", “Game", or “Company" in the publisher field

В этом индексе publisher — keyword-поле: match ищет один-единственный терм "Daybreak Game Company ", вместе с пробелом в конце, и находит только игры, у которых издатель ровно такой.

Слайд с датасетом указывает тип Publisher как Keyword (p. 1638), и агрегация terms по нему работает (p. 1657), а текстовое поле её бы отвергло; у keyword "does not have any analyser" (p. 598). Фраза верна только для текстовых полей. Экзамен могут сверять с напечатанной заметкой: знай, что в ней сказано, и что для keyword-поля это неверно.

Сколько слов должно совпасть?

Параметр operator решает, сколько проанализированных слов нужно документу: OR, "at least 1 word among the ones returned by the analyzer", — это "the DEFAULT"; AND требует "all the words" (p. 1646). Занятие пробует оба на своих видеоиграх из Steam, индекс steam_overviews (p. 1647):

# the AND variant of p. 1647: overview contains free, to and play
GET /steam_overviews/_search
{
  "query": {
    "match": {
      "overview": {
        "query": "free-to-play",
        "operator": "and"
      }
    }
  }
}

Анализатор режет "free-to-play" на free, to и play: с "or", как в запросе слайда, совпадает 61 игра; с "and" — 35. Лучшая оценка оба раза 1.4712923 (p. 1648): верхняя игра содержит все три слова, а её оценка — сумма по ним, ей не с чего измениться. Оператор решает, кто проходит, а не какую оценку получит прошедший.

Опции живут внутри объекта поля, рядом с "query"; когда опций нет, хватает компактной формы, как в задании "Extract all games which tags field contains the "Free-to-Play" tag" (p. 1665):

# games whose tags contain free, to or play (p. 1665)
GET /steam_overviews/_search
{
  "query": {
    "match": {
      "tags": "Free-to-Play"
    }
  }
}

Одно поле на match и подсчёт без документов

Назови два поля в одном match — и Elasticsearch откажет: "[match] query doesn't support multiple fields, found [SCORE] and [BORO]", статус 400 — "You can only match 1 field at time" (p. 600). Два условия — это две клаузы внутри bool (раздел 3). Когда важно только число, то же тело отправляют в _count (p. 599):

# how many inspections scored 13 (p. 599)
GET /nyc-restaurants/_count
{
  "query": {
    "match": {
      "SCORE": 13
    }
  }
}

Ответ — "count" : 32930: ни хитов, ни оценок. Это число ещё вернётся в разделе 4.

Точные условия и контекст фильтра

Для точного значения у занятия есть запрос term, который возвращает "documents that contain an exact term in a provided field". Тот же слайд предупреждает: "DO NOT use term queries for text fields. Remember that text fields are analyzed" (p. 1649).

# games published by exactly "Ubisoft " (p. 1649)
GET /steam_overviews/_search
{
  "query": {
    "term": {
      "publisher": {
        "value": "Ubisoft "
      }
    }
  }
}

Пробел внутри "Ubisoft " — не опечатка. Издатели в этом датасете заканчиваются пробелом — сохранённая игра выглядит как "publisher": "Daybreak Game Company " (p. 1640), — а term сравнивает байты: без пробела ничего не совпадёт. Компактная форма { "term": { "publisher": "Ubisoft " } } — это ответ занятия на задание "Extract all the games which publisher is "Ubisoft"" (p. 1664). Рис. 1 показывает, от чего защищает предупреждение про текстовые поля.

Два параметра "must be added within the field, together with the value parameter" (p. 1651): case_insensitive (по умолчанию false) позволяет term не различать регистр, а boost "is a float number that multiplies the relevance score of a query" — пригодится, когда оценки нескольких клауз складываются.

# "Ubisoft " in any case, with the parameter of p. 1651
GET /steam_overviews/_search
{
  "query": {
    "term": {
      "publisher": {
        "value": "ubisoft ",
        "case_insensitive": true
      }
    }
  }
}

Третий лист, range, принимает границы gt, gte, lt и lte и "usually employed with numerical fields or dates" (p. 1650):

# published in the last ten days, score doubled (p. 1650)
GET /steam_overviews/_search
{
  "query": {
    "range": {
      "publish_date": {
        "gte": "now-10d/d",
        "lte": "now",
        "boost": 2.0
      }
    }
  }
}

В индексе Steam нет поля publish_date (p. 1638 перечисляет пять полей): слайд показывает только синтаксис. "now-10d/d" — это арифметика дат (date math): точка отсчёта, now; шаг назад на десять дней, -10d; округление до дня, /d (p. 1652).

e.g., now +1d /M, now -1Y /Y, 2022.07.28 II +2M /M

Без пробелов и с настоящими символами: now+1d/M, now-1y/y, 2022-07-28||+2M/M. Годы — строчная y, а "II" на слайде означает две вертикальные черты, ||.

Арифметика дат в Elasticsearch знает единицы y, M, w, d, h (или H), m и s: заглавная M — месяцы, строчная m — минуты, а Y нет вовсе, поэтому now-1Y отвергается. Опорная дата должна быть в формате даты этого поля, а формат по умолчанию читает 2022-07-28, но не 2022.07.28. Округление /M ведёт к началу месяца для gte и lt и к его концу для gt и lte — а не «к ближайшей» единице, как сказано на слайде. Экзамен могут сверять с формулировкой слайда: знай её, а пиши рабочий синтаксис.

Два вопроса: насколько хорошо или подходит ли вообще

"By default, Elasticsearch sorts matching search results by Relevance Score, which measures how well each document matches a query" (p. 1642) — сегодня это оценка BM25, наследница TF-IDF из урока 24. Не у каждого условия есть «насколько хорошо». Слайд лекции про фильтры перечисляет пять свойств (p. 601): "Exact match", "For fields that are not analyzed", "No relevance", "The filter is either satisfied or not", "Cacheable". Его пример заворачивает term в filter внутри bool (p. 602):

Слайд подписывает этот запрос как "IN Query". term — это равенство из SQL; а IN из SQL со списком значений — это запрос terms, который на слайдах не встречается.
# inspections with violation code 04M, unscored (p. 602)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "filter": {
        "term": {
          "VIOLATION CODE": "04M"
        }
      }
    }
  }
}

8711 хитов, "max_score" : 0.0 и "_score" : 0.0 у каждого хита. Занятие называет два мира (p. 1643). Контекст запроса (query context) спрашивает "How well does this document match this query clause?": он решает, подходит ли документ, и оценка релевантности IS computed. Контекст фильтра (filter context) спрашивает "Does this document match this query clause?": он решает то же самое, но оценка IS NOT computed; он "Applied with the filter or must_not parameter". Рис. 2 пропускает одну клаузу через оба.

Зачем держать два контекста? Ответ «да/нет» не зависит ни от других клауз, ни от статистики индекса, поэтому Elasticsearch может сохранить его как битовое множество и переиспользовать в следующем запросе, а работу по подсчёту оценки он пропускает. Это и есть "It's more efficient than doing only queries" из лекции (p. 608). Фильтр — это ещё и способ попросить вообще без оценки, как в задании "Extract all games which publisher is exactly "Lag Studios" without computing the relevance score" (p. 1667):

"For fields that are not analyzed" описывает типичный фильтр, а не правило: filter — это контекст, и занятие само фильтрует через match по текстовому полю (p. 1678).
# publisher exactly "Lag Studios ", no score (p. 1667)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "publisher": "Lag Studios " } }
      ]
    }
  }
}

Последний фильтр лекции — prefix: документы, где есть слово, начинающееся с заданной строки (p. 607).

# descriptions with a word starting with "flies" (p. 607)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "filter": {
        "prefix": {
          "VIOLATION DESCRIPTION": "flies"
        }
      }
    }
  }
}

Описание первого хита начинается с "Filth flies": префикс проверялся слово за словом на проанализированном текстовом поле, а не на значении целиком. Сам префикс, как и term, не анализируется: "Flies" ничего бы не нашёл. В ответе стоит "value" : 10000, "relation" : "gte" — не меньше десяти тысяч хитов. Elasticsearch считает точно только до 10000, если его не попросить считать дальше (справка из документации Elasticsearch).

bool: четыре клаузы, два вопроса

У настоящих вопросов несколько условий, а правило одного поля запрещает упаковать их в один match. Лекция отвечает скелетом из трёх массивов, у каждого свой смысл (p. 603): must — AND, must_not — NOT, should — OR. Четвёртый массив, filter, — это то место, где стояли фильтры самой лекции (pp. 602, 607); занятие сводит правило для каждого в таблицу (p. 1653):

  • must: "The query must appear in matching documents and it will contribute to the score."
  • filter: "The query must appear in matching documents. However, unlike must the score of the query will be ignored."
  • should: "The query should appear in the matching document. If so, it will contribute to the score. If should is the only clause included, at least one of the conditions must be satisfied."
  • must_not: "The query must not appear in the matching documents. The scoring is ignored."

Четыре клаузы раскладываются по двум вопросам (рис. 3): обязан ли документ подходить под клаузу и добавляет ли клауза что-то к его оценке?

Каждый массив содержит список клауз — "Each of the clauses described may contain multiple conditions" (p. 1654), — а запрос может использовать "all or just a few of the clauses" (p. 1655):

# Multiplayer games by exactly "Ubisoft ", Action first (p. 1655)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Multiplayer" } }
      ],
      "filter": [
        { "term": { "publisher": "Ubisoft " } }
      ],
      "should": [
        { "match": { "tags": "Action" } }
      ]
    }
  }
}

Читай по клаузам. Тег Multiplayer: обязателен и оценивается. Издатель ровно "Ubisoft ": обязателен, без оценки. Тег Action: не обязателен, но его оценка прибавляется, поэтому игры с Action поднимаются выше. _score хита — это сумма оценок его клауз must и тех клауз should, под которые он подошёл, каждая умножена на свой boost; filter и must_not ничего не добавляют.

Рядом с must или filter клауза should никогда не убирает документ: она только добавляет оценку.

Эта вторая жизнь should и есть "prioritizing" занятия — "Extract all games which tags field contains the "Free-to-Play" tag, prioritizing those whose developer is "Daybreak Game Company"" (p. 1666):

# Free-to-Play games, Daybreak's first (p. 1666)
GET /steam_overviews/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Free-to-Play" } }
      ],
      "should": [
        {
          "term": {
            "developer": {
              "value": "Daybreak Game Company "
            }
          }
        }
      ]
    }
  }
}

"should": [ {} ] OR

should — это OR только в запросе bool, где нет ни must, ни filter. Рядом с must или filter её клаузы необязательны: они добавляют свою оценку подошедшим документам и никогда не убирают документ.

Это показывает собственная сборка лекции — загадка этого урока: клауза с подписью OR оставила число хитов на 8923 (pp. 605–606) и только подняла лучшую оценку. Таблица занятия формулирует правило: "If should is the only clause included, at least one of the conditions must be satisfied" (p. 1653). Экзамен могут сверять с напечатанной подписью: знай, что лекция называет should словом OR, и когда это верно.

Оба виджета ищут по двенадцати блюдам из табл. 1 — она наша, в стиле ресторана с экзамена 6 Sep 2024. Пробеги глазами описания и рецепты: в заданиях надо будет предсказывать.

Где стоит клауза

Четыре клаузы над блюдами из табл. 1. Поставь каждую в must, filter, should или must_not — или не ставь никуда. Ты видишь запрос, а под ним все блюда: сначала хиты, лучшая оценка первой, с долей оценки, которую дала каждая клауза; потом, пунктиром, невернувшиеся блюда и причина. Оценки считаются здесь по BM25 (k1 = 1.2, b = 0.75) — функции оценки по умолчанию в современном Elasticsearch — на этих двенадцати документах и округляются до двух знаков; range даёт постоянную оценку 1.0, как на слайде (p. 604).

  1. Начни с клаузы про salmon в must (кнопка «Начать заново»). Пока ничего не трогаешь, предскажи: если перенести её в filter, какие блюда исчезнут и что станет с их оценками? Потом перенеси.
    Что должно получиться

    Ничего не исчезает: возвращаются те же четыре блюда с лососем. Их оценки (1.31, 1.21, 1.04, 0.91) все становятся 0.00, и список откатывается к порядку индекса. Это и есть то единственное, ради чего построен виджет: перенос клаузы из must в filter никогда не меняет набор вернувшихся документов, только её долю в оценке, которая падает до нуля. Порядок до переноса — это работа BM25: в Salmon salad "salmon" встречается дважды; у Salmon tartare самое короткое описание.

  2. Убери клаузу про salmon и поставь "stir boil" одну в should. Сколько хитов? Теперь верни клаузу про salmon в must: предскажи число хитов и блюдо наверху.
    Что должно получиться

    В одиночку should — это OR: семь блюд, в рецепте которых есть stir или boil, первым Trofie al pesto (оба слова, короткий рецепт). С клаузой про salmon в must хитов становится четыре, по числу блюд с лососем, — should больше ничего не решает, — и наверх выходит Salmon pasta с 0.91 + 1.75 = 2.66, потому что в её рецепте есть оба слова. Grilled salmon и Salmon salad остаются, с долей should, равной 0.

  3. С salmon в must поставь "butter" в must_not, а потом в filter. Предскажи оба результата до переключения.
    Что должно получиться

    must_not: Grilled salmon исчезает («исключено must_not»), а три остальных сохраняют ровно свои оценки — отрицание ничего не добавляет. filter: противоположный набор, один Grilled salmon, всё ещё 1.04, а butter даёт 0. Та же клауза, та же проверка на вхождение, противоположный смысл — и ни в одном из мест она не оценивает.

  4. С salmon в must поставь "price > 10" в must, потом перенеси в filter. Может ли измениться порядок хитов?
    Что должно получиться

    В must Salmon salad (9.50) уходит, а три остальных получают ровно по 1.00: 2.21, 2.04, 1.91. В filter возвращаются те же три с 1.21, 1.04, 0.91 — в том же порядке. Клауза, которая даёт всем хитам одинаковую оценку, не может их переставить; она только тратит работу на подсчёт. Вот почему условию «да/нет» место в filter.

"Filter and Query combination"

Лекция подводит итог выигрышу в трёх строках (p. 608): "You can combine filter and queries", "It's more efficient than doing only queries", "You can increase the relevance of a document at query time". Но её пример подписывает клаузы так, что на экзамене это собьёт тебя с толку.

# the lecture's "Filter and Query combination" (p. 609)
GET /nyc-restaurants/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "SCORE": "20"
          }
        },
        {
          "term": {
            "BORO": {
              "value": "Manhattan"
            }
          }
        }
      ]
    }
  }
}

"match": { "SCORE": "20" } labelled Query, and "term": { "BORO": { "value": "Manhattan" } } labelled Filter — both inside "must": [ ]

Обе клаузы стоят в must, поэтому обе выполняются в контексте запроса и обе оцениваются. Условие, задуманное как фильтр, идёт в свой собственный массив, "filter": [ … ], рядом с must.

Ответ показывает цену: "max_score" : 1.9322574 на 3935 хитов (p. 609). Точное совпадение по числу даёт постоянную оценку 1.0, как range на слайде (p. 604) (это посчитано, а не напечатано), так что около 0.93 лучшей оценки приходит от клаузы с подписью Filter. Если требуется "the condition on the borough must not affect the final score", такая структура нарушает требование. Экзамен могут сверять с напечатанными подписями: знай их и знай, куда идёт настоящий фильтр.

Ещё один трюк с адресом (p. 610): "Elasticsearch allows to search in multiple index at the same time". /_search ищет по всем индексам, index_1,index_2/_search — по списку, а prefix*/_search — по всем индексам, имя которых начинается с префикса.

Считаем, не читая: агрегации

Лекция начинает с SQL (p. 611): SELECT score, count(*) FROM nyc-restaurants GROUP BY score превращается в

# inspections per score, SQL's GROUP BY (p. 611)
GET /nyc-restaurants/_search
{
  "size": 0,
  "aggs": {
    "score_groups": {
      "terms": {
        "field": "SCORE"
      }
    }
  }
}

Читай построчно. "size": 0: не присылать ни одного документа — "size=0 means we don't want actual documents, just the aggregation results" (p. 1656). "aggs": агрегации, сосед "query" на одном уровне. "score_groups": имя, которое ты выбираешь сам, и ответ его повторит. terms: бакетная агрегация (bucket aggregation) — по одному бакету на каждое различное значение SCORE, у каждого свой doc_count. Ответ (p. 612):

# the first four buckets of the response (p. 612)
"aggregations" : {
  "score_groups" : {
    "doc_count_error_upper_bound" : 0,
    "sum_other_doc_count" : 184789,
    "buckets" : [
      { "key" : 12, "doc_count" : 41375 },
      { "key" : 13, "doc_count" : 32930 },
      { "key" : 10, "doc_count" : 21892 },
      { "key" : 11, "doc_count" : 21330 },
      …

В бакете 13 лежат 32930 инспекций — тот самый _count из раздела 1. Бакеты приходят отсортированными по doc_count, самый большой первым. А "sum_other_doc_count" : 184789 говорит, что 184789 инспекций попали в бакеты, которые вообще не вернулись: агрегация terms возвращает только 10 самых больших бакетов, если не увеличить её собственный size (справка из документации Elasticsearch). Так что запрос со слайда — это GROUP BY с ORDER BY count DESC LIMIT 10. "doc_count_error_upper_bound" : 0 говорит, что счётчики точные; на индексе с несколькими шардами они могут быть приблизительными.

«С "size": 0 не вернётся ни одного бакета». Нет. size верхнего уровня — это число хитов, по умолчанию 10, и 0 их отбрасывает. Число бакетов — это size внутри terms, тоже 10 по умолчанию. Фраза занятия "The size parameter defines how many results are returned in the aggregation" (p. 1656) смешивает одно с другим; а её скобка — "size=0 means we don't want actual documents, just the aggregation results" — это точный смысл параметра верхнего уровня.

Лекция перечисляет четыре семейства агрегаций: "Metrics aggregations", "Bucket aggregations", "Pipeline aggregations", "Matrix aggregations" (p. 613). Занятие даёт три, с определениями (p. 1656). Метрические агрегации (metric aggregations) "calculate metrics from field values (count, min, max, avg, sum)". Бакетные "group documents into buckets, based on field values (terms), ranges (range), or other criteria (filters, etc..)". Конвейерные агрегации (pipeline aggregations) "take input from other aggregations instead of documents or fields". Четвёртое семейство лекции, matrix, считает статистики сразу по нескольким полям; современная документация знает три семейства занятия и относит эти статистики к метрическим (справка). Знай оба списка: материалы курса печатают оба.

На 64 играх Steam агрегация занятия games_per_publisher даёт "Daybreak Game Company " 3 игры и "sum_other_doc_count": 44 (p. 1657): десяти крупнейшим издателям принадлежат всего 20 игр. Набор инструментов дополняют три комбинации. Первая: запрос отбирает документы, а агрегация группирует уже их: "Aggregations can be combined with regular queries to filter the data and then perform the aggregation" (p. 1658). Упражнение занятия "For each developer, extract the count of the games whose tags field contains the "Free-to-Play" tag" (p. 1668):

  "query": {
    "bool": {
      "must": [
        { "match": { "tags": "Free-to-Play" } }
      ]
    }
  },
  "aggs": {
    "f2p_per_devs": {
      "terms": {
        "field": "developer"
      }
    }
  }

Тот же слайд добавляет N.B.: "term aggregations only work on keywords (for texts, one can use field_name.keyword to use the keyword version of the field)" (p. 1658) — его "term aggregations" — это агрегации terms из кода, а не запрос term. Вторая: несколько агрегаций могут стоять рядом в одном aggs, каждая — свой GROUP BY (p. 1659); с "size": 0 в ответе "hits": [] и "max_score": null, а total.value всё равно сообщает 64. Третья: бакетная агрегация может нести вложенные агрегации (sub-aggregations), "computed for each aggregation by considering the documents within each one of them" (p. 1660):

    "games_per_publisher": {
      "terms": {

Несмотря на своё имя, вложенная агрегация усредняет цену, а не игры: в pandas это было бы df.groupby("publisher")["price"].mean(), урезанное до десяти самых больших групп. От фразы экзамена к запросу

В семи из девяти прошлых экзаменов есть задача по Elasticsearch на 3 или 4 балла, всегда по одной сущности из ER-диаграммы этого экзамена и всегда в два хода. Сначала: "Provide the complete mapping of the index for the considered entity (i.e., field name, field type, the structure of the mapping, etc.)", с заготовкой "PUT …" или "PUT /", которую надо дописать. Потом один или два запроса. Структуру показывает собственное упражнение занятия на маппинг: "Define the full mapping describing a Person with 10 shards and 3 replicas" (p. 1663).

# a Person index with 10 shards and 3 replicas (p. 1663)
PUT /people
{
  "settings": {
    "number_of_shards": 10,
    "number_of_replicas": 3
  },
  "mappings": {
    "properties": {
      "personal_id": { "type": "keyword" },
      "name": { "type": "text" },
      "surname": { "type": "text" },
      "birth date": {
        "type": "date",
        "format": "yyyy-MM-dd"
      },
      "address": { "type": "text" },
      "eye_color": { "type": "keyword" },
      "height": { "type": "integer" }
    }
  }
}

settings нужен в ответе только тогда, когда экзамен спрашивает про шарды или реплики; mappings, properties и по одной записи с её type на каждый атрибут — вот что хочет каждый экзамен. Выбирай каждый тип под запросы, которые идут дальше, — полный список в уроке 25: text для всего, что ищут по словам, keyword для значения, которое сравнивают целиком или по которому считают, integer или double для чисел, date с его format, boolean для атрибута Yes/No. Подсчёт terms по текстовому полю падает, так что поле, по которому будешь считать, должно быть keyword. А запросы дальше следуют маленькому разговорнику (табл. 2).

Одна фраза, разобранная по клаузам

Экзамен 11 Feb 2025 был про гонки Formula 1. Его Pilot — это Team Member, ISA (P, E), а тот — Person, ISA (T, E): Personal_ID, Name, Surname, Birth_Date и Gender приходят от Person; Championships_Won и Career (Textual) — собственные атрибуты пилота (Career в задании напечатан дважды). Потом (2 PT): "Write a query to return male pilots who won at least 10 championships and whose career must include the words "Champion" and "Car", assigning a higher score to the ones whose career includes the word "Young"." Режь по клаузам. "Male" и "at least 10 championships" — условия «да/нет», без всякого «насколько хорошо»: filter. "Must include the words" — про слова: две клаузы match в must. "Assigning a higher score": should.

# male pilots, 10+ championships, Champion and Car; Young first
GET /pilots/_search
{

    "bool": {
      "must": [
        { "match": { "career": "Champion" } },

      ],
      "filter": [
        { "term": { "gender": "Male" } },
        { "range": { "championships_won": { "gte": 10 } } }

      "should": [
        { "match": { "career": "Young" } }
      ]
    }

}

Задание не говорит, что пол и чемпионства не должны влиять на оценку, так что must для них тоже был бы верен: term по keyword-полю и range дают всем хитам одинаковую оценку, которая не может поменять порядок, — это показывает задание 4 первого виджета. filter говорит ровно то, что ты имеешь в виду, и стоит дешевле.

Тринадцать упражнений занятия и загадка

Занятие заканчивается тринадцатью упражнениями на индексе employees50k, атрибуты которого оно перечисляет вместе с типами (p. 1669): Address, Designation, FirstName, Gender, Interests, LastName и MaritalStatus как Text; Age и Salary как Integer; DateOfJoining как Date.       "must": [

  1. "… whose interests contains one or more words among "Paragliding", "Kayaking", and "Playing". The more words are found, the higher the final score." (p. 1676)

{

  5. "… whose designation is "Manager" or "Delivery Manager" and whose salary is not higher than 150’000. Assign a higher score to those whose interests includes "Blogging"." (p. 1680)

    Проверь себя 
    GET /employees50k/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "Designation": {
              "query": "Delivery Manager",
              "operator": "or"
            }
          }
        },

      ],

        { "match": { "Interests": "Blogging" } }
      ]

    "Not higher than" — это lte. OR-match оставляет любую должность со словом "delivery" или "manager", а это покрывает оба значения — и любого другого менеджера. Строгая форма называет два значения: { "terms": { "Designation.keyword": ["Manager", "Delivery Manager"] } } в must, тот самый IN из раздела 2. Опция идёт внутрь объекта поля, рядом с "query": "match": { "Interests": { "query": "Paragliding Kayaking Playing", "operator": "or" } }. Поле называется Interests (p. 1669).

Записанный рядом с именем поля, "operator" выглядит как второе поле, и Elasticsearch отвечает как на слайде (p. 600): "[match] query doesn't support multiple fields". Назад к загадке

Explain the difference between query context and filter context in Elasticsearch. Which clauses of a bool query run in each context, and when would you place a condition in filter context?

Показать образец ответа

In query context a clause answers the question "how well does this document match?": it decides whether the document matches and also computes a relevance score, and the hits are sorted by that score. A leaf query placed directly under query, and the must and should clauses of a bool query, run in query context. In filter context a clause answers only "does this document match?": it decides membership, but no score is computed. The filter and must_not clauses of a bool query run in filter context. A condition belongs in filter context when it must hold but should not influence the ranking — an exact category, a date range, or any condition that the task says "must not affect the final score". Filtering is also cheaper: no scoring is done, and the yes/no result can be cached and reused by later queries.

Полный ответ называет два вопроса (насколько хорошо / подходит ли), говорит, что в одном оценка считается, а в другом нет, раскладывает все четыре клаузы — must_not тоже работает в контексте фильтра, и об этом часто забывают, — и даёт причину фильтровать: ранжирование против чистого условия, плюс кэш.

A bool query with a must clause (a range on the inspection date) and a must_not clause returns 8923 hits, all with score 1.0. A should clause, a term on the borough "Queens", is added. Which statement describes the new response?

  • Fewer hits: only the inspections in Queens. Так поступил бы второй must или filter. Рядом с must клауза should необязательна.
  • More hits: those in the date range or in Queens. Клауза should не может впустить документы, не прошедшие must: каждый хит по-прежнему обязан попасть в диапазон.
  • The same 8923 hits; the Queens inspections get a higher score and move to the top. Когда есть must, should только добавляет свою оценку подошедшим под неё документам: лекция печатает 8923 хита и лучшую оценку 2.487945 (p. 606).
  • The same hits with the same scores. Подошедшая клауза should "will contribute to the score" (p. 1653): инспекции из Queens получают по 1.4879451 каждая.
Показать образец ответа

The same 8923 hits. Because the query has a must clause, the should clause is optional: it removes and adds no document, but it adds its score to the inspections in Queens, which rise to the top (best score 1.0 + 1.4879451 = 2.487945).

Это собственный пример лекции (pp. 604–606). Слайд подписывает should как "OR", и ловушка — ответ «больше хитов». На экзамене за неверные закрытые ответы могут снимать баллы, так что если сомневаешься, вспомни: should — это OR, только когда она одна.

Проверь себя

В запросе bool есть match по описанию в must и range по цене в must. Ты переносишь range в filter. Что произойдёт?

  • Часть хитов исчезнет: filter строже, чем must. Оба массива обязательны: документ в любом случае должен подходить под клаузу, так что набор не меняется.
  • Те же хиты в том же порядке, каждая оценка на 1.0 меньше. range в контексте запроса даёт каждому хиту одинаковые 1.0; в filter — 0. Если вычесть одну и ту же величину из каждой оценки, порядок сохранится — задание 4 первого виджета.
  • Те же хиты, но в совсем другом порядке. Порядок мог бы измениться, только если бы range давал разным хитам разные оценки; он даёт всем 1.0.
  • Все оценки станут 0. Перестаёт оценивать только клауза в filter; match в must по-прежнему оценивает.

Запрос bool содержит только клаузы should. Какие утверждения верны? Выбери все подходящие.

  • Чтобы вернуться, документ должен подойти хотя бы под одну из них. "If should is the only clause included, at least one of the conditions must be satisfied" (p. 1653).
  • Возвращаются все документы индекса; клаузы только меняют их порядок. В одиночку should — это OR: документ, не подошедший ни под одну клаузу, не возвращается. Переставлять, ничего не убирая, should умеет рядом с must или filter — среди документов, которые впустили те клаузы.
  • При прочих равных документ, подошедший под две клаузы, получает больше, чем подошедший под одну. Оценки подошедших клауз should складываются.
  • У каждого хита оценка 0. should работает в контексте запроса: она оценивается. Оценку 0 дают filter и must_not.

В одиночку should — это оценивающий OR; рядом с must или filter — бонус.

Текстовое поле description блюда содержит "Salmon fillet with butter and herbs". Что вернёт { "term": { "description": "Salmon" } }?

  • Ошибку: term на текстовых полях запрещён. Elasticsearch выполняет его без всяких жалоб. "DO NOT use" — это совет, а причина — молчаливый пустой ответ.
  • Это блюдо, с оценкой 0. Оценку 0 даёт фильтр. А здесь блюдо вообще не находится.
  • Ни одного хита. Анализатор сохранил слово salmon в нижнем регистре; match перевёл бы в нижний регистр и запрос и нашёл бы блюдо (рис. 1).

В ответе со слайда (p. 607) стоит "total" : { "value" : 10000, "relation" : "gte" }. Что ты знаешь о числе совпавших документов?

  • Совпало ровно 10000. Точный счёт выглядел бы как "relation" : "eq".
  • Найти можно было не больше 10000. Elasticsearch находит каждое совпадение; он только перестаёт точно их считать.

  • Запрос упал после 10000 документов. Ничего не упало: хиты на месте, лучшие первыми.

Ты отправляешь "size": 0 и агрегацию terms без size внутри по keyword-полю с 25 различными значениями. Что вернётся?

  • Ни одного хита; 10 бакетов, самые частые значения первыми; документы остальных 15 значений посчитаны в sum_other_doc_count. size верхнего уровня отбрасывает хиты; число бакетов — это size у terms, по умолчанию 10.
  • Ни хитов, ни бакетов, потому что size равен 0. size верхнего уровня считает хиты, а не бакеты.
  • 25 бакетов, по одному на значение. Только с "size": 25 или больше внутри terms.
  • 10 хитов и 25 бакетов. "size": 0 значит «без хитов», а бакеты останавливаются на 10.

Какие запросы Elasticsearch отвергнет с ошибкой? Выбери все подходящие.

  • match, в объекте которого названы два поля, SCORE и BORO. "[match] query doesn't support multiple fields", статус 400 (p. 600).
  • Запрос term на "Male" по текстовому полю Gender. Он выполняется и молча ничего не возвращает: ни ошибки, ни хита.
  • Агрегация terms по текстовому полю вроде description. Текстовые поля не хранят одного значения на документ: "term aggregations only work on keywords" (p. 1658).
  • size и aggs, записанные внутри query. Внутри query Elasticsearch ждёт тип запроса; size им не является (p. 1681).

Опасен промах без ошибки: term по текстовому полю возвращает пустой список, который выглядит как настоящий ответ.

В запросе bool есть клауза filter и клауза should, а must нет. Какие блюда вернутся?

  • Те, что подходят и под filter, и под should. Когда есть filter, should необязательна — ровно как с must.
  • Те, что подходят под filter или под should. Фильтр обязателен: блюдо, которое его не прошло, выбывает.
  • Все блюда, подходящие под filter; те, что подходят ещё и под should, идут первыми. Фильтр решает, кто входит, с оценкой 0, а единственную оценку даёт клауза should.
  • Только блюда, подходящие под should, с оценкой от фильтра. Фильтр никогда не оценивает.

Главное

  • Поиск — это GET /index/_search с телом в JSON, где query — одна листовая клауза (match, term, range, prefix) или bool, который их объединяет; _count возвращает только число, а один match смотрит на одно поле.
  • match анализирует свой текст анализатором поля: на текстовом поле — слова, соединённые через OR (или через AND с "operator": "and"), на keyword-поле — всё значение целиком. term никогда не анализирует, и на текстовых полях ему не место; range принимает gt, gte, lt, lte и арифметику дат вроде now-10d/d.
  • Контекст запроса (query context) спрашивает, насколько хорошо документ подходит, и считает оценку; контекст фильтра (filter context) спрашивает только, подходит ли он, даёт 0 и может кэшироваться. filter и must_not работают в контексте фильтра.
  • must — обязательный оценивающий AND; filter — обязательный AND без оценки; must_not — NOT без оценки; should — бонус, а OR только тогда, когда стоит одна. Оценки складываются — 2.487945 = 1.0 + 1.4879451 на слайде (p. 606), — а boost умножает долю клаузы.
  • "size": 0 и именованная агрегация terms — это GROUP BY со счётчиками: возвращаются 10 самых больших бакетов, остальные только в sum_other_doc_count; запрос сначала фильтрует, вложенные агрегации выполняются внутри каждого бакета, а текстовое поле нужно считать через field.keyword.
  • Задача на экзамене — это маппинг, написанный под следующие за ним запросы, а потом фразы, переведённые клауза за клаузой: "includes the words" → must, "removing" → must_not, "must not affect the final score" → filter, "prioritising" → should, "the count for each" → terms.
