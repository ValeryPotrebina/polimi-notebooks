База данных без запросов: key-value хранилища и Redis

После этого урока ты сможешь объяснить, зачем существует база данных, которая отвечает только на вопрос «что лежит под этим ключом?», сказать, что Redis добавляет к этой идее и чем он не является, объяснить, почему один поток делает каждую команду атомарной и при этом быстрой, и выбрать под задачу нужный из семи типов данных.

"Every 1/10 second delay resulted in 1% loss of sales." Это цифра Amazon (p. 343): каждая десятая доля секунды задержки стоит 1 % продаж; на том же слайде Google теряет 20 % трафика за полсекунды задержки. Скорость — это деньги.

В 2009 году Сальваторе Санфилиппо пытался масштабировать LLOOGG — анализатор веб-логов в реальном времени, продукт его итальянского стартапа, — и традиционные системы баз данных не справлялись с частью его нагрузок. Он написал собственную базу данных и отказался почти от всего, что даёт реляционная: никакого SQL, никаких join, никаких вторичных индексов, всё хранится в памяти, и один поток выполняет по одной команде за раз. Он назвал её Redis.

Два из этих решений звучат шиворот-навыворот. Как база данных, которая отвечает только на один вопрос — «что хранится под этим ключом?», — может быть спасением, когда реляционная база слишком медленная? И как сервер, который использует одно ядро процессора и выполняет по одной команде за раз, может обходиться вообще без блокировок и всё равно успевать? К концу урока ты ответишь на оба вопроса словами слайдов.

Один ключ, одно значение, один шаг

Лекция открывается картой (p. 342), "Overview – NoSQL Family": "Data stored in 4 types: Document, Graph, Key-value, Wide-column", и в клетке key-value стоят Redis, Amazon DynamoDB, Aerospike и Riak (четыре семейства — в уроке 5). Key-value — самое простое из четырёх, а следующий слайд, "Why is performance important?" (p. 343), объясняет, зачем оно кому-то нужно: ради скорости. Кроме 1 % продаж Amazon и "20% drop in traffic" у Google, там сказано, что при "1-second delay in page-load time" некая "Industrial Group" насчитала "11% fewer page views", "16% decrease in customer satisfaction" и "7% loss in conversions".

Возьми пример с самого слайда — базу данных блога (p. 346, рис. 1). Чтобы показать страницу поста 101, нужны его текст из таблицы blog, имя автора из users и категория из category: три таблицы, связанные внешними ключами. Хранилище ключ-значение держит всю страницу — текст, автора, категорию — как одно значение под одним ключом, post:101, и отдаёт её за один шаг.

Хранилище ключ-значение (key-value store) — база данных, которая хранит каждое значение под уникальным ключом и добирается до него только через этот ключ: "(Business) Key -> Value" (p. 345). Весь её интерфейс: положить значение под ключ, получить значение по ключу, удалить ключ. Значение непрозрачно: хранилище никогда не заглядывает внутрь.

Примеры со слайда (p. 345) — это ключи, которые у бизнеса уже есть: "(twitter.com) tweet id -> information about tweet", "(kayak.com) Flight number -> information about flight", номер счёта в банке, номер товара на Amazon. Большинство запросов к сайту начинается с одного из них — отсюда последняя строка слайда: "Search by ID is usually built on top of a key-value store". В терминах Python хранилище — это dict: d[key] = value, d[key], del d[key] — и никакого цикла по значениям.

«Всё началось в 2004 году, когда Amazon работал на Oracle enterprise edition с кластеризацией и репликацией», — вспоминал в 2017 году Вернер Фогельс, CTO Amazon. База данных не могла «выдержать требования бизнеса к доступности, масштабируемости и производительности», а «подробный разбор того, как мы используем наши базы данных, показал, что их реляционные возможности часто вообще не использовались»: «около 70 процентов операций были вида ключ-значение — использовался только первичный ключ, и возвращалась одна строка». Это было «начало базы данных Amazon Dynamo», опубликованной в 2007 году; Riak из клетки key-value на карте (p. 342) — один из её клонов (p. 411), а в 2012 году появилась DynamoDB от Amazon.

Слайд (p. 346) задаёт очевидный вопрос, "Isn't that just a database?", и перечисляет, что такое реляционная база данных: "Queried using SQL", "Key-based", "Foreign keys", "Indexes", "Joins". Читай этот список как два столбца: у реляционной базы есть все пять пунктов, у хранилища ключ-значение остаётся один — key-based. Ключи есть и там и там, но играют они разные роли. В реляционном блоге первичные и внешние ключи связывают таблицы, индексы позволяют SQL искать по любому столбцу — запрос со слайда, SELECT user_id from users WHERE username = "jbellis", находит пользователя по имени, а не по ключу, — а join собирают страницу обратно. Конспект курса говорит это одной строкой: в хранилище ключ-значение "keys are just used to retrieve a specific value, unlike relational databases where primary and foreign keys are means to do searches and mapping between tables" — ключи только достают конкретное значение, а в реляционной базе первичные и внешние ключи служат для поиска и связи таблиц.

Итак, хранилище ключ-значение от многого отказывается: нет запросов по содержимому значений, нет join, нет вторичных индексов, нет схемы для проверки. Взамен оно покупает стоимость. Поиск по ключу в хеш-таблице занимает один шаг при любом числе ключей, и ничего не нужно разбирать, планировать или собирать. Гонка ниже ставит на это числа.

Гонка поиска: один ключ против дерева и join

Одна и та же запись достаётся тремя способами, пока таблицы растут от тысячи до миллиарда строк. Каждая кривая считает шаги одного поиска и умножает их на стоимость одного шага. Стоимости — принятые порядки величин, а не числа со слайдов: случайный доступ к памяти около 0.1 µs, случайное чтение страницы около 0.1 ms на SSD и 10 ms на вращающемся диске; B-дерево держит 100 ключей на страницу; ничего не кэшируется, если не выбрать RAM. Закрашенная полоса сверху — всё, что медленнее 100 ms, той задержки, которой слайд (p. 343) назначает цену. Обе оси логарифмические: каждая линия сетки в десять раз больше предыдущей.

  1. Оставь «вращающийся диск» и N = 1 млн. Прежде чем что-то трогать: какая кривая останется плоской, когда N вырастет до миллиарда, и сколько чтений страниц понадобится там B-дереву? Потом перетащи ползунок до правого края.
    Что должно получиться

    Плоской остаётся только линия ключ-значение: один шаг при любом N, потому что хеш-таблица прыгает прямо в ячейку ключа. B-дерево получает новый уровень каждый раз, когда N вырастает в сто раз: 4 чтения страниц при миллионе, 6 при миллиарде (5 уровней индекса и страница данных), 60 ms; join платит это трижды, 18 чтений, 180 ms. Ради этого виджет и существует: стоимость поиска по ключу не растёт вместе с данными, а любого другого пути — растёт.

  2. Всё ещё на вращающемся диске предскажи: при 1 000 строк в таблице попадает ли join трёх таблиц в закрашенную полосу, то есть медленнее ли он, чем 100 ms со слайда (p. 343)? Потом найди наименьшее N, при котором он входит в полосу.
    Что должно получиться

    Пока нет: 9 чтений страниц, 90 ms. В полосу он входит сразу после 10 000 строк (12,589 на ползунке): у B-дерева появляется третий уровень, каждому поиску нужно 4 чтения, а join — 12, итого 120 ms — в этой модели, где ничего не кэшируется.

  3. Переключись на «RAM, всё в кэше». Предскажи: выигрывает ли хранилище ключ-значение и при миллиарде записей, и насколько?
    Что должно получиться

    Да, но с куда меньшим отрывом: 100 ns против 600 ns у B-дерева и 1.8 µs у join, в 6 и 18 раз. В памяти разница — только в числе шагов; на диске её задаёт носитель, от трёх до шести порядков величины. Хранилище ключ-значение убирает и то и другое — один шаг, в памяти, — а настоящая база данных ещё и разбирает и планирует каждую SQL-команду и берёт блокировки, чего эта модель не учитывает.

Один шаг в памяти — в этом вся суть. Реляционный поиск, как бы хорошо он ни был проиндексирован, карабкается по дереву, высота которого растёт вместе с данными, и на диске платит за позиционирование головки на каждом уровне; join платит это за каждую таблицу.

Хранилище ключ-значение отвечает на один вопрос — что лежит под этим ключом? — и отказывается от всех остальных вопросов, чтобы отвечать на этот за один шаг.

Есть и второй подарок (контекст, не с этих слайдов). Раз каждый запрос называет свой ключ, ключи можно разложить по многим машинам, хешируя их, и любой клиент может вычислить, где живёт ключ. Dynamo размещала ключи и машины на кольце — это консистентное хеширование (consistent hashing), придуманное в MIT в 1997 году для веб-кэшей. Собственные способы Redis делить ключи появятся в уроке 19; само кольцо вернётся вместе с Cassandra в уроке 22.

«Хранилище ключ-значение — это реляционная таблица с двумя столбцами, key и value». Нет: таблицу можно искать по столбцу значений, индексировать и соединять. У хранилища ключ-значение ничего этого нет; единственный эффективный вопрос — точный ключ. Redis добавляет операции над значением (следующий раздел), но никогда — запрос по значениям.

Redis: словарь, который обслуживают по сети

Титульный слайд раздела (p. 347) расшифровывает название: REmote DIctionary Server. Словарь — хеш-таблица из ключей в значения, — который живёт на сервере и отвечает по сети. Слайд "What is REDIS ?" (p. 348) даёт определение:

Redis — "Redis is an advanced key-value store, where keys can contain data structures such as strings, hashes, lists, sets, and sorted sets. Supporting a set of atomic operations on these data types." Слайд выделяет следующую фразу: "Redis is a different evolution path in the key-value databases where values are complex data types that are closely related to fundamental data structures and are exposed to the programmer as such, without additional abstraction layers." Иначе говоря, значения в Redis — сложные типы, близкие к базовым структурам данных, и программист работает с ними напрямую, без лишних слоёв абстракции.

Здесь три идеи, которые надо различать. Это хранилище ключ-значение: доступ по ключу, и больше никак. Значение под ключом может быть структурой данных (data structure), которую сервер понимает, — string, hash, list, set, sorted set. И операции над этими структурами атомарны. Средняя идея — это и есть смысл слова "advanced". Для простого хранилища ключ-значение список — такая же строка байтов, как любая другая; для Redis это список, поэтому ты отправляешь операцию, а не значение (рис. 2).

Практическое занятие говорит то же простыми словами: "The stored values can be simple types (e.g., numbers) or complex structures (e.g., lists)" (p. 1581). Values, значения, — держи это слово в голове, когда перечитываешь первую фразу слайда (p. 348).

«В Redis ключ может быть списком или хешем». Нет: ключ — это всегда строка (binary-safe); string, hash, list, set или sorted set — это значение, которое под ним хранится. "Keys can contain data structures" со слайда — старый собственный слоган Redis, и означает он, что ключ содержит такое значение, как и говорит следующая фраза: "values are complex data types" (так же и таблица на слайде (p. 354), и занятие (p. 1581)). Проверь на команде: в HSET user:1 name John ключ user:1 — обычная строка, хеш с полем name — его значение, а TYPE user:1 отвечает hash, то есть тип значения. Если вопрос «верно/неверно» цитирует фразу слайда, это собственное определение слайда: считай его верным, а в своих ответах пиши "the value of a key can be".

Последняя строка слайда (p. 348): "Can be used as Database, a Caching layer or a Message broker", и у каждой роли своя причина. База данных — потому что "Redis can persist data to the disk": он умеет писать снимки и журналы и загружать их после перезапуска (урок 19). Слой кэширования — потому что "Redis is fast": копии данных, которые дорого достать или вычислить, отдаются из памяти. Брокер сообщений — потому что "Redis is not only a key-value store": клиенты публикуют сообщения в каналы, на которые подписаны другие клиенты, или передают работу через список, которого ждёт обработчик.

Слайд "What is not REDIS" (p. 349) проводит границы:

  • "Redis is not a replacement for Relational Databases nor Document Stores."
  • "It might be used complementary to a SQL relational store, and/or NoSQL document store."
  • "Even when Redis offers configurable mechanisms for persistency, increased persistency will tend to increase latency and decrease throughput."
  • "Best used for rapidly changing data with a foreseeable database size (should fit mostly in memory)."

Каждая граница следует из того, где живут данные. Раз в памяти, набор данных должен влезть в RAM, которую ты можешь себе позволить, так что его размер должен быть предсказуемым. Персистентность — это регулятор: чем чаще Redis пишет на диск, прежде чем ответить, тем дольше каждая запись ждёт диска — та самая цена, что ты видел в гонке. Поэтому основная система учёта (system of record) остаётся в другом месте, а Redis держит то, что маленькое, горячее и быстро меняется (рис. 3).

Сценарии использования со слайда (p. 350) — это роли в деле; таблица ставит рядом с каждым то, что делает работу в Redis. (Если ты когда-нибудь будешь обслуживать обученную нейросеть в приложении, признаки, которые она читает в момент предсказания, живут в таком же хранилище: лекция про feature store говорит, что они "typically stored in low-latency databases like Redis" (p. 735, урок 29).)

Слайд "When to consider Redis" (p. 351) сжимает всё это в четыре условия — две причины выбрать Redis, потом два ограничения, которые нужно соблюдать:

  • "Speed is critical" — данные в памяти, и большинство команд занимает один шаг.
  • "More than just key-value pairs" — тебе нужны структуры данных и атомарные операции над ними; для простых непрозрачных значений справится кэш попроще (memcached, урок 19).
  • "Dataset can fit in memory" — граница со слайда (p. 349).
  • "Dataset is not critical" — ты можешь позволить себе потерять последние изменения, если сервер упадёт, потому что сделать каждую запись долговечной стоит той самой скорости, ради которой ты пришёл.

Если повторяешь по конспекту курса: на с. 20 конспекта сказано, что "being in-memory means that a single shutdown will cost you all your data" — раз всё в памяти, одно выключение стоит всех данных. Слайды говорят иначе — "Redis can persist data to the disk" (p. 348). Падение может стоить самых последних записей, в зависимости от настройки персистентности (урок 19); именно этот риск и принимает "Dataset is not critical".

Redis — хранилище ключ-значение, значения которого — понятные серверу структуры данных: ты отправляешь операцию, а не всё значение.

Один поток, одна команда за раз

Слайд "Redis Architecture" (p. 352) — это список фактов. Сначала простые: Redis "Written in ANSI C by Salvatore Sanfilippo (@antirez)", "Works in most POSIX systems like Linux, BSD and OS X", "Linux is the recommended", и "No official support for Windows" (слайд добавляет порт под Win-64, который поддерживает Microsoft). Ещё две строки несут на себе экзамен.

Начнём со случая. Планшеты двух медсестёр в один и тот же момент записывают посещение одного отделения: оба отправляют INCR visits, а в visits лежит 10. Внутри сервера Redis «одного и того же момента» не бывает: две команды ждут в очереди и выполняются одна за другой, 10 → 11 → 12 (рис. 4).

Слайд: "Redis is a single-threaded server, not designed to benefit from multiple CPU cores. Several Redis instances can be launched to scale out on several cores." Однопоточный сервер не выигрывает от многих ядер; чтобы занять несколько ядер, запускают несколько экземпляров. И следствие, пунктом ниже: "All operations are atomic (no two commands can run at the same time)."

Атомарная команда (atomic command) — команда, которая выполняется от начала до конца без какой-либо другой команды посередине: ни один клиент не увидит её сделанной наполовину, и она происходит либо целиком, либо никак.

Однопоточный — значит атомарный, и нигде никаких блокировок: блокировка (lock) существует, чтобы не пустить два потока к одним данным, а здесь поток только один. Два клиента, которые одновременно отправляют INCR, всегда насчитают два; LPUSH никогда не наткнётся на наполовину построенный список.

«Все операции атомарны, так что всё, что я отправлю, безопасно». Атомарна каждая команда. GET, за которым идёт SET, — это две команды, и между ними может выполниться команда другого клиента — потерянное обновление (lost update), которое рисует практическое занятие, и причина, по которой существует INCR (урок 18 проигрывает это заново). Несколько команд становятся одним атомарным блоком только внутри транзакции (MULTI … EXEC) или Lua-скрипта: слайд с преимуществами называет "Atomic operations and Transactions" и "LUA scripting support" (p. 365), но не объясняет их — это контекст за пределами экзаменационных команд.

Один поток звучит медленно. Но он быстрый, и на то четыре причины:

  • Данные в памяти: на пути запроса нет диска, если только ты не заставишь каждую запись его ждать (регулятор со слайда (p. 349)), — гонка из раздела 1.
  • Шаги короткие: "It executes most commands in O(1) complexity and with minimal lines of code" (p. 352).
  • Никто ничего не ждёт: не нужно брать блокировки, не нужно переключаться между потоками.
  • Один поток обслуживает тысячи соединений: он следит за всеми сразу и обслуживает то, где команда уже готова (цикл событий, event loop; контекст).

Клеппман в Designing Data-Intensive Applications добавляет причину потоньше (контекст): «преимущество in-memory баз данных в производительности не в том, что им не нужно читать с диска… скорее они могут быть быстрее, потому что избегают накладных расходов на кодирование структур данных из памяти в форму, которую можно записать на диск». Список Redis — это список в памяти, а не формат страницы, который надо переводить туда и обратно.

У такого устройства есть цена. Пока выполняется одна команда, все остальные клиенты ждут, поэтому команда над огромным значением — все элементы set на миллион записей — задерживает всех; очередь движется как раз благодаря "most commands in O(1)". И один поток использует одно ядро: чтобы задействовать восемь ядер, запускают восемь экземпляров, у каждого часть ключей, — зародыш партиционирования (урок 19).

Redis до сих пор однопоточный?

В основном да. С Redis 6.0 (2020) чтение и запись сетевого трафика можно разнести по дополнительным потокам, а сохранение на диск идёт в отдельном дочернем процессе. Сами команды по-прежнему выполняются по одной в одном потоке — именно это и имеет в виду слайд, именно это делает их атомарными, и именно это экзамен ждёт от тебя услышать.

Следующий слайд (p. 353) рисует весь сервер на одной картинке, и она же служит картой этого урока и двух следующих (рис. 5).

Читай её как оглавление. Слева — структуры данных: следующий раздел, потом команды урока 18. Справа — персистентность: "journal (text)" — это журнал всех записей, AOF, а "snapshot (binary)" — снимок всего набора данных, файл RDB, — два механизма со слайда (p. 359). Внизу — механика для нескольких серверов: репликация держит slaves как "exact copies of the master" (p. 359), Sentinel повышает slave, когда master умирает, а Cluster вдобавок раскладывает ключи по нескольким masters (урок 19).

Один поток выполняет одну команду за раз: каждая команда атомарна без блокировок и быстра, потому что каждая — короткий шаг в памяти.

Семь форм для значения

Слайд "Redis data types" (p. 354) перечисляет, чем может быть значение под ключом: семь типов, у каждого — что он "Contains" и его "Read/write ability". Сначала посмотри на картинки (рис. 6); текст слайда для каждого типа — во вкладках под ними.

Занятие называет sorted set «ordered set» (p. 1602): это тот же тип.

Читай картинки парами. List и set оба хранят строки, но list хранит порядок вставки и повторы — C встречается дважды, — а set ни того ни другого: каждая строка один раз, без порядка. Практическое занятие даёт причину выбрать set: "SETS are useful as it is very quick to test the existence of a value, which is not as easy when it comes to lists" (p. 1600) — проверить, есть ли значение, в set очень быстро, а в list — нет. Sorted set (упорядоченное множество) — это set, элементы которого несут число, score (вес), и держатся в порядке score; у A и C поровну, 250, и они упорядочены по имени (Redis разрешает ничьи по алфавиту; контекст). Hash — маленький словарь внутри значения: его внутренние ключи называются полями (fields) (HSET user:1 name John), так что ключ Redis называет объект, а поля — его атрибуты.

На слайде напечатано 12Kb: читай 12 KB, килобайт.

Последние два построены на других. Geospatial index — это "Sorted set implementation using geospatial information as the score": позиция упаковывается в одно число, так что близкие точки в основном получают близкие score, и поиск в радиусе превращается в несколько диапазонов score (контекст), — TYPE для такого ключа отвечает zset. HyperLogLog отвечает только на один вопрос: сколько разных элементов было добавлено, — приблизительно и не больше чем в 12 KB; сами элементы он никогда не возвращает.

Contains: "Binary-safe strings (up to 512 MB), Integers or Floating point values, Bitmaps." Read/write ability: "Operate on the whole string, parts, increment/decrement the integers and floats, get/set bits by position."

Binary-safe значит «любые байты»: слово, JSON-текст, целый JPEG. Строку, в которой лежит число, можно увеличивать на сервере — счётчик из "Counting things". В Python: str, bytes или int, если там число. Используй её для одного значения: закэшированная страница, счётчик, флаг.

# p. 355: bar held 223; returns (integer) 1223
INCRBY bar 1000

Contains: "Unordered hash table of keys to string values". Read/write ability: "Add, fetch, or remove individual items by key, fetch the whole hash."

«Ключи» внутри hash — это его поля. В Python: dict из строк в строки. Используй его для одного объекта с именованными атрибутами — пользователь, пациент, газовый котёл, — чтобы читать одно поле или все сразу.

# p. 357: returns (integer) 1, the number of fields added to user:1
HSET user:1 name John

Contains: "Doubly linked list of strings". Read/write ability: "Push or pop items from both ends, trim based on offsets, read individual or multiple items, find or remove items by value."

Порядок вставки, повторы разрешены, дёшево с обоих концов. В Python: collections.deque. Используй его для очередей, стеков и «последних N».

# p. 357: returns (integer) 1, the new length of the list jobs
RPUSH jobs "foo"

Contains: "Unordered collection of unique strings". Read/write ability: "Add, fetch, or remove individual items, check membership, intersect, union, difference, fetch random items."

Без порядка, без повторов, быстрое «а оно там есть?». В Python: set. Используй его для тегов, членства и «что общего у этих двоих».

# p. 358: returns (integer) 2, the number of new members
SADD users "John" "Peter"

Contains: "Ordered mapping of string members to floating-point scores, ordered by score". Read/write ability: "Add, fetch, or remove individual items, fetch items based on score ranges or member value."

Уникальные элементы, у каждого score, хранятся в порядке score. Встроенного близнеца в Python нет: представь dict из элемента в score, который всегда отсортирован по score. Используй его для рейтингов, таблиц лидеров и всего, что «отсортировано по году».

# p. 358: the score comes before the member; returns (integer) 3
ZADD scores 50 "Peter" 200 "Charles" 1000 "Mary"

Contains: "Sorted set implementation using geospatial information as the score". Read/write ability: "Add, fetch or remove individual items, search by coordinates and radius, calculate distance."

Используй его для «что рядом с этой точкой». Команды принимают долготу первой.

# the point of p. 354, longitude first; returns (integer) 1
GEOADD places -103.55328 20.63373 "Value"

Contains: "Probabilistic data structure to count unique things using 12Kb of memory". Read/write ability: "Add individual or multiple items, get the cardinality."

Мощность (cardinality) — это число разных элементов. В терминах Python: len(set(items)), приблизительно и без хранения самого множества. Используй его для уникальных посетителей или различных поисковых запросов, когда небольшая ошибка допустима.

# returns (integer) 1: the structure changed
PFADD visitors "u17" "u03" "u17"
# returns (integer) 2: about two different visitors
PFCOUNT visitors
Как 12 KB могут сосчитать миллиард разных посетителей?

Контекст, не со слайдов: идея HyperLogLog с двумя числами из документации Redis — 16,384 регистра и 12 KB.

  1. Захешируй каждый элемент. Хороший хеш выглядит как ряд честных подбрасываний монеты, а вернувшийся посетитель даёт ровно тот же ряд, так что повторы ничего не меняют.

  2. Посмотри, как начинается каждый ряд. Серия из \(k\) нулей в начале встречается примерно один раз на \(2^{k}\) разных рядов: если самая длинная серия, увиденная до сих пор, — 20, то мимо прошло, вероятно, около миллиона разных элементов. Это одно маленькое число, а не сами элементы.

  3. Одна самая длинная серия — шумная догадка, поэтому 14 бит хеша отправляют каждый элемент в одну из \(2^{14} = 16\,384\) групп; каждая группа хранит свою самую длинную серию в регистре, и регистры объединяются в одну оценку.

  4. Регистр хранит только длину серии, а 6 бит считают до 63, так что у памяти есть фиксированный потолок, что бы ни приходило:

    \[ \begin{aligned} 16\,384 \times 6 &= 98\,304 \text{ bits} \\ &= 12\,288 \text{ bytes} \end{aligned} \]

    — те самые 12 KB со слайда (p. 354), максимум, который он когда-либо займёт, хоть для тысячи элементов, хоть для миллиарда.

  5. Цена — ошибка. При \(m = 16\,384\) регистрах стандартная ошибка равна

    \[ \frac{1.04}{\sqrt{m}} = \frac{1.04}{128} \approx 0.81\,\% \]

    — и, как стандартная ошибка среднего в статистике, она убывает как единица, делённая на квадратный корень из того, что усредняешь.

Семь типов слайда — классические. Новые версии добавляют Streams (с Redis 5.0, 2018) — журнал сообщений для очередей — и модули вроде JSON; это контекст, не со слайдов. Выбрать тип — значит выбрать, какие команды ты получишь бесплатно: спроси, что нужно вопросу, — порядок, уникальность, score, именованные поля, позиция, число разных элементов, — и тип найдётся сам. Попробуй на восьми случаях.

Разгадка

Вернёмся к двум решениям 2009 года, которые звучали шиворот-навыворот. База данных, которая отвечает только на «что лежит под этим ключом?», спасает, когда реляционная слишком медленная, потому что этот вопрос стоит одного шага в памяти при любом объёме данных, и ничего не нужно разбирать, планировать или соединять, — плоская линия из гонки. А Redis возвращает многое из того, что теряет простое хранилище ключ-значение: значение — это структура данных, так что push, инкремент или проверка членства — всё равно одна команда над одним ключом.

Одному потоку не нужна блокировка, потому что он не может состязаться сам с собой: команды выполняются одна за другой, каждая атомарно. Он успевает, потому что каждый шаг короткий и в памяти, а когда одного ядра мало, запускают ещё один экземпляр. Цена — на слайде (p. 349): данные должны влезать в память, и чем надёжнее ты их хранишь на диске, тем медленнее всё работает.

Введение в курс говорит, что каждая категория систем "is covered along 5 dimensions" — разбирается по пяти измерениям: модель данных, "(declarative vs. imperative) query languages", распределение данных, нефункциональные аспекты и архитектурные решения. Теоретический вопрос о свойствах Redis ложится на эту сетку:

Когда таблица экзамена на один балл спрашивает, какая технология БД подходит каким сущностям (урок 5), обосновывай строку key-value так: данные, к которым обращаются только по ID, которые очень часто читают и пишут, достаточно маленькие для памяти и некритичные, — сессии, корзины, счётчики, закэшированные результаты, живые рейтинги — в Redis.

What is a key-value store? Explain why search by ID is usually built on top of a key-value store, and what a key-value store gives up compared with a relational database.

Показать образец ответа

A key-value store is a dictionary: every value is stored under a unique key, typically a business key such as a tweet id, a flight number, an account number or an item number, and the only way to reach a value is through its key. The store does not interpret the value; its operations are put, get and delete by key. Search by ID is built on top of a key-value store because a lookup by key is the cheapest possible access: with a hash table in memory it takes constant time whatever the size of the data, and it needs no query parsing, planning or join. Compared with a relational database, which is queried using SQL and is key-based with foreign keys, indexes and joins, a key-value store keeps only the key: no queries on the content of the values, no foreign keys, no secondary indexes, no joins. Keys are used only to retrieve a value, not to search or to map tables to each other. In exchange the store is very fast and easy to split across machines by key.

Ответ полон, когда в нём три вещи: определение (один ключ, одно непрозрачное значение, доступ только по ключу), причина (поиск за константное время без разбора, планирования и join) и компромисс, сопоставленный с пятью пунктами слайда (p. 346). Один пример со слайда (p. 345) покажет, что ты знаешь слайд.

What is Redis? Explain its definition, the three roles it can play, and what Redis is not.

Показать образец ответа

Redis (REmote DIctionary Server) is an advanced key-value store in which the value stored under a key can be a data structure — a string, a hash, a list, a set or a sorted set — with a set of atomic operations on these data types. Unlike a plain key-value store, the values are complex data types close to the fundamental data structures and are exposed to the programmer as such, without additional abstraction layers, so the client sends an operation (append this element, add this member) and the server applies it. Redis can be used as a database, because it can persist data to disk; as a caching layer, because it is fast, the data being in memory; and as a message broker, because it is not only a key-value store (publish/subscribe, blocking queues). It is not a replacement for relational databases or document stores: it is used next to them. Increasing persistency increases latency and decreases throughput, and the dataset should fit in memory, so Redis is best used for rapidly changing data with a foreseeable size.

Три части слайда (p. 348), три роли, каждая со своей причиной, и границы со слайда (p. 349). Предпочитай "the value of a key can be a list" формулировке слайда "keys can contain data structures" (ловушка в разделе 2), но узнавай напечатанную фразу, если вопрос её цитирует.

True or false: since all operations in Redis are atomic, a client that reads a counter with GET and then writes the incremented value back with SET performs one indivisible operation.

  • True Каждая из двух команд атомарна сама по себе, но слайд (p. 352) гарантирует только, что никакие две команды не выполняются одновременно: между GET и SET может выполниться команда другого клиента.
  • False Атомарна каждая отдельная команда. GET и SET — две команды; SET другого клиента может вклиниться между ними, и инкремент потеряется. INCR делает чтение и запись одной командой.
Показать образец ответа

False. Redis is single-threaded, so no two commands run at the same time and every single command is atomic. A GET followed by a SET is two commands: another client's command can be executed between them, so an update can be lost. A single INCR (or INCRBY) is atomic.

Ловушка — слово "all". Урок 18 проигрывает эту гонку шаг за шагом. За неправильные ответы может быть штраф (правило объявляют прямо перед экзаменом): ставь галочку только там, где можешь обосновать.

Redis is a single-threaded server. Explain why this makes every command atomic, why Redis is nevertheless fast, and how it can use more than one CPU core.

Показать образец ответа

Redis executes commands on a single thread: the commands of all clients are queued and executed one at a time, each from start to end, so no two commands can run at the same time and no client can observe or interleave with a half-executed command. Every command is therefore atomic, and no locks are needed. Redis is nevertheless fast because the data is in memory, so no disk access is on the path of a request; because most commands run in O(1) and take very little time; because a single thread spends nothing on locks or on switching between threads; and because one event loop serves many connections. The cost is that a slow command, such as an O(N) operation on a large structure, delays every other client. Redis is not designed to benefit from multiple CPU cores: to use several cores, several Redis instances are launched, each holding part of the data.

Три вопроса, три ответа; цепочка «один поток, значит атомарность, значит никаких блокировок» — ядро ответа. Как контекст можно добавить, что с Redis 6.0 сетевой ввод-вывод может использовать вспомогательные потоки, а команды по-прежнему выполняются в одном потоке.

Which statements about the Redis data types are correct? Select all that apply.

  • A list may contain the same string more than once, in insertion order. List — это "Doubly linked list of strings"; list на рис. 6 содержит A, C, B, C.
  • A set returns its members in the order in which they were inserted. Set — это "Unordered collection of unique strings".
  • The members of a sorted set are ordered by a floating-point score. "Ordered mapping of string members to floating-point scores, ordered by score" (p. 354).
  • A geospatial index is implemented as a sorted set. "Sorted set implementation using geospatial information as the score" (p. 354).
  • A HyperLogLog returns the list of the unique items it has seen. Он только оценивает их число, мощность (cardinality), не больше чем в 12 KB; сами элементы не хранятся.
  • A string can hold an integer that Redis increments on the server. Strings содержат "Integers or Floating point values" и умеют "increment/decrement the integers and floats" (p. 354).
Показать образец ответа

Correct: the statements on the list, the sorted set, the geospatial index and the string. A set is unordered; a HyperLogLog only estimates the number of distinct items and cannot return them.

Вопрос «выбери все верные», где за неправильные галочки могут снять баллы: два неверных утверждения — классические путаницы, list против set и подсчёт против хранения.

Exam-style exercise, written for this notebook on the ER model of the exam of 30 May 2025 (its header prints June 30, 2025), tracking puzzles' production and sales; that paper has no Redis exercise. The part used: Puzzle (Puzzle ID, Name, Collection Name (e.g., Museum Collection), Number of Pieces, Width, Height, Description), produced by one Company (Produce, with Production Date: Company (1, N) – Puzzle (1, 1)); User (Personal ID, Name, Surname, Age, Birth Date, City, Country), who buys puzzles (Buy, with Buy Date: Puzzle (0, N) – User (0, N)). Exercise – Redis. For each request, state the Redis data type you use and why, in one line, then write the commands.

(1) Create a single key-value pair to store all the data of one Puzzle, with all the attributes describing the object.

(2) Store the puzzles of the "Museum Collection" sorted by their number of pieces. Then, query them to get the puzzle with the most pieces.

(3) Store the countries of the users who bought the puzzle "P1", each country only once. Then, check whether "Italy" is one of them.

Показать образец ответа

(1) A hash: one key for the puzzle and one field for each of its attributes, so a single attribute can be read or changed on its own. The values are examples, and the attribute names are written with underscores (a field name with spaces would need double quotes).

HSET puzzle:P1 Puzzle_ID "P1" Name "Starry Night" Collection_Name "Museum Collection" Number_of_Pieces 1000 Width 70 Height 50 Description "Van Gogh, 1889"

The reply is (integer) 7, the number of fields created. One string holding the whole puzzle as JSON would also be a single key-value pair, but reading one attribute would then mean reading the whole text.

(2) A sorted set: the number of pieces is the score, so Redis keeps the puzzles in that order whatever the order of insertion. The highest score is the last element, at index -1, so the second command returns "P3".

ZADD museum:by_pieces 1000 "P1" 500 "P2" 2000 "P3"
ZRANGE museum:by_pieces -1 -1

(3) A set: each country is kept once, however many users from it bought the puzzle, and the membership test is one command. SADD replies (integer) 3, because the second "Italy" is ignored; SISMEMBER replies (integer) 1.

SADD puzzle:P1:countries "Italy" "France" "Italy" "Spain"
SISMEMBER puzzle:P1:countries "Italy"

Написано для этой тетради формулировками экзаменов; официального решения к нему нет, как нет его и ни к одному прошлому экзамену. Оно тренирует тот же выбор, который экзамен 30 января 2026 года, упражнение 5, требует на своей больничной ER-модели (решено в уроке 18). Что делает каждый ответ полным: (1) все атрибуты Puzzle под одним ключом — hash или JSON в string; (2) структура, которая сама держит порядок, score записан перед элементом, и читается нужный конец: индекс 0 — наименьший score, -1 — наибольший; list потребовал бы класть головоломки уже в нужном порядке; (3) уникальность и проверка членства — две вещи, которые set даёт бесплатно, а list нет ("very quick to test the existence of a value", p. 1600).

Проверь себя

Хранилище ключ-значение держит каждый пост блога под ключами вида post:101, а значение — вся страница. На какой запрос оно само по себе ответить не может?

  • Вернуть пост 101 Это и есть единственный вопрос, на который хранилище ключ-значение отвечает, за один шаг: получить по ключу.
  • Перечислить посты, написанные jbellis Автор — внутри значений, а хранилище никогда не заглядывает внутрь; без второго ключа, который связывает jbellis с id его постов, входа нет.
  • Удалить пост 102 Удаление по ключу — одна из трёх его операций.
  • Заменить страницу поста 103 Положить новое значение под тот же ключ.

В гонке поиска выбери «RAM, всё в кэше» и увеличь N от миллиона до миллиарда. Что происходит?

  • Все три кривые остаются плоскими: в памяти каждый поиск занимает константное время Память делает каждый шаг дешёвым, но шагов не становится меньше: B-дерево всё так же спускается на уровень глубже каждый раз, когда N вырастает в сто раз.
  • Хеш-поиск остаётся на 1 шаге; B-дерево растёт с 4 до 6 посещений страниц, а join — с 12 до 18 Стоимость одного шага упала с миллисекунд до 0.1 µs; число шагов не изменилось.
  • Растёт только join: одиночный поиск по B-дереву от N не зависит Join растёт, потому что растёт каждый из трёх его поисков: 3 × (уровни + 1).
  • Хеш-поиск тоже растёт, потому что большей таблице нужно больше проб Хеш-таблица прыгает прямо в ячейку ключа; её ожидаемая стоимость не зависит от числа ключей.

Почему RPUSH jobs "baz" в Redis лучше, чем GET, дописывание и SET в простом хранилище ключ-значение (рис. 2)?

  • Redis знает, что значение — список, и дописывает один элемент на сервере одной атомарной командой; с GET и SET всё значение дважды проходит по сети, и другой клиент может записать посередине Сервер понимает структуру, поэтому ты отправляешь операцию, а не значение.
  • RPUSH пишет список на диск, а GET и SET работают только в памяти Обе работают со значением в памяти; персистентность — отдельный вопрос.
  • Redis выполняет команды над списками в нескольких потоках параллельно Redis выполняет команды в одном потоке (p. 352).
  • Никакой реальной разницы нет: для сервера и то и другое — один шаг GET плюс SET — две команды с работой в клиенте между ними, и всё значение путешествует дважды.

Что из этого следует из того, что Redis выполняет команды в одном потоке? Выбери все подходящие.

  • Каждая отдельная команда атомарна Никакие две команды не выполняются одновременно (p. 352).
  • Не нужна блокировка, чтобы не пустить две команды к одному ключу Нет второго потока, которого надо не пускать.
  • Одна медленная команда над огромным значением заставляет ждать всех остальных клиентов Поток занят, пока она не закончится; вот почему важно "most commands in O(1)".
  • Redis сам использует все ядра машины "not designed to benefit from multiple CPU cores" (p. 352): запускают несколько экземпляров.
  • GET, за которым идёт SET от одного клиента, выполняется без прерывания Это две команды: между ними может выполниться команда другого клиента.

Атомарность на команду, а не на разговор: эта черта отделяет теорию этого урока от INCR из урока 18.

В HSET user:1 name John какая часть — та структура данных, которую слайд (p. 348) имеет в виду под "keys can contain data structures"?

  • Значение, хранящееся под ключом user:1, — hash с полем name Ключ — обычная строка; hash — его значение: TYPE user:1 отвечает hash.
  • Сам ключ user:1, который становится хешем Ключи — всегда (binary-safe) строки; типы есть только у значений.
  • Поле name, то есть ключ внутри ключа name — поле хеша: собственный внутренний ключ хеша, часть значения.
  • Строка John John — значение одного поля внутри хеша.

Экран показывает здания больницы от самого нового к самому старому по году постройки, а новые записи со временем добавляются в любом порядке. Какой тип держит их в этом порядке без сортировки в твоём коде?

  • List, куда каждое здание добавляется при записи List хранит порядок вставки: здание, записанное позже, но построенное раньше, окажется не на своём месте.
  • Sorted set с годом в качестве score Redis держит элементы в порядке score; чтение от наибольшего score вниз даёт самые новые первыми, в каком бы порядке их ни вставляли.
  • Set из id зданий У set вообще нет порядка.
  • Hash из id здания в год Hash хранит годы, но возвращает поля без определённого порядка.

Больница собирается хранить все медицинские карты пациентов — 60 TB, растущие каждый год, и по закону их нельзя терять никогда — только в Redis. Какие условия со слайда (p. 351) этот план явно нарушает? Выбери все подходящие.

  • Dataset can fit in memory 60 TB, да ещё растущие, — гораздо больше памяти одного сервера и не предсказуемый размер: Redis "Best used for rapidly changing data with a foreseeable database size (should fit mostly in memory)" (p. 349).
  • Dataset is not critical Эти карты критичны, а сделать каждую запись долговечной стоит задержки и пропускной способности (p. 349) — той самой скорости, ради которой выбирают Redis.
  • Speed is critical В плане ничто этому не противоречит; скорость здесь просто не проблема.
  • More than just key-value pairs Карта вполне может быть хешем; типы данных — не проблема.

Место Redis — рядом с основной системой учёта (рис. 3), а не вместо неё.

Главное

  • Хранилище ключ-значение отображает бизнес-ключ в значение и отвечает только на «что лежит под этим ключом?» операциями put, get и delete; поиск по ID обычно строят на нём, потому что поиск по ключу в памяти занимает один шаг при любом объёме данных.
  • Реляционную базу данных опрашивают на SQL, она key-based, с внешними ключами, индексами и join; хранилище ключ-значение оставляет только ключ, отказывается от запросов по значениям, join и вторичных индексов и получает скорость и лёгкое распределение ключей по машинам.
  • Redis, REmote DIctionary Server, — продвинутое хранилище ключ-значение, значения которого — структуры данных, доступные программисту как есть, с атомарными операциями над ними; он служит базой данных, слоем кэширования или брокером сообщений — рядом с реляционным или документным хранилищем и никогда вместо него.
  • Redis стоит рассматривать, когда скорость критична, тебе нужно больше, чем пары ключ-значение, набор данных влезает в память, а данные некритичны; больше персистентности — значит больше задержка и меньше пропускная способность.
  • Redis, написанный на ANSI C, выполняет команды в одном потоке: никакие две команды не выполняются одновременно, поэтому каждая атомарна без блокировок, а быстрым он остаётся, потому что каждый шаг короткий и в памяти; больше ядер — значит больше экземпляров.
  • Семь типов: string (байты, числа, bitmaps), hash (поля в значения), list (порядок, повторы, оба конца), set (уникальные, без порядка, членство и операции над множествами), sorted set (элементы в порядке score), geospatial index (sorted set со score по позиции) и HyperLogLog (приблизительное число разных элементов в 12 KB) — выбирай по вопросу, который будешь задавать.
