Aggregation pipeline в формате экзамена

После этого урока ты сможешь превратить экзаменационную фразу вроде "the total number of X for each Y, returning only those with at least N" в pipeline из $match, $unwind, $group, $sort и $limit — и сказать, как выглядят документы после каждой стадии.

Занятие спрашивает: "Write a query to compute the total number of bedrooms available across all housings." Слайд с решением (p. 1500) отвечает одной стадией $group. Запусти её на коллекции занятия — учебном наборе AirBnB от MongoDB, 5,555 объявлений, — и она напечатает bedroom_count: 0.

Ни ошибки, ни предупреждения. Pipeline корректный, и MongoDB делает ровно то, что в нём написано. Но один символ в нём просит совсем другое. Попробуй найти его, пока читаешь; последний раздел его назовёт — вместе с целым семейством опечаток в один символ, из-за которых правильный на вид pipeline отвечает на другой вопрос.

Pipeline — это конвейер из стадий

Таблица терминов урока 13 закончилась обещанием: то, что в SQL называется "Aggregation (e.g. group by)", в MongoDB называется "aggregation pipeline" (p. 297). Лекция отводит ему один слайд, "Further Read Features: Aggregates" (p. 317): "SQL-like aggregation functionality", "Pipeline documents from a collection pass through an aggregation pipeline", "Expressions produce output documents based on calculations performed on input documents". Занятие превращает эти три строки в инструмент, на котором держится большинство запросов MongoDB на экзамене (pp. 1439–1442).

Начнём с первого pipeline среди решений занятия — ответа на "Write a query to count the number of housings based on their price" (p. 1499):

// the number of housings for each price (p. 1499)
db.air_bnb_collection.aggregate([
  {
    "$group": {
      "_id": "$price",
      "housing_count": { "$sum": 1 }
    }
  }
])

Читай его снаружи внутрь. aggregate([…]) запускает pipeline на коллекции: в квадратных скобках — массив стадий (stages), которые применяются по порядку, и каждая — документ с единственным ключом, именем стадии. Здесь стадия одна, $group. Её "_id": "$price" говорит, какие документы идут вместе, — те, у которых одинаковая цена, — а "housing_count": { "$sum": 1 } прибавляет 1 за каждый документ, попавший в группу. В SQL: SELECT price, COUNT(*) … GROUP BY price. Почему не find? "When applying $unwind or $group stages (explained later), it is necessary to apply the aggregate(...) method" (p. 1439): find умеет только фильтровать и проецировать.

Чтобы посмотреть, как pipeline работает, нужны данные. В этом уроке их пять жилищ (табл. 1). Первое — Ribeira Charming Duplex, документ со слайдов о наборе данных (pp. 1472–1474), со значениями, которые там напечатаны, — кроме отзывов: отзыв Théo есть на слайде (p. 1474), отзыв Bridget придуман нами. Остальные четыре жилища тоже наши и подобраны так, чтобы каждой стадии занятия было во что вцепиться: хозяин с двумя жилищами, отсутствующая плата за уборку, жилища без отзывов.

На этих пяти жилищах pipeline со слайда (p. 1499) возвращает три документа: { _id: 50, housing_count: 1 }, { _id: 80, housing_count: 3 } и { _id: 120, housing_count: 1 }. Вошло пять документов, вышло три, и ни один из них уже не жилище.

Экзаменационным вопросам нужна не одна стадия. Третье упражнение занятия на агрегацию сначала фильтрует, а потом считает: "Write a query to compute the total number of housings based on their cancellation policy, whose accommodates is greater than 6 and whose host has a profile picture" (p. 1501).

// housings per cancellation policy, after two filters (p. 1501)
db.air_bnb_collection.aggregate([
  { "$match": { "accommodates": { "$gt": 6 } } },
  { "$match": { "host.host_has_profile_pic": true } },
  {
    "$group": {
      "_id": "$cancellation_policy",
      "cancellation_policy_count": { "$sum": 1 }
    }
  }
])

$match — это фильтр find, перенесённый внутрь pipeline, — "$match defines filters" (p. 1442), — с синтаксисом из урока 14. Две стадии $match подряд работают как AND; одна $match с обоими условиями — тот же самый запрос. Рис. 1 провожает пять жилищ по этому конвейеру.

Этот рисунок — та самая привычка, которой требуют занятия: "Do not focus only on memorising the commands required to perform queries. Instead, focus on understanding how the query shapes the data. Think on how the dataset would change after each operation in the query is performed" (введение к упражнениям). Занятие учит шести стадиям; их перечисляет слайд (p. 1442) — "besides the previously explained $group, $unwind, $sort, and $limit stages, $match defines filters while $project defines projections", — а табл. 2 даёт каждой её двойника в SQL.

"These stages can be applied interchangeably in the aggregation pipeline" (p. 1442). Понимай это как «в любом порядке и сколько угодно раз», а не как «если поменять две стадии местами, ничего не изменится». $match по счётчику работает только после $group, которая этот счётчик создаёт, а $limit перед $sort оставляет случайные документы (раздел 4).

Следующий слайд лекции (p. 318), "Further Read Features: Map-Reduce", показывает более старый инструмент для той же работы — и только его сигнатуру: db.collection.mapReduce( , , { out: , query: , sort: , limit: , … } ). В два пустых места перед опциями ставятся две функции JavaScript: map, которая выдаёт пары ключ–значение из каждого документа, и reduce, которая объединяет значения одного ключа, — модель из урока 30, только запущенная внутри базы данных. Текущая документация MongoDB объявила map-reduce устаревшим начиная с версии 5.0 в пользу pipeline, и ни одно упражнение курса его не использует.

Стадия $group: по корзине на ключ

Стадию определяет слайд (p. 1440): "Aggregate operations, i.e., operations aimed at grouping with respect to one or more fields, are achieved by applying the $group stage within the aggregate(...) method. Such a stage requires defining the list of fields to perform the aggregation and the aggregation functions to be applied." Представь ряд корзин. Выражение _id написано на каждой корзине, каждый документ падает в корзину со своим значением, а функции агрегации (aggregation functions) — это счётчики, прикреплённые к каждой корзине. Документация MongoDB называет их accumulators; в этом уроке остаётся название со слайдов.

Ключ работает благодаря доллару. Внутри $group строка, которая начинается с $, значит «значение этого поля в текущем документе»; без доллара это просто строка. Исключение — фильтр $match: там, как и в find, "$price" — обычный текст. Слайд (p. 1441) показывает оба случая и делает вывод: "Whenever a grouping operation is to be performed on the whole dataset, it is possible to apply a dummy _id in the $group stage. It's enough to set the _id to true or a fixed value. The latter is why the $ in the grouping stage is important!" Убери доллар из "$price" — и "price" станет тем самым фиксированным значением (рис. 2).

Если использовать его намеренно, фиксированный ключ отвечает на "the total number of bedrooms available across all housings" (p. 1500): одна корзина на всю коллекцию, а $sum — по полю, а не по 1.

// total bedrooms, one group for all (p. 1500, corrected)
db.air_bnb_collection.aggregate([
  {
    "$group": {
      "_id": true,
      "bedroom_count": { "$sum": "$bedrooms" }
    }
  }
])

На пяти жилищах: { _id: true, bedroom_count: 11 }, то есть 3 + 1 + 5 + 2 + 0. "_id": null работает так же. Собственная версия слайда отличается от этой одним символом — помни про загадку.

Слайд их перечисляет: "sum, avg, min, max, etc." (p. 1440). Табл. 3 прогоняет каждую на пяти жилищах.

Чтобы группировать сразу по двум полям, запиши _id как поддокумент. Слайд (p. 1504) группирует по "_id": { "n_bed": "$bedrooms", "n_bath": "$bathrooms" }: по корзине на каждую пару, слева — имена, которые ты выбираешь сам, справа — пути к полям, с долларом. Ключи на выходе выглядят как { n_bed: 5, n_bath: 2 }; весь запрос — в разделе 3.

Что выживает? "Whenever a $group stage is applied, only the fields used to perform the aggregation or created by it will be available in the next stages" (p. 1440). После стадии со слайда (p. 1499) каждый документ — это { _id, housing_count }, и больше ничего: name, bedrooms, amenities исчезли, и следующая стадия, которая их читает, ничего не находит, — $match по accommodates, поставленная после этой $group, не пропускает ни одного документа. Это правило SQL после GROUP BY: остаются только сгруппированные столбцы и агрегаты.

После $group документ — это его _id и поля, созданные функциями агрегации, — больше дальше не идёт ничего.

db.parts.aggregate ( {$group : {_id: type, totalquantity : { $sum: quanity} } } )

Поля читаются с долларом, в кавычках, и поле называется quantity: db.parts.aggregate([ { "$group": { "_id": "$type", "totalquantity": { "$sum": "$quantity" } } } ]), а стадии — в квадратных скобках, как их всегда пишет занятие.

В напечатанном виде type и quanity — голые имена, и оболочка читает их как переменные JavaScript: команда останавливается с "ReferenceError: type is not defined", не дойдя до базы. В кавычках, но без доллара, "type" был бы константой — одна корзина на всё, то самое предупреждение со слайда (p. 1441), — а "$quanity" суммирует поле, которого ни у кого нет: 0 для каждого type (проверено на MongoDB 8.2). Экзамен могут сверять со слайдом как напечатано: знай строку в том виде, как она есть, а пиши исправленную форму.

Массивам нужен $unwind; группы фильтруют после группировки

"Write a query to compute the total number of housings for each amenity" (p. 1485) прячет проблему: amenities — массив, а $group видит документы целиком. Сгруппируй прямо по "$amenities" — и ключом станет каждый список целиком: пять корзин по одному жилищу (попробуй в виджете). Массив сначала нужно разобрать, и именно это делает $unwind: "It shapes the collection so that each document is replaced with a set of new ones, i.e., one for each element in the document's array on which the unwind stage is applied. These new documents contain all the fields from the main one and a field with the name of the array field that contains one of its documents" (p. 1439).

После unwind в amenities лежит одна строка на документ, и группировка по нему — это группировка по удобству (p. 1502):

// the number of housings for each amenity (p. 1502)
db.air_bnb_collection.aggregate([
  { "$unwind": { "path": "$amenities" } },
  {
    "$group": {
      "_id": "$amenities",
      "housing_with_amenity_count": { "$sum": 1 }
    }
  }
])

Пять жилищ превращаются в 3 + 2 + 3 + 1 + 2 = 11 документов, а 11 документов падают в четыре корзины: Wifi 4, TV 3, Iron 3, Cable TV 1. Слайд пишет длинную форму { "path": "$amenities" }; { "$unwind": "$amenities" } — та же самая стадия. В любом случае у пути есть доллар: он читает поле.

Документ с пустым или отсутствующим массивом не даёт ни одной копии. У River Loft и Attic Room нет отзывов, так что после unwind по "$reviews" остаются три жилища. Безобидно, когда считаешь элементы; ловушка, когда считаешь родителей: «число отзывов каждого жилища» потеряет жилища без отзывов, вместо того чтобы показать 0. Опция из документации "preserveNullAndEmptyArrays": true сохраняет их по одному разу; слайды её не используют.

Теперь условие на корзины: "returning only the amenities whose count is greater than 15" (p. 1503).

// amenities offered by more than 15 housings (p. 1503)
db.air_bnb_collection.aggregate([
  { "$unwind": { "path": "$amenities" } },
  {
    "$group": {
      "_id": "$amenities",
      "housing_with_amenity_count": { "$sum": 1 }
    }
  },
  { "$match": { "housing_with_amenity_count": { "$gt": 15 } } }
])

$match после $group видит корзины, а не жилища: она фильтрует по тому, что посчитала группа, под тем самым именем, которое дала ему $group. Поднять её выше нельзя — до $group поля, которое она проверяет, ещё не существует. Это HAVING из SQL; $match до группы — его WHERE. На пяти жилищах ни одно удобство не доходит до 16, и пустой ответ правильный. В виджете ниже порог можно понизить.

Слайд (p. 1504) сочетает составной ключ с двумя фильтрами в стиле HAVING:

// averages per (bedrooms, bathrooms), two filters (p. 1504)
db.air_bnb_collection.aggregate([
  {
    "$group": {
      "_id": { "n_bed": "$bedrooms", "n_bath": "$bathrooms" },
      "avg_price": { "$avg": "$price" },
      "avg_cleaning_fees": { "$avg": "$cleaning_fee" }
    }
  },
  { "$match": { "avg_price": { "$gt": 60 } } },
  { "$match": { "avg_cleaning_fees": { "$gt": 40 } } }
])

До фильтров корзин пять, по одной на пару (bedrooms, bathrooms). avg_price > 60 убирает (1, 1) — 50 у Tiny Studio. avg_cleaning_fees > 40 убирает (3, 1) — 35 у Ribeira — и (0, 1): у Attic Room нет cleaning_fee, её среднее — null, а null не больше 40. Остаются две корзины: (2, 1) со 120 и 50, (5, 2) с 80 и 60. Обрати внимание на имена: поле называется cleaning_fee, созданное поле — avg_cleaning_fees. Имена, которые создаёт $group, — твои; имена полей — данных.

Отзывы Ribeira несут её собственный id 10006546. Отзыв Bridget на Ribeira и отзыв в Big Villa с id 10006546 придуманы нами, чтобы развести два запроса.

$match принимает любой фильтр из урока 14, включая операторы массивов. Два последних фильтра занятия записаны как pipeline (pp. 1505–1506):

// housings with one review that has both values (p. 1505)
db.air_bnb_collection.aggregate([
  {
    "$match": {
      "reviews": {
        "$elemMatch": {
          "listing_id": "10006546",
          "reviewer_id": "11263097"
        }
      }
    }
  }
])
// a review of 10006546 and a review by Bridget (p. 1506)
db.air_bnb_collection.aggregate([
  { "$match": { "reviews.listing_id": "10006546" } },
  { "$match": { "reviews.reviewer_name": "Bridget" } }
])

Первый возвращает только Ribeira: у её второго отзыва, от рецензента 11263097, есть оба значения. Второй возвращает ещё и Big Villa, у которой первый отзыв несёт listing id 10006546, а второй написан Bridget. Те же два условия, два вопроса: «один отзыв с A и B» против «один с A и один с B» — различие со слайдов (pp. 1436–1438), которое разбирал урок 14.

Pipeline, по одной стадии за раз

Пять жилищ из табл. 1. Выбери pipeline, а потом нажимай «Следующая стадия» — или щёлкни по стадии на конвейере, — чтобы увидеть документы, которые выходят из каждой стадии; пунктирная карточка — документ, который стадия отбросила, жёлтая строка — то, что стадия затронула. Чтобы собрать свой pipeline, выбери стадию в палитре и добавь её в конец; $group берёт ключ и функцию агрегации из двух меню под палитрой. N — это число в стадиях, где есть N. Каждый результат посчитан на пяти жилищах, а не взят со слайда.

  1. Выбери «p. 1501 · два фильтра, счёт по политике». Прежде чем нажимать «Следующая стадия»: сколько документов выйдет из каждой из трёх стадий? Потом пройди по шагам.
    Что должно получиться

    5 → 3 → 3 → 2. Первая $match отбрасывает Tiny Studio (2 гостя) и Attic Room (4); вторая не отбрасывает никого, потому что у всех трёх оставшихся хозяев есть фото профиля; $group превращает три жилища в два документа, которые вообще не жилища, — moderate 2 и strict 1. Вот что показывает виджет: каждая стадия меняет и число, и форму документов, а следующая стадия видит только то, что ей передала предыдущая.

  2. Выбери «p. 1503 · удобства со счётом > N» (N = 15, как на слайде). Предскажи результат, потом дойди до конца. Теперь понижай N: при каком N появится первое удобство?
    Что должно получиться

    При 15 не проходит ничего: пять жилищ не могут дать 16. Wifi появляется при N = 3 (её счёт — 4); при N = 2 к ней присоединяются TV и Iron, по 3 у каждого; Cable TV нужно N = 0. $match фильтрует корзины по housing_with_amenity_count — полю, которое существует только начиная с $group.

  3. Выбери «p. 1500 · всего спален, как напечатано» и дойди до конца; потом «p. 1500 · всего спален, исправлено». Что возвращает каждый?
    Что должно получиться

    0 и 11. Напечатанный pipeline суммирует "$bedroom" — поле, которого нет ни у одного жилища, а $sum без всякой ошибки пропускает то, чего нет. Карточки показывают рядом настоящее поле, bedrooms.

  4. Выбери «свой pipeline». В палитре выбери стадию $group с ключом cancellation_policy и функцией агрегации «счёт» и добавь её; потом добавь «$match accommodates > N» с N = 6. Предскажи результат, прежде чем смотреть.
    Что должно получиться

    Ни одного документа. После $group документы — это { _id, count }: accommodates больше не существует, поэтому не проходит ничего. Те же две стадии в обратном порядке дают бо́льшую часть ответа на слайд (p. 1501).

Топ-N и подсчёт различных значений

$sort и $limit — это ORDER BY и LIMIT внутри pipeline, с теми же числами, что урок 14 использовал для sort(): 1 по возрастанию, -1 по убыванию. Вопрос «топ-N» — это счёт, сортировка и обрезка:

// the three amenities offered by the most housings
db.air_bnb_collection.aggregate([
  { "$unwind": { "path": "$amenities" } },
  { "$group": { "_id": "$amenities",
                "housing_with_amenity_count": { "$sum": 1 } } },
  { "$sort": { "housing_with_amenity_count": -1 } },
  { "$limit": 3 }
])

Результат: Wifi 4, затем TV и Iron по 3 — в любом порядке, потому что MongoDB не обещает порядка среди равных значений; если порядок важен, добавь второй ключ, "_id": 1. Держи $sort перед $limit. В find MongoDB применяет sort() до limit(), как их ни сцепляй; pipeline выполняет стадии в порядке записи. { "$limit": 2 }, поставленный первым, оставляет два первых жилища в порядке хранения — Ribeira (8 гостей) и Tiny Studio (2) — и только потом их сортирует, тогда как правильный порядок возвращает Big Villa (10) и Ribeira (8).

На слайде (p. 1442) в строке стадии match не хватает одной закрывающей скобки. Пересчитай скобки, когда будешь переписывать.

$project оставляет поля, помеченные 1 (и _id), или убирает помеченные 0. Слайд (p. 1442) сцепляет пять стадий из шести — все, кроме $limit, — на телефонных номерах из коллекции людей занятия:

// providers with over 10 numbers, count hidden (p. 1442)
db.people_collection.aggregate([
  { "$unwind": { "path": "$mobile_phone_numbers" } },
  {
    "$group": {
      "_id": {
        "provider": "$mobile_phone_numbers.service_provider"
      },
      "phone_numbers_per_provider": { "$sum": 1 }
    }
  },
  { "$match": { "phone_numbers_per_provider": { "$gt": 10 } } },
  { "$sort": { "phone_numbers_per_provider": -1 } },
  { "$project": { "phone_numbers_per_provider": 0 } }
])

Прочитай вслух: по документу на каждый номер; по корзине на провайдера, со счётом; оставить провайдеров, у которых больше 10 номеров; самые большие первыми; спрятать счёт. Отсортировать по полю и убрать его на следующей же стадии — нормально: к этому моменту порядок уже создан.

Занятие заканчивается подсчётом другого рода: "For each country, compute the total number of unique hosts" (p. 1507).

// for each country, the number of distinct hosts (p. 1507)
db.air_bnb_collection.aggregate([
  {
    "$group": {
      "_id": {
        "country": "$address.country", "host_id": "$host.host_id"
      },
      "duplication_count_per_host": { "$sum": 1 }
    }
  },
  {
    "$group": {
      "_id": "$_id.country",
      "unique_host_count": { "$sum": 1 }
    }
  }
])

Одна $group по стране с { "$sum": 1 } считает жилища: Portugal 3, потому что у хозяина 51399391 там два жилища. Занятие группирует дважды. Первая $group делает по одному документу на пару (страна, хозяин), сколько бы жилищ ни было у этой пары, — здесь дубликаты схлопываются. Вторая группирует эти документы-пары по стране, читая её внутри составного ключа через "$_id.country", и считает их: Portugal 2, Spain 2. duplication_count_per_host вопросу не нужно; оно лишь показывает, что схлопнулось. В SQL это COUNT(DISTINCT host_id) … GROUP BY country — агрегат, которого у изученных стадий нет.

Чтобы посчитать различные значения на каждый ключ: сгруппируй по (ключ, значение), потом сгруппируй по ключу и посчитай.

Уникальные хозяева по странам: две стадии $group

Пять объявлений из табл. 1, по стране и хозяину. «Дальше» запускает две стадии со слайда (p. 1507): сначала корзины (страна, хозяин), потом корзины стран. Пунктирная панель — соблазнительная одна $group по стране. Добавь шестое объявление и посмотри, какое число сдвинется.

  1. Прежде чем нажать «Дальше»: сколько документов выйдет из первой $group?
    Что должно получиться

    Четыре. У хозяина 51399391 два объявления в Portugal, Ribeira и River Loft; у них общая пара (Portugal, 51399391), и они схлопываются в один документ с duplication_count_per_host 2. У остальных трёх пар по одному объявлению.

  2. Добавь «третье объявление хозяина 51399391, в Portugal» — слайд с набором данных даёт этому хозяину host_listings_count: 3 (p. 1473). Какой ответ сдвинется: двухстадийный или одна группа?
    Что должно получиться

    Только одна группа: у Portugal становится не 3, а 4 объявления. Пара (Portugal, 51399391) просто вырастает до duplication_count_per_host 3, так что unique_host_count остаётся 2. Вывод: первая $group убирает дубликаты — по документу на (страна, хозяин), — а вторая считает то, что осталось.

  3. Выбери вместо этого «объявление хозяина 51399391 в Spain». Что произойдёт со Spain, и правильно ли это?
    Что должно получиться

    Spain становится 3 в обоих ответах: появляется новая пара, (Spain, 51399391). Хозяин считается по одному разу в каждой стране, где у него есть объявление, — ровно то, что спрашивает "for each country, the number of unique hosts".

От экзаменационной фразы к стадиям

Вариант 30 января 2026 года заканчивает каждый запрос MongoDB фразой "Use only the pipeline stages discussed during the practical lectures." Это шесть стадий из табл. 2. $lookup, стадии, которая соединяет две коллекции, среди них нет, и тот же вариант запрещает её в вопросе по дизайну: "You must design the relationships without using the MongoDB $lookup operation." Так что каждый запрос работает на одной коллекции, над документами, вложенными так, как их спроектировал урок 13. Другие стадии существуют — $count, $sortByCount, $addFields, — но их не проходили: не используй их. Функции агрегации вроде $push или $first — не стадии; где хватает sum, avg, min и max со слайда, бери их, а про любую другую напиши в комментарии, что она делает.

Одна привычка до первой стадии: твой запрос можно прочитать только на фоне твоего же документного представления, так что сформулируй его — или сошлись на свой ответ по дизайну — и назови массивы, которые будешь разворачивать. Потом переводи фразу кусок за куском. Вот метод на экзамене 12 сентября 2025 года, упражнение 5 ("tracking farmers and their sales at local markets"). В его ER есть Farm (Name, Address, State, Description) и Animal (Tag, Name, Age, Animal Type (e.g., Cow), Breed), связанные отношением House с атрибутом Housing Date: Animal (1, 1) – Farm (1, N). Запрос: "Write a query to compute the total number of farms that house at least 10 cows of at least 5 different breeds. (2 PT)"

// assumed: collection farm, animals nested in each farm
{
  "_id": "Green Acres",                     // Name: String
  "Address": "SP 12, km 3",                 // String
  "State": "Italy",                         // String
  "Description": "Dairy farm",              // String
  "animals": [
    { "Tag": "A-001",                       // String
      "Name": "Bessy",                      // String
      "Age": 6,                             // Integer
      "Animal_Type": "Cow",                 // String
      "Breed": "Holstein",                  // String
      "Housing_Date": ISODate("2020-03-01") // Date, of House
    }
  ]
}
// farms with at least 10 cows of at least 5 breeds
db.farm.aggregate([
  { "$unwind": { "path": "$animals" } },
  { "$match": { "animals.Animal_Type": "Cow" } },
  { "$group": { "_id": { "farm": "$_id",
                         "breed": "$animals.Breed" },
                "cows_of_breed": { "$sum": 1 } } },
  { "$group": { "_id": "$_id.farm",
                "n_breeds": { "$sum": 1 },
                "n_cows": { "$sum": "$cows_of_breed" } } },
  { "$match": { "n_cows": { "$gte": 10 },
                "n_breeds": { "$gte": 5 } } },
  { "$group": { "_id": true, "n_farms": { "$sum": 1 } } }
])

Вторая $group складывает две вещи: 1 за каждый документ (ферма, порода) — это считает породы — и поле cows_of_breed, которое считает коров. На пяти тестовых фермах pipeline превращает 77 животных в 47 коров после $match, затем в 25 пар (ферма, порода), пять ферм с двумя счётчиками, две фермы, прошедшие оба порога, и наконец { _id: true, n_farms: 2 }. Убери $match по Cow — и проскочит ферма с шестью коровами и десятью овцами (16 животных 8 пород), а ответ станет 3. Ещё одна деталь стоит комментария в ответе: если ни одна ферма не подходит, последняя $group ничего не получает и не возвращает ни одного документа, а не 0.

"More than N" — это $gt, "at least N" — $gte. "For each X" определяет _id. "Distinct" или "different" требуют двойной $group. "Top 10" — это $sort с -1, затем $limit. Условие на элемент массива ставится после его $unwind. На слайдах после последней стадии остаётся запятая (pp. 1503, 1504, 1506 и 1507): оболочка это принимает, но на бумаге её не ставь.

Тихие неверные ответы и пропавшая буква

Вернёмся к загадке. Слайд (p. 1500) суммирует "$bedroom", а поле называется bedrooms — "bedrooms: 3" на слайде с набором данных (p. 1472). $sum складывает значения-числа и пропускает остальное; несуществующее поле — не число; сумма ничего — 0. MongoDB не выдаёт ошибки, потому что у неё нет схемы, с которой можно сверить имена: поле с опечаткой — просто поле, которого нет ни у одного документа. Это schema-on-read (схема при чтении, урок 4), увиденная со стороны запроса.

"bedroom_count": { "$sum": "$bedroom" }

"bedroom_count": { "$sum": "$bedrooms" } — поле в наборе данных называется bedrooms (p. 1472), а упражнение просит "the total number of bedrooms".

В напечатанном виде pipeline возвращает bedroom_count: 0 на любой коллекции жилищ, без ошибки; с "$bedrooms" он возвращает настоящую сумму — 11 на пяти жилищах (запусти оба в первом виджете, пресеты «p. 1500»). Экзамен могут сверять со слайдом как напечатано: знай, что там напечатано "$bedroom", а ответу нужно "$bedrooms".

У пропавшей буквы есть родственники. Каждая строка табл. 5 — pipeline, который выполняется, что-то возвращает и при этом неверен; все они запущены на MongoDB 8.2.

MongoDB никогда не жалуется на поле, которого не может найти: сверяй каждое имя с ER-диаграммой, а каждую стадию — с документами, которые она получает.

Вопросы в формате экзамена

Четыре практических упражнения из прошлых вариантов, каждое — с ER-сценарием варианта, документным представлением, которое оно предполагает (дизайны из урока 13), и баллами, напечатанными в варианте; затем два теоретических вопроса в формате теоретической части, где неверные ответы на закрытые вопросы могут стоить баллов. Решения не публикуются: образцы ответов — наши, и каждый pipeline запущен на реальном сервере MongoDB на тестовых данных, собранных так, чтобы задеть его пороги.

Exam of 30 Jan 2026, exercise 3 (a hospital heating management system). ER: Hospital (Hospital_ID, Name); Building (Building_ID, Name, Year); Department (Department_ID, Specialty, N_Beds, Head_Physician_ID); Person (P_ID, Email). Has Building: Hospital (1:N) – Building (1:1); Has Dept.: Hospital (1:N) – Department (1:1); Works For, with Role: Department (1:N) – Person (1:N). Assume the documental representation of the design question: one collection, hospital; buildings and departments nested in each hospital; the people of each department nested in it, each with its Role.

"Write a query to return the total number of departments each person with the role 'maintenance' works for. Return only the top 10 people working in the highest number of departments. (2 PT) Use only the pipeline stages discussed during the practical lectures."

Показать образец ответа

Assumed documents (as designed in the first part): { "_id": "H01", "Name": …, "buildings": [ { "Building_ID", "Name", "Year" } ], "departments": [ { "Department_ID", "Specialty", "N_Beds", "Head_Physician_ID", "people": [ { "P_ID", "Email", "Role" } ] } ] }. Role belongs to Works For, so it is read per department: a person counts the departments in which they work as maintenance.

// top 10 maintenance people by number of departments
db.hospital.aggregate([
  { "$unwind": { "path": "$departments" } },
  { "$unwind": { "path": "$departments.people" } },
  { "$match": { "departments.people.Role": "maintenance" } },
  { "$group": { "_id": "$departments.people.P_ID",
                "n_departments": { "$sum": 1 } } },
  { "$sort": { "n_departments": -1 } },
  { "$limit": 10 }
])

The two $unwind stages give one document per (department, person). The $match keeps the maintenance entries; the $group counts them per P_ID — a person appears once per department, so the count is the number of departments; $sort with -1 and $limit keep the ten highest.

Проверь в своём ответе три вещи: оба unwind стоят до условия на Role, у ключа есть доллар ("$departments.people.P_ID"), а $sort идёт перед $limit. У вопроса есть второе прочтение — все отделы тех людей, которые где-то работают в maintenance, — и оно требует больше работы; скажи, на какое из них ты отвечаешь. Проверено на двенадцати работниках maintenance, распределённых по числу отделов от 12 до 1: возвращаются десять — от 12 до 3, по порядку.

Exam of 30 Jan 2026, exercise 3, continued. Same ER and same documents.

"Write a query to collect, for each hospital with more than 10 buildings, the number of departments with more than 25 people. Use only the pipeline stages discussed during the practical lectures. (2 PT)"

Показать образец ответа 
// hospitals with > 10 buildings: departments with > 25 people
db.hospital.aggregate([
  { "$unwind": { "path": "$buildings" } },
  { "$group": { "_id": "$_id",
                "n_buildings": { "$sum": 1 },
                "departments": { "$first": "$departments" } } },
  { "$match": { "n_buildings": { "$gt": 10 } } },
  { "$unwind": { "path": "$departments" } },
  { "$unwind": { "path": "$departments.people" } },
  { "$group": {
      "_id": { "hospital": "$_id",
               "department": "$departments.Department_ID" },
      "n_people": { "$sum": 1 } } },
  { "$match": { "n_people": { "$gt": 25 } } },
  { "$group": { "_id": "$_id.hospital",
                "n_departments": { "$sum": 1 } } }
])

Buildings are counted with $unwind and $group, and the hospitals with more than 10 are kept. That $group would drop the departments, so they are carried through it with the aggregation function $first, which keeps the value of the first document of the group — every copy of a hospital carries the same departments array. Then people are counted per (hospital, department), the departments with more than 25 are kept, and they are counted per hospital.

Больница, у которой больше 10 зданий, но нет отдела больше 25 человек, в ответе не появится вовсе: до последней стадии не доходит ни одного документа. Если считаешь, что ожидается 0, скажи об этом в комментарии. Более короткий ответ на тех же изученных стадиях начинается с { "$match": { "buildings.10": { "$exists": true } } } — элемент на позиции 10, то есть хотя бы 11 зданий, — и обходится без первых $unwind и $group. Обе версии, проверенные на больницах с 11, 10, 12 и 0 зданиями, возвращают только первую, с 2 отделами (26 и 30 человек; отдел из 5 исключён).

Exam of 30 May 2025 (its header prints June 30, 2025), exercise 5 (tracking puzzles' production and sales). ER: Company (Code, Name, Address, Phone Number, Biography); Puzzle (Puzzle ID, Name, Collection Name, Number of Pieces, Width, Height, Description); Produce, with Production Date: Company (1, N) – Puzzle (1, 1). Assume the documental representation of the design question: collection company, its puzzles nested in it, each with its Production_Date.

"Write a query to compute the total number of puzzles produced by each company, considering only puzzles produced after 30/04/1995 and with more than 500 pieces, and returning only the companies that produced more than 100 puzzles (1.5 PT)"

Показать образец ответа 
// companies with more than 100 qualifying puzzles
db.company.aggregate([
  { "$unwind": { "path": "$puzzles" } },
  { "$match": {
      "puzzles.Production_Date": { "$gt": ISODate("1995-04-30") },
      "puzzles.Number_of_Pieces": { "$gt": 500 } } },
  { "$group": { "_id": "$_id", "n_puzzles": { "$sum": 1 } } },
  { "$match": { "n_puzzles": { "$gt": 100 } } }
])

One document per puzzle, the two conditions on that puzzle, a count per company, and the threshold on the count. Production_Date is assumed stored as a date, so "after 30/04/1995" is $gt that day.

Суть упражнения — в месте первой $match. Поставь её до $unwind — и она оставит каждую компанию, у которой есть хотя бы одна такая головоломка, а потом посчитает все её головоломки: на наших тестовых данных компания с 80 подходящими головоломками из 150 была посчитана как 150 и прошла порог. "More than 100" — это $gt: компания ровно со 100 не проходит.

Exam of 13 Jun 2025 (its header prints Jan. 21, 2025), exercise 3 (tracking concert attendances and performances). ER: Orchestra (Name, Foundation Date, Biography); Musician, a child of Person (Personal ID, Name, Surname, Birth Date), with Biography; Instrument (Name, Type, Description). Compose: Orchestra (10,N) – Musician (1,2); Play, with Since: Musician (1,N) – Instrument (1,N). Assume the documental representation of the design question: collection orchestra; its musicians nested in it, each with the instruments they play and Since.

"Write a query to compute the number of members for each orchestra and each instrument, and return only the orchestras that include at least three musicians for at least four instruments (2.5 PT)"

Показать образец ответа 
// orchestras with 3+ members for each of 4+ instruments
db.orchestra.aggregate([
  { "$unwind": { "path": "$musicians" } },
  { "$unwind": { "path": "$musicians.instruments" } },
  { "$group": {
      "_id": { "orchestra": "$_id",
               "instrument": "$musicians.instruments.Name" },
      "n_members": { "$sum": 1 } } },
  { "$match": { "n_members": { "$gte": 3 } } },
  { "$group": {
      "_id": "$_id.orchestra",
      "n_instruments": { "$sum": 1 },
      "instruments": { "$push": { "instrument": "$_id.instrument",
                                  "n_members": "$n_members" } } } },
  { "$match": { "n_instruments": { "$gte": 4 } } }
])

The first $group computes the members of each (orchestra, instrument); the first $match keeps the instruments with at least three; the second $group counts those instruments per orchestra and keeps their counts in a list; the last $match keeps the orchestras with at least four.

Два уровня HAVING — схема подсчёта различных значений. $push — функция агрегации, которой нет на слайдах: без неё ответ всё равно возвращает оркестры с числом инструментов. Музыкант может состоять в двух оркестрах (Compose (1,2)) и хранится в обоих, но внутри каждого встречается один раз, так что ни один участник не считается дважды в одном оркестре. Проверено: оркестр с тремя музыкантами на каждый из piano, violin, cello и flute возвращается с 4; оркестр только с двумя флейтистами — нет.

Which of the following lists contains only stages of the MongoDB aggregation pipeline?

  • $match, $group, $unwind, $sort, $limit, $project Шесть стадий со слайда (p. 1442): $group, $unwind, $sort, $limit и "$match defines filters while $project defines projections".
  • $match, $elemMatch, $group $elemMatch — оператор запроса: он живёт внутри фильтра, в find или в $match. Один слайд занятия называет его стадией (p. 1438), но в pipeline он никогда не стоит сам по себе.
  • $group, $sum, $avg $sum и $avg — функции агрегации (в документации — accumulators), их пишут внутри $group.
  • $unwind, $exists, $sort $exists — оператор запроса из семейства element, используется внутри фильтра.
Показать образец ответа

The first list. A stage is an element of the array passed to aggregate(...) and transforms the stream of documents; query operators and aggregation functions are written inside stages.

Закрытый вопрос, где неверная галочка может стоить баллов: ловушка — слайд, который называет $elemMatch стадией. Знай наизусть шесть имён со слайда (p. 1442).

Explain how the $group stage of the MongoDB aggregation pipeline works: the role of _id and of the aggregation functions, the meaning of the $ in "_id": "$price", and which fields the next stage can use. How do you compute a single total over the whole collection?

Показать образец ответа

The $group stage partitions the documents it receives by the value of the expression in _id and outputs one new document per distinct value. The other fields of the stage are aggregation functions (accumulators, in the manual), computed on the documents of each group: { "$sum": 1 } counts them, { "$sum": "$field" } adds a field, $avg, $min and $max give the mean, the minimum and the maximum. A string that starts with $ is a field path: "$price" is the value of price in each document, so there is one group per price; "price" without the dollar is a constant, and all documents fall into one group. After the stage only _id and the fields created by the aggregation functions exist; to filter on one of them, a $match is placed after the $group, like HAVING in SQL. For a total over the whole collection the _id is set to a constant such as true or null, for example { "$group": { "_id": true, "bedroom_count": { "$sum": "$bedrooms" } } }.

Полный ответ покрывает четыре вещи: разбиение по _id, функции агрегации хотя бы с двумя примерами, доллар как путь к полю против константы и то, что переживает стадию, — "only the fields used to perform the aggregation or created by it" (p. 1440). Завершает ответ фиктивный _id со слайда (p. 1441). Слайды говорят "aggregation functions"; "accumulators" — слово документации для того же самого.

Проверь себя

Pipeline доходит до { "$group": { "_id": "$cancellation_policy", "n": { "$sum": 1 } } }. Какие поля сможет прочитать следующая стадия? Отметь все подходящие.

  • _id В нём лежит политика: "moderate", "flexible" или "strict".
  • n Поле, которое стадия создала своей функцией агрегации.
  • cancellation_policy Его значение теперь живёт в _id; само поле не выжило. Чтобы прочитать политику, пиши "$_id".
  • price Дальше идут только ключ и созданные поля (p. 1440). То, что нужно, проноси с собой функцией агрегации, например { "$avg": "$price" }.

После $group документ — это его _id и поля, созданные функциями агрегации.

{ "$unwind": "$amenities" } выполняется на пяти жилищах из табл. 1. Сколько документов выйдет?

  • 11 По одному на элемент: 3 + 2 + 3 + 1 + 2.
  • 5 Стадия не оставляет по документу на жилище: она делает по документу на каждый элемент массива.
  • 4 4 — это число различных удобств: столько документов делает $group по "$amenities" после unwind.
  • 3 3 — длина массива одной только Ribeira; разворачивается каждое жилище.

Тебе нужно число отзывов каждого жилища, включая жилища без отзывов. Ты делаешь unwind по "$reviews", потом группируешь по "$_id" с { "$sum": 1 }. Что будет с River Loft, у которой reviews — [ ]?

  • Её не будет в результате Пустой массив не даёт ни одной копии, так что River Loft до $group не доходит.
  • Она появится со счётом 0 Ничего от River Loft не доходит до $group, так что нет корзины, которая показала бы 0.
  • Она появится со счётом 1 Только с опцией из документации "preserveNullAndEmptyArrays": true, которая сохраняет документ один раз, — и тогда счёт будет 1, а не 0.
  • Pipeline остановится с ошибкой Пустой массив допустим; стадия просто ничего для него не производит.

Два pipeline отличаются только ключом, "_id": "$price" против "_id": "price", оба с "housing_count": { "$sum": 1 }. Что вернёт второй на пяти жилищах?

  • Один документ: { _id: "price", housing_count: 5 } Без доллара "price" — фиксированное значение, одно и то же для каждого жилища: одна корзина (p. 1441).
  • Три документа, как первый Для трёх корзин нужны три разных значения ключа; у константы оно одно.
  • Ошибку: ключ должен начинаться с $ Любая константа — допустимый ключ; именно так работает фиктивный _id со слайда (p. 1441).
  • Ни одного документа Каждое жилище входит в стадию, и все они оказываются в одной корзине.

Вопрос: "return the three hosts with the most housings". Какой порядок стадий на него отвечает?

  • $group по хозяину со счётом → $sort по счёту, -1 → $limit 3 Посчитать, упорядочить, обрезать: первая тройка.
  • $group → $limit 3 → $sort $limit оставляет трёх случайных хозяев и сортирует только их.
  • $sort → $limit 3 → $group Так отрезаются три жилища, а не три хозяина, и считается слишком поздно.
  • $limit 3 → $group → $sort Считаются только три жилища.

Почему первая $group со слайда (p. 1507) использует ключ { country, host_id }, а не один host_id?

  • Чтобы каждая пара (страна, хозяин) стала одним документом, а страна осталась для второй $group Дубликаты схлопываются по парам, а страна выживает внутри _id, где её читает "$_id.country".
  • Потому что в ключе должно быть хотя бы два поля Хватает и одного поля: слайд (p. 1499) группирует только по "$price".
  • Чтобы отсортировать хозяев по стране $group не сортирует; даже порядок её вывода не гарантирован.
  • Потому что host_id — строка Тип ключа для стадии не важен.

В группе flexible — Tiny Studio (cleaning_fee 45) и Attic Room, у которой cleaning_fee нет. Что даст для этой группы { "$avg": "$cleaning_fee" }?

  • 45 Среднее берётся по документам, у которых в поле число; Attic Room пропускается, а не считается за 0.
  • 22.5 Так было бы, если бы отсутствующая плата считалась за 0.
  • null null бывает, только когда поля нет ни у одного документа группы, — как у корзины (0, 1) с Attic Room, когда pipeline со слайда (p. 1504) работает на пяти жилищах.
  • Ошибку Отсутствующее поле в функции агрегации никогда не бывает ошибкой.

Главное

  • aggregate([…]) выполняет упорядоченный список стадий: каждая получает документы от предыдущей и передаёт дальше новые. Читай pipeline, спрашивая себя, как выглядят документы после каждой стадии.
  • $group делает по документу на каждое значение _id — поле, прочитанное с долларом; константа вроде true или null для одной общей группы; поддокумент для нескольких полей — с функциями агрегации (accumulators в документации): $sum от 1 считает, $sum от поля складывает, $avg, $min, $max. Дальше идут только _id и поля, которые они создали.
  • $match до $group фильтрует документы (WHERE); после неё — фильтрует группы по полям, которые группа создала (HAVING). $unwind делает по документу на элемент массива, а документ с пустым массивом исчезает.
  • Топ-N — это $group, потом $sort с -1, потом $limit. Подсчёт различных значений — две группы: по (ключ, значение), затем по ключу с $sum от 1.
  • На экзамене: только шесть стадий со слайда (p. 1442), никакого $lookup; сначала опиши свои документы, потом переводи фразу кусок за куском.
  • MongoDB никогда не жалуется на поле, которого не может найти: имя с опечаткой суммируется в 0 — ошибка со слайда (p. 1500) — или усредняется в null, а ключ без доллара даёт одну группу.
Pipeline
db.coll.aggregate([ { "$stage": … }, … ]), стадии по порядку
Фильтр
{ "$match": { "f": { "$gt": 6 } } }: WHERE; после $group — HAVING
Группировка
{ "$group": { "_id": "$f", "n": { "$sum": 1 } } }: по документу на каждое значение f
Общая группа
"_id": true (или null): одна корзина на всё
Составной ключ
"_id": { "a": "$a", "b": "$b" }; дальше читается как "$_id.a"
Функции агрегации
{ "$sum": 1 } счёт · { "$sum": "$f" } сумма · $avg · $min · $max · $push (нет на слайдах); в документации — accumulators
После группы
существуют только _id и поля, созданные группой
Unwind
{ "$unwind": "$arr" } = { "$unwind": { "path": "$arr" } }: по документу на элемент; пустые массивы исчезают
Топ-N
{ "$sort": { "n": -1 } }, затем { "$limit": 10 }
Проекция
{ "$project": { "f": 1 } } оставляет, { "f": 0 } убирает
Подсчёт различных
группировка по { key, thing }, затем по "$_id.key" с { "$sum": 1 }
Пороги
"more than N" $gt · "at least N" $gte
Тихие ошибки
опечатка в поле: $sum 0, $avg null · ключ без доллара: одна группа
Набор для экзамена
$match, $group, $unwind, $sort, $limit, $project; без $lookup

mapReduce(map, reduce, { out, query, … }): старый инструмент, устарел начиная с MongoDB 5.0
