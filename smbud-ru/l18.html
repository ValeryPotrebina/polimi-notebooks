Команды Redis в формате экзамена

После этого урока ты сможешь превратить любую фразу экзамена про Redis — значение со сроком жизни, список, множество, рейтинг, объект — в правильную структуру и точные команды и сказать, что Redis ответит на каждую.

Экзамен 13 июня 2025 года был про концерты, и его задание по Redis начиналось с сущности Instrument. Сначала: "Create a set of instruments including "Keyboard", "Violin", and "Drums"". Потом, за один балл: "Perform an operation to add "Flute" to the set, with time to live equal to 10".

Очевидный ответ — две команды, и Redis принимает обе: SADD instruments "Flute", затем EXPIRE instruments 10. Через одиннадцать секунд кто-то выполняет SISMEMBER instruments "Keyboard".

Что ответит Redis — 1 или 0? Запиши свою догадку. Последний раздел урока даст ответ и покажет, как сформулировать ответ, за который не снимут баллы.

Строки, ключи и счётчик, который не теряет

Каждая команда Redis называет ключ и говорит, что сделать со значением, которое под ним лежит. Самое простое значение — строка (string): кусок текста или число. На занятии её сохраняют командой SET и читают командой GET; для чтения "The only requirement is that we need to know the key_name" (p. 1582) — достаточно знать имя ключа. Лекция прогоняет эту пару на ключе foo (p. 355):

В блоках кода redis> — это приглашение, а строка под командой — ответ. На экзамене ты пишешь только команды, по одной в строке.
redis> SET foo "hello!"
OK
redis> GET foo
"hello!"

Читай это как разговор. SET отвечает OK и молча заменяет всё, что было под ключом; GET отвечает значением в кавычках или (nil), если такого ключа нет. Ключ или значение с пробелами берутся в двойные кавычки: экзамен 24 июня 2024 года хочет ключ с именем "Line #0001" и значением "A long time ago in a galaxy far, far away". На слайдах напечатаны типографские кавычки (“hello!“); набирай прямые.

Четыре команды работают с ключом целиком, какого бы типа он ни был (p. 356, pp. 1583–1584). EXISTS "returns a value of 1 if the field exists, 0 otherwise"; DEL удаляет ключ и отвечает, сколько ключей удалил; TYPE называет структуру под ключом; RENAME переносит значение под новое имя.

redis> EXISTS foo
(integer) 1
redis> TYPE foo
string
redis> RENAME foo greeting
OK
redis> GET greeting
"hello!"
redis> DEL greeting
(integer) 1
redis> EXISTS greeting
(integer) 0
redis> GET greeting
(nil)

Лекция добавляет четыре вспомогательные команды (p. 355). MSET и MGET пишут и читают несколько ключей за один обмен с сервером, STRLEN даёт длину, а GETSET сохраняет новое значение и возвращает старое. Ответ GETSET на слайде пропущен: это старое значение, "hello!".

redis> MSET foo "hello!" bar 1223
OK
redis> MGET foo bar
1) "hello!"
2) "1223"
redis> STRLEN foo
(integer) 6
redis> GETSET foo "bye!"
"hello!"

Посмотри на "1223": оно вернулось в кавычках. Redis хранит любое число как строку и читает его как целое, только когда команде нужно целое.

Счётчики и обновление, которое теряется

Строки, в которых лежат целые числа, умеют считать. Занятие перечисляет четыре команды (p. 1585): "INCR – Increases the value by 1", "DECR – Decreases the value by 1", "INCRBY – Increases the value by the amount set", "DECRBY – Decreases the value by the amount set". Отсутствующий ключ считается за 0, так что первый INCR нового счётчика отвечает 1; значение, которое не является целым числом, — как "bye!", что сейчас лежит в foo, — получает ошибку:

redis> INCR visits
(integer) 1
redis> DECR visits
(integer) 0
redis> DECRBY visits 5
(integer) -5
redis> INCR foo
(error) ERR value is not an integer or out of range

Пример лекции (p. 355) прибавляет тысячу за один шаг:

redis> SET bar 223
OK
redis> INCRBY bar 1000
(integer) 1223

Дальше занятие задаёт честный вопрос. Клиент мог бы прибавить единицу теми командами, что у него уже есть (p. 1586):

> x = GET key_name
  x = x + 1
  SET key_name x

"The proposed script is a general way of executing the increasing or decreasing operations. Then, why do we need them?" — то есть зачем вообще нужны отдельные команды? Ответ (pp. 1588–1593): два клиента оба делают GET и получают 10, оба у себя вычисляют 11, оба делают SET 11. Просили два инкремента, а счётчик сдвинулся на один: "Using the script will cause these two increases to be applied incorrectly!" Это потерянное обновление (lost update).

Атомарная операция (atomic operation) — операция, которая выполняется как один неделимый шаг: между её чтением и записью не может выполниться команда другого клиента. Словами занятия: "ATOMIC OPERATIONS are not affected by problems in case of concurrent access" (p. 1587).

Начиная с Redis 6 сетевой ввод-вывод может использовать дополнительные потоки; сами команды по-прежнему выполняются по одной.

Почему INCR атомарен, а три строчки — нет? Три строчки — это три обращения: чтение, сложение на клиенте, запись. Между чтением и записью остаётся окно, и туда может попасть чтение или запись другого клиента. INCR делает чтение, +1 и запись внутри сервера, одной командой, — а сервер выполняет команды по одной. Лекция говорит это в двух строчках (p. 352): "Redis is a single-threaded server" и "All operations are atomic (no two commands can run at the same time)". Никаких блокировок: пока выполняется одна команда, не выполняется ничего другого.

Инкремент безопасен, только когда его чтение и запись происходят внутри одной команды.

Два клиента, один счётчик

Картинка занятия (pp. 1588–1593) в виде последовательности, которую можно проиграть заново; время идёт сверху вниз. Выбери, что отправляет каждый клиент и в каком порядке шаги доходят до Redis, и жми «Дальше». Средняя дорожка — счётчик, который хранится в Redis, боковые — значение, которое держит у себя каждый клиент; серые подписи — шаги, которые ещё впереди.

  1. Оставь GET, +1, SET и порядок со слайда. Прежде чем шагать, предскажи значение счётчика на последнем шаге. Потом пройди по шагам: на каком шаге потеря уже предрешена?
    Что ты должен увидеть

    11. Потеря предрешена на шаге 3, когда клиент 2 читает 10, хотя клиент 1 вот-вот запишет 11: с этого момента оба клиента вычисляют 11, а две команды SET только делают это видимым. Ровно это виджет и должен показать: инкремент теряется, когда команда другого клиента попадает между твоими GET и SET.

  2. Попробуй три других порядка. Для каждого до прохода предскажи: 11 или 12?
    Что ты должен увидеть

    До 12 доходит только «клиент 2 после записи клиента 1». В трёх остальных один клиент читает между чтением и записью другого, так что оба стартуют с 10. Даже когда клиент 2 заканчивает первым («клиент 2 целиком в окне клиента 1»: читает и пишет, пока клиент 1 ждёт), запоздалый SET клиента 1 записывает своё устаревшее 11 поверх 11 клиента 2.

  3. Переключись на одну команду INCR и проиграй все четыре порядка. Что меняется и почему теперь ни один порядок не может потерять инкремент?
    Что ты должен увидеть

    Каждый порядок заканчивается на 12. Весь инкремент каждого клиента — одна команда, а Redis выполняет команды по одной ("no two commands can run at the same time", p. 352): между чтением и записью не остаётся окна, куда мог бы попасть другой клиент. Порядок решает только, кому вернётся 11, а кому 12.

То же лекарство ты знаешь из SQL: UPDATE counters SET value = value + 1 поручает сложение базе, а не клиенту. Одна команда получает ту изоляцию, которую урок 3 требовал от целой транзакции.

«Скрипты Redis не атомарны». Занятие называет три строчки "(a sort of) scripting" (p. 1586), но это три отдельные команды, которые шлёт клиент, а сложение делает сам клиент. Настоящие скрипты Redis — это код на Lua, который выполняется внутри сервера (среди преимуществ Redis он значится как "LUA scripting support", p. 365), и они выполняются атомарно, как одна команда (документация Redis, справочно). Объясняй атомарность однопоточным сервером, а не словом «script» со слайда.

Ключи со сроком жизни

Redis часто работает как кэш, а кэш должен забывать сам: сессию, которой никто не пользуется, страницу, которая устарела. Поэтому у любого ключа могут быть свои часы. Занятие называет такие пары "temporary key-value pairs" и даёт две команды (p. 1594): "EXPIRE – Set the lifespan of a variable (in seconds)" и "TTL – Returns the remaining lifespan of a variable (in seconds)". На слайде лекции (p. 356):

redis> EXPIRE foo 10
(integer) 1
redis> TTL foo
(integer) 10

EXPIRE отвечает 1, если завёл часы, и 0, если ключа нет. "PEXPIRE and PTTL achieves the same operations in milliseconds" (p. 1594) — достаточно точно, чтобы увидеть, сколько времени ушло на набор:

redis> PEXPIRE foo 60000
(integer) 1
redis> PTTL foo
(integer) 58904

Когда часы доходят до нуля, Redis удаляет ключ ровно так, как это сделал бы DEL: весь ключ, что бы в нём ни лежало.

TTL отвечает тремя способами, и экзаменационное "check its lifespan" — как раз про них (p. 1595): оставшиеся секунды; "-1 – The key will never expire"; "-2 – The key has already expired". Читай -2 как «такого ключа нет»: Redis отвечает одинаково для ключа, который истёк, был удалён или никогда не существовал. Три ответа — это три состояния ключа, и горстка команд переводит ключ между ними.

Первый переход — короткий путь: SET принимает срок жизни как опцию, так что значение и часы приходят одной командой (p. 1595). Это естественный ответ на "Create a key-value pair with "best_book", the value "La ragazza delle Arance", and TTL equal to 100" (экзамен 21 января 2025):

redis> SET best_book "La ragazza delle Arance" EX 100
OK

Следующая фраза слайда прячет ловушку: "whenever the key is SET, the TTL is reset". Reset здесь значит «удалён», а не «запущен заново». Простой SET заменяет значение и выбрасывает часы, и ключ становится постоянным:

redis> SET k "v" EX 100
OK
redis> SET k "w"
OK
redis> TTL k
(integer) -1

Команды, которые меняют значение на месте, — INCR, LPUSH, SADD, HSET — часы не трогают, а RENAME уносит их с собой под новое имя (документация Redis, справочно). Последний переход убирает часы намеренно: "The PERSIST operator can be used to solve such a problem. It permanently stores a temporary variable in the database" (p. 1596). Он отвечает 1, если снял таймаут, и 0, если таймаута не было:

redis> PERSIST best_book
(integer) 1
redis> TTL best_book
(integer) -1

«PERSIST записывает ключ на диск». Нет: он только снимает срок жизни. Сохранение данных на диск — снапшоты и append-only файлы — тема урока 19. Экзаменационное "make it permanently stored" (21 января 2025) означает PERSIST.

Списки: два конца и включительные индексы

Список (list) — последовательность строк в фиксированном порядке, повторы разрешены. Строится он с любого конца (p. 1597): "RPUSH – Puts one or more new elements at the end of the list" и "LPUSH – Puts one or more new elements at the beginning of the list". "If the key does not exist, it will be created. A key with an empty list will be automatically deleted." Обе команды отвечают длиной списка после вставки. Вот список задач jobs из лекции (p. 357) — с теми ответами, которые Redis даёт на самом деле:

redis> RPUSH jobs "foo"
(integer) 1
redis> LPUSH jobs "bar"
(integer) 2
redis> LRANGE jobs 0 -1
1) "bar"
2) "foo"

redis> RPUSH jobs “foo” (integer) 1 redis> LPUSH jobs “bar” (integer) 1

Второй ответ — (integer) 2: RPUSH и LPUSH отвечают длиной списка после вставки.

В jobs уже лежал "foo", так что после LPUSH в нём два элемента — собственный LRANGE jobs 0 -1 слайда выводит "bar" и "foo". Запусти в консоли раздела 5 сценарий «Слайд 357: список jobs» — тот же сеанс, что на слайде (p. 357), — и ответ будет 2. Экзамен могут сверять со слайдом: знай, что там напечатано 1, а Redis отвечает 2, и если в вопросе показан этот обмен, скажи, где что.

Если в одной команде несколько значений, два конца ведут себя по-разному. RPUSH дописывает их по одному в хвост, так что они сохраняют порядок, в котором ты их набрал. LPUSH ставит их по одному в голову, каждое перед предыдущим, так что порядок получается обратным.

Это закрывает экзамен 24 июня 2024 года, "create a new list of lines involving the lines "Hey you", "Watch out", and "Hello there"": с RPUSH первая набранная строка становится первой сохранённой.

Чтение диапазона

Слайд говорит, что первый индекс — "positive" число, "e.g., 0, 1": читай «неотрицательное». Он может быть и отрицательным: LRANGE l -3 -1 даёт последние три.

"The LRANGE operator can be used to retrieve a subset of values from a list" (p. 1598), пишется LRANGE key first_index last_index. Что вернётся, решают три правила. Индексы начинаются с 0. Отрицательный индекс считается с конца: -1 — последний элемент, -2 — предпоследний. И оба конца включены — в отличие от среза в Python, где l[0:2] останавливается перед индексом 2.

redis> RPUSH lines "Hey you" "Watch out" "Hello there"
(integer) 3
redis> LRANGE lines 0 2
1) "Hey you"
2) "Watch out"
3) "Hello there"

Слайд формулирует отрицательную границу иначе: "Negative numbers (e.g., -N) mean that the operator will return all values besides the last N-1 values (e.g., -2 means that we are collecting all the elements, besides the last one)". Это то же правило, только отсчитанное с хвоста: в списке из L элементов граница -N — это позиция L − N.

Достаём элементы: очереди и стеки

"LPOP – Removes the first item of the list and returns it", "RPOP – Removes the last item of the list and returns it", а LLEN даёт длину (p. 1599). LINDEX key index читает один элемент, не удаляя его (p. 357). Скомбинируй концы — и получишь две классические структуры: RPUSH с LPOP — это очередь (первым пришёл — первым ушёл), LPUSH с LPOP — стек (последним пришёл — первым ушёл).

redis> RPUSH q "job1" "job2" "job3"
(integer) 3
redis> LINDEX q 1
"job2"
redis> LPOP q
"job1"
redis> RPOP q
"job3"
redis> LLEN q
(integer) 1

Две списковые команды созданы для очередей задач (p. 357). RPOPLPUSH src dst снимает последний элемент одного списка и кладёт его в голову другого за один атомарный шаг: слайд переносит "foo" из jobs в proc, и в любой момент задача лежит в одном из двух списков. BLPOP и BRPOP — это блокирующие pop (blocking pops): на пустом списке клиент ждёт, пока не придёт элемент или не истечёт таймаут, — те самые "Blocking queues" среди сценариев использования из лекции (p. 350). На списке jobs выше ответ называет список, потому что одна команда может следить за несколькими:

redis> BLPOP jobs 0
1) "jobs"
2) "bar"

Blocking Pop BRPOP/BLPOP [key] O(1) redis> BLPOP jobs redis> BRPOP jobs

Таймаут обязателен: BLPOP key [key …] timeout, в секундах, и 0 значит «ждать вечно» — BLPOP jobs 0.

Без него Redis отвергает команду: (error) ERR wrong number of arguments for 'blpop' command — попробуй в консоли раздела 5. Pop, который ждёт, должен знать, сколько клиент готов ждать. Экзамен могут сверять с напечатанной на слайде формой: узнавай её, а в своих ответах пиши таймаут.

Проверка принадлежности — слабое место списка. Для "Check whether the animal "Bob" is in a list of animals named "Farm"" (экзамен 12 сентября 2025) на слайдах нет списковой команды: ты читаешь весь список через LRANGE Farm 0 -1 или спрашиваешь LPOS Farm "Bob" (Redis 6.0.6 и новее, справочно), который отвечает позицией или (nil). Обе команды проходят по списку — слайд помечает LINDEX и LRANGE как O(N). Когда вопрос звучит «есть ли там X?», структура, созданная для этого, — множество.

Множества, sorted sets и хеши

Множество (set) отбрасывает и порядок, и повторы: "SETS are similar to lists, but they don't have a specific value order, and each value can only appear once per set. SETS are useful as it is very quick to test the existence of a value, which is not as easy when it comes to lists" (p. 1600) — главное, что в множестве очень быстро проверить, есть ли значение. Его команды начинаются на S. SADD и SREM добавляют и удаляют элементы, SISMEMBER "Returns 1 if the value is part of the set, 0 otherwise", SMEMBERS "Returns all the members in the set" (p. 1601), а SCARD, которой на слайдах нет, их считает.

redis> SADD instruments "Keyboard" "Violin" "Drums"
(integer) 3
redis> SADD instruments "Violin"
(integer) 0
redis> SISMEMBER instruments "Flute"
(integer) 0
redis> SREM instruments "Drums" "Piano"
(integer) 1
redis> SCARD instruments
(integer) 2
redis> SMEMBERS instruments
1) "Keyboard"
2) "Violin"

SADD – Adds one or more values to a set. Returns 1 if the element is correctly added, 0 otherwise.

SADD возвращает число реально добавленных значений; значения, которые уже были в множестве, не считаются. Ответ 1 или 0 бывает, только когда передано одно значение. SREM, описанная так же, возвращает число удалённых значений.

Слайд лекции это показывает: SADD users "John" "Peter" отвечает (integer) 2 (p. 358); выше три инструмента отвечают 3, а SREM для "Drums" и "Piano" отвечает 1, потому что Piano в множестве никогда не было. Экзамен могут сверять с фразой занятия: если вопрос «верно/неверно» её цитирует, помни, что она описывает случай одного значения; с несколькими значениями ответ — количество.

Множества ещё и комбинируются. В примере лекции (p. 358) users = {John, Peter} и admins = {Peter}:

redis> SADD admins "Peter"
(integer) 1
redis> SADD users "John" "Peter"
(integer) 2
redis> SINTER users admins
1) "Peter"
redis> SUNION users admins
1) "John"
2) "Peter"
redis> SDIFF users admins
1) "John"

У множества нет порядка, поэтому Redis может перечислить элементы ответа в любом порядке — на слайде первым оказался "Peter". "SUNION – Combines two or more sets into one set" (p. 1601) возвращает объединение, не сохраняя его; SUNIONSTORE dest key1 key2 сохраняет его под новым ключом (справочно). SPOP удаляет и возвращает случайный элемент (p. 358). Блок SINTER на том же слайде (p. 358) есть в тексте слайда, но на отрисованной странице спрятан под другим блоком; его пример — тот, что выше.

Diff. multiple sets DIFF [key key …] O(N)

Команда называется SDIFF, как в строке примера того же блока (SDIFF users admins); все команды множеств начинаются на S.

DIFF — не команда Redis: Redis отвечает (error) ERR unknown command 'DIFF', with args beginning with: … — сценарий консоли «Слайд 358: множества» (p. 358) выполняет обе. Экзамен могут сверять со слайдом, так что закрытый вопрос может напечатать его заголовок; в своём ответе пиши SDIFF, с ключами в правильном порядке.

Sorted sets: множество со score

"Since sets are not ordered, Redis introduced the concept of an ORDERED SET. In an ORDERED SET, each element of the set is assigned to a score that is used to define the order in the set" (p. 1602). Слайд лекции называет эту структуру сортированное множество (sorted set) (p. 358), и документация Redis тоже: два имени, одна структура. Элементы остаются уникальными, как в множестве; их место решает score — числовой вес с плавающей точкой, от меньшего к большему, а при равных score — по алфавиту.

redis> ZADD scores 100 "John"
(integer) 1
redis> ZADD scores 50 "Peter" 200 "Charles" 1000 "Mary"
(integer) 3

Score идёт первым, ZADD key score member, пар можно сколько угодно, а ответ считает новые элементы. ZRANGE key start stop (p. 1602) читает по позиции в порядке score, с теми же включительными индексами, что и LRANGE, и отрицательные тоже работают; добавь WITHSCORES, чтобы увидеть score, и REV (Redis 6.2 и новее, справочно), чтобы начать с наибольшего.

redis> ZRANGE scores 0 -1 WITHSCORES
1) "Peter"
2) "50"
3) "John"
4) "100"
5) "Charles"
6) "200"
7) "Mary"
8) "1000"
redis> ZRANGE scores 0 0 REV
1) "Mary"
redis> ZRANK scores "Mary"
(integer) 3
redis> ZRANGEBYSCORE scores 200 +inf WITHSCORES
1) "Charles"
2) "200"
3) "Mary"
4) "1000"
redis> ZINCRBY scores 10 "Mary"
"1010"
redis> ZREMRANGEBYSCORE scores 0 100
(integer) 2

Все ответы sorted set на слайде (p. 358) сходятся. Ранги начинаются с 0, так что у Mary, старшей из четырёх, ранг 3. ZRANGEBYSCORE включает свои границы и принимает +inf. ZINCRBY отвечает новым score, в виде строки. Диапазон 0–100 удаляет Peter (50) и John (100). Именно эта структура стоит за "Create a list to store all Department specialties, sorted by their foundation year. Then, query the list to get the older one" (экзамен 30 января 2026): год — это score, а самая старая — ZRANGE key 0 0. Так же ты хранил бы лучший чекпойнт обучения модели: validation loss как score, и ранг 0 — та модель, которую нужно оставить.

Хеши: один объект под одним ключом

"HASHES are mappings between string fields and string values" (p. 1603): маленький словарь под одним ключом, очень похожий на dict в Python. Поэтому хеш (hash) — дом для одного объекта и его атрибутов. Ключ несёт тип и id объекта — user:1 на слайде (p. 357), — а каждый атрибут становится полем:

redis> HSET user:1 name John
(integer) 1
redis> HMSET user:1 lastname Smith visits 1
OK
redis> HGET user:1 name
"John"
redis> HGETALL user:1
1) "name"
2) "John"
3) "lastname"
4) "Smith"
5) "visits"
6) "1"

HSET принимает несколько пар «поле–значение» в одной команде (p. 1603) и отвечает, сколько полей новые; HMSET из лекции (p. 357) — более старое написание, и оно всё ещё работает. HGETALL отвечает одним плоским списком: поле, значение, поле, значение. HINCRBY держит счётчик внутри объекта и атомарен, как INCR:

redis> HINCRBY user:1 visits 1
(integer) 2

Часы по-прежнему принадлежат всему ключу. У HSET нет опции EX, так что "a single key-value pair to store all the data of one Gas Heater, with a TTL of 100" (30 января 2026) требует двух команд: HSET, потом EXPIRE. Допиши EX 100 в конец HSET — и Redis не выдаст ошибки: он сохранит поле с именем "EX" и значением "100", а ключ никогда не истечёт.

От фразы экзамена к командам

В пяти из девяти прошлых экзаменов есть задание по Redis, а правила 2026/27 называют Redis среди тем практической части. Каждое из пяти начинается с сущности из ER-диаграммы этого экзамена, стоит от 3 до 5 баллов (пункты по 1 или 2) и требует одних и тех же двух ходов: узнать структуру в формулировке, а потом написать её команды. В таблице собраны фразы всех пяти.

Помимо команд, помогают две привычки. Называй ключи по сущности из диаграммы и бери в кавычки всё, где есть пробел. А когда фраза просит то, что Redis не умеет сделать дословно, напиши ближайшие команды и добавь одно предложение о том, что Redis делает вместо этого: readme к прошлым экзаменам предупреждает, что "Exams might include minor typos", и просит "consider all the necessary assumptions to solve the exercise" — то есть делать нужные допущения.

Сколько стоит каждая команда

Нынешняя документация Redis помечает четыре из этих имён как устаревшие (deprecated), хотя они по-прежнему работают: GETSET, HMSET, RPOPLPUSH и ZRANGEBYSCORE. Писать нужно имена со слайдов.

Слайды дают стоимость каждой команды. Лекция подытоживает это так: "It executes most commands in O(1) complexity" (p. 352); таблица раскладывает команды со слайдов (pp. 355–358) по стоимости.

Документация Redis кое-где уточняет эти цифры: команда диапазона платит ещё и за то, что возвращает, так что ZRANGEBYSCORE стоит O(log(N)+M). На экзамене цитируй слайды.

У этой картины есть причина (документация Redis, справочно). Ключ находится по хешу, поэтому всё, что касается одного ключа и одного элемента, стоит O(1). Список связный, так что два его конца дешёвые, а середина — нет: LINDEX и LRANGE по нему проходят. Множество — это хеш-таблица, поэтому SISMEMBER стоит O(1), тогда как просмотр списка — O(N). Sorted set держит элементы упорядоченными в skip list (списке с пропусками), поэтому вставка и поиск по score стоят O(log(N)). Команды, которые отдают структуру целиком, SMEMBERS или HGETALL, стоят O(N) от её размера.

Читать ответы — один навык; предсказывать их — тот, что нужен на экзамене. Консоль ниже запускает маленький Redis прямо на этой странице, со всеми командами урока, и проигрывает сеансы со слайдов и пять экзаменов по строчке.

Redis на твоей странице

Набери команду и нажми Enter или выбери сценарий и выполняй его строка за строкой, предсказывая каждый ответ до того, как он появится. Каждый ключ — карточка с именем, типом, часами и элементами; у списка под каждым элементом видны оба индекса. Время стоит, пока ты его не сдвинешь: «Пустить время» отсчитывает одну секунду в секунду, «+1 s» и «+10 s» прыгают вперёд, а «Сбросить» очищает базу. Ответы такие же, как в redis-cli; несколько редких команд не реализованы, и консоль об этом говорит.

  1. Выбери «Экзамен 13.06.2025: Instrument» и жми «Следующая строка», пока не выполнится EXPIRE instruments 10. Предскажи: что ответят SISMEMBER instruments "Keyboard" и TTL instruments после одиннадцати секунд, которые идут следом? Потом выполни остальное.
    Что ты должен увидеть

    0 и -2. На t = 10 s журнал сообщает, что ключ instruments истёк вместе со всеми четырьмя элементами, и его карточка исчезает. Ради этого инсайта консоль и построена: TTL принадлежит ключу, поэтому всё, что лежит под ключом, уходит разом.

  2. Выбери «Слайд 357: список jobs» (сеанс со слайда, p. 357). Прежде чем выполнить LPUSH jobs "bar", предскажи ответ (на слайде напечатано (integer) 1). Продолжай до BLPOP jobs.
    Что ты должен увидеть

    (integer) 2 — длина после вставки. BLPOP jobs, набранный так, как напечатан на слайде, получает (error) ERR wrong number of arguments for 'blpop' command: не хватает таймаута. BLPOP proc 0 в конце возвращает имя списка и элемент.

  3. Набери RPUSH r a b c и LPUSH l a b c и предскажи порядок на каждой карточке. Потом предскажи LRANGE r 0 -2 и LRANGE l -2 -1, прежде чем их выполнить.
    Что ты должен увидеть

    r читается a b c, а l — c b a; под каждым элементом карточка показывает его индекс с головы и с хвоста. LRANGE r 0 -2 даёт a, b (всё, кроме последнего); LRANGE l -2 -1 даёт b, a (последние два элемента l).

  4. Выбери «Две ловушки: EX не на своём месте». Предскажи ответ на SADD instruments "Flute" EX 10 и что ответит после этого TTL instruments.
    Что ты должен увидеть

    (integer) 3 и -1. У SADD нет опций, так что "Flute", "EX" и "10" все стали элементами, а часы не завелись. HSET … EX 100 делает то же самое с полем по имени "EX". EX принимает только SET; любой другой структуре нужен отдельный EXPIRE.

Флейта: развязка

Вернёмся к загадке. Через одиннадцать секунд после EXPIRE instruments 10 команда SISMEMBER instruments "Keyboard" отвечает 0. Часы были заведены на ключ instruments; на t = 10 s Redis удалил ключ, а вместе с ним и все элементы — Keyboard, Violin и Drums, не только Flute. TTL instruments теперь отвечает -2.

Свежий Redis (7.4 и новее) умеет задавать срок жизни отдельным полям хеша; списки, множества и sorted sets — по-прежнему нет. В курсе это не используется.

Так что надёжный ответ — две команды и одно предложение: SADD instruments "Flute", EXPIRE instruments 10 и "in Redis a TTL belongs to a key, so the whole set expires after 10 seconds; a single member cannot have its own". Если исчезнуть должна только Flute, ей нужен собственный ключ, например SET instrument:Flute "Flute" EX 10. Чего писать нельзя — это SADD instruments "Flute" EX 10: у SADD нет опций, и Redis добавит ещё два элемента, "EX" и "10".

TTL принадлежит ключу — никогда не отдельному элементу списка, множества или sorted set.

Вопросы в стиле экзамена

Пять заданий по Redis из прошлых экзаменов, каждое — после той части ER-диаграммы, которую оно использует, и затем два теоретических вопроса в формах письменного экзамена. Официальных решений нет: образцовые ответы наши, и каждая команда и каждый ответ в них проверены на эмуляции Redis.

Exam of 24 Jun 2024, exercise 5 — Redis (3 PT). ER (tracking Disney's digital products), the part used: Script (ID, Length, Duration, Title) and Line (ID, Sequence Number, Text), linked by Include: Script 1:N – Line 1:1.

"Consider the Line table. Write the Redis code to create a new list of lines involving the lines "Hey you", "Watch out", and "Hello there". (1 PT)"

"Write the Redis operation to collect the first three lines in the list. (1 PT)"

"Write the Redis operations to create a new key-value pair named "Line #0001" with the value "A long time ago in a galaxy far, far away" and check its lifespan. (1 PT)."

Показать образцовый ответ 
RPUSH lines "Hey you" "Watch out" "Hello there"
LRANGE lines 0 2
SET "Line #0001" "A long time ago in a galaxy far, far away"
TTL "Line #0001"

Redis answers (integer) 3; then the three lines in the order given; then OK and (integer) -1, because a key created with a plain SET has no expiry.

Что важно не перепутать: RPUSH, потому что LPUSH сохранил бы строки в обратном порядке и «первые три» начинались бы с "Hello there"; включительная правая граница LRANGE (0 2 — три элемента, 0 3 запросил бы четыре); кавычки вокруг ключа с пробелом; и TTL для "check its lifespan" — если скажешь, что ответ будет -1, покажешь, что понимаешь, что это значит.

Exam of 21 Jan 2025, exercise 4 — Redis (4 PT). ER (tracking Netflix's digital content), the part used: Book (ID, name, number_volumes, publication_date); Write: Book 1:1 – Writer 1:N; Inspired: Cartoon 0:1 – Book 0:N.

"Consider the Book entity and write the commands for the following operations. Create a key-value pair with "best_book", the value "La ragazza delle Arance", and TTL equal to 100 (1 PT)"

"Check the TTL of the key-value pair "best_book" and make it permanently stored (1 PT)"

"Assume there exists a set named "HP Books" that includes all the Harry Potter books besides the first one. Add the movie "Harry Potter and the Philosopher Stone" to the set. (1 PT)"

"Check if the last movie "Harry Potter and the Deadly Hallows" is part of the set (1 PT)"

Показать образцовый ответ 
SET best_book "La ragazza delle Arance" EX 100
TTL best_book
PERSIST best_book
SADD "HP Books" "Harry Potter and the Philosopher Stone"
SISMEMBER "HP Books" "Harry Potter and the Deadly Hallows"

Replies: OK; the seconds left (at most 100), then (integer) 1, after which TTL best_book would answer -1; (integer) 1, one new member; (integer) 1 if the title is in the set, as it should be since the set holds every book but the first, otherwise 0. SET best_book "La ragazza delle Arance" followed by EXPIRE best_book 100 is an equally correct first answer.

Что важно не перепутать: EX или EXPIRE для TTL; TTL перед PERSIST, потому что пункт просит сначала проверить, а потом сделать постоянным; кавычки вокруг HP Books; SISMEMBER, а не SMEMBERS, для "check if". "Permanently stored" значит «без срока жизни», а не «запись на диск». Redis сравнивает строки точно: в задании написано "Deadly Hallows" вместо Deathly Hallows, так что написание должно совпадать с тем, что лежит в множестве.

Exam of 13 Jun 2025, exercise 4 — Redis (3 PT). ER (tracking concert attendances and performances), the part used: Instrument (Name, Type (e.g., chordophones), Description); Play – Since: Musician (1,N) – Instrument (1,N).

"Perform an operation to check whether "Flute" is part of the set (1 PT)"

Exam of 12 Sep 2025, exercise 4 — Redis (three items of 1 PT). ER (tracking farmers and their sales at local markets), the part used: Animal (Tag, Name, Age, Animal Type (e.g., Cow), Breed); House – Housing Date: Animal (1, 1) – Farm (1, N).

Exam of 30 Jan 2026, exercise 5 — Redis (5 PT). Показать образцовый ответ

(c) SUNION возвращает объединение; SUNIONSTORE all:specialties hospital1:specialties hospital2:specialties сохраняет его под новым ключом.

Redis offers INCR and INCRBY, although a client could read a value with GET, add one, and write it back with SET. Why are these commands needed? Explain what "atomic" means here and why Redis can guarantee it.

Показать образцовый ответ

GET, +1 and SET are three separate steps: the client reads the value, computes the new one on its side and writes it back. Between the read and the write another client can read the same old value, so two concurrent increments both write 11 over 10 and one of them is lost. INCR performs the read, the increment and the write inside the server, as one command. An atomic operation is indivisible: no other client's command can run in the middle of it, so it is not affected by concurrent access. Redis can guarantee this because it is a single-threaded server that executes one command at a time — no two commands can run at the same time — so every single command is atomic without any lock, and two INCR commands always add 2. The same holds for DECR, INCRBY, DECRBY and HINCRBY.

Полный ответ называет три вещи: потерянное обновление как конкретную проблему, «атомарность» как неделимость относительно других клиентов и единственный поток как причину. «Redis блокирует ключ» — неверно: блокировки нет, просто никакая другая команда в этот момент не выполняется.

A key is created with SET session "abc" EX 60. Twenty seconds later a client runs SET session "xyz". What does TTL session return right after?

  • 40 Для этого новый SET должен был бы сохранить старые часы. Простой SET их удаляет (сохранила бы их только опция KEEPTTL, которая в курсе не используется).
  • 60 Фраза слайда "whenever the key is SET, the TTL is reset" не значит, что старые часы запускаются заново: они удаляются.
  • -1 Простой SET заменяет значение и снимает таймаут: ключ теперь постоянный.
  • -2 -2 значит, что такого ключа нет; а этот ключ существует, его просто перезаписали.
Показать образцовый ответ

-1. SET overwrites the value and discards any time to live unless the new SET carries its own EX; the key now never expires.

Ловушка — слово "reset" на слайде (p. 1595). Неверный ответ на закрытый вопрос может стоить баллов: если колеблешься между 40 и 60, вспомни, что простой SET записывает совершенно новое значение без часов.

Проверь себя

Список q построен так: RPUSH q "a", потом RPUSH q "b", потом RPUSH q "c". Что вернёт LPOP q?

  • "a" RPUSH дописывает в хвост, а LPOP берёт из головы: первым пришёл — первым ушёл, это очередь.
  • "c" "c" лежит в хвосте; его вернул бы RPOP. Брать с того же конца, куда добавлял, — это схема стека.
  • "b" LPOP никогда не берёт из середины: pop работает только на двух концах, поэтому он и стоит O(1).
  • (nil) В списке три элемента; (nil) бывает только у пустого или отсутствующего списка.

У списка jobs TTL 50 секунд. Какие команды оставят его часы идти? Выбери все верные.

  • RPUSH jobs "x" Она меняет список на месте, и таймаут остаётся.
  • RENAME jobs work Значение переезжает под новое имя и забирает часы с собой.
  • SET jobs "done" SET заменяет список строкой и снимает часы: "whenever the key is SET, the TTL is reset" (p. 1595).
  • PERSIST jobs PERSIST — как раз та команда, которая снимает часы.

Меняешь значение на месте — часы остаются. Заменяешь значение или делаешь PERSIST — часы уходят.

В списке l лежат a b c d e. Что вернёт LRANGE l 1 -2?

  • b c d Начинаем с индекса 1 (b), заканчиваем на -2 (d, предпоследний), оба конца включены.
  • b c Это l[1:-2] в Python, где срез останавливается перед конечным индексом; LRANGE его включает.
  • a b c d Начало — 1, а не 0, так что a пропускается.
  • c d Индекс 1 — это второй элемент, b: LRANGE считает с 0.

Ключа tags ещё нет. Что ответит SADD tags "red" "blue" "red"?

  • (integer) 2 Реально добавлено два значения; когда пришло второе "red", оно уже было в множестве.
  • (integer) 3 Множество хранит каждое значение один раз, а ответ считает только реально добавленные.
  • (integer) 1 Фраза занятия "Returns 1 if the element is correctly added" описывает одно значение; когда их несколько, ответ — количество.
  • ошибка Повторы — не ошибка: они просто игнорируются.

Система должна всегда показывать три товара с наибольшими продажами, а продажи меняются каждую минуту. Какая структура подходит лучше всего?

  • Sorted set с продажами в качестве score ZINCRBY обновляет score за O(log(N)) и сохраняет порядок; ZRANGE sales -3 -1 читает три самых больших.
  • Список Список хранит порядок вставки, а не порядок продаж: при каждом обновлении пришлось бы самому искать и переставлять элемент.
  • Множество У множества вообще нет порядка.
  • Хеш с одним полем на товар Поля тоже не упорядочены; пришлось бы читать их все через HGETALL и сортировать самому.

Почему два INCR от двух клиентов по одному ключу никогда не теряют обновление?

  • Redis выполняет команды по одной, а INCR читает, прибавляет и пишет внутри одной команды "no two commands can run at the same time" (p. 352): второй INCR начинается только после того, как первый записал результат.
  • Redis блокирует ключ, пока клиент с ним работает Блокировок нет: пока выполняется одна команда, не выполняется ничего другого.
  • Клиент повторяет INCR, пока не получится Ничего не повторяется; INCR не может не сработать из-за другого клиента.
  • Redis хранит номер версии для каждого ключа Никаких версий: вся причина — в единственном потоке.

TTL k отвечает -2. Что может быть правдой? Выбери все верные.

  • k истёк Это прочтение самого слайда: "The key has already expired".
  • k удалили командой DEL Удалённого ключа тоже не существует.
  • k никогда не существовал TTL отвечает -2 для любого несуществующего ключа.
  • k существует, но без срока жизни Тогда ответ -1.

-2 говорит только одно: сейчас такого ключа нет.

Главное

  • Задание по Redis — это два хода: узнать структуру в формулировке — строку, список, множество, sorted set или хеш — и написать её команды заглавными буквами, по одной в строке, с двойными кавычками вокруг всего, где есть пробел.
  • Для строк — SET, GET, MSET, MGET, STRLEN и GETSET; для любого ключа — EXISTS, DEL, TYPE и RENAME. INCR, DECR, INCRBY и DECRBY атомарны, потому что однопоточный сервер выполняет команды по одной, а GET, +1, SET от двух клиентов могут потерять обновление.
  • TTL принадлежит ключу. EXPIRE, PEXPIRE или SET … EX заводят часы; TTL отвечает оставшимися секундами, -1 для ключа без срока жизни и -2, если ключа нет; простой SET снимает часы, а PERSIST снимает их намеренно.
  • RPUSH сохраняет набранный порядок, LPUSH его переворачивает, и обе отвечают новой длиной; LRANGE считает с 0, включает оба конца и читает -1 как последний элемент; RPUSH с LPOP — это очередь, а блокирующему pop нужен таймаут.
  • Множества хранят уникальные элементы без порядка и отвечают на SISMEMBER за O(1); SADD и SREM отвечают, сколько элементов изменилось, а SINTER, SUNION и SDIFF комбинируют множества. Sorted sets упорядочивают элементы по score: ZADD key score member, ранги с 0, наименьший score — первым.
  • Хеш хранит один объект под одним ключом вида type:id, с командами HSET (несколько пар сразу), HGET, HGETALL и HINCRBY; для срока жизни нужен отдельный EXPIRE.
