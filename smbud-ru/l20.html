Колоночные хранилища и модель данных Cassandra

После этого урока ты сможешь объяснить, что колоночное хранилище выигрывает и чем за это платит, раскодировать столбец, сжатый кодированием длин серий (run-length encoding), нарисовать данные Cassandra так, как их рисуют слайды, — keyspace, column family, ключ строки (row key), столбцы из имени, значения и временной метки, суперстолбцы (super columns), — и сказать, почему таблицы Cassandra проектируют, начиная с запросов.

Лекция этого урока называется "Columnar Databases – Cassandra" (p. 396). Первая её половина определяет семейство: "The Column Oriented Database stores data in columns", "mainly used in OLAP" (p. 401). График (p. 405) показывает зачем: чтобы прочитать 4 байта из каждой 148-байтовой записи, строковому хранилищу нужно около 51 секунды — и столько же, около 51 секунды, чтобы прочитать все 148. Колоночное хранилище читает эти 4 байта примерно за секунду.

Потом лекция переходит к Cassandra — той самой базе из её заголовка, — и на слайде написано: "think of cassandra as row-oriented" (p. 417). А ещё раньше (p. 412) — "Often write-heavy workloads": нагрузка с преобладанием записи, полная противоположность аналитике.

Так колоночное хранилище Cassandra или нет? Правы оба слайда. К концу урока ты будешь знать, в каком смысле сказано каждое утверждение и как это сформулировать на экзамене.

Wide-column stores и нагрузка, для которой они созданы

Представь сервис сообщений: множество пользователей весь день пишут и читают короткие сообщения, без всякого порядка, и нет двух одинаковых почтовых ящиков. Слайд "Issues with today's workloads" (p. 399) описывает ровно это:

  • "Data large and unstructured" — данных слишком много для одной машины, и фиксированного набора полей нет;
  • "Lots of random reads and writes" — много мелких операций, а не одно длинное сканирование;
  • "Foreign keys rarely needed" — каждая запись читается сама по себе.

Его "Actual Needs" (реальные потребности): "Incremental Scalability", "Speed", "No Single point of failure", "Low cost (TCO) and admin" (TCO — total cost of ownership, совокупная стоимость владения) и "Scale out, not up" — добавлять обычные машины, а не покупать одну побольше (урок 3).

Следующий слайд (p. 397) помещает системы, построенные под такую нагрузку, среди семейств NoSQL из урока 5: "Data stored in 4 types: Document, Graph, Key-value, Wide-column". Эта часть лекции называется "Big Column Stores" (p. 398); конспект курса объясняет название: в одной строке может быть "a huge number of different columns and that is why columnar db are also often called Big Column stores" — огромное число разных столбцов.

Слайд (p. 400) напоминает теорему CAP из урока 5 — "Consistency: all nodes have same data at any time", "Availability: the system allows operations all the time", "Partition-tolerance: the system continues to work in spite of network partitions" — и указывает место Cassandra: "Eventual (weak) consistency, Availability, Partition-tolerance". Для почтового ящика это правильный выбор: сообщение, пришедшее на секунду позже, никому не вредит, а ящик, который не открывается, — вредит.

"at most 2 out of the 3 guarantees"

От устойчивости к разделению (partition tolerance) отказаться нельзя: в распределённой системе разделения сети обязательно случаются. Пока разделение длится, система жертвует либо согласованностью, либо доступностью — Cassandra по умолчанию жертвует согласованностью.

Узел, отрезанный от остальных, может только отказать (нет доступности) или ответить из своей копии (нет согласованности) — это рассуждение из урока 5, где слайд (p. 195) делает то же утверждение, а следующий (p. 196) его исправляет ("CA doesn't make any sense"). Экзамен могут проверять по напечатанной формулировке: знай её, а отвечай с поправкой.

"Eventual" — лишь значение по умолчанию: каждое чтение или запись указывает, сколько копий должно ответить (CL из раздела 4), так что отдельная операция может купить согласованность ценой ожидания — это и есть "tuneably consistent" со слайда (p. 438) (урок 22).

Колоночное хранение: читаем меньше, пишем больше

Прежде чем дойти до Cassandra, слайды (pp. 401–408) описывают другую конструкцию, у которой общее с ней только слово «column». Возьмём сеть магазинов, которая записывает каждую продажу в пять столбцов со слайда (p. 402): дата, магазин, товар, покупатель, цена. Кассир добавляет продажу каждые несколько секунд. Аналитик раз в ночь спрашивает выручку каждого магазина — два столбца из пяти, по всем продажам за всё время.

Слайд (p. 401): "The Column Oriented Database stores data in columns", "mainly used in OLAP(online Analytical Processing), Data Mining operations". OLAP — это вопрос аналитика: мало столбцов, очень много строк. Противоположность — OLTP (online transaction processing), вопрос кассира: целые записи, по одной за раз.

Следующий слайд (p. 402) сравнивает две раскладки. Строковое хранилище (row store) держит каждую запись одним куском: "+ easy to add/modify a record", "- might read in unnecessary data". Колоночное хранилище (column store) держит каждый столбец отдельным куском: "+ only need to read in relevant data", "- tuple writes require multiple accesses" (tuple, кортеж, — это запись). Вердикт: "suitable for read-mostly, read-intensive, large data repositories" — подходит для больших хранилищ, которые в основном читают.

Одна таблица, два способа положить её на диск

Шестнадцать продаж по восемь столбцов (квартал, дата, магазин, товар, покупатель, количество, цена, канал), по четыре байта на значение. Сверху — строковое хранилище: продажи одна за другой, по две в строке. Снизу — колоночное: по файлу на столбец. В ячейках напечатаны только квартал и цена. Выбери запрос: пунктирные рамки показывают, что каждая раскладка читает с диска, а подкрашенные ячейки — что нужно запросу. Два переключателя сжимают столбец квартала и меняют порядок строк.

  1. Оставь запрос «сумма price по кварталам». Прежде чем смотреть на показания, предскажи: какую долю байтов, прочитанных строковым хранилищем, запрос действительно использует? Потом сравни пунктирные рамки сверху и снизу.
    Что должно получиться

    Четверть: 128 из 512 байт. Строковое хранилище вынуждено прочитать все шестнадцать записей целиком; колоночное читает два файла, 128 байт, и больше ничего. Ради этого виджет и сделан: колоночное хранилище читает только те столбцы, которые называет запрос, — здесь 2 из 8.

  2. Переключи на «вся запись продажи 7», затем на «вставить новую продажу». Для каждого случая предскажи, сколько отдельных мест на диске затрагивает каждая раскладка.
    Что должно получиться

    1 против 8, оба раза. Запись — один кусок в строковом хранилище и восемь кусков в колоночном: восемь позиционирований головки (seek) и сборка по позиции, чтобы прочитать её, восемь записей, чтобы добавить. Это и есть минусы со слайда (p. 404) — время позиционирования, стоимость вставок, восстановление кортежей — и причина слов "read-mostly".

  3. Вернись к «сумма price по кварталам» и включи кодирование длин серий. Предскажи, сколько серий (runs) получится из столбца квартала, затем посмотри показание для 1,750 строк. Напоследок отсортируй строки по покупателю и предскажи снова.
    Что должно получиться

    Четыре серии, (Q1, 1, 3) (Q2, 4, 3) (Q3, 7, 5) (Q4, 12, 5): 48 байт вместо 64. На 1,750 строках они превращаются в тройки со слайда (p. 407), и 7,000 байт сжимаются до 48. При сортировке по покупателю соседние кварталы всегда различаются: 16 серий длины 1 заняли бы 192 байта, втрое больше сырого столбца, поэтому он остаётся несжатым (те же 1,750 кварталов (p. 407) в смоделированном случайном порядке: 1,306 серий, 15,672 байта). Кодирование длин серий окупается только на отсортированных или сгруппированных столбцах.

В числах: при \(N\) записях из \(m\) столбцов по \(w\) байт запрос, которому нужны \(k\) столбцов, читает

\[ \begin{aligned} \text{row store:}\quad & N \cdot m \cdot w \\ \text{column store:}\quad & N \cdot k \cdot w \end{aligned} \]

то есть колоночное хранилище читает долю \(k/m\): 2 столбца из 8 — четверть. Слайд (p. 403) перечисляет четыре "Pros" только по названиям; их механизмы (дополнительно, не со слайдов):

  • "Data compression": значения одного столбца одного типа и повторяются (см. ниже).
  • "Improved Bandwidth Utilization": каждый перемещённый байт принадлежит нужному столбцу.
  • "Improved Code Pipelining": один плотный цикл по массиву одного типа — по той же причине операция NumPy над целым массивом обгоняет цикл на Python.
  • "Improved cache locality": соседние значения в памяти — как раз те, что будут прочитаны следующими.

"Cons" со слайда (p. 404) — цена разрезания записей на части, и виджет показал каждый: "Increased Disk Seek Time" (запись живёт в \(m\) файлах), "Increased cost of Inserts" (одна запись — \(m\) операций записи), "Increases tuple reconstruction costs" (целые записи приходится склеивать обратно).

Слайд "Tuple Reconstruction" (p. 405) измеряет этот компромисс (рис. 1). Строковое хранилище тратит одно и то же время, что бы ни выбирал запрос, потому что всегда читает кортежи целиком; время колоночного растёт с числом выбранных байтов и догоняет строковое только около 125 из 148. Пункт "Large prefetch hides disk seeks in columns" отвечает на первый минус: если читать каждый файл столбца большими кусками, множество мелких прыжков превращается в несколько длинных чтений.

Тот же слайд показывает, как записи собираются обратно ("Construct"). Позиция \(i\) каждого столбца принадлежит записи \(i\): восстановление — это склейка (zip) по позиции, без всяких ключей. А prodID хранится одной серией (4,1,4) — значение 4, начиная с позиции 1, четыре раза: это сжатие со следующих двух слайдов.

Слайд (p. 406): сжатие "Trades I/O for CPU" — меньше байтов читать, немного декодировать, — а сканирование ждёт диск, так что обмен выгоден. Больше всех выигрывают колоночные хранилища: "Higher data value locality in column stores" (соседи принадлежат одному атрибуту), "Techniques such as run length encoding far more useful", а сэкономленное место "Can use extra space to store multiple copies of data in different sort orders" — по копии на каждый вид запроса.

Кодирование длин серий (run-length encoding, RLE) — серия одинаковых соседних значений хранится одной тройкой (value, start_pos, run_length): значение, его первая позиция, число строк.

Конспект курса записывает серию двумя полями, ("Q1", 200): значение и сколько раз оно повторяется. Третье поле слайда, начальная позиция, позволяет найти строку, не суммируя предыдущие серии.

Слайд (p. 407) кодирует таблицу продаж, отсортированную по кварталу (рис. 2): Quarter схлопывается в четыре тройки, Product ID — в короткие серии, а Price остаётся несжатым — соседние цены редко повторяются, и кодировку выбирают для каждого столбца отдельно.

Прочитаем одну строку таблицы со слайда (p. 407), не раскодируя ничего лишнего:

  1. Тройка \((v, s, l)\) означает \(l\) копий \(v\), начиная с позиции \(s\):

    \[ c[i] = v \quad \text{for } s \le i \le s + l - 1 \]

    (Q1, 1, 300) покрывает 1–300, (Q2, 301, 350) покрывает 301–650.

  2. Каждая серия начинается там, где закончилась предыдущая, \(s_{j+1} = s_j + l_j\): 1 + 300 = 301, 301 + 350 = 651, 651 + 500 = 1151. Последняя заканчивается на 1151 + 600 − 1 = 1750: в таблице 1,750 строк.

  3. Запросим строку 304. Она лежит в 301–650: квартал — Q2.

  4. Product ID: (2, 304, 1) покрывает ровно 304, значит, товар — 2.

  5. Price не сжат: берём его 304-е значение. Блок Q2 на слайде начинается с 301 значениями 3, 8, 1, 4, так что цена — 4.

  6. Склеиваем по позиции: строка 304 — это (Q2, 2, 4). Снова восстановление кортежа.

Кодированию длин серий нужны серии. Отсортируй шестнадцать продаж виджета по покупателю — и никакие два соседних квартала не совпадут: шестнадцать серий длины 1, втрое больше сырого столбца. Это последнее задание виджета.

Колоночное хранилище читает только те столбцы, которые называет запрос, и платит по одному обращению на столбец всякий раз, когда целая запись читается или пишется.

Слайд (p. 408) заканчивается списком "List of Databases": Cassandra, Vertica, SybaseIQ, C-Store, BigTable, MonetDB, LucidDB. Пять из них — колоночные хранилища в смысле слайдов (pp. 401–407) (C-Store, университетский прототип, живёт дальше как Vertica — это дополнительно), как и Snowflake (урок 23) и колоночные файлы Spark (урок 40). Cassandra и BigTable — нечто другое.

Cassandra: модель данных Bigtable на кольце Dynamo

Слайд (p. 410): Cassandra была "Originally designed at Facebook" и сейчас "Open-sourced and now within Apache foundation".

Авинаш Лакшман — один из авторов статьи Amazon о Dynamo — и Прашант Малик написали Cassandra в Facebook для поиска по входящим сообщениям: те самые случайные чтения и записи со слайда (p. 399). Её код открыли в июле 2008 года, а в феврале 2010-го она стала проектом верхнего уровня Apache. Название — в честь троянской пророчицы, которой никто не верил. (Дополнительно: Wikipedia, «Apache Cassandra».)

Слайд "innovation at scale" (p. 411) даёт родословную. "google bigtable (2006)": "consistency model: strong", "data model: sparse map", "clones: hbase, hypertable". "amazon dynamo (2007)": "O(1) dht", "consistency model: client tune-able", "clones: riak, voldemort". Итог: "cassandra ~= bigtable + dynamo".

Модель данных взята у Bigtable, распределение — у Dynamo. Разреженная карта (sparse map) — это таблица, в строках которой заполнены только те ячейки, что у них есть; пустые ячейки ничего не стоят. DHT (distributed hash table, распределённая хеш-таблица) раскладывает ключи по машинам, хешируя их; O(1) значит, что любой узел добирается до владельца ключа за один переход, потому что каждый узел знает всё кольцо (урок 22). «~=» тут честное: в отличие от Bigtable, у Cassandra вообще нет мастера.

Слайд (p. 412) рисует модель на примере "blog keyspace" (рис. 3): "Column Families: Like SQL tables; but may be unstructured (client-specified); Can have index tables", "No schemas", "Some columns missing from some entries", "Supports get(key) and put(key, value) operations", "Often write-heavy workloads".

Строки находят по ключу — здесь это имена пользователей. time_ordered_blogs_by_user — не сущность, а заранее подготовленный ответ: «записи jbellis по времени» — это чтение одной строки. Звёздочки отмечают вторичные индексы (secondary indexes) на двух столбцах: запомни их до раздела 4.

«На слайде (p. 412) написано "column-oriented databases", значит, Cassandra хранит каждый столбец в отдельном файле, как Vertica». Нет: ярлык идёт от column families. Строка Cassandra хранит все свои столбцы вместе под ключом строки — "think of cassandra as row-oriented" (p. 417). Клеппман, учебник курса, называет этот ярлык для данного семейства «очень вводящим в заблуждение» (гл. 3, дополнительно). Оставь слово курса, но говори, какой смысл имеешь в виду.

Слайды (pp. 413–417) дают словарь, снаружи внутрь:

Keyspace (пространство ключей) — "~= database", "typically one per application", "some settings are configurable only per keyspace" (p. 415): прежде всего репликация — сколько копий каждой строки хранится и где (урок 21).

Column family (семейство столбцов) — "group records of similar kind", "not same kind, because CFs are sparse tables" (p. 416); настройки: компаратор (comparator) и тип, standard или super (p. 413). Примеры: User, Address, Tweet, PointOfInterest, HotelRoom.

Row (строка) — "each row is uniquely identifiable by key"; "rows group columns and super columns" (p. 417).

Column (столбец) — имя, значение и часы (clock) (p. 413): раздел 4.

"settings (eg, partitioner)"

Партиционер (partitioner) — не настройка keyspace: у кластера Cassandra один партиционер на все его keyspaces. Keyspace задаёт свою репликацию — стратегию и число копий каждой строки.

Партиционер превращает ключ строки в позицию на кольце узлов, а все keyspaces кластера делят это одно кольцо. В современной Cassandra партиционер — одна строка в конфигурации узла (дополнительно), а CREATE KEYSPACE принимает параметр репликации и никакого партиционера (урок 21). Экзамен могут проверять по напечатанной рамке: знай её, а на вопрос, что настраивает keyspace, называй репликацию.

На двух слайдах (pp. 418 и 419) пользователи переставлены: строка 123 — это eben на одном и alison на другом. Виджет следует слайду (p. 419).

Слайд (p. 417) — тот самый из загадки: "think of cassandra as row-oriented" — один ключ открывает строку, и её столбцы возвращаются вместе. Слайд (p. 414) сопоставляет "Row Key" пары "Column Keys/Names" и "Column Values"; слайд (p. 418) показывает две строки одного семейства с разными столбцами; слайд (p. 419) записывает их как вложенные карты:

// p. 419: User as nested maps
User {
  123 : { email: alison@foo.com,
          icon:  [the Cassandra eye] },
  456 : { email: eben@bar.com,
          location: The Danger Zone }
}

Думай о column family как о карте карт: ключ строки → столбцы этой строки, отсортированные по имени, каждый из которых — имя, значение и временная метка.

У столбца три части, у суперстолбца — столбцы

Приблизимся к одной ячейке. Слайд "a column has 3 parts" (p. 420):

name — "byte[]", "determines sort order", "used in queries", "indexed".

value — "byte[]", "you don't query on column values".

timestamp — "long (clock)", "last write wins conflict resolution".

Имя — это ключ внутренней карты строки: оно отсортировано, так что диапазон имён — одно непрерывное чтение, и проиндексировано внутри строки, так что имя находится без сканирования. Значение — непрозрачные байты: строка, число, картинка с глазом со слайда (p. 418) — хранится как пришло и никогда не сортируется.

Временная метка (timestamp) разрешает разногласия между копиями. Одна реплика строки 456 хранит email = eben@bar.com с меткой 1004, другая — email = eben@new.com с меткой 1010: когда их сравнивают, на обеих побеждает 1010. Часы клиент передаёт с каждой записью (p. 428); удаление тоже несёт метку, поэтому оно может победить более старое значение. Просто и быстро, но есть цена: из двух одновременных записей одна молча теряется.

"you don’t query on column values"

Читай это как правило проектирования, а не как ограничение системы: Cassandra умеет находить строки по значению столбца через вторичные индексы — слайд (p. 412) этой же лекции отмечает два из них, "* = secondary indexes", — а в CQL есть CREATE INDEX и ALLOW FILTERING (урок 21).

Эта фраза старше вторичных индексов (2011, версия 0.7 — дополнительно). Каждый узел индексирует только свои строки, поэтому запрос по значению опрашивает все узлы, а column family с ключом по этому значению (p. 431) читается на одном. Экзамен могут проверять по напечатанной формулировке: в теоретическом ответе процитируй её и добавь нюанс; в упражнении "If any further operation is required" обычно означает CREATE INDEX.

Порядок сортировки задаёт компаратор (comparator) column family (p. 421): "byte", "utf8", "long", "timeuuid", "lexicaluuid", "<pluggable>", "ex: lat/long" — тип имён столбцов. Для имён 2 и 10 utf8 сравнивает символы и ставит "10" первым, long сравнивает числа и ставит первым 2; timeuuid упорядочивает идентификаторы на основе времени по времени — естественный выбор для ленты событий.

Слайд (p. 422) добавляет уровень: "super columns group columns under a common name". У суперстолбца (super column) есть имя, "name: byte[]", а вместо значения — карта столбцов, "cols: Map<byte[], IColumn>". Column family бывает standard или super ("type" со слайда (p. 413)); в super column family каждая строка содержит суперстолбцы.

Слайды (pp. 423–424) заполняют одно такое семейство: PointOfInterest с ключом по почтовому индексу (ZIP). Строка 85255 содержит суперстолбцы Phoenix Zoo и Spring Training, строка 10019 — Central Park и Empire State Building; в каждом есть phone и desc — или только desc, как у Central Park: "flexible schema".

Всё это — Cassandra 2010 года. Современная Cassandra предлагает ту же модель через таблицы CQL — язык практических занятий и прошлых экзаменов (урок 21); Thrift убрали в версии 4.0 (2021), а суперстолбцов больше не существует. Теоретические вопросы пользуются словами слайдов, упражнения — словами CQL:

Никакого SELECT … WHERE: начинай с запросов

Слайд (p. 429) спрашивает "what about… SQL?" и перечисляет пять привычек: SELECT, WHERE, ORDER BY, JOIN ON, GROUP. Ответ — это способ проектировать, а не ещё одна клауза.

Слайд (p. 430): "rdbms: domain-based model — what answers do I have?"; "cassandra: query-based model — what questions do I have?"; "Start from queries, then design the data model". Реляционный проектировщик моделирует предметную область — сущности, связи, нормальные формы (уроки 8–9) — и отвечает на будущие вопросы джойнами. Cassandra находит строки только по ключу и не делает джойнов, так что на вопрос, под который не построена структура, эффективного ответа нет: сначала ты перечисляешь вопросы.

Слайд "cassandra is an index factory" (p. 431): у column family USER ключ UserID и столбцы username, email, birth date, city, state. Она отвечает на «дай пользователя 123» за одно чтение — и больше ни на что. "How to support this query?"

-- p. 431: the query that USER, keyed by UserID, cannot answer
SELECT * FROM User WHERE city = 'Scottsdale'

Ответ слайда: "Create a new CF called UserCity" с ключом по городу, столбцы которого — "IDs of the users in that city". Запрос превращается в чтение одной строки плюс multiget_slice по USER за самими пользователями. UserCity "uses the Valueless Column pattern" (шаблон «столбец без значения»): информация лежит в именах столбцов, значения пусты. То, что СУБД делает индексом, ты делаешь вручную — по column family на каждый вопрос, записывая их вместе с USER, — фабрика индексов (index factory).

В CQL (урок 21) UserCity — это таблица, у которой partition key — город, а id пользователей — значения clustering column, те самые столбцы без значения:

-- UserCity of p. 431 in CQL: one partition per city
CREATE TABLE user_city (
  city text,
  user_id text,
  PRIMARY KEY ((city), user_id)
);
-- all the users of Scottsdale: one partition read
SELECT user_id FROM user_city WHERE city = 'Scottsdale';

Два условия сразу? Слайд (p. 432): "Use an aggregate key" (составной ключ) — state:city: { user1, user2} — затем "Get rows between AZ: & AZ; for all Arizona users" и "Get rows between AZ:Scottsdale & AZ:Scottsdale1 for all Scottsdale users". Почему эти границы работают?

  1. Четыре строки — AZ:Phoenix, AZ:Scottsdale, AZ:Tucson, CA:Fresno, — в каждой её пользователи как столбцы без значения. Ключи сравниваются как строки, символ за символом, и префикс идёт первым: AZ: стоит перед AZ:Phoenix.

  2. В ASCII двоеточие — 58, точка с запятой — 59. У каждого аризонского ключа на третьем месте двоеточие, поэтому он сортируется перед AZ;. CA:Fresno идёт после AZ;, потому что C стоит после A. Так что от AZ: до AZ; лежат ровно аризонские строки.

  3. Аналогично AZ:Scottsdale1 сортируется сразу после AZ:Scottsdale: в этом диапазоне одна строка — Scottsdale.

  4. Для этого строки должны лежать в порядке ключей: нужен order-preserving partitioner (партиционер, сохраняющий порядок). Случайный (random) хранит строки в порядке MD5 их ключей — AZ:Phoenix (ab66…), AZ:Tucson (f163…), CA:Fresno (f3ca…), AZ:Scottsdale (f412…), — так что калифорнийская строка оказывается между аризонскими, и «строки между AZ: и AZ;» больше не означают пользователей из Аризоны.

Слайд "ORDER BY" (p. 433): "Columns are sorted according to CompareWith or CompareSubcolumnsWith" (компараторы имён и имён подстолбцов); "Rows are placed according to their Partitioner: Random: MD5 of key; Order-Preserving: actual key". Клаузы ORDER BY нет: чтобы получать записи по времени, сделай время именем столбца. Последнюю строку слайда нужно поправить:

"are sorted by key, regardless of partitioner"

Строки хранятся в порядке токена (token) партиционера: это сам ключ при order-preserving partitioner и MD5 ключа при random — порядок, никак не связанный с ключом. Диапазоны ключей вроде AZ: … AZ; (p. 432) работают только с order-preserving partitioner.

Захешируй ключи из пошагового разбора: CA:Fresno попадает между AZ:Tucson и AZ:Scottsdale. Order-preserving partitioner платит за диапазоны горячими точками (hot spots) — все ключи AZ: на одних и тех же узлах, — а CQL не принимает диапазон по partition key: диапазоны задаются по clustering columns (урок 21). Экзамен могут проверять по напечатанной строке: знай её — и правильную.

Ни один слайд не отвечает словами на JOIN ON и GROUP; пример с отелем (pp. 434–435) (рис. 4) отвечает на них самим проектированием. Восемь реляционных таблиц, связанных внешними ключами, где страница отеля требует нескольких джойнов, превращаются в семь column families без внешних ключей, каждое из которых сделано под те чтения, которые оно обслуживает.

Вернёмся к загадке. "The Column Oriented Database stores data in columns" (p. 401) и "think of cassandra as row-oriented" (p. 417) — оба верны, потому что «column» означает две разные вещи. В Vertica или C-Store столбец — это файл: один атрибут всех записей, хранящийся вместе, сжатый и сканируемый, — OLAP. В Cassandra столбец — это имя в отсортированной карте строки, хранящееся вместе с остальной строкой; строка может содержать их огромное количество, отсюда и "Big Column Stores". Лекция и экзамены ("you decide to store it in a columnar database", экзамен 12 сентября 2025 года) называют «columnar» оба варианта: сохраняй этот ярлык, но говори, какой из них имеешь в виду.

Вопросы в стиле экзамена

Теоретические вопросы в форматах теоретической части — «верно/неверно», выбор вариантов и короткие открытые ответы, где за неправильный ответ могут снять баллы, — и одно практическое упражнение в формулировках прошлых экзаменов, построенное на отеле со слайдов (pp. 434–435).

True or false: Cassandra stores the values of each column of a column family together, separately from the other columns, as a column-oriented database such as Vertica does.

  • True Это колоночное хранение со слайдов (pp. 401–407). Cassandra держит столбцы строки вместе под её ключом строки: "think of cassandra as row-oriented" (p. 417).
  • False Cassandra — wide-column store: строка, которую находят по ключу, хранит все свои столбцы вместе (p. 417). Хранить каждый столбец отдельно — это аналитическое колоночное хранилище со слайдов (pp. 401–407).
Показать образец ответа

False. Cassandra is a wide-column (column-family) store: each row is uniquely identified by its key and keeps all its columns, sorted by name, together, so it should be thought of as row-oriented. Storing each column separately is the design of column-oriented databases such as Vertica or C-Store, built for OLAP: a query reads only the columns it needs, while inserts and whole-record reads touch every column. Cassandra is called columnar because of its column families and its very wide rows, and it is built for write-heavy workloads.

Ловушка — в слове «column», общем для двух разных конструкций (разделы 2 и 3). За неправильные ответы может быть штраф, о нём объявляют прямо перед экзаменом: отвечай только то, что можешь обосновать.

Explain how a column-oriented database stores a table and compare it with a row-oriented database: advantages, disadvantages, and the workloads each one suits.

Показать образец ответа

A row-oriented database stores each record contiguously; a column-oriented database stores each column contiguously, in its own storage. A query that needs k of the m columns therefore reads only those k columns in a column store, while a row store reads whole records and may read unnecessary data. The column layout also compresses better (the values of a column share a type and repeat, so techniques such as run-length encoding work well) and improves bandwidth utilisation, code pipelining and cache locality. Its disadvantages are increased disk seek time (a record is spread over many files), an increased cost of inserts (one write per column) and increased tuple reconstruction costs (records must be rebuilt by position). Column stores therefore suit read-mostly, read-intensive, large repositories — OLAP and data mining — while row stores suit OLTP, with frequent inserts and updates of whole records.

У полного ответа четыре части: две раскладки, довод про чтение (k из m столбцов), плюсы и минусы словами слайдов (pp. 403–404) и типы нагрузки. Сильное дополнение — график со слайда (p. 405): колоночное хранилище проигрывает, только когда запрос выбирает почти весь кортеж.

The Quarter column of a sales table, sorted by quarter, is stored with run-length encoding as (Q1, 1, 300), (Q2, 301, 350), (Q3, 651, 500), (Q4, 1151, 600). Which statements are correct? Select all that apply.

  • (Q2, 301, 350) means that Q2 is stored at the positions from 301 to 350. Третье число — длина, а не конец: Q2 занимает 350 позиций с 301 по 650.
  • The table has 1,750 rows. Последняя серия заканчивается на 1151 + 600 − 1 = 1750 — столько же, сколько 300 + 350 + 500 + 600.
  • Position 700 holds Q3. Q3 начинается с 651 и покрывает 500 позиций, до 1150.
  • The Price column of the same table would shrink just as much with the same encoding. Соседние цены редко повторяются: каждая цена превратилась бы в тройку, втрое больше сырого размера, — поэтому слайд (p. 407) оставляет Price несжатым.
  • Sorted by customer instead, the same Quarter column would usually compress far less. Сериям нужны равные значения рядом; другой порядок сортировки их разбивает.
Показать образец ответа

The second, third and fifth statements. Each triple is (value, start_pos, run_length), so (Q2, 301, 350) covers the positions 301 to 650; the last run ends at 1151 + 600 − 1 = 1750; position 700 lies in the run of Q3, from 651 to 1150. Run-length encoding pays only when equal values are adjacent: the Quarter column is sorted and the prices are not, so the encoding is chosen column by column and Price stays raw.

Числа взяты со слайда (p. 407), так что ответ можно сверить со слайдом. Классическая ошибка — принять run_length за конечную позицию. За неверные отметки может быть штраф: отмечай только то, что можешь обосновать.

Describe the data model of Cassandra as presented in the lecture — keyspace, column family, row, column and super column. Explain why a column family is called a sparse table and what the timestamp of a column is used for.

Показать образец ответа

A keyspace is the outermost container, roughly a database and typically one per application; some settings, such as the replication, are configured per keyspace. It contains column families, the analogue of tables, which group records of a similar but not identical kind; their settings include the comparator and the type, standard or super. A column family holds rows, each uniquely identified by its row key; Cassandra should be thought of as row-oriented, because a row's columns are stored and returned together. A column has three parts: a name (bytes; it determines the sort order, is used in queries and is indexed), a value (bytes; values are not queried) and a timestamp. A super column groups columns under a common name: it has a name and a map of columns instead of a value, and its sub-column names are not indexed. A column family is a sparse table because each row stores only the columns it has: a missing column costs nothing and is not a NULL. The timestamp (clock) is supplied with every write and resolves conflicts between replicas: the last write wins.

Дай цепочку вложенности по порядку и три части столбца с их свойствами (p. 420). «Sparse» и «last write wins» — два «почему», о которых спрашивает вопрос. Если цитируешь пример настройки keyspace со слайда, partitioner, добавь, что на самом деле он задаётся для всего кластера (красная ручка к слайду (p. 413)).

Explain the difference between the domain-based model of an RDBMS and the query-based model of Cassandra. How would you support the query SELECT * FROM User WHERE city = 'Scottsdale' on a column family User keyed by UserID, and what does the solution cost?

Показать образец ответа

An RDBMS follows a domain-based model: you model the entities and relationships of the domain, normalise them, and answer any later question by combining tables with joins ("what answers do I have?"). Cassandra follows a query-based model: rows are found by key, column values are not queried and there are no joins, so you list the questions first and build a structure for each one ("what questions do I have?" — start from queries, then design the data model). For the query, create a second column family, UserCity, keyed by city, whose column names are the IDs of the users living there, with empty values (the Valueless Column pattern): the query becomes one row read, followed by a multiget of the users from User. This is why Cassandra is called an index factory. The cost is duplication: every user is written to both column families, and the application must keep the copies consistent, with no joins and no referential integrity to help.

Ответ держится на двух вещах: почему (строки находятся только по ключу, джойнов нет) и цена (дублирование, копии синхронизирует приложение). В CQL та же идея — таблица с PRIMARY KEY ((city), user_id). Другой инструмент с практического занятия — вторичный индекс, CREATE INDEX; задание на проектирование в экзамене 30 января 2026 года исключает его словами "Do not use indexes".

Our exercise, in the wording of the past papers: the hotel of pp. 434–435. Consider the following ER diagram. Hotel (Hotel_ID, Name, Phone, Address, City, State, Zip); Room (Room_ID, Room Number, Rate); Guest (Guest_ID, Name, Phone, Email). Relationships: Has, Hotel (1, N) – Room (1, 1); Reserve, Guest (0, N) – Room (0, N), with the attributes Start Date and End Date.

Suppose you expect to record a large-scale, continuously increasing number of reservations, and therefore you decide to store them in a columnar database. Write the specification of the tables (column families) of a Cassandra deployment so that one can query the hotels of a state, the hotels of a city of a given state, and the reservations of a guest by phone number, the most recent first. Do not use indexes.

Показать образец ответа

Two tables, one per access path: the hotels by location, partitioned by state and clustered by city, and the reservations by guest phone, partitioned by phone and clustered by start date, the most recent first. Each reservation carries copies of the guest, hotel and room data it shows, because Cassandra has no joins.

-- the keyspace (one per application)
CREATE KEYSPACE hotels
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};
-- queries 1 and 2: the hotels of a state, or of a city in it
CREATE TABLE hotels_by_location (
  state text,
  city text,
  hotel_id text,
  name text,
  phone text,
  address text,
  zip text,
  PRIMARY KEY ((state), city, hotel_id)
);
-- query 3: a guest's reservations, with copies, newest first
CREATE TABLE reservations_by_guest_phone (
  guest_phone text,
  start_date date,
  reservation_id uuid,
  end_date date,
  guest_name text,
  hotel_id text,
  hotel_name text,
  room_number int,
  rate float,
  PRIMARY KEY ((guest_phone), start_date, reservation_id)
) WITH CLUSTERING ORDER BY (start_date DESC, reservation_id ASC);
-- all the hotels of Arizona: one partition
SELECT * FROM hotels_by_location WHERE state = 'AZ';
-- the hotels of Scottsdale: the first clustering column fixed
SELECT * FROM hotels_by_location
  WHERE state = 'AZ' AND city = 'Scottsdale';
-- a guest's reservations, the most recent first
SELECT * FROM reservations_by_guest_phone
  WHERE guest_phone = '+1 480 555 0101';

Every reservation is one INSERT into reservations_by_guest_phone, with reservation_id from uuid() and the guest's name, the hotel's name and the room's number and rate copied in.

Это слайды (pp. 431–435) на CQL. hotels_by_location — это составной ключ state:city со слайда (p. 432): штат — partition key, а город — первый clustering column, так что одна таблица отвечает на оба вопроса о местоположении без диапазона ключей и без order-preserving partitioner. reservations_by_guest_phone — это Reservation со слайда (p. 435): ключ — то, по чему ищет приложение, с копиями вместо джойнов; reservation_id разделяет два бронирования одного гостя на один день, потому что INSERT с уже существующим первичным ключом перезаписывает строку. Прошлые экзамены спрашивают то же самое — задание 1 из экзамена про фермеров от 12 сентября 2025 года решено в уроке 21 вместе с правилами CQL, стоящими за каждой строкой.

Проверь себя

В таблице продаж 20 столбцов одинаковой ширины и десять миллионов строк. Запрос считает среднее по одному столбцу. Какую примерно долю байтов строкового хранилища читает колоночное?

  • Ту же: оба должны прочитать десять миллионов строк Оба проходят десять миллионов строк, но колоночное читает по одному значению на строку, а строковое — по двадцать.
  • Одну двадцатую \(k/m = 1/20\): с диска едет только один столбец, который называет запрос.
  • Половину Ничто здесь не делится пополам: доля — это доля нужных столбцов, 1 из 20.
  • В двадцать раз больше, потому что колоночное хранилище должно собирать кортежи Среднему кортежи не нужны, так что собирать нечего. Восстановление стоит денег, только когда возвращаются целые записи.

Показания датчиков хранятся отсортированными по id датчика, по 50,000 показаний на датчик. Какой столбец больше всех выиграет от кодирования длин серий?

  • температура, потому что этот столбец запрашивают чаще всего Частота запросов не создаёт серий; температура меняется от показания к показанию.
  • время показания, потому что оно всегда растёт Всегда растущие значения никогда не повторяются: каждая серия будет длины 1.
  • id датчика Таблица по нему отсортирована, поэтому 50,000 одинаковых соседей каждого датчика становятся одной тройкой.
  • все столбцы одинаково: кодирование длин серий не зависит от данных Оно целиком зависит от данных: ему нужны одинаковые соседние значения.

Две реплики строки 456 расходятся: одна хранит email = eben@bar.com с меткой 1004, другая — email = eben@new.com с меткой 1010. Что будет на них после сравнения?

  • eben@new.com на обеих, потому что побеждает бо́льшая метка "last write wins conflict resolution" (p. 420): решают часы, а проигравший отбрасывается.
  • eben@bar.com на обеих, потому что оно записано первым Правило — последняя запись, а не первая.
  • оба значения, как две версии столбца У столбца одно значение; проигравшая запись молча отбрасывается — цена last write wins.
  • то значение, которое хранит более быстрая реплика Скорость ничего не решает; решают временные метки.

В time_ordered_blogs_by_user имена столбцов — временные метки в миллисекундах (компаратор long). Какой предикат среза вернёт десять последних записей пользователя?

  • start и finish пустые, reverse выключен, count 10 Так имена проходятся вверх: десять самых старых записей.
  • start и finish пустые, reverse включён, count 10 Reverse проходит отсортированные имена с новейшего конца; count останавливается после десяти, как LIMIT.
  • start = новейшая метка, reverse выключен, count 10 От новейшего имени вверх есть только новейшая запись: один столбец, а не десять.
  • никакой: в Cassandra нет ORDER BY, поэтому записи нельзя вернуть в порядке времени Клаузы ORDER BY нет, но имена отсортированы компаратором — сделать время именем столбца и есть способ получить порядок (p. 433).

Нужно отвечать на «пользователи в Scottsdale» и «пользователи в Аризоне», не читая всю column family User. Какие схемы из лекции работают? Выбери все подходящие.

  • две column families, одна с ключом по городу, другая — по штату, имена столбцов в которых — ID живущих там пользователей UserCity со слайда (p. 431), построенная дважды: каждый вопрос — чтение одной строки, и каждый пользователь записывается в оба семейства.
  • SELECT * FROM User WHERE city = 'Scottsdale' на column family User с ключом UserID Строки находятся по ключу; без индекса это означает прочитать всё — именно этого слайд (p. 431) и стремится избежать.
  • column family с ключом state:city, которую читают диапазоном ключей от AZ: до AZ; при order-preserving partitioner Слайд (p. 432): одно семейство отвечает на оба вопроса, пока строки лежат в порядке ключей.
  • то же семейство state:city при random partitioner Тогда строки идут в порядке MD5 ключа: калифорнийская строка оказывается между аризонскими, и диапазон ключей больше не означает Аризону (красная ручка к слайду (p. 433)).
  • джойн User с column family City "Doesn't support joining" (p. 437).

Обе работающие схемы — фабрики индексов: данные копируются в семейство с ключом по тому значению, по которому ищут.

Почему Cassandra отказывается от джойнов (p. 437)?

  • Потому что значения столбцов — непрозрачные байты, которые нельзя сравнивать Джойн сравнивает ключи, а ключи сравнивать можно; препятствие в другом.
  • Потому что column family не может хранить ключ другой строки Может: Reservation хранит hotelID и roomID (p. 435). Просто никто их не проверяет и не следует по ним.
  • Потому что теорема CAP запрещает джойны в AP-системах CAP ничего не говорит о джойнах; она про реплики во время разделения сети.
  • Потому что объединяемые строки жили бы на разных узлах, и координировать их на каждом запросе стоило бы той линейной масштабируемости и доступности, ради которых Cassandra построена Поэтому данные, которые читают вместе, и хранят вместе, при необходимости дублируя: "Tables contain duplicate denormalize data" (p. 437).

В super column family PointOfInterest тебе нужен только телефон Empire State Building (строка 10019). Что прочитает Cassandra?

  • только столбец phone, найденный через индекс "sub-column names in a SCF are not indexed" (p. 425).
  • всю строку 10019, включая Central Park Имена суперстолбцов проиндексированы, так что она может сразу перейти к Empire State Building.
  • весь суперстолбец Empire State Building, desc и phone, а потом выберет phone Верхний уровень проиндексирован, подстолбцы — нет: суперстолбец читается целиком.
  • ничего: суперстолбец нельзя прочитать по имени Путь к столбцу (column path) может назвать суперстолбец и даже подстолбец (get, p. 427); отличается стоимость.

Главное

  • Строковое хранилище держит каждую запись одним куском, колоночное — каждый столбец: запрос, которому нужны \(k\) из \(m\) столбцов, читает в колоночном хранилище долю \(k/m\) байтов, но чтение или вставка целой записи затрагивает \(m\) мест — "suitable for read-mostly, read-intensive, large data repositories" (pp. 402–405).
  • Колоночные хранилища хорошо сжимаются, потому что соседние значения принадлежат одному атрибуту; кодирование длин серий хранит (value, start_pos, run_length) и окупается только на отсортированных или сгруппированных столбцах (pp. 406–407).
  • «Columnar» называет два семейства: column-oriented stores (Vertica, C-Store, MonetDB, SybaseIQ, LucidDB) и wide-column stores (Cassandra, BigTable, HBase) — "think of cassandra as row-oriented" (p. 417).
  • "cassandra ~= bigtable + dynamo": модель данных Bigtable (разреженная карта) на распределении Dynamo (O(1) DHT, согласованность, настраиваемая клиентом); по умолчанию AP и согласованность в конечном счёте (eventual consistency), "tuneably consistent" для каждой операции.
  • keyspace › column family › строка (по ключу) › столбец (имя, значение, временная метка): имена отсортированы компаратором и читаются срезами, по значениям по замыслу не запрашивают, побеждает последняя запись; суперстолбцы добавляют уровень именованных групп, подстолбцы которых не индексируются.
  • Модель Cassandra основана на запросах: начинай с запросов, строй по column family на каждый вопрос (фабрика индексов, столбцы без значения, составные ключи), получай порядок проектированием (компаратор, партиционер) и денормализуй вместо джойнов — ни джойнов, ни ссылочной целостности.
  • Сегодня ту же модель записывают на CQL (урок 21): таблица, partition key, clustering columns; ни суперстолбцов, ни Thrift.
