Колоночные хранилища и модель данных Cassandra

После этого урока ты сможешь объяснить, что колоночное хранилище выигрывает и чем за это платит, раскодировать столбец, сжатый run-length encoding, нарисовать данные Cassandra — keyspace, column family, ключ строки, столбцы из имени, значения и временной метки, суперстолбцы — и сказать, почему таблицы Cassandra проектируют от запросов.

Лекция называется "Columnar Databases – Cassandra". Первая её половина объясняет базы, которые хранят данные по столбцам и сделаны для аналитики. Вторая половина — про Cassandra, и там сказано: "think of cassandra as row-oriented" (p. 417), причём Cassandra рассчитана на интенсивную запись.

Так колоночная Cassandra или нет? Правы обе половины, потому что «столбец» здесь означает две разные вещи. К концу урока ты научишься их различать — а экзамен это проверяет.

Wide-column stores и нагрузка, для которой они созданы

Представь мессенджер. Миллионы пользователей весь день пишут и читают короткие сообщения, без всякого порядка, и двух одинаковых почтовых ящиков нет. У такой нагрузки три черты (p. 399):

  • данных слишком много для одной машины, и фиксированного набора полей у них нет;
  • много мелких случайных чтений и записей, а не длинные сканы;
  • записи читаются по одной, поэтому внешние ключи почти не нужны.

Что нужно такой системе: расти, добавляя обычные машины ("scale out, not up", урок 3), оставаться быстрой и не иметь единой точки отказа. Семейство NoSQL, созданное для этого, — wide-column store (хранилище с широкими столбцами) (урок 5): Cassandra, HBase, Bigtable. «Широкое» — потому что одна строка может держать огромное число столбцов.

В терминах CAP (урок 5) Cassandra выбирает доступность и устойчивость к разделению, с согласованностью в конечном счёте (eventual consistency, p. 400). Для почтового ящика это правильный выбор: сообщение, пришедшее на секунду позже, никому не вредит, а ящик, который не открывается, — вредит. «В конечном счёте» — лишь умолчание. Каждое чтение или запись может потребовать ответа от большего числа реплик и получить более сильную согласованность ценой ожидания: Cassandra "tuneably consistent" — согласованность настраивается (урок 22).

Колоночное хранение: читаем меньше, пишем больше

Сначала — другой смысл слова «столбец» (pp. 401–408). Возьмём сеть магазинов, которая записывает каждую продажу: дата, магазин, товар, покупатель, цена. Этой таблицей пользуются двое:

  • кассир каждые несколько секунд добавляет одну продажу целиком — OLTP (online transaction processing, обработка транзакций);
  • аналитик раз в ночь спрашивает выручку каждого магазина — два столбца, но по всем продажам за всё время. Это OLAP (online analytical processing, аналитическая обработка): мало столбцов, очень много строк.

Положить таблицу на диск можно двумя способами (p. 402):

  • строковое хранилище (row store) держит каждую запись одним куском. Добавить или изменить запись легко, но запрос, которому нужны два столбца, всё равно читает все;
  • колоночное хранилище (column store) держит каждый столбец отдельным куском. Запрос читает только нужные ему столбцы, но запись одной строки означает запись в каждый файл столбца.

Поэтому колоночное хранилище подходит для данных, которые читают гораздо чаще, чем пишут: для больших аналитических хранилищ. Попробуй обе раскладки:

Одна таблица, два способа положить её на диск

Шестнадцать продаж, восемь столбцов, по четыре байта на значение: сверху строковое хранилище, снизу колоночное (по файлу на столбец). Выбери запрос: пунктирные рамки показывают, что каждая раскладка читает с диска, закрашенные клетки — что нужно запросу. Переключатели сжимают столбец квартала и меняют порядок строк.

  1. Оставь запрос «сумма price по кварталам». Прежде чем смотреть на показания, предскажи: какую долю байтов, прочитанных строковым хранилищем, запрос действительно использует? Потом сравни пунктирные рамки сверху и снизу.
    Что должно получиться

    Четверть: 128 из 512 байт. Строковое хранилище вынуждено прочитать все шестнадцать записей целиком; колоночное читает два файла, 128 байт, и больше ничего. Ради этого виджет и сделан: колоночное хранилище читает только те столбцы, которые называет запрос, — здесь 2 из 8.

  2. Переключи на «вся запись продажи 7», затем на «вставить новую продажу». Для каждого случая предскажи, сколько отдельных мест на диске затрагивает каждая раскладка.
    Что должно получиться

    1 против 8, оба раза. Запись — один кусок в строковом хранилище и восемь кусков в колоночном: восемь позиционирований головки (seek) и сборка по позиции, чтобы прочитать её, восемь записей, чтобы добавить. Это и есть минусы со слайда (p. 404) — время позиционирования, стоимость вставок, восстановление кортежей — и причина слов "read-mostly".

  3. Вернись к «сумма price по кварталам» и включи кодирование длин серий. Предскажи, сколько серий (runs) получится из столбца квартала, затем посмотри показание для 1,750 строк. Напоследок отсортируй строки по покупателю и предскажи снова.
    Что должно получиться

    Четыре серии, (Q1, 1, 3) (Q2, 4, 3) (Q3, 7, 5) (Q4, 12, 5): 48 байт вместо 64. На 1,750 строках они превращаются в тройки со слайда (p. 407), и 7,000 байт сжимаются до 48. При сортировке по покупателю соседние кварталы всегда различаются: 16 серий длины 1 заняли бы 192 байта, втрое больше сырого столбца, поэтому он остаётся несжатым (те же 1,750 кварталов (p. 407) в смоделированном случайном порядке: 1,306 серий, 15,672 байта). Кодирование длин серий окупается только на отсортированных или сгруппированных столбцах.

В числах: при \(N\) записях из \(m\) столбцов по \(w\) байт запрос, которому нужны \(k\) столбцов, читает

\[ \begin{aligned} \text{row store:}\quad & N \cdot m \cdot w \\ \text{column store:}\quad & N \cdot k \cdot w \end{aligned} \]

значит, колоночное хранилище читает долю \(k/m\): 2 столбца из 8, четверть.

На слайдах четыре преимущества (p. 403) и три издержки (p. 404). Учи их парами «что — почему»:

Насколько велик выигрыш? Рис. 1 — измерение со слайда (p. 405). Строковое хранилище всегда читает кортежи целиком, поэтому его время одинаково, что бы ни выбирал запрос. Время колоночного растёт с числом выбранных байтов, и проигрывает оно, только когда запросу нужен почти весь кортеж. Чтение каждого файла столбца большими кусками ("large prefetch") прячет большую часть лишних перемещений головки.

Чтобы собрать запись, ключи не нужны: позиция \(i\) каждого файла столбца принадлежит записи \(i\), так что файлы просто «сшиваются» по позиции.

Теперь сжатие (p. 406). Сжатые данные — это меньше байтов на чтение и немного процессора на распаковку. Скан всё время ждёт диск, так что обмен выгоден. Больше всех выигрывают колоночные хранилища: соседние значения относятся к одному атрибуту и часто повторяются. В сэкономленное место можно даже положить дополнительные копии данных, отсортированные по-разному, — по одной на тип запроса.

Кодирование длин серий (run-length encoding, RLE) — серия одинаковых соседних значений хранится одной тройкой (value, start_pos, run_length): значение, его первая позиция, число строк.

В конспекте курса серия записывается двумя полями, ("Q1", 200). Третье поле слайда, начальная позиция, позволяет найти строку, не складывая длины предыдущих серий.

На рис. 2 (p. 407) таблица продаж отсортирована по кварталу. Quarter превращается в четыре тройки, Product ID — в короткие серии, а Price остаётся как есть: соседние цены редко повторяются. Кодирование выбирают для каждого столбца отдельно.

Прочитай одну строку этой таблицы, ничего больше не раскодируя:

  1. Тройка \((v, s, l)\) означает \(l\) копий \(v\), начиная с позиции \(s\):

    \[ c[i] = v \quad \text{for } s \le i \le s + l - 1 \]

    (Q1, 1, 300) покрывает 1–300, (Q2, 301, 350) покрывает 301–650.

  2. Каждая серия начинается там, где закончилась предыдущая, \(s_{j+1} = s_j + l_j\): 1 + 300 = 301, 301 + 350 = 651, 651 + 500 = 1151. Последняя заканчивается на 1151 + 600 − 1 = 1750: в таблице 1,750 строк.

  3. Запросим строку 304. Она лежит в 301–650: квартал — Q2.

  4. Product ID: (2, 304, 1) покрывает ровно 304, значит, товар — 2.

  5. Price не сжат: берём его 304-е значение, 4.

  6. Сшиваем по позиции: строка 304 — это (Q2, 2, 4).

Run-length encoding нужны серии. Если ту же таблицу отсортировать по покупателю, соседние кварталы будут различаться, каждая серия будет длины 1, и «сжатый» столбец окажется втрое больше исходного (последнее задание виджета).

Колоночное хранилище читает только те столбцы, которые называет запрос, и платит по одному обращению на столбец всякий раз, когда целая запись читается или пишется.

Настоящие колоночные хранилища этого типа: Vertica, C-Store, MonetDB, SybaseIQ, LucidDB (p. 408), а позже Snowflake (урок 23) и колоночные файлы Spark (урок 40). На том же слайде есть Cassandra и BigTable, но это другое — как покажет следующий раздел.

Cassandra: модель данных Bigtable на кольце Dynamo

Авинаш Лакшман — соавтор статьи Amazon о Dynamo — и Прашант Малик написали Cassandra в Facebook для поиска по входящим сообщениям: ровно та нагрузка мессенджера из раздела 1. Код открыли в 2008 году, а в 2010-м Cassandra стала проектом верхнего уровня Apache (p. 410). Название — в честь троянской пророчицы, которой никто не верил.

Слайды описывают Cassandra одной строкой: "cassandra ~= bigtable + dynamo" (p. 411).

  • От Google Bigtable она берёт модель данных — разреженную карту (sparse map): строки хранят только те ячейки, которые у них есть, так что пустая ячейка ничего не стоит.
  • От Amazon Dynamo она берёт распределение: ключи раскладываются по машинам хешированием (распределённая хеш-таблица, DHT), любой узел достаёт до владельца ключа за один шаг, а клиент выбирает, насколько согласованной будет каждая операция (урок 22).

В отличие от Bigtable, у Cassandra вообще нет мастера: все узлы равны.

Рис. 3 — пример со слайда, блог (p. 412). Column family похожа на таблицу SQL, но без фиксированной схемы: у каждой строки свои столбцы, и некоторых столбцов у некоторых строк нет. Читают и пишут по ключу, как get(key) и put(key, value).

Строки находят по ключу — здесь это имена пользователей. Обрати внимание на time_ordered_blogs_by_user: это не сущность, а заранее подготовленный ответ. «Записи jbellis по времени» — одно чтение строки. Эта идея вернётся в разделе 5.

«Cassandra — колоночная база, значит, каждый столбец лежит у неё в отдельном файле, как в Vertica». Нет. Название идёт от column families. Строка Cassandra хранит все свои столбцы вместе под ключом строки: "think of cassandra as row-oriented" (p. 417). Клеппман, учебник курса, называет этот ярлык для данного семейства «очень вводящим в заблуждение».

Словарь, снаружи внутрь (pp. 413–417):

Keyspace — примерно база данных, обычно одна на приложение. Задаёт репликацию: сколько копий каждой строки хранить и где (урок 21).

Column family — группа записей похожего, но не одинакового вида: разреженная таблица. Её настройки — компаратор (как сортируются имена столбцов) и тип, standard или super.

Строка (row) — опознаётся уникальным ключом; группирует столбцы (или суперстолбцы).

Столбец (column) — имя, значение и временная метка: раздел 4.

"settings (eg, partitioner)"

Partitioner — не настройка keyspace: у всего кластера один partitioner. Keyspace задаёт свою репликацию.

Partitioner превращает ключ строки в позицию на кольце узлов, и все keyspace делят это одно кольцо. CREATE KEYSPACE принимает параметр репликации и никакого partitioner (урок 21).

Итак, один ключ открывает строку, и её столбцы возвращаются вместе. Проще всего представлять column family как вложенные карты (p. 419):

// p. 419: User as nested maps
User {
  123 : { email: alison@foo.com,
          icon:  [the Cassandra eye] },
  456 : { email: eben@bar.com,
          location: The Danger Zone }
}

Думай о column family как о карте карт: ключ строки → столбцы этой строки, отсортированные по имени, каждый из которых — имя, значение и временная метка.

У столбца три части, у суперстолбца — столбцы

Приблизимся к одной ячейке. У столбца три части (p. 420):

name — байты. Задаёт порядок сортировки, используется в запросах и индексируется.

value — байты. По значениям столбцов не запрашивают.

timestamp — число (часы): побеждает последняя запись.

Имя — это ключ внутренней карты строки. Имена отсортированы, так что диапазон имён читается одним куском, и проиндексированы, так что одно имя находится без сканирования. Значение — просто байты: строка, число, картинка, — хранится как пришло.

Временная метка (timestamp) разрешает споры между копиями. Одна реплика строки 456 хранит email = eben@bar.com с меткой 1004, другая — email = eben@new.com с меткой 1010. При сравнении на обеих побеждает 1010. Клиент присылает метку с каждой записью; удаление тоже несёт метку, поэтому может победить более старое значение. Просто и быстро, но из двух одновременных записей одна молча теряется.

"you don’t query on column values"

Читай это как правило проектирования, а не жёсткое ограничение: Cassandra умеет находить строки по значению через вторичные индексы (звёздочки на рис. 3), а в CQL есть CREATE INDEX (урок 21).

Каждый узел индексирует только свои строки, поэтому запрос по значению опрашивает все узлы, а column family с этим значением в ключе (раздел 5) читается на одном. В теоретическом ответе процитируй правило и добавь этот нюанс.

Как сортируются имена, задаёт компаратор (comparator) column family (p. 421): byte, utf8, long, timeuuid и другие. Это важно: для имён 2 и 10 utf8 сравнивает символы и ставит "10" первым, long сравнивает числа и ставит первым 2. timeuuid сортирует по времени — естественный выбор для ленты событий.

Ещё один уровень: суперстолбец (super column) группирует столбцы под общим именем (p. 422). Вместо значения он держит карту столбцов. В super column family каждая строка состоит из суперстолбцов. Пример (p. 424): PointOfInterest с ключом — почтовым индексом; каждое место — суперстолбец со своим телефоном и описанием, а у Central Park телефона нет — схема гибкая.

// p. 424: a super column family as nested maps
PointOfInterest {
  key: 85255 {
    Phoenix Zoo { phone: 480-555-5555,
      desc: They have animals here. },
    Spring Training { phone: 623-333-3333,
      desc: Fun for baseball fans. },
  }, //end phx
  key: 10019 {
    Central Park { desc: Walk around. It's pretty.} ,
    Empire State Building { phone: 212-777-7777,
      desc: Great view from 102nd floor. }
  } //end nyc
}

Имена суперстолбцов проиндексированы, имена подстолбцов — нет (p. 425). Поэтому прочитать один подстолбец значит прочитать весь его суперстолбец. Суперстолбцы использовали для денормализации: копировать данные туда, где их читает запрос.

Чтобы прочитать часть столбцов строки, посылают предикат среза (slice predicate) (p. 426): начальное имя, конечное имя (пусто = остановиться по count), reverse и count (как LIMIT). Раз имена отсортированы, срез — это один отрезок строки:

Вложенная карта: от keyspace до одного столбца

Keyspace (здесь он называется app) держит три column family со слайдов. Выбери строку, чтобы увидеть её столбцы в порядке компаратора, каждый с именем, часами и значением. Потом задай предикат среза: возвращённые столбцы закрашиваются и нумеруются в порядке выдачи. Часы и две записи ленты придуманы.

  1. Выбери «User › строка 123», start и finish оставь пустыми, count 4. Предскажи, в каком порядке вернутся четыре столбца.
    Что должно получиться

    email, icon, n, user: по алфавиту, потому что компаратор — utf8. Решает порядок имён — не часы и не значения. В этом главная мысль виджета: чтение называет ключ строки и участок отсортированных имён столбцов, но никогда — значение.

  2. Поставь start = icon и count = 2. Затем включи reverse, оставив start на icon. Предскажи оба ответа.
    Что должно получиться

    Вперёд: icon, n. С reverse: icon, email — когда reverse включён, start становится верхней границей участка, и имена проходятся вниз.

  3. Выбери «time_ordered_blogs_by_user › строка jbellis», start и finish пустые, reverse включён, count 1. Что вернётся и почему это именно то чтение, которое нужно ленте?
    Что должно получиться

    1290020640615 = e03a9d7, самая новая запись. Имена — временные метки, сравниваемые как числа (компаратор long), поэтому reverse с count читает «последние N» — то, что в SQL пишут как ORDER BY … DESC LIMIT.

  4. Выбери «PointOfInterest › строка 10019», поставь start = Empire State Building и count = 1. Предскажи, что вернётся.
    Что должно получиться

    Весь суперстолбец Empire State Building, desc и phone вместе. Срез идёт по именам суперстолбцов, которые проиндексированы; подстолбцы — нет, поэтому суперстолбец возвращается целиком (p. 425).

Слайды показывают API 2010 года (Thrift RPC, pp. 427–428). Отдельного update нет: запись в существующий столбец сохраняет новое значение с более новой меткой, и побеждает более новая.

Никакого SELECT … WHERE: начинай с запросов

Как же сделать WHERE, ORDER BY, JOIN или GROUP BY без SQL (p. 429)? Ответ — способ проектирования, а не конструкция языка (p. 430):

  • в реляционной базе ты моделируешь предметную область — сущности, связи, нормальные формы (уроки 8–9) — и отвечаешь на любой будущий вопрос джойнами: "what answers do I have?";
  • Cassandra находит строки только по ключу и не делает джойнов, поэтому у вопроса, под который не построена структура, нет эффективного ответа. Сначала перечисляешь вопросы: "what questions do I have?"

Пример (p. 431). Column family USER с ключом UserID и столбцами username, email, birth date, city, state. Она отвечает на «дай пользователя 123» за одно чтение — и больше ни на что. Как ответить на такой запрос?

-- p. 431: the query that USER, keyed by UserID, cannot answer
SELECT * FROM User WHERE city = 'Scottsdale'

Создаёшь вторую column family, UserCity, с ключом city, у которой имена столбцов — ID пользователей, живущих в этом городе. Запрос становится одним чтением строки плюс multiget_slice по USER за данными пользователей. Значения в UserCity пустые, вся информация в именах столбцов: это паттерн valueless column (столбец без значения). То, что RDBMS делает индексом, ты делаешь руками — по column family на каждый вопрос, записывая её вместе с USER. Поэтому слайды и называют Cassandra фабрикой индексов (index factory).

В CQL (урок 21) UserCity — это таблица, у которой partition key — город, а id пользователей — значения clustering column, те самые столбцы без значения:

  city text,
  user_id text,

-- all the users of Scottsdale: one partition read

А если искать и по штату, и по городу? Используй составной ключ (aggregate key) (p. 432): ключи строк вида state:city, например AZ:Scottsdale. Тогда все пользователи Аризоны — это строки между AZ: и AZ;, а все пользователи Скоттсдейла — строки между AZ:Scottsdale и AZ:Scottsdale1. Почему эти границы работают?

  1. Четыре строки — AZ:Phoenix, AZ:Scottsdale, AZ:Tucson, CA:Fresno, — в каждой её пользователи как столбцы без значения. Ключи сравниваются как строки, символ за символом, и префикс идёт первым: AZ: стоит перед AZ:Phoenix.

  2. В ASCII двоеточие — 58, точка с запятой — 59. У каждого аризонского ключа на третьем месте двоеточие, поэтому он сортируется перед AZ;. CA:Fresno идёт после AZ;, потому что C стоит после A. Так что от AZ: до AZ; лежат ровно аризонские строки.

  3. Аналогично AZ:Scottsdale1 сортируется сразу после AZ:Scottsdale: в этом диапазоне одна строка — Scottsdale.

  4. Для этого строки должны лежать в порядке ключей: нужен order-preserving partitioner (партиционер, сохраняющий порядок). Случайный (random) хранит строки в порядке MD5 их ключей — AZ:Phoenix (ab66…), AZ:Tucson (f163…), CA:Fresno (f3ca…), AZ:Scottsdale (f412…), — так что калифорнийская строка оказывается между аризонскими, и «строки между AZ: и AZ;» больше не означают пользователей из Аризоны.

А ORDER BY (p. 433)? Такой конструкции нет. Столбцы внутри строки отсортированы компаратором, поэтому, чтобы получать записи по времени, время делают именем столбца — как в time_ordered_blogs_by_user. Строки размещает partitioner: случайный использует MD5-хеш ключа, сохраняющий порядок (order-preserving) — сам ключ.

"are sorted by key, regardless of partitioner"

Строки следуют partitioner: порядок ключей — только при order-preserving. При случайном порядок с ключом никак не связан, так что диапазоны ключей вроде AZ: … AZ; работают только с order-preserving partitioner.

См. последний шаг выше. Order-preserving partitioner платит за диапазоны горячими точками (все ключи AZ: на одних и тех же узлах), а CQL не принимает диапазон по partition key: диапазоны задают по clustering columns (урок 21).

JOIN и GROUP BY тоже решаются проектированием. В примере с отелями (рис. 4, pp. 434–435) восемь реляционных таблиц, связанных внешними ключами, превращаются в семь column family без внешних ключей, каждая под те чтения, которые она обслуживает.

True or false: Cassandra stores the values of each column of a column family together, separately from the other columns, as a column-oriented database such as Vertica does.

  • True Это колоночное хранение со слайдов (pp. 401–407). Cassandra держит столбцы строки вместе под её ключом строки: "think of cassandra as row-oriented" (p. 417).
  • False Cassandra — wide-column store: строка, которую находят по ключу, хранит все свои столбцы вместе (p. 417). Хранить каждый столбец отдельно — это аналитическое колоночное хранилище со слайдов (pp. 401–407).
Показать образец ответа

False. Cassandra is a wide-column (column-family) store: each row is uniquely identified by its key and keeps all its columns, sorted by name, together, so it should be thought of as row-oriented. Storing each column separately is the design of column-oriented databases such as Vertica or C-Store, built for OLAP: a query reads only the columns it needs, while inserts and whole-record reads touch every column. Cassandra is called columnar because of its column families and its very wide rows, and it is built for write-heavy workloads.

Ловушка — в слове «column», общем для двух разных конструкций (разделы 2 и 3). За неправильные ответы может быть штраф, о нём объявляют прямо перед экзаменом: отвечай только то, что можешь обосновать.

Explain how a column-oriented database stores a table and compare it with a row-oriented database: advantages, disadvantages, and the workloads each one suits.

Показать образец ответа

A row-oriented database stores each record contiguously; a column-oriented database stores each column contiguously, in its own storage. A query that needs k of the m columns therefore reads only those k columns in a column store, while a row store reads whole records and may read unnecessary data. The column layout also compresses better (the values of a column share a type and repeat, so techniques such as run-length encoding work well) and improves bandwidth utilisation, code pipelining and cache locality. Its disadvantages are increased disk seek time (a record is spread over many files), an increased cost of inserts (one write per column) and increased tuple reconstruction costs (records must be rebuilt by position). Column stores therefore suit read-mostly, read-intensive, large repositories — OLAP and data mining — while row stores suit OLTP, with frequent inserts and updates of whole records.

У полного ответа четыре части: две раскладки, довод про чтение (k из m столбцов), плюсы и минусы словами слайдов (pp. 403–404) и типы нагрузки. Сильное дополнение — график со слайда (p. 405): колоночное хранилище проигрывает, только когда запрос выбирает почти весь кортеж.

The Quarter column of a sales table, sorted by quarter, is stored with run-length encoding as (Q1, 1, 300), (Q2, 301, 350), (Q3, 651, 500), (Q4, 1151, 600). Which statements are correct? Select all that apply.

  • (Q2, 301, 350) means that Q2 is stored at the positions from 301 to 350. Третье число — длина, а не конец: Q2 занимает 350 позиций с 301 по 650.
  • The table has 1,750 rows. Последняя серия заканчивается на 1151 + 600 − 1 = 1750 — столько же, сколько 300 + 350 + 500 + 600.
  • Position 700 holds Q3. Q3 начинается с 651 и покрывает 500 позиций, до 1150.
  • The Price column of the same table would shrink just as much with the same encoding. Соседние цены редко повторяются: каждая цена превратилась бы в тройку, втрое больше сырого размера, — поэтому слайд (p. 407) оставляет Price несжатым.
  • Sorted by customer instead, the same Quarter column would usually compress far less. Сериям нужны равные значения рядом; другой порядок сортировки их разбивает.
Показать образец ответа

The second, third and fifth statements. Each triple is (value, start_pos, run_length), so (Q2, 301, 350) covers the positions 301 to 650; the last run ends at 1151 + 600 − 1 = 1750; position 700 lies in the run of Q3, from 651 to 1150. Run-length encoding pays only when equal values are adjacent: the Quarter column is sorted and the prices are not, so the encoding is chosen column by column and Price stays raw.

Describe the data model of Cassandra as presented in the lecture — keyspace, column family, row, column and super column. Explain why a column family is called a sparse table and what the timestamp of a column is used for.

Показать образец ответа

A keyspace is the outermost container, roughly a database and typically one per application; some settings, such as the replication, are configured per keyspace. It contains column families, the analogue of tables, which group records of a similar but not identical kind; their settings include the comparator and the type, standard or super. A column family holds rows, each uniquely identified by its row key; Cassandra should be thought of as row-oriented, because a row's columns are stored and returned together. A column has three parts: a name (bytes; it determines the sort order, is used in queries and is indexed), a value (bytes; values are not queried) and a timestamp. A super column groups columns under a common name: it has a name and a map of columns instead of a value, and its sub-column names are not indexed. A column family is a sparse table because each row stores only the columns it has: a missing column costs nothing and is not a NULL. The timestamp (clock) is supplied with every write and resolves conflicts between replicas: the last write wins.

Дай цепочку вложенности по порядку и три части столбца с их свойствами (p. 420). «Sparse» и «last write wins» — два «почему», о которых спрашивает вопрос. Если цитируешь пример настройки keyspace со слайда, partitioner, добавь, что на самом деле он задаётся для всего кластера (красная ручка к слайду (p. 413)).

Explain the difference between the domain-based model of an RDBMS and the query-based model of Cassandra. How would you support the query SELECT * FROM User WHERE city = 'Scottsdale' on a column family User keyed by UserID, and what does the solution cost?

Показать образец ответа

An RDBMS follows a domain-based model: you model the entities and relationships of the domain, normalise them, and answer any later question by combining tables with joins ("what answers do I have?"). Cassandra follows a query-based model: rows are found by key, column values are not queried and there are no joins, so you list the questions first and build a structure for each one ("what questions do I have?" — start from queries, then design the data model). For the query, create a second column family, UserCity, keyed by city, whose column names are the IDs of the users living there, with empty values (the Valueless Column pattern): the query becomes one row read, followed by a multiget of the users from User. This is why Cassandra is called an index factory. The cost is duplication: every user is written to both column families, and the application must keep the copies consistent, with no joins and no referential integrity to help.

Ответ держится на двух вещах: почему (строки находятся только по ключу, джойнов нет) и цена (дублирование, копии синхронизирует приложение). В CQL та же идея — таблица с PRIMARY KEY ((city), user_id). Suppose you expect to record a large-scale, continuously increasing number of reservations, and therefore you decide to store them in a columnar database. Write the specification of the tables (column families) of a Cassandra deployment so that one can query the hotels of a state, the hotels of a city of a given state, and the reservations of a guest by phone number, the most recent first. Do not use indexes.

Показать образец ответа

Two tables, one per access path: the hotels by location, partitioned by state and clustered by city, and the reservations by guest phone, partitioned by phone and clustered by start date, the most recent first. Each reservation carries copies of the guest, hotel and room data it shows, because Cassandra has no joins.

-- the keyspace (one per application)
CREATE KEYSPACE hotels
  WITH replication = {'class': 'SimpleStrategy',
                      'replication_factor': 3};
-- queries 1 and 2: the hotels of a state, or of a city in it
CREATE TABLE hotels_by_location (
  state text,
  city text,
  hotel_id text,
  name text,
  phone text,
  address text,
  zip text,
  PRIMARY KEY ((state), city, hotel_id)
);
-- query 3: a guest's reservations, with copies, newest first
CREATE TABLE reservations_by_guest_phone (
  guest_phone text,
  start_date date,
  reservation_id uuid,
  end_date date,
  guest_name text,
  hotel_id text,
  hotel_name text,
  room_number int,
  rate float,
  PRIMARY KEY ((guest_phone), start_date, reservation_id)
) WITH CLUSTERING ORDER BY (start_date DESC, reservation_id ASC);
-- all the hotels of Arizona: one partition
SELECT * FROM hotels_by_location WHERE state = 'AZ';
-- the hotels of Scottsdale: the first clustering column fixed
SELECT * FROM hotels_by_location
  WHERE state = 'AZ' AND city = 'Scottsdale';
-- a guest's reservations, the most recent first
SELECT * FROM reservations_by_guest_phone
  WHERE guest_phone = '+1 480 555 0101';

Every reservation is one INSERT into reservations_by_guest_phone, with reservation_id from uuid() and the guest's name, the hotel's name and the room's number and rate copied in.

Это слайды (pp. 431–435) на CQL. hotels_by_location — это составной ключ state:city со слайда (p. 432): штат — partition key, а город — первый clustering column, так что одна таблица отвечает на оба вопроса о местоположении без диапазона ключей и без order-preserving partitioner. reservations_by_guest_phone — это Reservation со слайда (p. 435): ключ — то, по чему ищет приложение, с копиями вместо джойнов; reservation_id разделяет два бронирования одного гостя на один день, потому что INSERT с уже существующим первичным ключом перезаписывает строку.   • никакой: в Cassandra нет ORDER BY, поэтому записи нельзя вернуть в порядке времени Клаузы ORDER BY нет, но имена отсортированы компаратором — сделать время именем столбца и есть способ получить порядок (p. 433).

  • две column families, одна с ключом по городу, другая — по штату, имена столбцов в которых — ID живущих там пользователей UserCity со слайда (p. 431), построенная дважды: каждый вопрос — чтение одной строки, и каждый пользователь записывается в оба семейства.
  • SELECT * FROM User WHERE city = 'Scottsdale' на column family User с ключом UserID Строки находятся по ключу; без индекса это означает прочитать всё — именно этого слайд (p. 431) и стремится избежать.
  • column family с ключом state:city, которую читают диапазоном ключей от AZ: до AZ; при order-preserving partitioner Слайд (p. 432): одно семейство отвечает на оба вопроса, пока строки лежат в порядке ключей.
  • то же семейство state:city при random partitioner Тогда строки идут в порядке MD5 ключа: калифорнийская строка оказывается между аризонскими, и диапазон ключей больше не означает Аризону (красная ручка к слайду (p. 433)).
  • джойн User с column family City "Doesn't support joining" (p. 437).

Обе работающие схемы — фабрики индексов: данные копируются в семейство с ключом по тому значению, по которому ищут.

Почему Cassandra отказывается от джойнов (p. 437)?

  • Потому что значения столбцов — непрозрачные байты, которые нельзя сравнивать Джойн сравнивает ключи, а ключи сравнивать можно; препятствие в другом.
  • Потому что column family не может хранить ключ другой строки Может: Reservation хранит hotelID и roomID (p. 435). Просто никто их не проверяет и не следует по ним.
  • Потому что теорема CAP запрещает джойны в AP-системах CAP ничего не говорит о джойнах; она про реплики во время разделения сети.
  • Потому что объединяемые строки жили бы на разных узлах, и координировать их на каждом запросе стоило бы той линейной масштабируемости и доступности, ради которых Cassandra построена Поэтому данные, которые читают вместе, и хранят вместе, при необходимости дублируя: "Tables contain duplicate denormalize data" (p. 437).

В super column family PointOfInterest тебе нужен только телефон Empire State Building (строка 10019). Что прочитает Cassandra?

  • только столбец phone, найденный через индекс "sub-column names in a SCF are not indexed" (p. 425).
  • всю строку 10019, включая Central Park Имена суперстолбцов проиндексированы, так что она может сразу перейти к Empire State Building.
  • весь суперстолбец Empire State Building, desc и phone, а потом выберет phone Верхний уровень проиндексирован, подстолбцы — нет: суперстолбец читается целиком.
  • ничего: суперстолбец нельзя прочитать по имени Путь к столбцу (column path) может назвать суперстолбец и даже подстолбец (get, p. 427); отличается стоимость.

Главное

  • Строковое хранилище держит каждую запись одним куском, колоночное — каждый столбец: запрос, которому нужны \(k\) из \(m\) столбцов, читает в колоночном хранилище долю \(k/m\) байтов, но чтение или вставка целой записи затрагивает \(m\) мест — "suitable for read-mostly, read-intensive, large data repositories" (pp. 402–405).
  • Колоночные хранилища хорошо сжимаются, потому что соседние значения принадлежат одному атрибуту; кодирование длин серий хранит (value, start_pos, run_length) и окупается только на отсортированных или сгруппированных столбцах (pp. 406–407).
  • «Columnar» называет два семейства: column-oriented stores (Vertica, C-Store, MonetDB, SybaseIQ, LucidDB) и wide-column stores (Cassandra, BigTable, HBase) — "think of cassandra as row-oriented" (p. 417).
  • "cassandra ~= bigtable + dynamo": модель данных Bigtable (разреженная карта) на распределении Dynamo (O(1) DHT, согласованность, настраиваемая клиентом); по умолчанию AP и согласованность в конечном счёте (eventual consistency), "tuneably consistent" для каждой операции.
  • keyspace › column family › строка (по ключу) › столбец (имя, значение, временная метка): имена отсортированы компаратором и читаются срезами, по значениям по замыслу не запрашивают, побеждает последняя запись; суперстолбцы добавляют уровень именованных групп, подстолбцы которых не индексируются.
  • Модель Cassandra основана на запросах: начинай с запросов, строй по column family на каждый вопрос (фабрика индексов, столбцы без значения, составные ключи), получай порядок проектированием (компаратор, партиционер) и денормализуй вместо джойнов — ни джойнов, ни ссылочной целостности.
  • Сегодня ту же модель записывают на CQL (урок 21): таблица, partition key, clustering columns; ни суперстолбцов, ни Thrift.
Row store
каждая запись одним куском: лёгкие вставки и обновления, "might read in unnecessary data" (OLTP)
Column store
каждый столбец отдельным куском: "only need to read in relevant data"; читает \(k/m\) байтов (OLAP)
Pros (p. 403)
data compression · bandwidth utilization · code pipelining · cache locality
Cons (p. 404)
disk seek time · cost of inserts · tuple reconstruction
Tuple reconstruction
позиция \(i\) каждого столбца = запись \(i\); "Large prefetch hides disk seeks in columns"
Тройка RLE
(value, start_pos, run_length): покрывает start_pos … start_pos + run_length − 1; следующий start = start + length
cassandra ~= bigtable + dynamo
модель данных sparse map + O(1) DHT и согласованность, настраиваемая клиентом
CAP (p. 400)
Cassandra: eventual (weak) consistency, availability, partition tolerance; "tuneably consistent" (p. 438)
Keyspace
~= база данных, одна на приложение; задаёт репликацию (партиционер — один на кластер)
Column family
разреженная таблица похожих записей; компаратор; тип standard или super
Column
name (отсортировано, используется в запросах, проиндексировано) · value (по нему не запрашивают) · timestamp (last write wins)
Comparator
порядок имён столбцов: byte, utf8, long, timeuuid, lexicaluuid, pluggable
Super column
имя + карта столбцов; имена подстолбцов не индексируются, читается целиком
SliceRange
start, finish (пусто = остановиться по count), reverse, count (как LIMIT)
API чтения и записи
get, get_slice, multiget_slice, get_range_slices; insert, batch_mutate, remove — ключ первым, CL последним
Query-based model
"Start from queries, then design the data model": фабрика индексов (index factory), столбцы без значения (valueless columns), составные ключи (aggregate keys)
ORDER BY (p. 433)
столбцы — по компаратору; строки — по токену партиционера, порядок ключей только с order-preserving
vs RDBMS (pp. 436–437)
без мастера; без джойнов; без ссылочной целостности; дублированные, денормализованные данные
