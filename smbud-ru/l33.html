Потоки в Hadoop: Storm, Flume и Sqoop

После этого урока ты сможешь объяснить, почему топология Storm никогда не заканчивается и в какую задачу попадает каждый кортеж, собрать и рассчитать поток Flume из source, channel и sink по его файлу свойств и скопировать реляционную таблицу в HDFS или Hive с помощью Sqoop.

Flume — это водяной лоток, по которому брёвна сплавляют от места вырубки к лесопилке (p. 943). Apache Flume взял себе это имя, а вместе с ним и устройство: производят во многих местах, потребляют в одном, а лоток несёт груз между ними.

У интернет-магазина 64 веб-сервера, и каждый отправляет в Hadoop по 2 000 строк логов в секунду. Однажды ночью HDFS — та самая лесопилка — встаёт на час; серверы — нет. Где ждут 460 миллионов строк этого часа и насколько большой должна быть комната ожидания?

Ответ — однострочное эмпирическое правило со слайдов о расчёте Flume, одно-единственное умножение. По дороге встретятся Storm, который вычисляет на данных, которые никогда не кончаются, и Sqoop, который вообще не работает с потоками.

Вычисление, которое никогда не заканчивается

Все инструменты до сих пор читали вход, который уже закончился. Задание MapReduce (урок 30), скрипт Pig или запрос Hive (урок 32) стартует с файлов в HDFS, работает и останавливается. Слайд (p. 924): "Lots of tools for data (i.e. batch) processing", но "None of them are realtime systems which is becoming a real requirement for businesses". Оповещение о мошенничестве не может ждать, пока файл закончится, потому что этот файл не закончится никогда.

Конспект курса описывает этот сдвиг так: в потоковой обработке данные «преобразуются и анализируются непрерывно, по мере того как они генерируются», вместо того чтобы сначала сохраняться и обрабатываться потом (конспект, гл. 4). Вход — это поток данных (data stream), неограниченная последовательность меняющихся во времени данных. Запрос остаётся зарегистрированным и работает над протекающими мимо данными, а поскольку конца неограниченного входа никто дождаться не может, он смотрит на ограниченные окна (windows) — например, клики за последнюю минуту. На карте «пропускная способность — задержка» из конспекта это зона "Continuous": низкая задержка, за которую платят пропускной способностью.

BackType купил Twitter в мае 2011 года; в сентябре того же года Storm стал open source, а в 2014-м — проектом верхнего уровня Apache (история Storm от Натана Марца, в ресурсах).

Storm, как сказано на том же слайде, был "Developed by BackType which was acquired by Twitter" и "provides realtime computation" с четырьмя обещаниями: "Scalable" — каждый кусок вычисления выполняется как множество параллельных задач; "Guarantees no data loss"; "Extremely robust and fault-tolerant" — упавший воркер перезапускается, а работа умершей машины переназначается; "Programming language agnostic". "Realtime" здесь значит низкую задержку, результаты за секунды, а не жёсткий дедлайн.

«Guarantees no data loss — значит, каждый кортеж обрабатывается ровно один раз». Нет: документация Storm обещает обработку at-least-once (хотя бы один раз). Кортеж, который не успели полностью обработать вовремя, заново проигрывается из spout, так что ничего не теряется, — но после сбоя один и тот же кортеж может быть обработан дважды, и счётчик может посчитать его дважды.

Четыре слова: stream, spout, bolt, topology

Stream (поток) — "Unbounded sequence of tuples" (p. 927). Кортеж (tuple) — это именованный список значений, например (word: "fresh").

Spout — "Source of streams" (p. 928): читает данные снаружи — из очереди сообщений, лога, API — и выпускает кортежи.

Bolt — "Processes input streams and produces new streams: Can implement functions such as filters, aggregation, join, etc" (p. 929).

Topology (топология) — "Network of spouts and bolts" (p. 930): ориентированный граф, в котором каждый bolt подписан на потоки других компонентов.

Топология — это потоковый двойник задания MapReduce, с двумя отличиями: это любой граф, а не фиксированная пара «map, потом reduce», и, словами туториала Storm, «задание MapReduce в конце концов заканчивается, а топология обрабатывает сообщения вечно (или пока ты её не убьёшь)». Storm — не последний потоковый процессор курса: Spark Streaming из модуля 11 (урок 38) принимает входы из "Kafka, Flume, Twitter, TCP Sockets" (p. 1200) — и Flume, второй инструмент этого урока, среди них.

Кластер

Слайд (p. 925) рисует три группы машин (рис. 2). Nimbus, "Master node (similar to Hadoop JobTracker)", рассылает код топологии по кластеру, распределяет её задачи по машинам и переназначает их, когда машина падает, — это JobTracker из урока 31. Supervisors "Run worker processes" на рабочих машинах. Между ними стоит ZooKeeper, "Used for cluster coordination".

Зачем третья сторона? Nimbus и Supervisors никогда не говорят напрямую: назначения и heartbeat-сигналы идут через ZooKeeper. Оба демона «fail-fast и без состояния; всё состояние хранится в Zookeeper или на локальном диске» (туториал Storm), так что любой из них можно убить и перезапустить без потерь, а пока Nimbus лежит, работающие топологии продолжают работать.

Топология (topology) — граф из spouts и bolts, который никогда не заканчивается; Nimbus распределяет его задачи, Supervisors их выполняют, ZooKeeper хранит состояние.

Какая задача получит кортеж?

"Spouts and bolts execute as many tasks across the cluster" (p. 931): каждый компонент получает некоторое число задач (tasks), и каждая выполняет один и тот же код на своей доле кортежей. Масштабировать топологию — значит поднять эти числа, а не переписывать код. Подсчёт слов из туториала Storm — на входе предложения, на выходе текущий счётчик по каждому слову — задаёт их последним аргументом:

// Storm tutorial word count: 5 spout, 8 split, 12 count tasks
TopologyBuilder builder = new TopologyBuilder();
builder.setSpout("sentences", new RandomSentenceSpout(), 5);
builder.setBolt("split", new SplitSentence(), 8)
        .shuffleGrouping("sentences");
builder.setBolt("count", new WordCount(), 12)
        .fieldsGrouping("split", new Fields("word"));

Каждый выпущенный кортеж ставит вопрос со следующего слайда: "When a tuple is emitted which task does it go to?" Ответ — группировка потока (stream grouping), которая объявляется на каждом ребре, когда bolt подписывается на поток, — выше это .shuffleGrouping(…) и .fieldsGrouping(…). Слайд (p. 933) перечисляет четыре.

На слайде сказано consistent hashing. Документация Storm описывает хеш полей по модулю числа задач. Для экзамена важно свойство: одинаковые значения — одна и та же задача.

Выбор между ними решает подсчёт. Задача подсчёта держит счётчик на каждое слово в собственной памяти. При shuffle grouping кортежи "fresh" расходятся по всем задачам, и каждая хранит лишь часть счёта; итога не знает ни одна. При fields grouping по "word" каждый "fresh" попадает в одну задачу, которая поэтому и хранит истинный счёт, — потоковый близнец правила MapReduce «один ключ — один редьюсер» (урок 30). Рис. 3 добавляет report bolt на global grouping, чтобы одна задача видела все счётчики.

Теперь разведи слова сам. Виджет делает так, что одну мысль невозможно пропустить: fields grouping держит одно и то же слово в одной и той же задаче — и именно это делает параллельный подсчёт правильным.

Песочница топологии: куда идёт каждое слово?

Подсчёт слов с рис. 3, но без report bolt. Spout снова и снова выпускает шесть коротких постов с фермерского рынка; split bolt превращает каждый пост в кортежи-слова; каждая задача подсчёта держит собственные счётчики. Задай число задач для каждого компонента и группировку ребра split → count (ребро spout → split остаётся на shuffle), потом выпускай предложения. Рисунок показывает кортежи последнего предложения, а таблица — что насчитала к этому моменту каждая задача подсчёта. Fields grouping хеширует слово (FNV-1a, простой хеш строки) по модулю числа задач; shuffle выбирает задачу случайно, но с фиксированным seed, так что каждый прогон после «Сбросить» одинаков.

  2. Переключись на fields grouping (прогон начнётся заново) и дважды нажми «Следующий раунд». Предскажи, сколько столбцов в строке "fresh" будет заполнено.

    Один: задача 1 хранит "fresh" 8 раз, истинный счёт, вместе с "milk" (4). Каждое слово живёт ровно в одной задаче — одно и то же слово всегда идёт в одну и ту же задачу, и это и есть главная мысль виджета. Посмотри и на нагрузку: задача 0 считала только "honey" (6 кортежей), а задача 2 — 18. Fields grouping распределяет ключи, а не кортежи.

    Что должно получиться

    144 доставки, по 4 копии каждого кортежа, и каждая задача хранит "fresh" 8: точно, но посчитано четыре раза. All grouping — для того, что нужно каждой задаче, например новой конфигурации, а не для разделения работы.

  4. Выбери global grouping, по-прежнему 4 задачи подсчёта, и прогони два раунда. Какая задача работает? Потом поставь spout на 2 задачи, а split на 4 и снова прогони два раунда — изменятся ли счётчики?
    Что должно получиться

    Задача 0, с наименьшим id, получает все 36 кортежей; задачи 1–3 простаивают, так что параллелизм count bolt пропадает зря. Global grouping подходит для одного итогового значения или top-N. Больше задач spout или split ничего не меняют в счётчиках: ни один из этих компонентов не хранит состояния, так что любая их задача может обработать любое предложение.

Flume: пруд на каждой станции

Прежде чем что-то запустить на Hadoop, данные должны туда попасть. Вопрос со слайда (p. 935): "How do you get your data from these sources to Hadoop?" — а источники здесь — RDBMS и приложения (рис. 4). У каждого компонента Hadoop есть Java API (p. 936), так что каждое приложение могло бы писать в HDFS само; почему этого мало, перечислено на следующем слайде: "Multiple events", "Streaming", "Diverse sources", "Buffering" — "Flume and Sqoop can help!"

Производителей много, их число "changes constantly", и они сидят "in different governance zones, data centers, continents" (p. 940). Их данные тоже дрейфуют: датацентр переходит на IPv6, разработчик "changes logs (again)", у JSON-записи появляется новое поле (p. 941). Код на каждом производителе пришлось бы менять вслед за каждым таким изменением.

Определение даёт слайд (p. 939): "Apache Flume is a continuous data ingestion system" — open source, надёжная, масштабируемая, управляемая, настраиваемая, — которая доставляет логи, потоки кликов, данные датчиков, социальные потоки и фиды в хранилища (HDFS, S3), в системы запросов (Hive, HBase, Cassandra…) или в поисковые движки. Она была "Originally designed to be a log aggregation system by Cloudera Engineers" и "Evolved to handle any type of streaming event data" (p. 943). Flume перемещает данные, но не вычисляет на них.

Агент: source, channel, sink

Агент (agent) — это "Simplest unit in Flume" (p. 944): один процесс, который соединяет "any number of sources to any number of data stores" через три вида компонентов (p. 948).

Source (источник) — "Accepts incoming Data", "Scales as required", "Writes data to Channel".

Channel (канал) — "Stores data in the order received".

Sink (сток) — "Removes data from Channel", "Sends data to downstream Agent or Destination".

Едет по этой цепочке событие (event), "the base unit of communication between components" (p. 946): заголовок (header) с метаданными, который "Can be used for routing content", и тело (body), "actual content" (p. 947), — байты, которые Flume понимать вовсе не нужно. Важны стрелки на том же слайде: "Source pushes events", "Sink polls for events". Sink всё время спрашивает channel «Got any events?», а channel сам никого не вызывает. Слайд (p. 966) добавляет кратности: "Source – Channel: many-to-many", "Channel– Sink: one-to-many (sink reads only from one channel)".

Транзакции

Агенты выстраиваются в цепочки: лекция рисует "Distributed Pipeline Architecture" из агентов от веб-логов до HDFS, у каждого свой channel, и sink одного агента питает source следующего. Слайд (p. 949): "Source uses transactions to write to the channel", "Sink uses transactions to remove data from the channel", "Sink transaction commits only after successful transfer of data". Source коммитит батч только тогда, когда channel принял его целиком. Sink берёт батч, доставляет его — в HDFS или в source следующего агента, который коммитит его в свой channel, — и только потом коммитит, удаляя батч. При любом сбое транзакция откатывается, и события остаются на месте: эстафетная палочка, которую отпускают, только когда её взяла другая рука.

"This ensures no data loss in Flume pipeline"

Транзакции делают безопасной каждую передачу, пока агенты работают: событие покидает channel только после того, как его получил следующий узел. Это отсутствие потерь в пути при надёжном (file) channel, и это at-least-once, а не exactly-once: батч, повторённый после неудачного коммита, может прийти дважды. С memory channel события в канале теряются, когда процесс агента умирает.

Слайд (p. 968) называет memory channel "Not persistent", слайд о размерах батчей предупреждает о "duplication impact" больших батчей, а руководство пользователя Flume говорит, что «любые события, оставшиеся в memory channel, когда процесс агента умирает, восстановить нельзя», — попробуй кнопку сбоя в виджете ниже. Слайд (p. 986) повторяет утверждение ("Flume never loses any data in transit between Agents"): экзамен может его напечатать, так что знай его и его условия.

Зачем нужны каналы?

Слайд (p. 951) даёт три причины: channel "Buffers data and insulates downstream from load spikes", "Provides persistent store for data in case the process restarts" и "Provides flow ordering* and transactional guarantees". У звёздочки нет сноски; уточнение — на итоговом слайде о Flume: "weak ordering guarantee, i.e., in the absence of failures the data will arrive in the order it was received". График на том же слайде рассказывает жизнь канала: в установившемся режиме он почти пуст; растёт, когда отказывает пункт назначения; на "Channel Full" отказывают и записи source, и давление уходит вверх по течению; когда пункт назначения восстановлен, накопившееся рассасывается.

Слайд (p. 968) предлагает два вида. Memory channel — это "In-memory queue", "Fast", "Not persistent", "Limited capacity". Второй, "Disk", в конфигурации называется file channel (type = file): он пишет события на локальный диск, переживает перезапуск и может быть намного больше — ценой скорости.

От трёх веб-серверов к сходящемуся потоку

Слайды (pp. 952–956) рассказывают случай, ради которого Flume и строили: логи веб-серверов в HDFS. При "only 3 web servers at the time of launch" "Ad-hoc solution will likely suffice!" (p. 953). Рост приносит проблемы: "How do you manage your output paths on HDFS?" и "How do you maintain your client code in face of changing environment as well as requirements?"

Один агент Flume между серверами и HDFS (p. 954) даёт "Insulation from HDFS downtime", "Quick offload of logs from Web Server machines" и "Better Network utilization" — но "What if the Flume node goes down?" Два агента, к которым подключён каждый сервер (p. 955), дают "Redundancy and Availability" и "Automatic load balancing and failover" — пока не появятся новые серверы. Масштабируемый ответ — сходящийся поток (converging flow) (p. 956): агенты рядом с серверами, агрегируемые уровнями (tiers) 2 и 3 "before being put into destination system".

На этих слайдах "batch size" значит, сколько агент отправляет вниз по течению за единицу времени. В конфигурации Flume batchSize — это число событий в одной транзакции.

Зачем сходиться? HDFS предпочитает немногих писателей, которые пишут большие файлы (урок 31): каждый файл стоит памяти на NameNode. "Closer a tier is to the destination, larger the batch size it delivers downstream", отсюда и "Optimized handling of destination systems". На одного агента объём событий "is least in the outermost tier" и "highest in the innermost tier" (p. 958); на уровень — "In steady state, all tiers carry same event volume", а "Transient variations in flow are absorbed and ironed out by channels" (p. 959). Тот же итог, меньше агентов — больше на каждого.

Три эмпирических правила

"What we know" (p. 960): число веб-серверов, объём логов на сервер за единицу времени, пункт назначения и маршрутизация к нему, худший случай простоя пункта назначения. "What we will calculate": число уровней, размеры батчей на выходе, ёмкость канала — по одному правилу на каждое (pp. 961–964):

\[ N_{t+1} = \left\lceil N_t / f \right\rceil, \quad 4 \le f \le 16 \] \[ B_t = V / N_t \] \[ C = r_{\text{in}}^{\max} \times T_{\text{out}}^{\max} \]
\(N_t\)
число агентов на уровне \(t\); уровень 1 — клиентские агенты
\(f\)
fan-in: "One Aggregating Agent (A) can be used with anywhere from 4 to 16 client Agents" (p. 961)
\(V\)
объём событий, входящих в поток в установившемся режиме, одинаковый на каждом уровне (p. 959)
\(B_t\)
размер батча на выходе одного агента уровня \(t\): "total exit data volume divided by number of Agents in a tier" (p. 962)
\(C\)
ёмкость канала: "worst case data ingest rate sustained over the worst case downstream outage interval" (p. 963)
\(r_{\text{in}}^{\max}\)
худшая скорость поступления, в событиях в секунду
\(T_{\text{out}}^{\max}\)
худший простой ниже по течению, в секундах

Слайды формулируют правила словами; первая формула — это соотношение «от 4 до 16», применённое уровень за уровнем. Второе правило нарисовано на слайде (p. 962): \(n\) клиентских агентов отправляют по \(k\), так что один агент ниже по течению должен доставлять \(n * k + \Delta\), а два — по \((n * k + \Delta)/2\), где \(\Delta\) — запас. У каждого правила есть свои "Considerations": уровни должны ещё и обеспечивать "routing, load-balancing and failover"; "Having some extra room is good", а большие батчи делают дубликаты дорогими; "Multiple disks will yield better performance", и "Channel size impacts the back-pressure buildup in the pipeline" — больший канал отодвигает момент, когда производителям начинают отказывать. И у каждого есть "Test": нагрузочно проверить установившийся режим, пик и failover и ожидать, что "need more disk space than the physical footprint of the data size". Интернет-магазин из загадки, шаг за шагом:

  1. Что мы знаем: 64 веб-сервера, по 2 000 событий в секунду каждый, 500 байт на событие; пункт назначения — HDFS, без маршрутизации; худший простой HDFS — один час, 3 600 секунд.

  2. Уровни (p. 961): по клиентскому агенту на сервер дают \(N_1 = 64\). Fan-in 8 даёт \(N_2 = 8\). Ещё один fan-in 8 дал бы единственный агрегатор, а единственный агент — это единая точка отказа (p. 954); fan-in 4 даёт \(N_3 = 2\).

    \[ 64 \to 8 \to 2 \]

  3. Объём (p. 959): в установившемся режиме каждый уровень несёт то, что входит в поток, — 64 МБ в секунду при 500 байтах на событие.

    \[ V = 64 \times 2000 = 128\,000 \ \text{events/s} \]

  4. Размер батча на выходе одного агента (p. 962): уровень 1 отправляет 2 000 событий/с на агента, уровень 2 — 16 000, уровень 3 — 64 000. Добавь запас \(\Delta\) и проверь failover: если один агент уровня 3 упал, второй должен в одиночку пропускать все 128 000.

    \[ B_3 = 128\,000 / 2 = 64\,000 \]

  5. Ёмкость канала (p. 963): уровень 3 должен удержать всё, что придёт за время простоя, — 460.8 миллиона событий по 500 байт, около 230 GB, то есть по 115 GB на агента. Это file channel, разложенный на несколько дисков; memory channel даже близко не подходит.

    \[ \begin{aligned} C &= 128\,000 \times 3600 \\ &\approx 4.6 \times 10^{8} \ \text{events} \end{aligned} \]

Агент в десяти строках свойств

Запуск Flume — это два шага (p. 970): "Configure agent(s) in property file", потом "Run Flume agent from console". Один файл может описывать несколько агентов; --name выбирает, какой запустить.

$ flume-ng agent --conf-file spool-to-logger.properties \
  --name agent1

Слайд (p. 971) — это весь файл агента «1-1-1»: один source, один channel, один sink:

# spool-to-logger.properties (p. 971)
agent1.sources = source1
agent1.sinks = sink1
agent1.channels = channel1

agent1.sources.source1.channels = channel1
agent1.sinks.sink1.channel = channel1

agent1.sources.source1.type = spooldir
agent1.sources.source1.spoolDir = /Users/udi/tmp/spooldir

agent1.sinks.sink1.type = logger
agent1.channels.channel1.type = file

Читай его тремя блоками. Сначала имена компонентов agent1. Потом проводка: source перечисляет свои channels, во множественном числе, потому что может питать несколько; sink называет свой channel, в единственном, — правило о кратностях зашито прямо в имена ключей. Наконец, type и свойства каждого компонента. Этот агент превращает каждую строку каждого файла, брошенного в spooling-каталог, в событие, держит его в file channel и печатает через logger sink.

Каталог компонентов (pp. 967–969). Sources: Spooling Directory — "Text Files, Immutable, Unique name", поскольку source отслеживает файлы по имени и останавливается с ошибкой, если файл изменился или имя повторилось (руководство пользователя Flume), — SysLog, Exec (вывод команды вроде tail -F) и Custom. Channels: Memory и Disk. Sinks: HDFS, HBase, "Console Log" и "Local Directory" — в конфигурации это logger sink (type = logger) и file_roll sink.

HDFS sink

# p. 972: the logger sink replaced by an HDFS sink
agent1.sinks.sink1.type = hdfs
agent1.sinks.sink1.hdfs.path = /tmp/flume
agent1.sinks.sink1.hdfs.filePrefix = events
agent1.sinks.sink1.hdfs.fileSuffix = .log
agent1.sinks.sink1.hdfs.inUsePrefix = _
agent1.sinks.sink1.hdfs.fileType = DataStream

hdfs — короткое имя класса со слайда, org.apache.flume.sink.hdfs.HDFSEventSink. Файлы ложатся в /tmp/flume как events.<timestamp>.log — это ответ на вопрос про "output paths" из истории с веб-серверами. Пока файл пишется, его имя начинается с _, а задания Hadoop такие файлы пропускают: ни одно задание не прочитает половину файла. Sink «перекатывает» файл (roll) — закрывает его и открывает новый, — и "By default, files are rolled over every 30 seconds", а rollCount и rollSize служат дополнительными триггерами (p. 973). fileType выбирает "SequenceFile = binary format", "DataStream = uncompressed files (text)" или "CompressedStream = compressed files" (p. 974).

30 секунд со слайда (p. 973) — это hdfs.rollInterval. Руководство пользователя Flume даёт значения по умолчанию и двум другим триггерам — rollSize 1024 байта, rollCount 10 событий, — и побеждает тот триггер, что сработал первым, так что загруженный sink с настройками по умолчанию закрывает файл после 10 событий или 1 KB, смотря что наступит раньше, и забивает HDFS крошечными файлами. Поставь триггер в 0, чтобы его выключить.

HTTP на входе, папки по заголовку

Слайд (p. 975) меняет source на HTTP-сервер, перед memory channel на 1 000 событий:

# p. 975: an HTTP source on port 8989 and a memory channel
httpagent.sources.http-source.type = org.apache.flume.source.http.HTTPSource
httpagent.sources.http-source.bind = localhost
httpagent.sources.http-source.port = 8989
httpagent.channels.ch.type = memory
httpagent.channels.ch.capacity = 1000
Команда на слайде (p. 976) напечатана с фигурными кавычками и незакрытой строкой тела; версию здесь можно набрать.

Клиенты отправляют события в "Fixed format: header + body" (p. 976): JSON-массив объектов с headers и body. Когда канал полон, source отвечает HTTP 503 (руководство пользователя Flume): обратное давление (back-pressure), которое клиент видит.

$ curl -X POST -H 'Content-Type: application/json; charset=UTF-8' \
  -d '[{"headers": {"eventheader1": "event1", "eventheader2": "event2"},
        "body": "This is the body1"}]' \
  http://localhost:8989

"Bucketing" (p. 977) — это "Dynamic assignment of files to folders": %{topic} в пути заменяется, событие за событием, значением заголовка topic, так что событие со слайда с "topic" : "topic1" попадает в /tmp/flume/http/topic1/. Имена заголовков чувствительны к регистру: "Topic" со слайда — это topic и в пути, и в событии. Bucketing по времени (p. 978) использует escape-последовательности дат:

# p. 977: one folder per value of the header topic
httpagent.sinks.hdfs-sink.hdfs.path = /tmp/flume/http/%{topic}

# p. 978: one folder per hour, read from the sink's own clock
agent1.sinks.sink1.hdfs.useLocalTimeStamp = true
agent1.sinks.sink1.hdfs.path = /tmp/flume/twitterinterceptor/%Y/%m/%d/%H

Escape-последовательностям времени нужен заголовок timestamp, который HTTP- и spooling-source сами не добавляют; useLocalTimeStamp = true позволяет sink взять вместо него собственные часы. Папка на каждый час — это та самая раскладка «партиция на каталог», которую читает Hive (урок 32).

"They must exist already in HBASE" (p. 979): таблица и семейство столбцов — должны; квалификатор pCol появляется с первой записью, как столбцы в HBase (урок 32).

Те же события можно отправить и в HBase (p. 979):

# p. 979: each event into the column test:pCol of the HBase table test_table
agent1.sinks.hbaseSink.type = org.apache.flume.sink.hbase.AsyncHBaseSink
agent1.sinks.hbaseSink.table = test_table
agent1.sinks.hbaseSink.columnFamily = test
agent1.sinks.hbaseSink.serializer = org.apache.flume.sink.hbase.SimpleAsyncHbaseEventSerializer
agent1.sinks.hbaseSink.serializer.payloadColumn = pCol

Несколько каналов, selectors и interceptors

Source может "replicate or multiplex data across many channels", каждый из которых опустошает свой sink (p. 950). Слайд (p. 980) подключает один HTTP source к двум каналам — ch1 в HDFS sink, ch2 в logger sink:

# p. 980: one source, two channels, two sinks
httpagent.sources = http-source
httpagent.sinks = hdfs-sink log-sink
httpagent.channels = ch1 ch2

httpagent.sources.http-source.channels = ch1 ch2
httpagent.sinks.hdfs-sink.channel = ch1
httpagent.sinks.log-sink.channel = ch2

Какое событие куда идёт, решает channel selector этого source (p. 981): "Replicating • Default • Every event sent everywhere" или "Multiplexing • routes events to channels based on their headers". Следующий слайд (p. 982) добавляет четыре строки — "If show = 1, route to ch1", если show = 2 — в ch2. Selector принадлежит source: маршрутизация происходит до каналов.

# p. 982: route by the header show (without these lines: replicating)
httpagent.sources.http-source.selector.type = multiplexing
httpagent.sources.http-source.selector.header = show
httpagent.sources.http-source.selector.mapping.1 = ch1
httpagent.sources.http-source.selector.mapping.2 = ch2
Руководство пользователя Flume не знает у этого класса свойства keywords: он берёт выборку из 1 % всех твитов и отправляет их дальше как события Avro.

Социальные сети — ещё один source (p. 983): Twitter source принимает четыре учётных данных аккаунта разработчика Twitter, которые на слайде замазаны, и список ключевых слов. Слайды (pp. 985 и 978) завершают его конвейер: оставить твиты о выборах и разложить их по одной папке HDFS на каждый час.

# p. 983: tweets as events (the slide masks the credentials as **)
agent1.sources.source1.type = org.apache.flume.source.twitter.TwitterSource
agent1.sources.source1.consumerKey = **
agent1.sources.source1.consumerSecret = **
agent1.sources.source1.accessToken = **
agent1.sources.source1.accessTokenSecret = **
agent1.sources.source1.keywords = @realDonaldTrump, @HillaryClinton

Наконец, interceptor "can process events based on their contents or headers": "Simple data processing", "Overhead for Flume", "To be used with caution!" (p. 984). Он работает внутри source на каждом событии, так что медленный interceptor замедляет приём. Слайд (p. 985) оставляет только события, тело которых совпадает с регулярным выражением; excludeEvents = true наоборот отбрасывало бы их.

# p. 985, with the registration line it needs: keep only events whose body contains "election"
agent1.sources.source1.interceptors = regexInterceptor
agent1.sources.source1.interceptors.regexInterceptor.type = regex_filter
agent1.sources.source1.interceptors.regexInterceptor.regex = .*election.*
agent1.sources.source1.interceptors.regexInterceptor.excludeEvents = false

«Трёх строк interceptor со слайда достаточно, чтобы фильтр заработал». Не сами по себе: interceptor работает, только когда его имя перечислено на source, как в первой строке выше (a1.sources.r1.interceptors = i1 i2 в руководстве пользователя Flume). Без этой строки ничего не фильтруется.

Теперь собирай потоки и прогоняй через них нагрузку. Виджет делает видимой одну мысль: channel поглощает разницу между тем, что приходит, и тем, что может уйти, а когда он полон, отказ уходит вверх по течению, — поэтому его ёмкость должна покрывать худшую скорость поступления за худший простой.

Конструктор агента Flume: собери поток и ударь по нему

Выбери поток: один агент, как на слайде (p. 975), один агент с двумя каналами и двумя sinks, как на слайде (p. 980), или четыре клиентских агента, сходящихся к агрегатору. Четыре веб-сервера отправляют по 100 событий в секунду каждый; между t = 10 s и t = 30 s приходит всплеск нагрузки, простой HDFS или и то и другое. Каналы — это ряды ячеек, которые заполняются. Файл свойств после показаний генерируется из выбранного тобой потока. Скорости (100, 300 и 600 событий в секунду) и 20 000 событий file channel — круглые числа виджета (настоящий file channel по умолчанию вмещает миллион); 1 000 у memory channel — значение со слайда (p. 975).

  1. Один агент, memory channel, HDFS лежит, всплеск × 1. Прежде чем нажать «Пуск, 90 s»: приходит 400 событий в секунду, а уйти не может ни одно. Когда заполнится канал на 1 000 и сколько событий будет отвергнуто к t = 30 s? Потом повтори с file channel.
    Что должно получиться

    Полон примерно через 2.5 s после начала простоя (1 000 / 400); дальше source отвергает всё: около 7 000 событий к t = 30 s. Правило со слайда (p. 963) требует 400 × 20 = 8 000 событий, как говорит последнее показание. File channel принимает их все: его пик — около 8 000 при t = 30 s, потом он опустошается со скоростью 600 − 400 = 200 в секунду и снова пуст примерно к t = 70 s.

  2. Сходящийся поток, memory channels, HDFS лежит, всплеск × 1. Предскажи, какой канал заполнится первым и когда веб-серверам начнут отказывать.
    Что должно получиться

    Канал агрегатора, к t = 13 s. Его source затем отвергает батчи клиентов (пунктирные стрелки), и каждый клиентский канал растёт на 100 событий в секунду: полон к t = 23 s. Только тогда отказывают веб-серверам — около 3 000 событий к t = 30 s против 7 000 с одним агентом. Каждый узел буферизует, и обратное давление идёт вверх по течению по одному уровню за раз.

  3. Сходящийся поток, HDFS работает (выключи простой), всплеск × 3. Где поглощается всплеск — с memory channels, а потом с file channels?
    Что должно получиться

    Каждый клиент получает 300 событий в секунду и может отправить 300, так что уровень 1 пропускает всплеск дальше. Агрегатор получает 1 200, а пишет в HDFS только 600: с memory channels он полон к t = 12 s, клиенты — к t = 19 s, и отвергнуто около 7 000 событий. С file channels агрегатор поглощает (1 200 − 600) × 20 = 12 000 событий и рассасывает их за следующие 60 s: "Transient variations in flow are absorbed and ironed out by channels" (p. 959).

  4. Два канала, memory, HDFS лежит. С replicating selector продолжает ли logger печатать во время простоя? Переключись на multiplexing и сравни; прочитай строки selector в файле. Наконец, нажми «Сбой и перезапуск» во время простоя, пока в каналах есть события, — один раз с memory, другой раз с file channels.
    Что должно получиться

    Replicating кладёт каждое событие в оба канала, поэтому, как только ch1 полон (t = 13 s), source отвергает всё, и logger тоже голодает. С multiplexing отвергается только половина с show = 1 (около 3 000 событий), а show = 2 продолжает доходить до logger; в файле появляются четыре строки selector со слайда (p. 982). Сбой опустошает memory channel — события потеряны, хотя веб-серверам сказали, что они доставлены, — а file channel после перезапуска находит их на диске.

Слайд (p. 986) подводит итог Flume: она "is suitable for large volume data collection, especially when data is being produced in multiple locations"; "Once planned and sized appropriately, Flume will practically run itself"; она даёт слабую гарантию порядка, транзакционный обмен между агентами и "rich out-of-the box features such as contextual routing".

Sqoop: ночной грузовик

Второй источник из того же вопроса — реляционная база данных. Sqoop (p. 988): "Importing from relational DB sources", "PULL-based (no streams)", "Bulk imports", "With one command line action, import data from RDBMS to HDFS/Hive", с коннекторами для MySQL, Oracle, SQL Server, PostgreSQL. Сценарии использования (p. 989): "Occasional copy for running map-reduce tasks" и "Keep RDBMS for transactional needs and periodically dump data on HDFS" — транзакции остаются в базе данных, анализ переезжает в Hadoop. Flume — труба, которая никогда не закрывается; Sqoop — грузовик, который едет, когда его вызвали.

# p. 990: copy the table tradingDays of the MySQL database nseProd into HDFS, one mapper
sqoop import \
--connect jdbc:mysql://localhost:3306/nseProd \
--username=qt \
--password=password \
--table=tradingDays \
--target-dir /mysql/nseProd \
--m 1
Руководство пользователя Sqoop пишет -m 1 или --num-mappers 1; слайды пишут --m 1.

Читай: инструмент (import), JDBC-адрес базы nseProd на локальном MySQL, учётные данные, таблица, каталог HDFS, который надо создать, число мапперов. За этой командой Sqoop запускает задание MapReduce только с map-задачами: каждый маппер читает свою долю таблицы собственным SELECT и пишет собственный файл (part-m-00000, …) в целевой каталог.

Как делятся строки

Доли — это диапазоны одного столбца, по умолчанию первичного ключа: Sqoop спрашивает у базы его наименьшее и наибольшее значение и режет этот интервал на столько диапазонов равной ширины, сколько мапперов (рис. 7). --split-by называет другой столбец — "explicitly specify the column to use for splitting rows between mappers" (p. 992), — когда первичного ключа нет или он делит плохо. Равная ширина — не равное число строк: ключ с большими дырами оставляет часть мапперов без работы.

"Sqoop uses the primary key to decide how many mappers to use, and for splitting the rows among mappers" · "--m 1 fixes 1 mapper / mandatory if the table you are importing doesn’t have a primary key, or if you are importing a query"

Число мапперов задаёт -m (--num-mappers), и по умолчанию их четыре; первичный ключ решает только то, как строки делятся между ними. Один маппер нужен, когда у таблицы нет первичного ключа и не задан столбец --split-by. Импорт по запросу тоже может идти параллельно — с --split-by.

Руководство пользователя Sqoop: «по умолчанию используются четыре задачи»; без первичного ключа и без --split-by «импорт упадёт, если число мапперов явно не задано равным единице»; запрос в свободной форме либо выполняется параллельно, и тогда «нужно также выбрать столбец разбиения через --split-by», либо «импортируется последовательно, с одной map-задачей через -m 1». Экзамен может напечатать фразу со слайда: знай, что в ней сказано и что Sqoop делает на самом деле.

Вместо целой таблицы — запрос (p. 993): "Instead of full table", "$CONDITIONS mandatory". Одна эта опция — ещё не команда: полной команде нужны целевой каталог и либо один маппер, либо столбец разбиения:

# p. 993, completed: three columns of the 2016 rows, four mappers split on month
sqoop import \
--connect jdbc:mysql://localhost:3306/nseProd \
--username=qt \
--password=password \
--query 'select year, month, day from tradingDays where year=2016 and $CONDITIONS' \
--split-by month \
--target-dir /mysql/tradingDays2016 \
-m 4

Sqoop заменяет токен $CONDITIONS в копии запроса каждого маппера диапазоном month этого маппера. Это не переменная shell: одинарные кавычки не подпускают к нему shell.

В Hive, и только новое

Ещё две опции превращают импорт в таблицу Hive (p. 994). Целевой каталог здесь новый: как и любое задание MapReduce, Sqoop отказывается писать в уже существующий выходной каталог, а /mysql/nseProd занят первым импортом.

# p. 994: the same table, registered in Hive as tradingDays
sqoop import \
--connect jdbc:mysql://localhost:3306/nseProd \
--username=qt \
--password=password \
--table=tradingDays \
--hive-import \
--hive-table=tradingDays \
--target-dir /mysql/table/tradingDays2 \
--m 1

"Sqoop will create an external table and point the table to the directory in HDFS"

По умолчанию --hive-import создаёт обычную (managed) таблицу Hive и перемещает импортированные файлы в каталог хранилища Hive; в целевом каталоге ничего не остаётся, а удаление таблицы стирает данные.

Руководство пользователя Sqoop: «Sqoop сгенерирует скрипт Hive, содержащий операцию CREATE TABLE, которая определяет твои столбцы в типах Hive, и оператор LOAD DATA INPATH, перемещающий файлы данных в каталог хранилища Hive». Storm, Flume и Sqoop не входят в практические темы по правилам экзамена, и ни в одном прошлом варианте нет упражнения на них: они относятся к теоретической части. A Storm topology counts the occurrences of each word in a stream of sentences. A bolt splits the sentences and emits one tuple per word to a counting bolt with several tasks, each keeping a counter per word. Which stream grouping lets the counting tasks share the work while the count of each word stays exact in a single task?

  • Shuffle grouping Работу она делит, но кортежи одного слова попадают в случайные задачи: каждая задача хранит частичный счёт, и итога не хранит ни одна.
  • All grouping Каждая задача получает каждый кортеж и считает всё: счётчики точные, но вычисляются в каждой задаче, так что работа не делится.
  • Fields grouping on the field "word" Задача выбирается по хешу слова ("consistent hashing on a subset of tuple fields", p. 933): одно и то же слово всегда попадает в одну и ту же задачу, а разные слова расходятся по задачам.
  • Global grouping Все кортежи идут в задачу с наименьшим id: счётчики точные, но всю работу делает одна задача.
Показать образец ответа

Fields grouping on "word". The tuple is routed by a hash of the chosen field, so all tuples with the same word reach the same task, which therefore holds the exact count for that word, while different words are spread over the tasks. Shuffle grouping would split each word's count over several tasks; all grouping would make every task count everything; global grouping would send everything to one task.

Суть вопроса — связь группировки и состояния: bolt, который хранит состояние по ключу, должен получать кортежи этого ключа в одном месте. Каждый неверный вариант прав в чём-то другом — shuffle для bolts без состояния, all для рассылки всем, global для одного итога, — поэтому они и соблазнительны.

Describe the main concepts of Apache Storm — stream, spout, bolt, topology — and the components of a Storm cluster. In what does a Storm topology differ from a MapReduce job?

Показать образец ответа

Storm is a distributed system for realtime computation, developed at BackType, which Twitter acquired. A stream is an unbounded sequence of tuples, a tuple being a named list of values. A spout is a source of streams: it reads data from an external source and emits tuples. A bolt processes one or more input streams and produces new streams; it can implement filters, aggregations, joins or any function. A topology is a network of spouts and bolts — a directed graph — and every component runs as many tasks across the cluster; a stream grouping (shuffle, fields, all, global) decides which task receives each tuple. The cluster has a master node, Nimbus, similar to Hadoop's JobTracker, which distributes the code, assigns tasks to machines and monitors failures; a ZooKeeper cluster used for coordination, which keeps the cluster state; and Supervisors on the worker machines, which run the worker processes. A MapReduce job reads a bounded input and finishes; a topology processes an unbounded stream with low latency and runs until it is killed.

Полный ответ — это четыре определения, три компонента и одно отличие «заканчивается / никогда не заканчивается». Если есть место, добавь, зачем ZooKeeper стоит между Nimbus и Supervisors: собственного состояния они не хранят, так что любой можно перезапустить, а топологии продолжают работать, пока Nimbus лежит (туториал Storm).

Explain how Apache Flume moves events from a source to a sink within an agent, and from one agent to the next, without losing them. What does this mechanism not guarantee?

Показать образец ответа

A Flume agent hosts a source, a channel and a sink. The source accepts incoming data, turns it into events (headers with metadata, used for routing, and a body with the content) and writes them into the channel inside a transaction, which commits only when the channel has accepted the whole batch. The sink polls the channel and removes a batch inside its own transaction, and commits only after a successful transfer — when the destination, such as HDFS, has written it, or when the source of the next agent has committed it into its own channel. On any failure the transaction rolls back and the events stay in the channel to be retried. An event therefore leaves a channel only when the next hop holds it, and no event is lost in transit between agents. Not guaranteed: durability with a memory channel, which is not persistent — its events are lost if the agent process dies, so only a file (disk) channel survives a restart; exactly-once delivery, since a batch retried after a failed commit can arrive twice; and strict ordering, since Flume gives only a weak ordering guarantee: events arrive in the order received in the absence of failures.

Слайды печатают "This ensures no data loss" (p. 949): повтори это, а потом добавь условия — красную ручку этого урока. Вопрос просит обе половины: сначала механизм, потом три ограничения.

True or false: Apache Flume guarantees that events always reach the destination in the order in which the source received them.

  • True Только "in the absence of failures": итоговый слайд о Flume называет это "weak ordering guarantee". Если агент умирает и его веб-серверы переключаются на второй агент (p. 955), события из file channel первого агента приходят после более новых.
  • False Слайд (p. 986): "Flume provides weak ordering guarantee, i.e., in the absence of failures the data will arrive in the order it was received". Именно «Always» делает утверждение ложным.
Показать образец ответа

False. Flume provides only a weak ordering guarantee: in the absence of failures, events arrive in the order in which they were received. After a failure — for example an agent that dies and whose producers fail over to another agent — events can arrive out of order.

Ищи абсолютное слово: гарантия со слайда действует только без сбоев. "flow ordering*" со слайда (p. 951) несёт то же ограничение в своей звёздочке.

Проверь себя

Count bolt с 3 задачами получает слова через shuffle grouping. Что через некоторое время хранит задача 0 для слова "fresh"?

  • Точное число появлений "fresh" в потоке Только fields (или global) grouping привела бы каждый "fresh" в одну задачу; здесь часть из них получили задачи 1 и 2.
  • Ничего, поскольку shuffle grouping отправляет всё в задачу с наименьшим id Это global grouping.
  • Часть счёта; остальное разбросано по задачам 1 и 2 Shuffle выбирает случайную задачу для каждого кортежа, так что каждая задача хранит частичный счёт — виджет показал 6 + 1 + 1.
  • Утроенный истинный счёт, по копии на задачу Копии в каждую задачу — это all grouping, и даже тогда каждая задача хранит истинный счёт один раз, а не три.

Ты поднимаешь подсчёт слов с 1 до 4 задач на каждый bolt и оставляешь группировки: shuffle в split bolt, fields по "word" в count bolt. Какие утверждения верны? Отметь всё подходящее.

  • Split bolt по-прежнему работает: чтобы разбить предложение, не нужно помнить другие предложения Bolt без состояния может принять любой кортеж в любой задаче — поэтому там shuffle grouping и годится.
  • Счётчики теперь разбросаны по 4 задачам, так что нужна итоговая сумма по задачам Не с fields grouping: каждое слово считается только в одной задаче.
  • Global grouping на count bolt подошла бы ничуть не хуже Счётчики были бы точными, но всю работу делала бы одна задача, а остальные три простаивали бы.
  • Каждое слово по-прежнему считает ровно одна задача подсчёта Fields grouping хеширует слово, так что одно и то же слово всегда попадает в одну и ту же задачу, каким бы ни было число задач.

Группировка следует за состоянием: шагам без состояния — shuffle, состоянию по ключу — fields.

Главное

  • Батч-инструменты читают входы, которые закончились; поток — это неограниченная последовательность кортежей, к которой запросы идут непрерывно, по окнам. Storm вычисляет на потоках с помощью топологий — графов из spouts (источников потоков) и bolts (обработки), которые работают, пока их не убьют, — на кластере, где Nimbus распределяет, Supervisors выполняют, а ZooKeeper координирует.
  • Каждый компонент выполняется как множество задач; stream grouping каждого ребра решает, какая задача получит кортеж: shuffle (случайная), fields (одинаковые значения — одна задача; нужна для состояния по ключу, например подсчёта слов), all (копия каждой задаче), global (задача с наименьшим id). "No data loss" у Storm — это at-least-once.
  • Агент Flume — это source → channel → sink: source принимает данные и проталкивает события (headers + body) в channel, который хранит их в порядке поступления; sink опрашивает, забирает и доставляет. Source может питать много каналов; sink читает один.
  • Транзакции по обе стороны канала, где sink коммитит только после доставки, предотвращают потери в пути — с надёжным (file) channel, at-least-once и со слабой гарантией порядка. Memory channel быстрый, но при сбое теряет свои события.
  • Сходящиеся потоки рассчитывают по трём правилам: от 4 до 16 клиентских агентов на агрегатор; размер батча на выходе = выходной объём уровня / число агентов на уровне; ёмкость канала = худшая скорость поступления × худший простой. Файл свойств объявляет имена, подключает sources к каналам, а sinks — каждый к одному каналу, и задаёт типы: HDFS sink с путём, префиксами и типом файла, bucketing по заголовку или времени, replicating или multiplexing selectors, interceptors.
  • Sqoop забирает таблицы или результаты запросов целиком через JDBC, как задание MapReduce только с map: -m мапперов на диапазонах первичного ключа или --split-by; $CONDITIONS в --query; --hive-import в managed-таблицу Hive; сохранённые инкрементальные задания с check column и последним значением.

Spout · bolt (pp. 928–929)
источник потоков · обрабатывает входные потоки и порождает новые (фильтры, агрегация, join)
Topology (p. 930)
сеть из spouts и bolts; работает, пока не убьют; компоненты выполняются как множество задач (p. 931)
Кластер Storm (p. 925)
Nimbus: master node, аналог JobTracker · ZooKeeper: координация кластера, хранит состояние · Supervisors: запускают worker processes
Stream grouping (p. 933)
shuffle: случайная задача · fields: хеш полей, одинаковые значения → одна задача · all: каждая задача · global: задача с наименьшим id
Гарантия Storm
"no data loss" = at-least-once: кортежи проигрываются заново, дубликаты возможны
Flume
"a continuous data ingestion system" (p. 939), родилась для агрегации логов в Cloudera

Event (p. 947)
header: метаданные, для маршрутизации · body: само содержимое
Push · poll (p. 946)
source pushes events · sink polls for events

source–channel many-to-many · channel–sink one-to-many: sink читает один channel
Channels (p. 968)
memory: очередь в памяти, быстрая, не персистентная, ограниченная ёмкость · Disk = file channel (type = file): надёжный

один агрегирующий агент на 4–16 клиентских агентов

hdfs.path = /tmp/flume/http/%{topic} · …/%Y/%m/%d/%H с hdfs.useLocalTimeStamp = true
Selectors (pp. 981–982)
replicating: по умолчанию, каждое событие в каждый канал · selector.type = multiplexing, selector.header = show, selector.mapping.1 = ch1

sources.source1.interceptors = regexInterceptor, затем ….regexInterceptor.type = regex_filter, regex = .*election.*, excludeEvents = false
Sqoop (p. 988)
импорт из реляционных БД; pull-based, без потоков; целиком; одна команда
Импорт (p. 990)

Мапперы и разбиение
-m мапперов (по умолчанию 4); диапазоны первичного ключа или --split-by col; -m 1, когда нет ни ключа, ни столбца разбиения
Импорт по запросу (p. 993)
--query '… where … and $CONDITIONS' с --target-dir и --split-by или -m 1
Hive (p. 994)
--hive-import --hive-table=tradingDays: managed-таблица, файлы перемещаются в хранилище
Инкрементальное задание (pp. 995–999)
sqoop job --create myjob -- import … --append --incremental lastmodified --check-column ts · sqoop job --exec myjob; следующий запуск берёт данные > LastValue; --append позволяет каждому запуску писать в уже существующий целевой каталог
