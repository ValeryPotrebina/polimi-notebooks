Данные из веба: API и scraping

После этого урока ты сможешь разобрать вызов веб-API по частям — метод, хост, путь, параметры — вместе с JSON, который он возвращает, и для любого сайта решить: можно ли спросить API, достаточно ли просто скачать и распарсить страницу или придётся управлять настоящим браузером, — а также сказать, что из BeautifulSoup, Scrapy и Selenium делает что.

На занятии по API показывают вот такой запрос к сервису ViaggiaTreno компании Trenitalia (p. 1517):

http://www.viaggiatreno.it/infomobilita/resteasy/viaggiatreno/partenze/S00219/Wed%20Nov%2005%202025%2020:43:00%20GMT+0100%20(Central%20European%20Standard%20Time)

В ответ пришла не веб-страница, а список из двенадцати отправлений, и каждое — запись с именованными полями. Теперь посмотри на хвост URL. В раскодированном виде там написано "Wed Nov 05 2025 20:43:00 GMT+0100 (Central European Standard Time)". Никто не вводит дату так в адресную строку: день недели, секунды, сдвиг от Гринвича, часовой пояс словами в скобках и %20 вместо каждого пробела.

Так кто же написал этот URL? Ответ заодно объясняет, почему скрипт, скачавший веб-страницу, иногда не находит ничего на странице, которую твой браузер показывает полной данных. Держи вопрос в голове — ответ будет в конце урока.

API — это окошко, где программы просят данные

Конспект курса называет сбор данных (data ingestion) "the first and fundamental step of any Data Analysis Pipeline" (§5.1.1) — это нижний слой архитектуры из урока 4, и именно этот шаг в большинстве курсов делает за тебя готовый датасет. Из веба есть два пути: спросить API или соскрапить страницу.

Представь окошко выдачи еды навынос: туда уходит бланк с фиксированными полями, оттуда выходит подписанная коробка, а кухню ты так и не видишь. Первый слайд определяет такое окошко для программ (p. 1510):

Application Programming Interface (API) — "a set of rules and protocols that allows different software applications to communicate with each other and exchange data. Often can be called remotely." "APIs act as an intermediary layer, enabling developers to use existing functions and services from other applications, which simplifies development." (Набор правил и протоколов, через которые программы общаются и обмениваются данными; API — промежуточный слой, позволяющий пользоваться чужими функциями и сервисами.)

Определение общее: функции Python-библиотеки — тоже API. Слово "remotely" сужает его до веб-API (web API), который вызывают по сети через HTTP; в конспекте курса: "A Web API is a API which is based on the HTTP protocol, and it's usually used to give programmatic access to data and platforms" (§5.1.2). Заголовок первых двух слайдов, "API without Libraries", на них не объясняется; понимай его как вызов API напрямую — URL в браузере, в Postman или через curl, — а не через клиентскую библиотеку, которая оборачивает эти вызовы.

Каждый вызов указывает HTTP-метод (HTTP method) и URL: "APIs can be invoked through HTTP methods (e.g., GET, POST, etc.) depending on the kind of operations to be performed", и "As an end-user, the most used requests for APIs are GET requests" (p. 1511). GET читает, а тот, кто собирает данные, в основном читает; к тому же такой запрос помещается в один URL — поэтому каждый пример занятия можно просто вставить в браузер.

Для разработки и тестирования API "Postman is one of the most renowned ones" (p. 1511). Следующий слайд — его скриншот с четырьмя выносками, перерисованный на рис. 1.

На слайде выноска "Query" накрывает всю строку запроса. Строго говоря, query string — это только часть после вопросительного знака.

Читай четыре части в том порядке, в каком ими пользуешься. API Collection хранит сохранённые запросы; в "API 101" на каждую операцию с клиентами свой HTTP-метод — GET, чтобы прочитать всех или одного, POST, чтобы добавить, PUT, чтобы обновить, DEL (DELETE), чтобы удалить. Выноска Query указывает на строку запроса: метод и URL. Request Parameters перечисляет пары key=value после ?. В Result — статус 200 OK, время, размер и тело в JSON; а раз сервер — эхо, тело показывает, что на самом деле ушло: твои параметры как args плюс headers, которые клиент добавил сам.

Почему на каждую операцию свой метод? Соглашение REST, стоящее за "API 101" (из конспекта, не со слайдов)

Большинство веб-API следуют парадигме REST: она даёт URL предсказуемую форму, METHOD http://domain/collection/item — например, GET http://example.com/user/1234, — и фиксирует, что делает каждый метод над коллекцией или над одним элементом (конспект курса, §5.1.2):

Имена в "API 101" читаются по этой таблице: "Get all customers" — это GET над коллекцией, "Get one customer" — GET над элементом, "Add new customer" — POST над коллекцией (на скриншоте видны имена, а не URL).

Веб-API отвечает на метод и URL данными для программ — обычно JSON, — а не страницей для людей.

Читаем запрос: примеры с iTunes Store

Первый разобранный пример занятия просит у Apple iTunes Store "Retrieve the first 10 artists whose name contains "maroon"" (p. 1513). Ни приложения, ни логина: весь вопрос — один URL.

GET https://itunes.apple.com/search?term=maroon&entity=allArtist&attribute=allArtistTerm&limit=10

Читай его слева направо: https — это схема (scheme), то есть протокол; itunes.apple.com — хост (host), сервер, который отвечает; /search — путь (path), сервис, который ты вызываешь. После ? идёт строка запроса (query string): пары key=value, разделённые &, и каждая — инструкция для поиска. Конспект курса приводит общую форму (§5.1.2); части в скобках необязательны:

URL format (RFC 2396):
scheme:[//[user:password@]host[:port]][/]path[?query][#fragment]
Справка из документации Apple: limit по умолчанию равен 50, максимум — 200.

Ответ — не страница, а JSON-документ: объект с resultCount и results, массивом объектов-артистов. Его начало (p. 1513):

{
  "resultCount": 10,
  "results": [
    {
      "wrapperType": "artist",
      "artistType": "Artist",
      "artistName": "Maroon 5",
      "artistLinkUrl": "https://music.apple.com/us/artist/maroon-5/1798556?uo=4",
      "artistId": 1798556,
      "amgArtistId": 529962,
      "primaryGenreName": "Rock",
      "primaryGenreId": 21
    },
    … nine more artist objects ("Maroon" is the second)
  ]
}

resultCount равен 10, потому что limit=10 разрешил не больше десяти; каждый элемент results — запись с именованными полями. Эту структуру API даёт тебе даром, а скрапингу приходится восстанавливать её из вёрстки страницы.

Второй вызов, "Retrieve all the artist whose surname is "Stallone"" (p. 1514), — это GET https://itunes.apple.com/search?term=Stallone&entity=movieArtist: ни attribute, ни limit. В ответе "resultCount": 6, и у первых двух записей разный набор полей:

"artistType": "Artist",
"artistName": "Frank Stallone",
"artistLinkUrl": "https://music.apple.com/…",
"artistId": 91734703,
"amgArtistId": 5513,
"primaryGenreName": "Pop",
"primaryGenreId": 14
"artistType": "Movie Artist",
"artistName": "Sylvester Stallone",
"artistLinkUrl": "https://itunes.apple.com/…",
"artistId": 186052826,
"primaryGenreName": "Drama",
"primaryGenreId": 4406

У Frank Stallone есть amgArtistId и ссылка на music.apple.com; у Sylvester Stallone amgArtistId нет, а ссылка ведёт на itunes.apple.com. Записи одного ответа не обязаны иметь одинаковые поля — та же свобода, которую документное хранилище даёт документам одной коллекции (урок 13), — поэтому программа должна проверить, что поле есть, прежде чем его использовать.

«URL фильтрует артистов по фамилии». Нет: ключа «фамилия» здесь нет, term=Stallone — полнотекстовый поиск по именам, а подпись сообщает намерение, а не механизм. Скриншот показывает и больше: хотя вызов просит entity=movieArtist, его первый результат, Frank Stallone, — это "Artist" с жанром Pop. Вероятная причина (на слайде её нет): документация Apple относит movieArtist к медиатипу movie, а этот вызов ключ media не задаёт. Читай ответ, а не подпись.

В URL не может быть пробела, а &, ? и # он читает как разделители. Внутри значения такие символы записывают через percent-кодирование (percent-encoding): % плюс код символа двумя шестнадцатеричными цифрами, так что пробел — это %20, а & — %26. Иначе сервер прочитал бы & внутри значения как начало новой пары. В URL из разминки девять %20.

В Python (справка) requests собирает и кодирует строку запроса из словаря — так же, как Postman из своей таблицы:

# the request of p. 1513, in Python
import requests

url = "https://itunes.apple.com/search"
params = {"term": "maroon",
          "entity": "allArtist",
          "attribute": "allArtistTerm",
          "limit": 10}
r = requests.get(url, params=params)
data = r.json()       # a dict
data["resultCount"]   # 10

Анатомия запроса

Два вызова iTunes со слайдов и ещё один, которого на слайдах нет, разобраны так, как их показал бы Postman. Выбери вызов, двигай limit (0 значит, что ключ не отправляется) и включай-выключай percent-кодирование: URL, пары, которые читает сервер, и ответ обновляются, будто ты нажал Send. Виджет работает офлайн. Записи, напечатанные на слайдах, показаны целиком; остальные помечены «не напечатано», а у каждого числа сказано, печатает ли его слайд или его посчитал виджет.

  1. Главная мысль: URL — это весь вопрос целиком; каждая пара key=value после ? — одна инструкция, которую читает сервер. Начни с вызова со слайда (p. 1513). Предскажи: при limit = 3 чему равен resultCount и сколько объектов в results? Потом двигай слайдер.
    Что должно получиться

    resultCount становится 3, а в results три объекта: Maroon 5, Maroon и одна запись, которую слайд не печатает. Больше в URL ничего не менялось, поэтому ответ изменился только там, где изменилась инструкция: limit ограничивает, сколько результатов придёт.

  2. Выбери вызов со слайда (p. 1514). Он приходит без limit, как на слайде, и resultCount равен 6. Предскажи resultCount при limit = 8, потом проверь. Заодно сравни первые две записи.
    Что должно получиться

    По-прежнему 6, как считает виджет: без limit вызов и так вернул только шесть артистов, хотя по умолчанию Apple разрешает 50, — значит, больше возвращать нечего. limit — это максимум, а не обещание. Записи различаются: у Frank Stallone есть amgArtistId, у Sylvester Stallone его нет (виджет помечает отсутствующее поле), а Frank — музыкальный "Artist", хотя вызов просит артистов кино.

  3. Выбери третий вызов, с term Simon & Garfunkel. Прежде чем выключить percent-кодирование, предскажи, сколько пар прочитает сервер и что он примет за значение term.
    Что должно получиться

    С кодированием значение уходит как Simon%20%26%20Garfunkel, и сервер читает его целиком: две пары (три — с limit). Без кодирования голый & разрезает значение: сервер читает term = "Simon " (с пробелом на конце), а затем пару с ключом " Garfunkel" и пустым значением. Один незакодированный символ превратил одну инструкцию в две неправильные.

Параметры в пути, дни в миллисекундах: ViaggiaTreno

Сервис ViaggiaTreno компании Trenitalia устроен иначе: его параметры едут внутри пути, по одному на сегмент, и нужно два вызова — первый возвращает ключ, который нужен второму. Сначала автодополнение номера поезда 798 (p. 1515):

GET http://www.viaggiatreno.it/infomobilita/resteasy/viaggiatreno/cercaNumeroTrenoTrenoAutocomplete/798

798 - SALERNO - 04/11/25|798-S09818-1762210800000
798 - SALERNO - 05/11/25|798-S09818-1762297200000

Две строки обычного текста, по одной на каждый рейс поезда 798: тот, что отправляется 4 ноября, и тот, что отправляется 5 ноября. Слева от | — подпись для людей; справа — ключ для программ: номер поезда, код станции (S09818 — это SALERNO, как написано в строке) и день отправления через дефисы. Второй вызов кладёт части ключа в путь (p. 1516; его ответ здесь урезан до нескольких полей):

GET http://www.viaggiatreno.it/infomobilita/resteasy/viaggiatreno/andamentoTreno/S09818/798/1762210800000

{tipoTreno: "PG", orientamento: null, codiceCliente: 4, fermateSoppresse: [], …}
  arrivato: true
  categoria: "ICN"
  circolante: true
  compClassRitardoLine: "regolare_line"
  compDurata: "14:35"
  compImgCambiNumerazione: "&nbsp;&nbsp;"
  compImgRitardo: "/vt_static/img/legenda/icone_legenda/regolare.png"
  …

Второй ответ — это состояние поезда с итальянскими ключами: categoria: "ICN", compDurata: "14:35" (продолжительность), arrivato: true. Ключи comp несут куски самого сайта — имена CSS-классов вроде "regolare_line", пути к картинкам, HTML-сущность &nbsp;, — то есть полную противоположность "Separation between model and presentation" (разделения модели и представления), которое конспект курса называет первым преимуществом веб-API (§5.1.2).

Что значит 1762210800000

День — это число: epoch time (время Unix) в миллисекундах, то есть число миллисекунд с 1 января 1970 года, 00:00:00 UTC, — обычный способ, которым компьютеры хранят момент времени. Шаги ниже проверяют, что 1762210800000 — это полночь 4 ноября 2025 года по итальянскому времени.

  1. Фиксируем момент: в ноябре Италия живёт по CET, UTC + 1, так что местная полночь 4 ноября — это 23:00 UTC 3 ноября.

  2. Полные годы 1970–2024: 55 лет по 365 дней плюс по одному дню за каждый из 14 високосных годов 1972 … 2024.

    \[ 55 \times 365 + 14 = 20\,089 \text{ days} \]

  3. В 2025 году январь–октябрь дают 304 дня; 1 и 2 ноября — итого 306.

    \[ 20\,089 + 306 = 20\,395 \text{ days} \]

  4. В сутках \(24 \times 3600 = 86\,400\) с; переводим, потом добавляем 23 часа 3 ноября.

    \[ 20\,395 \times 86\,400 = 1\,762\,128\,000 \] \[ +\ 82\,800 = 1\,762\,210\,800 \text{ s} \]

  5. API считает миллисекунды: умножь на 1000 — и получишь ключ со слайда (p. 1515), цифра в цифру.

    \[ 1\,762\,210\,800\,000 \text{ ms} \]

  6. Днём позже — на 86 400 000 ms больше: это второй ключ со слайда (p. 1515).

    \[ 1\,762\,297\,200\,000 \text{ ms} \]

«Поезд отправляется в 1762210800000». В подписи к слайду (p. 1516) стоит "at", будто число — это время. На самом деле это день, названный по его первой миллисекунде: рейс поезда определяется номером поезда, станцией отправления и днём отправления — тремя частями ключа.

Третий вызов запрашивает все отправления со станции в заданный момент (p. 1517) — это и есть длинная дата из разминки. В раскодированном виде URL читается так:

http://www.viaggiatreno.it/infomobilita/resteasy/viaggiatreno/partenze/S00219/Wed Nov 05 2025 20:43:00 GMT+0100 (Central European Standard Time)

Ответ — JSON-массив из двенадцати отправлений. У элемента 0, compNumeroTreno: "REG 3143", есть codOrigine: "S00219" и рядом друг с другом dataPartenzaTrenoAsDate: "2025-11-05" и dataPartenzaTreno: 1762297200000 — один и тот же день для людей и для программ, и это то самое число, которое автодополнение дало для 5 ноября.

"Search for trains departing from station «S09818» on «Wed Nov …»"

Вызов ищет отправления со станции S00219, а не S09818: код станции — это сегмент пути после partenze/, а в URL под подписью написано …/partenze/S00219/….

Слайд везде согласован сам с собой, кроме подписи: у первого отправления в ответе codOrigine: "S00219", а S09818 — это SALERNO, станция отправления поезда 798 (pp. 1515–1516); похоже, подпись сохранила станцию с предыдущего слайда. Читай запрос по его URL, а не по подписи. Экзамен могут сверять с напечатанной формулировкой, так что знай оба варианта: подпись, как она напечатана, и станцию, которую вызов запрашивает на самом деле.

Поставщики данных и их правила

Ещё три слайда представляют поставщиков данных, доступных через API.

Слайд про Twitter сам помечает этот API как больше не работающий так, как описано. И правда (справка): версия, которую слайд называет v1, была v1.1, а с 2023 года X, как теперь называется Twitter, продаёт доступ к своему API на чтение платными тарифами. На экзамене описывай две версии словами слайда; а остаётся сама идея: API — это контракт, который его владелец может изменить (кто может его вызывать, до каких данных он дотягивается), и каждый пайплайн, построенный на нём, зависит от этого контракта.

Чего нет на слайдах: зачем поставщики дают API, ключи, пагинация, rate limits, коды статуса (справка из конспекта курса и стандартного HTTP)
  • Зачем поставщики дают API. Конспект курса перечисляет преимущества веб-API (§5.1.2): "Separation between model and presentation"; регулируемый доступ к данным (отслеживаемые аккаунты, только часть данных); никакого прямого доступа к сайту платформы; ограничение частоты запросов (throttling); никакой перегрузки сервера; защита от DoS- и DDoS-атак; платный доступ ко всем данным или к большим объёмам.
  • Ключи и токены. "Almost all the APIs require a kind of user authentication": ты регистрируешься на портале разработчика у поставщика, получаешь ключ и секрет и обмениваешь их на токен, который отправляется с каждым запросом, обычно через OAuth (конспект курса, §5.1.2).
  • Пагинация (pagination). "most APIs support data pagination to split huge chunks of data into smaller set of data" (§5.1.2): limit — это одна половина, номер страницы или курсор на следующую порцию — другая.
  • Ограничения частоты (rate limits). Поставщики "put a limit on the number of requests a single account can make" (§5.1.2), поэтому большой краулер распределяет запросы по нескольким аккаунтам по кругу (round robin).
  • Коды статуса (status codes). 200 OK (p. 1512) — успех; из остальных первыми тебе встретятся 401 и 403 (ключа нет или он неверный, доступ запрещён), 404 (не найдено), 429 (слишком много запросов: сработал rate limit) и 5xx (сбой на сервере).

API нет? Скрапь страницу — и познакомься с DOM

API отдаёт тебе записи с именованными полями; веб-страница отдаёт текст в тегах, свёрстанный для человеческих глаз. Когда у сайта нет API, ты берёшь саму страницу. Лекция о скрапинге открывается определением (p. 1523):

Веб-скрапинг (web scraping) — "the automated process of extracting data from websites and organizing it into a structured format, such as a spreadsheet or database. It uses specialized software or scripts, called scrapers, to pull information like text, prices, or images from the HTML code of web pages, which can then be used for analysis."

Слайд отделяет скрапинг от обхода сайтов (web crawling), "which is used by search engines to index web content": краулер переходит со страницы на страницу по ссылкам, скрапер извлекает из них данные, — а Scrapy, о котором ниже, умеет и то и другое.

Что можно скрапить (p. 1527)? "Social networks: Facebook, Instagram, etc.", "Retailers: Amazon, Tripadvisor, Google Maps, etc." и "Any website with valuable contents and no official API (e.g. events, train schedules, etc.)". Последний пункт и есть правило: скрапь, когда API нет; конспект курса называет скрапинг "a last resort" (крайней мерой) (§5.1.3). Расписания поездов в списке есть, но первая лекция добралась до них через API: если API существует, это лучшая дверь.

Страница — это дерево

Что такое страница для программы? Слайды отвечают определением W3C (p. 1524):

Document Object Model (DOM) — "a platform and language-neutral interface that allows programs and scripts to dynamically access and update the content, structure, and style of a document." "In other words it is a standard for how to get, change, add, or delete HTML elements." (Не зависящий от платформы и языка интерфейс, через который программы читают и меняют содержимое, структуру и стиль документа.)

"When a web page is loaded, the browser creates a Document Object Model of the page" (p. 1525), и эта модель определяет "The HTML elements as objects", "The properties of all HTML elements", "The methods to access all HTML elements" и "The events for all HTML elements". Третий слайд о DOM — картинка (p. 1526), перерисованная на рис. 3; вот HTML, который за ней стоит (слайд называет атрибут, но не его значение):

<html>
  <head>
    <title>My title</title>
  </head>
  <body>
    <a href="page2.html">My link</a>
    <h1>My header</h1>
  </body>
</html>

Почему это важно скраперу: парсер вроде BeautifulSoup строит из HTML-текста то же самое дерево; шаблоны, которые выбирают данные со страницы, — это пути в нём; а собственные скрипты страницы могут изменить его после загрузки — "dynamically access and update", тема следующего раздела.

Как указать на узел: три вида шаблонов

Когда страница уже в руках, "Another basic step is parsing the page, extracting data that respects specific patterns" (p. 1530): CSS-селекторы, регулярные выражения и XPath. Все три добираются до ссылки с рис. 3 (справка: слайды называют техники, но не вызовы):

# html holds the page of Fig. 3 as text
import re
from bs4 import BeautifulSoup
from lxml import html as lh

# 1. CSS selector, with BeautifulSoup
soup = BeautifulSoup(html, "html.parser")
link = soup.select_one("body > a")
link.get_text()     # 'My link'
link["href"]        # 'page2.html'

# 2. XPath, with lxml
lh.fromstring(html).xpath("//a/@href")
# ['page2.html']

# 3. regular expression, on the raw text
re.findall(r'<a href="([^"]*)">', html)
# ['page2.html']

CSS-селекторы и XPath идут по дереву: body > a — это «a, которое является потомком body», //a/@href — «атрибут href любого a»; до атрибута добираются через @ или ["href"], а не спускаясь на уровень ниже (рис. 3). Регулярное выражение читает сырой текст, не видя вложенности, и работает, только пока HTML написан ровно так, как ожидает шаблон. Отсюда слайд (p. 1529): "Since HTML code is tagged text, any tool that allows to manipulate and process text could be potentially used to parse a page" — именно potentially, «в принципе»; парсер, строящий дерево, надёжнее.

Скрапинг восстанавливает структуру из вёрстки: DOM — дерево, по которому он ходит, а селектор — путь в этом дереве.

Статическая или динамическая: когда скачать страницу недостаточно

Для статической страницы скрапинг занимает два шага (p. 1530): "retrieving a static page from the Web" — через "curl, using command line" или "requests, using Python scripts", — а потом парсинг шаблонами из предыдущего раздела (в лекции другой группы перечислены только XPath и регулярные выражения, p. 1542). Возьмём маленькую страницу ресторана, отзывы с которой тебе нужны, — Trattoria Rossi, придуманную для этого урока:

# step 1, from the command line: download the page into a file
curl -s "https://example.com/trattoria-rossi" -o page.html
# steps 1 and 2 in Python: download, then parse
import requests
from bs4 import BeautifulSoup

r = requests.get("https://example.com/trattoria-rossi")
soup = BeautifulSoup(r.text, "html.parser")
# one element per review in the page
reviews = soup.select("div#reviews > p.review")

Дальше идёт фраза, вокруг которой крутится вторая половина занятия: "Most websites have dynamic-generated content: downloading and parsing the HTML page could not be sufficient" (p. 1529). Браузер показывает тебе DOM после того, как отработал JavaScript страницы; requests скачивает текст, который прислал сервер, до запуска любого скрипта — это не браузер, он ничего не выполняет. Когда скрипт заполняет страницу после загрузки, отзывов, которые ты видишь, в скачанном просто нет (рис. 4).

«Динамическая страница — это страница, которую генерирует программа на сервере». Для скрапера — нет: страница, которую сервер написал до отправки, с точки зрения скрапера статическая — содержимое есть в скачанном. Проблема — содержимое, которое строится в браузере, JavaScript-ом, после загрузки. Лекция говорит "dynamic" в трёх смыслах: "dynamic-generated content" (p. 1529), содержимое, которое подгружается по клику или прокрутке (p. 1531), и "Dynamic Websites", чей HTML "changes over time" (p. 1537). А "could not be sufficient" значит "may not be sufficient" — «может оказаться недостаточно».

Следующий слайд задаёт два вопроса, на которые простое скачивание не отвечает (p. 1531): "What happens if we want to obtain pages in sequence (e.g.: pages of reviews from Amazon or TripAdvisor)?" и "What we need to do if the page loads the content we need only after clicking a specific field or while scrolling the page itself (e.g.: Facebook and Instagram posts)?"

Три модуля, три работы

"Python is one of the best languages to build scrapers: it is easy to learn, fast to code and it has plenty of libraries to get anything done efficiently" (p. 1532). Лекция представляет три из них.

Происхождение Selenium объясняет, почему он отвечает на оба вопроса со слайда (p. 1531): инструмент для тестирования должен делать то же, что пользователь, поэтому он управляет настоящим браузером — браузер выполняет скрипты, Selenium нажимает «дальше» или прокручивает, и DOM, который он читает в конце, — уже отрисованный. Передача в BeautifulSoup — одна строка, driver.page_source:

# the dynamic page: a real browser loads it, BeautifulSoup parses
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC
from bs4 import BeautifulSoup

# start a real browser and open the page
driver = webdriver.Chrome()
driver.get("https://example.com/trattoria-rossi")
# wait (at most 10 s) until the script has added a review
WebDriverWait(driver, 10).until(
    EC.presence_of_element_located((By.CSS_SELECTOR, "p.review")))
# hand the rendered page to the parser
soup = BeautifulSoup(driver.page_source, "html.parser")
driver.quit()
reviews = soup.select("div#reviews > p.review")

Статическая или динамическая?

Страница Trattoria Rossi в трёх версиях и два скрапера. В статической версии сервер вписывает отзывы прямо в HTML; в динамических он присылает пустой div#reviews и скрипт, который запрашивает отзывы после загрузки страницы, — а в последней ещё по три отзыва при каждой прокрутке. Выбери страницу и скрапер и пройди каждый шаг: что было прислано, что выполнилось и что в итоге досталось BeautifulSoup.

  1. Главная мысль: скрапер парсит только то, что ему дали, — requests отдаёт HTML до запуска любого JavaScript, Selenium — страницу после того, как браузер её выполнил. Статическая страница, requests: предскажи, сколько отзывов вернёт soup.select.
    Что должно получиться

    3 из 3, одним HTTP-запросом. Отзывы есть в тексте, который присылает сервер, поэтому двух шагов со слайда (p. 1530) — скачать, распарсить — достаточно.

  2. Переключись на динамическую страницу и оставь requests. Браузер посетителя показывает три отзыва. Предскажи, что найдёт скрапер.
    Что должно получиться

    0 из 3. В скачанном — пустой div#reviews; reviews.js так и не запускается, поэтому запрос к /api/reviews, который принёс бы отзывы, никогда не отправляется. Ничего не сломалось — отзывов просто никогда не было в том, что получил requests.

  3. Теперь переключи скрапер на Selenium. Что изменится и во сколько HTTP-запросов теперь обойдётся скрапинг?
    Что должно получиться

    3 из 3. Браузер загружает страницу, выполняет reviews.js, скрипт просит отзывы у собственного API сайта (JSON) и вставляет их; page_source — это уже такая страница, и BeautifulSoup их находит. Цена — 3 запроса вместо 1: страница, скрипт и вызов API. Заметь, что отзывы приехали как JSON из API — первая половина урока спряталась внутри второй.

  4. Страница с бесконечной прокруткой и Selenium: сколько прокруток нужно, чтобы собрать все 9 отзывов? И что найдёт на этой странице requests?
    Что должно получиться

    Две прокрутки: 3 при загрузке, потом 6, потом 9. Третья прокрутка запрашивает четвёртую порцию и получает пустой список. requests находит 0, и прокручивать он не умеет вовсе: у него нет страницы, только текст. А каждая прокрутка — ещё одно действие, которое сайт может заметить: "repeated scrolling" — пример самого слайда тех "weird behaviours" (странного поведения), которые ловят защиты (p. 1528).

"Three modules are needed to set up a scraper: - BeautifulSoup - Scrapy - Selenium"

Это три модуля, которые курс сочетает, а не три, которые нужны любому скраперу. Какие нужны — зависит от страницы: статической хватит загрузчика (curl или requests) и парсера вроде BeautifulSoup; содержимому, которое отрисовывает JavaScript или которое открывается по клику и прокрутке, нужен браузер под управлением Selenium; много связанных ссылками страниц можно обойти Scrapy или пройти с Selenium.

Собственный рецепт лекции для статической страницы не использует ни Scrapy, ни Selenium (p. 1530), а Scrapy "bith [both] crawls a website and extracts data" (p. 1534), так что может работать без двух других. Две лекции не сходятся даже в числе: у другой группы написано "Two modules are needed to set up a scraper: - Selenium - BeautifulSoup" (p. 1543), а конспект курса называет эту пару "One very popular toolset" (§5.1.3) — популярный выбор, а не требование. Виджет выше показывает, как решает страница: один модуль и requests на статической, Selenium на динамической. Экзамен могут сверять с напечатанной формулировкой, так что знай напечатанные списки — три модуля (p. 1532), два (p. 1543) — и правильное прочтение.

Пайплайн и почему скраперы ломаются

"The image below represents the interactions between the three presented modules: their simple combination is the basis for a web scraper" (p. 1536). Рис. 5 перерисовывает эту картинку с двумя обратными петлями из версии другой группы (p. 1545).

Читай его как «скачать, распарсить, сохранить»: Selenium скачивает, когда странице нужен браузер, Scrapy — когда нужно обойти много страниц, а BeautifulSoup превращает HTML-страницу в распарсенные данные. Петли прямо по названию отвечают на два вопроса со слайда (p. 1531): "get dynamic elements" (кликнуть или прокрутить, потом прочитать снова) и "get another page". Два упрощения: статический путь со слайда (p. 1530) (requests, потом BeautifulSoup) не нарисован, а страница от Scrapy идёт через BeautifulSoup, хотя Scrapy умеет извлекать данные сам.

Хрупкий по своей природе

API — это контракт с именованными полями; страница — это вёрстка, которую владелец может переделать в любую ночь. "Most of the times, the HTML changes over time, especially the classes and sometimes the structure of the HTML. Therefore, it is really important to keep the scraper updated" (p. 1537, "Dynamic Websites" — третий смысл слова). Переименуй класс в div#reviews > p.review — и скрапер вернёт пустой список без всякой ошибки; поэтому конспект курса и называет скраперы очень трудными в поддержке (§5.1.3).

Сайты ещё и защищаются: "Some websites have some protections against scraping. They are able to detect weird behaviours (e.g., repeated scrolling) and prevent you from scraping" (p. 1528). А Selenium нужен "chromedriver" — программа, через которую он управляет браузером, так что их версии должны совпадать: "Check out your Google Chrome/EDGE version", потом "Download and put the correct chromedriver version within the folder" (p. 1538). Начиная с версии 4.6 Selenium сам скачивает подходящий драйвер (справка).

Слайды перечисляют защиты, но не правила; конспект курса предупреждает, что "many website providers don't allow scraping, so you could run into legal problems if you do" (§5.1.3). Хорошая практика: прочитай условия использования и robots.txt сайта, не торопи запросы, честно представляй свой клиент и обращайся с персональными данными так, как требует закон о приватности (в ЕС — GDPR).

Кто написал URL из разминки

Вернёмся к разминке. Её раскодированный хвост — это ровно тот текст, который JavaScript выдаёт для даты (попробуй new Date().toString() в консоли браузера на английском языке и с итальянским временем), а %20 вместо каждого пробела при нетронутых : и + — ровно то, что делает из него encodeURI в JavaScript. Значит, этот URL написала программа на JavaScript — скорее всего, сама веб-страница ViaggiaTreno, которая после загрузки спрашивала у своего сервера отправления. Занятие показывает вызов, но не то, как его нашли; это прочтение — наше.

Если прочтение верное, это динамическая страница со слайда (p. 1529), увиденная изнутри: табло, заполняемое таким способом, приходит в браузер пустой рамкой, и requests.get получает только рамку. Выхода два: управлять браузером через Selenium и парсить то, что он отрисует, или вызвать тот же API, который вызывает сама страница, — как и сделали на занятии. Когда вызов виден, второй путь проще и надёжнее: именованные поля вместо вёрстки, и ничего не ломается, когда переименовывают CSS-класс.

Если API есть — бери API; если скрапишь — скачивай самым простым инструментом, который видит данные, парси BeautifulSoup и будь готов поддерживать скрапер.

True or false: "As an end-user, the most used requests for APIs are GET requests."

  • True Слово в слово со слайда (p. 1511). Конечный пользователь в основном потребляет данные, а GET — метод, который читает.
  • False POST, PUT и DELETE создают, обновляют и удаляют; тот, кто собирает данные, в основном читает, а чтение — это GET.
Показать образец ответа

True. APIs are invoked through HTTP methods depending on the kind of operation; an end-user mostly retrieves data, and retrieval is a GET request, which can be written as a single URL (as in the iTunes and ViaggiaTreno examples).

Фраза взята со слайда, так что вопрос «верно/неверно» может использовать её как есть. Если она вернётся как открытый вопрос, добавь причину: метод несёт намерение операции.

Consider the request https://itunes.apple.com/search?term=maroon&entity=allArtist&attribute=allArtistTerm&limit=10, shown in the exercise session on APIs. Identify the scheme, the host, the path and the query parameters, explain what limit=10 does, and describe the structure of the answer.

Показать образец ответа

It is a GET request to a web API. The scheme is https, the host is itunes.apple.com (the server that answers) and the path is /search (the service called). After the question mark comes the query string: four key=value pairs separated by ampersands — term=maroon, the text searched for; entity=allArtist, the kind of object returned (artists); attribute=allArtistTerm, the field the term is matched against (the artist's name); limit=10, the maximum number of results. The answer is a JSON object with resultCount, here 10 because of the limit, and results, an array of artist objects with named fields such as artistName, artistId and primaryGenreName — the first two are Maroon 5 and Maroon. Records of the same answer may have different fields. Special characters inside a value must be percent-encoded, for example %20 for a space.

Назови все четыре части URL их терминами, потом покажи, что понимаешь каждый параметр как инструкцию серверу. Сказать, что ответ — «веб-страница», значит упустить смысл API: он возвращает данные, JSON, для программ.

In the Trenitalia ViaggiaTreno example, the autocompletion for train 798 returns the lines 798 - SALERNO - 04/11/25|798-S09818-1762210800000 and 798 - SALERNO - 05/11/25|798-S09818-1762297200000. Explain the structure of these lines, what the number 1762210800000 represents, why the two numbers differ by 86400000, and how the result is used in the next request.

Показать образец ответа

Left of the vertical bar is a label for people: train number, origin station and date. Right of it is a key for programs: train number, station code (S09818, Salerno) and departure day, separated by dashes. The day is written as epoch time in milliseconds, the number of milliseconds since 1 January 1970, 00:00 UTC: 1762210800000 is the midnight of 4 November 2025 in Italian time (23:00 UTC on 3 November). One day lasts 24 × 3600 × 1000 = 86 400 000 ms, so the second key is the next day, 5 November. The parts of the key are then placed in the path of the second call, andamentoTreno/S09818/798/1762210800000 (station, train, day), which returns the status of that run of the train in JSON — for example category ICN, duration 14:35, arrived. It is a two-step workflow in which the first call provides the identifiers needed by the second, and the parameters travel in the path rather than in a query string.

Три вещи, которые надо сказать правильно: число — это день, а не время отправления; единица — миллисекунды, а не секунды; и ключ питает следующий вызов. Слайды печатают числа без объяснений — вывод в этом уроке наш, и он сходится цифра в цифру.

What is web scraping? How does it differ from web crawling, and when is scraping the appropriate way to collect data?

Показать образец ответа

Web scraping is the automated process of extracting data from websites and organizing it into a structured format, such as a spreadsheet or a database. Programs called scrapers pull information such as text, prices or images from the HTML code of web pages, for later analysis. Web crawling, used by search engines to index web content, is about visiting pages by following links; scraping is about extracting data from them. The two can be combined: Scrapy both crawls a website and extracts data. Scraping is appropriate for websites with valuable content and no official API — social networks, retailers, events, train schedules — and it should be a last resort: when an API exists it provides structured, documented data, while scrapers break when the HTML changes and websites may detect and block them.

Ядро — определение со слайда (p. 1523); противопоставление обходу сайтов (crawling) — классический дополнительный вопрос. Аргумент про "last resort" (поддержка, защиты) показывает, что ты знаешь, почему API предпочтительнее.

What is the Document Object Model (DOM), what does it define, and why does it matter for web scraping?

Показать образец ответа

The W3C DOM is a platform- and language-neutral interface that allows programs and scripts to dynamically access and update the content, structure and style of a document — a standard for how to get, change, add or delete HTML elements. When a web page is loaded, the browser creates the DOM of the page. It defines the HTML elements as objects, the properties of all HTML elements, the methods to access them and their events. It is a tree: the document, the root element html, the elements head and body, their child elements, and text nodes as leaves; attributes such as href are attached to their element. For scraping it matters because parsers such as BeautifulSoup build the same tree from the HTML, and selectors (CSS selectors, XPath) are paths in it; and because scripts can update the DOM after loading, the HTML that is downloaded can differ from what the browser shows.

Процитируй определение, перечисли четыре вещи, которые определяет DOM (p. 1525), и добавь связь со скрапингом — именно последняя фраза превращает заученное определение в понимание.

Why may downloading and parsing the HTML of a page not be sufficient to extract its content? Which tool does the exercise session propose, and why that tool?

Показать образец ответа

Most websites have dynamically generated content: the HTML returned by the server (and downloaded with curl or requests) is the page before its JavaScript runs, and the content may be loaded by scripts only after the page has loaded, after a click on a specific field, or while scrolling (for example Facebook and Instagram posts); content may also be split over pages in sequence (pages of reviews on Amazon or TripAdvisor). A plain download does not contain that content and cannot click or scroll. The session proposes Selenium, a module developed for automating website testing: it drives a real browser and simulates clicks, drags, scrolls and any other interaction, so it retrieves data that is not loaded with the source page and navigates several pages. The rendered page is then passed to BeautifulSoup, the parser that extracts the data after the page is fully loaded.

Решающее слово — "browser": Selenium работает, потому что скрипты выполняет браузер. Ответ, где сказано только «используй Selenium», без объяснения, почему скачанное пусто, упускает механизм, который проверяет экзаменатор.

Which of the following statements about the scraping tools presented in the exercise session are correct? Select all that apply.

  • BeautifulSoup is an HTML (and XML) parser, used to extract data after the page is fully loaded; it does not download pages itself. Слайд (p. 1533): он ходит по документу, который скачал кто-то другой.
  • Selenium was developed to parse HTML documents faster than BeautifulSoup. Selenium создан для автоматизации тестирования сайтов: он имитирует клики, перетаскивания и прокрутку в браузере (p. 1535). Парсинг — работа BeautifulSoup.
  • Scrapy is a Python framework that both crawls a website and extracts data. Слайд (p. 1534): фреймворк для обхода сайтов и извлечения данных, для создания скраперов и пауков (spiders).
  • curl and requests extract data from a page by means of CSS selectors. Они скачивают страницу (p. 1530); извлечение через CSS-селекторы, регулярные выражения или XPath — отдельный шаг, парсинг.
  • Selenium is used to retrieve data that is not loaded with the source page, or to navigate several pages of a site. Почти слово в слово со слайда (p. 1535).
  • Once a scraper works, it keeps working as long as the website is online. HTML со временем меняется, особенно классы, поэтому скрапер надо поддерживать в актуальном состоянии (p. 1537); к тому же сайты могут его распознать и заблокировать (p. 1528).
Показать образец ответа

The first, third and fifth statements are correct. In the pipeline of the session, Selenium or Scrapy obtains the HTML page from the Internet, BeautifulSoup parses it, and the result is the parsed data.

Два неверных варианта меняют местами роли двух инструментов или двух шагов — автоматизация браузера против парсинга, скачивание против парсинга; последний забывает, что HTML меняется и что сайты распознают скраперы. За неправильные ответы может быть штраф, так что отмечай только то, что можешь обосновать слайдом.

Проверь себя

В запросе со слайда (p. 1513) ты меняешь limit=10 на limit=3 и больше ничего. Что придёт в ответ?

  • resultCount, равный 10, но в results только третий артист limit — не индекс: он ограничивает, сколько результатов придёт, а не выбирает один из них.
  • resultCount, равный 3, и три объекта-артиста в results Каждая пара — одна инструкция; эта ограничивает число результатов, а resultCount считает то, что пришло.
  • resultCount, равный 3, а в results по-прежнему все десять объектов resultCount считает объекты в results; эти два числа всегда совпадают.
  • Ошибка: сервис ожидает ровно 10 10 на слайде — просто значение, которое выбрали на занятии; любое значение до максимума сервиса — корректный запрос.

Вызов со слайда (p. 1514) просит entity=movieArtist, но его первый результат, Frank Stallone, имеет "artistType": "Artist" и жанр Pop, а ещё у него есть amgArtistId, которого нет у Sylvester Stallone. Какой вывод правильный?

  • Ответ повреждён, и его надо выбросить Это корректный JSON; записям одного ответа просто разрешено различаться.
  • API фильтрует по фамилии, как сказано в подписи к слайду Ключа «фамилия» нет: term — полнотекстовый поиск по именам. Подпись сообщает намерение, а не механизм.
  • Запрос задаёт форму поиска, но получаешь ты то, что содержит ответ: читай записи и проверяй, что поле есть, прежде чем его использовать Сам скриншот показывает оба факта: музыкальный артист среди результатов и поле, которое в одной записи есть, а в следующей нет.
  • Ключ entity вообще ни на что не влияет Один вызов этого показать не может: Sylvester и Sistine Stallone — артисты кино. Он показывает лишь, что параметр не отсёк всех остальных артистов.

Какие из этих страниц можно соскрапить одними requests и BeautifulSoup? Выбери все подходящие.

  • Страницу, отзывы на которой PHP-программа вписывает в HTML на сервере до отправки Сгенерировано на сервере — значит, уже есть в скачанном: с точки зрения скрапера страница статическая.
  • Страницу, посты на которой появляются только при прокрутке Кто-то должен прокручивать и выполнять скрипт, который подгружает следующие посты: браузер под управлением Selenium (p. 1531).
  • Страницу, скрипт которой после загрузки заполняет пустой div отзывами requests не выполняет скриптов, так что в полученном div остаётся пустым: это динамическая страница из виджета.
  • Простую HTML-страницу с таблицей расписания поездов Скачать, потом распарсить: двух шагов со слайда (p. 1530) достаточно.

Критерий — не то, как страница была создана, а есть ли содержимое в тексте, который присылает сервер.

В дереве DOM со слайда (p. 1526) рамка "Attribute: "href"" соединена с "Element: <a>" горизонтальной линией, а не висит под ним. О чём это говорит?

  • Атрибут принадлежит элементу, но не является одним из его дочерних узлов Поэтому его читают у самого элемента — @href в XPath, tag["href"] в BeautifulSoup, — а не находят, спускаясь по дереву.
  • Атрибут — элемент-сосед (sibling) для <a> Это вообще не элемент; соседи <a> — элементы вроде <h1>.
  • Атрибут — родитель <a> Родитель <a> — это <body>, он выше.
  • Атрибут — текстовый узел Текстовый узел <a> — это "My link", он ниже; href — цель ссылки, а не её текст.

ViaggiaTreno обозначает день числом миллисекунд эпохи для его полуночи по итальянскому времени. 5 ноября 2025 года — это 1762297200000. Какое число обозначает 6 ноября 2025 года?

  • 1762297286400 Здесь прибавлено 86 400 — секунды суток, прочитанные как миллисекунды: на 86.4 секунды позже.
  • 1762297200001 На одну миллисекунду позже — всё ещё 5 ноября.
  • 1763161200000 Здесь прибавлено 864 000 000 ms, лишний ноль: десять дней.
  • 1762383600000 Плюс 24 × 3600 × 1000 = 86 400 000 ms, ровно одни сутки.

Скрапер месяцами работал нормально; теперь он возвращает пустые списки, хотя в браузере страница по-прежнему показывает данные. На какую причину указывает слайд "Dynamic Websites"?

  • Сервер удалил свои данные Тогда и браузер бы их не показывал.
  • Сайт изменил свой HTML — имя класса или структуру, — и селекторы больше не совпадают Слайд (p. 1537): "the HTML changes over time, especially the classes", поэтому скрапер надо поддерживать в актуальном состоянии.
  • Вышла новая версия API Скрапер не пользуется API; версии — риск клиентов API, история с Twitter (p. 1518).
  • BeautifulSoup может распарсить страницу только один раз У парсера нет памяти о прежних страницах; он парсит любой текст, который ему дали.

Какой из трёх модулей сам никогда ничего не скачивает?

  • Selenium Он управляет браузером, а браузер загружает страницы и скрипты.
  • Scrapy Он обходит сайт: запрашивает страницы и переходит по их ссылкам.
  • BeautifulSoup Парсер: он получает HTML от requests, Scrapy или Selenium, "after the page is fully loaded" (p. 1533).
  • Ни один: скачивают все три BeautifulSoup только парсит текст, который скачал другой инструмент.

Главное

  • API — набор правил и протоколов, через которые приложения общаются и обмениваются данными; веб-API вызывают по HTTP методом и URL, и он отвечает данными для программ, обычно JSON. Конечные пользователи в основном отправляют GET-запросы, а Postman показывает четыре части запроса: коллекцию, строку запроса, параметры, результат.
  • URL читается как scheme://host/path?key=value&key=value: каждая пара — одна инструкция серверу, зарезервированные символы внутри значения кодируются через percent-encoding (%20 — пробел, %26 — амперсанд), а некоторые API, например ViaggiaTreno, кладут параметры в путь.
  • Читай ответ, а не подпись: iTunes возвращает resultCount и массив results, записи которого не обязаны иметь одинаковые поля; ViaggiaTreno возвращает ключ, который питает следующий вызов, а день записан в миллисекундах эпохи (одни сутки = 86 400 000 ms).
  • У API есть правила, и они меняются: Twitter v1 был бесплатным и открытым и давал твиты за последнюю неделю, v2 требует авторизации для каждого приложения и даёт доступ к старым твитам. Ключи, пагинация, rate limits и коды статуса — часть работы с реальными API.
  • Веб-скрапинг — автоматическое извлечение данных из HTML веб-страниц в структурированный формат (crawling ходит по ссылкам, scraping извлекает), и это вход, когда у сайта ценное содержимое и нет API. DOM — дерево страницы, которое строит браузер, а CSS-селекторы и XPath — пути в нём.
  • Статической странице нужны два шага: скачать (curl, requests) и распарсить (CSS-селекторы, регулярные выражения, XPath). Содержимому, которое отрисовывает JavaScript или которое подгружается по клику или прокрутке, нужен Selenium: он управляет настоящим браузером и умеет проходить страницы по порядку; BeautifulSoup парсит, Scrapy обходит и извлекает.
  • Скраперы хрупкие: классы и структура HTML меняются, поэтому их надо поддерживать, а сайты распознают поведение вроде многократной прокрутки. Если API есть — бери API; часто это тот самый API, который вызывает сама страница.
